## 必修问题

### P2-1：跨越Markdown inline代码边界，把别的工具参数当编译Target

位置：`collectLiteralCompileTargets`，受审版本第578–602行，特别是第596行只用 `;|&` 分割参数。

输入：

```text
`scripts/compile_test.ps1 -Target publish` 与 `build.ps1 -Target custom`
```

实际：报 `unsupported literal compile target alias: custom`。

预期：编译命令只有publish；build.ps1的custom不属于本规则。另一个等价反例是只在散文中提到 `compile_test.ps1`，随后同一行描述build.ps1的参数。

**建议**：以独立Markdown code span/已明确的shell语句为最小证明范围；不要从某个文件名一路扫描到整行末尾。无法明确划界的散文/多命令表达式可降为警告或不作alias判断，避免造完整shell解释器。

### P2-2：shell注释中的历史错误被当现役命令

受审版本第584–602行未剥离注释。

输入：

```powershell
scripts/compile_test.ps1 -Target publish # old -Target levels is invalid
```

实际：报levels错误。HTML注释中的同样命令也被硬拦。

**建议**：对已识别shell代码按引用状态过滤注释；或者把规则进一步收窄到一条可证明的Target参数，复杂内容只警告。新增“正确命令+错误示例注释”误报负例，不应要求用户删掉诊断解释才过门。

### P2-3：Target表格的编译归属延伸过远

受审版本第557、577–581、606–611行。`compileSection`一旦置true，仅遇标题才复位。

输入：

```text
## Tools
`compile_test.ps1 -Target publish`

`build.ps1` 的参数：
| Parameter | Target |
| --- | --- |
| build target | custom |
```

实际：第7行custom被硬拦。

**建议**：只关联紧邻、明确属于编译命令的表格；出现其他工具上下文后解除关联。至少新增该反例；不需要维护全仓所有工具名称清单。

### P2-4：resolver结构变化时会漏掉合法裸case并继续声称别名不存在

受审版本第537–546行只统计带引号case。向真实switch中插入PowerShell合法的：

```powershell
levels { $targetPath = 'levels.xfl' }
```

实际：`parseCompileTargetAliases`仍返回原七个别名而非null，随后合法levels被判unsupported。

这违背注释宣称的“不支持的PowerShell结构返回null，不猜测语义”。

**建议**：有限解析无法证明已读完所有分支时返回不可核对，不输出完备别名断言。无需支持所有PowerShell语法，关键是检测unknown并停止下结论。

### P2-5：无法核对的结构变化目前也是硬错误

受审版本第621与1332行：resolver parse失败返回 `cannot verify`，driver仍一律 `errors.push`。

**建议**：这种情形不能证明文档断言错误，应明确severity=warn；确定的unsupported alias才error。测试须验证CLI/汇总层的severity，不只检查message出现。
