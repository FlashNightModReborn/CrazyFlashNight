## 1. 背景

launcher 有两个**独立**的性能问题，本文档统一处理：

**问题 A — 合成路径卡顿（MPO churn）。** launcher 当前是一个 6~7 个 DWM 顶级 HWND 的窗口栈（GuardianForm + 嵌入的 Flash 子窗口 + WebOverlayForm + WebView2 自己的 Chromium 子 HWND + InputShieldForm + DesktopCursorOverlay + NativePanelBackdrop）。DWM 的 MPO（Multiplane Overlay）planner 面对这种透明窗口层叠栈会反复 promote/demote 叠加平面，每次重配置在 present 队列插一个 stall → 帧时间尖刺、WebView2「假死」。已诊断确认。

**问题 B — Flash 本体单核吃紧。** Flash 是 AVM1，单线程、单核，无多核能力。实测把 Flash 的 `_quality` 从 medium 降到 low 是**目前最有效的提帧杠杆**，单核估算可省 50%+ 开销。

两个问题的解都指向同一件事：**把合成收回 launcher 自己管，并把能 offload 的渲染工作移出 Flash 单核。** 因此合并决策。

> 相邻决策（已固化，不在此展开）：shipping launcher **绝不**写 `OverlayTestMode` 等全局注册表项来治 MPO（杀软/SmartScreen 启发式命中 + 反盗版 Guardian 叠加风险 + Steam 口碑）。生产修复必须**进程作用域**。本架构正是那个"进程作用域修复"。详见 `web-overlay-perf-harness` memory 的 MPO 段 / `tools/mpo/`。

## 2. 当前约束与研究边界

2026-09-22 复核：区分当前实现选择与尚未验证的能力，不把旧推断作为永久技术禁令。

### 2.1 当前继续使用 Adobe 独立播放器（SA）

- 当前捕获、输入桥与数据加载以本仓 SA 为基线，未启动运行时替换。其他运行时必须另验 AVM1、多 SWF、资源/存档与输入兼容性；旧“Ruffle 官方无意支持多 SWF”说法未获本轮证据支持，不再作为排除依据。
- 插件宿主也可以使用独立进程；“进程内嵌入必然与 AVM1 抢同一核”不成立。替换成本来自宿主协议、兼容性、部署与重新验证，不能由进程数量推导。
- 统一玩家看到的窗口及输入归属，不要求把 Flash、Host、WebView2 合并成一个进程；继续保留 Flash 独立进程边界。独立进程也不等于独占物理核。

### 2.2 Adobe SA 播放器的舞台不透明

- 当前 SA 窗口捕获没有可用的世界逐像素 alpha；原生合成 shader 输出 alpha=1。隐藏源窗口、将输出窗口设透明或统一窗口，都不会恢复已与背景混合的像素信息。
- Flash 内部当然存在透明混合；但本项目没有验证从 SA 中间渲染结果导出 RGBA 的入口。已有鼠标输入桥不证明渲染钩子可行。
- 非浏览器透明宿主有历史先例：F-IN-BOX 的 ActiveX 宿主记录了透明模式及带 alpha 位图；这不证明当前 SA 可以零复制输出 RGBA。Windowless transparent 也可能由宿主先绘背景再混合，不等于公开了透明纹理。出处见文末。
- 同一游戏状态下黑/白背景双渲染与色键不同，不要求整治素材用色，但要解决同帧一致性和额外光栅化成本；两次普通连续捕获不能替代。AS2 内 `BitmapData.draw` 也会增加 Flash 端工作。它们是未验证的研究选项，不作为统一合成前置。
- 当前无用色治理，色键不作为默认路线。AI 抠图若参与实时世界拆分，必须另证角色/细小弹体/半透明特效的精度、时序、前景颜色去污染与总开销；静态地图 mask 无法保护飞到天空区域的角色。优先保留确定性素材拆分/离线辅助空间。

### 2.3 最低支持 OS = Win10

- → `Windows.Graphics.Capture`（WGC，Win10 1803+）可用。这是抓取 D3D 加速窗口内容的现代正解。

## 3. 目标架构

### 3.1 一句话

**目标是让游戏内部图层先合成为不透明输出，再交给桌面呈现。** 当前原型使用 C# 宿主 + 同进程 C++ D3D11/WGC 模块；内部图层仍消耗像素填充、带宽和同步成本。仅把多个 DirectComposition visual 放入同一 HWND 不等于已压成单张输出。

减少独立透明顶级窗口是目标之一，不保证 Independent Flip、零 MPO churn 或绕过核显输出。混合显卡上仍可能存在跨适配器传输，收益必须以真实呈现路径复验。

### 3.2 Flash 层 = WGC 抓帧

- Flash 在合成器里是一张**不透明贴图**，来源 = WGC 抓帧。
- **源窗口展示模型待验证**：先用明确 PID/HWND 的可见顶级 Flash 窗口验证 WGC，再分别观察遮挡、屏幕外、隐藏及最小化。2026-09-21 本机原型发现屏幕外/隐藏/最小化可停止捕获更新，旧“只要不最小化就能离屏持续出帧”假设不成立。游戏内原型已采用 Guardian 捕获 + Flash 区域裁切 + 可点击穿透的不透明 GPU 输出；Flash 保持原有嵌入位置，窗口最小化时隐藏输出，恢复等新帧。宿舍点击、面板往返、调色和窗口恢复已有有限实测，战斗手感及完整切屏体验仍须另验。
- **为什么不是现有的 GDI 抓帧**：当前 `GpuRenderer.cs` / `FlashSnapshot.cs` 用 `GetDC` + `BitBlt`。GDI 读的是窗口的 GDI 设备上下文；Flash 开硬件加速后画面走 D3D swapchain present，GDI DC 基本是空的 → **黑帧**。`FlashSnapshot.IsLikelyBlackFrame` 和 `GpuRenderer` 的 10 帧失败 fallback 就是这个问题留下的疤。WGC 抓的是 DWM 合成输出，能正确拿到 D3D 内容。
- 连续显示应保持 GPU 纹理路径。当前仓库 Agent Runtime 的 `WindowsGraphicsCapturePixelProducer` 是带 staging readback 的单帧观察器，不可直接循环调用作为渲染器；原型另外持有长生命周期设备、帧池和交换链，诊断像素读回仅显式采样时执行。

### 3.3 抽象

- 合成器把 Flash 层当一个"贴图源"接口（`IFlashLayerSource` 之类），合成器只管把若干层叠起来。
- 当前只实现 WGC 不透明来源；接口显式表达纹理尺寸、坐标变换、帧/场景身份、有效区域、色彩与 alpha 约定。未来透明来源属于可选能力，未实现时明确报告不支持；不因暂时不透明而把所有图层和后处理写死为单一 Flash 画面。

### 3.4 瓶颈在哪（CPU 还是 GPU）

**瓶颈必须测量，不能预先排除吞吐或跨卡传输。**

- 图层合成、捕获复制、后处理和最终呈现分别计成本；核显、独显和混合呈现可能得到不同结果。
- 真正的成本与风险是 **帧步进 / 多时钟域同步**：Flash（SWF 帧率，常 30）、WebView（cap 60）、显示器（可达 240）三个时钟域。自建合成器后你就拥有了这个问题 —— 这是 **CPU 侧的调度问题**，不是吞吐问题。
- 抓帧获取必须 **latest-frame-wins、绝不阻塞**；阻塞式等捕获 fence 会自造 stall（和 MPO churn 同一类病）。
- 增量延迟尚未实测；WGC 帧时间戳到取帧的差值不等于输入到显示延迟，不能承诺固定增加一两帧。

**这笔交易的本质**：把一个看不见、不可控的 DWM 调度问题（MPO churn），换成一个看得见、可 profile、可修的进程内调度问题（帧步进）。这是好交易 —— 你能修自己的调度器，修不了 DWM 的 MPO planner。

### 3.5 WebView2 层 = 合成器方案的承重柱

Flash WGC 只是半边终局。若 WebView2 仍以当前形态存在（`WebOverlayForm` 顶级透明窗 + WebView2 Chromium 子 HWND + `InputShieldForm` 命中窗），DWM 仍会看到多个顶级/分层窗口，"1 个可见不透明 flip 窗口"就没有真正达成。因此 WebView2 如何进入合成器，是本方案最重要的承重柱级问题。

候选路线：

| 路线 | 定位 | 风险 |
|---|---|---|
| `CoreWebView2CompositionController` | 官方正路：WebView2 输出接入 DirectComposition / Windows.UI.Composition visual tree | 不能直接复用 WinForms `WebView2` 控件；需要自己转发鼠标/指针/焦点、处理 IME/拖拽/可访问性、补齐 crash recovery 与 DevTools 入口；当前 WebView2 SDK 版本也要核对是否需要升级 |
| 保留 WebView2 HWND，但先塌 overlay 数量 | 近期风险对冲：不追求终局，只先把 MPO churn 的窗口栈削薄 | 仍不是单一 flip 窗口；DWM 可能仍有透明 overlay 成本，但如果高 churn 只来自 3~4 个分层顶级 overlay，这条可能先把主要尖刺压下去 |
| Native HUD 继续迁移，WebView2 只承担 opaque panel | 把常驻半透明 HUD 从 WebView2 移走，WebView2 只在全屏/不透明面板时出现 | 需要继续迁移运行态 UI；短期功能面较广 |
| 抓 WebView2 成贴图再合成 | 理论兜底，不建议作为首选 | 捕获链路、输入回灌、帧同步、延迟和复制成本都会叠加；比 `CompositionController` 更像绕远路 |

**判据**：终局施工前必须有一个单独 spike 回答 WebView2 composition 是否可用，至少覆盖透明背景、CSS 动画/视频、CDP 输入注入替代或保留策略、键盘焦点、IME、DevTools、WebView2 renderer crash 后恢复、DPI/多屏与 panel 模式。没有这个 spike，"自建合成器"只能算 Flash 侧实验，不能算完整架构方案。

### 3.6 合成技术栈选择

2026-09-21 当前 launcher 已为 `net10.0-windows + WinForms`，含用于适配器枚举的 Vortice.DXGI。此前 net462/C#5 的限制已过时。此次原型选择 C# 宿主 + 小型 C++/WinRT/D3D11 DLL，复用本机 MSVC/Windows SDK，不新增 NuGet 图形依赖；这不是认定现代 C# 图形绑定不可用。以下保留历史选型理由，不能据此要求再做一次 .NET 迁移：

- SharpDX 仓库已归档且只读；`SharpDX.DirectComposition` 4.2.0 包最后更新时间停在 2018-08-24。
- SharpDX 对现代 DirectComposition / WGC / WebView2 composition interop 的覆盖不够可靠，遇到 COM interop 边角会很快变成维护泥潭。
- Microsoft 对 Win10 桌面新合成路线更推荐 Windows.UI.Composition；但在 net462/C#5 下直接接这套 API 也不是无成本。

可选技术底座：

1. **小型 native C++ bridge DLL**：由 C++ 持有 D3D11/DXGI/DirectComposition/WGC/WebView2 composition 的底层对象，C# 只发控制命令与接收状态。最符合当前 net462 现实，也最容易拿到官方头文件和 COM 接口。
2. **Windows.UI.Composition / WinRT 路线**：符合 Win10 之后的推荐方向，但要评估 net462 投影、打包、部署和 WinForms 互操作成本。
3. **迁到现代 .NET 后用 Vortice/TerraFX**：绑定更现代，但 Vortice.DirectComposition 当前目标是 net8/net9/net10，TerraFX.Interop.Windows 当前目标是 net10；这条是"框架迁移 + 渲染重写"组合拳，不是对现有工程的 drop-in 替换。

**当前倾向**：先以已选原型验证捕获与呈现，正式合成底座再按结果确定；不扩张 SharpDX，不重复 .NET 迁移。

## 4. 三大杠杆

### 杠杆 1 — `_quality` = LOW + GPU 后处理（头号 CPU 杠杆）

这是**合成器存在的第一理由**。实测 `_quality` medium→low 是最强提帧杠杆、单核省 50%+。

**数据出处要写清楚**：`scripts/类定义/org/flashNight/neur/PerformanceOptimizer/paper.md` / `paper_cn.md` 是历史性能调参论文，里面的 Kalman/PID/四级调度实现已经与当前代码脱节；当前权威实现是 C# `PerfDecisionEngine` + AS2 `PerformanceScheduler.applyFromLauncher` + `PerformanceActuator` 的二级 tier/softU。论文仍有价值的是实测数据与当时对 `_quality=LOW` 收益的定量确认。`figures/derived_metrics.json` 记录了开环 L0 基线 mean FPS 约 17.16、低于 20 FPS 比例 93.3%；闭环样本 mean FPS 约 26.86、低于 20 FPS 比例 8.7%。这些数据只能证明"降画质杠杆很大且值得工程化"，**不能**拿来复活旧 Kalman/PID 设计。

- `_quality` 只影响光栅化器，**不碰 AVM1**。所以省的是主线程里光栅化那一段；收益最大的恰好是视觉密集场景（密集伤害数字、战斗 VFX）—— 也正是会卡的那些。
- 思路：Flash 跑 LOW（省核），GPU 侧后处理把画质补回来 —— AA 这件事从 Flash 单核搬到 GPU。GPU 后处理一个 pass 在 1080p 下约 0.1~0.3ms，弱核显也无所谓。**CPU 轴上 50%+ 一分不还。**
- **诚实的限度**：后处理是"重建"不是"还原"。AA 是创造信息（亚像素覆盖率），`_quality=LOW` 时这个覆盖率根本没被算出来。后处理只能检测边缘 + 猜测性平滑。**LOW + 后 AA ≈ 介于 LOW 和 MEDIUM 之间**，不等于 MEDIUM。能否接受要弱机肉眼验收。

> **关键纠正**：现有 `GpuRenderer` 的着色器是 **CAS（锐化）**。`_quality=LOW` 的病是**锯齿**，锐化会**放大**锯齿 —— CAS 单用对这个杠杆是**错的工具**。
>
> 两个独立杠杆，要配不同的后处理：
> | 杠杆 | 伪影 | 对的后处理 |
> |---|---|---|
> | `_quality` → LOW | 原生分辨率锯齿 | **后 AA：SMAA / FXAA** |
> | 降低渲染分辨率 | 模糊 / 块感 | **升采样 + 锐化：EASU + CAS（FSR1 配方）** ← 现有 CAS 属这条 |
>
> 最可能的最优解是**两杠杆叠加**：Flash 渲染又小又 LOW → GPU EASU 升采样（升采样滤波本身糊掉一部分锯齿）→ CAS 锐化。具体按实测定。

- **文字 / 伤害数字迁到 web overlay**：`_quality=LOW` 最难看的是文字（无字体 AA），而后 AA 对小字恰恰最弱（FXAA 会把小字糊坏）。把伤害数字、UI 文字迁到 web overlay 渲染 —— 那边不受 Flash `_quality` 影响、永远清晰；顺带卸掉 Flash 的 glyph 光栅化负载，与 50% 杠杆叠加。

### 杠杆 2 — 外部背景（边界受限）

意图：把复杂后景的渲染移出 Flash 单核，让 C#/web 在别的核/GPU 上渲。

- **当前约束**：玩家飞行能力极强，一般关不能假设角色始终在天空区域之外。“外部背景透出 gameplay”需要可靠的逐像素透明度/遮挡信息，当前捕获没有提供。
- **结论**：
  - **一般关**：在透明度/遮挡来源通过验证前，背景留在 Flash；统一合成不自动解除这一条件。动态分辨率和画质调度继续独立生效。
  - **外部丰富背景只限演出关**（见第 5 节）—— 那里禁用飞行能力合情合理，背景区与角色活动区可分离。

### 杠杆 3 — 接缝（外部层与 Flash 层如何拼）

仅在演出关/有外部层时涉及。两条诚实的路：

- **作者区域 mask**：外部渲染只在场景作者标注的有界区域可见（电梯舷窗外、墙上一块屏）。边界是不透明 Flash 美术框，硬边、**零抠像伪影**。约束：角色不能进入该区域。
- **抠像（chroma key）**：外部层透到所有 sprite 之后。`_quality=LOW` 让矢量边变硬 → 矢量内容键得干净；但**位图 sprite 的烘焙 alpha、辉光/加色 VFX 仍会镶边**（CF7 有位图素材）。背景又暗又乱时 halo 不显眼。属"流媒体级"质量，需肉眼验收 + 美术规避。

## 5. 演出层（延后）

把丰富/动态背景做成"演出"—— 甚至用玩家的战斗操作实时驱动另一款开源游戏（如 FreeDOOM）当背景，给演出"升维"。

- **定位**：演出关、禁用飞行。演出为代入感服务，**不考核玩家操作**，因此可松耦合、延迟可接受。
- **选定传输**：RTMP/FLV 直播流入 Flash（AS2 内建 `NetConnection`/`NetStream` + `Video` 对象）。
  - **为什么是它**：`Video` 是 AS2 原生显示列表部件 —— 背景能与 AS2 UI 自由交错、由 Flash 自己的渲染器正确合成（真 alpha 混合，无抠像伪影），相当于"背后放一块大屏幕显示器"。这种集成性是 C# 侧合成给不了的。RTMP/FLV 是 AS2 成熟可靠的内建路线。
  - **代价/待测**：RTMP 是带缓冲的流媒体传输，结构性带延迟（实时端到端几百 ms 起步）—— 松耦合下可接受。**关键待测项**：Flash 侧实时视频解码成本落在 Flash 进程，会吃问题 B 正在优化的那个核。因此演出层**必须**排在游戏本体优化之后，且届时实测解码成本。
- **被否的替代**：把外部游戏做成 C# 合成器的原生层（低延迟、不吃 Flash 核）—— 技术上更优，但牺牲了"AS2 原生部件集成"。鉴于演出可松耦合，作者选择了集成性优先。若未来某个演出需要**跟手**的强耦合，再单独评估这条。

## 6. 被否决的方案及理由（防止重新捡起）

| 方案 | 否决理由 |
|---|---|
| 当前阶段替换 Flash 运行时或插件宿主 | 未完成兼容性/部署验证，不纳入统一合成前置；不是永久否决其能力（§2.1） |
| 当前阶段依赖 Flash 真 soft-alpha | SA 可用输出入口未验证；保留后续研究，不能声称播放器内部从未计算 alpha（§2.2） |
| GDI BitBlt/PrintWindow 抓 Flash | 读不了 D3D 加速内容 → 黑帧（§3.2） |
| 仅用静态区域 mask 在一般关做外部背景透出 | 无法正确保留进入天空区域的角色/特效；需要动态遮挡来源（杠杆 2） |
| shipping launcher 写 OverlayTestMode 治 MPO | 全局/持久/未公开设置，AV 启发式 + Guardian 叠加风险（§1 注） |
| 继续把 SharpDX 扩张为长期合成底座 | 项目已归档、DirectComposition/WGC/WebView2 composition 覆盖不足；只保留为现有实验代码的战术遗留（§3.6） |

## 7. 施工顺序与关键判据

2026-09-22 后续优先级正在按 §7.2 评估调整：统一合成与输入优先于新增粒子和天空拆分。以下 2026-09-21 段落记录已启动阶段的范围，不能据此跳过本次顺序讨论直接开始粒子施工。

**2026-09-21 当前顺序**：连续捕获 → GPU 原样呈现/颜色矩阵 → 源窗口状态与恢复 → 真实游戏输入/显示替换 → 天气粒子与光照 → 其他显示层。时间、奖励、夜视判定继续归 AS2；天空、地图与角色遮挡首期留在 Flash。粒子可独立准备，完整 WebView2/HUD 合并不作为最小天气原型前置。第二阶段开发构建默认启用捕获合成，临时“其他 → 测试”开关退役；AS2 保留逻辑权威，世界/天空整体光照改为轻量状态投影与 GPU 矩阵。天空渐变/粒子仍在 AS2，曲线/LUT 预设工具不作为迁移门槛；仍使用配套开发构建而非正式 runtime。人工节点集中于真正可玩构建的操作手感和天气可见度，不为编译、黑帧定位或机器报告要求人验。下面的 2026-05 顺序保留为历史路线，已由本段更新当前排期。

施工要拆成两条线：**终局线**解决"一个可见 flip 窗口"，**风险对冲线**先验证"少几个 overlay 是否已经足够治 MPO churn"。不要让终局合成器阻塞近期可落袋收益。

1. **游戏本体性能优化优先**，演出层延后。
2. **零成本预检**（可先于一切）：直接把 `_quality=LOW`、不加任何后处理，在弱机上肉眼看一眼。横版动作运动量大，裸 LOW 或许已勉强可接受 —— 若如此，不赌后处理就能先落袋一部分。
3. **spike B（成败命门）**：`_quality=LOW` 的 Flash + SMAA（或 低分辨率 + EASU/CAS）在**弱机**上跑、肉眼验收。后处理若压不住 LOW 的伪影 → 50% 不可落袋 —— 这是整个架构 ROI 的命门，**要最早证伪**。
4. **spike B0：Overlay Count Collapse（兜底绕路）**。目标不是终局合成器，而是先把最会 churn MPO 的 3~4 个分层顶级 overlay 合并：
   - `WebOverlayForm + InputShieldForm` 优先合并成一个顶级 overlay，命中区用 `WM_NCHITTEST` / panel hit rect / CDP 输入注入控制，避免再叠一层命中窗。
   - `DesktopCursorOverlay` 尽量并入同一个 overlay 或 Native HUD；若 cursor 延迟因此变差，再保留独立路径。
   - `NativePanelBackdrop` 并入同一个 overlay，或改成 GuardianForm 客户区里的 opaque panel/backdrop。
   - **注意 airspace**：把所有东西塞进 `GuardianForm` 客户区会撞 Win32 child-window z-order/透明/airspace 限制；从风险上看，"一个顶级分层 overlay"通常比"全塞客户区"更现实。
   - 判据：顶级 layered HWND 数量明显下降、MPO present 尖刺下降、WebView2 假死消失或显著减轻、panel/hover/拖拽/ESC/输入穿透不回归。
5. **spike A：off-screen Flash + WGC**。验证 off-screen 顶级窗口 + WGC 抓帧干净（无黑帧、无冻结、延迟可控），同时复核焦点、Alt-Tab、DPI、最小化/恢复、Flash watchdog 与 PostMessage 输入转发。
6. **spike C：WebView2 composition**。验证 `CoreWebView2CompositionController` 或等价路线是否能进入同一 visual tree；若失败，终局线必须重新设计，不能假装只剩 Flash WGC。
7. **spike D：技术底座**。在 SharpDX、native bridge、WinRT/Windows.UI.Composition、现代 .NET 迁移之间做一次小样，不通过小样不进入大重写。

### 7.1 2026-09-21：首版渲染分辨率调度

本轮开发构建已区分 Flash 渲染尺寸和最终显示尺寸：`WindowManager` 实际缩小 Flash 子窗口，GPU 裁剪源视口后等比放大，Native HUD/WebView2 仍按输出尺寸绘制。逻辑视野不变。倍率 0.85 / 0.75 / 0.67 对应约 72% / 56% / 45% 的源像素面积；AS2 逻辑、碰撞、对象遍历不随像素面积一起下降，不能据此承诺等比例总帧率收益。

缩放后已用坐标映射替代原有点击穿透。目标进程内的 x64 输入桥处理 Flash 原生按钮、捕获状态和 DPI；只向所属 Flash UI 线程安装钩子，不改桌面鼠标位置。缩放中的拖动、窗口恢复与首次点击纳入实际游戏验证。GPU 使用双线性放大，仅缩放后的 LOW 附带可关闭的轻度局部钳制锐化；它不是 CAS，不能恢复已丢失的抗锯齿信息。更高级的空间重建留给后续，不采用旧文中的理论收益比例作为实测结论。

调度参考 [PerformanceOptimizer/paper.md](../scripts/类定义/org/flashNight/neur/PerformanceOptimizer/paper.md) 的非对称确认、趋势门控、驻留和紧急降级，不直接套用旧 PID 参数与旧机器增益。C# `RenderSchedule` / `PerfDecisionEngine.Render` 统一决定倍率、quality 和既有 softU 预算，AS2 `PerformanceScheduler` 负责约 500 ms 实际时间窗口的计数汇总、带场景/命令号的应用与断连回退。旧两字段指令保持兼容，旧采样格式不再同时驱动第二个宿主控制器；合成器重复呈现旧帧的 FPS 不作为游戏 FPS。

首版使用有限阶梯、较快降级、较慢恢复及恢复失败退避。转场保留档位并清空统计，暂停、失焦、最小化和捕获未就绪期间不累计确认；鼠标手势期间继续观测，只延后实际尺寸提交。恢复不再要求帧率连续单调上升，正常采样抖动不会清空进度；尺寸交接先同步冻结合成线程，等 Flash 重绘确认后再提交新裁剪。MEDIUM 默认先降尺寸再进入 LOW；参数表、启动方式及原始证据入口统一维护在 [开发与验证说明](../launcher/perf/flash-compositor/README.md#首版动态分辨率调度)。本轮只用既有斗兽轮子做固定阵容的粗对照，不调战斗数值。按地图学习、识别“降分辨率无收益”并提前停止、GPU 压力联合调度和画质精调仍未实现；长期调教不阻塞首版人验。当前状态是配套开发构建，正式 runtime 未部署。

### 7.2 2026-09-22：统一合成与输入优先的顺序评估

**状态：讨论提案，尚未启动统一合成施工或提交/推送/正式发布。** 建议保留现有捕获、光照、动态分辨率和字体修复成果，先收口为可追溯的配套构建，再推进“统一显示 + 统一输入归属”，随后接入粒子，最后按独立可行性结果安排天空/地图拆分。此建议更新 §7 的后续优先级，不撤销已完成的光照卸载，也不把天空透明化当作合成前置。源码推送、构建生成、正式 runtime promotion 与标准入口复验是不同动作，不能互相替代。

#### 顺序造成的额外成本

以下是设计判断，尚无可校准的实际工时；只比较先后顺序导致的返工，不把模块本身的开发成本重复计入。

| 后续工作 | 先统一合成的增量影响 | 当前应保留的边界 |
|---|---|---|
| 位于世界前方的雨雪/尘埃 | 低，通常是新图层接入和回归；若先独立实现窗口，还要再迁一次呈现与生命周期 | GPU 图层、世界/屏幕坐标、混合方式、是否接受世界调色、暂停/转场时钟 |
| 位于角色/地图背后的粒子 | 合成器接入成本低，但遮挡来源仍是独立难点，不能以“粒子已迁移”涵盖 | 支持前后排序，不伪造当前没有的深度或 alpha |
| 天空/背景拆分 | 核心研究成本基本不因顺序增加；主要未知仍是透明来源、动态遮挡、素材导出与镜头一致性 | Flash 来源能力可替换，背景插入点与遮挡合同显式表达 |
| 若未来必须更换 Flash 宿主 | 可能有较大适配与全链路回归，不可承诺零返工；这是路线变化成本 | 将来源采集和 Flash 输入适配与合成调度/逻辑焦点权威分离 |

不建议为避免这部分小规模接入而先完成整套天气粒子/天空方案。反过来，如果当前把单一不透明源、固定图层数、桌面坐标和“鼠标永远发 Flash”写死，后续将同时重写呈现、输入和同步，顺序成本会显著放大。

#### 合成和输入作为同一阶段设计

当前源码分别以 `AppActivationState` 判断应用激活、`PanelFocusRestoreGate` 限制跨面板代际的恢复、`PointerInputBoundary` 拒绝旧鼠标边沿；`WindowManager` 仍负责物理焦点设置及跨线程恢复，动态分辨率桥负责 Flash 鼠标交付。它们有可复用的保护，尚不等于单一游戏会话输入权威。旧现场 W 键/慢点击故障也没有因此获得完整根因证明。

目标是一套会话状态决定输入去向，物理窗口/进程仅执行适配：

1. **显示和坐标**：稳定的玩家可见主窗口，图层共享输出/DPI/世界视口变换；输入使用当前呈现帧对应的映射，尺寸交接期间不能混用新旧变换。区分世界调色域和不受调色的 HUD/面板。
2. **逻辑输入归属**：游戏、面板、文本输入、模态阻断、后台/最小化和关闭状态由一处裁决；键盘焦点、鼠标命中与鼠标捕获是不同字段，允许不同但必须由同一权威协调。每次切换带代际，旧回调不得重新夺焦点。
3. **手势与恢复**：按下/松开成对归属；切换 owner 时取消旧手势并释放旧捕获，不将迟到事件补发到新界面。应用激活与真实键盘焦点分开验证，IME/文本输入交给对应引擎，不能只靠投递键码模拟。
4. **生命周期与证据**：暂停、转场、最小化恢复、源进程或设备重建统一通知图层与输入适配器。记录输入来源、逻辑 owner/代际、实际目标、拒绝/完成原因及相应呈现状态，沿用既有诊断边界，不新建平行会话权威。

这能从结构上消除多顶级窗口之间反复激活、多个组件各自恢复焦点的一类竞态，但“窗口变少”不能证明全部输入故障治愈。Flash、WebView2、IME、系统对话框和第三方叠层仍有自己的线程/窗口协议；保留 Flash 独立进程，无需为统一体验合并进程。

#### 下一阶段的可执行边界与人验

- 先用真实游戏的一个功能面板验证 WebView2 composition 与 Flash 键鼠/中文输入的往返，确认统一输入归属可行；沿用现有存档和开发入口，不另建强制测试角色。WebView2 接入同一 visual tree 与所有内容压成一张输出分别验，不能把前者当作后者完成。
- 随后逐个接入 HUD、伤害数字、面板背景和光标，替换相应窗口职责；保留当前 GPU 光照、动态分辨率与输入桥作为可复用模块。具体 WebView2 渲染承接是主要不确定性，需先验证再估总工期。
- 自动覆盖按键/鼠标成对、面板快速开关、按住键切屏、过期恢复回调、转场、缩放/DPI、最小化与进程/设备恢复；对照同尺寸下 AS2 推进、CPU/GPU 成本和呈现延迟。不能只比较合成器 FPS。
- 人工节点放在首个可玩的统一窗口纵向样例，验证操作跟手、首次点击、中文输入与 Alt-Tab 观感；完整接入后再验真实战斗和功能面板往返。机器协议/构建失败继续自动修复，不要求人替代日志判读；人体感受不能由自动通过代签。
- 粒子接入和天空拆分研究后续独立推进；曲线、Gamma、分区调色、选择性饱和度及 LUT/预设编辑器属于视觉迭代，不阻塞合成与输入施工。
