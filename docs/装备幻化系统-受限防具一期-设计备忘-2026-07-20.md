## 0. Compact 恢复入口

后续会话只读本文时，先恢复以下结论：

1. **一期只做防具，不做武器**。武器外观与枪口、刀口、判定点、弹道锚点和手感耦合；它不是防具幻化的普通扩展，而是另一项判定系统解耦工程。
2. **一期只做五个可见防具部位**：头部、上装、手部、下装、脚部；项链没有稳定的 `dressup` 表示，排除。
3. **幻化是纯视觉覆盖层，不是装备替换**。来源装备只能提供经过白名单确认的视觉字段；属性、技能、副武器、生命周期、套装逻辑、动作类型、插件和进阶一律不继承。
4. **玩法上可以叫“幻化插件，并占用进阶通道”**；技术上不得把来源名伪装成普通 `mods[]`，也不得新增假 `tier`。推荐独立保存 `value.appearance`，再由权威服务强制 `tier` 与 `appearance` 互斥。
5. **目标装备按最终有效行为判冲突**：存在 `skill`、`subweapon`、`lifecycle` 或其他会访问具体影片剪辑结构的行为时，一期拒绝幻化；不能只检查 UI 分类或插件名称。
6. **来源装备默认也只开放纯视觉项**。带生命周期的来源即使不复制函数，也可能依赖函数创建披风、喷口、外挂件等视觉对象；特殊项只能经人工验证后进入白名单。
7. **同部位幻化**，例如头部只能模拟头部。来源的基础外观可用，来源的进阶、插件和二次幻化不参与一期解析，避免递归和变体身份不清。
8. **持有资格按装备名称计算，不绑定物理槽位**。提交时仍用容器、slot、lease 防并发；存档只保存来源名。默认一件来源装备可以授权多个目标。
9. “当前持有”推荐包含 **装备栏 + 背包 + 战备箱 + 仓库**。若最后一件来源被移出持有范围，保留幻化记录但显示为“来源未持有，暂时失效”；重新获得后恢复，不能静默删除记录。
10. **调制页新增独立“幻化”页签**，复用现有 AS2 preview/token/commit 权威和 Web 工作台，不另建第二套装备写入系统。
11. 当前装备定义审计给出足够大的一期内容池：651 件防具中 552 件有 `dressup`，501 件没有声明 `lifecycle/skill`；40 级以上 112 件全部不可进阶，其中 95 件没有声明 `lifecycle/skill`。
12. 可发布一期约需 **10–15 人日**；若严格做到跨四类持有区域的实时失效/恢复，总计约 **15–23 人日**。特殊生命周期外观按装备家族持续付费，不应混入一期底座。

## 1. 问题、目标与裁决

### 1.1 玩家需求

玩家希望将装备数值构筑与角色外观解耦，使已经持有的旧装备、收藏装备和高等级防具继续产生外观价值。这个需求有三个明显收益：

- 不改变战斗数值即可获得高感知体验提升；
- 复用已有美术资产，延长旧装备内容寿命；
- 提升收集、背包、战备箱和仓库的长期价值。

### 1.2 当前技术障碍

直接把另一件装备的数据或影片剪辑替换到目标装备，会破坏两类现役耦合：

1. 防具生命周期函数可能依赖装备影片剪辑的实例层级、挂点、命名和特定子对象。
2. 武器命中、枪口、刀口、弹道和攻击判定依赖具体影片剪辑内的判定点；更换影片剪辑会改变手感和性能。

因此不能把幻化定义成“把来源装备完整套到目标装备上”，只能定义为经过约束的视觉投影。

### 1.3 总体裁决

| 维度 | 评价 | 结论 |
|---|---|---|
| 玩家收益 | 高 | 值得立项，尤其适合盘活高等级不可进阶防具 |
| 平衡风险 | 低 | 只要不复制功能字段，数值和战斗身份保持不变 |
| 技术可行性 | 较高 | 现役换装、调制、库存和 Web 预览可以复用 |
| 一期投入 | 中等偏高 | 难点是跨容器持有、权威互斥和失效刷新，不是绘制页面 |
| 长期维护 | 可控 | 必须坚持默认拒绝行为装备，特殊项走白名单 |

**Go 条件**：以“防具纯视觉覆盖层”立项，接受一期不能覆盖全部标志性装备，并明确武器不在本路线内。

## 2. 已验证的现役结构

### 2.1 外观与功能数据的读取位置

现役 `DressupInitializer` 已经给出可利用的分界：

- `updateDressupKeys()` 从各部位的计算后装备数据读取 `data.dressup`；头部还读取 `helmet` 以决定是否隐藏头发。
- `updateWeqaponSkills()` 从功能装备数据装载主动战技或副武器。
- `updateLifeCycles()` 从各部位功能装备数据的 `lifecycle` 装载生命周期函数。

关键路径：

- `scripts/类定义/org/flashNight/arki/unit/UnitComponent/Initializer/DressupInitializer.as`
- `scripts/逻辑/单位函数/单位函数_fs_装备生命周期配置.as`
- `scripts/逻辑/装备函数/README.md`

这说明外观覆盖可以集中在 dressup key 解析阶段，不需要让来源装备进入功能装备计算链。

### 2.2 进阶不是通用插槽

`TierSystem` 对进阶名称、可用条件和覆盖字段具有既定语义，并允许进阶数据覆盖 `skill`、`lifecycle`：

- `scripts/类定义/org/flashNight/arki/item/equipment/TierSystem.as`

因此 `value.tier = "幻化:某装备"` 会把视觉功能伪装成进阶，污染价格、状态展示、进阶判定、后续迁移和拆卸语义。一期只能复用“进阶通道互斥”这一产品规则，不能复用 `tier` 字段承载数据。

### 2.3 普通插件也不是动态外观绑定

现役插件具有以下假设：

- `value.mods` 是静态插件名称数组；
- 插件来自材料集合，安装时消耗、拆卸时返还；
- `TagManager` 根据静态标签、用途、技能和副武器判断冲突；
- `EquipmentCalculator` 将插件解析为对装备数据的覆盖或数值修改。

关键路径：

- `data/items/equipment_mods/README.md`
- `scripts/类定义/org/flashNight/arki/item/equipment/TagManager.as`
- `scripts/类定义/org/flashNight/arki/item/equipment/EquipmentCalculator.as`

如果把每件来源装备做成普通插件，需要生成数百个静态插件定义；如果让 `mods[]` 保存动态对象，又会破坏现有字符串数组、材料返还、tooltip 和存档修复假设。故本文只复用插件的产品表现和材料经济，不复用 `mods[]` 保存来源绑定。

### 2.4 调制服务可以成为唯一写权威

`EquipmentTuningService` 已具备 snapshot/preview、opaque token、commit 重新验证、lease、原子提交与 reconcile 语义：

- `scripts/类定义/org/flashNight/arki/item/EquipmentTuningService.as`
- `launcher/src/Tasks/EquipmentTuningTask.cs`
- `launcher/web/modules/equipment-tuning/`

但当前调制目标和 source ref 都严格限制为背包；Web 工作台也只允许从背包卡片进入调制。要让幻化来源覆盖战备箱、仓库和装备栏，需要新增权威候选查询与持有索引，不能只放宽 Web 按钮。

### 2.5 存档对象可以承载独立字段，但修复分层必须同步

`BaseItem.toObject()` 会克隆完整 `value`，`createFromObject()` 也会保留未知字段并归一化 `mods`。普通保存/读取在结构上可以携带 `value.appearance`：

- `scripts/类定义/org/flashNight/arki/item/BaseItem.as`

但损坏存档修复目前主要认识物品名称和 `value.mods[]`。正式施工时必须同步检查：

- `launcher/src/Save/SaveFieldLayering.cs`
- `tools/cf7-save-repair/src/layering.ts`
- `tools/cf7-save-repair/tests/layering.test.ts`

否则正常存档虽然能保存，损坏修复时 `appearance.sourceName` 可能按默认低信任字段被丢弃或得到不一致处理。

## 4. 一期领域模型

### 4.1 术语

| 术语 | 含义 |
|---|---|
| 功能目标 | 保留名称、数值、插件、技能和生命周期身份的真实装备 |
| 外观来源 | 玩家持有、只贡献视觉字段的同部位装备定义 |
| 幻化模块 | 提供操作成本并占用进阶通道的通用插件型材料 |
| 幻化绑定 | 保存于目标装备 `value.appearance` 的来源名称与版本信息 |
| 有效幻化 | 绑定合法、来源仍持有、资源可解析且未命中行为冲突 |
| 暂时失效 | 绑定仍保存，但来源未持有或资源暂不可解析；显示目标基础外观 |

### 4.2 推荐存档形状

建议形状，不代表现役 schema：

```text
value: {
    level: Number,
    tier: String | undefined,
    mods: Array<String>,
    appearance: {
        version: 1,
        moduleName: "通用幻化模块",
        sourceName: "来源装备名"
    } | undefined
}
```

约束：

- 不保存来源容器、slot 或 lease；它们只服务一次 preview/commit。
- 不保存来源装备的完整 `value`，避免复制属性、进阶、插件或二次幻化。
- 不保存 `active`；它是根据当前持有与资源状态派生的运行时结果。
- `sourceName` 必须重新通过 `ItemUtil`/物品字典解析，不能信任存档内自带的视觉数据。
- `version` 为以后增加纯视觉变体留迁移入口；一期只支持来源基础外观。

### 4.3 视觉覆盖包

一期允许的来源字段应是封闭集合：

| 部位 | 允许字段 | 备注 |
|---|---|---|
| 头部 | `data.dressup`、`helmet` | `helmet` 会影响头发显隐，属于必要视觉语义 |
| 上装 | `data.dressup` | 继续由现役逻辑拼接身体、手臂和性别键 |
| 手部 | `data.dressup` | 继续由现役逻辑派生左右手键 |
| 下装 | `data.dressup` | 继续由现役逻辑派生臀、腿、小腿键 |
| 脚部 | `data.dressup` | 直接作为脚部装扮键 |

明确禁止从来源复制：

- `data` 内除视觉白名单外的任何属性；
- `skill`、`subweapon`、`lifecycle`；
- `setId`、动作类型、子弹或命中信息；
- 来源 `tier`、`mods`、`appearance`；
- 来源运行时创建的 MovieClip、监听器、计时器或任务对象。

### 4.4 运行时分流原则

推荐新增单一 `EquipmentAppearanceResolver` 或等价集中 helper：

```text
真实 BaseItem
  ├─ 功能数据：照常经过 EquipmentCalculator → skill/lifecycle/属性
  └─ 外观数据：读取 value.appearance → 校验持有/同部位/资源 → 输出视觉覆盖包
```

`DressupInitializer.updateDressupKeys()` 只在读取视觉字段时查询 resolver；`updateWeqaponSkills()` 和 `updateLifeCycles()` 必须继续读取功能目标。不要把来源数据整体合并进功能装备数据，也不要原地改写共享 XML 对象。

即使一期拒绝所有带行为的目标，也要保留这条结构隔离，避免未来白名单扩展时重新引入生命周期串线。

## 5. 权威资格与互斥矩阵

### 5.1 目标装备

目标必须同时满足：

- `type == 防具`；
- `use` 属于头部、上装、手部、下装、脚部；
- 位于背包，并由当前调制 session 的有效 slot lease 指定；
- `value.tier` 为空；
- 未安装另一个 `value.appearance`，或操作明确为“替换幻化”；
- 经过基础数据和现有插件计算后，不含 `skill`、`subweapon`、`lifecycle` 或其他声明为 MovieClip 结构敏感的行为；
- 物品及 `value` 通过现役装备完整性检查。

数值型插件可以共存。战技、副武器、生命周期及未来行为型插件必须与幻化互斥。判断应集中在 AS2 权威 helper，不让 Web、旧 renderer 和 runtime resolver 各自猜测。

### 5.2 来源装备

来源必须同时满足：

- 当前持有索引中数量大于 0；
- 与目标 `use` 完全相同；
- 来源名不是目标本身的无意义同名模拟；
- 原始定义存在且基础 `data.dressup` 非空；
- 对当前角色性别可解析，所需皮肤键、符号和帧均通过资源校验；
- 一期默认没有根级 `skill/lifecycle`；
- 只读取来源基础定义，不读取来源实例的 `tier/mods/appearance`。

后续如果要开放行为来源，必须通过显式白名单证明“移除其行为后视觉仍完整”，并对男女角色和所有动作做真机检查。不得因为来源装备成功显示静态纸娃娃就直接放行。

### 5.3 进阶通道与材料

推荐冻结：

- 幻化与真实进阶互斥；已有进阶时不能安装幻化。
- 已幻化时不能直接进阶，必须先拆除幻化。
- 幻化模块是独立材料；安装消耗一件，拆除返还一件，沿用普通插件的经济直觉。
- 替换外观来源只更新现有绑定，不重复消耗模块；来源暂时失效时仍允许拆除并正常返还模块。
- 来源装备只作为持有授权，不被消耗、不被锁定。
- 互斥本身已经形成机会成本，一期不宜再设置很高的金币或稀有材料成本。

尚未冻结幻化模块的具体物品名、稀有度、掉落和价格；这些属于施工前最后的游戏设计输入，不影响本文技术边界。

## 6. 当前持有语义

### 6.1 推荐持有范围

```text
装备栏 + 背包 + 战备箱 + 仓库
```

用户原始设想列出背包、战备箱、仓库，但如果“当前持有”字面排除装备栏，玩家将来源装备穿上后反而失去授权。推荐把装备栏纳入权威计数；Web 不一定要完整展示装备栏格子，但 AS2 持有索引必须计数。

### 6.2 名称级授权

一期按 `sourceName` 授权：

- 任意持有区域至少有一件同名装备，则来源有效；
- 一件来源可以授权多个目标；
- 来源在持有区域之间移动不影响绑定；
- 不尝试绑定某个物理实例。

若未来要求“一件来源只能支持一件目标”，必须先为装备引入稳定实例 ID、跨容器转移语义和存档迁移；这会显著扩大工程，不属于一期。

### 6.3 状态迁移

| 事件 | 绑定 | 显示 | 建议反馈 |
|---|---|---|---|
| 安装成功 | 新增 | 来源外观 | 显示来源名和模块状态 |
| 来源在持有区之间移动 | 保留 | 不变 | 无提示 |
| 最后一件来源被出售/丢弃/移出范围 | 保留 | 回退目标基础外观 | “来源未持有，幻化暂时失效” |
| 重新获得来源 | 保留 | 自动恢复 | 可做轻量恢复提示 |
| 来源资源损坏或版本不兼容 | 保留 | 回退目标基础外观 | “外观资源不可用”并记录诊断 |
| 主动拆除 | 删除 | 目标基础外观 | 返还幻化模块 |

### 6.4 实现建议

- 建立按装备名称计数的 `AppearanceOwnershipIndex`，而不是每帧扫描所有库存。
- 索引监听背包、战备箱、仓库及装备栏的事务完成事件；只在 mutation revision 变化后更新。
- preview/commit 对选中的来源仍使用 `{containerId, slot, expectedLease}`，并绑定相关容器 revision。
- runtime 换装刷新只查询名称计数；来源失效时不修改存档，不在读取路径写回。
- 对没有覆盖到统一事务事件的出售、丢弃、装备穿脱和存档修复路径补测试；这是严格持有语义的主要施工成本。

如果排期不足，可以先做“安装提交时验证持有，安装后不实时失效”的简化版，但必须在 UI 和文档中明确；它不等同于本文推荐的严格当前持有承诺。

## 7. 调制事务与 UI

### 7.1 推荐 operation

名称仅为施工建议，正式 wire shape 变更时需同步 canonical doc：

- `apply_appearance`：安装或替换来源外观；需要目标 lease、来源 lease/名称、幻化模块和预期 revision。
- `detach_appearance`：拆除幻化并返还模块；只需要目标 lease。

两者都必须走现役模式：

```text
snapshot → preview plan → opaque token → 单次 commit → fresh snapshot / needs_reconcile
```

AS2 是规则和写入权威；C# 只做严格白名单、wire shape 和长度/枚举校验；Web 只渲染候选、预览结果并提交 intent。

### 7.2 preview 至少返回

- 目标装备摘要及当前 `tier/mods/appearance`；
- 来源名称、部位、持有位置摘要与资源可用性；
- 当前外观键、候选外观键和 `helmet` 变化；
- 幻化模块的持有数、消耗和拆除返还；
- `active/inactive` 及稳定 reason code；
- 冲突的有效技能、副武器、生命周期或行为插件名称；
- 提交绑定的 target/source lease、inventory revisions 和 session generation。

### 7.3 UI 归属

在装备调制右栏增加独立顶级页签“幻化”，不要混入“配件”列表：

- 来源是装备，不是普通材料卡片；
- 需要跨背包、战备箱、仓库和装备栏检索；
- 需要原外观与候选外观并排预览；
- 需要清楚表达进阶通道占用、行为冲突和来源失效。

推荐页面内容：

1. 目标装备基础外观、当前外观和当前绑定。
2. 只列同部位、当前持有、资源可解析的来源。
3. 容器筛选、名称搜索、“仅安全来源”固定筛选。
4. 纸娃娃或 dressup inspector 预览，至少覆盖当前性别。
5. 明确的不可用原因，不把候选静默隐藏成“系统没有这件装备”。
6. tooltip 同时显示“功能装备：X / 当前外观：Y”。

现役顶部四页签契约会变为五页签，Web harness、键盘导航、1024×576 布局和 Host/Web 测试均须同步更新。

## 8. 建议施工切片

### P0：规则冻结与可重复审计，1–2 人日

- 冻结幻化模块的物品名、成本、返还和获得方式。
- 冻结严格持有或安装时持有语义。
- 将本次临时 XML 统计固化为 validator/report，输出安全候选、行为拒绝项、缺失皮肤键和男女资源差异。
- 选取五部位各 3–5 件代表装备，包含高等级、带 helmet、男女键和预期拒绝样本。

### P1：AS2 领域底座，3–5 人日

- 增加 `value.appearance` 校验与 clone/保存测试。
- 增加集中资格 helper 和 `EquipmentAppearanceResolver`。
- 让 dressup key 走视觉 resolver，技能和生命周期继续走功能数据。
- 扩展 `EquipmentTuningService` 的 snapshot/preview/commit、token 绑定、材料事务和拆除返还。
- 增加 `EquipmentTuningServiceTest.as` 和 resolver 专项测试。

### P2：持有索引与跨容器来源，2–4 人日

- 建立装备栏、背包、战备箱、仓库的名称计数。
- 提供分页/过滤候选投影，不把整仓库一次性塞入消息。
- 覆盖移动、整理、出售、丢弃、穿脱、重载和最后一件来源消失。
- 若一期只做安装时持有，可压缩本切片，但会削弱产品承诺。

### P3：Host/Web 纵切，3–5 人日

- C# operation 白名单、source ref、reason code、payload 和测试。
- Web 增加“幻化”页签、候选列表、预览、确认和失效提示。
- 复用 dressup renderer/inspector，不在 Web 重算资格。
- 更新 equipment-tuning harness 的五页签、三视口和失败态样本。

### P4：存档、真机与发布验证，2–4 人日

- 更新 C#/TS save layering 和损坏样本。
- 覆盖存档重启、来源移动/失效/恢复、模块返还和原子回滚。
- TestLoader 获取新鲜 trace；涉及 `scripts/` 注入时按 AS2 编译约束发布 `asLoader`。
- 男/女角色五部位真机检查；任何 lifecycle 例外单独建验收账本。
- 更新 `launcher/README.md`、`agentsDoc/testing-guide.md`、数据 schema/插件 README 等实际发生变化的 canonical doc，并运行文档治理校验。

### 成本汇总

| 范围 | 估算 |
|---|---:|
| 只读技术样机，无完整持久化/UI | 3–5 人日 |
| 可发布一期，安装时验证持有 | 10–15 人日 |
| 严格实时持有、失效与恢复 | 额外 5–8 人日 |
| 推荐完整一期 | 15–23 人日 |
| 生命周期特殊装备 | 每个装备家族约 0.5–2 人日，持续投入 |

当前装备调制仍是活跃迭代区，排期应在上述估算外预留约 20% 的合并、真机回归和 CS6 窗口成本。

## 9. 验收矩阵

### 9.1 领域不变量

- 应用或拆除幻化前后，目标名称、强化度、进阶、插件、属性、技能、生命周期和套装身份不变。
- 来源装备不减少、不改变、不被锁槽。
- 幻化模块只在 commit 成功后扣除；拆除成功后返还；失败和 stale token 零写。
- `tier` 与 `appearance` 不能同时存在；坏档出现共存时必须确定性 fail-closed 或修复。
- 来源的 `tier/mods/appearance` 永远不能渗入目标。
- 来源与目标不同部位时权威拒绝，Web 不能绕过。

### 9.2 持有与存档

- 来源分别位于装备栏、背包、战备箱、仓库时均按冻结规则生效。
- 来源跨容器移动、整理换槽后保持有效。
- 多件同名来源减到一件时保持有效；最后一件消失后转暂时失效。
- 来源重新获得后恢复；绑定不需要重新安装。
- 保存、退出、重启后绑定、模块成本和 active/inactive 派生态一致。
- 损坏的 `sourceName/version/moduleName` 不执行任意查找或加载，安全回退基础外观。

### 9.3 外观与资源

- 男/女角色分别覆盖头、上装、手、下装、脚五部位。
- 头部 `helmet` 正确控制头发显隐。
- 左右手、臀/腿/小腿等派生键正确，不只验证静态正面帧。
- 行走、跳跃、攻击、受击、换武器和场景切换后外观稳定。
- 缺失皮肤键、符号或帧时回退基础外观并输出诊断，不留空身体或半套结构。
- 纸娃娃预览与游戏运行态使用同一来源解释，不出现 Web 可见、游戏不可见。

### 9.4 行为隔离

- 目标带基础 lifecycle、skill、subweapon 时拒绝。
- 安装行为插件后拒绝；只有数值插件时允许。
- 带 lifecycle 的来源默认拒绝，即便静态 dressup 能显示。
- 任意成功幻化都不新增任务、监听器、射击控制槽、生命周期 task 或影片剪辑挂件。
- 武器、项链和未知 `use` 全部 fail-closed。

### 9.5 验证入口

实际施工时统一按 [testing-guide](../agentsDoc/testing-guide.md) 选择命令，不在本文复制易漂移命令。至少覆盖：

- `EquipmentTuningServiceTest.as` 与新增 appearance resolver 测试；
- `launcher/tests/Tasks/EquipmentTuningTaskTests.cs`；
- `tools/cf7-save-repair/tests/layering.test.ts`；
- `launcher/web/modules/equipment-tuning/dev/harness.html`；
- dressup manifest/report 和资源完整性验证；
- TestLoader 新鲜 trace 与男女角色真机 smoke。

没有新鲜 trace、输出日志或 IDE 复核时，不得声称 AS2 编译通过。

## 10. 风险、停线与非目标

### 10.1 主要风险

| 风险 | 控制 |
|---|---|
| 标志性装备因 lifecycle 被排除，玩家认为功能残缺 | 候选卡显示不可用原因；特殊项按家族白名单，不降低底座规则 |
| 低级装备在进阶和外观间二选一显得惩罚 | 模块成本保持温和、拆除可逆、提交前明确提示 |
| 跨仓库实时持有导致频繁全量扫描 | 名称计数索引 + mutation revision/event，不在每帧扫描 |
| 来源出售后外观突然变化 | 保留绑定、明确暂时失效、重新获得自动恢复 |
| 普通插件与幻化各自复制冲突逻辑 | 单一 AS2 资格 helper，Web/Host 只消费结果 |
| 来源数据合并污染功能数据 | 封闭视觉包 + 独立 resolver，不复制来源对象 |
| 纸娃娃成功但战斗动作缺件 | 真机动作矩阵；带行为来源默认拒绝 |

### 10.2 硬停线

- 不以“已经改了 `dressup`”为理由放开带生命周期目标。
- 不允许 Web 或 C# 自行判断最终行为冲突。
- 不新增数百个“某装备外观插件”静态定义来模拟动态绑定。
- 不把来源装备的容器/slot 当作长期身份。
- 不在读取、预览或来源失效路径静默改写存档。
- 不因防具一期成功而直接开放武器。
- 不在缺少男女资源、动作真机证据时将特殊来源加入白名单。

### 10.3 明确非目标

- 武器幻化、武器判定点归一化和视觉锚点系统。
- 跨部位混搭、上装模拟下装等自由映射。
- 染色、材质替换、局部组件选择。
- 将来源装备消耗为永久衣柜解锁。
- 一件来源只授权一件目标的实例级占用。
- 复制来源进阶外观、插件外观或幻化链。
- 自动兼容所有生命周期装备。

## 11. 尚待施工前冻结的产品决策

以下问题不需要重新做技术可行性探索，只需产品裁决：

1. 幻化模块的正式名称、稀有度、获取和金币成本。
2. 拆除是否完整返还模块；本文推荐返还。
3. 是否严格执行实时当前持有；本文推荐严格执行并采用暂时失效。
4. 装备栏是否纳入持有；本文推荐纳入。
5. 一件来源能否授权多个目标；本文推荐可以。
6. 是否开放极少量带 lifecycle 的来源白名单；本文推荐一期不开放，运行稳定后逐家族评估。
7. 是否在一期显示不可用来源及原因，还是只显示安全来源；本文推荐默认列安全来源，并提供“查看不可用”诊断筛选。

只要以上产品项冻结，后续可以直接从 §8 的 P0/P1 开始施工，无需重新证明“防具纯视觉覆盖是否可行”。
