## 1. 决策摘要

本次变化定义为一次事务边界重构，而不是继续在拾取、商店、任务、制作、换弹等外部入口逐个调用播报函数。

- 领域服务继续拥有价格、容量、任务条件、容器写入、回滚与存档 dirty 等业务权威。
- `PlayerAssetTransaction` 位于权威写入与可选消费者之间，只收集已经实际发生的玩家所有权变化，并在最外层领域提交后发布 detached receipt。
- `ItemUtil.acquire/submit/singleAcquire/singleSubmit` 是通用物品写入适配层；复合交易、制作、任务等以显式 `begin → record → commit/rollback` 包住它，普通旧入口可使用隐式短事务。
- 独立 UI、关卡和素材 XFL 不拥有稳定的 `scripts/类定义` classpath，也不得把事务类版本编进各自 SWF；时间轴统一调用 asLoader 注入的 `_root.开始玩家物资事务/提交玩家物资事务/回滚玩家物资事务/记录玩家物资变化/记录玩家货币变化/玩家物品是否装备` 门面，类库选择只留在主运行时。
- AS2 根时间轴只把 receipt 中的权威物品键解析为展示名、图标与进阶外观，再投影为 `loot` v1；Host 只校验、去重、调度与绘制，不反向修改资产。
- 播报消费者失败、socket 离线或 NativeHud 异常不得使已经完成的资产写入回滚；反过来，尚未提交或已经回滚的领域变化不得产生卡片。

物品对象本身不持有交易原因、领域终点或回滚能力，因此“内聚到物品内部”在这里具体落实为“内聚到玩家物资事务基座”，而不是让每个 `BaseItem` 在字段变化时自行广播。这样可以排除背包换位、装备穿脱、配件嵌入/拆回等位置变化，也避免制作/NPC 混合交易回滚时出现幽灵播报。

## 2. 冻结语义

### 2.1 纳入与排除

| 资产域 | kind | 播报规则 |
|---|---|---|
| 金钱、K点 | `money` / `kpoint` | 按最终账本差值播 gain/loss；同一 checkout 不重复播 gross 与 net |
| 情报、材料、普通物品、装备 | `intel` / `material` / `item` / `equip` | 只播玩家所有权净变化；装备默认一件，批量须显式数量语义 |
| 经验、技能点 | — | 本轮明确排除；它们是进度聚合，不伪装成物品卡，但仍必须 dirty/按既有升级规则存盘 |
| HP/MP、战宠体力、弹仓 shot、管式预付装填池 | — | 状态或内部池，不是玩家所有权资产 |
| 背包换位、装备穿脱、仓库/战备箱迁移、可回收配件嵌入与拆回 | — | 纯位置变化，`ownershipDelta=0`，不播 gain/loss |
| 击杀 | `kill` | 保留旧 neutral 事件链；不是资产事务，但继续复用同一 NativeHud feed |

所有物资 effect 的 `count` 都是 `1..9007199254740991` 的正整数 magnitude，方向只能由 `direction=gain|loss` 表达；不允许以负数或小数绕过契约。复合操作按 `direction + kind + authority item key + source + reason + tier + mergeScope` 聚合，且不跨所有权方向合并。

### 2.2 事务与存档终点

```text
领域 preflight
    |
    v
begin asset transaction
    |
    +--> 权威资产写入 + dirtyMark
    |       |
    |       +--> record gain/loss fact（仍不可见）
    |
    +--> 领域失败：恢复真实资产，再 rollback receipt
    |
    +--> 领域状态完成：commit outer transaction
               |
               +--> deferred strong-save attempt（如升级请求）
               +--> detached receipt
                         |
                         +--> AS2 wire projector --> XMLSocket loot v1
                                                     --> Host dedupe/model/widget
```

`commit` 表示资产与对应领域状态已经在内存权威中完成，不承诺磁盘已耐久。升级触发的强存档在有外层事务时延迟到最外层 finality；`flushNow=false` 或抛错时保留 dirty 供重试、`strongSaveFlushed=false`，但已经提交的 receipt 仍发布。若某业务要求“耐久后才能对外确认”，必须在该领域另行定义 durable acknowledgment，不能把 NativeHud 卡片冒充存档收据。

嵌套事务只向父事务合并 detached effect；内层不能提前发布。`rollback` 只丢弃尚未发布的消费者回执，不能替代领域资产快照恢复。任何会恢复领域资产的 `catch` 都不得包住已经完成的 `commit`。

隐式短事务只拥有自己创建的栈帧：记录输入在归一化或聚合阶段抛错时，必须先回滚该栈帧再原样传播异常；不得留下一个永久占据栈顶的 open transaction，也不得发布部分回执。显式事务仍由领域调用方决定提交或回滚，记录函数不得越权处置调用方的外层事务。

`ItemUtil.acquire` 的 dirty 必须先于金币/K点/经验/技能点或任一容器首写置位。写入、升级回调、容器或回执记录中途抛错时，函数原样传播异常，并只回滚自己创建且仍为栈顶的隐式事务；已有显式外层保持 open，由领域调用方依据自身资产快照恢复后决定 rollback。失败批次不得按原请求发布“全部获得”回执；没有通用领域快照的旧隐式入口只能以 dirty 保存事实并由调用方重新读取权威状态，不能把事务回执误当成资产回滚。

## 3. 协议

### 3.1 AS2 receipt

```text
{
  version: 1,
  operationId, source, reason, startedAt, committedAt,
  effects: [{direction, kind, name, count, source, reason, tier, mergeScope}]
}
```

receipt 中 `effect.name` 是权威物品键，不保存 catalog 可变对象。`operationId` 由外部提供或由基座生成；`mergeScope:"operation"` 在 begin/record 时展开为该 operationId。一个 effect 投影失败只丢该 effect 并继续后续 effect；消费者异常不会越过提交边界反向破坏权威状态。

### 3.2 XMLSocket `loot` v1

```text
{
  v:1, direction, kind, itemKey, name, count, source, operationId,
  icon?, tier?, mergeScope?, reason?
}
```

- `itemKey` 是权威身份，`name` 是 AS2 catalog/tier 解析后的展示名；两者在 v1 都是必填字符串。
- `v/source/direction/operationId/itemKey/kind/name/count` 为 v1 必填，显式 `v:null`、错型、未知 source、非整数或超 JavaScript safe integer 都 fail-closed。
- `icon/tier/mergeScope/reason` 若出现必须是受长度约束的字符串。`kill` 还可携 `eliteLevel` 与受限 `doll` 元组。
- 完全缺少 `v` 才进入 legacy 兼容：非 kill 默认为 gain，kill 默认为 neutral，未知 source 归一 `unknown`，超大整数只在 legacy 路径 clamp。旧 façade 只保留现役 kill 生产者，不再承载新增资产渠道。
- Host 幂等身份为 `operationId + direction + kind + itemKey + tier + source + reason + mergeScope`；同身份同 count 重放丢弃，同身份不同 count 视为冲突重放并 fail-closed。缓存为有界 512 项。
- Native 视觉模型合并键包含 `direction/kind/itemKey/tier/派生调度策略/eliteLevel`，并要求展示名/图标一致；`operationId/reason/mergeScope/raw source` 仍保留在 receipt 与 Host 幂等身份中，但不进入卡片模型。不同 raw source 只有在 retention/urgency/priority/hold 完全相同且都非 `unknown` 时才可聚合，因此不会跨越 reload immediate、guaranteed reward 或普通 prompt 边界。这样同一资产在 2500ms 窗口内的连续已提交操作会聚成一张卡，超过窗口仍新建卡；gain/loss 采用同一规则且绝不跨方向合并。`reload` 为 immediate exact-aggregate；loss 使用珊瑚红负号，数量一也明确显示 `−1`，其 `−1→−2` 不改变几何，只有 `−9→−10` 等位数变化才更新 bounds。

当前 v1 `source` 白名单由 `LootFeedTask.AllowedSources` 机器真源持有：`pickup`、`level_reward`、`quest_reward`、`achievement_reward`、`quest_turn_in`、`inventory_discard`、`equipment_tuning`、`loot_box`、`npc_shop_purchase`、`npc_shop_sale`、`kshop_purchase`、`kshop_claim`、`crafting`、`consumable_effect`、`pet_service`、`mercenary_service`、`reload`、`skill_cost`、`weapon_cost`、`item_use`、`task_entry`、`arena_entry`、`arena_reward`、`base_upgrade`、`tavern_purchase`、`vehicle_service`、`gym_training`、`appearance_service`、`player_revive`、`cheat`、`system_reward`、`kill`、`unknown`。新增 source 必须同轮更新生产者、Host parser 负例/正例和本文。

### 4.1 换弹 exact-once

- 普通单持、双持、管式与长枪副武器都以最终 `singleSubmit(...)===true` 作为弹仓/`reloadCount` 注入门；动画开始或库存 preflight 不是提交点。
- 动画期间库存被其他行为抢占时，保留原 `shot`，恢复战术回收池，零 loss receipt；补回弹匣重试时只扣一次并只发一次。
- 管式武器首次补充内部装填池时一次性扣库存并发一次 loss，之后逐发只消费池，不重复播报。
- AI/非控制单位走既有免费换弹分支，不产生玩家资产 loss。

## 5. 已知残余与非目标

- `ItemUtil.acquire` 已覆盖“首个写入成功、后续写入抛错”的 dirty、隐式清栈与零虚假全量回执，但它没有通用资产快照，不能把异常批次称为原子回滚；`submit`、少数直接 XFL producer 及 UI invalidation 仍未统一获得同等级 exception-safety hardening。
- 极端损坏/作弊存档若已有币余额逼近 JavaScript safe integer，绕过 `ItemUtil` 的旧直接标量 writer 可能先发生 Number 精度损失；正常经济量级不可达，后续应以统一 scalar mutator 收敛。
- 历史 KShop 待领取装备的 `quantity>1` 存档形状缺少真实旧档证据；现役兼容入口已事务化，但该畸形历史数据仍属 reachability-unproven。
- 击杀仍是无 `v` 的 legacy neutral 生产者；它复用显示面，不属于玩家资产所有权事务。
- 本轮不把经验/SP、实体招募本身、血量/体力或装备位置变化扩成 feed，也不新增 Web fallback、统计账本或可撤销事务引擎。
