## 3. 明确可修

### F1：阻断危险 SVG 的全部运行时回退路径

**证据。** 四份原转储都有 `FATAL:SkRuntimeEffectPriv.h(158)] error: program is too large`，包含 `kMaxKernelWidth = 128` / `kMaxKernelHeight = 128` 的生成程序及同一 SVG 路径。共同异常为 `0x80000003`、RVA `0x78f282d`；共同 RVA 本身不等于共同完整调用栈，本轮未完成带符号的完整栈展开。

| 已有资产 | Git 原始字节与特征 |
|---|---|
| [危险 SVG](../launcher/web/assets/enemy-portraits/subjects/b101d424c2e7d64279cc4f89.svg) | 747,089 字节；SHA-256 `B101D424C2E7D64279CC4F8983885445351740B6F1FABE098E14B5C34EAB5E6F`；33 个 `order="100 100"` 卷积节点 |

| [敌人头像 manifest](../launcher/web/assets/enemy-portraits/manifest.json) | “敌人-方舟妖姬”当前 `preferredFormat=svg`、`embeddedRasterCount=0`、`isRasterHeavy=false`；“敌人-拟态投影”存在复用 |

官方 m118 [矩阵卷积实现](https://skia.googlesource.com/skia/+/refs/heads/chrome/m118/src/effects/imagefilters/SkMatrixConvolutionImageFilter.cpp)为大卷积核生成程序并把尺寸取到 2 的幂，100 变为 128；[程序规模检查](https://skia.googlesource.com/skia/+/refs/heads/chrome/m118/src/sksl/analysis/SkSLCheckProgramStructure.cpp)检查展开后的代价，[错误处理](https://skia.googlesource.com/skia/+/refs/heads/chrome/m118/src/core/SkRuntimeEffectPriv.h)在失败时执行致命终止。JavaScript `try/catch`、图片 `onerror` 和禁用 GPU 都不是该路径的可靠恢复手段。

独立浏览器夹具已有结果，无需接手后为读报告再跑一次：

| 环境 | 输入 | 结果 |
|---|---|---|
| Chrome for Testing 118.0.5993.70 | 原始 SVG | 子进程新 dump 再现相同 fatal 与 128×128 程序 |
| 同上 | 已有 PNG | 完成渲染，像素有内容 |
| Chrome 152.0.7977.84 | 原始 SVG / PNG | 两者均完成渲染 |
| Chrome 118，`--disable-gpu` | 单个 20×20 卷积的最小 SVG | 完成渲染 |
| Chrome 118，`--disable-gpu` | 单个 100×100 卷积的最小 SVG | 相同 fatal 再现 |

这是**同代 Chromium 机制复现**，不是测试员物理 WebView2 的业务 E2E，也没有给出最早修复版本。原 SVG 夹具根进程在 25 秒、最小用例在 15 秒超时后被清理；判断依据清理前已经生成的子进程转储，不依据根进程的清理退出码。

**施工入口与范围。**

1. [共享生成器](../tools/portrait-pilot/promote-team-portraits-v1.py)的 representation 分析当前主要根据内嵌位图决定 `preferredFormat`（核对点约 1196、1597 行）；[敌人头像生成器](../tools/portrait-pilot/promote-enemy-portraits-v1.py)复用该能力。补可复验的危险滤镜识别 / 运行时禁用 SVG 策略，重新生成受影响的派生清单。保留原画、身份、别名、几何与来源，优先使用已有 PNG；不手改内容寻址 SVG 来伪装同一个哈希。
2. [portrait-resolver.js](../launcher/web/modules/portrait-resolver.js) 的 `applyChain` 在 PNG 优先时仍追加 SVG（约 263～273 行）。**只改 `preferredFormat=png` 不足够**：PNG 缺失或失败后仍可能崩溃。危险资产必须从实际加载链、可见像素探测及预览复用路径中排除 SVG，再退到已确认安全的占位图 / 旧资源。
3. 为生成策略和消费契约同步文档与验证器。库存找到 29 个含卷积的 SVG，不是“29 个均已证实崩溃”；按结构识别和实际消费者扩查，不能把 20×20 直接定为通用危险阈值。

**验收。** 以 [portrait resolver 测试](../tools/test-portrait-resolver-runtime.js)和[头像工具说明](../tools/portrait-pilot/README.md)为入口：危险项与别名使用安全表示；PNG 失败、缺失、延迟回调时不请求危险 SVG；普通矢量头像选择与几何不回归。再在隔离浏览器和真实 WebView2 候选中打开对应头像 / loot 报告，记录实际 Runtime、原生进程身份、加载资源和无新 fatal 的结果。旧档恢复报告旅程与原始输入事故分开验收。

### F2：修正历史 dump 的事件归属与时间字段

**确定的缺陷。** [WebViewFailureReportCollector.cs](../launcher/src/Diagnostic/WebViewFailureReportCollector.cs)按目录去重，把一个 `Referrer` 绑定到整个目录（约 239～263 行），枚举 14 天内有界文件，再把 `folder.Ref` 的 `session/kind/reason/classification/exitCode/documentGeneration/browserVersion/recordedAtUtc` 写到每个 included 文件（约 399～415 行）。现场 manifest 与此吻合：前三个前一晚生成的文件也带上了次日早上的事件属性。

**施工要求。** 分开文件自身证据与“哪个事件引用了这个目录”。保留文件 SHA、字节、文件时间、来源路径和有界采集；目录引用明确标为 referrer 元数据。有可靠逐文件证据才填对应事件，无法确定保留未知，不能按最近事件、同目录或文件名直接认定 session。无需为避免误关联而删历史文件或缩短既有 14 天窗口。

同项还需核对：原包 `recordedAtUtc` 为 null，而 JSONL 的 `atUtc` 有值；`JObject.Parse` 后 ISO 时间可能是 `JTokenType.Date`，现 `StringProp` 只接受 String，`TimestampProp` 又复用它（约 663～687 行）。**本轮未执行独立日期解析回归，不能写成已实测的唯一原因。** 修复时覆盖 String / Date、UTC 规范化、缺值和坏值。

**验收。** 扩充 [WebViewFailureReportCollectorTests.cs](../launcher/tests/Diagnostic/WebViewFailureReportCollectorTests.cs)：两个会话共用目录、旧新 dump 混放、无引用文件、同目录多次引用、时间字段类型、异常或缺失元数据；回归手动包与退出自动包。保留大小 / 数量 / 路径 / reparse point 限制。若 schema 改动，同步消费者与[焦点诊断文档](焦点管理-诊断与卡顿排查-2026-05-24.md)，旧包导入不得继续把 referrer 当 crash identity。

## 4. 防御性补漏

### B1：修饰键与按键消费状态恢复

[KeyboardHook.cs](../launcher/src/Guardian/KeyboardHook.cs) 和 [HotkeyGuard.cs](../launcher/src/Guardian/HotkeyGuard.cs)各有由 Ctrl 边沿更新的 `_ctrlHeld`。缓存为 true 时 W/R/P/O 等受保护，A/S/D 不在同一拦截表，是符合症状的具体候选；没有证据证明事故时缓存错误。两套 hook 前台范围也不同：KeyboardHook 对前台为空仍可能拦截，HotkeyGuard 要求实际 Guardian 前台。

防御包括左右 Ctrl 分开表达、在明确的失焦 / 重新激活 / hook 生命周期边界校准、可解释的状态恢复及消费配对。不要只在某个关卡初始化中清 native 缓存，也不要对其他应用全局合成松键。当前对白新增的物理键集合、消费键集合、长按去重与 Esc 交互需一并评估，防止修旧 Ctrl 却制造新残留。

低级键盘回调执行时当前键的异步状态尚未更新，不能把回调内 `GetAsyncKeyState` 无条件当作当前事件之后的真值；校准要选择正确时机，与左右键事件顺序一致。[Microsoft 回调契约](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc)

验收：左右 Ctrl 单独 / 同时按住、释放其中一个、在外部应用松键再回游戏、真实 Ctrl+W/R 仍保护、普通 W/R 可用、短暂前台为空、全屏切换；当前对白 Space / Enter / F / Esc、长按去重、down/up 配对和关闭后恢复。单测证明状态策略，物理键盘旅程证明交接行为；两者不替代 I1 事故取证。

### B2：失焦前产生、失焦后才到达的鼠标消息

[NativeHudOverlay.cs](../launcher/src/Guardian/NativeHudOverlay.cs)已有 `CancelPointerGesture`，覆盖 owner hidden、panel suspend、capture lost 等；[RightContextWidget.cs](../launcher/src/Guardian/Hud/RightContextWidget.cs)已有业务 gesture token 和 run / revision 校验。现场迟到复活请求第一条成功，第二条被 `revision_mismatch` 拒绝，既有保护正在发挥作用。

空隙在于：**物理 down 还在输入队列里时，没有已创建的 widget 手势可取消；它晚到后又可能按“当前业务状态”建立新 token。** 应将原始消息时间与可信的激活 / 业务代际边界比较，对确属旧交互周期的边沿拒绝或取消整段手势；不能只在消息到达时盖一个新代际章。

设计保留 32 位 tick 环绕、关联不唯一、无 hook 采样、down/up 配对、双击及合成测试消息边界；不能让默认关闭的 `diagFocusTrace` 决定业务保护是否生效。也不要单凭“超过 2 秒”吞掉全部慢操作，或在 hook 内补发业务点击绕过原生顺序。

验收：跨失焦的 down/up、失焦前尚未抵达的 down、场景 / revision 更换、旧 down 新 up、双击、快速合法点击、诊断关闭、无关联样本、计时环绕。复用 [NativeHudInputRoutingTests](../launcher/tests/Guardian/NativeHudInputRoutingTests.cs) 与 [RightContextWidgetTests](../launcher/tests/Guardian/RightContextWidgetTests.cs) 系列；物理任务栏往返另验。SendMessage 夹具不独立证明真实输入队列已复现。

复活处理中限制重复提交、及时显示处理状态可作附属保护；它减少迟到点击影响，不解决输入为何迟到。暂不添加高频 `Focus()` 轮询、额外大范围 `AttachThreadInput` 或鼠标注入式“解卡”。

### B3：让下一次 W 故障可以分层定位

沿用 `diagFocusTrace` 的默认关闭、固定容量和退出打包，补缺失证据，不重做已有鼠标环与 Crashpad 收集器：

| 位置 | 最小所需信号 | 区分目标 |
|---|---|---|
| 原生键盘入口与两套拦截器 | W/A/S/D/R 等白名单、左右修饰键、边沿时间、是否注入、哪个 hook 作何决定、缓存值与实时前台 | 键未进入本进程，还是本进程主动拦截 |
| Flash 采样 | 同时窗键码配置、`Key.isDown(上键)`、方向 mask、控制对象身份、采样是否禁用 | 原生之后未送达，还是采样 / 对象变化 |
| 角色移动 | 上行意图、阻挡 / 暂停 / 碰撞或控制权原因的有界变化 | 输入存在但移动不执行 |
| 鼠标消息泵 | 物理边沿、`GetMessageTime`、处理时间、线程 / 前台 / capture / GUI 状态；必要时记过滤或嵌套循环进入退出 | 输入排队与业务执行耗时 |

只采游戏白名单和状态位，不记聊天文本或任意键盘内容；不在低级 hook 同步刷盘，不逐帧无上限输出。丢样、环溢出、关联不唯一须明示，不拼出假的端到端关联；跨进程时钟需明确对齐方式。

若需 AS2 新字段，按[测试指南](../agentsDoc/testing-guide.md)走对应 TestLoader / asLoader 与新鲜 trace；源码可读不代表实际 SWF 已带上观察点。

## 5. 继续探查：区分实验与停止条件

### I1：W 失灵的丢失层

视频可见按 W 不上行、其他方向有动作，不能显示操作系统或 Flash 收到什么。[逐帧输入](../scripts/通信/通信_fs_帧计时器.as)约 483～499 行每帧用 `Key.isDown` 更新 mask 和上行。单纯“上行=false 残留”通常会被下一帧覆盖；“丢 W keyup 导致一直按下，所以不能继续上行”也与按电平采样的链路不符。

需要一次故障期间同时取得 B3 的原生决策、Flash 键态、移动状态：本进程明确拦截普通 W 且 Ctrl 缓存与正确物理序列不符，才把 B1 提升为本案归因；本进程放行而 Flash 无键态则继续查送达 / 焦点；Flash mask 有上行则查角色控制与碰撞。`Key.isDown(87)=false` 单独不能证明 Host 吞键，已审代码也不足以宣布全部 AS2 和设备原因均被排除。

给测试员的低负担观察：同一次故障中记录 R 是否失效、分别轻按并松开左右 Ctrl 是否改变症状、何时恢复及是否已回基地，附同会话诊断包。Ctrl 轻按后恢复只是支持线索，不是独立证明；无变化也不完全排除事件序列。不要为验证猜测覆盖原档。

**停止条件**：取得可重复的同一丢失层和可区分干预，或明确交付一次带 B3 的现场采样；不继续从没有逐键信息的现有日志推导确定根因。

### I2：鼠标队列延迟与任务栏 / 焦点

`focus-trace.log:1462` 的 mouse.187 非注入，`hookDispatchMs=0`，观察到的后续 hook 返回 0；`:1606` 的 `WM_LBUTTONDOWN` 与其唯一关联，hookTime 和 `GetMessageTime` 同为 `51163484`，迟到 **8922 ms**。该点击最终进了处理函数，不能简单称为永久吞键。

期间有 142 条同一 managed thread 的其他事件，Flash 帧号由 28034 到 28158；削弱“整个 GUI / 游戏连续冻住 9 秒”的解释，不能证明队列为空。迟到消息处理时前台为 `Shell_TrayWnd`；邻近 `Activation gained` 不证明该快照时刻已回到游戏。

| 09-12 集中到达时间 | 最大延迟 | 原始定位 |
|---|---:|---|
| 09:58:56.792 | 3.265 秒 | `focus-trace.log.2:3149` |
| 11:06:47.433 | 5.125 秒 | `focus-trace.log.1:5576` |
| 22:44:38.141 | 2.094 秒 | `focus-trace.log:494` |
| 22:57:31.613 | 8.922 秒 | `focus-trace.log:1606` |
| 23:36:01.296 | 2.890 秒 | `focus-trace.log:4035` |

三个会话共 16 条 ≥2 秒的 down/up 边沿，归为 8 个按下、5 次集中到达，不是 16 次点击。全部慢事件到达时前台为任务栏；168 个原生 down 中有 160 个较快，其中 50 个也处于任务栏前台，所以相关性不能代替因果。

[WindowManager.cs](../launcher/src/Guardian/WindowManager.cs)通过跨进程 `SetParent` 嵌入 Flash。跨线程父子关系的隐式输入关联、共享输入顺序与过滤输入消息泵，能够解释非输入消息活动而输入不推进；这是优先检验的机制，尚无本事故调用栈证明。参考 Microsoft 的[父子窗口与输入队列](https://devblogs.microsoft.com/oldnewthing/20130607-00/?p=4143)、[共享输入顺序](https://devblogs.microsoft.com/oldnewthing/20130605-00/?p=4163)与[过滤输入示例](https://devblogs.microsoft.com/oldnewthing/20130606-00/?p=4153)。

下一轮在另一机器的隔离候选，以相同 native / AS2 身份复现死亡 → 复活 → 任务栏往返，先加有界消息泵状态；出现迟到时短时捕获线程栈或 ETW，区分共享队列顺序、过滤 / 嵌套循环和其他路由。自动夹具与真实键鼠旅程分开留证。

当晚 FocusRestore 都为 pass 1，未见显式 `AttachThreadInput` 的 pass 2；这只排除“该晚由 pass 2 直接触发”，不排除嵌入的隐式关联。第三方 `#32770` 弹窗或任务栏 capture 不足以指认某程序安装了吞键 hook。23:01:08.434 一次 fg=0 快照与约 39 秒后重新激活，也不证明全程前台为空。

**停止条件**：找到可复现积压条件与队列 / 栈证据，或明确下一次短时采样窗口。B2 可先降低迟到消息危害，不等这项唯一归因。

### I3：两名测试员是否同源

第一位精确恢复时刻未录到，且确认恢复前已回基地；“过两图恢复”与第二位“回基地才恢复”暂不能排除同源。第二位还缺失效键、触发动作、Launcher / SWF / Runtime 身份与日志。

下一次只补最小事实：是否仅 W，A/S/D/R 状态，是否死亡复活后切过任务栏，恢复在地图切换还是回基地之前，附同会话诊断包。按 B3 故障签名合并或分开；不因“老 bug”称呼强行合并，也不因聊天描述不同就断言不同根因。

### I4：选定可承诺的 Runtime 版本

旧 Chromium 机制失败、新 Chrome 对照通过，尚未证明最早修复版本，不能直接把 152 或某 SDK 配套版本定为最低 Runtime。优先测试准备实际分发的受支持 WebView2 版本，不必为 F1 穷举全部历史版本。

至少覆盖 F1 资产 / 安全回退、旧档报告恢复、Bootstrap / Overlay 初始化、常用面板、渲染器失败后的既有降级 / 恢复、焦点交接与普通用户权限。冻结前记录实际 WebView2 进程路径、版本、候选 build identity 和测试结果，再更新 B4 版本政策。W 是否解决仍依据 I1。
