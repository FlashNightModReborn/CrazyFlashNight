## 0. 术语

| 术语 | 含义 |
|---|---|
| 日常插话 | 玩家在 NPC 日常对话（`data/dialogues` 那套）播放过程中输入一句话，切换到 AI 聊天 |
| 任务插话 | 玩家在任务前/任务后对话播放过程中插话；模型必须回到任务主线 |
| 原对话 | 本组对话的原始台词数组（可能来自日常 XML，或任务 `get_conversation` / `finish_conversation`） |
| 已播历史 | 本组本次播放中**已经真正显示过**的台词，包括原作台词、$PC 台词、玩家插话、AI 输出；被模型改过且已播放的台词也计入 |
| 已越过 | 播放进度已经走过去的原始台词，包括已播放和被移除后跳过的；下一次插话不再把它列为剩余台词 |
| 原始剩余台词 | 从当前播放点开始、尚未越过的原对话台词；每次请求按 1..N 重新编号 |
| 参考续写 | 上一轮模型已经生成、但因为玩家中途插入或关闭而没有播放的新增/修改/移除；只作为下一次请求的参考，不重播、不进已播历史 |
| 新增（add） | 模型新写的一条台词；日常和任务都排在本轮最前面播放 |
| 改写（edit） | 模型按原始编号替换某一条原台词；可替换成多条 |
| nochange | 模型明确声明某个原始编号保持原文；台词为空 |
| remove | 模型声明移除某一条原台词 |
| end | 模型声明“从原第 N 条开始接回原文”；不输出 end＝本轮输出构成剩余部分的整组替换，不再使用原文 |
| mute | 任务插话专用；模型判定玩家输入无法接话时，本组后续禁止玩家说话 |
| 结束语（closing） | 日常插话的可选收尾台词；可为空。为空时本轮最后一条新增即为结束语 |
| 组内实例 | 一次对话组播放（一次日常组播放，或一次任务前/后对话播放）；同一组内多次插话共享一个 `dialogue_instance_id` |
| session | 后端会话库中的一条会话，对应一个组内实例；用于终端回顾、长期记忆与聊天记录 |

## 1. 背景、目标与范围

### 1.1 背景

游戏内的日常对话与任务前/后对话现在由 Native 对话框播放（已从 Flash 迁出）。玩家希望在这些对话中直接向 NPC 说话，由 AI 接着演下去，而不是必须先打开终端面板。

### 1.2 目标

1. 在 Native 对话 UI 内提供可展开的输入框；玩家发送后，先播一条 `$PC` 台词，再播模型输出。
2. 日常插话：复用终端聊天链路（含发布任务工具），但输出改成可逐条播放的对话，并提供可选的结束语。
3. 任务插话：禁掉任务发布类工具，模型必须回到任务原有脉络；支持按原始编号局部改写、nochange、remove、end、mute。
4. 一组对话一个 session；首次插入建立，后续插入复用；日常同一组重播时新建 session。
5. 首句尽早播放：模型完整输出一句，前端就能播一句，不等待整段结束。
6. 失败时不做任何额外操作，直接回到原对话逻辑继续播。

### 1.3 非目标

- 不把插话生成的内容写进 `dialogue_overrides.json` / `task_text_overrides.json`；运行时改写只影响本次播放。
- 任务插话不允许发布新任务、改案、确认、取消。
- 不支持为其他 NPC 新增台词（其他 NPC 的原台词可以 nochange/remove/按原编号改写，但不新增）。
- 不改终端聊天面板的 UI；终端只共用 session 数据库。
- 不做定时器自动关闭；“没及时回复”由玩家点击关闭/点过最后一条触发。
- 不做逐字流式；以“一句”为单位推送即可。

## 2. 已确认的架构与核心决策

| 编号 | 决策 |
|---|---|
| D-01 | 现役对话 UI 是 **Native**（C# Host 内），本功能不做在旧 AS2 对话框里。 |
| D-02 | 插话的线路/播放由 Host 侧 Native 会话掌握；AS2 的 wire `rowCount` 不变，Host 在本地追加/替换台词。 |
| D-03 | 玩家台词复用现有 `$PC` 台词播放方式；发送后本地立即播 `$PC`，同时后台发请求，用播放时间掩盖首字延迟。 |
| D-04 | 一组对话＝一个 session。日常同一组重复触发时，每次首次插入新建 session，不共用上一次的 session。 |
| D-05 | 插话本身不改聊天文件；运行时新增/改写/移除只存在于本次 Native 会话与后端 session 记录中。 |
| D-06 | 首次插入时，把本组在首次插入前已经播过的原作台词作为 session 已有历史写入；`$PC` 视为玩家输入，其他 NPC 的台词写成玩家侧动作描写 `【NPC名：台词】`。 |
| D-07 | 日常成功插话后，原对话剩余部分不再播放，由 AI 对话与结束语收尾；日常失败则回到原对话剩余部分继续。 |
| D-08 | 任务改写编号永远以“原始剩余台词”为基准；已经播放的（包括被模型改过且已播放的）不再让模型重写，已越过的也不再出现在剩余列表。 |
| D-09 | 没播放的新增/修改/移除只作为“参考续写”，不重播、不进已播历史；下一轮编号仍按原始剩余台词。 |
| D-10 | 每句台词从**开始显示**起就可输入，不等逐字播完，也不等整轮新增播完；播放中插入按 D-09 把未播内容转参考续写。唯一例外：一条超长台词被拆成多段时，前面的非末段可暂锁输入（UI 策略），末段开始显示即可输入。任务模式所有普通台词从显示起即可输入，整组唯一的锁是禁言。 |
| D-11 | 单条台词与结束语硬上限 165 字（约 UI 容量 195 的 85%），提示词要求 135 字（约 70%）；玩家输入上限 150 字。 |
| D-12 | 模型输出采用 JSONL，一行一个 JSON 对象；后端逐行解析、逐行推 SSE，首句尽早播放。 |
| D-13 | 插话提示词去掉所有动作描写要求，并明确“只允许输出对话内容，禁止任何动作描写或括号内容”；后端剥离括号内容作为机制闸。 |
| D-14 | 日常保留终端的全部工具（含任务发布、长期记忆、对话改写委派）；任务只保留查询/检索与长期记忆写入，禁掉任务类工具和对话改写委派。 |
| D-15 | 日常触发任务草案时跳过过渡语，等草案就绪后只给最终对话＋结束语；草案在玩家关闭对话后保留，可回终端继续。 |
| D-16 | “没及时回复”＝玩家主动关闭，或在最后一条（结束语/无结束语时的最后输出/任务组最后一条）上仍点击下一条；不设定时器。 |
| D-17 | 取不到有效返回时不做任何额外操作：无视这次玩家说话，直接回到原对话逻辑继续播；日常与任务一致。 |
| D-18 | 日常 session 落库后终端应能看到；任务 session 也落库但可用 title/来源区分；终端可见性是可选验收，不阻塞核心功能。 |
| D-19 | 老 exe 不做版本门控；首次展开输入框走现有 health/EnsureReady，接口不存在则按 D-17 降级。用户通常同时更新游戏与终端。 |
| D-20 | Native v2 的 `advance_past_end` 仍要求 `finalIndex == AS2 原始 rowCount-1`；Host 本地多播的台词不改变 AS2 rowCount，结束时按原始最后一行的编号发 finish。 |

## 3. 日常插话

### 3.1 入口与输入 UI

- 对话 UI 底部有一个默认收缩的入口（胶囊按钮/图标，文案如“说点什么…”），不遮挡原“下一条”操作。
- 点开后展开输入框并**在本组内一直保持展开**；本组结束/关闭对话 UI 后复位为收缩。
- 玩家台词上屏期间（含逐字打完、仍停在玩家行等“下一条”），输入框整条隐藏，不论展开与否；下一句非玩家台词上屏后才恢复。
- 输入框是单行文本，Enter 发送；中文输入法组词中的 Enter 只确认候选，不发送。
- 输入框最多 150 字，显示计数；输入时暂停游戏热键/按键采样，点击输入框不得推进对话。
- 输入可用时机：每句 AI 台词从**开始显示**起即可输入，不要求逐字播完或整轮播完；发送时若当前句仍在逐字显示，先补全当前句再播 `$PC`。一条超长台词被拆成多段时，前面的非末段可暂锁输入，末段开始显示即可用。
- 展开时如果终端未就绪，后台走 Host `EnsureReady`（health/拉起/bind）；期间输入框禁用并显示“正在连接通讯终端…”。失败则禁用并提示不可用，原对话照常继续。
- 展开面板头条右端有一个白色齿轮按钮：无论模型是否已配置、输入是否可用，都可点击重新打开插话的模型设置小窗；终端离线时先拉起终端再打开。收起态不显示齿轮。

### 3.2 一次日常插话的完整时序

1. 玩家在 NPC 任一句台词开始显示后（输入可用时）输入并发送；若当前句还在逐字显示，Host 先补全当前句。
2. Host 立刻把玩家输入作为一条 `$PC` 台词插入 Native 会话并播放（复用现有 `$PC` 的名字/立绘/播放逻辑；若本组前面出现过 `$PC` 行，沿用其外观）。
3. 同一时刻后台发请求，请求带上：本组已播历史、原对话剩余台词（仅参考）、玩家输入、日常模式。
4. 播放玩家台词期间输入 UI 隐藏（玩家自己说话时不能插话）。
5. 玩家台词播完进入等待：输入仍锁定，显示“……”（不生成 NPC 台词）；若第一句在玩家台词播完前已到，排队，等玩家台词播完再播。
6. 模型输出按 JSONL 逐句到达；第一句完整到达即开始播放，不等待结束语或 done。
7. AI 每一句**开始显示时输入即可用**；不必等该句播完，也不必等整轮新增播完。若当前句仍在逐字显示，发送时先补全当前句；发送即取消在途请求，已收到但未播的内容转参考续写。
8. 唯一例外：一条超长台词被拆成多段播放时，前面的非末段可暂锁输入（“（暂时不适合插话）”），末段开始显示即恢复可用。
9. 本轮新增播完后进入结束语；结束语从开始显示起即可输入。玩家此时可以：
   - 继续输入 → 结束语视为已播内容，开启新一轮插话（同一组、同一 session）。
   - 点击“下一条” → 关闭对话 UI，本组结束。
   - 不操作 → 停在结束语，不自动关闭（D-16）。

### 3.3 输入可用状态

| 状态 | 输入 UI | 提示 |
|---|---|---|
| 玩家 `$PC` 台词播放 | 隐藏 | 无 |
| 等待首句 | 显示但禁用 | “……” |
| AI 新增/结束语（自然单条） | **可用**（开始显示即可用） | 无 |
| 超长台词拆分的前置段 | 可暂锁（默认禁用） | “（暂时不适合插话）” |
| 任务草案生成中 | 显示但禁用 | “（正在准备…）” |
| 禁言（仅任务） | 显示但禁用 | “（NPC名）暂时不打算让你插话” |

发送时若当前句仍在逐字显示，先补全当前句；发送会取消在途请求，已收未播的新增/改写/移除转参考续写（D-09）。拆分前置段的暂锁对两种模式一致，防的是把一句话从中间截断；任务模式自然多行之间不锁，整组唯一的锁是禁言。v1 UI 直接按本表开放逐句输入，不再有“整轮新增期间统一锁定”的策略。

### 3.4 结束语

- 模型可以在本轮新增之后额外给一条 `closing`；也可以给空。
- 结束语不是固定句，任何能让本次对话自然收尾、不像中断的话都可以；优先根据玩家这句话做扩展，也可以选择参考或不参考原对话剩余内容。
- 结束语为空时，本轮最后一条新增就是结束语；点它后面的“下一条”关闭对话。
- 日常成功轮：AI 新增/结束语播完后即到组末，点“下一条”关闭本组；原对话剩余台词只作参考，不再接回播放。
- 失败轮例外：见 3.6，已播 AI 句之后回到原对话剩余继续。
- 结束语从开始显示起即可输入（不必等逐字播完）；发送时若还在逐字显示，先补全当前句。结束语前一条新增同样从开始显示起即可输入。
- 结束语播完后玩家仍可继续说话，等同于不结束、继续聊天流程；此时结束语已经算已播内容。
- 结束语同样受 165 字硬上限和 135 字提示词上限约束（D-11）；结束语被拆分时，前置段按 3.3 处理。

### 3.5 触发任务草案

- 日常保留终端全部工具，包括 `route_task_draft` 及草案存在时的 confirm/cancel/update。
- 模型决定发布任务时，不输出“我去准备一下”之类的过渡语；Host 保持等待状态，等草案就绪后只播放最终确认对话＋结束语。
- 结束语的大意是“不接的话就算了/这活就搁着”，但不要求固定措辞；具体由模型结合玩家的话生成。
- 最终对话播放完后，玩家回复即进入同一 session 的下一轮，模型可用现有 confirm/cancel/update 工具完成发布、取消或讨价还价；发布后走既有任务热重载。
- 玩家关闭对话后草案**保留**，可以回终端继续；不做关闭即作废。
- 草案生成期间输入锁定；玩家台词已经播过，不重复。

### 3.6 失败与降级

- 取不到有效返回（连不上、零条可解析、接口 404 等）：无视这次玩家说话，**直接回到原对话剩余部分继续播**；不播任何额外 NPC 台词、不弹额外提示、不做覆盖层写入（D-17）。
- 玩家已经播出的 `$PC` 台词保留在已播历史/session 中；没有对应的 AI 回复。
- 如果原对话已经到末尾、没有剩余可播，则按正常结束流程关闭。
- 收到部分有效句后流中断：已收到的句子照常播放，然后回到原对话剩余部分继续；不补写、不重试整段。
- 后端可在“零条有效输出”时做一次修复性重试；仍失败按上述处理。重试不得阻塞已经收到的句子。
- 播放中插入触发的取消只停止本轮后续生成；已完成的工具副作用不回滚（任务草案按 3.5 保留，长期记忆写入与已派出的对话改写委派沿用各自既有语义）。

### 3.7 重复触发与 session

- 日常一组对话可以重复触发（玩家再次找 NPC 聊天）。
- 每次**本次播放的首次插入**新建一个 session；session 包含本次播放从组开头到当前的全部已播内容。
- 下一次重复触发同一组时，再次首次插入仍新建 session，不共用上次 session，也不续写上次 session。

## 4. 任务插话

### 4.1 与日常的区别

- 任务插话发生在任务前对话或任务后对话中。
- 任务前入口：`GetTask`（接取）、选关界面的任务对话（接取前预览）；自动接取最终走 `GetTask`。任务后入口：`TaskRewardCommit`（结算对话）。这些入口必须显式标记 `task_pre` / `task_post`，并同时带任务 id（`dialogueTaskId`）。
- 任务对话的任务 id 由 AS2 随 book 报文传入（可选字段 `dialogueTaskId`）；Host 用它从任务目录/存档读取本任务、上一个已完成任务与 `next_task_id` 配对，组装 `task_context`。后端不反查游戏任务表。`task_pre`/`task_post` 组缺任务 id 或读不到本任务时，Host 不开放任务插话（fail-closed），不猜当前任务。
- NPC 此时不能发布其他任务：禁掉全部任务类工具（草案/确认/取消/改案），禁掉对话改写委派。
- 保留查询/检索工具与长期记忆写入（长期记忆写入在同一次调用内完成，不额外起一次调用，D-14）。
- 模型无论玩家说什么，最后都必须回到任务原有对话脉络；不能像日常一样聊开就不管后续。
- 输出不是“新增＋结束语”，而是“新增＋按原始编号改写＋接回原文/整组替换”。

### 4.2 任务上下文

游戏侧随请求上传两段任务摘要（后端不反查游戏任务表）：

| 对话类型 | 已完成任务（completed） | 将完成任务（upcoming） |
|---|---|---|
| 任务前对话 | 上一个任务 | 本任务 |
| 任务后对话 | 本任务 | 下一个任务（`next_task_id` 配对；没有则空） |

每段包含：

- 任务 id、标题、NPC；
- 通关条件/目标（`objectives`，逐条）；
- 奖励（`rewards`，逐条）；
- 已完成任务的“玩家完成了什么”（`outcome`，可由任务目标与完成状态生成；没有则用目标本身）。

没有上一个/下一个任务时对应段为空，提示词不拼该块。任务 id 只用于记录，不要求模型输出。

### 4.3 编号、“已播”与“已越过”

- 每次请求都把**当前播放点之后的原始剩余台词**按 1..N 编号给模型；编号与绝对索引的映射由 Host 维护。
- 已经播放的台词（包括被模型按编号改过、然后已经播放的版本）算已播，**不再出现在剩余列表**，也不允许下一轮再改写。
- 已经越过的台词（播放过，或被 remove 后跳过）也不再出现在剩余列表。
- 原台词被模型改过但**尚未播放**：原编号仍留在剩余列表（原文）；改过的版本只进“参考续写”，下一轮模型可以再次改写/移除/保持。
- 原台词被 remove 但**尚未越过**：原编号仍留在剩余列表；remove 只进“参考续写”，下一轮可再次移除或恢复。
- 上一轮新增但未播放：只进参考续写，不编号；下一轮的 `add` 整体取代它们。
- 参考续写块只用于让模型知道“上一轮本来打算怎么接”，不参与已播历史、不写入 session。

### 4.4 输出格式

任务模式一行一个 JSON 对象，字段如下：

| 字段 | 语义 |
|---|---|
| `{"mute":true}` | 可选，最先输出；本组后续禁止玩家说话 |
| `{"add":"…","emo":"普通"}` | 新增台词，排最前面按顺序播放；可多条 |
| `{"n":3,"nochange":true}` | 原第 3 条保持原文；台词为空 |
| `{"n":4,"line":"…","emo":"普通"}` | 用这条替换原第 4 条；同一个 n 可出现多次＝一条拆成多条 |
| `{"n":5,"remove":true}` | 移除原第 5 条 |
| `{"end":7}` | 从原第 7 条开始接回原文；之后的编辑/移除一律忽略 |

规则：

- **新增排最前**，然后按原始编号从前往后逐个检查；不需要改的显式 `nochange` 或直接留到 `end`。
- `end` 不输出＝不再接回原文，本轮新增＋改写构成剩余整组；只有在对原有信息脉络没有依赖、或整组都改完时才允许这样。
- 能直接用原文时必须用 `end` 接回，不做无实际意义的微调。
- 只改当前 NPC 的台词；其他 NPC 的台词一般 `nochange` 或让 `end` 覆盖，必要时才按原编号改写。不允许给其他 NPC 新增台词。
- 改写某条原台词时保留原说话人/称谓/立绘，只替换正文与情绪。
- 后端对 `n` 越界、`end` 越界、`nochange` 带正文、`remove` 带正文等做宽容处理：记录并忽略非法部分，不整段打回；内容是否漏信息只进提示词，不做强校验。

### 4.5 播放与接回

1. 玩家发送 → 播 `$PC` 台词，同时请求。
2. 收到 `add` 句即开始播；任务模式下 `add` 是当前 NPC 对玩家的回应。
3. 每句（新增、改写版、接回的原文）从开始显示起即可输入，禁言除外；超长台词拆分的前置段可暂锁（与日常一致）。任一句播放中发送按 4.6 处理。
4. 收到 `plan`（含 edits/end/mute）后，Host 从当前播放点构建后续序列：
   - `end` 存在：从播放点到 `end-1`，有 edit 用 edit，有 remove 跳过，其余用原文；从 `end` 到组末用原文（`end` 之后的编辑/移除忽略）。
   - `end` 不存在：只使用本轮新增与 edit 构成剩余内容，不再使用未改写的原文。
5. 播放过程中逐条标记“已越过”；编辑过的台词播放后以编辑版本进入已播历史，原编号不再可改。
6. 播到组末后点“下一条”关闭；本组结束。
7. 任务模式没有单独的结束语；组最后一条就是终点。

### 4.6 再次插话与中途打断

- 任一句（AI 新增、改写版、接回的原文）开始显示后、输入可用时（禁言除外），玩家可再次插话；Host 先补全当前句、取消在途请求、播 `$PC`，再发新一轮请求。新一轮带：当前已播历史、当前原始剩余台词（重新编号 1..N）、上一轮未播放的参考续写、玩家新输入、任务摘要。
- 在 `add` 新增段播放中插入：停止后续未播新增；未播新增转参考续写。若 `plan` 已收到但尚未应用，也一并丢弃，并把其中的改写/移除意图转参考续写（不应用到播放序列）。播放点仍停在当前原始剩余的第一条；新一轮按 4.3 重新编号。
- 在改写版/接回原文播放中插入：已播放/已越过的按 4.3 排除，剩余从下一条未越过的原始台词开始重新编号；未播放的编辑/移除意图只进参考续写。
- 已经播放的编辑版台词算已播；未播放的编辑/移除仍以原编号留在剩余列表，编辑/移除意图只在参考续写里。
- 移除只有在播放进度真正越过该条后，才从剩余列表消失。

### 4.7 禁言

- 玩家输入严重无法接话、无法正常回到任务主线时，模型可输出 `{"mute":true}`。
- 第一句 `add` 用符合 NPC 口吻的话无视、打断或化解；随后按正常 4.5 接回原文。
- 本组后续输入 UI 禁用并显示“（NPC名）暂时不打算让你插话”；本组结束/关闭后重置。禁言是任务模式唯一的整组输入锁。
- 禁言不影响任务状态机，也不写任何持久数据。

### 4.8 组结束与任务状态机

- 任务前/后对话的播完钩子仍由 Native v2 的 `advance_past_end` 触发；Host 追加的 AI 台词不改变 AS2 的 `rowCount`。
- Host 在真正播到组末时，用 **AS2 原始最后一行的 `finalIndex`** 发 finish（D-20）；AS2 的 `finalIndex == rowCount-1` 校验不受影响。
- 提前关闭用 `close`，`finalIndex` 取当前播放点**已到达的最大原始行号**（增强行不推进），并钳在 `[0, wireRowCount-1]`；没有原始行时为 0。任务前 `AddTask` 已先于对话、任务后奖励已先于 finish_conversation，提前关闭不破坏任务状态。
- Host 对 mutation 的 ack 若带 `rowCount`，只能是 **wire 行数**；本地增强行数不得写进 ack。`NativeDialogueService.onMutationApplied` 在 `appliedEpoch===s.epoch` 且 `resp.rowCount` 为数字时会覆盖 `s.rowCount`，带增强数会让后续 `advance_past_end` 全部被拒。
- Host 进入 closing 后立即取消在途插话流并 finalize；已收到但未插入的台词不再进入本组。
- 任务对话的下一任务配对沿用既有 `next_task_id`。

### 4.9 失败与降级

- 取不到有效返回：无视玩家说话，回到原对话当前播放点继续；不做改写、不输出额外台词、不写持久数据（D-17）。
- 收到部分 `add` 后失败：已播 `add` 保留；没有完整 `plan` 就不应用任何改写，直接回原对话当前点继续。
- 收到部分 `plan` 后失败：不应用不完整计划，直接回原对话当前点。
- 原对话已到组末则正常结束。

## 5. 请求 / SSE / JSONL 协议

### 5.1 请求

**路径（建议，后端按此实现）**：`POST /api/game/dialogue-interject`，SSE 响应。
**存档作用域**：沿用 `/api/integration/bind` 的绑定槽位；请求不重复传 slotKey。

```json
{
  "mode": "daily",
  "dialogue_instance_id": "全局唯一 UUID，同一组本次播放复用",
  "turn_id": "本轮唯一 UUID，用于重试幂等",
  "npc": "当前说话 NPC 名",
  "player_input": "玩家输入（≤150 字）",
  "session_title": "日常插话 · NPC名 · 2026-10-18 14:03",
  "dialogue": {
    "kind": "daily",
    "group_id": "可选；日常组 id / 任务文本 key",
    "played": [
      {"seq": 0, "role": "npc", "name": "NPC名", "text": "…", "emotion": "普通"},
      {"seq": 1, "role": "player", "name": "$PC", "text": "…"},
      {"seq": 2, "role": "other_npc", "name": "另一NPC", "text": "…"},
      {"seq": 3, "role": "ai", "name": "NPC名", "text": "…", "emotion": "普通"}
    ],
    "remaining": [
      {"index": 1, "name": "NPC名", "text": "原文台词", "emotion": "普通"}
    ],
    "reference_continuation": [
      {"kind": "add", "name": "NPC名", "text": "上轮未播新增", "emotion": "普通"},
      {"kind": "closing", "name": "NPC名", "text": "上轮未播结束语", "emotion": "普通"},
      {"kind": "edit", "index": 5, "name": "NPC名", "text": "上轮未播改写", "emotion": "普通"},
      {"kind": "remove", "index": 6}
    ]
  },
  "task_context": null,
  "limits": {"line_hard_max": 165, "line_prompt_max": 135}
}
```

任务模式：

```json
{
  "mode": "task",
  "dialogue": {"kind": "task_pre", "group_id": "任务文本 key"},
  "turn_id": "本轮唯一 UUID",
  "npc": "当前说话 NPC 名",
  "player_input": "玩家输入（≤150 字）",
  "session_title": "任务插话 · 任务名 · 任务前 · 2026-10-18 14:03",
  "task_context": {
    "completed": {
      "task_id": 200123, "title": "…", "npc": "…",
      "objectives": ["…"], "rewards": ["…"], "outcome": "…"
    },
    "upcoming": {
      "task_id": 200124, "title": "…", "npc": "…",
      "objectives": ["…"], "rewards": ["…"]
    }
  }
}
```

（任务请求同样带 `dialogue.played/remaining/reference_continuation` 与 `limits`，上例省略。）

字段约定：

- `role`：`npc`＝当前 NPC 原作台词；`player`＝$PC 台词或玩家插入；`other_npc`＝其他 NPC 的原作台词；`ai`＝当前 NPC 的 AI 输出。
- `dialogue.kind ∈ {daily, task_pre, task_post}`：`mode=daily` 只能为 `daily`；`mode=task` 只能为 `task_pre` / `task_post`。
- `remaining[].index` 与 `reference_continuation[].index` 固定为 **1..N**，与模型看到的 `n` 同口径；Host 负责与原始绝对行号互转。
- `played[].seq` 与 SSE `line.seq` 为 0 基单调序号；同一 session 内不重复。
- `played` 是**本轮玩家发送之前**的已播历史，包含首次插入前的原作台词；本轮 `$PC` 由 `player_input` 表示，不重复放进 `played`，由 finalize 按实际播放写入。同一 `seq` 不得重复。
- `reference_continuation` 只在有未播完的上一轮计划时出现；`kind ∈ {add, closing, edit, remove}`，日常未播的结束语以 `kind:"closing"` 进入。
- `reference_continuation` 的 edit/remove `index` 必须在当前 `remaining` 的 1..N 内；越界属 Host 记账错误，后端以 422 拒绝，不做宽容渲染。
- 后端只按请求现场拼提示词；session 历史不参与本轮上下文拼装，避免重复/错位。
- **组类型来源**：Host 从 Native book 报文的可选 `dialogueKind` 读取当前组类型，缺省按 `daily`；任务前/后对话由 AS2 在对应入口显式标记 `task_pre` / `task_post`。`stage` 不开放插话；未带标记的旧任务对话不在支持范围。
- `dialogue.group_id` 是 Host 侧的不透明组标识：当前实现填当前 Native book 会话的 `requestId`（形如 `nd:N`），同一组 append 不变，新 book 即新组。后端只记录/透传，不用于 session 定位；session 定位一律用 `dialogue_instance_id`。
- `emotion` 字段可选：Host 取该行原作立绘表情（`char` 的 `#` 后缀），缺省 `普通`；后端缺失时按 `普通` 处理。它只是语气提示，不要求与原作行语义严格一致，也不作为输入校验依据。
- **finalize 时机**：Host 可在每轮结束（done/error/cancel）发一次 best-effort finalize，并在关闭/组末再发最终一次；每次 `transcript` 都是截至当时的全量前缀，按 seq 幂等。关闭/组末那一次是权威收尾，每轮那次只用于尽早保住已播内容，不改变对账语义。
- 进入 closing（`advance_past_end` 或 `close`）后，Host 立即取消在途插话流并 finalize；closing 期间输入隐藏，不再接受新的插话。
- **2026-10-23 物品往来扩展（可选字段）**：请求可带 `action`（选项直连）与 `player_item_names`（仅 daily 索取池用）；2026-10-24 追加 `player_item_counts`（仅 daily 索取回复轮的持有提示）；SSE 新增 `action` / `item_claim` 与回执端点。完整 schema、状态机与降级见 §7.5；不带这些字段时，请求/SSE 行为与既有协议完全一致。

**finalize 请求**：`POST /api/game/dialogue-interject/finalize`，body `{dialogue_instance_id, turn_id?, transcript:[已播行]}`；`transcript` 使用与 `played` 相同的行结构，表示该 session 截至当时的**全部已播行**（含历轮）。后端以此幂等对账，未出现在 transcript 中的未播内容不落库。
**finalize 响应**：成功 `200 {"ok":true,"dialogue_instance_id":"…","session_id":"…","appended":N,"total":M}`；session 不存在且 transcript 为空时 `{"ok":false,...,"session_id":""}`。Host 以 `ok`/`session_id` 判断收尾成功，`appended`/`total` 仅供日志。

### 5.2 SSE 事件

```text
event: status
data: {"stage":"connecting|thinking|searching|drafting|waiting","ui_hint":"拟定委托中"}

event: mute
data: {"mute":true}

event: line
data: {"kind":"add|closing","text":"…","emotion":"普通","speaker":"NPC名","seq":0,
       "split":{"index":0,"count":2},"interim":true}

event: plan
data: {"end":7,"mute":false,"edits":[
  {"n":3,"kind":"nochange"},
  {"n":4,"kind":"edit","lines":[{"text":"…","emotion":"普通",
                                "split":{"index":0,"count":2}}]},
  {"n":5,"kind":"remove"}
]}

event: done
data: {"dialogue_instance_id":"…","session_id":"…","usage":{...}}

event: error
data: {"code":"…","message":"…","valid_lines":2}
```

- `status.ui_hint` 可选：子 Agent 的 ≤12 字进度提示（如「准备候选中」「拟定委托中」「校验修正中」「查资料中」）。它只用于等待占位，不写转录、不落库、不改变 plan/finalize 语义；缺失时 Host 回落 `stage` 文案，再缺失回落「思索中…」。
- `line` 只用于**当前可播放**的 `add` / `closing`；任务改写不通过 line 推送，统一在 `plan` 里。
- `line.interim` 可选，`true` 表示这是任务草案等待期由后端自行生成的过渡话（不是模型 JSONL 行）。它仍是一条正常 `add`，要进已播与 finalize；Host 另用它判断：玩家越过该句后若本轮尚未结束，继续显示最新 `ui_hint` 占位，等最终确认对话到达时原位替换占位。缺省/false＝普通台词，按既有末行推进语义收组。
- `split`：仅当一条模型正文被 165 硬上限拆成多段时出现，`index` 从 0 到 `count-1`；`count=1` 或缺省表示自然单条。Host 据此把非末段（`index < count-1`）按“拆分前置段”处理（可暂锁输入），末段开始显示即恢复可用。`plan.edits[].lines[]` 使用同一 `split` 结构。
- 首句 `line` 必须尽早发出：解析到第一条完整 JSON 并通过校验/拆分后立即推，不等 done/plan。
- `plan.end` 为 `null`/缺省＝不接回原文；该模式下 `nochange`/`remove` 没有可作用的对象，后端可以不放进 `plan.edits`（播放语义不变，Host 对两种形状都要兼容）；`mute` 可同时通过 `mute` 事件和 plan 下发。
- `done` 成功结束；`error` 失败结束。失败前已发出的 `line` 仍可能已播。
- `error.valid_lines`＝本轮已接受的有效正文行（`add`/`closing`/任务 `line`）条数，按模型输出行计、拆分前；`mute` 不计。
- 后端不得在 `line` 之前自动持久化 AI 台词；以 Host 的 finalize 已播记录为准。
- 物品往来新增 `action` / `item_claim` 两类 SSE 事件与 `action-result` 回执端点；形状、时序与终态边界见 §7.5.9。未启用物品往来的请求不会收到这两类事件。

#### 5.2.1 任务草案等待期的事件顺序

```text
status(thinking)
status(drafting)
status(drafting, ui_hint=准备候选中)
status(drafting, ui_hint=拟定委托中)
line(add, interim=true, 过渡话)
line(最终确认 add/closing, 无 interim)
done
```

- 过渡话只生成一次；若草案终态先到，则不发过渡话，直接进入最终确认轮。
- 玩家越过过渡话但最终确认对话尚未到达时，Host 继续显示最新 `ui_hint` 占位；最终对话首句到达时原位替换占位，不追加到占位之后。
- 过渡话必须只点方向，不报具体数字/物品/金额/人名/地名；不复述候选池范围。
- `ui_hint`/过渡话都失败或缺失时，退回既有 stage 文案与最终确认对话，不阻断主流程。

### 5.3 模型 JSONL

模型只输出一行一个 JSON 对象，不带 Markdown、代码围栏、解释文字。示例：

日常：

```jsonl
{"add":"…","emo":"普通"}
{"add":"…","emo":"普通"}
{"closing":"…","emo":"普通"}
```

任务：

```jsonl
{"mute":true}
{"add":"…","emo":"普通"}
{"n":1,"nochange":true}
{"n":2,"line":"…","emo":"普通"}
{"n":2,"line":"…","emo":"普通"}
{"n":3,"remove":true}
{"end":4}
```

- 模型必须在第一句可输出时立即输出第一行，不要等整段想完。
- 单条正文提示词上限 135 字；模型可自行拆多条。
- 禁止括号内容/动作描写；禁止输出说话人名字前缀之外的任何格式标记（如 `[动作]`）。

### 5.4 校验与降级

后端逐行解析：

1. 去掉空行/围栏；**完全没有任何 JSON 特征**的裸台词按 `add` 兜底接收（情绪留空，由 Host 回落默认表情）；带 `{}`/`[]`/`"key":` 等 JSON 特征但非完整对象的坏行记录并跳过。
2. 日常只收 `add` / `closing`；任务只收 `mute` / `add` / `nochange` / `line` / `remove` / `end`；裸台词兜底在两种模式下都按当前 NPC 的 `add` 处理。
3. 每条正文（含裸台词兜底）：剥离 `（…）` / `(…)` 内容；为空则丢弃该条。
4. 超过硬上限 165：按 5.6 拆分，拆出的多条保持同一情绪/说话人。
5. 情绪：JSON 行必须在当前 NPC 的 `npc_state_db` 情绪白名单内，否则回落“普通”；裸台词兜底的情绪为空串，由 Host 回落默认表情。
6. 任务 `n`/`end` 越界：记录并忽略该条；`nochange` 带正文、`remove` 带正文：按标记处理并忽略正文；`end` 指向被移除条目：跳到下一条未移除原文，没有则结束。
7. `nochange`/remove 缺失但 `end` 存在：`end` 之前的未提及条目视为 nochange（宽容）。
8. 整轮零条有效输出：可做一次修复性重试；仍零条则 `error`，Host 按 D-17 回原对话。

部分有效：已发出的 line 保留；错误后不补写、不重试整段。

### 5.5 情绪与说话人

- `add`/`closing` 的说话人固定为当前 NPC；Host 用当前 NPC 的名字/立绘，情绪映射到现有 `char`/表情机制。
- `edit` 保留原台词的说话人、称谓、立绘；只替换正文与情绪。其他 NPC 的情绪若不在其白名单，回落原台词情绪或“普通”。
- 玩家 `$PC` 台词使用现有 `$PC` 播放逻辑；情绪不参与模型输出。

### 5.6 字数与拆分

- UI 正文框容量（源码估算）：文字宽约 476 本地 px、字号 12、行高 14.4、框高 72.65，约 39 字/行 × 5 行 ≈ **195 个中文字**。
- 硬上限 **165**（约 85%）；提示词要求 **135**（约 70%）；**单条台词与结束语同口径**；玩家输入上限 **150**。
- 拆分算法（后端，对每条模型正文和结束语）：
  1. 若长度 ≤165，原样。
  2. 否则取“不超过 165 的最长前缀”，优先在 `。` 结束；没有则 `！？…；`；再没有则 `，、：`；最后硬切。
  3. 对剩余部分重复，直到全部 ≤165。
  4. 拆分后的每段独立作为一条 `line` 推送（plan 内的改写行同理），顺序不变；每段带 `split:{index,count}`，供 Host 识别拆分前置段并暂锁输入。
- 不做“本次回复总上限”；任务组可以很长，只约束单条。
- 运行时需在 Native 正文框做一次实测校准并记录最终数字；若实测容量不同，按同一 85%/70% 比例调整，并同批更新本节。

### 5.7 流式首句

- 后端 LLM 客户端按 delta 收流；JSONL 解析器按行缓冲，每完成一行立即校验/拆分/推送。
- 第一句 `line` 不得等待整轮、plan 或 done。
- Host 收到第一句即可播放；玩家台词播放期间到达的首句排队。
- 工具调用/草案生成导致的延迟用等待状态表现，不用过渡台词填充。

## 6. Session、历史与记忆

### 6.1 一组一 session

- 每个 `dialogue_instance_id` 对应一个 session；首次插入时创建，后续插入复用。
- 日常同一组重播：新的 `dialogue_instance_id`＝新 session；不续写旧 session。
- 任务前/后对话：每次组播放一个 session；同一组连续多次插话共用一个。
- 没有发生任何插入的组不创建 session。

### 6.2 session 内容与角色映射

session 记录**已播内容**（从组开头到当前），映射规则：

| 已播内容 | session 角色 | 说明 |
|---|---|---|
| 当前 NPC 的原作台词 | assistant | 首次插入前已播的也要补；之后播放的原作/改写版也追加 |
| `$PC` 原作台词 | user | 视为玩家当时说的话 |
| 其他 NPC 的原作台词 | user | 内容写成 `【NPC名：台词】`，作为玩家侧的动作描写，避免模型误认当前 NPC 说的 |
| 玩家插入的话 | user | 原样 |
| AI `add` / `closing` | assistant | 只记录真正播放过的 |
| 被模型改过且已播放的原台词 | assistant/user | 按原说话人映射，正文用改后版本 |

- 首次插入：先把首次插入前已播的原作历史写入 session；再把玩家本轮输入写入。
- 之后每轮：只追加真正播放过的内容；未播放的 `add`/edit/remove 不写入。每轮 `$PC` 在 finalize 时按实际播放追加，请求的 `played` 不重复包含本轮 `$PC`。
- 失败轮：玩家的 `$PC` 台词已在 session 中；没有 AI 回复；原对话继续时后续原作台词按规则追加。
- 写入以 Host 上报的已播记录为准：请求带 `played` 现场，关闭/组结束时带 finalize；后端按现场对账，不把“已推送但未播放”的台词写进去。

### 6.3 终端可见与继续

- session 使用正常会话表（title、npc_name、slot_key），`/api/game/sessions` 按绑定槽位列出。
- 标题建议：`日常插话 · NPC名 · 时间`；`任务插话 · 任务名 · 任务前/后 · 时间`。
- 终端打开后应能看到这些 session 并回顾；继续聊时走终端自己的请求/提示词逻辑，不要求插入流程与终端流程耦合。
- 若终端列表当前只显示/筛选特定来源，允许在终端侧加最小展示；插入核心功能不以终端可见性为前置。

### 6.4 长期记忆

- 日常：保留终端的长期记忆工具与既有机制。
- 任务：保留长期记忆写入工具；它在同一次模型调用内完成，不额外起一次总结调用。
- session 的已播历史可作为记忆来源；原作台词按 6.2 的角色映射参与。
- 插话流程本身不写 `dialogue_overrides.json` / `task_text_overrides.json`；对话改写委派是独立的持久化动作，见 7.4。

### 6.5 重试与幂等

- 每个请求带 `turn_id`；同一 `turn_id` 重发不得重复写入玩家消息或创建重复 session。
- finalize 按 `dialogue_instance_id` 对账，重复调用幂等；`transcript` 是该 session 截至当时的全部已播行（含历轮），不在其中的未播内容不落库。
- 不设独立 cancel 端点；真取消＝Host 关闭 SSE 连接。后端在客户端断开时取消 LLM/工具，随后由 Host 发 finalize 收尾；已播内容不因取消而丢失。
- 关闭/取消时 Host 发 finalize，后端以最终已播现场收尾。

## 7. UI、工具与交互

### 7.1 Native 输入控件

- Native 对话框是自绘 GDI+，没有现成输入框；实现前先做 spike：WebView2 输入浮层 vs WinForms TextBox。
- 硬要求：中文 IME 可用、组词 Enter 不误发送、获得焦点时不触发游戏热键/不推进对话、点击输入框不被“下一条”捕获、视觉与对话框风格一致。
- 默认收缩；展开后本组常驻；关闭/组结束复位。
- 输入上限 150 字，显示计数；Enter 发送；不做多行编辑。

### 7.2 播放状态机

```text
Collapsed
  └─展开→ Ready
Ready
  ├─发送→ PlayerLine（$PC 句播放；输入隐藏）
  │        └─播完→ Waiting（输入禁用“……”）
  │                 ├─首句到达→ Playing（每句开始显示即可输入）
  │                 └─错误/零有效→ 回原对话（输入随原对话解锁）
  └─关闭→ 结束
Playing
  ├─每句开始显示→ 输入可用（拆分前置段可暂锁，末段恢复）
  ├─玩家发送→ 补全当前句→ PlayerLine（取消在途；已收未播转参考续写）→ Waiting→ Playing
  ├─新增播完→ Closing（有结束语播结束语；无则最后一条新增即结束语）
  └─（任务）plan 应用→ 播改写/接回原文→组末→结束
Closing（开始显示即可输入）
  ├─继续输入→ 新一轮（同 session）
  └─点下一条/关闭→ 结束
任务：Playing 中每句（新增/改写/原文）开始显示即可输入；整组锁只有禁言（拆分前置段的暂锁只作用于该段）
Muted：本组输入禁用，提示“（NPC名）暂时不打算让你插话”
```

### 7.3 点击与按键语义

- 打字中点击“下一条”：先补全当前句，不推进。
- 当前句已完整：点击推进。
- 等待首句/任务草案生成期间：不响应推进（没有下一句可播）。
- AI 新增/改写逐字显示中：点击只补全当前句，不跳过；输入可用性不受点击影响。
- 结束语/最后一条：点击“下一条”关闭整个对话 UI。
- 输入框聚焦时：Enter 发送；Esc 不关闭对话（避免误操作）。发送时若当前句未显示完，先补全当前句。

### 7.4 工具矩阵

| 工具 | 终端 | 日常插话 | 任务插话 |
|---|---|---|---|
| 任务路由/草案/确认/取消/改案 | 有 | 有 | 禁 |
| 查询/检索 | 有 | 有 | 有 |
| 长期记忆写入 | 有 | 有 | 有（同轮完成） |
| 对话改写委派 `delegate_dialogue_rewrite` | 有 | 有，但提示词降权：只有非常必要时才调用 | 禁 |
| 赠送物品 `give_item_to_player` | 禁 | 有（仅日常） | 禁（提示词要求推辞） |
| 索取物品 `request_item_from_player` | 禁 | 有（仅日常） | 禁（提示词要求推辞） |
| 取消索取 `cancel_item_request` | 禁 | 有待处理索取时 | 禁 |

- 日常的对话改写委派在后台 worker 执行，不得阻塞插入请求/播放；如果出现模型/端点并发导致的明显前台延迟，优先在插入模式停用该工具。
- 任务模式不得写任何任务文件/覆盖层；只允许查询、记忆写入和对话输出；物品交接一律推辞（§7.5.1）。
- 物品动作与任务动作互斥：有待确认草案时不注册物品工具；有索取待处理时不注册任务草案/确认/取消工具；前者优先把当前索取处理完。

### 7.5 物品赠送与索取（2026-10-23 冻结；BACK/GAME 源码已施工，未进游戏验证）

作者裁定：日常插话里 NPC 可以直接赠送/索取物品，减少“要点小东西也要走任务发布”的摩擦；任务对话和终端不做物品交接，避免破坏任务脉络或出现“玩家不在场却收下东西”的抽象情况。

#### 7.5.1 范围

| 场景 | 赠送 | 索取 | 提示词 |
|---|---|---|---|
| 日常插话 | 有工具 | 有工具 | 工具说明＋物品往来记忆＋本组赠送明细 |
| 任务插话 | 禁 | 禁 | 明确推辞＋物品往来记忆 |
| 游戏内终端（embedded） | 禁 | 禁 | 明确“不能接收也不能赠送；声称已送但账本无记录＝不是真的”＋物品往来记忆 |
| 非游戏启动（standalone 终端） | 不变 | 不变 | 不注入任何物品块、不注册物品工具 |

- 任务模式与终端只通过提示词约束，不设置物品工具。
- 物品账本只在游戏内（embedded）读写；standalone 不写、不注入。
- 任务模式推辞口径：当前不能赠送、不能索取或接收物品；玩家提出时推辞——任务紧急就用“任务紧急，先处理要事”作理由，任务看起来不重要就说“等忙完再说”之类，按情景决定。

#### 7.5.2 工具

日常插话新增三个工具，但**不在一轮里同时注册**：

```text
give_item_to_player(name?, quantity, keyword?, instruction?)
request_item_from_player(name?, quantity, keyword?, instruction?)
cancel_item_request()
```

| 轮次状态 | 注册的物品工具 |
|---|---|
| 日常普通轮（无 pending claim） | 赠送、索取 |
| 调用赠送/索取的当轮 | 只处理该物品工具；工具结果后的最终台词轮 `tools=None`，三个都不注册 |
| 已有 pending claim 的后续玩家输入轮 | 只注册 `cancel_item_request`；不注册赠送、索取 |
| claim 关闭（接受/拒绝/取消/超时/组结束）后的下一轮 | 恢复赠送、索取 |
| 任务插话 / embedded 终端 / standalone | 不注册任何物品工具 |

- 没有 pending claim 时，模型没有“取消索取”这个动作可调；有 pending claim 时，也不能再发起新的赠送/索取，先把当前索取处理完。
- `cancel_item_request` 只在存在待处理索取时注册；玩家明确拒绝时调用。
- `quantity` 必填，正整数；`name`/`keyword`/`instruction` 至少一个；`name` 要求精确物品名，模型不确定就留空。
- 工具说明只写行为判据，不解释 Host/参数/系统机制。
- 调用工具的那一轮只发工具调用，不输出 add/closing；工具结果回来后用正常 JSONL 说最终台词。
- 工具结果后的最终 LLM 轮 tools=None：不出现赠送/索取工具说明，也不拼“调用工具的那一轮”纪律；只保留索取指令（如有）、物品信息块与正常台词格式。
- 工具结果/最终请求附物品信息块（名称、称呼、分类、单价、描述、获取途径），不把工具参数原文写进台词。
- 一轮最多处理一个物品动作；同轮多余的物品调用忽略并记录。
- 物品动作与任务动作互斥（§7.4）。

#### 7.5.3 有效池

- **赠送池**＝核心任务奖励池（`TaskRegistry.list_core_reward_item_names`）的全量物品，不是随机奖励子集。
- **索取池**＝有正常获取途径的物品（`item_sources`：合成、NPC 商店、K 点商店、关卡掉落、任务奖励）∪ 金币 ∪ Host 本组快照里的玩家持有物品名。
- 过滤（两方向共通）：剔除无价格物品（赠送无法计价）、战场补给、修改器/作弊专属、任务关键/绑定物品；索取另剔除经验值/K 点/技能点。
- 金币在索取**抽选**候选里固定排第一；关键词命中时按关键词结果排，不强行改序。
- 有效池只决定“可不可选”，不代表玩家真的持有；持有由 Host 在选项上实时查询。
- 装备类索取只查背包，不查穿戴中的装备栏；同名多件取强化度最低的一件，同强化度取背包顺序第一件。装备数量固定 1（模型给多件时按 1 件处理并说明）。
- 装备的持有数与最低强化度由 Host 显示选项时实时查询；后端只按物品名建池，不查背包实例。

#### 7.5.4 名称解析与子 Agent

1. `name` 精确命中有效池 → 直接使用，不跑子 Agent。
2. 否则若有关键词 → 在有效池内关键词检索（最多 10 条）。
3. 无命中/无关键词 → 从有效池抽 10–20 条；索取池抽选把金币放第一位。
4. 把候选（含物品信息块）、**本轮候选之外剩余池**的分类计数（武器/防具/消耗品/材料/其他/金币）与有效池总数、原始指示交给物品选择子 Agent。
5. 子 Agent 每轮只能返回：选定精确物品名 / `none` / `search:<新关键词>`；`search` 只允许一次，第二轮只能选物品或 `none`。
6. 返回名必须仍在有效池；否则按失败处理，不得把模型编的名字直接交给 Host/AS2。
7. 失败结果回给聊天模型：赠送→拒绝赠送；索取→“未找到有效的物品，你要求的索取任务（名称/数量/关键词/指示）执行失败，无法索取，请在不能索取物品的前提下继续聊天”。

- 子 Agent 首轮允许直接判 `none`；只有它认为换关键词可能有用时才申请再查一次。
- 每次候选都附剩余池分类计数与有效池总数，让它知道是否值得再查。
- 子 Agent 不写台词、不调物品写入；只返回物品名或失败。

#### 7.5.5 赠送

- 价值上限＝按“传话”类任务的奖励上限（阶段基数 × 好感系数；不含提交/持有加成）。
- 单价取物品注册表；金币/经验值/K点/技能点/强化石用固定单价；无价格物品直接失败。
- 请求数量×单价 ≤ 上限：按请求数量赠送。
- 超过上限且数量>1：自动降到 `floor(上限/单价)`；金币/经验值再向下取整到 500 的倍数；降到 0 则失败。
- 1 个都超过上限：失败，工具结果给出“你选择了赠送XXX，因价值过高，赠送失败。”；模型必须据此拒绝，不得声称已送。
- 没有硬性频次上限；靠提示词的场景判断和本组赠送明细约束。
- 成功路径：工具轮发 `action`（Host 执行 AS2 真实发放）→ Host 回执成功 → 后端记账本/本组明细 → 最终 LLM 才说“已赠送 X 个”（实际数量，可能被自动下调）；工具结果附物品信息块，并说明“原请求 N、实际 X、因价值上限调整”。
- 执行失败/回执超时：不记账本、不说已送；模型按失败拒绝。
- 提示词判据：关系不错、财大气粗、打算讨好/答谢玩家等场景才送；不想送时即使玩家索取也拒绝，不调用工具。

#### 7.5.6 索取

- 无价值上限；金币可索取，经验值/K点/技能点不可。
- 成功解析后：后端保存 pending claim（一次只一个），SSE `item_claim(state=pending)`；工具结果要求模型用符合身份的话向玩家索要/询问是否给；最终 LLM 轮不再注册赠送/索取工具。
- Host 收到 claim 后查询当前持有，显示两按钮＋原输入框：
  - 普通物品：`赠送X个XXX（当前持有Y）`；持有不足时 Y 标红且按钮禁用。
  - 装备：只统计背包、不含穿戴中；同名多件取强化度最低的一件。强化度 Z>1 时按钮为 `赠送 1 个 XXX （当前持有Y个;强化度为Z）`；Z≤1 或背包无货时沿用普通文案并置灰。Y 为背包内同名数量，Z 为背包内同名最低强化度。
  - `不赠送`。
  - 输入框保持原占位（“说点什么…”），玩家直接说话＝聊天，不改文案。
- 点“赠送”：Host 先重新查询背包并扣除选定的那件（金币特殊处理），成功后再发 `action(kind=item_take_accept)`，装备附 `item_level`；后端记账、清 claim、最终 LLM 说已收到。扣除失败则不发成功结果，保留/关闭选项按 §7.5.10，模型按失败回应。
- 点“不赠送”：发 `action(kind=item_take_decline)`；后端清 claim、不记账，模型回应。
- 玩家直接输入：正常一轮；prompt 带 pending claim 块。模型可调用 `cancel_item_request` 取消；不调用则 claim 保留，Host 继续显示选项。玩家口头答应不算已交付，只有实际交付动作算。
- claim 在组结束/关闭/超时（建议 10 分钟）清空；单轮 `done` 只表示本轮结束，不清 claim。数量固定，v1 不支持部分赠送/改数量，玩家要先拒绝再重新提出。
- 两按钮的可用性只由“存在 pending claim + AS2 真实持有”决定，不跟随输入框的启用/禁用状态连坐；输入框仍按原有规则可聚焦打字，占位文案不变。
- 索取失败（解析不到有效物品）不创建 claim，不显示选项。
- 提示词判据：通常索取物品应走任务发布；只有玩家主动提出送且不要报酬、玩家声称已经送了（含动作描写）、NPC 想要但不想付报酬、或只是价值不高的小东西时，才调用索取工具。
- 索取工具结果：`你现在要索取物品：{X}个{XXX}，该物品确认有效，可以索取。现在，请用符合你身份且符合上下文的语句，向玩家索要物品或询问玩家是否要把该物品给你。` 后附物品信息块。最终 LLM 轮 `tools=None` 且 system 不带物品工具说明；该限制由机制保证，不在文本里写“不要调用”之类否定句。
- 索取完成（玩家点赠送后）：普通物品拼“玩家把 X 个 XXX 交给了你”；装备拼“玩家把 1 个 XXX（强化度Z，{成本描述}）交给了你”，物品信息块再加一行强化度与成本描述。Z>1 才加强化度与成本描述：Z<5 为“经过了一定幅度的强化”，5≤Z≤8 为“经过了较高成本的强化”，Z≥9 为“经过了极高成本的强化”。

#### 7.5.7 记忆与提示词块

- 新增跨对话账本（按存档＋NPC＋方向＋物品名合并数量）：

```text
【物品往来记忆（跨对话）】
你曾经送给玩家以下物品：3个XXX，1个YYY
玩家曾送给你以下物品：5个ZZZ
```

没有就写“无”；两行都保留。该块进入 daily/task 插话与 embedded 终端；standalone 不注入。

- 本组赠送明细（只在 daily 插话、只在同一组内）：

```text
【本组已赠送】
第1轮：3个XXX
第3轮：1个YYY
```

成功赠送时记录实际数量；不跨组，组结束清空。跨组只保留上面的数量总账，不保留逐轮明细。轮次＝本组内第 N 次插话请求（turn_id），从 1 开始；同一轮多次赠送合并写在同一轮。

- 最近成功块：赠送成功由上面的本组明细覆盖；索取成功另保留 2–3 轮的“玩家刚刚给了你 X 个 XXX”，装备再带强化度与成本描述，例如“玩家刚刚给了你 1 个 K5项链（强化度6，经过了较高成本的强化）”。强化度只进本轮与最近成功块，不进跨对话账本（账本仍只按物品名合并数量）。
- 失败/拒绝信息只保留最近 2–3 轮，不进账本：赠送价值过高失败、索取找不到物品、玩家拒绝赠送。
- 日常插话提示词：口头答应不等于交付；只有东西真正到你手上才算。玩家声称已送但账本没有记录时不要当真。
- 任务模式提示词：按 §7.5.1 的推辞口径；不描述不存在的工具。任务本身的提交/奖励按既有任务机制，不在对话里直接交接。
- 终端（embedded）提示词：不能接收玩家赠送，也不能赠送玩家物品；玩家要送就让其当面来；玩家声称已送但账本没有记录＝不是真的。任务奖励、商店买卖等既有机制不受此限，这里只限制玩家主动赠送。

#### 7.5.8 选项直连（任务接受/拒绝）

- 现有“我接了/我不接”不再先当成普通玩家输入路由；Host 发 `action(kind=task_accept|task_decline)`，后端预执行确认/取消，跳过路由 LLM 轮，只做最终台词。
- `action_id` 对任务动作同样幂等：重复/重试只返回首次结果，不重复发布或取消；首次结果未知时不得自动重放发布，按任务发布恢复合同核对。
- 只对插话输入条的选项生效；终端和其他聊天仍走原链路（玩家手打同样文字不保证直连）。
- 后端执行失败（无草案/发布失败）时，结果块告诉模型失败，模型正常回应；Host 本轮不再重复弹“我接了/我不接”。
- 确认文案生成的那次 LLM 仍在；本改造只省一次路由调用。

#### 7.5.9 请求/SSE/回执扩展

请求可选字段：

```json
"action": {
  "kind": "task_accept|task_decline|item_take_accept|item_take_decline",
  "action_id": "幂等 UUID",
  "claim_id": "索取时必填",
  "item_name": "索取时必填",
  "quantity": 3,
  "item_level": 6
},
"player_item_names": ["玩家当前持有物品名"],
"player_item_counts": {"物品名": 3, "金币": 100}
```

- `player_item_names` 只用于索取池；不代表持有数量，不进入台词/prompt。
- `player_item_counts` 只用于索取回复轮：Host 在同一份持有快照上附带 `name → 可交付数量`（金币取 `money`，装备取背包件数）。仅在玩家回复 NPC 索取的那一轮（pending claim、无 `action`）追加到【待处理的索取】末尾：数量 0 → “玩家看起来没有这个物品。”；不足 → “玩家看起来拥有该物品的数量不足。”；足够不追加。NPC 发问那一轮尚无 claim，不拼；任务模式不查询也不发送。
- `item_level` 只在 `item_take_accept` 且物品为装备时出现，Host 传背包内实际扣掉那件的强化度；后端只用于拼接提示，不据此校验背包。
- `action` 只在选项点击时出现；普通打字不带。
- 选项点击轮的 `player_input` 就是玩家那条可见台词，四选一：`我接了`／`我不接`／`【赠送了X个物品名给NPC名】`／`【没有赠送物品】`。X 取真实扣除数量（不是索取请求量）。它同时进游戏对话框和后端上下文，后端按普通玩家发言处理，`action` 仍单独决定扣增、claim 关闭与幂等；失败重试与无头补送复用同一份 `player_input`，且不再重复显示 `$PC`。

SSE 新事件：

```text
event: action
data: {"action_id":"…","kind":"item_grant","npc":"NPC名","item_name":"…","quantity":3,"requested_quantity":5}

event: item_claim
data: {"state":"pending|closed","claim_id":"…","npc":"NPC名","item_name":"…","quantity":3}
```

- `action(kind=item_grant)` 要求 Host 执行真实发放并回执；Host 不得只播台词不落地。
- 回执端点：`POST /api/game/dialogue-interject/action-result`，body `{action_id, success, error?, actual_quantity?, overflow_money?}`；同 action_id 幂等。
- `item_claim(state=pending)` 后 Host 显示两按钮；`closed` 用于模型取消/组结束，Host 清选项。
- `action`/`item_claim` 不是终态；`done`/`error` 仍是唯一终态。

#### 7.5.10 降级

| 场景 | 行为 |
|---|---|
| 赠送 AS2 失败/回执超时 | 不记账本、不说已送；模型按失败拒绝；Host 记日志 |
| 赠送已发放但回执丢失/迟到 | Host 用同 action_id 重试；后端按 action_id 幂等，迟到回执仍补记账本（物品已动），但本轮不声称成功；仍失败则记日志对账 |
| 赠送已发放且账本已记，但最终台词零有效/报错 | 物品与左下消息不撤销、不重放；下一轮按账本显示；本轮无台词 |
| 索取解析失败/子 Agent 超时 | 不建 claim、不显示选项；模型说明无法索取 |
| 索取已发 `pending`，但本轮最终台词零有效/报错 | `error` 前补发 `item_claim(closed)`（best effort）并清 claim；Host 收 `error`/断线也清选项；下一轮无 pending |
| 玩家点赠送但持有不足/扣除失败（含装备只剩穿戴中、背包已空、强化度已变） | Host 点击时重新查询背包并按实际最低件扣除，不按旧强化度/旧实例扣；失败不记账、不发成功 action，保留/关闭选项按实现，模型按失败回应 |
| 玩家点赠送、Host 已扣但请求未达/失败 | Host 保留 claim 与同 action_id，重试同一请求；不得再次扣款；后端按 action_id 幂等补记账；仍失败则记日志人工对账 |
| 账本写失败 | 物品已真实转移；记日志，不中断本轮；下轮按已有账本显示，必要时人工对账 |
| 流在 action 等待期断开 | Host 已执行则尽量回执；后端取消等待；记日志，不产生半截 claim |
| claim 超时/组结束 | Host/后端都清 claim；不再显示选项 |

## 8. 错误与降级矩阵

| 场景 | 行为 |
|---|---|
| 终端 exe 不存在/未就绪 | 展开输入时提示不可用并禁用；原对话照常 |
| 老 exe 无插话接口 | 首次请求失败→按 D-17 回原对话；不做版本门控 |
| 请求超时/断线 | 已播句子保留；回原对话剩余 |
| 零条有效 JSON | 可选一次修复重试；仍失败→回原对话，无额外台词 |
| 部分有效后中断 | 已播句子保留；不补写；回原对话剩余 |
| 括号/动作描写 | 后端剥离；为空则丢弃该条 |
| 超 165 字 | 按句末拆分，不打断语义 |
| 情绪非法 | 回落“普通”/原情绪 |
| 任务 n/end 非法 | 忽略非法部分，宽容继续 |
| 玩家关闭/点过最后一条 | 取消在途请求（真取消），未播内容不落盘，session 按已播 finalize |
| 已进入 closing | 隐藏输入、真取消在途流、按已播 finalize；不再接受插话 |
| 每轮 done/error/取消 | 可发 best-effort finalize 保住已播内容；关闭/组末的最终 finalize 为权威收尾 |
| 播放中再次插话（默认可输入） | 补全当前句、取消在途、播 `$PC`；已收未播新增/改写/移除转参考续写；新一轮同 session |
| 赠送/索取子 Agent 超时或失败 | 不创建 claim、不发放；工具结果告诉模型失败，模型按角色拒绝 |
| 赠送 AS2 执行失败/回执超时 | 不记账本、不说已送；模型按失败拒绝（§7.5.10） |
| 索取选项扣除失败（持有不足/并发变化） | 不记账、不发成功 action；保留或关闭选项按实现，模型按失败回应 |
| 账本写失败但物品已转移 | 记日志、不中断本轮；下轮按已有账本显示，必要时人工对账 |
| 任务模式/终端出现物品交接请求 | 不注册工具；按提示词推辞，不产生任何物品写入 |

## 9. 兼容性与证据边界

- Native v2：Host 维护 `wireRowCount`（AS2 原始行数）与本地增强行列表；结束用原始 `rowCount-1` 发 `advance_past_end`，提前关闭用 `close` 且 `finalIndex` 在原始范围内。必须加单测证明 AS2 校验通过。
- AS2 为任务前/后插话识别做一次可选字段扩展：`SetDialogue` / `handleAssign` 透传 `dialogueKind` 与 `dialogueTaskId`，Native book 报文可选携带；`dialogueKind` 缺省 `daily`，`dialogueTaskId` 只在任务组出现。日常插话不依赖这两个字段；该扩展需重编 SWF 才能在游戏内生效，编译授权与证据另记。
- G0 验证未发现 finish 之外还有校验；Host 侧完成拼接与 finish 单测，AS2 wire 语义未改。
- 老 exe：不做能力版本门控；首次展开走现有 `EnsureReady`；接口不存在按失败降级。用户通常同时更新游戏与终端。
- 旧/新 Host 与 SWF 组合：插话是 Host 侧能力；旧 Host 没有入口；新 Host + 旧 SWF 只要 finish 契约不变即可工作。
- 本批文档只定义需求/协议；实际可运行性要等 Native Host 构建、候选运行和真模型走查，证据级别按仓库 AGENTS.md 的 `compiled → candidate_built → candidate_executed → e2e_verified` 分层。

## 10. 明确不做

- 不把插话内容写进对话/任务文本覆盖层。
- 任务插话不发布新任务、不改案、不确认、不取消。
- 不为其他 NPC 新增台词。
- 不做定时器自动关闭/自动结束。
- 不做逐字流式；以句为单位。
- 不改终端面板 UI；终端只读共用 session。
- 不引入新的对话数据格式或改原作 XML/JSON。
- 物品往来 v1 不做：战备箱扣除（按 `ItemUtil` 原生容器：背包/药剂栏/材料/情报）、经验值/K点/技能点索取、任务关键/绑定/战场补给物品、部分赠送或改数量、终端物品工具、跨组逐轮赠送明细、穿戴中的装备索取、同强化度装备的进阶/词条区分与槽位展示。

## 11. 验收标准

### 11.1 日常

- [ ] 展开输入后本组一直保持展开；关闭后复位；输入框中文 IME 正常，组词 Enter 不误发。
- [ ] 发送后先播 `$PC` 台词，同时后台请求；首句到达即播，不等待结束语/整段。
- [ ] 每句 AI 台词从开始显示起输入即可用（不等逐字播完/整轮播完）；发送时补全当前句、取消在途请求，未播内容转参考续写。
- [ ] 超长台词拆分时非末段可暂锁、末段开始显示即可输入。
- [ ] 结束语为空时最后一条新增即结束语；点“下一条”关闭；结束语时继续说话可开启新一轮。
- [ ] 触发任务草案时不播过渡语；草案就绪后播最终对话＋结束语；关闭后草案保留。
- [ ] 失败/超时/零有效输出时无额外 NPC 台词，直接回原对话剩余继续。
- [ ] 同一组重复触发的新 session 不复用旧 session。
- [ ] 首次插入前已播原作进入 session；`$PC` 为 user，其他 NPC 为 `【NPC名：…】` user。
- [ ] 插话不产生 `dialogue_overrides.json` / `task_text_overrides.json` 写入。
- [ ] 赠送：精确名命中时不跑子 Agent；价值超上限自动降数量（金币/经验按 500 取整）；1 个都超限时只拒绝、不发放；成功时 AS2 真实入包并记账本/本组明细，失败时不说已送。
- [ ] 索取：解析成功显示两按钮＋原输入框；持有不足时数量标红且按钮禁用；点赠送才真实扣除并记账；点不赠送/模型取消清 claim；直接打字时 claim 保留、口头答应不算交付。
- [ ] 装备索取：只查背包、穿戴中拒绝；同名多件取最低强化度；Z>1 时选项显示强化度；完成时把强化度与成本描述拼给模型；跨组账本仍只记名字与数量。
- [ ] 索取池：金币在抽选候选第一位；金币可扣、经验值/K点/技能点不可；关键词池按关键词结果排。
- [ ] 物品往来记忆：跨组只显示数量总账（无则“无”）；本组赠送明细只在本组、按轮次列出；失败/拒绝信息只保留最近几轮。
- [ ] 任务对话和 embedded 终端不出现物品工具；任务对话按情景推辞；终端拒绝接收赠送，账本无记录时不承认玩家“已经送了”。
- [ ] standalone 终端不注入物品块、不注册物品工具，行为与改动前一致。
- [ ] “我接了/我不接”在插话输入条走 action 直连，不再多一次路由 LLM 调用；终端手打同样文字仍走原链路。

### 11.2 任务

- [ ] 任务模式无任务类工具；查询与长期记忆写入可用；提示词要求回到任务主线。
- [ ] 任务前/后分别拿到正确的已完成/将完成任务摘要（含条件与奖励）。
- [ ] 新增排最前；按原始编号 nochange/edit/remove；end 接回原文；不给其他 NPC 新增台词。
- [ ] 已播放的编辑版算已播，不再出现在剩余列表；未播放的编辑/移除只进参考续写。
- [ ] 任务模式普通台词（新增/改写/原文）全部从开始显示起可输入；禁言是唯一整组锁。
- [ ] 多条新增/改写/原文播放中插入（默认允许）→ 未播部分转参考续写，重新编号正确；禁言时不可插入。
- [ ] mute 时第一句化解，本组后续输入禁用并显示指定提示。
- [ ] 组末 finish 使用 AS2 原始 finalIndex，任务状态机正常推进。

## 12. 开放风险与待验证

1. **输入控件/IME**：Native GDI+ 上叠加输入控件的焦点、层级、中文组词；先 spike 再定。
2. **Native v2 finish**：Host 本地多播后台词后，仍须通过 AS2 `finalIndex == rowCount-1` 校验；加单测并进游戏验证。
3. **JSONL 模型遵从度**：不同模型的 JSONL/首句流式表现；零有效时的修复重试策略需真模型走查。
4. **字数实测**：G0-4 已按生产排版链路实测 5×39=195，165/135 成立；仍需游戏内正文框复验。
5. **终端 session 列表**：插入 session 是否直接显示、能否继续；若前端筛选则需要最小改动。
6. **对话改写委派并发**：保活时后台 worker 是否影响前台首句延迟；若明显则日常也停用。
7. **`$PC` 外观**：本组前面没有 `$PC` 行时，玩家插入行使用玩家当前外观/立绘的取值路径需验证。
8. **逐句输入的高频中断**：每句一开始就能插话，会比整轮锁定产生更多取消与半截计划；取消只停后续生成、已发生的工具副作用不回滚，需在 G0-3/P1 用 fixture 验证对账与 session 落库。
9. **物品权威写入与回执**：赠送必须 Host→AS2 真实发放并回执，索取必须 Host 真实扣除；回执丢失/流断开时存在“物品已动但账本未记”的窗口，需要 action_id 幂等、Host 重试与日志对账。不得用“模型已说送了”代替真实发放。
10. **物品池与子 Agent 选择质量**：赠送池是全量核心奖励池，价格跨度大；价值上限只防单次超发，不防模型反复赠送。需要真模型走查看场景判断与选择命中率，必要时再加频次/冷却。
11. **装备/变体扣除歧义（已收敛）**：穿戴中的装备不可索取；只查背包，同名多件取强化度最低的一件，同强化度取背包顺序第一件；选项在最低强化度大于 1 时显示该数值，完成时把强化度与成本描述拼给模型。仍不区分同强化度下的进阶/词条，也不展示具体槽位；若现场不可接受再扩展实例标识。
12. **金币扣除路径**：`ItemUtil.submit` 不处理金币；新 AS2 服务必须复用现有扣款/脏标/事务语义，失败不得先扣后报成功。经验值/K点/技能点明确不做索取，避免成长系统被绕过。
13. **任务对话类型标记**：AS2 当前只传 `mode=ordinary|stage`，任务前/后对话与日常同形。P2 必须补 `dialogueKind` 并重编 SWF，否则 P4 不进入；未标记时不得把任务对话当日常开放工具。
