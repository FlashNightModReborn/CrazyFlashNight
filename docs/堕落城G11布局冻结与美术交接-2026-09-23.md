# 堕落城 G11 布局冻结与 Blender 美术交接

**文档角色**：本轮美术施工工单与交付边界。2026-09-23，用户授权“按之前的规格思路冻结细化所必要的上下文背景资料，制作工单，打包准备由我转交给美术机施工”。G11 可作为美术布局底稿；不代表最终美术、默认游戏镜头或游戏集成已通过。

布局依据为 [G11 活动范围与深处街坊](堕落城G11活动范围与深处街坊-2026-09-23.md)；前序争议按 [G10 逐地点裁决](堕落城G10逐地点攻击审阅与范围裁决-2026-09-23.md) 解释。方法沿用 [三维选关创作与交接经验](三维选关场景创作与交接经验.md)，结合 [总部 R7 工单](黑铁会总部R7布局与美术交接-2026-09-20.md)，不照搬总部的灯光、镜头、面数或势力语义。

## 1. 收件目标与资料优先级

将堕落城从可解释的 G11 城建原型精修为可供游戏选关集成的风格化场景；延续废城、黑铁会总部的沙盘风格，并保留三层地势、城防环线与缺口、城区活动关系。先完成整体构图和代表区样板，再批量精修，避免细节做完后重新搬城。

交接目录为 `tmp/fallen-city-g11-handoff-20260923/`，压缩包解压后的根目录为 `fallen-city-g11/`。从 `WORK_ORDER.html` 进入；工单、源资料索引、历史交流和截图可离线阅读，Three.js 预览需用 `START_PREVIEW.cmd` 或 `python tools/serve.py` 启动本地服务。服务仅绑定 127.0.0.1；默认无写入接口，无外网依赖。Python 3 为接收机前置条件；源码检查另需 Node.js，Blender 导入脚本需接收机已有 Blender。

资料冲突按身份处理：游戏入口与关卡配置负责真实 ID、关卡内容；世界观原文负责已写定背景，情报文件保留叙述者局限；本工单及 G11 布局负责此次空间设计；旧审阅和聊天只负责追溯理由。遇到冲突列出原文与模型位置，不能以旧助手建议覆盖后续用户选择，也不能把空间解释自动写成新剧情。

## 2. 已冻结的空间关系

| 分区 | 保留关系与精修重点 |
|---|---|
| 整城地势 | 企业核心高地、招商/公共服务中层、低层产业与边缘住区形成三级；保留可读的坡道、桥下低槽、台地立面和实际出入口。不能用一圈光滑巨墙把城市做成港湾或水库。 |
| 黑铁会核心 | 方形园区与高地城防相接；总部和三堂为四个地标。参考现成总部的建筑本体与轮廓，制作城市尺度远景版本，不能复制总部独立选关页的全部外围环境。 |
| 城防工业环线 | 控制/通信、加工修造、试炼、货运、公用设施和灾损分段应可辨认；保留朝外的雷达、通信、导弹/束能装置轮廓，避免做成全向自动扫清一切的完好防御体系。 |
| 灾损与沙海 | 后方沙脊压迫城市；缺口向城内侵入，与军阀据点、争夺区和摇滚方向有空间关系。禁止为外观闭环而补齐缺口、掩埋通路或把设施一律修成崭新可用。 |
| 正常货运/人口进出 | 受控城市入口、物流接驳和黑铁会征收驻点有自身通路；军阀缺口不是所有人唯一进城口。跨高差道路必须有可读落地接口，不能误读成封闭管道。 |
| 商业街—酒吧 | 商业前场、服务/维修小院、酒吧外壳及室内是相邻且连续的街区段；外交室内有实际所属建筑，不能成为额外悬空房间。 |
| 大学—摇滚—赛事 | 一诺成遗产作为设计联系，具体占据、人物背景及现状按原文分述；大学靠近城防，校门、教学、宿舍、地下工坊有各自接口；摇滚舞台、后台与前场要可辨认。 |
| 死亡竞赛 | 低层露天多场地、主场/入门场、服务/医疗报名和训练环境区分；与 A 兵团试炼系统保持独立，不因同为战斗设施而合并。 |
| 试炼场 | 城防产业遗产与地下/内部支线相接；城市准入 TR01、厂房 TR02 与内部 T01—T03 不混为同一个门。内部锚点不要求在城市外观中建出整套地牢。 |
| 下水道 | 保留入口、服务院落与地下交通的区分；原地下关卡及转场作为依据，不把所有缺失城市基础设施随意塞进同一井口。 |
| 盗贼/居民 | 店铺收货、公共分拣、黑铁接驳和见缝插针的小势力有不同归属；不把全部居民楼涂成盗贼领地。深处沿主街进入 DF01 背巷，再抵 DF02 内院。 |

护盾失效原因、审判日打击、势力继承与地下设施用途等，保留在“已写定文本 / 可用设计解释 / 尚未定案”的各自层级。模型只表达遗产、损坏和控制现状，不擅自定案具体打击武器、幕后行动或支线结局。

## 3. 地点、建筑归属与战役覆盖

包内 `data/building-units.json` 是 70 个建筑单元清单，`data/activity-scopes.json` 是 42 个逐地点验收条目；`data/place-unit-catalog.html` 将参考图、原文来源、单元功能和关系放在一起，作为逐项施工清单。所有编号保持稳定，新子件可使用 `单元ID_用途_序号` 命名。

五类关系为主要活动、经过联系、共享服务、入口锚点、相邻参照。关卡经过一栋楼，不改变该楼的常驻功能或控制归属；同一栋楼可以服务多个关卡。保卫战 P18 覆盖商业街、酒吧、黑铁门前和摇滚终段，不能仅按入口归属，也不能把校园本体推断为战场。压制摇滚 P04 使用市区集结 AS01，不能搬回摇滚大本营。P07 深处的主要活动为 DF01/DF02，周边住宅是相邻环境。

游戏“基地车库”只有 **19 个真实关卡入口、4 个导航配置**。P/U/I/E/T 验收编号不是新增游戏关卡。`data/game-frame.snapshot.json` 保存真实配置，`selection-anchors.json` 保存 19 个稳定 ID 的视觉定位候选；`navigation-anchors.json` 区分 2 个世界定位候选与 2 个系统按钮。锚点不是唯一物理门口，也不是战役完整范围。

## 4. 允许美术发挥与需回报的调整

可直接细化屋顶、立面、门窗、材质、UV、破损、设备轮廓、招牌、生活小件和局部院落密度；强调企业建造层、后占据改建层、沙海与维修痕迹的区别。关键职能应能从默认视角的轮廓和院落读出，不依赖贴满文字。

道路接口、主入口、建筑归属、三层标高关系、灾损缺口、关卡范围、总部四地标和跨区联系属于冻结骨架。如有遮挡或美术理由需要调整，回包附 `changes.json`，逐项列原值/新值/原因/影响地点和对比图。未获进一步选择前，不擅自改关卡 ID、剧情内容、势力现状或跨层关系。模型不能把所有预留广场填满；集散、货运转弯、防火间隔与前场需要用途和尺度。

## 5. 编辑模型、坐标与重现

`model/fallen-city-g11-editable.glb` 从全新中性场景导出，保留实体地形、道路、楼群、城防和永久地面标记；不含路线审阅层、活动范围填色、选择高亮、DOM 标签。`checks/editable-export.json` 保存对象与单元信息，`checks/glb-roundtrip.json` 保存浏览器重导入结果。

模型未按运行时合批。源 Three 场景有 1451 个实体网格、45229 个三角形；导出时按材质面组拆为 1604 个单材质网格，三角形和世界包围盒不变。这是编辑组织差异，不能当作运行时 draw call 指标。70 个 `UNIT_编号__名称` 组及共享地形/道路/设备组独立保存；19 个关卡和 2 个导航世界候选以 `ANCHOR_真实ID` 空对象保存，C1/C2 镜头同样只是候选。

Three 坐标为 Y 向上，Blender 转为 `(x,-z,y)`，相对单位，不承诺 1 单位等于 1 米。保留原点和统一比例；禁止逐栋归零或重复烘焙变换。原始布局横向变换为 `(u-500)*0.24`；原始 v 在 135—255 范围伸展、255 之后整体加 100，再转换为世界 z。**当前 GLB 顶点已经完成高差和 v 变换，不能再次套用原始布局变换。** JSON 的原始 box、道路渲染坐标与 GLB 世界坐标不能混用。

接收机运行 `blender --background --factory-startup --python tools/import_into_blender.py`：导入独立场景、建立单元集合、核对网格/三角面/21 个锚点轴向、打包贴图，另存 `model/fallen-city-g11.blend`。脚本拒绝覆盖已有同名 blend。发送机未安装可用 Blender，未宣称本机完成 Blender 导入；收件端须提供 `checks/blender-inbound-check.json`。

`preview/` 保留 G11 可复现源码、冻结 G10 输入、逐地点查看器和原场景参考图。仅包内历史链接作便携化修正，原型现场未被改写。重新生成会覆写查看器，不应在已精修模型上自动重跑生成器。`checks/frozen-inputs.json` 保存来源哈希；`data/package-overrides.json` 解释包内差异。

## 6. 分阶段交付与验收

1. **接收与构图检查**：先验证 manifest，运行 Blender 导入检查。用 C1/C2 起步比较正面斜俯视和较高俯角；在 1024×576 看整城、三层地势、19 个入口及 2 个世界导航。回传整城无 UI / 定位叠加图、镜头参数、最拥挤街区局部和遮挡清单。包内入口投影是诊断标签，不是正式游戏 UI，重叠处需要处理。最终默认镜头仍需人类核对。
2. **代表组团样板**：商业街—酒吧—征收节点、大学—摇滚组团、城防缺口各做一个可见样板；黑铁四地标做尺度匹配。先看材质、光影和画幅内识别，再扩展到全部单元。不要先花大量时间做镜头看不见的室内。
3. **全量精修与逐项核对**：42 个地点逐项回报，70 个单元逐项标明保留/细化/调整，附全图编号和分区图。通路、入口、活动范围、建筑归属分别核对，不能以一张远景“看着不错”代替。
4. **回包供游戏集成**：交付编辑源、运行候选 GLB、贴图/烘焙源、可复现脚本和依赖版本、选择集合/对象来源映射、锚点与镜头、变更清单、性能数据及截图。游戏锁定状态、难度、简报、键鼠焦点和进关逻辑由项目侧接入；美术展示页不是游戏权威。

## 7. 光照、性能与回包合同

可参考 BM-009 固定光影与发光分工、BM-010 语义选择独立于合批；材质必须说明 lit/unlit、顶点色、色彩空间、AO/光照烘焙及 bloom 依赖。关掉 bloom 仍应看清建筑，高差不要只靠高光。若烘焙了主体光照，运行端不能再次重照导致发灰或过曝。

废城参考约 19.28 万三角形、8.62 MB；总部游戏模型约 5.33 万三角形、7.07 MB，仅作为可比较案例。G11 当前约 4.52 万三角形并不代表精修预算已满或已足够。回包报告三角面、网格/primitive、材质、纹理尺寸/数量、GLB 字节、实测渲染调用和测量环境。不能把编辑模型的 1604 个网格直接称为发布性能通过；最终体积和性能需要项目侧实际窗口验证。

建议回包结构：`source/` 放 blend 和完整可编辑源；`runtime/` 放候选 GLB 与贴图；`semantic/` 放 70 单元映射、19 关卡稳定 ID、4 导航、五类关系与独立选择覆盖；`scripts/` 放生成/导出/烘焙及版本说明；`review/` 放镜头、对比图、42 地点结果、变更与未解决项；`experience/` 放可复用技法与失败修正；根目录放 README、manifest 和校验脚本。运行模型允许合批，编辑源不能只剩一个无法分区的合并 mesh。
