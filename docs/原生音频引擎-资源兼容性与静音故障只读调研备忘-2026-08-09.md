## 1. 一句话结论

“部分音乐或音效播不出”已经可以程序化拆成资源、容器/codec、目录能力、桥接/readiness、播放图、真实设备和终端可听七层；当前树同时存在**确定的格式契约错位**、**确定的资源错配/缺失**和**可形成全静音假成功的 Null backend 路径**，但尚无 tracked 的端到端音频资格报告可以把所有玩家反馈归到单一原因。

## 5. 当前已确认事实

### 5.1 格式能力错位

- vendored miniaudio 是 `0.11.25`。
- miniaudio 内建 decoder 只有 WAV、MP3、FLAC；Vorbis/Opus 等需要额外 decoder。vendored `0.11.25` 含可接外部 `stb_vorbis.c` 的 optional wrapper，但 codec 本体不在仓库，不能表述为现役内建 Vorbis。
- `MusicCatalog.AUDIO_EXTENSIONS` 和玩家说明却把 `.ogg` 列为可发现格式。
- 当前 native 初始化没有注册任何 Vorbis backend，因此“出现在曲库”不等于“现役 DLL 可解码”。

官方依据见 [miniaudio decoding/manual](https://miniaud.io/docs/manual/index.html) 与 [custom decoder example](https://miniaud.io/docs/examples/custom_decoder.html)。

R2 前置取舍已核对：`stb_vorbis` push mode 的 cursor 会维护，外部评审所称“cursor 恒 0”错误；实际是 length 返回成功但为 `0`，后向 seek 需重建并向前解码。当前 BGM 又使用 resource-manager/VFS streaming，因此目标合同保留 libvorbis adapter 路线，以满足 duration/seek/EOF 资格语义。该结论是实现路线裁决，不代表现役 DLL 已支持 Vorbis。

当前 `runtime/miniaudio.dll` 大小为 `778240` bytes，SHA-256 为 `D022E69501D9589FE464038DA818F3EBF4241511C3EA0C18D19F384071811E2D`，与 `config/build/runtime-release-consensus.json` 中正式闭包记录一致。

这个 `79/11/1` 是当日 spot probe 与 2026-08-07 批量观察合成的 E2 调查分桶，不是同轮 91 文件完整重测或 tracked qualification：本轮没有对 79 个文件重新解码到 EOF，也没有证明播放图、真实 endpoint 或人工可听。

### 5.4 2026-08-07 动态观察的证据上限

先前交互式只读 probe 使用当前 DLL 做过批量 load 与 PCM 窗口采样：

- 11 个 MP4/AAC 伪装文件无法由当前 miniaudio decoder 加载。
- 其余 816 个候选均可加载，并在延长 warm-up 或 seek 后观察到非零 PCM。
- 676 个 SFX 资产的内容也观察到非零 PCM，但当时借用了 BGM peak 路由探测；这不证明真实 SFX fast-lane、voice pool、增益与设备端点 E2E。
- 初始 35 ms 窗口曾把 16 个文件误判为零，延长到 300–400 ms 或 seek 后均出现信号，证明“短采样为零”不能直接判定空音频。

该 probe 的原始输出没有作为 tracked qualification artifact 落盘，实施前必须重建为正式工具，不能用上述数字直接签发 Gate。

### 5.5 Null backend 假成功

当前 `ma_bridge_init()` 以 `ma_engine_config_init()` 生成的全默认 config 调用 `ma_engine_init()`。miniaudio 的 Windows 默认顺序包含 WASAPI、DirectSound、WinMM，并以 Null 为末尾；本地 vendored 实现明确写明 Null backend “always works”。因此当真实 backend/device 都失败时，初始化仍可能成功并运行一个不向物理设备输出的时钟/图。

这会产生完整的假成功表象：

- engine 初始化成功；
- 文件 load 成功；
- `ma_sound_start()` 可能成功；
- cursor/时钟前进；
- 插在 engine 图内部的 peak 可能非零；
- 玩家端始终无声。

这不是“文件本身为空”，而是设备层被静音 backend 吸收。

### 5.6 桥接与 readiness 缺口

- AS2 `playBGM()` 的 `true` 仅表示消息已送入 socket，不表示 native 已加载或启动。
- C# `AudioTask.Handle()` 明确 fire-and-forget；BGM 失败只写粗粒度 rc 日志。
- Launcher 当前在音频初始化失败时记录 warning 后继续启动，但没有版本化 `audio_unavailable`/降级状态供 AS2 与 UI 区分。
- native BGM 三条启动路径忽略 `ma_sound_start()` 返回值。
- SFX preload 异步进行；完成前 linkageId 解析为 `-1` 并静默丢弃。
- SFX fast-lane 忽略 `ma_bridge_sfx_play()` 的返回值，无法区分 throttle、未知 handle 和启动失败。
- 只有 BGM peak；当前没有 SFX bus peak，也没有选中 backend/device 的稳定诊断面。
- 旋转日志中 6 个 session 的 marker `[LaunchFlow] WaitingGameReady -> Ready` 早于完整 SFX preload marker，观察差为 `0.900–9.667 s`；源日志 SHA/mtime、session/ready/preload 最小原始行、signed pairing 规则与六个 delta 已固化在 [`research-ready-preload-observation.json`](evidence/audio-v2/research-ready-preload-observation.json)。它保存的是可审计摘要而非完整日志归档，仍只是 E2：证明 ready 合同存在窗口，但没有逐条请求证据，不能写成“窗口内已经发生玩家可达丢音效”。
- BGM peak 节点初始化失败会静默退化为零值；cursor/length/isPlaying 也把失败、未加载和真实零折叠为 `0`。
- 路径转换使用固定 1024 wchar buffer，超长会截断；负 `fadeSec` 在转 unsigned 毫秒前没有验证，可能形成极长淡入。
- native 全局 mutation 没有统一 owner queue；socket、UI polling、preload ThreadPool 和 shutdown 存在跨线程进入面，当前只有局部锁不足以证明生命周期安全。
- 当前 Launcher 测试中的 `AudioHudStateTests` 只覆盖 HUD 状态；未见 decoder、device、`AudioEngine`/`AudioTask`/`MusicCatalog` 或 native bridge 的专项资格门。

## 6. “可加载解析但播放为空”是否可能

答案是**可能，而且至少有五种不同语义**：

| 层 | 假成功形态 | 程序化判据 |
|---|---|---|
| 内容 | decoder 可打开，但帧全零或有效信号在很长前导静音之后 | 解码到 EOF，统计 frames、peak、RMS、leading/trailing silence、NaN/Inf |
| 播放图 | 文件有信号，但 source/group/master 增益为 0 或 start 失败 | 检查 start rc、cursor、各级 gain、BGM/SFX bus meter |
| readiness | 请求在 SFX 预载前或未知 ID 时被丢弃 | ready generation、pre-ready drop、unknown-id、start-failure counters |
| 设备 | engine 落入 Null，或真实设备停止/丢失 | backend/device identity、device state/generation、stop/reroute callback |
| 终端 | 图内有 PCM，但系统 mixer、endpoint 或用户硬件静音 | WASAPI loopback/端点捕获 + 人工听感 |

必须使用以下单向证据阶梯，禁止逆推：

```text
reference_exists
  → container_codec_identified
  → decode_to_eof_succeeds
  → decoded_pcm_nonzero
  → graph_started_and_advancing
  → real_device_active
  → endpoint_pcm_nonzero
  → human_audible_and_acceptable
```

## 7. 建议的程序化审计分层

### 7.1 Runtime catalog compatibility

catalog 热路径只做后台有界 probe：等待 `size+mtime` 稳定，content sniff + capability match 后限制 wall time、输入字节与 decoded frames；不要求 EOF、不用全零短窗口判 `ok_silent`。timeout/复制中输入分别保留 `inconclusive_timeout` / `unstable_input`，不得缓存成 unsupported/malformed。精确 R2 上限以 decision manifest 为准。

### 7.2 离线资产审计

对每个引用和物理文件输出稳定 JSON：路径、大小、SHA-256、extension、container、codec、decoder backend、frames、duration、peak、RMS、leading/trailing silence、non-finite count 和 EOF 状态。

最低分类：

```text
ok_nonzero | ok_silent | missing | unsupported_container |
unsupported_codec | malformed | truncated | io_error | decoder_error
```

### 7.3 无设备 native qualification

- 用测试专用 Null/offline sink 验 ABI、decoder、seek、loop、crossfade、SFX voice pool 和错误映射。
- 该测试不得进入 production backend 配置，也不能证明真实可听。

### 7.4 真实设备自动 E2E

- 在 exact isolated candidate 中跑 AS2 → socket → C# → native → 真实 Windows backend。
- BGM、SFX 分别取证；记录 backend/device/sample rate/channels/generation。
- 使用 WASAPI loopback 或同等级端点捕获证明最终 PCM 非零。

### 7.5 人工听感

人工确认音量、切歌、淡入淡出、seek、loop、密集 SFX、设备切换、休眠恢复、失真/爆音和延迟。机器非零波形不能代签听感。

## 8. 方案比较与推荐甜区

| 方案 | 收益 | 代价 | 裁决 |
|---|---|---|---|
| 只修 11 个文件与缺路径 | 快速恢复随包资源 | 目录/engine 契约、Null 假成功和 bridge 仍在 | 不足以作为平台收口 |

| WMA | MF 路径的边际实现成本可能较低 | 扩大公开承诺和长期测试面 | 默认不公开，后续按证据决定 |
| FFmpeg/libVLC/GStreamer | 格式覆盖最广 | 二进制、CVE、许可、更新与可复现构建面大幅扩大 | 明确不纳入本轮 |

Windows Media Foundation 原生列出的容器包括 ADTS AAC、MP4/M4A 和 WMA；Source Reader 可选择输出格式并逐 sample 读取、seek 和 drain。参考 [Supported Media Formats](https://learn.microsoft.com/en-us/windows/win32/medfound/supported-media-formats-in-media-foundation) 与 [Processing Media Data with the Source Reader](https://learn.microsoft.com/en-us/windows/win32/medfound/processing-media-data-with-the-source-reader)。

Vorbis 内部路线比较：外部 `stb_vorbis.c` + miniaudio optional wrapper 的源码面较小，但 resource-manager push mode length/后向 seek 语义不符合本轮 BGM 合同；官方 libvorbis adapter 需要 libogg/libvorbis/libvorbisfile 与 notice/build closure，却更适合完整 streaming duration/seek/EOF。R2 选择后者；这项选择进入 H1 manifest，A3 不再自行翻案。

## 9. 二进制与发布含义

- 修改 native/C#/P/Invoke 必然改变 runtime artifact source/build identity，最终需要新的 v2 binary train。
- `launcher/native` 下 C/C++/H 会进入 artifact source，但当前 producer 只规范化/编译 `miniaudio_bridge.c + miniaudio.h`；新增 decoder 源必须同步 producer recipe。
- LICENSE、lock manifest、qualification corpus 等不会因为位于 native 目录就自动全部进入正确身份域；必须显式设计 artifact/policy 归属。
- 新增库应固定源码版本与哈希，静态链接进同一个 `miniaudio.dll`，更新 `launcher/THIRD-PARTY-NOTICES.txt`。
- 正式状态仍只能按 `compiled → candidate_built → candidate_executed → e2e_verified → promoted → standard_entry_verified` 前进。
- 当前只读备忘不会改变任何上述状态。
