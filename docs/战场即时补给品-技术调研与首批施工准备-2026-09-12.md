## 1. 接续时先看

结论：适合建设轻量的“战场即时补给”能力。已有集中拾取入口、药效组合注册表、治疗封顶、Buff、转场补弹和战斗补弹实例，可复用已有行为实现。主要新增工作是拾取结算、作用范围、战斗中武器同步及关卡禁药入口。

后续恢复任务时，先重新检查本文件 §3 的源码和工作区占用，再按 §10 的顺序施工。这里列出的拟议接口和字段均未落地，不能当成现有 API 调用；当前 HEAD 也不等于已发布 runtime 身份。

本轮有六项不能丢失的结论：

1. 当前非战斗转场只补装备栏的长枪、手枪、手枪2，不遍历背包。全量包覆盖背包枪械是新增范围。
2. “弹药补满”指武器弹仓状态；不增加背包里弹匣、榴弹弹药等数量型物品。
3. `shot = 0` 表示普通满弹，但 GM6 的奖励弹药可令 `shot < 0`。补给不能把合法超装误当污染并清掉。
4. 现有药效注册表的成功数量包含表现词条，不能直接作为“应当消耗地面包”的判据，也不提供组合原子性。
5. `scaleWithAlchemy=false` 不足以单独关闭现有治疗的炼金生命封顶；战场补给需要中性的效果上下文。
6. 当前药剂有快捷键与背包直服两条入口。禁药必须在权威使用前拦截，地面补给则按自己的来源规则放行。

## 2. 需求与建议的区分

### 2.1 用户提出的目标

- 为需要控制外部恢复资源的关卡提供即时补给：捡起后恢复或强化，不先进入背包。
- 补给按医疗包、弹药包、Buff 包三大类设计，并便于后续组合行为。
- 弹药包细分长枪、双枪、全量三种；全量范围包含随身背包内的枪械。
- 优先复用非战斗转场补弹的已有逻辑。
- 先完成必要调研并沉淀文档，待当前重型施工之后择机实现。

“背包内的”在本方案中解释为背包枪械的弹仓；不解释为补出无限或固定数量的备用弹药。此前“转场等同全量包”的范围已由源码纠正，见 §5。

### 2.2 助手建议的首批八个测试配方

以下配方、叠加方式、拾取方式与具体数值均属于建议，尚未逐项形成用户裁决。测试配方数量不等于必须向所有正式关卡投放八种商品。

| 类别 | 配方 | 建议效果 | 用来验证什么 |
|---|---|---|---|
| 医疗 | 医疗包 | 固定量即时 HP 恢复 | 单项收益、封顶、满血不浪费 |
| 医疗 | 复合急救包 | 按比例即时恢复 HP/MP，再缓回一段 HP | 多资源、部分已满、即时与持续效果共存 |
| 弹药 | 长枪弹药包 | 已装备长枪及可支持的附属弹仓 | 精确槽位、长枪与副武器同步 |
| 弹药 | 双枪弹药包 | 装备栏手枪、手枪2 | 双槽分别结算，只装备一把也可使用，不依赖当前攻击模式 |
| 弹药 | 全量弹药包 | 已装备枪械 + 随身背包枪械 | 背包遍历、同名多实例、补满后重新装备与存档回读 |
| Buff | 突击强化包 | 短时伤害加成 | 单项 Buff、重复刷新、到期还原 |
| Buff | 防护强化包 | 防御力与属性抗性提升，持续时间不同 | 两种处理器共存、独立到期 |
| 组合测试 | 战备补给包 | 全部已装备枪械补满 + 即时回血 + 突击强化 | 三类跨行为组合、无收益分支、前置失败 |

战备组合包建议先用“全部已装备”范围，以便把跨效果结算与背包批量写分开定位。它与独立突击包共享突击效果身份，用于验证不同配方提供同一 Buff 时的处理。

具体恢复值、增益强度和持续帧数先使用容易核对的测试档，正式数值另按关卡档位校准。不能把本表当成已经完成数值平衡。

## 4. 建议的最小结构

按“来源与实体、领取规则、效果执行、表现反馈”分开职责，保持一条可检查的主路径：

```text
关卡摆放 / 敌人掉落
  -> 地面拾取实体（定义、实例身份、是否可领取）
  -> 判定普通物品或即时补给
     -> 普通物品：原有入包流程
     -> 即时补给：确定受益者 -> 完整预检 -> 执行效果 -> 结算收益 -> 消失与反馈
```

建议新增两个小型职责，名称只是提案：

- `PickupEffectService`：中性上下文、受益者、效果预检、重复领取保护与结果汇总。
- `AmmoSupplyService`：选择真实枪械实例、计算缺弹、按来源策略补满、同步运行态与数据。

第一波只开放 `heal`、`regen`、`buff`、`resistanceBuff` 和拟议补弹效果；表现跟随已提交结果。原注册表还有 `global`、`grantItem` 等类型，不应未经评估全部开放为战场补给。现有 [PurifyEffect](../scripts/类定义/org/flashNight/arki/item/drug/effects/PurifyEffect.as) 还修改全局地形伤害系数，也不能预设为纯目标局部操作。

### 4.1 实体只领取一次

- 对当前实体设置同步领取占用，重复输入在最前端退出；成功结算后立即移出可拾取集合并解除交互，消失动画只是后续表现。
- 配置不支持、目标死亡、换弹保护等前置失败：零效果，实体恢复可领取状态。
- 有效配置但全部资源已满、也没有新增或延长的持续效果：零收益，保留实体。
- 部分恢复项已满、另一些项有效：只应用有效收益，然后整包消耗。
- 新增或实际延长 Buff/缓回属于收益；仅播放特效、重复写同值、清零计数本身不属于收益。
- 若执行中出现异常且已经产生效果，不能把完整原包重新开放领取。结果必须保留已应用事实并关闭本实体重试；不能仅凭预检声称任意组合全或无，也不能沿用“成功词条数量大于零”伪装完整成功。

建议结果至少能区分：前置拒绝、无收益、已应用、部分应用后错误；携带实际 HP/MP 增量、分实例补弹变化、新增/延长的 Buff 信息。它是本地同步结果，不要求另建跨栈持久 receipt 系统。

### 4.2 拾取与本局生命周期

现有键盘拾取有角色距离/碰撞判断，鼠标拾取只检查鼠标命中。首版建议玩家本人近距领取，鼠标和键盘服从同一距离规则；是否自动碰触领取仍属产品选择。

同伴代领若启用，必须明确收益仍给玩家，并同时修正代捡的满背包前置和 AI 候选筛选。敌人不能继续无条件吞掉仅允许玩家使用的补给。只修 `PickUpManager.pickup` 无法覆盖这些外围入口。

已有 `一次性领取ID` 写入 `_saveExt.一次性领取`，用于长期领取记录。战场包的一次性是实体/本局语义，不直接借用该存档标志。固定补给点建议在同一次 GameStage 内领后不因重访子图重生，新开一局重置；不要只靠 MovieClip 存活证明已领取。

## 5. 共享补弹能力的精确边界

### 5.1 一个能力，四种内部范围

| 调用用途 | 范围 | 兼容要求 |
|---|---|---|
| 原非战斗转场 | 三个已装备枪槽及原有长枪副武器字段 | 保留现有非战斗判断、清理后调用时机与重置语义，不自动扩大到背包 |
| 长枪包 | 已装备长枪及明确支持的附属弹仓 | 不改变手枪和背包里的其他枪 |
| 双枪包 | 已装备手枪与手枪2 | 不依赖当前攻击模式；空槽跳过，不改变长枪 |
| 全量包 | 已装备枪械 + 随身背包枪械 | 仓库、佣兵装备、暂存奖励不在范围；按真实实例去重，同名不同枪仍分别处理 |

“长枪”“手枪”以物品权威类型和规范装备槽判断，不能只按名称猜，也不能把 lifecycle 借用的运行态 alias 当成额外一把枪。

### 5.2 补满和重置要可区分

转场旧函数对目标写 `shot=0`、`reloadCount=0`，并重置长枪的两个副武器字段。对于战斗补给，建议只增加缺失弹药：普通正数已发射计数归零；已满或合法超装的枪保持现值。未初始化的背包字段不等同于“缺弹”，应按当前武器初始化约定读取，避免凭空创造收益。

`reloadCount` 对逐发装填和普通战术回收含义不同。是否让弹药包连同池一起清零尚未裁决；建议首版以原转场规则为参考，但只对实际补弹的实例清理，并明确提示其语义。不得为了让全满包“可领取”而单独清空已有回收池。转场仍保留旧行为，不能因抽共享函数顺带改掉。

### 5.3 战斗中的写入与同步

- 预检记录当前受控单位、规范装备引用、value 引用、攻击实例、换弹状态/代次和背包身份；提交前复核，不通过则本次整包不执行。
- 第一波建议有补弹效果的整包在换弹期间保留地面，先避免旧动画晚到扣弹。若以后要求随时领取，需实现真正的换弹取消/提交失效机制；只清 `换弹标签` 或只推进代次不证明旧回调已失效。
- 已装备枪按真实射击读取的对象更新；普通 HUD、副武器 HUD 和相关 `updateBullet` 视觉应看到同一结果。表现异常不撤销已经生效的弹药，也不让包再次可领取。
- 全量包扫描背包时保持物品对象和 `level/tier/mods` 等身份数据；补弹后再装备必须读回同一结果。
- 背包 `ArrayInventory` 有一次推进 revision 的批量 value 事务，可以评估复用；但它会替换 value 对象，已装备武器的 live 引用不能直接照搬。不要重建整个人物来达到补弹和刷新目的。
- 背包枪械 value 会序列化；按现有保存与容器事件约定落脏/刷新，避免逐枪完整保存、逐枪重建背包索引，也不把补弹伪装成玩家获得/消耗库存弹药。

### 5.4 长枪副武器需要专项兼容

`getFiredCount` 优先读取虚拟副武器的 `value.shot`，之后才读取长枪存储镜像。`setFiredCount` 可以同步两者，但还不等于完成装填池、付款资格、冷却与显示的整套策略。

- `onLoadGroup`：补给是否视为这组弹已由补给支付，需要与 `groupPaid`、首次发射扣费以及存储重建共同验证，不能只设置一个 live 布尔值后宣称跨装备/重启仍成立。
- `onFire`：每次射击仍按原规则消耗备用弹药及其他既有成本；清弹仓计数不会生成该库存，因此不能承诺“没有备用弹药也能开火”。
- 首版范围可以覆盖已核实的普通附属弹仓；未支持模式须明确拒绝或明确列为不补给对象，不能显示“全量完成”却静默遗漏。

这些差异是后续定向测试的工作，不是本轮已经验证过的运行结果。

## 6. 关卡规则、数值和效果标识

建议把“禁止携带药剂使用”作为来源规则，放在快捷使用与背包直服共享的领域判断中，并在药效、冷却、扣药发生前拒绝。补给用独立来源调用效果层，不借用会扣药/占冷却的入口。现有 [限制系统](../scripts/逻辑/关卡系统/关卡系统_lsy_限制系统.as) 已有条目机制，但当前没有通用禁药条目。

补给上下文的炼金等级建议显式为零，恢复量和封顶均按补给规则计算。掉落概率是否接受逆向修正要单独决定；首个测试关卡固定摆放，生产关卡以确定性保底和本局总量为主，再考虑随机补给。

稳定效果身份的建议：

- 同款重复获取只刷新时长，不叠强度；突击包与战备组合包共享突击身份。
- 防御力与抗性使用各自标识、各自持续时间；突击与防护可以共存。
- 缓回用独立于 `药剂_缓释_HP/MP` 的战场标识；按固定总量分摊，明确重复获取是刷新该计划而非悄悄叠加多个来源。
- 到期、死亡、离开关卡应正确清理；同关跨子图是否延续仍需定稿，首版可以保持现有单位生命周期语义，不新增 Buff 存档。
- 只读打开角色构筑或查看物品不应重新初始化角色并清掉 Buff。

禁药只控制携带消耗品这条外部资源输入，吸血、被动回复、装备造弹等差异仍然存在。满弹还节省换弹空窗，其收益应按整匣输出与补给间隔评估。全量包额外受随身枪械数量影响，适合少量固定节点，不能把它按普通长枪包的预算批量投放。

## 7. 定义、图标与投放边界

`createCollectible` 依赖物品定义的 displayname/icon；敌人掉落也先要求 `getItemData` 有效。建议复用物品目录的名称、图标和效果配置，新增明确的“即时激活”策略标识与受控效果列表。具体 XML 字段待实现时统一定稿，本文件不声明新 schema 已存在。

必须同时表达“即时补给不能走普通库存获取”。仅加一种 `use` 值并不能保证这一点，因为 [ItemUtil](../scripts/类定义/org/flashNight/arki/item/ItemUtil.as) 的 `isItem` 只判断目录存在，普通获取还有背包兜底。首批投放限固定地面拾取与核实的敌人地面掉落，配置校验应阻止误放到未支持的商店、任务奖励、礼包和 Web 库存型资源箱。

沿用 [可拾取物2](../flashswf/arts/things/LIBRARY/可拾取物相关/可拾取物2.xml) 可复用飞出、静止、消失和图标展示。专属图标后续按资产规范装配；显示应表达即时恢复/强化，不能出现“获得弹药若干件”的虚假资产播报。已有 `Pickup` 事件是否继续用于关卡事件需核对实际消费者，并保证只在领取结算后发布一次。

## 8. 定向测试矩阵

本表是拟执行清单，所有新功能用例当前均未运行。确定性逻辑优先自动化，真人只承担最后的拾取手感、可读性和战斗感受。

| 组 | 关键输入 | 必须观察的结果 |
|---|---|---|
| 配置 | 单词条、多词条、未知类型、非法数值/时长 | 数组归一正确；坏配置在任何收益前拒绝 |
| 恢复 | 缺血、满血缺蓝、全部已满、合法超额 HP、死亡 | 真实增量与封顶正确；无收益保留；不复活、不削掉已有超额生命 |
| 缓回 | 即时+缓回、重复拾取、已有药剂缓回 | 总量、tick、余数和独立槽位正确，重复策略符合定义 |
| Buff | 同款两份、不同包同一突击效果、突击+防护 | 刷新不叠强度，共存不互相覆盖 |
| 到期 | 防御与抗性不同持续时间 | 各自到期，属性恢复，无永久遗留 |
| 范围 | 长枪包、双枪包、只装一把、当前持刀 | 只改目标集合，不依赖当前攻击模式 |
| 全量 | 背包多枪、同名多实例、空槽、非枪物品、alias | 正确筛选/去重，不漏同名实例、不误改其他物品 |
| 超装 | GM6 负 shot、普通满弹、缺弹混合 | 补给不降低合法已有弹量，无变化项不计收益 |
| 换弹 | 开始/提交/结束、双枪分手、逐发装填 | 前置拒绝时整包零写；成功后无迟到扣弹或重复回收 |
| 副武器 | 镜像不一致、onLoadGroup、linkedFirstFire、onFire | 实际弹仓、付款状态、射击成本、切换/重建一致；明确支持边界 |
| 组合 | 血满弹空、血缺弹满、资源全满但 Buff 可刷新 | 只应用有效项后整包消耗；无法执行项在预检阶段阻断 |
| 异常 | 表现报错、效果执行中断、同步监听器重入 | 不重复领取，不把部分生效伪装成零写或完整成功 |
| 交互 | 连续键鼠输入、消失动画期再次点击、满背包、远处鼠标、同伴/敌人 | 距离和受益者一致；每实体至多一次；满背包不误阻挡即时补给 |
| 禁药 | 快捷药、背包服用、地面补给、退出关卡 | 禁药前置零扣药零冷却，补给按规则可用，离场恢复原入口 |
| 生命周期 | 重访子图、重开一局、死亡、切图、查看角色构筑 | 固定点不被重复刷取；本局记录与 Buff 清理符合约定 |
| 持久化 | 补背包枪后装备、保存、退出、重启读回 | 弹仓状态正确；库存数量、强化、进阶、插件无漂移 |
| 成本 | 多枪全量补给 | 一次受控遍历/批量更新；无逐件完整存盘、无角色重建 |

测试场景建议每个配方固定摆两份，配三种枪和一个已有缓回/Buff 来源。逻辑用例应自动设置明确前态，不要求测试员反复手动打空几百发或制造特定伤害。

## 10. 后续施工顺序与共享文件避让

1. **重新建立基线**：检查 HEAD、dirty 文件和重型施工状态，重读 §3 入口。特别核对 MouseProxy/原生交互、TooltipComposer、BootSequencer、ItemUse 和当前编译 runner，不复用旧行号作为接口保证。
2. **确定最小规则并做医疗纵切**：确定受益者/距离、本局领取与无收益语义，接通一个固定医疗包到真实地面拾取，验证满背包、满血和重复输入。
3. **抽共享补弹并接两个装备范围**：保留转场兼容入口，加入长枪/双枪包；先验证换弹和合法超装，再加入明确支持的副武器模式。
4. **扩到全量包**：接背包规范实例、批量更新和存档回读，单独测再次装备与同名多枪。
5. **接持续效果和组合包**：固定 Buff/缓回标识、收益结果和独立到期；完成两款 Buff、复合急救与战备组合用例。
6. **接关卡禁药与试点投放**：统一快捷/背包入口，使用一个固定补给预算的测试关卡；验证退出恢复与重复进入。
7. **同步实际契约并完成验收**：只有 schema/入口实际改变时更新对应 canonical doc，再运行文档治理；合并真实编译与最小实机旅程，不把全部数值平衡留给真人反复操作。

可能触及的主要文件群是拾取、药效、Shoot/转场、DrugInput/ItemUse、物品目录和测试场景。首次垂直验证优先控制在一个可回归的小改动内，后续分片推进；无需为了此文档创建 worktree 或占用 CS6。

大致难度：单纯 HP/MP 与两个已装备弹药范围低至中；完整八配方连同背包、特殊副武器、保存和禁药为中等，最终工作量取决于支持范围与并行施工后的接口。此前口头的 4–7 个开发日仅是熟悉工程、沿用素材情况下的规划估算；新发现的超装/副武器付款边界需要在施工定稿时重新估计，不能当成交付承诺。
