# 套装系统设计与剑圣一期验收

**文档角色**：套装运行时、`item_sets.xml` 效果 schema 与分阶段验收的 canonical design doc。
**状态**：一期实现已落地，本轮已执行的自动门禁与 Flash CS6 smoke 均通过；剩余组合矩阵与游戏内验收仍须按 §6 在真实换装/战斗场景执行。冻结范围包含装载三态、显式失败原子性、TaskManager 时序边界、原体伤害数值和剑圣各 tier 行为。
**最后核对代码基线**：commit `4cfb8b2ac0`（2026-07-14）。

## 1. 目标与一期边界

套装系统在现有 `setId/setName/setOrder` 展示元数据之上增加游戏效果，但不改变物品身份，也不把定制行为硬塞进通用数值系统。

一期以“剑圣装甲套装”重构作为纵向切片，同时验证两条效果路线：

- **声明式效果**：通用、无周期的单位属性表项配给；一期以剑圣套声明原体抗性表项为样本。该表项是会开启对应定向特攻破击的负向暴露，不得按普通防御 Buff 理解。
- **定制效果**：腕刃、肩炮、剑匣、战术扫描、战技强化等行为；参数和函数引用继续留在成员 `<lifecycle>`，由套装控制器统一门控、通用生命周期 loader 负责解析与装载。

一期不实现多套装标签、通用 3/4/5 抗性曲线、项链 `+2` 计数、Web 套装详情面板或运行时热调参；这些能力必须能在不推翻本期 XML 效果结构的前提下追加。

## 2. 已冻结的架构决策

### 2.1 身份、计数与触发

- `setId` 继续使用稳定 ASCII `snake_case`，名称只负责展示。
- 运行时只统计**当前已装备槽位**，不统计中心表中的候选成员总数；同一槽位的多个可选头甲最多贡献 1 件。
- 阈值由每个效果显式配置，不在代码中写死。常规套装可采用 3/5 件，剑圣一期是明确例外：所有套装效果只在 5 个不同槽位齐全时激活。
- 一期每次换装都走单位完整重初始化；套装在单件生命周期装载前 `prepare`，装载后 `finalize`，不做战斗帧内的增量件数侦测。

### 2.2 每单位一个逻辑控制器，子部件 tick 保持自治

每个单位只创建一个 `SetEffectController`，负责计数、门控、声明式效果、共享 context 与清理登记。剑圣一期不强制控制器接管五个既有组件生命周期：各部件保留独立 `ref` 和状态机，需要周期的组件继续拥有独立任务，降低重构风险并保留组件组合自由度。

```text
SetEffectController.prepare()
  ├─ 统计五个唯一槽位
  ├─ 把五个成员 lifecycle 解析成无副作用的规范化 descriptor
  ├─ 建立 effect record 与 active/tier 信号
  └─ 调用 prepareRoutine 创建 context；此时不注册任务
       ↓
通用 loader 逐个处理成员 lifecycle
  ├─ 未激活的 gated attr 整段跳过
  ├─ 激活时从 descriptor 创建五个 ref 并提交组件初始化
  └─ 仅记录 ready_cycle，暂不注册；由 finalize 统一调度
```

这种结构保留多个 TaskManager 分发和各自的 `EquipmentTick`，但允许合并重复计算，并以共享 placement 通道复用同一肢体引用的坐标换算。这里的稳定不变量是“五个必需组件 ref”，不是“五个周期任务”：鞋和无进阶组件可以合法地没有 tick。只有性能分析证明任务分发成为热点后，才进入“单一物理周期调度全部组件”的二阶段优化。

### 2.3 TaskManager 时序契约与共享 context

2026-07-14 的 Flash CS6 TestLoader 实测：同一 TaskManager 中按 first→second→third 首次进入 `zeroFrameTasks` 的三个零间隔生命周期任务，连续两帧均按 first→second→third 执行。正式契约只覆盖以下边界：

- 顺序位置取决于任务**本次进入** `zeroFrameTasks` 的先后；持续留在该表中的 `0→0` 更新只替换内容，不换位。
- `0→正间隔→0` 已离开再进入，按新入队处理，排到当时队尾；不得宣称所有 `addOrUpdateTask` 更新都保持最初位置。
- ID 快照在时间轮到期任务和 `_pendingReschedule` 处理完成后、进入零间隔分发阶段时才收集。因此时间轮回调新建的零任务会在同次 `updateFrame()` 的零阶段执行；只有快照完成后、零任务回调中才创建的新 ID 必然延后到下次 `updateFrame()`。快照时已有 ID 若在轮到它前执行 `0→正间隔→0`，当前实现仍可能在本次执行；该重入时序不作稳定保证。

对应基建回归必须覆盖首次入表、`0→0`、分发外 `0→正间隔→0`、时间轮回调新建零任务本次执行、零任务回调新建 ID 下次执行，以及快照已有 ID 重入的限制探针。快速 runner 每个 case 使用新的 `TaskManagerTester`，避免持久任务跨 case 污染。

套装预计算任务必须在子装备生命周期任务之前注册，因此每帧先写共享 context、随后由子周期消费。context 通过现有 `ref + param` 的第二参数传递并跨帧复用，不得每帧创建新对象：

- `ref`：部件自己的持久状态、挂件引用、计数器与 tier。
- `param/context`：当前帧共享状态与 placement 通道。普通共享快照由套装预计算任务写；肢体基向量只能由对应 placement 事件在引用已进入显示树后写，不能由帧前预计算任务采样。
- placement 通道以 `target` 本地坐标系缓存原点和 X/Y 基向量。同一引用的所有组件共享一次 `localToGlobal`，消费时再转换到挂件的实际容器，因此胸甲在 `target` 与 `底层背景` 间切换不会改变缓存语义。
- 通道拒绝 `!source._parent` 的 stale ref。placement 回调必须在引用重建后同步完成首次位置校正；同一引用还会随动作时间轴逐帧运动，因此套装预计算任务每帧对每个有效共享引用采样一次基向量，组件周期每帧消费缓存，不得各自重复执行肢体 `localToGlobal`。
- 预计算任务每次运行将 `context.frameStamp` 单调加一；共享普通快照的组件可用 stamp 判断新鲜度。placement 通道另用 `epoch` 表示引用就位版本，不得把 `frameStamp` 当作肢体引用已就绪的证明。

现有生命周期 loader 注册任务时应改用可被初始化函数覆盖的 `反射对象.生命周期参数`，而不是再次直读 `cycle.cycleParam`。配置 `cycleRoutine` 的套装组件将它指向同一个 context；没有共享生产者或未参与套装的装备保留各自原 cycleParam，行为不变。

### 2.4 声明式效果与定制效果

| 类型 | 数据职责 | 运行时职责 | 是否进入周期 |
|------|----------|------------|----------------|
| `template` | 模板名、参数、阈值、说明 | 通用处理器一次性声明单位属性表项 | 否 |
| `routine` | 初始化/周期函数名、参数、阈值、说明 | 注册定制组件；一期子周期自治并消费控制器 context | 按需 |

一期模板注册表至少支持 `resistance_entry`：指定抗性属性、计算方式、缺失基数和值。剑圣原体抗性必须走该模板，禁止在 `剑圣套装周期` 中逐帧赋值。

这里的“抗性”不是单向正收益。当前 `UniversalDamageHandle` 的破击路径先检查 `target.魔法抗性[破击属性]` 是否存在：字段不存在时退化为纯物理；字段存在时才追加对应定向破击分量。对“原体”这类非元素标签，额外分量为 `power * 0.5 * (100 - resistance) / 100`（再叠加物理部分）。因此必须区分两个维度：

- **字段存在性**：暴露标签，是 Debuff/弱点；获得原体抗性意味着能够被原体定向特攻破击。
- **字段数值**：暴露成立后的减伤幅度；数值越高，只会压低额外破击分量，不会取消暴露。`0` 仍是有效表项，不能当作“无效果”；只有字段不存在才表示不吃该类定向破击。

该模板直接参与装备属性重建，不注册为 Buff，也不依赖 BuffManager 表达身份或清理。一期只允许 `calculation=add`，并冻结为以下顺序无关的聚合算法：

1. `DressupInitializer.updateProperties()` 完成普通装备聚合后，template 先进入 `templateEligible`：其自身 preflight 成功、所属 group 的 routine 已全部到达 `routinesReady`、且组内 `requires` 已满足。此时 group 尚未 committed，不得用 `groupCommitted` 作为自己的前置条件。
2. 一期校验器规定全局每个 `attribute` 最多一个 `resistance_entry`，避免跨 activation group 聚合产生未定义的失败归属。读取目标字段原值：`raw == undefined`（AS2 宽松比较，同时覆盖 `null/undefined`）时使用必填的 `baseIfMissing`；有限数值（包括 `0`）以现值为基数；NaN/Infinity 使本组 fail-closed。
3. 合格 template 写回一次；写入成功后其 group 才从 `routinesReady` 变为 `committed`。一期不开放同属性多声明、`override/multiply`；以后开放前必须设计跨组属性聚合事务和显式优先级契约。
4. 写入层不钳制，保持现有装备聚合语义；配置值和中间和必须为有限数值。剑圣的“原体”是非魔法破击标签，只有 `UniversalDamageHandle` 的**破击分支**在读取时将它钳制到 `[-1000, 100]`；不得把魔法伤害分支的 `95～100` 软上限曲线套到该模板上。

剑圣一期固定 `attribute=原体`、`baseIfMissing=10`、`value=75`：无其他原体来源时最终运行值为 `85`，等价于当前五个正确填写的成员各贡献 15 时的结果；若普通装备聚合已建立原体表项，则在其现值上再加 75。`MagicDamageTypes.isMagicDamageType("原体")` 必须为 `false`，所以破击额外分量在 85 抗性时精确为 `power * 0.5 * 0.15 = power * 0.075`，总伤害为物理分量加该值。高度定制的行为继续手写 AS2。XML 只保存函数名和参数，不嵌入脚本、表达式或任意 AS2 代码。

### 2.5 成员生命周期门控与 routine 执行协议

剑圣组件的完整配置继续保存在各成员物品的 `<lifecycle>/<attr_N>` 中，包括头甲扫描参数、胸甲 bullet、腿甲剑匣、手甲倍率和鞋战技段数。不得把这些参数复制到 `item_sets.xml`。每个受套装控制的 attr 只增加最小引用：

```xml
<attr_0>
    <setGate>
        <effectId>combat_suite</effectId>
        <componentId>chest_cannon</componentId>
    </setGate>
    <init>...</init>
    <cycle>...</cycle>
    <bullet>...</bullet>
</attr_0>
```

- `effectId` 引用本物品 `setId` 对应中心表效果；`componentId` 引用该效果的中心组件清单。两者都只表达身份，不复制参数。
- 无 `setGate` 的 attr 完全保持现有单件生命周期语义。存在 gate 但效果未激活时，loader 在解析 bullet、调用初始化函数或注册任务之前整段跳过。
- 激活时仍由通用 loader 构造 `反射对象`、预解析 `子弹配置`、调用成员初始化函数并按返回三态决定是否注册成员周期；中心 routine 只准备共享 context，不替代五个成员函数。
- gated 任务标签固定为 `set:<setId>:<effectId>:<slot>:<componentId>`；共享预计算任务标签固定为 `set:<setId>:<effectId>:context`。组件 ID 在同一效果内唯一，同槽只能解析出一个当前装备组件。
- 控制器以 `<setId>:<effectId>` 建立 effect record，保存 `active/status/context/descriptors/componentRefs/cycleTaskIds`，并引用所属 activation-group transaction。transaction record 是 `rollbackPlan/teardownPlan` 的唯一所有者，保证同组多个 effect 的逆操作按一个全局顺序执行；每个 plan 均含 `stopStack/resourceStack` 两阶段。五个 ref 按 `componentId` 存于 routine effect 的 `componentRefs`，不另建第二份状态。
- gated loader 在调用 init 前设置 `反射对象.套装事务` 与 `反射对象.套装上下文`；init 只能通过前者登记副作用，不把 transaction 塞入每帧 param。若 init 返回 `ready_cycle` 但 descriptor 没有有效 cycle 函数，按 `failure` 回滚；返回 `ready_static` 时即使 XML 保留 cycle 字段也不注册。

#### 2.5.1 单一解析器与规范化 descriptor

preflight 与 commit 必须消费同一份只读 descriptor，禁止各自解释一次 XML。通用解析器在任何初始化副作用前完成：

- 固定 `setId/effectId/componentId/slot/attrKey/tier` 与 init/cycle 函数引用；
- 深复制 init/cycle param、skill/data，并把 bullet 归一化为只读 spec；preflight 只验证 spec，commit 为每个 ref 单独物化可变的 `子弹配置`。胸甲运行时写入的 `lockShooterAttributes/shootX/shootY/shootZ` 不得反向修改 descriptor 或泄漏到下一次重建；
- bullet spec 缺少 `power` 时显式归一化为本装备的 `威力基数`，百分比和绝对值沿用现有 loader 语义。不得继续对缺失值直接调用 `split/indexOf`，也不得依赖 AVM1 的静默 `undefined` 行为；
- 校验 descriptor 与当前装备数据、中心 manifest 一致。`EquipmentUtil.calculateData` 等上游处理后仍须保留顶层 `setId` 与 `lifecycle`，以单元测试锁定该集成前提。

#### 2.5.2 初始化返回三态

一期重构后的 gated init 必须返回以下闭集结果；`undefined`、其他字符串或结构均视为 `failure`：

- `ready_cycle`：初始化成功，ref 有有效周期行为；loader 只记录待调度组件，由 `finalize` 先注册可选 context 生产者，再统一注册子周期。
- `ready_static`：初始化成功，但只产生一次性行为或合法无行为；保存 ref，不注册 cycle。鞋的战技/速度修改以及无进阶组件都属于此态。
- `failure`：配置或运行前置不成立；触发整个 activation group 回滚。

因此五件基础、混合进阶和全高阶装备都能满足“五组件存在”；tier 只决定各组件返回 `ready_cycle` 还是 `ready_static` 及其行为强度，不决定套装计数。初始化函数不得再调用“先请求移除、随后仍由 loader 注册”的 `移除周期函数(ref)` 模式来表达静态成功。

#### 2.5.3 事务、所有权与显式失败原子性

装载采用明确的三阶段事务。遵守本项目生产代码不使用 `try...catch` 的约束，原子性只承诺 preflight 错误、三态 `failure` 和测试故障点返回的**显式失败**；不宣称对任意未捕获运行时异常具备 exception safety。所有可预见外部 API 失败必须在调用前验证或转换为显式返回，故障注入也必须返回 `failure`，不能用 throw 冒充协议路径：

group 状态机固定为 `candidate → preflighted → routinesReady → committed`；任一步显式失败进入 `rollingBack → rolledBack`，且 `rolledBack` 不持有运行时句柄。

1. **preflight（无副作用）**：核对中心必需组件、当前装备 gate、函数注册、tier、descriptor/bullet、依赖图和任务标签。任一失败则 activation group fail-closed，不运行 routine、不注册任务、不写抗性。
2. **commit（可回滚）**：先调用 `prepareRoutine(record, transaction)` 创建共享 context，再按固定槽位顺序提交五个 descriptor，但暂不注册任何周期。任何 dispatcher/WeatherSystem 订阅、MovieClip、Buff、主动战技覆盖或其他外部句柄一经创建，创建方必须立刻登记幂等逆操作。只需处理本次失败的动作进入 group `rollbackPlan`；换装时仍需释放的资源同时进入 group `teardownPlan`。主动战技覆盖的 rollback 保存并恢复 commit 前旧值。
3. **schedule/finalize**：五个 init 均成功后 group 进入 `routinesReady`。若至少一个返回 `ready_cycle` 且配置了 `cycleRoutine`，先注册 context 生产任务，再按固定槽位顺序注册所有 `ready_cycle` 子任务并给它们同一 context；没有 `cycleRoutine` 时不建共享 context 任务，子周期保留 descriptor 自己的 cycleParam。若全为 `ready_static`，两类任务都不注册。随后才 finalize `templateEligible` 的声明式效果。其旧字段状态只登记到 rollback，不进入 teardown。全部写入成功后才标记 `committed`、安装唯一 group teardown 入口，并立即清空仅用于失败恢复的 `rollbackPlan`；运行期只保留 `teardownPlan`。

任一阶段显式失败时，按 `rollbackPlan` 的两阶段顺序撤销已创建资源，再清空两个 plan、context、refs/descriptors/task IDs，撤销未提交的 group hook，并删除 group/effect runtime record。失败诊断只能另存不捕获 ref/MovieClip/dispatcher 的纯值摘要，避免闭包继续强引用资源。

`prepareRoutine` 是每次装备重建只调用一次的 routine 初始化入口，只能通过 transaction 创建可追踪资源；`cycleRoutine` 是可选的每帧 context 单写者，不承担组件调度。即使配置了 `cycleRoutine`，本次没有任何 `ready_cycle` 消费者时也不注册 context 任务。

剑圣两个 5 件效果属于同一 `activationGroup=sword_saint_full_set`，`proto_resistance_entry` 显式依赖 `combat_suite`。一期约束同组效果 threshold 必须相同，且 `requires` 只允许指向同组效果；activation group 就是唯一事务边界，依赖只决定组内拓扑顺序。因此 routine 的 preflight/commit 失败时抗性也不提交，不能出现只有抗性、没有定制组件的半套状态。未分组效果各自形成单效果事务；跨组依赖一期非法。

### 2.6 换装清理契约

换装/模板重初始化必须先 teardown 上一次已提交的套装事务，再重建本次装备派生属性和主动战技。当前 `DressupInitializer.initialize()` 是先 `updateProperties/updateWeqaponSkills`、后在 `updateLifeCycles` 内清理旧生命周期；一期接线必须把旧 `生命周期函数列表`/`SetEffectController` 清理拆成独立前置阶段，避免旧清理恢复战技或资源时覆盖新结果。

随后 `BuffManagerInitializer.reset()`/装备初始化按既有总流程重建托管状态。抗性表项不属于 Buff：`DressupInitializer.updateProperties()` 重建整个 `target.魔法抗性` 后，由本次套装声明式效果在 `UnitInitialized` 前写入；套装失活时依靠本次完整属性重建恢复为字段不存在。正常 teardown 不恢复旧抗性值，只有同一次尚未 committed 的事务失败才用 rollback 恢复写入前状态。

套装控制器以一个 group teardown 动作接入现有 `生命周期函数列表`。gated 提交模式下，通用 loader 和五个 init **禁止**再向全局列表追加逐组件清理；任务、Weather、挂件等全部只登记到 group transaction。ungated 路径继续沿用旧 loader 行为，避免双重所有权。

transaction 内部不是一条按资源类型碰运气排序的普通栈，而是两个阶段：

1. `stopStack`：逆序停止所有子周期，最后停止 context 生产任务，保证消费者先于生产者退出。
2. `resourceStack`：逆创建顺序释放 dispatcher/WeatherSystem 订阅、MovieClip、Buff、主动战技覆盖及其他句柄，最后清空五个 ref 和 runtime record。

`rollbackPlan` 和 `teardownPlan` 各自包含这两个阶段；资源动作可在两者间复用同一幂等函数，但职责不可混淆。dispatcher 逆操作必须捕获**注册时的 dispatcher 实例**，禁止清理时动态读取可能已替换的 `target.dispatcher`。

由新 BuffManager 托管且已成功提交的 Buff 可随正常重建销毁；但 commit 中途失败时，新建 Buff 同样必须有即时 rollback。所有 rollback/teardown 动作必须可重复调用且对“资源已不存在”安全。

该简化依赖“套装件数变化必经完整单位重初始化”。若未来允许战斗中不重初始化地改变套装计数，必须先补激活/卸载的增量事务，不能直接复用一期假设。

### 2.7 文案单一真源

- 成员物品 `<description>` 只写单件世界观、外观和真正的单件固有效果。
- 套装阈值效果的玩家文案只在 `item_sets.xml` 对应 `<effect_N>/<description>` 保存一份。
- 定制效果允许人工撰写专属说明；一期不建设从复杂参数自动生成完整文案的 DSL。
- 标准模板以后可以由 UI 根据参数补充机械明细，但不得在每个成员物品上复制整套说明。
- 一期只落数据与 AS2 运行时，不扩展现有 AS2 → Host → Web 逐物品协议；套装详情 UI 另期开工。

## 3. `item_sets.xml` 效果 schema

现有必填字段 `id/name/order` 保持不变。效果为可选扩展；没有 `<effects>` 的 65 套继续只承担展示分组，不产生运行时行为。

```xml
<set>
    <id>sword_saint_armor</id>
    <name>剑圣装甲套装</name>
    <order>160</order>
    <description>集齐五件后启动剑圣装甲协同系统。</description>
    <effects>
        <effect_0>
            <id>proto_resistance_entry</id>
            <threshold>5</threshold>
            <activationGroup>sword_saint_full_set</activationGroup>
            <requires><effectId>combat_suite</effectId></requires>
            <kind>template</kind>
            <template>resistance_entry</template>
            <params>
                <attribute>原体</attribute>
                <calculation>add</calculation>
                <baseIfMissing>10</baseIfMissing>
                <value>75</value>
            </params>
            <description>集齐五件后呈现原体抗性；可被原体定向特攻破击。</description>
        </effect_0>
        <effect_1>
            <id>combat_suite</id>
            <threshold>5</threshold>
            <activationGroup>sword_saint_full_set</activationGroup>
            <kind>routine</kind>
            <mode>member_components</mode>
            <prepareRoutine>剑圣装甲套装准备</prepareRoutine>
            <cycleRoutine>剑圣装甲套装预计算周期</cycleRoutine>
            <components>
                <component_0><id>head_scan</id><slot>头部装备</slot></component_0>
                <component_1><id>chest_cannon</id><slot>上装装备</slot></component_1>
                <component_2><id>leg_sword_case</id><slot>下装装备</slot></component_2>
                <component_3><id>foot_skill_boost</id><slot>脚部装备</slot></component_3>
                <component_4><id>hand_wrist_blade</id><slot>手部装备</slot></component_4>
            </components>
            <description>启动战术扫描、腕刃、剑匣、铁血肩炮及战技强化。</description>
        </effect_1>
    </effects>
</set>
```

上例的抗性值就是一期验收值：缺失基数 10 加套装贡献 75，最终为 85。后续平衡调整必须同时更新中心 XML、伤害期望测试和本文，不能由实现者临场选择。

### 3.1 字段约束

- `effect_N/id`：套内唯一稳定标识，同一效果升级不得靠改名创建重复实例。
- `threshold`：正整数，且不得大于该套可装备的唯一槽位数；剑圣固定为 5。
- `activationGroup`：可选稳定 ID；同组效果 threshold 必须相同，并在一次装备重建中共同 preflight/commit/finalize，任一失败则整组回滚。未分组效果视为自己的单效果 group。剑圣两个效果必须同属 `sword_saint_full_set`。
- `requires/effectId`：可选套内、同 activation group 依赖，必须存在、不得自依赖或成环；只决定组内提交拓扑，不扩大事务边界。跨组依赖一期非法。剑圣 `proto_resistance_entry` 必须依赖 `combat_suite`。
- `kind`：一期只允许 `template` 或 `routine`。
- `template`：必须命中闭集注册表；一期仅开放 `resistance_entry`。
- `resistance_entry.params`：一期 `attribute` **只允许精确值 `原体`**，且全局同一 attribute 最多一个声明，避免在尚无统一特攻标签注册表和跨组属性事务时伪造通用聚合；`calculation` 只能是 `add`；`baseIfMissing/value` 必填且为有限数值。校验与运行时必须保留 `0`，不得用 truthy 判断吞掉有效表项。开放其他标签前，先建立独立于 `MagicDamageTypes` 的 canonical 特攻/暴露标签注册表及伤害路径分类。
- `routine`：一期 `mode` 只能是 `member_components`，`prepareRoutine` 必填，`cycleRoutine` 可省略；`components/component_N` 必须给出套内唯一 `id` 和唯一装备 `slot`，只作 manifest，不承载成员参数或 bullet。
- 成员 gated attr：`setGate/effectId` 必须命中所属套装的 `routine`，`componentId` 必须命中其 components；同一物品不得为同一 component 提供多个候选 attr。
- `description`：玩家可读的 canonical 文案；不得依赖脚本注释作为 UI 真源。

### 3.2 校验器扩展

`tools/validate-item-sets.js` 在现有成员与唯一性门禁上追加：

- effect ID 套内唯一；
- 阈值、activation group、requires DAG、kind、模板名及模板参数合法；
- 一期全局每个 resistance attribute 最多一个 `resistance_entry`；
- routine 组件清单、成员 gate 引用和函数字段组合合法；
- 剑圣效果阈值均为 5；
- 剑圣两效果同组且抗性显式依赖 routine；
- 配置了效果的套装至少存在足够的唯一装备槽位；
- 剑圣 3 个头部候选均提供 `head_scan`，胸/腿/手/鞋分别提供中心清单规定的组件；模拟任意合法头部选择都能闭合五组件 preflight；
- 剑圣头部装甲、胸、腿、手、鞋的所有 tier 不得再保留 `<magicdefence><原体>`；两个般若半覆面当前本就没有原体项，五件激活后同样由中心效果获得最终 85；
- 成员描述不得与中心效果 description 完全相同。不得以数字 `15/5` 等是否在其他属性出现作为“复制效果参数”的机械判据。

## 4. 加载与运行时接线

### 4.1 中心配置索引

`ItemDataLoader` 已把 `item_sets.xml` 附加为 `combinedData.itemSets`。一期在 `ItemUtil.loadItemData()` 中额外保留完整中心项：

```text
_root.物品套装配置索引[setId] → item_sets.xml 的完整 set 配置
```

现有 `_root.物品套装索引` 的 `{id,name,order,items,itemsByUse}` 形状保持不变，避免影响库存、商店和 Web 筛选消费者。

### 4.2 构建时机

套装接线分为前后两相，不能只依赖当前位于单件生命周期之后的空钩子 `_root.主角函数.完成生命周期函数装载()`：

```text
StaticInitializer：teardown 上次生命周期与 SetEffectController
  → BuffManager reset
  → 读取本次装备数据
  → 本次装备属性/动作/战技重建
  → SetEffectController.prepare(target)
      统计套装、建立 effect record、解析五个 descriptor、完成无副作用 preflight
      调用 prepareRoutine 创建 context，但不注册任务
  → 单件生命周期装载
      ungated attr 照旧；gated attr 按 active 跳过或提交对应 descriptor
      gated init 只返回三态并收集待注册周期，不在此处注册
  → 完成生命周期函数装载()
  → SetEffectController.finalize(target)
      有 ready_cycle 且存在 cycleRoutine 时先注册 context
      再按槽位注册 gated 子周期；无 producer 时保留各自 cycleParam
      写入声明式属性表项、安装唯一 group teardown
  → UnitInitialized（只允许不会失败、不首次取得资源的通知行为）
```

gated 组件的初始化型 Buff、MovieClip、订阅和战技覆盖必须在 commit 阶段创建，并在返回 `ready_*` 前完成 rollback/teardown 登记。`UnitInitialized` 不是事务延长阶段；group committed 后不得再用它首次申请可失败资源。剑圣手甲与鞋的 Buff 因此在各自 init 内同步建立，不再等待 `UnitInitialized`。

`prepare` 从固定装备槽位读取 `target[槽位 + "数据"].setId`，按唯一槽位聚合计数并激活满足阈值的配置。旧生命周期 teardown 必须从当前 `updateLifeCycles()` 的“清理后立即装载”拆为 `DressupInitializer.teardownLifeCycles(target)`，由 `StaticInitializer` 在发布 `UnitReInitialized` **之后、调用 `ComponentInitializer.initialize(target)` 销毁旧 dispatcher 之前**执行；它自然也早于 `BuffManagerInitializer.reset(target)`。这样旧订阅仍可针对捕获的旧 dispatcher 正常解除。`updateLifeCycles()` 此后只负责本次装载。

`prepare` 位于本次属性/战技重建完成之后、第一件单件装备调用 `装载生命周期函数()` 之前。五个 init 全部返回后才进入 schedule：若存在 `ready_cycle` 且配置了 `cycleRoutine`，context 任务先进入 `zeroFrameTasks`；随后按槽位注册实际需要的子周期。没有共享 producer 时只注册子周期并保留各自 cycleParam。`finalize` 复用现有完成钩子，并且只提交 preflight/commit 全部成功的 activation group。装备遍历/组件提交顺序冻结为头、上装、下装、脚、颈、手、刀、长枪、手枪、手枪2、手雷。

### 4.3 函数注册与编译归属

一期继续复用 `_root.装备生命周期函数` 注册表及现有 `ref/生命周期函数列表/TaskManager` 约定，不新增第二套帧脚本协议。新增或拆分 `.as` 仍须遵守：

- UTF-8 with BOM；
- `scripts/asLoaderManifest/frame37.as` 编译接线；
- `scripts/逻辑/装备函数/README.md` 索引；
- `tools/validate-equip-fn-coverage.js` 一致性门；
- asLoader/TestLoader 的 Flash CS6 验证边界。

## 5. 剑圣一期重构范围

### 5.1 数据迁移

- 在 `sword_saint_armor` 中增加唯一套装文案和两个 5 件效果：原体抗性表项声明、剑圣定制组件。
- 保留剑圣 3 个可选头甲、胸甲、腿甲、手甲、鞋上的完整 `<lifecycle>` 参数、函数引用和 bullet，只给对应 attr 增加 `setGate/effectId/componentId`；五件不足时由 loader 跳过，不删除配置也不复制到中心表。
- 仅剑圣头部装甲、胸甲、腿甲、手甲、鞋当前含有 `<magicdefence><原体>15</原体></magicdefence>`，这些表项必须从所有 tier 删除并迁移为五件套 `resistance_entry`；两个般若半覆面无需删除，但五件激活后得到相同的最终原体抗性 85。
- 三个头甲属于同一头部槽位，任意一个均可完成五件套，但不得相互叠加计数。
- 鞋数值真源冻结为当前 XML 运行值：二阶只开启追踪/反弹且不改段数，三阶 `iaiCount=3/raidenCount=4`，四阶 `5/7`。实现时将脚本注释、脚本 fallback 以及防具 XML 中仍写着旧值的内联注释全部同步为这组值；不得改成 `4/5、6/8`。

### 5.2 行为重构

- 新增剑圣套装 `prepare/finalize` 与共享 context 预计算入口；五个现有文件继续作为自治组件，配置继续由成员 lifecycle 提供，通用 loader 创建并把五个 ref 登记到 effect record。五个 init 全部改为显式三态返回并移除“初始化中请求稍后删除周期”的控制方式。
- 五件不足时：不挂腕刃/肩炮/剑匣，不注册夜视扫描，不装载套装战技强化，不添加套装 Buff，也不创建 `魔法抗性["原体"]` 暴露表项。
- 五件齐全时：保持现有各进阶能力；一期默认各组件读取对应部件 tier，暂不引入“整套取最低 tier”。
- 五件基础或混合 tier 同样视为完整套装：无进阶组件返回 `ready_static`，不产生其高阶外观/行为，也不导致整组失败；鞋始终不注册空周期。
- 套装预计算任务先于子任务注册；胸甲和腿甲共享 `身体_引用` placement 通道，手甲消费 `左下臂_引用` 通道。事件在引用真正就位后同步写入 target-local 基向量并立即校正所有挂件；预计算任务随后每帧各采样一次有效肢体，组件周期逐帧消费缓存以跟随动作时间轴。挂件重建时也立即消费最后一份有效缓存。这样既不采样 stale ref，也不让多个 tick 重复执行同一肢体的全局坐标换算。
- 头甲包含两条独立能力：夜视系统只为主角注册，由 `WeatherSystem` 随昼夜亮度启停且在装备有效期内不得超时注销；扫描、AABB 锁定框与躲闪 debuff 不依赖夜视或当前光照，所有有效佩戴者始终按 `scanInterval` 到期并以 `searchRange` 搜索。`scanInterval` 仅作为 TargetCache 刷新间隔，不得代替搜索半径。
- 原体抗性由 `resistance_entry` 模板一次性聚合写入 85，不进入定制周期或 BuffManager。

## 6. 一期验收标准

### 6.1 自动化

- `validate-item-sets` 覆盖新 schema 的正反例，并继续通过现有 66 套/327 件成员基线。
- 新增 `SetEffectController` 测试：0～4 件不激活、5 个唯一槽位激活、同槽变体不重复计数；全基础、混合 tier、全高阶都得到五个 ref，周期任务数分别按三态结果断言而非写死为五，且全 `ready_static` 时 context/子任务都为 0；descriptor/preflight 失败无副作用，commit 每一种副作用后的显式故障点均按两阶段 plan 回滚并释放闭包，正常重建不重复注册；模板仅在依赖的 routine 到达 `routinesReady` 后提交，成功 commit 后 `rollbackPlan` 为空且只保留 `teardownPlan`。
- loader 测试锁定同一规范化 descriptor 同时供 preflight/commit 使用、`calculateData` 后保留 `setId/lifecycle`、缺失 bullet power 回落到威力基数、百分比/绝对值兼容、非法 init 返回值 fail-closed，以及 `ready_static` 绝不注册周期。
- `TaskManagerTester` 用独立实例固定验证首次入表顺序跨帧稳定、`0→0` 不换位、分发外 `0→正间隔→0` 重新排到队尾、时间轮回调新建零任务本次执行、零任务回调新建 ID 下次执行，并用快照已有 ID 重入探针记录“不保证延后”的限制；套装集成测试另证 context 任务早于所有实际存在的子周期。
- 剑圣专项测试验证所有 `ready_cycle` 子周期收到同一个 context、预计算任务每次单调推进 `frameStamp`；同一 `身体_引用` 只建立一个共享通道，placement 后胸甲/腿甲同轮完成校正，`!source._parent` 不污染最后有效缓存，挂件跨容器重建仍可消费 target-local 基向量。头甲另验证白天仍扫描/显示 AABB/刷新 debuff，夜视只在低光启用且经历昼夜往返后仍可再次生效。
- 模板测试验证 0～4 件或 routine 未到达 `routinesReady` 时 `魔法抗性["原体"] === undefined`；原值 `undefined/null→85`、`0→75`、其他有限值 `x→x+75`，原值/配置 NaN 或 Infinity fail-closed；重复 attribute 配置在校验期拒绝，写入层不钳制。伤害回归必须同时断言 `MagicDamageTypes.isMagicDamageType("原体") == false`，无表项时 `damage=physicalPart`，85 表项时 `damage=physicalPart + power*0.075`，并覆盖破击分支 `[-1000,100]` 钳制。
- 既有 `InventoryPanelServiceTest`、物品筛选测试和 Web 协议快照保持不变。
- 文档与装备函数覆盖校验通过；所有改动 `.as` 文件保持 BOM。

### 6.2 Flash CS6 smoke

- TestLoader 新鲜 trace 覆盖 4 件、5 件、同槽变体和换装降回 4 件；无 `[FAIL]`。
- asLoader publish 显示编译器 0 错误且 `scripts/asLoader.swf` 确认刷新。
- 不以 `publish_done.marker` 单独宣称编译成功。

### 6.3 游戏内验收

1. 只穿 1～4 件时没有任何剑圣特殊表现或数值。
2. 任一合法头甲 + 胸/腿/手/鞋集齐后，一次性激活全部效果。
3. 腕刃、肩炮、剑匣、扫描、刀剑乱舞与一文字落雷强化保持现有进阶行为；胸甲三级 bullet 配置仍由通用 loader 预解析，鞋三/四阶段数严格为 `3/4、5/7`。
4. 原体抗性表项只由模板聚合一次，无其他来源时严格为 85，反复换装不叠加；五件齐全时原体破击总伤害严格为物理分量加 `power*0.075`，降回四件后字段消失并退化为纯物理。
5. 脱下一件后经换装重初始化，Buff、任务、外部注册和挂件全部消失。
6. 套装预计算周期早于所有实际注册的子装备周期；五个 component ref 完整，鞋和无进阶组件不遗留空 tick；胸甲、腿甲、手甲在动作切帧与引用刷新期间无旧坐标覆盖、跳点或闪烁。
7. 库存、商店、合成与 Web 套装筛选协议无变化。
8. 人为制造任一必需组件配置/函数缺失或在每类 commit 副作用后注入失败时整组 fail-closed：没有套装子任务、挂件、监听、Buff、战技覆盖或 ref 残留，也不提交原体抗性；重复执行清理不报错。

满足以上三层证据后，剑圣重构才可作为套装系统一期验收产物；只完成中心 XML 或只看到效果触发均不算完成。
