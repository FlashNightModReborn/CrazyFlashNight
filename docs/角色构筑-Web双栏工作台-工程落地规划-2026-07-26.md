## 1. 为什么现在做，以及技能迁移能复用什么

### 1.1 排序裁决

装备槽不再只是旧 UI 内部功能。它已经有三个外部消费者：

1. 背包物品要进入装备栏；
2. 背包药剂要命中玩家信息 HUD 的药剂栏；
3. 已穿戴装备需要进入调制。

若只迁装备槽、不迁药剂装配，旧玩家信息 HUD 仍是管理流程必需品；若只迁纸娃娃、不迁已穿戴调制，玩家仍需“脱下 → 调制 → 再穿回”；若每次穿脱都刷新 live hero，则会把射击清理、单位重初始化和装备生命周期反复塞进普通 UI 点击。因此现在最有价值的工作是先冻结一个能同时承接这些消费者、又不合并其领域权威的 `CharacterBuildSession`。

### 1.2 从 Skill 迁移复用的方法

| Skill 已验证方法 | 角色构筑如何复用 |
|---|---|
| 管理交互与战斗执行分开 | Web 管理药剂槽；`DrugInputService`/`ManualCooldownService` 继续负责使用和冷却 |
| HUD 可缺失，领域写不依赖 renderer | 药剂写成功后可选刷新旧 HUD；HUD-null 不影响容器 authority |
| 固定槽白名单与结构化 descriptor | Skill 12 槽换成装备 11 键 + 药剂 4 索引，不接受 Web 任意键 |
| 合法服务外写用 stateSignature + synchronize 观察 | 装备栏用 11 槽签名发现拾取/战技等变化；旧全屏 UI writer 已退役，药剂复用既有 mutation revision |
| expectedRevision + writeEpoch + 显式 reconcile | loadout 写、迟到 snapshot、未知结果沿用同一反乱序原则 |
| close/断线撤销 session/token | 角色构筑额外要求先 flush dirty live actor，并在关闭路径完成持久化 finalize，再释放 pause |
| HUD-null、坏档与外部 writer 单独 Gate | 角色构筑保持 HUD 可缺失、坏档 fail-closed 与外部变化可观察；旧全屏 UI 不再是验证或回退路径 |
| 分片施工而非一次删壳 | B0 合同 → B1 只读 → B2 穿脱/药剂 → B3 worn tuning → B4 切流 |

### 1.3 明确不照搬 Skill 的部分

- 不新建 `panel=drugs` 或 `panel=character-build`；角色构筑与收纳需要共享同一 workbench/pause/session。
- 不把 DrugInventory 伪装成快捷技能数组，也不复用 Skill 的教师 session、学习 token 或 80 行存档规则。
- 药剂装配是背包与 DrugInventory 之间的真实物品事务，必须携背包 slot lease；Skill equip 没有这个容器交换问题。
- 角色构筑有延迟活体刷新，Skill 没有同等的 close flush barrier。
- Skill 的 same-panel trainer rebind 不是 `build ↔ storage` 的实现模板；后者应是同一实例内部 view switch。

## 2. 已核实的当前地面事实

### 2.1 当前调用拓扑

```text
NativeHud EQUIP_UI
  → LauncherCommandRouter
  → openInventoryWorkbench(profile=battlebox, view=build,
      source=nativehud_equipment, openRequestId)
  → AS2 preflight + panel_request
  → PanelHost workbench / domain=loadout
       ├─ 11 个 EquipmentInventory 槽
       ├─ 4 个 DrugInventory 槽
       ├─ PlayerInfoProvider 只读属性
       └─ EquipmentTuningService 已穿戴单件调制

背包药剂装入/卸下
  → CharacterBuildService 领域命令与现场裁决
  → _root.玩家信息界面.快捷药剂界面[0..3]
  → DrugInventory

现役 Web workbench
  ├─ view=storage：背包 ↔ 仓库/战备箱
  ├─ view=build：角色构筑、药剂与个人信息
  └─ view=tuning：背包/已穿戴装备 → EquipmentTuningService
```

目标不是把上述所有责任塞进一个新类，而是让同一 Web 会话组合四个明确参与者：

```text
CharacterBuildSession（生命周期、revision、flush barrier）
  ├─ loadout authority：装备/药剂管理
  ├─ InventoryCoordinator：背包 lease、战备箱收纳、external write gate
  ├─ EquipmentTuningService/View：背包或已穿戴单件调制
  └─ PlayerInfoProvider projection：flush 后只读属性
```

### 2.2 容器与槽位

| 权威 | 当前类型 | 槽位 | 现有版本能力 | 角色构筑含义 |
|---|---|---:|---|---|
| 背包 | `ArrayInventory` | 50 | 容器提供 `mutationRevision`/transactionWrite；`InventoryPanelService` 另行签发 slot lease | 候选唯一直接来源 |
| 装备栏 | `EquipmentInventory` | 11 个字符串键 | 无 mutation revision、无事务写 API | B0 首要缺口 |
| 药剂栏 | `DrugInventory` | 4 | 继承 `ArrayInventory` 的 revision/事务能力 | 可复用，但写前需冷却权威复核 |
| 战备箱 | `ArrayInventory` | 剧情开放前缀 | 现役 InventoryPanel authority | 只通过 storage 搬到背包 |
| live hero | MovieClip + 装备生命周期 | 非容器 | `_root.刷新人物装扮` 重建 | 只在 stats/close 批次刷新 |

装备栏必须显式白名单，因为 `EquipmentInventory` 自身检查的是 `_root.getItemData(item.name).use == key`，另有 `use=手枪 → key=手枪2` 特例，并不提供完整合法键集合。现役 dressup manifest 虽有 99 个 `use=颈部装备` 条目，但这些条目的 `dressup` 均为空、`fieldsByGender` 均无有效分支，`ARMOR_FOCUS_CONTEXT["颈部装备"]` 也为空；运行时只能回退静态物品图标，不能称为已有视觉 projection。B0 要锁定这一现状以及其他部位未知值/缺素材 fallback：视觉降级不得让管理槽、候选、snapshot 或提交能力消失。

### 2.3 服务外写者不能忽略

| 写者 | 装备/药剂影响 | B0 对策 |
|---|---|---|
| 旧物品 Hub 拖放/卸下 | 2026-07-30 已退役，不再是生产写者 | 源与 main/SWF 可达性负门禁止恢复；签名观察不为它提供兼容 |
| 组合键拾取 | 可直接装备、替换旧装备并切武器模式 | 不在首版重写；签名发现，按现役外部 writer 审计 |
| 长枪主动战技的手雷 fallback | `调用射击发射其他弹药` 在 `singleSubmit` 失败且目标为受控自机时才尝试装备栏手雷；数量大于 1 时直接 `value -= 1`，绕过 `addValue`、事件与任何 revision，耗尽才 `remove("手雷")` 并刷新 | 装备签名必须覆盖 stack 数量/对象更新时间；不能只依赖容器事件或 revision |

暂停游戏能降低并发，但 `ManualCooldownService` 明确在暂停期间继续推进，且现役代码仍有不依赖玩家输入的外部 writer。session 设计必须以版本/签名为依据，不以“理论上不会发生”为依据。

### 2.4 活体刷新是行为重建

`_root.刷新人物装扮` 不只是换贴图。它会清理射击状态、重新运行单位初始化、卸载/安装装备生命周期、重建 Buff/组件与参数、重算负重/速度/技能、切换武器模式并把角色送回安全动作帧。候选 hover、点击预览或每次装备提交都调用它，会把普通菜单操作变成反复重建角色。

因此首版只允许：

```text
装备穿脱 / 已穿戴调制提交成功
  → loadoutRevision++
  → liveRefreshDirty=true
  → Web 纸娃娃立即用结构化装备快照重绘
  → stats/close 时最多执行一次 live flush
```

药剂装配提交只推进 `drugRevision` 与全局存档 dirty；它不进入上述 loadout/live 刷新链。

当前函数没有显式成功返回值。B0 必须由 wrapper 建立“调用前依赖齐全 + 调用后 live hero 与装备投影一致”的 Boolean 证明；失败时保留 dirty 与 pause，不能猜成功。只检查“没有 throw”或 `UnitInitialized` 事件不足以证明外层被动、Buff、安全帧和装扮引用刷新已完成。

### 3.1 状态机

```text
edit/candidates（默认主态）
  └─ 当前槽已有装备 / 调制当前装备 ──→ edit/tuning（右栏钻取，复用 tuning view）
edit/tuning ── 返回候选 ──→ edit/candidates

edit/candidates ── 信息 ──→ flush_pending(stats)
       ▲                         ├─ 成功 → stats（全宽 SecondaryPage）─ 返回编辑 ─┘
       └─────────────────────────┴─ 失败 → flush_failed ── 重试/返回 ──┘

edit/candidates ── 收纳 ──→ storage（同 panel，同 pause，不 flush）
storage ── 返回构筑 ──→ fresh snapshot → edit/candidates

edit/candidates/stats ── 整备→技能（B7 on；off 为技能配置） ──→ finalize → exact Web retire
  └─ AS2 recoverDetach 已确认 / coordinator settled
       └─ Host `skillPanelOpen(openRequestId)`
            └─ AS2 `panel_request(skills,nativehud/manage,exact openRequestId)`
                 └─ Host baseline/nonce 全匹配后打开 Skills
                      ├─ 显式“返回构筑” → exact Skills close
                      │    └─ visual idle + SkillTask closed/settled
                      │         └─ `openInventoryWorkbench(new openRequestId)` → fresh build
                      └─ × / Esc / native backdrop → 普通关闭到游戏

Skill 打开失败 ──→ 至多一次 `skill_open_rollback` → fresh build
  └─ 回滚失败：停止并提示从“装备”重开，不循环

任一可关闭态 ── close ──→ flush_pending(finalize)
  ├─ live/global 均 clean：finalize no-op 成功后发 exact close
  ├─ live/global 任一 dirty：finalize 刷新/存盘成功后发 exact close
  └─ write_pending / needs_reconcile / flush_failed：保持面板或 pause，不越过
```

`write_pending` 与 `needs_reconcile` 是覆盖态，不是可借切页逃逸的普通页面。出现时禁止进入 tuning/stats/storage 和发起第二个写；确定失败回到可操作态，未知写只允许权威对账，不自动重投。

### 3.3 槽、候选与提交

1. fresh open 不自动选择槽；焦点先到角色构筑区域标题/首槽，右栏立即显示无目标背包总览，不显示“先选槽”空态。
2. 点击或 Enter/Space 选择槽后进入该 target 的 `compatible` 筛选；点“背包”范围清除 target 并恢复总览。切换都会丢弃未提交候选预览，不写 AS2。
3. `candidates` 有两种浏览语义：已选 target 的 `compatible` 只返回当前槽候选；无 target 的 `backpack` 返回全部合法背包行及权威资格。两种 scope 中的装备候选都携同一 AS2 权威 `equipmentEligibility` 白名单；scope 只控制候选集合，不能把兼容态的落点钉死为当前浏览槽。两者都按物理槽稳定排序；筛选与搜索只能缩小可见集合，不能改变 authority。
4. hover 只显示共享 tooltip，键盘 focus 只更新候选摘要；二者都不换装、不提交。hover 纸娃娃预览不是 B0/B1 Gate，若以后增加，必须先过 doll 性能 spike，并采用 debounce/latest-wins。
5. 候选单击或首次 Enter/Space 固定预览；纸娃娃仍是单 Canvas，以当前已提交 state 加一层候选覆盖重建。再次单击同一候选或在同一候选上按 Space 清除选择/预览且零写入；只有同一已预览候选上的明确、非 auto-repeat Enter 等价触发主 CTA。
6. 主 CTA 只发送一次原子 equip，且与“同一候选第二次 Enter”共用同一 disabled/write gate。拖拽可把候选送到白名单中的任一 exact 落点，药剂目标的 per-slot 冷却由 Host/AS2 写前复验。成功后采用完整 loadout + affected inventory snapshot，清预览并保留写前浏览上下文：无目标背包总览仍无 target，兼容槽 A 拖到槽 B 后仍以 A 为筛选锚点；确定失败和对账收束同样不得采用 drop target。只有显式点槽或切换 scope 能改变浏览上下文。候选物理格仍存在则保留焦点，否则回到浏览锚点或总览入口。
7. 普通装备在目标已占用时仍 swap：新装备进目标槽，旧装备回 exact 背包来源槽；目标为空时是 move。数量型手雷/药剂的同名装入则是 merge：保留已装 target 对象、累加数量并删除 source；异名才 swap。该语义由 AS2 事务和 rollback 测试锁定，Web 只发 exact target/source。
8. “卸下”位于右侧当前装备动作区，不在 48px 槽角落放小 `×`。手雷/药剂卸下先合并到物理槽序最小的同名背包堆，没有同名堆时才需要空位；普通装备仍必须有空位。无合并目标且满包时保持原状态并显示原因。
9. 候选动作直接并入“背包候选 / 候选对比”同一 PaneChrome 标题行，最多按“装备 / 调制（或不可调制）/ 卸下”排列；按钮 `aria-label` 使用完整动作语义，不可调制目标同时给出 disabled、`aria-label` 与 `title` 原因。药剂槽与未知写对账分别把主动作切为“装入 / 装入所选药剂”和“确认 / 重新确认结果”。“装备”是唯一主 CTA。现役候选 projection 没有候选专属详情，故不保留 generic“详情”与 pin。1024×576 下最多三项保持单行、不换行、不横向溢出；候选可滚区底部不重复 action rail 或长篇 Space/Enter 帮助。
10. density 在构筑态只作用右栏候选网格，在 embedded tuning 只作用材料、配件、转换候选等浏览型卡片。full 使用 68px owned-card 节奏并保留名称与关键 meta；compact 使用共享 48px 格、40px 图标和 4px 间距。compact 隐藏的中性 preview badge 不得承载独占业务信息，选中、blocked、数量等继续由角标、ARIA 与单行摘要表达；左侧 11+4 槽、纸娃娃、operation tabs 与主提交语义保持不变。
11. storage、Character Build 候选和 embedded tuning 复用同一个持久化 density toggle DOM、同一个 `GridDensityController` 与 `cf7.itemgrid.mode.workbench`：切换上下文时只迁移挂载点，不复制控件、不创建第二份偏好。full → compact → full 必须保持候选顺序、选择、预览和稳定 key 焦点，且不产生任何 loadout/inventory/tuning 业务请求。

### 3.4 药剂管理

- 选择药剂槽后，右侧只显示 `use=药剂` 的背包候选。
- `equipDrug/unequipDrug` 写前重新检查 `ManualCooldownService.isReady("drug:"+slot)`；Web 的冷却显示不是授权。
- 现役 `ManualCooldownService.getSnapshot()` 只返回 `ready/totalSteps/currentStep/progressPercent/animationFrame`，没有 `remainingMs`。目标协议中的 `remainingMs` 必须由 AS2 projection 使用公开 `FRAME_MS` 推算为 `ready ? 0 : max(0, totalSteps-currentStep) * FRAME_MS`，不能当作现成 getter。`keyLabel` 必须由 AS2 沿用 `DrugInputService.getKeyName(slot) → _root[keyName] → _root.keyshow(keyCode)` 的现役来源生成，不能从纸娃娃 renderer 或 Web 默认数字猜。Web 可本地显示估算进度，到预计结束时只发一次 fresh `snapshot` 再开放写按钮；不创建独立 `drugState` 命令，也不做高频轮询。
- 药剂写返回 DrugInventory 新 revision、四槽完整快照和受影响背包窗口；真实改变统一 dirtyMark。
- 任务、购物与普通拾取继续共用 `ItemUtil.acquire`。对可合并数量先预计划已装同名手雷，再预计划已装同名药剂，然后才查同名背包堆/空位；因此背包已满也能直接补入已装堆。合并保留已装 exact item ref 并更新数量/时间戳，Shift 拾取不先把已装手雷拆回背包。
- 战斗中消耗/耗尽引发 revision 变化后，下次 snapshot 直接采用权威状态；Web 不维护独立数量镜像。
- 旧 HUD 存在时可以继续接受可选 renderer projection；HUD-null 是正常路径，不得成为装配写前置。

### 3.5 已穿戴调制

- 调制能力门与 AS2 `validateEquipment` 的可观察前置保持一致：`itemKind=equipment`、`majorType=武器|防具`、`enhancementLevel` 为不小于 1 的整数。空槽/药剂隐藏入口；占用但不满足能力门的装备槽显示 disabled“不可调制”及精确原因。数量型手雷虽位于装备栏，仍是 `itemKind=stack`，不能以槽位位置冒充装备。
- 进入后撤销候选预览，右栏挂载同一 `EquipmentTuningView`，source 文案改为当前槽/当前装备；同一 density toggle 随之迁入 tuning 标题行，只改变调制浏览型卡片的密度。
- adapter 形状严格区分 `sourceKind=inventory|loadout`：背包来源固定为 `{sourceKind:"inventory",containerId:"背包",slot,expectedLease}`；已穿戴来源固定为 `{sourceKind:"loadout",sessionGeneration,slotKey,expectedLoadoutRevision}`。`loadout` 必须同时命中当前 CharacterBuild session generation、显式 11 槽白名单和当前 loadout revision，不接受任意 `containerId/slot/expectedLease`；Host 与 AS2 各自按 exact key set 复核。
- 允许 enhance、tier、install/replace/detach mod 等单件原地操作，也允许 loadout source 与 exact 背包 inventory target 的 `convert`。convert 候选只由现役背包投影返回；非背包 target、stale loadout revision、stale target lease 或非同 `use` 均 fail closed。
- 非 convert 成功 commit 继续先提交 worn value + 材料事务，`inventorySnapshots` 必须为空；改变强化度的 loadout convert 则在单一 AS2 临界段中以 worn receipt + backpack receipt 提交双侧，任一 pre-authority 失败必须回滚 value/lastUpdate/两个 raw revision。成功时 `CharacterBuildService.synchronize()` 只推进一次 `loadoutRevision`并置 live dirty，回包同时携写后 tuning snapshot 和唯一完整背包 snapshot；同级 no-op 两侧零写且不伪造背包快照。
- Web 在同一 external-write 锁下先采用 Host 校验的写后 tuning/背包证明，再发普通 `domain=loadout snapshot` 收敛完整 11+4 projection。convert 成功后必须清除旧 target，用新 lease 重读候选；任一快照不完整或采用失败，保持锁定并进入 retry/reconcile。
- tuning commit 的未知结果先在同一有序 socket 上取得 fresh `domain=loadout snapshot`，再用当前 generation/revision 发送 `domain=equipment_tuning snapshot + reconcileAfterCallId`。若操作为 convert，还必须在释放锁前 fresh 刷新背包；三份证明都成功才解锁，绝不重放 token。不得拿提交前的 stale `expectedLoadoutRevision`/旧 target lease 绕过校验，不得让 `EquipmentTuningTask` 直接篡改 `CharacterBuildTask` Host shadow。
- 返回候选时恢复原槽、候选滚动和合理焦点。强化 number/range/mark/stepper/cap preview 保持发起控件焦点，只有候选/交换 preview 才允许迁移 CommitBar 语义焦点；`projectLoadout` 锁必须按 owner 保存/恢复 base/original `disabled` 与 `aria-disabled`，不得误解锁 drug/empty/blocked 或原生 disabled；confirmation wrapper 使用具名 `role="group"`，generic section 不承载 `aria-disabled`。旧版 tuning 全量重建 DOM 曾只恢复 scroll、不恢复焦点；该债已与 adapter 同轮关闭，现役实现按稳定实体键恢复焦点。
- tuning 活跃时选择另一件可调制装备，必须在同一 tuning session 内完成 source rebind，并让左侧选中、右侧标题与 snapshot 一起切换；选择数量型手雷、药剂、空槽或其他不可调制目标时，先发送一次 exact detach。detach 成功后才用微任务重新执行普通槽选择与候选读取，detach 失败或仍在途则立即回滚左侧 provisional selection 并保持右侧原调制对象；迟到回调还必须匹配原 mount generation 与 panel instance，禁止复活已卸载视图。
- 现役 rich tooltip 已通过 `bindAsyncHover` 兼容名迁移到 neutral input contract，pointer 与键盘 focus 都可达，B3 不得重复造一套“键盘等价 tooltip”。已在同轮偿还的可用性债包括：tab 主标签从 9px 提升到至少 11px、31px 主 CTA 提升到至少 40px、用完整文字“调制说明”替代含义不明的 `i`、全量 DOM 重建后按稳定实体键恢复焦点。说明主题按 operation 显示强化当前/目标与上限、进阶当前档位、已安装配件数量或转换强化水位，并始终跟随当前 operation/focus；不提供会跨选择保留陈旧对象的 pin。Esc 先关闭检视 modal，再收起内联说明，最后才退出调制。本轮只修这些接入债，没有借机重做整套调制视觉。

### 3.6 个人信息

个人信息已冻结为覆盖整个 workbench body 的全宽 SecondaryPage，不再把 40+ 个展示字段/派生写入挤入右侧候选决策栏，也不保留一块不可操作却持续占宽的纸娃娃。旧 MovieClip renderer 只使用稳定口径“40+”，不把实现层随版本漂移的直接字段/派生写入拆分当作协议；现役结构化 `PlayerInfoSnapshotBuilder` 则冻结为 **9 组、47 行**：基础信息 6、负重 6、生命与能量 3、魔法抗性 8、防御 5、韧性 4、命中与移动 4、伤害加成 5、武器威力 6。两种口径不得混写。

- 进入 personal info 前必须排空写、完成 reconcile 并经过 `flush_pending(stats)`；只有 `liveRefreshDirty=true` 时实际刷新人物，live clean 时 barrier 以 no-op 通过；

- 正文至少 11px，字段名不得截断，不允许嵌套横滚；1024×576 仍要覆盖最长中文、极端数值和完整键盘顺序；
- stats 是只读 SecondaryPage，装备/药剂/调制控件不挂载、不可聚焦；返回 edit 不刷新，只重新挂载编辑视图并恢复先前槽焦点。

负重带是旧 Flash 设计的忠实升级，而不是 Web 侧新公式：指针只读取 AS2 已钳位的 `weightRatio`，刻度只读取 `lightMediumThreshold / mediumHeavyThreshold / heavyThreshold`，速度只显示 AS2 终值 `movementSpeed`，状态只读取 `encumbranceState`。轨道保持 0–25% 绿→黄、25–50% 黄、50–100% 黄→红的连续语义；颜色之外同时显示轻/中/重文字、三个 kg 刻度、状态和当前读数。任一比例缺失或阈值无序时不画 gauge，只保留原始 47 行，禁止默认为 0。

武器威力与魔法抗性的横条由 `character-build-stats-view.js` 仅在整组都是有限非负值时呈现。武器威力先用 `log10(value + 1)` 做视觉压缩，再按当前组最大变换值归一，并明确标注“对数相对量级”；抗性保持原值线性组内归一并标注“当前组相对量级”。两者始终打印原始数值；任一行缺值或为负，或整组全零时，只撤掉对应图表、保留完整明细，不能用绝对值把负数画成同方向高值。这个 `log10` 只服务显示，不能进入 AS2 公式、候选预测、DPS 或 authority。抗性首屏使用 4 列 × 2 行，完整明细使用 2 列 × 4 行；八种抗性各有 `currentColor` inline SVG 装饰图标，统一 `aria-hidden`，中文字段名和原始值仍是可访问权威。抗性可超过 100，不能硬套 0–100 轴；防御、减伤、生命、经验等缺少明确共同边界或构成合同的字段只作 KPI/精确读数，不画雷达、饼图、sparkline、经验/HP 伪进度或防御堆叠条。

stats wire 只接受结构化值：

```js
{
  group: "defense",
  key: "damageReduction",
  label: "减伤率",
  value: 95.7,
  unit: "%",
  displayHint: "percent-1"
}
```

普通 row 固定上述标量形状；称号仍以纯文本标量 `value` 为权威，并可额外携带受限 `spans:[{text,color?,size?}]` 与 `displayHint:"styled-text"`。AS2 只接受现役 `<font color=... size=...>` 子集，`color` 限 `#RRGGBB`、`size` 限 `1..72` 整数；未知属性、未知/嵌套/未闭合标签整段降为不可执行纯文本。legacy renderer 只能从已净化 spans 重建受限 font；Web 现役 presenter 会复核 `spans.text` 拼接等于标量 `value`，再以 `textContent` 与 DOM span 投影安全颜色/受布局上限约束的字号，不把原始 HTML 重新引入 DOM。

不得把 `<font color=...>`、MovieClip 字段名、布局坐标或拼好的 `"14.6m/s"` HTML 当作协议权威。现有 getter 可作为公式来源，`populatePlayerInfo(target)` 后续应成为结构化 snapshot 的 legacy renderer adapter，而不是反过来从旧 UI 抄值。

### 3.7 收纳、Esc 与焦点

- `PreparationNavigationV1` 默认 on 时由“整备 → 战备箱”进入同一 workbench 的 `view=storage`，只显示背包 ↔ 战备箱 transfer-pair；显式 off 或非法配置恢复旧 header“收纳”导航 presentation，但仍打开同一 Web workbench，不打开第二 panel 或任何 AS2 fallback。
- “整备 → 技能”不是同实例 view dispatch。它先走 Character Build finalize，再发送 exact `navigate_skills` close，由 Host 在视觉退休和 AS2 恢复确认后触发现役 Skills preflight；Web 不乐观挂载 Skills，也不携带 loadout session 状态过去。落点与刘海屏“技能”业务能力一致，固定为 `source=nativehud, view=manage`；不签发教师 capability、不带 `trainerSession/canReturnTrainer`，因此只允许管理自身技能。只有 Character 来源的 exact manage 可额外显示无权限 `canReturnCharacterBuild`，Notch 直开不显示；旧 header“技能配置”不再是入口。
- 在 Skills 面板内，“← 返回构筑”是该面板唯一反向入口，发送 exact `navigate_character_build`；`×`、物理 Esc 与 native backdrop 始终普通关闭到游戏。返回入口在 Skill write/reconcile/cleanup 非 idle 时 disabled，Host 仍复验能力；帮助/确认模态与展开搜索先消费 Esc。返回成功后重建 fresh Character session/snapshot；默认 on 时焦点落到稳定“整备”，显式 off 或非法配置时落到旧“技能配置”presentation。两种 gate 状态都不保留旧 Skills DOM opener，也不恢复退役 AS2 技能 UI。
- 进入前撤销未提交预览与 tuning token，等待所有写定局；不 flush live actor。
- storage → 构筑强制 fresh backpack/loadout/drug/candidate snapshot，保留仍合法的所选槽，不保留旧 slot lease；Skills → 构筑是新 session；默认 on 恢复稳定“整备”焦点，显式 off 或非法配置恢复旧“技能配置”presentation focus，但都不恢复旧槽位/候选或任何 AS2 全屏 UI。
- Esc 顺序固定：关闭纸娃娃放大预览 → 关闭调制检视 modal / 收起调制说明 → 清未提交候选 → 退出 tuning/stats/storage 回 edit → 请求关闭。每次只消费最上层；`write_pending/needs_reconcile` 时 Esc 不得抹状态。
- 当前共享 `EntityTile` 只处理 Enter/Space，方向键导航仍是 `inventory-ui.js` 的私有实现，仓库里并不存在可直接宣称复用的 Grid keyboard primitive。B0 要从该语义提取一个窄、无领域知识的 `RovingGridFocus`：只管理 active tabindex、四方向移动和销毁；护具、武装、药剂组可提供显式邻接，候选 grid 提供列数。B1 前不得再造全局空间导航引擎。
- 格子区域把护具、武装、药剂、候选四个逻辑组各压成一个 Tab stop，组内用方向键移动；header、筛选、主 CTA、调制和卸下等普通动作仍按正常 Tab 顺序可达。不要让 15 个槽加全部候选形成超长串行 Tab。
- selected、preview、cooldown、disabled 不得只用颜色表达；必须有文字/图形状态、清晰 focus ring、ARIA label/state 和提交后的 aria-live 回报。

## 4. AS2 authority 与 `CharacterBuildSession`

### 4.1 最小职责，不造万能 Coordinator

术语在三层固定分工：`CharacterBuildSession` 仅指跨 Web/Host/AS2 的逻辑会话寿命、pause、revision 与 flush barrier；AS2 唯一业务类暂称 `CharacterBuildService`；Web 对应的薄状态模块是 `character-build-session.js`。本文出现 Session 不代表再新增一个与 Service 并列的 AS2 writer。

首版建议只有一个窄的 AS2 `CharacterBuildService`（最终类名可在 B0 spike 后冻结）：

- 开始/结束一个构筑 session；
- 读取 11 个装备槽、4 个药剂槽、背包候选和纸娃娃 projection；
- 原子执行 equip/unequip equipment、equip/unequip drug；
- 维护装备签名、`loadoutRevision/liveRevision/liveRefreshDirty`；
- 读取 DrugInventory revision；
- 调用/验证一次性 live flush 与关闭 finalize；
- 生成结构化 stats snapshot；
- 为 generic unpause 和 socket detach 提供幂等 fallback。

它不接管：

- InventoryPanel 的仓库/战备箱规则；
- EquipmentTuningService 的强化/材料事务；
- DrugInputService 的使用/耗尽；
- ManualCooldownService 的调度；
- PlayerInfoProvider 的公式；
- Host 的 call tracker 或 Web DOM。

只有当单类在实际 B1 代码中越过现有体积/职责审计阈值，才拆 `CharacterBuildProjection` 等叶模块；B0 不预造通用 loadout framework。

### 4.2 session 状态

逻辑状态至少包括：

```js
{
  sessionGeneration,
  capturedPauseLease,
  equipmentRef,
  drugRef,
  backpackRef,
  equipmentSignature,
  loadoutRevision,
  liveRevision,
  liveRefreshDirty,
  lastDrugRevision,
  state: "idle|write_pending|needs_reconcile|flush_pending|flush_failed"
}
```

关键规则：

1. `loadoutRevision` 是装备栏权威状态水位；装备/已穿戴调制语义变化与手雷数量等状态漂移都会推进，药剂变化不推进。若变化不要求重建且 live hero 通过 exact reference 已同步观察到（典型为同一手雷对象直接扣量），`liveRevision` 同步追平且不置 dirty；只有需要重建的变化才令两者分叉并置 `liveRefreshDirty`。
2. 每次 snapshot、候选读取和写前都同步装备签名与容器引用；发现服务外变化时推进 revision、撤销旧 preview/token 并按当前 live 匹配情况置 dirty。
3. 装备观察分为两层。session 的 state signature 比较 11 个显式有序键的 exact item reference，并纳入数值 value 与 item `lastUpdate`，用于捕获手雷数量和持久状态水位；`RuntimeEquipmentProjection` 则在完整 Dressup 后保存 applied canonical exact refs 与仅含 `level/tier/mods` 的 live semantic signature。`mods` 为 Array 时保序，为 legacy Object 时按键排序后编码。`shot/reloadCount/subweaponShot/subweaponReloadCount/当前战技/wa90变形/长柄形态`、HP/MP、Buff 内容、姿态与攻击模式均不是 live identity。复合武器只可通过 owner/version 绑定的空槽 alias intent 物化运行态槽位，manager 将其规范化回 canonical 后再判定 aligned；未登记裸写、exact ref 替换或 live semantic 变化仍为 mismatch。
4. DrugInventory 使用自身 `mutationRevision`；引用替换或 revision 倒退视为 session stale，不在 Web 端修复。
5. session 写成功后重新签名，只推进一次 revision；no-op 不 dirty、不刷新、不推进。
6. 已穿戴 tuning commit 必须显式回调/通知 session；下次 synchronize 的签名发现只是兜底，不是正常成功路径。
7. `flushLive/finalize` 的业务拒绝、后置条件失败或本地存盘明确失败进入 `flush_failed`；Host 已接受后发生 timeout、断线或畸形结果则是结果未知，进入同一个 `needs_reconcile` 覆盖态。
8. unknown `flushLive` 可由越过在途水位的 fresh snapshot 证明 `liveRevision==loadoutRevision && liveRefreshDirty==false` 后收敛；unknown `finalize` 不能只凭 live clean 发 close，必须在同一 `sessionGeneration` 下对幂等 finalize 做显式重试并取得 persistence phase success。该重试不是 mutation 自动重放，AS2 socket fallback 也必须走同一幂等函数。

### 4.3 装备事务缺口

`EquipmentInventory` 当前没有 `transactionWrite/getMutationRevision/publishTransactionChange`。B0 要比较两个最小方案，默认优先更窄者：

| 方案 | 优点 | 风险 | 裁决门 |
|---|---|---|---|
| A：只给 `EquipmentInventory` 增加 mutation revision 与无事件单槽事务 API | 影响面最小，语义明确 | 与 `ArrayInventory` 有少量重复 | 能覆盖 11 键、rollback、dispatcher 统一 publish |
| B：把事务能力上提到 `Inventory` 基类 | 以后其他 Inventory 可复用 | 可能与 ArrayInventory 现有实现/版本语义冲突 | 只有确认无 shadow/override/初始化回归才考虑 |

首版禁止直接串联公开 `remove()+add()` 后宣称原子。装备 ↔ 背包、药剂 ↔ 背包的事务必须：

1. 完整预检 source lease、target revision/signature、等级/use/手枪2/冷却/容量；
2. 备份两个槽；
3. 无事件写入两个容器；
4. 第二写失败时恢复 exact before；
5. 全部成功后统一推进各自 revision、失效旧 lease、发布兼容事件、dirtyMark；
6. 返回完整权威快照。

同步事件监听器不得观察到半交换状态。raw `ArrayInventory/EquipmentInventory.mutationRevision` 是保守失效水位：第一写后第二写失败并回滚时允许继续单调推进，以确保旧 lease 全部失效；但物品 exact state、全局 dirty 与领域 `loadoutRevision` 必须保持事务前值。测试必须有“第二写失败、rollback false/throw、dispatcher 重入”反例，不能把 raw revision 推进误报为业务提交成功。

### 4.4 live flush 与成功证明

`flushLive(expectedLoadoutRevision)` 的顺序：

1. synchronize；若出现未知服务外写，先返回 fresh snapshot/`stale_state`；
2. 若 `loadoutRevision == liveRevision && liveRefreshDirty==false`，返回 `changed:false`，零刷新；
3. 确认控制目标、live hero、装备容器、刷新函数与必要初始化依赖存在；至少检查 hero 仍挂在 gameworld，dispatcher、Buff、被动、goto、安全帧与装扮刷新依赖可调用；
4. 捕获旧 dispatcher、旧 buffManager、`RuntimeEquipmentProjection` 的 applied canonical 状态和装备派生 data 引用；
5. 调用一次 `_root.刷新人物装扮(_root.控制目标)`；
6. 重新取得 live hero，验证身份与 parent 未漂移；
7. 验证 dispatcher/buffManager 已被重建且有效，manager 对新装备栏 exact refs/语义签名返回 aligned；已提交的空槽 alias 允许运行态 `hero[slotKey]` 指向其 source exact ref，未登记槽写仍失败；
8. 对有装备的槽验证派生 data 已重建；关键 `重量、行走X速度、hp满血值、mp满血值、防御力` 均为有效数值，`魔法抗性/主动战技/生命周期函数列表` 形状有效；
9. 验证外层尾段已完成：`格斗架势===false`，且 dressup 刷新不再处于进行中；
10. 只有后置条件全部成立才写 `liveRevision=loadoutRevision`、清 live dirty；
11. 失败返回 `flush_failed`，保留原 revision/dirty/pause，不调用 stats projection，并锁存 retry-required；即使失败刷新已留下 aligned equipment stamp，也不能在下一次 synchronize 中把半完成结果自动采信为 clean。

初始 open/synchronize 的 dirty 只由 manager 的 canonical `aligned/mismatch` 决定。派生 data 或投影 stamp 缺失属于 `live_unavailable`，不能猜测式刷新；重量、速度、满 HP/MP、防御、抗性、主动战技、lifecycle 数组与 `格斗架势===false` 只保留为真实刷新后的后验，不参与“查看面板是否需要刷新”的判断。

B0 可以在 AS2 `CharacterBuildService` 的同步 wrapper 中用 `try/catch + 前后不变量` 完成首版证明，不需要改造整套初始化器或新增事件框架。不能用固定延时、动画帧猜测或“函数没 throw”代替成功证明。

### 4.5 正常关闭、generic unpause 与 socket detach

正常路径：

```text
Web requestClose
  → discard local preview
  → Web character-build-session wait/reconcile
  → domain=loadout cmd=finalize
      ├─ live dirty 时执行并证明一次人物刷新
      └─ 全局 dirty 时执行现有 SaveManager.flushNow()
  → success + clean live revision + persistence phase success（actual flush true 或 global-clean no-op）
  → exact workbench close envelope
  → Host 校验 active panelInstanceId / CharacterBuildTask clean，并先原子立 recovery/admission barrier
  → Host exact-instance 关闭当前 native/Web visual，等待视觉退场完成回调
  → Host-only domain=loadout recoverDetach（generic Web 无权发送）
  → CharacterBuildService 重放 finalize receipt、校验 captured/global exact lease
  → release captured pause lease
  → Host 校验 acknowledged terminal proof 后才消费 binding、解除 open/returnTo gate
```

跨面板双向交接在上述 Character close proof 之外再增加独立 Host 能力，不能把两套领域状态合并：

- Character→Skills 的 one-shot 只在 exact Character close 前武装；Skill `panel_request` 经 `openRequestId/source/view/baseline` 准入后，Host 在生成 Skills `panelInstanceId` 后才可将 `canReturnCharacterBuild` 与该实例绑定。Web 夹带同名字段、Notch/trainer 来源或 rebind 不能铸造能力；
- 显式 `navigate_character_build` arm 时即原子消费返回能力，但不会立刻打开 Character。Host 先 authoritative-close Skills，再等待 tracked visual idle 与 `SkillTask.IsClosedAndSettled`；后者要求 binding 已清、write idle、pending/queued reconcile/cleanup/backoff 全空。visual 与 coordinator 两条完成回调乱序时共享 exact generation，一次成功后其余回调 no-op；
- 新 workbench preflight 始终携新的 `openRequestId`，且只允许 exact `{panel:"workbench",source:"nativehud_equipment",profile:"battlebox",view:"build"}`。AS2 的职责仅是严格 token 校验与该 tuple 顶层回显；Host baseline 同时验证 active panel/instance、queued command、reserved owner/instance 与 idle/processing fence。迟到 A 不得消费 B，其他 tuple 或缺/错 nonce 不得取消正确 wait；
- Web navigation/热重载、socket disconnect 与 shutdown 是 lifecycle cancellation barrier：先推进 cancellation generation/epoch，再撤销 Character↔Skills navigation one-shot、Skill/workbench opener wait、queued/reserved admission 与未绑定 init context；所有完成回调在创建下一段 wait 或 open 前复验该 epoch，相邻 intent 只允许 latest 胜出。competing panel 同样撤销当前能力；active Skills 仍先走 `HandleAuthoritativePanelClosed`/cleanup，Character authority 仍走自身 recovery barrier；
- 前向 Skill 打开失败只允许一次 `skill_open_rollback`。回滚 Character 的 preflight 或 open 再失败就终止并 toast；反向失败不回开 Skills。任何 false open/rebind 都记录失败，不能落 `opened` 成功事件。
- workbench 与 Skill opener 都没有旧 Host 兼容。缺/错/stale nonce 必须 fail-closed；变更两侧已由同一 immutable source/candidate 配对并完成 GUI 人工验收、双故障域共识与 promotion；当前正式 build identity / payload closure 为 `58F1C3F3B128B22CEA4EDAEF74B402976D13ACB09D4A934240FCCFF3FA7C0465` / `B529199F6CC00BC0687E8EED6950C6490F239C56E2A2D4AC27E90366CE2C8CAF`。

异常兜底：

- `webPanelUnpause` 在现有 loot fence 之后只调用 `CharacterBuildService.blocksGenericPauseRelease()` 纯查询。只要仍有未被 Host exact proof 消费的 CharacterBuild authority，就直接保留 pause；generic close 不再执行 finalize、不得重放 receipt，也不得释放当前或后来 lease。
- `ServerManager.onSocketClose` 在清 pending callback 前调用 `reconcileSocketDetach()`。它只可本地 finalize/persist 并**保留** session 开始时捕获的 exact pause lease；AS2 不知道 Host visual 是否已退场，因此 socket close 本身没有释放权。
- Host 的正常 close、navigation 与 socket detach 统一为两阶段：先立 no-new-call/no-rebind barrier，取消或冻结 queued/returnTo open；再等待 exact visual close completion；最后才允许发送 Host-only `recoverDetach`。重连若早于视觉退场，只记录 ready generation，不得抢先发送。
- `recoverDetach` 发现 captured lease 与全局 lease 不一致时固定返回 `stale_pause_lease`，零释放、零消费旧 authority；不得把 mismatch、TCP send 成功或 finalize receipt 降格解释为视觉已退场证明。
- Host 在 acknowledged terminal proof 消费 binding 之前阻断所有新 panel、同名 rebind、loot admission 与 returnTo reopen。AS2 成功回执至少证明 exact panel/session、水位不回退、`active=false`、`closed=true`、`pauseReleased=true`、persistence success、`loadoutRevision==liveRevision` 且 dirty 已清。

当前只有 loot 和角色构筑需要这种特殊处理。B0 使用两个显式、可测试 hook；不因“以后可能还有”提前建通用 registry。出现第三个真实消费者时再评估抽象。

### 4.6 存档 finalize

只标 `dirtyMark` 不足以复刻旧入口的关闭语义：

- 旧 Hub close 在 dirty 时调用 `_root.自动存盘()`，最终进入 `SaveManager.saveAll()`；它只是启动约 300ms trailing debounce，返回不代表已经落盘。
- 现役 Web inventory/tuning 写只标 dirty，generic workbench close 不发保存命令；同场景关闭后立即杀进程存在比旧 Hub 更弱的窗口。

角色构筑把正常 close 视为低频、高价值批次边界，使用现有强入口而不新增通用保存服务：

1. 每个真实装备/药剂/调制写设置 dirty；no-op 不标脏；
2. finalize 先完成 live flush 证明；
3. 若全局 dirty，调用 `_root.强制存盘()` / `SaveManager.flushNow()`；若全局原本 clean，记录 persistence `changed:false` 并直接通过该阶段；
4. 本轮实际调用 `flushNow()` 时，只有 `=== true` 才返回 finalize success；`false` 至少包括 `_root.允许存档 !== true`、已有 save in-flight、当前角色/场景写入 gate 拒绝，以及 SharedObject flush 返回失败/`pending`，任一 `false` 或异常都保留 dirty/pause并允许明确重试；
5. 成功只证明本地 SharedObject flush。随后启动的 Launcher shadow 推送未被该返回值等待，文案与验收不得扩大为“所有外部副本已确认”。

源码复核已确认 `flushNow()` 目前按 `_saveInFlight=true → _doSaveAll() → _saveInFlight=false` 顺序执行，`_onDebounceFire()` 也有同样缺口。B0 必须对两条入口做同一窄化 `try/finally` 健壮性修复，确保 `_doSaveAll` 抛错时 `_saveInFlight` 仍复位，再用失败注入锁定；这不是“发现反例后再看”的可选项。

`try/finally` 本身只解决 in-flight 门，不自动解决提交语义：`_doSaveAll()` 当前在 `flushSO(so) === true` 后立即清两个 dirty latch，随后才执行 `UpdateTaskProgress()`、日志与 Launcher shadow 推送。B0 必须把 `flushSO(true)` 冻结为本地提交点：提交点前失败保留 dirty 并返回 false/throw；提交点后通知失败不得把“本地已落盘”误报成未提交，也不得把 shadow 失败扩写为本地失败，二者分别记录与验收。

另一个独立缺口是“global clean”判定：`SaveManager.isDirty()` 当前只返回私有 `_dirtyMark`，而多数现役 writer 先写 `_root.存档系统.dirtyMark`，后者要到 `saveAll()`/`_doSaveAll()` 才同步进入私有 latch。B0 应增加一个无写副作用的窄查询（语义等价于 `_dirtyMark || _root.存档系统.dirtyMark === true`）供 finalize 决定 clean no-op；不得因为 `isDirty()==false` 就跳过实际待保存状态。

## 5. 协议草案

### 5.1 路由

当前施工工作树的正式候选入口：

```json
{
  "panel": "workbench",
  "initData": {
    "mode": "runtime",
    "profile": "battlebox",
    "view": "build",
    "source": "nativehud_equipment",
    "debug": false
  }
}
```

Host 只接受冻结枚举：

- `profile=warehouse`：仍只允许 storage；
- `profile=battlebox`：允许 storage、tuning、build；
- `view=build` 只能来自 `agent_control` 或 `nativehud_equipment` 白名单 source；NativeHud 路径还必须先完成 AS2→Host 的 exact preflight，普通 Web 消息不能自铸该 source；
- `EQUIP_UI` 固定发起上述 Character Build 路由；旧环境开关与 `openEquipUI` 已物理删除，准入或挂载失败显示可见错误并 fail-closed；
- `MATERIALS` 不伪装成 build view：它在无 Character Build binding/recovery、无其他 Host visual 且 socket 可投递时发送 `openMaterialUI`，进入 Web crafting materials 视图；失败显示 toast，不跳转旧材料帧。

角色数据不放 initData。panel 打开、Web mount 并取得 Host 盖章 `panelInstanceId` 后，再向 AS2 拉 snapshot。

### 5.2 业务 envelope

沿用现役严格形状：

```js
{
  type: "panel",
  panel: "workbench",
  domain: "loadout",
  cmd: "snapshot",
  callId: "character-build.<nonce>.1.17",
  panelInstanceId: "workbench.instance.42",
  payload: { v: 1 }
}
```

业务字段只能放 `payload`；Host 按命令白名单重建 AS2 请求，不透传未知键。`callId` 沿用 `PanelRequestMux` 的字符串 generation/sequence 形状，不能改成可跨会话撞号的裸整数。每个 loadout 请求、业务回包和 panel-control close/cancel 都必须回显并 exact 校验 `panelInstanceId`。全局 close 仍是独立 panel-control envelope，不伪装成 loadout 命令。

### 5.3 最小命令表

| Web cmd | 写？ | 核心输入 | 成功核心 |
|---|---:|---|---|
| `snapshot` | 否 | `v`；对账时带显式 reconcile watermark | 完整 `CharacterBuildSnapshot` |
| `candidates` | 否 | `slotKey` 或 `drugSlot`、expected revisions | 结构匹配候选、disabled reason、背包 source lease |
| `equipEquipment` | 是 | 目标装备键、背包 source ref、expected loadout revision | 完整 loadout + affected backpack snapshot |
| `unequipEquipment` | 是 | 目标装备键、expected revision | 完整 loadout + 背包落位 snapshot |
| `equipDrug` | 是 | `drugSlot 0..3`、背包 source ref、expected drug revision | 四槽药剂 + affected backpack snapshot |
| `unequipDrug` | 是 | `drugSlot 0..3`、expected drug revision | 四槽药剂 + 背包落位 snapshot |
| `flushLive` | 条件写 | expected loadout revision | `changed`、live/loadout revisions、clean state；用于进入 stats |
| `finalize` | 条件写 | expected loadout revision、当前 session generation | live flush 证明 + persistence phase（本地 `flushNow` true 或 global-clean no-op）；用于正常 close |
| `statsSnapshot` | 否 | expected clean live revision | 结构化分组 stats；`liveRefreshDirty=true` 时拒绝 |

Equipment tuning 仍走既有 `domain=equipment_tuning` 命令；只扩它的 source descriptor 和响应组合，不把 tuning cmd 复制到 loadout。`snapshot/preview` 的 `source` 使用 §3.5 的两个 exact 互斥形状，`commit` 仍只消费单次 `expectedTuningToken`；token 内部绑定 source、CharacterBuild generation/revision、规则/材料签名和 operation。`sourceKind=loadout` 的 `convert` 只接受 exact 背包 inventory target，已改变的成功回包必须同时携一份完整背包 snapshot；其他 loadout operation 与 convert no-op 必须携空 `inventorySnapshots`。Host 据 operation/no-op 分支严格校验，Web 按“tuning 证明 + 背包证明 → fresh loadout snapshot”收敛；不新增跨 Task 的隐式状态同步回调。

active `panelInstanceId` 下的首次 `snapshot` 建立或绑定 AS2 `sessionGeneration`；该值随 snapshot 返回，之后的 candidates/write/flush/stats/finalize payload 都必须 exact 携带。Host 不自行铸造它，AS2 对缺失或 stale generation fail-closed；reconnect/reopen 必须先取得新 snapshot，不能续用旧值。

### 5.4 snapshot 最小形状

```js
{
  v: 1,
  sessionGeneration: 4,
  loadoutRevision: 12,
  liveRevision: 10,
  liveRefreshDirty: true,
  drugRevision: 31,
  equipment: [{
    slotKey: "手枪2",
    label: "副手手枪",
    occupied: true,
    item: { /* InventoryPanelService 的安全展示投影 */ }
  }],
  drugs: [{
    slot: 0,
    keyLabel: "1",
    ready: false,
    totalSteps: 90,
    currentStep: 42,
    remainingMs: 1600, // 目标 projection：由 AS2 使用 FRAME_MS 推算，非现役 getter
    occupied: true,
    quantity: 3,
    item: { /* 安全展示投影 */ }
  }],
  portrait: {
    gender: "男",
    equipment: {},
    appearance: {}
  },
  stateHealth: "ok",
  diagnostics: []
}
```

数值只是示例，不是 fixture。真实 schema 必须保持：

- 11 个装备槽和 4 个药剂槽完整、稳定有序；
- 空槽显式 `occupied:false`，不靠缺键猜；
- item 只含安全展示投影，不泄漏 BaseItem 引用、内部 token 或规则对象；
- portrait 复用现有 renderer 输入，不把 Canvas 结果回传；
- `drugs[].keyLabel` 来自 AS2 `DrugInputService` 的现役键位解析链，不从 portrait 或 Web 默认键映射推导；
- `drugs[].remainingMs` 是 AS2 新投影字段，必须从同一份 cooldown snapshot 与 `ManualCooldownService.FRAME_MS` 推算；
- corrupt/unknown state 只读可展示，写 fail-closed。

### 5.5 写状态与对账

Host `CharacterBuildTask` 与 Web session 均使用：

```text
idle → write_pending → idle
                    ↘ needs_reconcile → post-write snapshot → idle
```

- 确定成功采用响应内完整快照；
- 确定失败保持旧权威快照并恢复可操作；
- browser bridge 在 Host 接受前明确返回的同步 `not_sent` 是确定未投递，可恢复 idle；Host 已接受写后，backend `TrySend(false)` 的 `DeliveryUnknown`、timeout、断线、畸形/不完整成功才进入 `needs_reconcile`；
- 普通旧 snapshot 不得清未知写；沿用 Skill 已验证的 `writeEpoch + reconcileId/reconcileAfterCallId` 或同等显式水位；
- 不自动重放 equip/unequip/tuning 等 mutation；unknown `flushLive/finalize` 只按 §4.2 的 post-watermark 证明或同 generation 幂等显式重试收敛；
- pending/recent call 有上限，close/rebind 不得靠清字典伪装已定局。

## 7. 关键转移与失败矩阵

| 场景 | 允许动作 | authority 行为 | UI/关闭行为 |
|---|---|---|---|
| 候选 hover/focus | tooltip/摘要 | 零请求或只读 | 不换装；首版不驱动 doll |
| 候选 click/首次键盘确认 | 固定预览 | 零写 | 单 Canvas 预览，显示 CTA；同候选第二次 Enter 走同一 CTA gate |
| equip 成功 | 采用完整快照 | 背包/装备原子写、revision/dirty | 清预览，恢复槽/焦点 |
| equip 确定失败 | 可重选 | 零部分写 | 显示原因，保持页面 |
| equip 未知 | 仅对账 | 禁止自动重放 | 锁写/切页/关闭，直到 post-write snapshot |
| drug cooldown 未完成 | 可查看 | AS2 拒绝装配写 | disabled + 剩余时间；预计结束后 fresh read |
| 进入 tuning | 撤销候选预览 | 签发/绑定当前 worn source | 右栏钻取，左栏 current-only |
| tuning 未知 | 仅 tuning/loadout 对账 | token 不重放 | 禁止返回 storage/stats/close |
| 进入 stats | wait + flush | `liveRefreshDirty=true` 时恰好一次刷新；否则 no-op | 成功后切全宽 SecondaryPage 才显示准确属性 |
| 进入 storage | wait，不 flush | session dirty 保留 | 同 panel 切 view；返回 fresh all |
| 正常 close | wait/reconcile/finalize | live clean 且 persistence phase 成功（actual flush true 或 clean no-op）后才允许 release | 显示“正在应用并保存当前构筑…” |
| finalize 未知 | 同 generation 幂等显式重试 | fresh snapshot 只可证明 live 部分；不得冒充 persistence success | 不发 close、不释放 pause |
| socket detach | AS2 本地 fallback | exact session finalize/lease proof | Host 视觉关闭不等于已解暂停 |
| flush 失败 | 可重试/诊断 | dirty/live revision 不变 | pause 保持；不得静默回游戏 |
| 外部签名漂移 | fresh snapshot | revision 推进、旧 token/lease 失效 | 丢预览，提示状态已更新 |
