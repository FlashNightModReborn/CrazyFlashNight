# CF7 issue #78｜R1 独立裁决

**结论：有值得消除的重复返工，但证据不足以把现役发布安全链整体判为“流程腐败”。推荐 B′——仅发布入口、复用既有能力、成本受限的前置检查——为主线；A′——两次常规候选窗口的软性攒批——为条件性试行；C 只随主线顺带收敛，不单独立项；不支持无期限 D。原样“每次提交加硬门”的 B 和“强制每日一趟”的 A 均不采纳。**

## Q1｜是否值得行动，选择哪条路线？

### 裁决：处理重复返工，不拆安全链

应区分三类成本：首次正确发布必须支付的信任链成本；可以通过准备顺序减少的失败重来；现有记录尚无法量化的人力等待和注意力成本。不能把三者统称为浪费。

附件足以证明第二类确实存在。例如，任务播报、三维选关、报告恢复，都能对应到已启动的旧云构建，随后因派生闭包问题停用。但另有多份记录明确写着旧 request 在本地被阻断，**没有产生旧云构建**。这既证明优化机会存在，也证明现役前置阻断已经发挥作用。〔P:416–420、470、510、530、585、621〕

| 选项              | 明确结论                                  | 量化理由与收益边界                                                        |
| --------------- | ------------------------------------- | ---------------------------------------------------------------- |
| **B′：发布入口前置检查** | **首选路线；只支持复用既有工具、有限成本验证，不做全提交 hook。** | 至少识别出 3 个派生问题相关旧云 run，合计 **15.47 分钟**工作流挂钟。存在提前发现的机会，但未证明未来净收益。  |
| **A′：常规窗口软性攒批** | **条件性试行，不强制每日一趟。**                    | 同日多次 promotion 很常见，但没有 ready 时间、紧急程度、可合并性证据。应先两窗口试行，不直接追求“省55%”。 |
| **C：提交瘦身**      | **不单独立项；配置一次写对、可合并的记录随 B′顺带处理。**      | 显性 tag 指针桶 6 条、发布审计文档桶 2 条，合计 **8/534＝1.50%**；减少提交不自动减少构建和验收。    |
| **D：保持现状**      | **不作为无期限结论；可以是暂缓工程投入的限时状态。**          | 数据不能证明人力成本不可接受，也不能证明已经可接受。不能用错误统计掩盖已经出现的具体返工。                    |

这里的“首选”是风险与证据约束下的优先序，**不是已经证明某组合具有最高货币收益**。

窗口内 78 个云构建的工作流挂钟总和为 **385.4 分钟，约6.42小时**。177 个 Audit run 合计 **486.8分钟**。这些是工作流时长，不是账单金额，也不能直接认作人的工时；更不能据此支持大型治理工程的确定性收益。〔`cloud-builder-runs.json`、`audit-runs.json`；S:91–110〕

**所有不可动边界保留：**双 signer／双 faultDomain、不可变 source tag 与远端 ruleset、strict v2 production receipt、唯一 promotion writer 原子写入、独立事后 Audit、禁止 v2→v1 降级。小包下载、CAS 复用、身份批量计算和 promotion 校验去重已经存在，不再重复认领收益。〔M:62–67、94；P:17–25、138、199–217〕

Epic 明确要求消除经常性成本，不接受只增加流程。因此，B′若扩成新的完整审计系统、额外人工审批链或精细台账，就超出本裁决支持的范围。〔`issue-78-与Epic26-原文.md`:19〕

## Q2｜40% 与23.8%的分歧，是否影响立项正当性？

**影响立项理由的强度，但不取消调查和小幅优化的正当性。更重要的是：23.8%也不是已经清洗干净的窄口径。**

按包内同一窗口的534条日志重算：

| 口径                  |                 结果 | 能说明什么              |
| ------------------- | -----------------: | ------------------ |
| 主题含“发布／部署／冻结／列车／审计” | **218/534＝40.82%** | 关键词命中率。            |
| 原脚本四类“仪式”分类         | **127/534＝23.78%** | 该分类器的命中率，不是真实成本比例。 |

主材料引用的约210/522旧快照没有独立附入，不能核验其旧统计时刻和组成；应改用当前所附同一窗口的218/534。〔M:35–38；G；S:33–43〕

### 窄口径存在明确业务误收

原正则只要遇到“冻结”就会命中：

* `b994d87b0545` 是佣兵装备托管功能，“冻结”指背包装备的业务语义，却被归入 `ceremony-freeze-derive`。〔G:490〕
* `96c7be5f7a69` 是 NativeHud 功能迁移，“冻结”出现在“面板打开期间会冻结、关闭后显示”的交互说明中，也被计作仪式。〔G:530；P:873〕

“冻结对白协议”“冻结窗口生命周期架构”“冻结军阀关卡化方案”等文档提交也被同一规则收入，不能据此认定发生过发布冻结。没有逐提交 diff，本次不把标题人工修正包装成完整真值分类。〔G:50、354、362、442；S:39–40〕

**仅排除上述两条明确业务反例，就变为125/534＝23.41%。**这不是最终校准值，却已足以推翻“真实值必在23.8%—40%之间”的下界说法。

此外，即便暂时接受127，其中**63条、约49.6%是部署落盘**；剩余64条仍包含必要的首次冻结和真实派生更新，不是64条可删除浪费。提交数也不等于人时、费用或注意力消耗。将其余407条全部归入 `business-or-other`，无法证明仪式是“最大的单类非业务开销”。〔M:40；`commit-classification.csv`〕

因此，立项理由应改成：

> **现有记录显示若干重复出现、可能前移发现的发布准备失败，需要在不削弱信任链的前提下减少失败重来；不能因为“约四成提交含发布词”，就认定四成产能被浪费。**

## Q3｜攒批有没有客观节奏建议？

### 统计支持“值得试”，不支持“每日一次最优”

63次 consensus 变更、28个发车日及其日分布可以复算；22/28＝**78.6%**的发车日有至少两次变更。

但63包含同一业务的 v1→v2 重部署。9月5日至少有“焦点诊断”和“存盘／领奖反馈”两组，不能直接将它们当作可互相合并的独立业务批次。〔M:25–26；`train-inventory.csv`；P:679–685、702–704〕

以下仅是在“当日所有变更均可合并、没有紧急豁免、无需追加回归”的理想假设下计算：

| 理想日上限 |              按原63次计数 |       仅扣除已知两次同业务重部署后 |
| ----- | -------------------: | -------------------: |
| 每日一趟  | 63→28，少35次，**55.6%** | 61→28，少33次，**54.1%** |
| 每日两趟  | 63→50，少13次，**20.6%** | 61→50，少11次，**18.0%** |

61不是已经完整去重的业务列车总数；扣除两次也不表示那两次重部署不必要。表中数字用于剥离返工与独立发车混计的影响，**都不是可兑现节省量**。

主材料的 `35×（云5分钟＋尾部16分钟）` 不能作为人时或同一条关键路径的节省：所谓16分钟从云 dispatch 开始，**已经包含云构建**；它也没有测量人是否始终在操作或等待。云资源占用和发布周转时间可以分别报告，不能相加包装成总收益。〔M:20、58、74；S:135–145〕

即使再假定每少一次 promotion 恰好少一次平均云构建，35次也只是约**173分钟云工作流挂钟**；去除已知重部署后的33次约为**163分钟**。仍未扣除豁免、合并回归和延期成本，也不是账单金额。

### 建议：每日两个常规候选窗口，紧急随发

**常规发布。**窗口与维护者、测试员共同可用时段对齐；没有 ready 候选就不发空车。只合并已具备现有发布资格、兼容且能解释回退边界的变更，不为等待未完成项目拖住已经 ready 的项目。窗口是发车机会，不是必须一天发两趟，也不是强迫不兼容变更合成一趟。

**紧急豁免。**正在造成存档／资产损坏、安全风险、核心流程不可用，或者存在早于下一窗口的既有明确现场诊断／验收时限，可以随发。仅“代码刚写完”“想同步源码与部署”不构成紧急；协议本来就允许 `source-ahead`。豁免只改变时机，不豁免正式门或既有授权。〔P:46、225–239〕

**批次边界。**共用一次发布，不等于共用一个未经区分的验收结论。各专项尚未完成的验收仍保持未完成。包内已有“K店批量领取＋多包开礼包”“SafeExit＋ArchiveTask”组合发布，因此“每趟只能一个业务”不是不可动协议；必须保留的是清晰的身份、范围和验收边界。〔P:721–727〕

建议把“非紧急 ready 项原则上不因攒批超过24小时”作为试行约束。**两窗口、24小时都是本次建议的政策参数，不是日志推导出的最优值。**附件没有共同值守时段、ready时刻、紧急标记或回归工作量，不能据此指定某个钟点，也不能承诺人验成本下降。

## Q4｜冻结前派生门的净收益是否为正？

### 先否定前提：没有已测得的“37%浪费主因分布”

原脚本把“云 run 的 source SHA 没有匹配正文中特定写法的 `release source`”直接当成“废弃源”。**未被正则识别，不是未部署。**〔S:80、91–99〕

对原来被列为“浪费”的29个 run，完成以下有明确锚点的保守核对：

| 原29个 run 中的类型          |     数量 |        工作流挂钟 | 正确解释                     |
| ---------------------- | -----: | -----------: | ------------------------ |
| 正文记载为最终采用，但正则漏识别       |      3 |      14.65分钟 | 不能计为废弃构建。                |
| 曾本机 promotion，随后同业务重部署 |      2 |       9.55分钟 | 是实际使用过的中间部署，不是“从未使用”。    |
| 本次逐条对应到明确未部署／退役记录的子集   |      6 |      30.47分钟 | 确有未用于部署的构建，但不全是可避免派生错误。  |
| 其余本次不作废弃认定             |     18 |      86.80分钟 | 保留未分类，不能静默并入浪费或成功采用。     |
| **合计**                 | **29** | **141.47分钟** | **这是原正则未匹配集合，不是已证浪费总额。** |

三个漏识别的最终采用 run 是：

`35672805431`——9月22日世界光照；`33255138023`——8月29日启动前门；`33220240979`——8月29日关卡转场复活。正文分别用了“最终冻结源”“release source commit”“该 commit 是最终 release source”等不同写法。〔P:943–951、757–760、769–772〕

两个中间本机 promotion 是 `33957634090` 和 `33945207841`。文档明确记载 v1 曾本机部署，只是没有分别推到 main，不能改写为 `NOT_DEPLOYED`。〔P:685、704〕

六个明确未部署记录对应 `34745615347`、`34702454701`、`34641981631`、`34455545619`、`34376555533`、`34097840213`。其中既有派生问题，也有样式门和测试修复。**6/78只是已核对的子集，不是把真实浪费率改定为7.7%。**〔P:371、387、416–420、470、510、595–604〕

反过来，世界光照v1、理发店早期request、地图撤退早期request等，都明确“未 dispatch 云构建”。它们可以贡献重冻结成本，却不能贡献旧云构建成本；只改policy又可能复用本地CAS，不能对称追加一次114.8秒本地构建。〔P:951、530、585、138〕

所以，**“37%云浪费”“派生占其一半”“B能把它降到18%”均缺少可接受的事件级依据。**全史词频也不能代替本窗口逐run归因。

### 原样B的净正收益不能确认；全提交hook不采纳

能明确识别为派生闭包问题的三个旧run如下：

| 事件              |        旧run |     挂钟 | 原文锚点      |
| --------------- | ----------: | -----: | --------- |
| 报告恢复的图标／材料／商店闭包 | 34641981631 | 5.05分钟 | P:416–420 |
| 任务播报的材料与商店来源    | 34455545619 | 5.10分钟 | P:470     |
| 三维选关合并上游后的头像来源  | 34376555533 | 5.32分钟 | P:510     |

合计**928秒＝15.47分钟**。这证明存在前移检查的候选机会，不证明未来一定重现，也不证明所提检查一定能全部拦住。

仅作预算算术：假定三个机会全部被消除、不同机器的挂钟暂按等权比较、暂不计实现维护及误报成本，则：

$$
\text{平均新增检查秒数}<\frac{928}{\text{实际检查次数}}
$$

放到534次普通提交上，收支点只有**1.74秒／次**；举例只检查63次发布入口，则是**14.73秒／次**。63是promotion代理数，不是实测冻结尝试数，实际入口次数还需按既有记录确定。

这些只是对三个已识别机会的条件性算术，**不是实际费用ROI，也不是整个B的总收益上限**。

“四域hash已秒级”不能证明完整派生检查也秒级；“字节幂等”表示重复运行不制造内容变化，不等于运行成本近零。检查耗时、误报、修复人时，以及当前是否还会重现这些历史问题，都没有实测。因此不能裁定原B净收益为正。〔M:81；P:42、76；`candidate-stage-seconds.json`〕

### 支持的是B′：少量检查点，复用现役语义

**冻结前：**把派生一致性和“本轮sourceRef配置已进入待冻结源码”纳入已有发布准备入口，不拦普通业务提交、方案文档或合法 `source-ahead`。派生器若只因时间戳制造diff，应按既有协议修门，不能要求维护者反复提交时间漂移。〔P:46、64–76〕

**dispatch前：**复用已有本地preflight优先顺序和source tag精确解析检查。冻结前只能检查配置准备，不能冒称已验证尚不存在的远端tag；创建tag后，仍须由现役helper核验tag→source commit。〔P:140、146〕

**最终证明：**production policy、双构建证明和原子promotion全部保留。前置PASS不替代最终receipt；不得为“更稳妥”给每次发布再加一遍无独立需求的完整 `promote -VerifyOnly`，协议已明确避免这种重复验证。〔P:199–215〕

B′若变成昂贵全量生成、维护第二套依赖清单、反复误拦合法开发，或无法通过少量既有发布记录显示减少了重复失败，就不升级成普遍硬门。

地图工作台“policy已40/40，后因测试等待问题再冻结”，以及9月5日“首次部署后上游又变化”，本来就不是一个派生自检能够消灭的全部问题。〔P:604、702〕

## Q5｜若全部暂不行动，什么阈值触发复审？

**D只能是有边界的预算选择，不能解释为“成本已证明可接受”。**以下是建议的管理阈值，不是附件估计出的自然临界点；触发意味着复审，不自动授权施工或减门。

| 观察项           | 建议复审阈值                                   | 复审方向                             |
| ------------- | ---------------------------------------- | -------------------------------- |
| 已确认可提前发现的同类失败 | 14天内至少2次；或最近20个云run中至少3个可明确归因此类失败的未采用构建  | 复审对应发布入口B′；未映射run保持未知，不能当作“无返工”。 |
| 纠偏后的仪式提交代理    | 连续两个完整ISO周均≥30%，且每周总提交≥30                | 拆分部署、首次准备、重复修正和业务误收，不直接减安全门。     |
| 真正可攒批的分开发车    | 14天内至少3天，出现至少两项发布前已ready、非紧急且回退边界兼容的独立发车 | 复审A′；排除同业务返工和现场止血。               |
| 周转时间异常        | 至少10条能一一对应的run→promotion记录，P75超过30分钟     | 定位队列、验证和编排变化，仍不把挂钟当作持续注意力。       |

按第一条，包内9月上中旬已出现可复核的派生失配重复事件。因此，无限期“全不动”不能以“没有具体问题”为理由；最多是暂缓投入，并接受复审。

建议D最长保留一个**14天观察周期**。以包内UTC+8日期2026年9月22日为起点，复审节点是**2026年10月6日**。

只复用现有request／worker／promotion阶段记录和issue关闭说明，不为本议题新建精细台账或逐次人工工时报表。阶段sidecar在协议中已有定义，但实际记录未附入本包，本次未读取。〔P:123；`issue-78-与Epic26-原文.md`:19〕

正式门的真实失败仍按原协议处置，不等待成本阈值，也不通过重跑或豁免把红灯洗掉。
