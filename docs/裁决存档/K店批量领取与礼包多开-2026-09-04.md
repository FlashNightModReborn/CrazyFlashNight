# 第三次裁决回执：K 店 `shopClaimBatch` 与礼包 `itemUseOpenMany`

**日期：2026-09-04**  
**裁决性质：方案与施工边界裁决；不直接实现代码**  
**前置状态：专项 A① durable finality 已入主线；R1 SaveManager 四层 API 正在按 19 步分片施工**

---

## 一、执行结论

### 1. 总裁决

1. **K 店 batch 定位为 legacy 存量待领取行的收尾能力，不是长期通用产品能力。** 因此只允许一个显式、有限、整批原子的命令；不建设通用 workflow、逐行状态机、per-child journal、自动重放器或新的恢复 UI。
2. **`shopClaimBatch` 条件采纳。** 请求仍采用 `batchOperationId + expectedPurchasedToken + 冻结行列表`；但行身份必须解释为 **`(purchasedToken, rowFingerprint)` 的快照纪元内 identity**，不是永久行 ID。
3. **partial failure 选 b：全或无。** 任一行无效、容量不足或无法交付，整批零写；成功时全部入包、全部删除、一个 terminal receipt、批尾一次 durable fence。a“有序前缀但整批崩溃回滚”与 c“best effort”均否决。
4. **礼包 `openMany` 同样选择全或无，并采纳方案 1；方案 2/F2 mini-WAL 继续否决。** 但不扩展既有 `itemUseOpen` 的可选 `count`，新增显式命令 `itemUseOpenMany`，避免改变单包协议与现有 receipt fingerprint。
5. **现有 unknown-response 链足够：** timeout、断线、畸形回包、`commit_pending` 继续走 C# `NeedsReconcile/reconcile_required` → Web `bulkQuery`；禁止 Web 自动重放写命令。batch 不新增恢复命令。
6. **K batch 的 terminal receipt 只复用 `RewardInboxService` 的“lookup → exact request compare → replay/conflict”模式，不共用 Reward receipt 存储。** K 使用独立、批域隔离、非 FIFO 淘汰的有限 receipt lane；Reward 的 `recordReceipt()` 当前会在 128 条后 `shift()`，不能拿来承诺 K 的严格 operation conflict。
7. **施工顺序采用交错路线：R1 步骤 6 → A②/`shopClaimBatch` 与 `openMany` → R1 步骤 9。** 业务 handler 始终调用领域 wrapper；不得因为 R1 已提供新 API 就让 batch/openMany 直接调用 `flushDurableNow()`。

### 2. 路线裁决表

| 项目 | 裁决 | 核心条件 / 理由 |
|---|---|---|
| A③ operationId、冻结列表 | **条件采纳** | 专用 K terminal receipt；lookup 必须先于 token/行校验；同 id 同完整请求返回首次结果，同 id 不同请求 `operation_conflict`；旧 token 重放只能经 Host 注入的 `replayOnly` 只读路径 |
| A④ unknown response | **采纳原链路** | 复用 `NeedsReconcile → bulkQuery`；不加恢复命令、不自动重放、不把“行已消失”推断成已成功 |
| A⑤-a 有序前缀 | **否决** | capacity 层面是行前缀，崩溃层面却仍是整批 `{0,K}`，同一命令出现两种“已提交前缀”定义；证明与 UX 成本不值 legacy 收尾投入 |
| A⑤-b 全或无 | **采纳** | 可复用 checkout 的 aggregate `require/acquire`；失败零写、成功一次 fence；durable unit 清晰为 `{0,K}` |

| A② 行指纹 | **条件采纳** | fingerprint 只在 token epoch 内有效；哈希只覆盖 canonical 五元组，`occurrenceOrdinal` 独立编码；64-bit 双 lane + 碰撞 fail-closed；不改五元组存档 schema |
| 单项 claim `expectedRowFingerprint` | **采纳，但目标协议中必须存在** | 不做永久 optional 双形状；同一 wire cut 中把单项 claim 升为显式 v1 exact shape，token 后再核对 index 行 fingerprint |
| B 方案 1 `openMany` | **条件采纳** | 新命令、K 包一次业务原子操作、K 次 roll/append、一个 receipt、一个 fence；总 occurrence 容量预检；失败 exact restore |
| B 方案 2 per-package durable prefix | **继续否决** | 要么仍 N 次全量存盘，要么复活 root journal/mini-WAL；没有新证据推翻第一次 F2 否决 |
| 排期 | **交错采纳** | R1 步骤 6 先清同文件 D1/D2；新业务在旧 wrapper 上完成；R1 步骤 9 最后一次性迁 wrapper 内部目标并跑联合门 |

## 二、证据基线与裁决边界

### 1. 已冻结事实

- A① 已把 K 店 checkout/claim 固定为“权威写 → `flushStrongSaveNow()` → durable 后才 `commit`；false/throw exact restore → `commit_pending`”，并冻结成功恰好一次 fence、失败一次失败尝试且零 receipt、stale/invalid 零 fence。见 `01-裁决输入/kshop-batch-adjudication-input-20260904.md:5-42`。
- legacy purchased 列表由 `_root.商城已购买物品` 五元组投影；当前唯一正常 mutation 是 claim 的 splice，checkout 已直接交付且不再增加待领取行。见同文 `:55-76`，以及 `商城系统_WebView.as:130-165,600-720`。
- C# 当前在发 Flash 命令前先绑定 Host authority；claim 的 token 不等或 index 不存在会在 Host 侧直接 `stale_state`，不会到 AS2。见 `ShopTask.cs:630-721`。这意味着 persisted operation receipt 若要支持旧 token 重放，必须增加受信的 replay-only 绑定模式，不能只在 AS2 里“先 lookup”。
- Web 当前 unknown write 会进入 `_startReconcile()` 并发 `bulkQuery`，对账后返回 `reconciled_unknown_result` 类失败，不自动重发原写。见 `kshop-runtime.js:893-939`。
- `RewardInboxService.recordReceipt()` 目前在 receipt 超过 128 条时 FIFO `shift()`；该行为只提供有界重放窗口。见 `RewardInboxService.as:302-315`。
- 第一次裁决已明确：显式 batch 可以把多个 child 重定义为一个业务命令并在批尾一次存盘；若既要减少全量存盘又保留每 child durable prefix，只剩 mini-WAL，而 F2 已否决。见 `第一次裁决回执-存盘风暴-gptpro.md.txt:180-226,250-259`。

### 2. 本轮不改变的契约

- A① 的 flush→commit 次序、exact restore、`commit_pending` fail-closed 与存盘次数不变量全部冻结。
- 不修改 `PlayerAssetTransaction.commit()` 对 `requestStrongSave()` 的既有语义。
- 不触碰 `商店系统_兼容.as` NPC 对照路径。
- 不修改 `_root.商城已购买物品` 五元组 schema。
- 不靠 debounce 合并写命令。
- 不把 AS2 业务 handler 改成直接调用 R1 新 SaveManager API。

## 三、逐题裁决

## 0. batch 的产品定位与复杂度上限

**裁决：legacy 存量行收尾能力。**

这不是新的 K 店长期购买模型。新 checkout 已经是最多 40 行的一次原子 batch，且直接交付；待领取列表只减不增。`shopClaimBatch` 的价值仅是让历史存档中剩余的 legacy 行尽快收敛，并消除“逐项 claim = 逐项全量存盘”的尾部放大。

因此复杂度上限冻结为：

- 一个显式命令，协议最大 40 行；UI 只在可选行数 ≥2 时展示批量操作，单行仍走单项 claim。
- 一个整批 durable cut；不提供行级 durable prefix。
- 一个小型 terminal receipt lane；不是通用 operation framework。
- 一个现有 `bulkQuery` 对账面；不增加 status/query/retry command。
- 无 streaming、无进度回包、无 child receipt、无服务端自动拆批。

若未来产品重新引入“购买后待领取”并让该列表持续增长，应另开长期产品 ADR；本轮实现不得自动升级为长期基础设施。

## 1. A③：operationId、冻结列表与 exact result 证明

### 1.1 协议成立，但必须增加 Host `replayOnly` 模式

草案：

```json
{
  "v": 1,
  "batchOperationId": "kcb.172...",
  "expectedPurchasedToken": "shop...",
  "rows": ["kpr1.0123456789abcdef.0", "kpr1.aabbccddeeff0011.0"]
}
```

**条件采纳。** 约束如下：

- `v` 必须严格等于 `1`。
- `batchOperationId`：`^[A-Za-z0-9._-]{1,96}$`；与 `callId` 分离。
- `expectedPurchasedToken` 沿用 K shop token 词法与长度门。
- `rows`：1..40；每项必须是合法 rowFingerprint；不得重复。
- 请求顺序必须等于当前 purchased 快照中的严格递增顺序；Host/AS2 均不得静默排序。顺序属于 operation identity。
- 行 selector 的完整身份是 `(expectedPurchasedToken, rowFingerprint)`；单独 fingerprint 不能跨 token epoch 使用。

C# 增加 `BatchBindMode = Fresh | ReplayOnly`：

- **Fresh：** token 等于 Host 当前 token，所有 fingerprint 在当前 Host view 中唯一命中，且顺序严格递增；冻结 raw/view/token 后下发。
- **ReplayOnly：** Host 已有当前 authority，但请求 token/rows 无法 fresh bind。Host 仍可把请求发给 AS2，不过必须额外注入 `replayOnly:true`；该字段不能从 Web 输入透传。
- Host 没有当前 authority 时不下发写，先要求现有 bulk reconcile。

Host → AS2 exact shape：

```json
{
  "task": "cmd",
  "action": "shopClaimBatch",
  "callId": 123,
  "v": 1,
  "batchOperationId": "kcb.172...",
  "expectedPurchasedToken": "shop...",
  "rows": ["kpr1.0123456789abcdef.0", "kpr1.aabbccddeeff0011.0"],
  "replayOnly": false
}
```

`replayOnly:true` 时，AS2 **只能 lookup receipt 并返回 replay/conflict/stale；不得 rotate token、不得 acquire、不得 splice、不得标脏、不得 fence。** 仅靠 C# 在响应后拒绝异常 fresh 回包不够，因为资产写可能已经发生。

### 1.2 K batch receipt：复用模式，不共用 Reward 存储

推荐持久化形状：

```text
_root._saveExt.kshopClaimBatch = {
    v: 1,
    receipts: [
        {
            operationId: <batchOperationId>,
            kind: "claimBatch",
            status: "committed",
            policy: "atomic",
            request: {
                v: 1,
                expectedPurchasedToken: <token>,
                rows: [<ordered rowFingerprint>...]
            },
            committedPurchasedToken: <token after this batch>
        }
    ]
}
```

规则：

1. lookup 必须在 current token、current rows 校验之前。
2. 同 operationId 且 `kind/policy/v/token/rows 顺序` 全部 exact 相同：返回首次 immutable result，`replayed:true`，不存盘。
3. 同 operationId 任何字段不同：`operation_conflict`，不存盘。
4. receipt 在资产/list mutation 完成后、durable fence 之前写入同一全量快照；fence 失败必须连同资产、purchased list、token、dirty 一起 exact restore。
5. lane 上限建议 `128`，**不做 FIFO 淘汰**。满时新 batch 返回 `batch_receipt_ledger_full`，零写；单项 claim 仍可用。这保证每个已接受 batch 的 operation conflict 语义不会因淘汰静默失效。
6. future/malformed lane 只 quarantine batch 能力；不得连带阻断 K bulk、checkout、单项 claim。

这不是对 F2 的翻案：receipt 与资产/list 一起进入同一个全量 snapshot，只记录整批 terminal operation；它既不能恢复半批，也没有独立文件、CRC、append-only 日志、compaction 或双权威。

### 1.3 AS2 fresh 执行状态机

顺序必须冻结为：

1. exact envelope、operationId 与 receipt lane 校验；lookup prior。
2. `replayOnly` 无 prior → `stale_state`，立即返回。
3. fresh token 校验；构造 canonical purchased snapshot；解析全部 fingerprint，拒绝 unknown/duplicate/乱序/collision。
4. 对全部选中行构造 aggregate acquire plan；用 `ItemUtil.require(...)` 做纯预检。任一容量不足整批零写，且 **token 不轮换**。
5. capture：玩家资产、原 purchased 数组、原 token、K receipt lane、dirty 状态；开始 PAT transaction。
6. `markDirtyRequired()`；在第一个可能 mutation 之前 rotate token。
7. 一次 aggregate `ItemUtil.acquire(...)`；失败时 exact restore。
8. 按冻结 pre-index **降序** splice 所有行；响应顺序仍按请求顺序。
9. 记录一个 batch receipt。
10. `PlayerAssetTransaction.flushStrongSaveNow()` 恰好一次。
11. false/throw：恢复 capture，丢弃未发布 PAT frame，返回 `commit_pending`。
12. true：操作已 durable；随后 `PAT.commit()`。**进入 durable 后不得再进入“恢复 pre-state”的 catch。** 后置投影、埋点、回包失败只能走 unknown/reconcile。

### 1.4 成功与失败响应精确形状

Flash → Host fresh/replay 成功：

```json
{
  "task": "shop_response",
  "callId": 123,
  "success": true,
  "v": 1,
  "batchOperationId": "kcb.172...",
  "policy": "atomic",
  "replayed": false,
  "committedPurchasedToken": "shop...",
  "resultRows": [
    {"rowFingerprint": "kpr1....0", "status": "claimed"},
    {"rowFingerprint": "kpr1....0", "status": "claimed"}
  ],
  "purchased": [["id", "item", "type", 10, 1]],
  "purchasedView": [
    {
      "purchasedIdx": 0,
      "item": "...",
      "displayname": "...",
      "icon": "...",
      "quantity": 1,
      "rowFingerprint": "kpr1....0"
    }
  ],
  "purchasedToken": "shop-current...",
  "catalog": []
}
```

约束：

- fresh：`replayed=false`；`committedPurchasedToken == purchasedToken`；并且不等于请求 token。
- replay：`replayed=true`；`committedPurchasedToken` 来自首次 receipt；`purchasedToken` 是当前 authority token，二者允许不同。
- `resultRows` 长度、顺序、fingerprint 必须与请求 exact 相同；atomic 成功唯一合法 status 是 `claimed`，不允许 `skipped/failed/pending`。
- Host → Web 删除 raw `purchased`，把 `purchasedView` 作为业务字段 `purchased` 输出；raw 五元组绝不进入 Web。

AS2 确定性失败继续使用当前 K failure 基形：

```json
{
  "task": "shop_response",
  "callId": 123,
  "success": false,
  "error": "inventory_full",
  "purchasedToken": "shop-current..."
}
```

batch 的 definitive 零写错误至少包括：

```text
unsupported_version
invalid_payload
invalid_operation_id
stale_state
item_not_found
unknown_row
row_duplicate
row_order_invalid
purchased_identity_collision
inventory_full
destination_full
acquire_failed              # 仅 exact restore 成功后
operation_conflict
batch_receipt_ledger_full
```

`commit_pending`、timeout、disconnect、畸形 success、fresh/replay mode 不匹配、durable 后投影失败均为 ambiguous，进入现有 reconcile。

### 1.5 sanitizer 的证明强度

#### Fresh 模式：C# 必须证明

1. success exact keys；`v=1`、operationId/policy/resultRows exact；`replayed=false`。
2. 请求 token 与冻结 Host token 相同；终态 token 改变，且 `committedPurchasedToken == purchasedToken`。
3. 用冻结 raw snapshot 解析请求 fingerprint → pre-index；删除这些 raw 行得到 expected raw 终态。
4. 用冻结 view 删除同 fingerprint；重新编号 `purchasedIdx`；同 tuple digest 组重新计算 `occurrenceOrdinal`；逐字段比较 expected view。
5. AS2 返回 raw/view 必须彼此对应，且 raw expected 与返回 raw `JToken.DeepEquals`。
6. catalog 做 exact schema 与静态身份验证；静态列/order 必须与旧 catalog 一致。`maxQuantity`、balance/procurement 等依赖本次资产变化的动态列只能做类型、范围与局部一致性验证，不能伪称可由 Web 逐字段重建。
7. 全部通过后才更新 Host authority。

#### ReplayOnly 模式：C# 必须证明

1. `replayed=true`；operationId/resultRows/policy exact。
2. 返回的当前 purchased raw/view/token 与 Host 在下发 replay-only 前冻结的当前 authority **完全不变**；这是“该请求没有再次写”的状态证明。
3. `committedPurchasedToken` 合法，但允许不同于当前 token。
4. 若 AS2 在 replay-only 下返回 `replayed=false`、token/list 变化或新 durable result，一律视为畸形 write response，进入 reconcile。

#### Web 必须独立证明

- fresh：从 Web 自己冻结的 authority view 删除请求 fingerprints、重排 index/ordinal，与 C# 输出逐字段比较。
- replay：当前 view/token 必须与发起 replay 前 Web authority 相同；immutable resultRows 只用于展示首次结果。
- Web 不重新计算 tuple hash，只解析 fingerprint 词法、digest base 与 ordinal。

**结论：该证明强度足以证明一个普通整批 terminal operation 的 exact result；它不等同于第一次 Reward root 的 per-child durable-prefix 证明。** 本命令 durable state 只有 `{0,K}`，没有 `1..K-1` 的合法 crash-recovery 状态。

## 2. A④：unknown response 与恢复政策

**裁决：现有链路足够，不增加恢复面。**

- timeout / socket 断开 / send failure / response sanitizer 失败 / `commit_pending`：C# 进入 `NeedsReconcile`，写闸关闭。
- Web 对 origin=`claimBatch` 调现有 `bulkQuery`；成功 authority snapshot 才解除写闸。
- 对账完成后，Web 返回“结果未知但状态已同步”，不自动把旧写命令重发。
- 用户若当前快照仍有目标行，可重新选择并生成 **新的** batchOperationId；若行已消失，只更新 UI，不依据“缺行”自行宣告旧批次成功。
- same-ID replay 是协议层 duplicate/诊断能力，不是 Web 默认恢复动作；需要发生时由 Host `ReplayOnly` 保证只读。

禁止新增：

- `shopClaimBatchStatus` / `shopClaimBatchRetry`；
- Web timeout 后自动重发；
- 对账后按行缺失推断 success；
- 把 `commit_pending` 加入 definitive failure 集。

## 3. A⑤：partial failure 拍板

### 3.1 采纳 b：全或无

K batch 的确定性结果只有：

```text
全批可交付：全部 acquire + 全部 splice + 1 receipt + 1 fence
任一行不可交付：0 acquire + 0 splice + 0 receipt + 0 fence
```

理由：

1. checkout 已有 aggregate capacity 预检与一次 `ItemUtil.acquire()` 的可复用骨架（`商城系统_WebView.as:311-328,356-407,410-468`）。
2. a 的“首个 capacity 失败前成功若干行”并不是 durable prefix：在批尾 fence 之前进程崩溃，整个前缀仍回到 0。它会让“业务返回的行前缀”与“崩溃恢复的 durable 前缀”含义冲突。
3. 全或无使 operation receipt、response sanitizer、unknown 对账和用户重试都只处理 `{0,K}`。
4. 满仓一件卡住整批是可接受的 legacy UX 代价：UI 显示阻塞原因，用户可缩小选择或用单项 claim。

### 3.2 openMany 必须采用同一原子哲学

“同一个哲学选择”指：**一个显式批命令 = 一个 durable operation = 一个 terminal receipt = 一个批尾 fence**。它不要求 K 与 Reward 共用 receipt store、错误码或执行类。

## 4. A②：行指纹 identity

### 4.1 采纳范围

`fingerprint = H(id,item,type,price,qty,occurrenceOrdinal)` 原式需要修正：

- 哈希主体只包含 canonical 五元组 `(id,item,type,price,qty)`。
- `occurrenceOrdinal` 独立放在 fingerprint 尾部，不参与 digest。
- 完整 identity 是 `(purchasedToken,rowFingerprint)`。

推荐格式：

```text
rowFingerprint = "kpr1." + tupleDigest16Hex + "." + occurrenceOrdinalDecimal
regex          = ^kpr1\.[0-9a-f]{16}\.(0|[1-9][0-9]{0,3})$
```

`occurrenceOrdinal` 为同一 canonical 五元组在当前快照中的 0-based 出现序号。删除较早重复行后，幸存重复行的 ordinal 可在新 token epoch 中重排；这是预期行为，不是永久 row ID 漂移。

### 4.2 哈希算法与长度

| 方案 | 裁决 | 说明 |
|---|---|---|
| 单 FNV-1a32 / CRC32 | **否决** | 10,000 行的 birthday collision 量级约 1.16%，即使最终 fail-closed，也会制造可见兼容故障 |
| 双 32-bit lane，输出 64-bit/16 hex | **采纳** | 词法短、AS2 成本低；10,000 行随机碰撞量级约 `2.7e-12`；再配合同快照 collision guard，碰撞只能拒绝服务，不能误领 |
| SHA-256 全长 | **本专项否决** | 若仓库已有完全匹配的实现可复用则可截断 96/128 bit；否则为 legacy 收尾引入重型 AS2 hash 实现不合投入上限 |

推荐双 lane：

- canonical tuple 采用固定字段顺序、类型标签、UTF-16 code-unit 长度前缀；不使用裸分隔符拼接。
- `price` 先走现有 canonical Number；拒绝 NaN/±Infinity，`-0` 归一为 `0`；`qty` 为十进制正整数。
- lane A = FNV-1a32(`"A\0" + canonical`)；lane B = FNV-1a32(`"B\0" + canonical`)。
- 对每个 UTF-16 code unit 依次喂 low byte、high byte。
- AS2 的 `* 16777619` 不得依赖超出 53-bit 精确域的普通乘法；32-bit lane 使用 `h + (h<<1) + (h<<4) + (h<<7) + (h<<8) + (h<<24)` 后截断到 32 bit，并统一输出 unsigned lowercase 8-hex。
- 实现前先检索仓库已有 FNV/hex utility；只有字节序、Number 归一和 unsigned 语义完全相同时才复用。

### 4.3 collision guard

AS2 每次构造 purchased snapshot 时维护：

```text
digest -> canonicalTupleString
```

同 digest 再遇到相同 tuple，只增加 ordinal；同 digest 遇到不同 tuple，整个 purchased identity 投影返回 `purchased_identity_collision`，零写。

Host 还应交叉验证：

- 相同 raw 五元组必须具有相同 digest base；
- 相同 digest base 不得对应不同 raw 五元组；
- ordinal 必须从 0 连续递增；
- view 与 raw 数量/order 一致。

这样 hash collision 只导致 fail-closed，不会把 A 行解释成 B 行。

### 4.4 投影列

canonical raw 仍保持五元组：

```text
[id, item, type, price, qty]
```

`purchasedView` exact keys 改为：

```json
{
  "purchasedIdx": 0,
  "item": "...",
  "displayname": "...",
  "icon": "...",
  "quantity": 1,
  "rowFingerprint": "kpr1.0123456789abcdef.0"
}
```

### 4.5 单项 claim

值得随 batch 一次完成，但目标协议不保留永久 optional：

```json
{
  "v": 1,
  "purchasedIdx": 3,
  "expectedPurchasedToken": "shop...",
  "expectedRowFingerprint": "kpr1....0"
}
```

AS2 校验顺序：token → build canonical snapshot → index 范围 → 该 index 的 fingerprint exact echo → mutation。fingerprint 不符返回 `stale_state`，零写。

若发布流程无法保证 Web/Host/AS2 同 bundle 切换，可保留一个明确有删除日期的 legacy 无 v 分支；不能在 v1 内把 `expectedRowFingerprint` 永久设为 optional，否则 exactKeys 与证明长期存在两套语义。

## 5. 专项 B：`openMany` 最终确认

### 5.1 方案选择

**确认方案 1，否决方案 2。** 但协议采用新 action：

```text
itemUseOpen      —— 原单包协议，保持不变
itemUseOpenMany  —— 新的多包原子协议
```

不在旧 `itemUseOpen` 上加 optional `count`，原因：

- 当前 open v1 是 exact envelope，receipt `kind:"open"` 且 fingerprint 仅覆盖 source；直接加 count 容易形成同 operationId 不同 count 的兼容歧义。
- 新命令可以独立冻结 count 范围、response shape、receipt kind 与测试矩阵；回滚时可只关闭新 action。

### 5.2 请求 exact shape

```json
{
  "task": "cmd",
  "action": "itemUseOpenMany",
  "callId": 123,
  "v": 1,
  "operationId": "openmany.172...",
  "panelInstanceId": "...",
  "sessionGeneration": 7,
  "source": {
    "physicalSlot": 3,
    "slotLease": "...",
    "itemName": "礼包名",
    "backpackVersion": 42
  },
  "count": 2
}
```

- exact keys；`count` 为整数 `2..64`。`1` 继续走 `itemUseOpen`。
- lookup prior receipt 必须先于 current source 校验。
- 同 operationId、同 kind、同 exact source、同 count：replay；任一不同：`operation_conflict`。
- receipt 中直接存 exact normalized request object，不复用现有 `sourceFingerprint()` 的裸 `|` 拼接；当前 source 字符串未禁止 `|`，该拼接不适合新协议作为冲突证明。

### 5.3 fresh 执行顺序

1. exact envelope/context；lookup receipt。
2. validate source，且礼包当前数量 ≥K。
3. normalize recipe 一次。
4. 按 `ordinal=0..K-1` 连续调用 `rollRecipe()`；保存 K 份 ordered rolled entries。
5. 汇总 `totalOccurrences = Σ rolled[i].entries.length`；用 `canAppendOccurrenceCount(totalOccurrences)` 一次预检。容量按 occurrence 数，不按奖励数量求和。
6. capture：完整背包、整个 Reward feature、dirty；begin PAT。
7. 标脏；背包一次扣 K，并验证 before-after exact 等于 K；PAT 记录一笔数量 K 的 loss。
8. 按 ordinal 调 `appendRewardBatch()` K 次；即使某包 0 命中，也保留返回的 batchId/entryCount 到 operation receipt。
9. 记录一个 `kind:"openMany"` receipt。
10. `ItemUseService.flushSave()` 恰好一次。
11. false/throw：恢复 bag + whole Reward feature + dirty；丢弃 PAT frame；`commit_pending`。
12. true：PAT commit；后置 projection/response 失败只走 query/reconcile，不做 pre-state rollback。

### 5.4 receipt exact shape

```text
{
    operationId: <id>,
    kind: "openMany",
    status: "committed",
    request: {
        v: 1,
        source: {
            physicalSlot: ...,
            slotLease: ...,
            itemName: ...,
            backpackVersion: ...
        },
        count: K
    },
    consumed: K,
    remaining: <source count at commit>,
    packages: [
        {ordinal: 0, batchId: "open.41", entryCount: 3},
        ...
    ]
}
```

- `packages.length == K`，ordinal 必须连续 0..K-1。
- 不创建 K 个 child receipt。
- current inbox summary / reward authority 不写进 immutable receipt；响应时从当前 Reward authority 重建。


`executeQuery/projectReceipt` 必须能投影 `openMany` 的 `requestedCount/consumed/remaining/packages`。

### 5.6 success 证明与 unknown recovery

Host/Web 对 fresh success 至少证明：

1. response exact keys，`command="openMany"`、operationId/context 与请求 exact，`replayed=false`。
2. `requestedCount == consumed == K`；若 Host 已冻结 source authority，则 `remaining == source quantity before - K`。
3. `packages.length == K`，ordinal 连续 0..K-1，batchId 非空且互不重复，entryCount 为 0..64 的整数；packages 顺序不得重排。
4. inboxSummary/rewardAuthority 通过现有 authority sanitizer 后才应用。若 Host 已冻结 pre-inbox summary，则 fresh 终态还应满足：`remainingCount` 增量等于 `Σ entryCount`，`authorityRevision` 增量等于非空 package 数。
5. 当前 `RewardInboxService.materializeAuthority()` 只暴露 Loot authority 元数据，不暴露 batchId/openOperationId/entry manifest；因此 Host/Web **不能伪称**从 `rewardAuthority` 独立证明每个 package descriptor。该对应关系由 AS2 领域测试直接检查 `_saveExt.rewardInbox.batches + receipts`，并由真实 save-image restart 复验。若未来要求跨层独立证明随机 manifest，必须另加只读 raw proof 投影，不能用现有 `rewardAuthority` 冒充。

对 replay success：

- `replayed=true`，immutable `requestedCount/consumed/remaining/packages` 必须与 persisted receipt exact 相同。
- 不要求旧 batch 仍存在于 current rewardAuthority；它可能已经被正常 claim/prune。当前 summary/authority 是恢复时的实时状态，不是首次 success 的历史快照。

unknown response 不重发 `openMany`：

- 复用现有 `itemUseQuery {operationId}`/receipt lookup 作为读恢复面（`ItemUseService.as:222-234`）。
- query 找到 receipt：按 committed result 收束；query 未找到：刷新背包与 inbox authority 后，由用户生成新 operationId 重试。
- `commit_pending` 已 exact restore 时 query 应未找到 receipt；durable 后回包丢失时 query 必须找到同 packages。

### 5.7 RNG 与幂等边界必须如实冻结

- 给定相同初始 RNG 状态且中间没有其他 draw，openMany 内部消耗顺序等于连续 K 次调用现有 `rollRecipe()`；不得重新排序、合并或预采样。
- 它**不保证**与玩家跨帧点击 K 次得到相同结果，因为两条命令之间可能有其他系统消耗全局 RNG。
- 现有 AS2 `random()` 无可恢复状态。capacity rejection、append fault、flush failure 后虽然资产/Reward feature exact restore，RNG 已推进；同 operationId 在 `commit_pending` 后重试可能重新 roll。保证的是“不重复扣礼包、不重复 durable batch”，不是“失败重试必得同一随机结果”。若要冻结随机结果，需要可持久 pending intent/RNG state，属于另一个持久化设计，不在本轮偷渡。
- `RewardInboxService` receipt 当前 FIFO 128。故 openMany 与现有 open 一样，能诚实承诺的是 **保留窗口内 exact replay/conflict**；窗口外仍由 stale source/version fail-closed，但不能宣称永久返回首次结果。若产品要求 lifetime operationId ledger，需单独治理 Reward receipt retention，不能把 1–1.5 天估时继续沿用。

### 5.8 为什么不推翻 F2

openMany 只承认两个 durable 状态：0 包或 K 包。K 次 `appendRewardBatch()` 是同一内存事务内的 staged mutation，不是 K 个已确认 child operation。没有 root journal、mini-WAL、每包 CRC/sequence、snapshot/WAL compaction 或启动恢复 pass，因此第一次 F2 否决原样有效。

## 7. 回归门：防协议落地后语义被偷换

## 7.1 两层计数定义

### 领域层

- K：`flushStrongSaveNow` 入口次数、PAT committed receipt 数、K batch persistent receipt 数、purchased/token/资产快照差量。
- ItemUse：`flushSave` 入口次数、Reward operation receipt 数、bag/Reward feature/dirty 差量。

### SaveManager 层（R1 步骤 9 后）

沿用第二次裁决的物理八桶与 API 桶：

```text
API ingress: flushDurableNow
origin:      fullFromDurable
physical:    doSaveAll / packGameState / flushAttempt(full)
outcome:     success / pending / false / throw
shadow:      shadowDispatch
```

### 计数断言

| 场景 | 领域 fence | `flushDurableNow` ingress | full save | terminal receipt | 状态 |
|---|---:|---:|---:|---:|---|
| fresh success | 1 | 1 | 恰好 1 | 恰好 1 | durable 新状态 |
| SharedObject false/pending | 1 | 1 | 恰好 1 次物理失败尝试 | 0（restore 后） | exact pre-state |
| pack/precommit throw | 1 | 1 | 按 fault cut 可能尚未到 `flushAttempt`; 但不得超过 1 | 0 | exact pre-state |
| invalid/stale/capacity/conflict | 0 | 0 | 0 | 0 | token 与资产不变 |
| operation replay | 0 | 0 | 0 | 不新增 | authority 不变 |

不得把“领域调用了一次 fence”与“底层 SharedObject 已发生一次物理 flushAttempt”混成一个计数。precommit throw 时前者为 1，后者可能为 0；门应按注入 cut 精确断言。

若 D2 的 `requestSave(shop.cart_edit)` 已 pending，随后 K strict batch 到来：

```text
requestSave ingress       == 1（或 N）
flushDurableNow ingress   == 1
requestAbsorbedByFence    == 1
总 doSaveAll/packGameState == 1
推进 timer 后额外 full save == 0
```

## 7.2 K 店矩阵

至少冻结：

1. 单项 claim fresh success：1 fence；fingerprint mismatch：0。
2. `claimBatch` K=1/2/40：每次 fresh success 均恰好 1 fence、1 K receipt、1 PAT published receipt。
3. invalid version/id/token、unknown/duplicate/乱序 fingerprint、identity collision、receipt lane full：0 fence、0 receipt、token 不变。
4. 任一行容量不足：整批零资产差量、零 splice、零 token rotation、零 fence。
5. aggregate acquire 返回 false：restore 后 `acquire_failed` definitive；若 restore 不完整则 ambiguous，不得回 definitive。
6. 在 acquire 后、每个 splice cut、receipt append 后注入异常：资产/list/token/ledger/dirty exact restore，0 fence（若 cut 在 fence 前）。
7. fence false/pending/throw：领域 fence 1；K receipt 与 PAT receipt 0；资产/list/token/ledger/dirty exact restore；返回 `commit_pending`。
8. fence 成功后、PAT commit/投影/发送前注入异常：**不得 restore**；重启后新状态与 receipt 可见；C#/Web 走 reconcile。
9. same operationId + exact request：`replayed=true`、0 fence、0 token rotation；same id + token/rows/order 任一变化：`operation_conflict`、0 fence。
10. old token same-id 请求：Host 只能下发 `replayOnly=true`；AS2 无 receipt 时 `stale_state`，有 receipt 时 replay；两种均 0 write。
11. replay-only 若返回 fresh 或改变 current purchased/token：C# sanitizer 拒绝并进入 reconcile。
12. 全同重复五元组：ordinal 0..n-1；删除中间/首个后新 epoch 正确重排；Host/Web 期望终态一致。
13. success 回包丢失 → 真实进程重启 → bulkQuery：只出现 durable `{0,K}`；不得出现部分 list 删除或部分资产。
14. K receipt lane future/malformed：只禁 batch，不破坏 checkout/单项 claim/bulkQuery。

## 7.3 open/openMany 矩阵

1. 既有 `open` 仍恰好 1 fence，现有用例不变。
2. `openMany` K=2、边界 K=64：成功均 1 fence、1 operation receipt、K package descriptors、背包恰扣 K。
3. 同 operationId exact request replay：0 fence、0扣包、返回同 packages；同 id 不同 count/source/kind：conflict 0 fence。
4. count 0/1/65、source 数量<K、stale source、unsupported item、invalid recipe、aggregate occurrence 超64：0 fence、0扣包、0 receipt。
5. fixed/independent/chooseOne 使用固定 test RNG：K 次 roll 的 draw 顺序、package ordinal、batchId/entryCount 均固定。
6. 某包 0 命中：仍有 package descriptor，Reward pending batch 可不存在；sequence 与 batchId 行为锁定。
7. 在第 i 次 append、recordReceipt、fence 前注入异常：bag/whole Reward feature/dirty exact restore；PAT frame 清空。
8. fence false/pending/throw：领域 attempt 1、receipt 0、背包不扣、Reward feature exact pre-state；重试不翻倍扣包。测试必须允许重新 roll，不得错误断言结果完全相同。
9. fence success 后 response 丢失/进程重启：query 同 operationId 返回同 packages；Reward batches 不重复。
10. Reward receipt 第 128/129 条边界：测试并文档化 retained-window 语义；不得声称第 1 条在被 FIFO 淘汰后仍 exact replay。

## 7.4 协议 exact 门

- JS `normalizeRequest`、C# `TryNormalizePayload`、AS2 `onlyKeys/validateEnvelope` 对每个新命令都做 missing/extra/wrong type/NaN/Infinity/oversize fuzz。
- K raw 五元组只存在 Flash→Host，不得进入 Host→Web。
- C#/Web success sanitizer 必须 exact keys；任何 `partial/skipped` status、缺 resultRows、token 关系不符、fresh/replay mode 不符都拒绝。
- 静态扫描：
  - 新业务 handler 内不得出现 `_root.强制存盘`；
  - 不得出现 `requestSave`；
  - 不得出现直接 `flushDurableNow`；
  - 每个命令只允许一个领域 fence 调用点；
  - receipt 写在 fence 前，PAT commit 写在 fence true 后；
  - durable 后的 catch 不得调用 pre-state restore。
- AS2 `.as` UTF-8 BOM；新类进入 asLoader 注入层。
- Flash CS6 fresh trace/Output Panel、Compiler 0/0；不能以 marker 替代。
- 真实 save-image restart，不得用同进程 reset 冒充 crash recovery。
- 保留现有基线：KShop 37/37、PAT 117/117、map-loot 648/648、Web 33/33 + Edge 155/155，并在其上增加新门；不能只改数字门槛不加 fault-cut 语义断言。

## 十、最终裁决摘要

- **K batch：做，但只做 legacy 原子收尾。** `shopClaimBatch` 的 durable unit 是 `{0,K}`；一个 receipt、一个 fence；使用 token-epoch fingerprint；Host stale replay 必须 `replayOnly`。
- **K receipt：专用、有限、非淘汰；满则 batch fail-closed，单项 claim 兜底。** 不与 Reward 共用故障域。
- **unknown：继续 bulkQuery 对账；禁止自动重放。**
- **partial：K 与 openMany 均全或无。**
- **openMany：新增显式 `itemUseOpenMany`，K 次 roll/append、一次扣 K、一个 receipt、一次 fence。** 不复活 F2；不承诺失败重试随机结果相同。
- **R1：步骤 6 先，业务专项居中，步骤 9 后。** 新业务只依赖领域 wrapper，SaveManager API 迁移保持局部可回滚。

本裁决没有新理由推翻第一次对 root journal/mini-WAL 的否决，也没有授权削弱 A① 已冻结的 durable finality。
