## 1. 结论与专项使命

后续仍有大量 AS2 UI 待迁。继续让每个领域分别实现 Web session、C# pending/timeout/callId、AS2 revision/token、断线清理和未知写对账，会重复制造物资箱已经暴露的组合度爆炸。

P0-F 只消除其中 **transport lifecycle** 这一维的重复组合；领域因果关系、业务写状态和 reconcile 政策仍由各领域承担。F3 新页面必须用显式终态门证明这些领域状态可收敛，但本专项不把它们抽成公共状态机。

P0 拆为：

- **P0-S 稳定性止损**：冻结物资箱协议继续泛化，完成 `force_flush`、安全退出和 shadow/SOL 窗口加固。
- **P0-F 迁移基座收敛**：只收口已被多个真实消费者证明重复的跨层机械代码，并让一个后续写面板原生复用。

P0-F 的唯一业务价值指标是：

> 新增一个持久写 Panel 时，领域代码只实现命令映射、payload/回包校验、业务规则和领域 reconcile，不再自建 pending、timer、callId mux、迟到回包和 transport cleanup。

本文同时是本轮高强度跨层开发的收尾边界：先把已经取得的契约、runtime、事务和测试成果变成可维护接缝，清点仍在场的临时路径，再开始下一轮高风险纵切；不以“趁热再迁一个页面”扩大范围。

纯展示/纯本地页面继续沿用现有 `Panels`，不进入本专项。除 F3 试点外，本开发机新的持久状态或经济写页面持续暂停到 F4 写入 terminal 记录；确需先行时必须登记 §10.1 具名例外、复用缺口和未来删除路径。若最终不是 `Closed`，F4 必须同轮写入替代治理入口，不能静默恢复批量施工。

## 3. 已有基建与真实重复

### 3.1 直接复用，不重建

- Web：`Panels`、lazy registry、`panel-runtime.js`、`workbench-lifecycle.js` 及既有 focus/primitives/components；`inventory-runtime.js / InventoryCoordinator` 继续作为库存领域共享协调器。
- Host：`MessageRouter`、`TaskRegistry`、`PanelHostController`、`PanelBridge`。
- AS2：`PanelRequestEnvelope`、`ArrayInventory.mutationRevision`、`InventoryPanelService` 的稳定 snapshot/slot lease/原子 transfer。
- 领域事务：NPC/KShop/Crafting/Equipment Tuning 已有 preview → opaque token → commit。
- 存档：`SolResolver`、`SaveMigrator`、`ArchiveTask`、修复字典和 `cf7-save-repair`。
- 验证：契约 validator/变异测试、Web harness、Launcher xUnit、AS2 TestLoader、isolated candidate 和 runtime v2 promotion。

`PanelBridge` 已把多份安全 envelope 构造收口为一个 helper，是本专项应遵循的模式：先确认重复，再提取最小机械原语。

### 3.2 当前值得收口的重复

本基线静态扫描中，`launcher/src/Tasks` 有 25 个 `*Task.cs`；15 个持有 `_pending`，15 个自行持有 `Timer`，13 个暴露 `ClearPending()`，17 个处理 timeout。数字只是当前快照，不是设计目标。

复核口径：

```powershell
$taskFiles = Get-ChildItem launcher/src/Tasks -Filter '*Task.cs' -File
$taskFiles.Count
rg -l --glob '*Task.cs' '_pending' launcher/src/Tasks | Measure-Object -Line
rg -l --glob '*Task.cs' '\bTimer\b' launcher/src/Tasks | Measure-Object -Line
rg -l --glob '*Task.cs' 'ClearPending\(' launcher/src/Tasks | Measure-Object -Line
rg -li --glob '*Task.cs' 'timeout' launcher/src/Tasks | Measure-Object -Line
```

`NpcShopTask` 与 `CraftingTask` 已重复实现：

- backend callId 分配；
- pending/timer；
- active/recent callId；
- timeout、发送失败和迟到响应；
- 断线清理及 Web 回包投递。

两者的业务写门并不相同：NPCShop、Crafting、Equipment Tuning、Skill 对“哪一份 snapshot/preview 能解除未知态”有不同规则。因此 P0-F 只抽 transport lifecycle，不抽通用业务 `writeState/reconcile` 状态机。

### 3.3 明确不得泛化

- Loot 的 suspended anchor、`openAttemptSeq`、socket generation、causal proof、journal、暂停和视觉关闭；
- `InventoryCoordinator` 的库存 lease、窗口刷新和外部写协调；
- inventory slot lease、交易 token、trainer capability、execution lease 之间的业务语义；
- 价格、容量、任务、装备、伙伴和宠物规则；
- 各领域不同的 reconcile 查询和 close 副作用；
- AS2 每帧模拟、StateCore 持久化、SOL 修复逻辑。

Loot 是压力测试和反例，不是基座母版。

## 4. P0-F 最小范围

### 4.1 机器契约最小演进

优先演进现有 `panel-contracts` 和 validator，不平行新建完整 Domain Registry。P0-F 只需要表达：

- `domain`；
- `query | transaction` 能力；
- command 级 `businessDecisionOwner`（暂名，由 F1 冻结）；
- command access / 读写级别；
- handler binding；
- 现役消费者真正要求的 identity。

上述字段均是需求级暂名，精确 schema 由 F1 在现有机器契约中裁决。这里的 owner 只表示某条命令当前由哪层作业务裁决，不是持久 aggregate 的完整 `authorityMode`。不在 P0-F 登记持久化布局、Bootstrap editor/save-repair 门控、未来 StateCore backend、价格或特性恢复 key；现役聚合级权威仍由架构 canonical doc 管理，未来若启动存档 v4 则另立独立 ADR。

是否需要升级为 v2、拆引用文件或只扩充 v1，必须由现行 strict validator、兼容性和唯一 source of truth 要求裁决；不得为了少改版本号静默改变 v1 含义，也不得先造第二份表。

### 4.2 固定现有 Web Runtime Profile

不创建新的“Panel SDK”。新 Query/Transaction Panel 默认组合：

```text
Panels + panel-runtime + workbench-lifecycle
+ 按需的 focus / primitives / components
```

P0-F 只补至少两个真实消费者都缺少的 primitive。checkpoint、write gate 或 reconcile 即使名称相同，也必须先证明实现形状同构才能抽取；共享故障分类和测试向量优先于共享状态机。

### 4.3 Host 窄 transport helper

以 `NpcShopTask` 与 `CraftingTask` 为当前首选候选；F0 冻结两个参考消费者后，只从它们的同构部分提取组合式 pending-call primitive：

- backend callId；
- pending/timer 生命周期；
- 现役保守投递分类；
- 迟到/重复回包；
- disconnect/dispose cleanup；
- Web response 回送所需关联信息。

领域 Task 继续负责 command 白名单、payload 重建、严格回包校验、token、write gate 和 reconcile policy。

当前 `XmlSocketServer.TrySend(false)` 同时覆盖未连接和 `Write/Flush` 异常，不能证明“确定未投递”。P0-F 对写请求的 `TrySend=false` 一律保守归为 `delivery_unknown`；未来若要细分，必须以窄 `TransportSendResult` ADR 和独立测试推进，不能把未经证明的分类暗含在 pending helper 中。

若接入第二个消费者时公共 helper 出现 `npcshop/crafting/skill/loot` 等领域分支，应立即缩回更小 helper，而不是增加 capability flag。

### 4.4 AS2 与可观测性

P0-F 不建设 AS2 adapter 层，也不横扫所有服务加入 `authorityMode` guard。只复用 `PanelRequestEnvelope`/现有领域服务，并完成 writer 清单与静态审计接缝。writer 清单是 F0 临时审计工件，F4 必须删除或把稳定事实回流唯一 canonical；静态审计只能落入现有契约 validator 或一个具名 lint 脚本，若成为活动验收入口则同轮路由到 `testing-guide.md`，不得再形成长期平行文档。

公共关联先复用现役字段；没有两个消费者的 `contextEpoch/authorityEpoch/idempotencyKey` 不提前进入 wire。P0-F 只实现 Query/Transaction 所需的迟到、重复、断线、close 和未知写故障向量；execution lease、场景 teardown、角色热切换留给 RogueRun ADR。

### 4.5 明确不做

- Authority Router、StateCore backend、`mydata v4` 或 SOL 退役实现；
- 新数据库、进程、事件存储、DI 框架、代码生成或反射式插件系统；
- 万能 Panel renderer、万能 domain model、巨型 `BaseTask`；
- 新增跨进程 hop 或 Host 每帧裁决；
- 批量重写稳定旧面板；
- 强迫 Skill/Loot 接入公共 helper；
- 为未来假设预留未使用 schema 字段。

- 迟到、重复、断线、close/reopen、保守 `delivery_unknown` 和权威确定结果有确定终态；
- 没有特性专用 recovery key 组合进入公共层；

若没有合适试点，专项只能以 `Partial` 关闭，不能把未经第三个消费者证明的 helper 宣布为后续强制基座。

### F4：删除、回流、关闭

## 6. 反过度设计硬门

一个“轮次”是一次完整阶段交付尝试，加适用的验证和审阅；只有发生代码、契约或生产配置变化时才要求对应构建与定向回归。每个阶段退出门最多尝试两轮；同一退出门连续两轮未通过即停止。专项 `Active` 窗口固定为 2026-07-23 至 2026-09-17（八个日历周），到期仍未完成必须按已有证据以 `Partial` 或 `Rejected` 关闭；不得在本文内续期，重启必须另立 ADR。

terminal 判定是：

- `Closed`：F0–F4 全部通过，包含 F3 第三个消费者证明；
- `Partial`：F4 清理、canonical 回流和替代治理入口已完成，保留的成果均已证明，但缺少至少一个后续证明；
- `Rejected`：公共抽象不保留，F4 已完成删除、必要事实回流和替代治理入口。

任何 terminal 都必须经过 F4，不能用状态标签跳过清理。

公共原语必须同时满足：

1. 至少两个生产消费者存在同构机械重复；
2. 同轮删除或禁止复制对应旧机制；
3. 不包含领域 payload、错误政策或特性分支；
4. 有独立测试、owner 和可删除边界；
5. 不增加 IPC hop；
6. 不要求无关稳定面板适配。

触发任一条件即停止抽象：

- 第二个消费者迫使 helper 增加领域 `if`；
- F2 结束仍保留新旧 pending/timer 双轨；
- 公共字段或状态没有两个真实调用点；
- 测试必须模拟尚不存在的 StateCore/双 backend；
- 新 Panel 仍需自建同类 transport 状态机；
- 公共组件比复制前更难读，且无法由删除量和故障覆盖解释；
- 同一退出门连续两轮未通过。

触发后删除未证明的公共代码；F0 审计结论按 F4 回流 canonical，临时清单随专项清理。机器契约成果只有在同轮进入现有契约 canonical 与 validator 后才可保留，否则一并删除。随后以 `Rejected` 或 `Partial` 关闭。证明“不值得抽”也是合法成功结果。

## 7. 验收口径

### 成功必须同时满足

- F0 冻结的两个参考 Task 已停止自行拥有 §5 F2 所列 backend pending-call 机械状态，原业务回归保持；
- 新试点零自建 pending map、timer、backend callId mux；
- 公共层无领域名分支，不持有价格、容量、token 或 reconcile 政策；
- 未新增 command/authority 第二 source of truth；
- Skill/Loot 未被迫适配；
- 未引入新技术栈、额外 IPC 或 StateCore 假实现；
- 共享故障向量和真实领域 harness 都能复现确定终态；
- 稳定事实已回流 canonical docs，专项已关闭。

### 不作为成功指标

- 新增公共类数量；
- “框架完整度”；
- 单纯新增/删除 LOC；
- 只有 helper 单测或 build exit 0；
- 把更多现役领域迁进公共层。

## 8. 与长期路线的关系

- P0-S 可与 F0/F1 并行，稳定性修复不得等待基座。
- 全仓直接 writer、动态别名和旧 UI 写路径普查仍属于 P1；P0-F 只覆盖参考/试点接缝。
- P1 的 `EconomyFacade/CombatSupplyService` 可消费本专项形成的契约和 transport primitive，但不得反向扩张 P0-F。
- 其余 `Task` 不在 P0-F 批量接入 helper；后续仅在 P1 或各面板被实际触及时，按“同构证明 + 同轮删除旧机制”的门逐个采用。
- StateCore、Authority Router 和混合存档 schema 等第二个 backend/owner 真实出现后再立 ADR。
- RogueRun 是未来 execution lease/context switch 试点，不进入 P0-F 的 Query/Transaction 基座。
- P4/P5/P6 批量迁移按领域/事务闭包切换，不因 P0-F 自动获得权威迁移许可。

## 10. 阶段决策、例外与关闭规则

专项激活时已经冻结 §4 范围、§6 硬门和 terminal 关闭语义。以下不是立项前置条件，而是必须在指定阶段关闭的 gate output：

1. F0 关闭两个 F2 参考消费者和一个 F3 试点的选择；
2. F1 关闭现有 `panel-contracts` 如何最小表达 command business decision owner、capability，以及是否升级版本；
3. F1 用 validator 关闭参考/试点命令裁决路径唯一性；
4. F2 开始前冻结 Host pending-call helper 的最小 API。

任一决策未在所属阶段两轮内关闭，按 §6 直接进入 `Partial` 或 `Rejected`，不得以“继续研究”穿越阶段。

| ID | 范围 | 原因 | owner | 删除门或期限 | 状态 |

所有事项在进入任一 terminal 状态时必须是“完成、拒绝或移交到具名 ADR”，不得保留“继续研究”。`Closed / Rejected / Partial` 都必须移除 [AS2 UI → Web Panel 迁移护栏](../agentsDoc/as2-web-panel-migration.md) 和[上位长期路线](AS2-Launcher持久状态权威与战术携行集-长期演进调研-2026-07-23.md)中的活动期必读措辞；后续需求不能自动重新激活专项。活动期暂停门也不得静默消失：F4 必须同轮把“采用已证明基座继续”“维持暂停等待后继 ADR”或“停止该类迁移”的裁决回流迁移护栏。
