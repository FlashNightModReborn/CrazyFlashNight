## 0. Compact 后从这里恢复

### 0.1 一句话结论

现在值得启动角色构筑 B0：产品形态已经足够稳定，真正未知的不是“页面画成什么样”，而是装备栏缺少事务/revision、药剂仍被旧 HUD 消费、已穿戴调制跨越现有背包假设，以及关闭/断线必须在释放 pause lease 前于 `liveRefreshDirty` 时至多完成一次可证明的活体刷新，并完成持久化 finalize。先证伪这四点，再做只读页面；不要直接切 `EQUIP_UI`。

### 0.2 当前事实、目标与下一步

### 0.3 已冻结决策

| ID | 决策 |
|---|---|
| C1 | 药剂装配必须纳入角色构筑。否则 `_root.玩家信息界面.快捷药剂界面` 仍是背包药剂的唯一装配消费者，旧 HUD/装备链无法独立收口。 |
| C2 | 药剂只迁移“装入、替换、卸下、查看数量/键位/冷却”；实际使用、扣量、耗尽清理继续由 `DrugInputService`，逻辑冷却继续由 `ManualCooldownService` 权威负责。 |
| C3 | 顶层继续使用 `panel=workbench`；建议入口为 `profile=battlebox, view=build`。`build ↔ storage` 是同一 panel instance 内的 view 切换，不走 return stack、不重复暂停。 |
| C4 | `storage` 只允许背包 ↔ 战备箱。战备箱物品必须先进入背包才能装备、装入药剂栏或调制；首版不做战备箱直装。 |
| C5 | 角色构筑编辑主态仍是双栏：左约 45% 为一个纸娃娃、6 个护具槽、5 个武装槽和底部 4 药剂槽；右约 55% 只在候选与当前装备调制之间互斥。个人信息使用覆盖整个 workbench body 的全宽 SecondaryPage，与编辑态互斥；不得扩成三栏。 |
| C6 | 11 个装备协议键严格固定为 `头部装备、上装装备、下装装备、手部装备、脚部装备、颈部装备、长枪、手枪、手枪2、刀、手雷`；Web 文案可把 `手枪2` 显示为“副手手枪”。药剂只接受索引 `0..3`，禁止接线旧第五视觉槽。 |
| C7 | 新鲜打开时不强选任意槽位。右栏先显示“选择一个装备或药剂槽”；选择空槽进入相应候选。占用装备槽默认进入替换候选，并显式提供“调制当前装备 / 卸下”；占用药剂槽只提供“替换 / 卸下”，不出现调制。 |
| C8 | 候选单击或首次键盘确认只固定本地预览；唯一主 CTA 执行“装备/替换”。键盘在同一已预览候选上再次按 Enter 等价触发该 CTA，但不得绕过 disabled/写门。不再弹二次确认框，也不提供 loadout 安全/快速偏好。未提交预览在切槽、进调制/个人信息/收纳或关闭时直接丢弃。 |
| C9 | 结构性不兼容候选由 AS2 projection 直接排除；槽位兼容但暂时受等级/职业/冷却等条件阻断的候选保留为 disabled，并返回玩家可读原因。Web 筛选不是写入授权。 |
| C10 | 装备/药剂提交立即修改 AS2 容器 authority，并返回完整受影响快照；Web 只保留未确认预览，不把整套换装延迟到退出时批量提交。 |
| C11 | 装备穿脱及已穿戴调制推进 `loadoutRevision` 并置 `liveRefreshDirty`；药剂写只推进 `drugRevision`/存档 dirty，不触发人物活体重建。 |
| C12 | `edit → stats` 使用一次性 live flush；正常 close 与 socket detach 使用更强的 finalize。只有 `loadoutRevision != liveRevision` 时才调用一次人物刷新；成功后才能更新 `liveRevision`。无装备变更切页/关闭零人物刷新。 |
| C13 | `build → storage` 不 flush，只暂停构筑视图、撤销未提交预览/调制 token并排空写；返回时重新读取 backpack/loadout/drugs/candidates，旧 lease 全部作废。关闭即使发生在 storage 仍要结算原 CharacterBuildSession 的 dirty。 |
| C14 | 业务 wire 使用独立 `domain=loadout`；不把装备/药剂槽注册为 `InventoryPanelService` 的第四、第五类普通容器。Host/Web 可以有一个 session barrier，但 AS2 的装备规则、药剂规则、调制规则和库存规则不合并成“万能槽服务”。 |
| C15 | 已穿戴调制继续走 `domain=equipment_tuning` 和同一 `EquipmentTuningService/View`。首轮只放行单件原地强化、升阶、插件安装/替换/拆卸；强化度转换等跨背包/装备双 lease 操作继续拒绝。 |
| C16 | standalone tuning 的来源筛选增强纳入同一 epic、单独切片：左侧由 AS2/Inventory projection 只给武器/防具候选，不再先拉完整背包再靠 Web 跳过非装备；它不得与 worn adapter 混成同一大提交。 |
| C17 | 准确个人信息只来自 flush 后的 `PlayerInfoProvider` 结构化 snapshot。编辑态最多显示物品自身差异和少量静态摘要，不承诺实时人物总属性，不把长期 TS/AS2 portable stats kernel 设为首版前置。 |
| C18 | B4 真机关闭、断线、重启回读与剩余旧 Hub 责任审计前，不改 `EQUIP_UI`，不删除旧物品 Hub、玩家信息 HUD、技能/材料/情报资产，也不宣称角色构筑迁移完成。 |
| C19 | 旧 Hub close 至少会调用 `saveAll()` 排程，而现役 Web workbench 只留 dirty；角色构筑正常 close 必须显式调用 AS2 `finalize`。finalize 在 live flush 证明后，仅对全局 dirty 调用现有 `flushNow()`；本轮实际调用时只有明确返回 `true` 才通过，若全局原本 clean 则 persistence phase 可作为 no-op 成功。当前 `flushNow()` 缺少异常下复位 `_saveInFlight` 的 `try/finally`，这项窄修复是开放 finalize 的硬前置。 |
| C20 | generic lazy-cancel、force-close、正常 close 与所有相关回包都必须携并校验 active exact `panelInstanceId`；缺失或 stale 一律拒绝，不能只凭 `panel=workbench` 影响后来实例。 |

### 0.4 硬停线

- `EquipmentInventory` 的版本观察和原子回滚未通过 B0 反例测试前，禁止开放首个穿脱写命令。
- `_root.刷新人物装扮` 没有明确成功返回值；未建立可测试后置条件前，禁止让 close 无条件把 `liveRevision` 追平。
- `SaveManager.flushNow()` 未用 `try/finally` 保证异常后 `_saveInFlight` 复位，且实际调用时的 `true`/`false`/throw、本地 SharedObject 与 Launcher shadow 证据边界未形成测试前，禁止开放 finalize 或把回包称为完整持久化成功。
- close、ESC、backdrop、lazy cancel、force close、socket detach、reconnect 任一路径可越过 dirty barrier 时，禁止切 `EQUIP_UI`。
- 已穿戴 source adapter 未证明材料与装备写原子、未知结果可对账、焦点可恢复前，只读展示可以继续，调制提交必须关闭。
- 旧 UI、拾取、手雷战技、药剂获得/消耗等服务外写仍存在；不得仅靠“面板已暂停”假设状态不会漂移。
- 不为首版创建通用 PanelCloseBarrierRegistry、万能容器协议、完整人物数值预测器、预设套装/撤销历史、第五药剂槽或跨容器调制转换。

## 1. 为什么现在做，以及技能迁移能复用什么

### 1.1 排序裁决

装备槽不再只是旧 UI 内部功能。它已经有三个外部消费者：

1. 背包物品要进入装备栏；
2. 背包药剂要命中玩家信息 HUD 的药剂栏；
3. 已穿戴装备需要进入调制。

若只迁装备槽、不迁药剂装配，旧玩家信息 HUD 仍是管理流程必需品；若只迁纸娃娃、不迁已穿戴调制，玩家仍需“脱下 → 调制 → 再穿回”；若每次穿脱都刷新 live hero，则会把射击清理、单位重初始化和装备生命周期反复塞进普通 UI 点击。因此现在最有价值的工作是先冻结一个能同时承接这些消费者、又不合并其领域权威的 `CharacterBuildSession`。

### 1.2 从 Skill 迁移复用的方法

| Skill 已验证方法 | 角色构筑如何复用 |
|---|---|
| 管理交互与战斗执行分开 | Web 管理药剂槽；`DrugInputService`/`ManualCooldownService` 继续负责使用和冷却 |
| HUD 可缺失，领域写不依赖 renderer | 药剂写成功后可选刷新旧 HUD；HUD-null 不影响容器 authority |
| 固定槽白名单与结构化 descriptor | Skill 12 槽换成装备 11 键 + 药剂 4 索引，不接受 Web 任意键 |
| 服务外 legacy 写用 stateSignature + synchronize 观察 | 装备栏在观察期用 11 槽签名发现旧 UI/拾取/战技写；药剂复用既有 mutation revision |
| expectedRevision + writeEpoch + 显式 reconcile | loadout 写、迟到 snapshot、未知结果沿用同一反乱序原则 |
| close/断线撤销 session/token | 角色构筑额外要求先 flush dirty live actor，并在关闭路径完成持久化 finalize，再释放 pause |
| HUD-null、坏档、旧 writer 单独 Gate | 角色构筑同样先证明服务化，再切入口，最后才退役旧 UI |
| 分片施工而非一次删壳 | B0 合同 → B1 只读 → B2 穿脱/药剂 → B3 worn tuning → B4 切流 |

### 1.3 明确不照搬 Skill 的部分

- 不新建 `panel=drugs` 或 `panel=character-build`；角色构筑与收纳需要共享同一 workbench/pause/session。
- 不把 DrugInventory 伪装成快捷技能数组，也不复用 Skill 的教师 session、学习 token 或 80 行存档规则。
- 药剂装配是背包与 DrugInventory 之间的真实物品事务，必须携背包 slot lease；Skill equip 没有这个容器交换问题。
- 角色构筑有延迟活体刷新，Skill 没有同等的 close flush barrier。
- Skill 的 same-panel trainer rebind 不是 `build ↔ storage` 的实现模板；后者应是同一实例内部 view switch。

## 2. 已核实的当前地面事实

### 2.1 当前调用拓扑

```text
NativeHud EQUIP_UI
  → LauncherCommandRouter
  → game command openEquipUI
  → 旧 _root.物品栏界面
       ├─ 背包 ↔ 11 个 EquipmentInventory 槽
       ├─ 旧个人信息页
       ├─ 旧调制入口
       └─ 技能 / 材料 / 情报等剩余责任

背包药剂拖放
  → InventoryIcon hitTest
  → _root.玩家信息界面.快捷药剂界面[0..3]
  → DrugInventory

现役 Web workbench
  ├─ view=storage：背包 ↔ 仓库/战备箱
  └─ view=tuning：背包装备 → EquipmentTuningService
```

目标不是把上述所有责任塞进一个新类，而是让同一 Web 会话组合四个明确参与者：

```text
CharacterBuildSession（生命周期、revision、flush barrier）
  ├─ loadout authority：装备/药剂管理
  ├─ InventoryCoordinator：背包 lease、战备箱收纳、external write gate
  ├─ EquipmentTuningService/View：背包或已穿戴单件调制
  └─ PlayerInfoProvider projection：flush 后只读属性
```

### 2.2 容器与槽位

| 权威 | 当前类型 | 槽位 | 现有版本能力 | 角色构筑含义 |
|---|---|---:|---|---|
| 背包 | `ArrayInventory` | 50 | 容器提供 `mutationRevision`/transactionWrite；`InventoryPanelService` 另行签发 slot lease | 候选唯一直接来源 |
| 装备栏 | `EquipmentInventory` | 11 个字符串键 | 无 mutation revision、无事务写 API | B0 首要缺口 |
| 药剂栏 | `DrugInventory` | 4 | 继承 `ArrayInventory` 的 revision/事务能力 | 可复用，但写前需冷却权威复核 |
| 战备箱 | `ArrayInventory` | 剧情开放前缀 | 现役 InventoryPanel authority | 只通过 storage 搬到背包 |
| live hero | MovieClip + 装备生命周期 | 非容器 | `_root.刷新人物装扮` 重建 | 只在 stats/close 批次刷新 |

装备栏必须显式白名单，因为 `EquipmentInventory` 自身只检查 `item.use == key`，另有 `use=手枪 → key=手枪2` 特例，并不提供完整合法键集合。现役 dressup manifest 已包含 `颈部装备` 的视觉 projection；B0 仍要对每个部位验证未知值和缺素材 fallback，管理槽与 snapshot 不能因某次视觉资源缺失而消失。

### 2.3 服务外写者不能忽略

| 写者 | 装备/药剂影响 | B0 对策 |
|---|---|---|
| 旧物品 Hub 拖放/卸下 | 直接换装备并立即刷新；部分路径 dirty 语义不一致 | 观察期保留，session open/snapshot/write 前同步签名 |
| 组合键拾取 | 可直接装备、替换旧装备并切武器模式 | 不在首版重写；签名发现，切流后另做 legacy writer 审计 |
| 手雷主动战技 | 直接减装备栏手雷数量，耗尽时移除并刷新 | 装备签名必须覆盖 stack 数量/对象更新时间 |
| `DrugInputService` | 使用药剂、减数量、耗尽移除 | DrugInventory revision 天然可见；Web snapshot 不持久假设数量 |
| `ItemUtil.acquire/submit` | 可向药剂栏合并或从中扣除 | 读/写前比较 drug revision；未知结果重拉 |
| `EquipmentTuningService` | 原地修改装备 value/lastUpdate | worn adapter 成功后显式通知 session；签名仍作兜底 |

暂停游戏能降低并发，但 `ManualCooldownService` 明确在暂停期间继续推进，且现役代码仍有不依赖玩家输入的外部 writer。session 设计必须以版本/签名为依据，不以“理论上不会发生”为依据。

### 2.4 活体刷新是行为重建

`_root.刷新人物装扮` 不只是换贴图。它会清理射击状态、重新运行单位初始化、卸载/安装装备生命周期、重建 Buff/组件与参数、重算负重/速度/技能、切换武器模式并把角色送回安全动作帧。候选 hover、点击预览或每次装备提交都调用它，会把普通菜单操作变成反复重建角色。

因此首版只允许：

```text
装备穿脱 / 已穿戴调制提交成功
  → loadoutRevision++
  → liveRefreshDirty=true
  → Web 纸娃娃立即用结构化装备快照重绘
  → stats/close 时最多执行一次 live flush
```

药剂装配提交只推进 `drugRevision` 与全局存档 dirty；它不进入上述 loadout/live 刷新链。

当前函数没有显式成功返回值。B0 必须由 wrapper 建立“调用前依赖齐全 + 调用后 live hero 与装备投影一致”的 Boolean 证明；失败时保留 dirty 与 pause，不能猜成功。只检查“没有 throw”或 `UnitInitialized` 事件不足以证明外层被动、Buff、安全帧和装扮引用刷新已完成。

## 3. 产品形态与交互合同

### 3.1 状态机

```text
                    ┌───────────────┐
                    │ edit/candidates│  ← 默认主态
                    └───────┬───────┘
                            │ 当前槽已有装备
                            ▼
                    ┌───────────────┐
                    │  edit/tuning  │  ← 右栏钻取，复用 tuning view
                    └───────┬───────┘
                            │ 返回
                            └────────────→ edit/candidates

edit/candidates ── 信息 ──→ flush_pending(stats)
       ▲                         ├─ 成功 → stats（全宽 SecondaryPage）─ 返回编辑 ─┘
       └─────────────────────────┴─ 失败 → flush_failed ── 重试/返回 ──┘

edit/candidates ── 收纳 ──→ storage（同 panel，同 pause，不 flush）
storage ── 返回构筑 ──→ fresh snapshot → edit/candidates

任一可关闭态 ── close ──→ flush_pending(finalize)
  ├─ live/global 均 clean：finalize no-op 成功后发 exact close
  ├─ live/global 任一 dirty：finalize 刷新/存盘成功后发 exact close
  └─ write_pending / needs_reconcile / flush_failed：保持面板或 pause，不越过
```

`write_pending` 与 `needs_reconcile` 是覆盖态，不是可借切页逃逸的普通页面。出现时禁止进入 tuning/stats/storage 和发起第二个写；确定失败回到可操作态，未知写只允许权威对账，不自动重投。

### 3.2 1024×576 语义线框

槽位分组冻结，精确像素不冻结：

- 6 个护具槽：头、颈、上装、手、下装、脚，围绕纸娃娃的身体语义排列；
- 5 个武装槽：长枪、主手手枪、副手手枪、刀、手雷，形成独立武装轨，避免 11 个槽全部散落在人物轮廓上；
- 4 个药剂槽固定底栏，显示数量、实时键位与冷却/可更换状态；
- 所有目标维持至少 44px、设计值 48px；密度切换不得缩小装备/药剂槽。

### 3.3 槽、候选与提交

1. fresh open 不自动选择槽；焦点先到角色构筑区域标题/首槽，右栏给短指引。
2. 点击或 Enter/Space 选择槽。切槽会丢弃未提交候选预览，不写 AS2。
3. `candidates` 只返回当前槽的候选。默认按背包物理槽稳定排序；筛选与搜索只能缩小可见集合，不能改变 authority。
4. hover 只显示共享 tooltip，键盘 focus 只更新候选摘要；二者都不换装、不提交。hover 纸娃娃预览不是 B0/B1 Gate，若以后增加，必须先过 doll 性能 spike，并采用 debounce/latest-wins。
5. 候选单击或首次 Enter/Space 固定预览；纸娃娃仍是单 Canvas，以当前已提交 state 加一层候选覆盖重建。键盘在同一已预览候选上再次按 Enter 等价触发主 CTA；Space 只负责固定预览，避免滚动/重复按键意外写入。
6. 主 CTA 只发送一次原子 equip，且与“同一候选第二次 Enter”共用同一 disabled/write gate。成功后采用完整 loadout + affected inventory snapshot，清预览并恢复到同槽；候选物理格仍存在则保留焦点，否则回到当前装备槽。
7. 目标已占用时沿用旧有效语义：新装备进入目标槽，旧装备回到所选背包来源槽；目标为空时是 move。手雷/药剂等数量型同名堆叠语义必须由 AS2 明文测试，不由 Web 猜测。
8. “卸下”位于右侧当前装备动作区，不在 48px 槽角落放小 `×`。卸下需要背包空位；不足时保持原状态并显示原因。

### 3.4 药剂管理

- 选择药剂槽后，右侧只显示 `use=药剂` 的背包候选。
- `equipDrug/unequipDrug` 写前重新检查 `ManualCooldownService.isReady("drug:"+slot)`；Web 的冷却显示不是授权。
- snapshot 返回 `ready/totalSteps/currentStep/remainingMs` 与当前键位文案。`keyLabel` 必须由 AS2 沿用 `DrugInputService.getKeyName(slot) → _root[keyName] → _root.keyshow(keyCode)` 的现役来源生成，不能从纸娃娃 renderer 或 Web 默认数字猜。Web 可本地显示估算进度，到预计结束时只发一次 fresh `snapshot` 再开放写按钮；不创建独立 `drugState` 命令，也不做高频轮询。
- 药剂写返回 DrugInventory 新 revision、四槽完整快照和受影响背包窗口；真实改变统一 dirtyMark。
- 战斗中消耗/耗尽引发 revision 变化后，下次 snapshot 直接采用权威状态；Web 不维护独立数量镜像。
- 旧 HUD 存在时可以继续接受可选 renderer projection；HUD-null 是正常路径，不得成为装配写前置。

### 3.5 已穿戴调制

- 只有当前占用装备槽显示“调制当前装备”。
- 进入后撤销候选预览，右栏挂载同一 `EquipmentTuningView`，source 文案改为当前槽/当前装备。
- adapter 形状区分 `sourceKind=inventory|loadout`；`loadout` 只接受显式 11 槽白名单和当前 loadout revision，不接受任意 containerId。
- 首轮允许 enhance、tier、install/replace/detach mod 等单件原地操作；convert 与任何需要第二件背包装备的跨容器计划仍返回明确不支持。
- 成功 commit 同时更新 tuning snapshot、loadout snapshot、材料/背包相关 projection，推进 `loadoutRevision` 并置 live dirty；任一结果不完整进入 reconcile。
- 返回候选时恢复原槽、候选滚动和合理焦点。现役 tuning 全量重建 DOM 只恢复 scroll、不恢复焦点，这项债必须与 adapter 同轮修复。
- 进入角色构筑前必须同轮偿还四项已核实的可用性债：tab 主标签从 9px 提升到至少 11px、31px 主 CTA 提升到至少 40px、hover-only 信息提供 focus-visible/键盘等价路径、全量 DOM 重建后按稳定实体键恢复焦点。只修这些接入债，不借机重做整套调制视觉。

### 3.6 个人信息

个人信息已冻结为覆盖整个 workbench body 的全宽 SecondaryPage，不再把 35–39 个字段挤入 55% 右栏，也不保留一块不可操作却持续占宽的纸娃娃：

- 进入 personal info 前必须排空写、完成 reconcile 并经过 `flush_pending(stats)`；只有 `liveRefreshDirty=true` 时实际刷新人物，live clean 时 barrier 以 no-op 通过；
- flush 成功后 header 切为“角色信息 / 返回构筑 / ? / ×”，body 使用全宽分组两列和唯一纵向滚动区；
- 正文至少 11px，字段名不得截断，不允许嵌套横滚；1024×576 仍要覆盖最长中文、极端数值和完整键盘顺序；
- stats 是只读 SecondaryPage，装备/药剂/调制控件不挂载、不可聚焦；返回 edit 不刷新，只重新挂载编辑视图并恢复先前槽焦点。

stats wire 只接受结构化值：

```js
{
  group: "defense",
  key: "damageReduction",
  label: "减伤率",
  value: 95.7,
  unit: "%",
  displayHint: "percent-1"
}
```

不得把 `<font color=...>`、MovieClip 字段名、布局坐标或拼好的 `"14.6m/s"` HTML 当作协议权威。现有 getter 可作为公式来源，`populatePlayerInfo(target)` 后续应成为结构化 snapshot 的 legacy renderer adapter，而不是反过来从旧 UI 抄值。

### 3.7 收纳、Esc 与焦点

- header “收纳”进入同一 workbench 的 `view=storage`，只显示背包 ↔ 战备箱 transfer-pair；不打开第二 panel。
- 进入前撤销未提交预览与 tuning token，等待所有写定局；不 flush live actor。
- 返回构筑强制 fresh backpack/loadout/drug/candidate snapshot，保留仍合法的所选槽，不保留旧 slot lease。
- Esc 顺序固定：清未提交候选 → 退出 tuning/stats/storage 回 edit → 请求关闭。`write_pending/needs_reconcile` 时 Esc 不得抹状态。
- 当前共享 `EntityTile` 只处理 Enter/Space，方向键导航仍是 `inventory-ui.js` 的私有实现，仓库里并不存在可直接宣称复用的 Grid keyboard primitive。B0 要从该语义提取一个窄、无领域知识的 `RovingGridFocus`：只管理 active tabindex、四方向移动和销毁；护具、武装、药剂组可提供显式邻接，候选 grid 提供列数。B1 前不得再造全局空间导航引擎。
- 格子区域把护具、武装、药剂、候选四个逻辑组各压成一个 Tab stop，组内用方向键移动；header、筛选、主 CTA、调制和卸下等普通动作仍按正常 Tab 顺序可达。不要让 15 个槽加全部候选形成超长串行 Tab。
- selected、preview、cooldown、disabled 不得只用颜色表达；必须有文字/图形状态、清晰 focus ring、ARIA label/state 和提交后的 aria-live 回报。

### 3.8 顶栏动作预算

1024 宽顶栏是不换行 flex，常驻动作只保留：

- 主态中的“收纳 / 个人信息”；
- stats/storage/tuning 中的单一“返回构筑”；
- 情境帮助 `?`；
- close `×`。

current/preview 放纸娃娃区域；筛选与密度放右栏 PaneChrome；tuning 的安全/快速只在 tuning 内出现。不得把 density、stats、storage、tuning、安全/快速、帮助和 close 全部堆在 header。

当且仅当 `liveRefreshDirty=true` 时，标题旁显示非操作性状态徽标“构筑待应用”；不得显示 revision、dirty、flush 等技术词，也不得把徽标做成按钮。进入 stats/finalize 成功后消失，药剂-only 变化不会点亮。

## 4. AS2 authority 与 `CharacterBuildSession`

### 4.1 最小职责，不造万能 Coordinator

术语在三层固定分工：`CharacterBuildSession` 仅指跨 Web/Host/AS2 的逻辑会话寿命、pause、revision 与 flush barrier；AS2 唯一业务类暂称 `CharacterBuildService`；Web 对应的薄状态模块是 `character-build-session.js`。本文出现 Session 不代表再新增一个与 Service 并列的 AS2 writer。

首版建议只有一个窄的 AS2 `CharacterBuildService`（最终类名可在 B0 spike 后冻结）：

- 开始/结束一个构筑 session；
- 读取 11 个装备槽、4 个药剂槽、背包候选和纸娃娃 projection；
- 原子执行 equip/unequip equipment、equip/unequip drug；
- 维护装备签名、`loadoutRevision/liveRevision/liveRefreshDirty`；
- 读取 DrugInventory revision；
- 调用/验证一次性 live flush 与关闭 finalize；
- 生成结构化 stats snapshot；
- 为 generic unpause 和 socket detach 提供幂等 fallback。

它不接管：

- InventoryPanel 的仓库/战备箱规则；
- EquipmentTuningService 的强化/材料事务；
- DrugInputService 的使用/耗尽；
- ManualCooldownService 的调度；
- PlayerInfoProvider 的公式；
- Host 的 call tracker 或 Web DOM。

只有当单类在实际 B1 代码中越过现有体积/职责审计阈值，才拆 `CharacterBuildProjection` 等叶模块；B0 不预造通用 loadout framework。

### 4.2 session 状态

逻辑状态至少包括：

```js
{
  sessionGeneration,
  capturedPauseLease,
  equipmentRef,
  drugRef,
  backpackRef,
  equipmentSignature,
  loadoutRevision,
  liveRevision,
  liveRefreshDirty,
  lastDrugRevision,
  state: "idle|write_pending|needs_reconcile|flush_pending|flush_failed"
}
```

关键规则：

1. `loadoutRevision` 只描述需要 live hero 重建的装备/已穿戴调制变化；药剂变化不推进它。
2. 每次 snapshot、候选读取和写前都同步装备签名与容器引用；发现服务外变化时推进 revision、撤销旧 preview/token 并按当前 live 匹配情况置 dirty。
3. 装备签名至少覆盖 11 个键、对象存在性/名称、数量或完整装备 value、tier/mods/level、lastUpdate；不能只比较显示名。
4. DrugInventory 使用自身 `mutationRevision`；引用替换或 revision 倒退视为 session stale，不在 Web 端修复。
5. session 写成功后重新签名，只推进一次 revision；no-op 不 dirty、不刷新、不推进。
6. 已穿戴 tuning commit 必须显式回调/通知 session；下次 synchronize 的签名发现只是兜底，不是正常成功路径。
7. `flushLive/finalize` 的业务拒绝、后置条件失败或本地存盘明确失败进入 `flush_failed`；Host 已接受后发生 timeout、断线或畸形结果则是结果未知，进入同一个 `needs_reconcile` 覆盖态。
8. unknown `flushLive` 可由越过在途水位的 fresh snapshot 证明 `liveRevision==loadoutRevision && liveRefreshDirty==false` 后收敛；unknown `finalize` 不能只凭 live clean 发 close，必须在同一 `sessionGeneration` 下对幂等 finalize 做显式重试并取得 persistence phase success。该重试不是 mutation 自动重放，AS2 socket fallback 也必须走同一幂等函数。

### 4.3 装备事务缺口

`EquipmentInventory` 当前没有 `transactionWrite/getMutationRevision/publishTransactionChange`。B0 要比较两个最小方案，默认优先更窄者：

| 方案 | 优点 | 风险 | 裁决门 |
|---|---|---|---|
| A：只给 `EquipmentInventory` 增加 mutation revision 与无事件单槽事务 API | 影响面最小，语义明确 | 与 `ArrayInventory` 有少量重复 | 能覆盖 11 键、rollback、dispatcher 统一 publish |
| B：把事务能力上提到 `Inventory` 基类 | 以后其他 Inventory 可复用 | 可能与 ArrayInventory 现有实现/版本语义冲突 | 只有确认无 shadow/override/初始化回归才考虑 |

首版禁止直接串联公开 `remove()+add()` 后宣称原子。装备 ↔ 背包、药剂 ↔ 背包的事务必须：

1. 完整预检 source lease、target revision/signature、等级/use/手枪2/冷却/容量；
2. 备份两个槽；
3. 无事件写入两个容器；
4. 第二写失败时恢复 exact before；
5. 全部成功后统一推进各自 revision、失效旧 lease、发布兼容事件、dirtyMark；
6. 返回完整权威快照。

同步事件监听器不得观察到半交换状态。测试必须有“第二写失败、rollback false/throw、dispatcher 重入”反例。

### 4.4 live flush 与成功证明

`flushLive(expectedLoadoutRevision)` 的顺序：

1. synchronize；若出现未知服务外写，先返回 fresh snapshot/`stale_state`；
2. 若 `loadoutRevision == liveRevision`，返回 `changed:false`，零刷新；
3. 确认控制目标、live hero、装备容器、刷新函数与必要初始化依赖存在；至少检查 hero 仍挂在 gameworld，dispatcher、Buff、被动、goto、安全帧与装扮刷新依赖可调用；
4. 捕获旧 dispatcher、旧 buffManager、11 槽 live 引用和装备派生 data 引用；
5. 调用一次 `_root.刷新人物装扮(_root.控制目标)`；
6. 重新取得 live hero，验证身份与 parent 未漂移；
7. 验证 dispatcher/buffManager 已被重建且有效，11 槽 `hero[slotKey]` 与装备栏对应项保持 exact 同一对象；
8. 对有装备的槽验证派生 data 已重建；关键 `重量、行走X速度、hp满血值、mp满血值、防御力` 均为有效数值，`魔法抗性/主动战技/生命周期函数列表` 形状有效；
9. 验证外层尾段已完成：`格斗架势===false`，且 dressup 刷新不再处于进行中；
10. 只有后置条件全部成立才写 `liveRevision=loadoutRevision`、清 live dirty；
11. 失败返回 `flush_failed`，保留原 revision/dirty/pause，不调用 stats projection。

B0 可以在 AS2 `CharacterBuildService` 的同步 wrapper 中用 `try/catch + 前后不变量` 完成首版证明，不需要改造整套初始化器或新增事件框架。不能用固定延时、动画帧猜测或“函数没 throw”代替成功证明。

### 4.5 正常关闭、generic unpause 与 socket detach

正常路径：

```text
Web requestClose
  → discard local preview
  → Web character-build-session wait/reconcile
  → domain=loadout cmd=finalize
      ├─ live dirty 时执行并证明一次人物刷新
      └─ 全局 dirty 时执行现有 SaveManager.flushNow()
  → success + clean live revision + persistence phase success（actual flush true 或 global-clean no-op）
  → exact workbench close envelope
  → Host 校验 active panelInstanceId / CharacterBuildTask clean
  → AS2 webPanelUnpause
  → CharacterBuildService 最终 clean 断言
  → release captured pause lease
```

异常兜底：

- `webPanelUnpause` 在现有 loot fence 之后、真正 release lease 之前调用 CharacterBuildService 的幂等 close barrier。active+dirty 时同步重试 finalize；失败则 handled=true 并保留 pause。
- `ServerManager.onSocketClose` 在清 pending callback 前调用 `reconcileSocketDetach()`。它只可本地 finalize/释放 session 开始时捕获的 exact pause lease；若后来 panel 已取得不同 lease，绝不能释放后来者。
- Host reconnect 的 generic unpause 仍会经过同一 AS2 barrier，作为失败后的重试点；不得在 C# 假定旧 generic panel 可立即解暂停。
- 正常 Web 已成功 preflush，因此 generic hook 多数只做 clean assert/close；异常路径不依赖 Web 仍存活。

当前只有 loot 和角色构筑需要这种特殊处理。B0 使用两个显式、可测试 hook；不因“以后可能还有”提前建通用 registry。出现第三个真实消费者时再评估抽象。

### 4.6 存档 finalize

只标 `dirtyMark` 不足以复刻旧入口的关闭语义：

- 旧 Hub close 在 dirty 时调用 `_root.自动存盘()`，最终进入 `SaveManager.saveAll()`；它只是启动约 300ms trailing debounce，返回不代表已经落盘。
- 现役 Web inventory/tuning 写只标 dirty，generic workbench close 不发保存命令；同场景关闭后立即杀进程存在比旧 Hub 更弱的窗口。

角色构筑把正常 close 视为低频、高价值批次边界，使用现有强入口而不新增通用保存服务：

1. 每个真实装备/药剂/调制写设置 dirty；no-op 不标脏；
2. finalize 先完成 live flush 证明；
3. 若全局 dirty，调用 `_root.强制存盘()` / `SaveManager.flushNow()`；若全局原本 clean，记录 persistence `changed:false` 并直接通过该阶段；
4. 本轮实际调用 `flushNow()` 时，只有 `=== true` 才返回 finalize success；`false`（包括已有 save in-flight）或异常均保留 dirty/pause并允许明确重试；
5. 成功只证明本地 SharedObject flush。随后启动的 Launcher shadow 推送未被该返回值等待，文案与验收不得扩大为“所有外部副本已确认”。

源码复核已确认 `flushNow()` 目前按 `_saveInFlight=true → _doSaveAll() → _saveInFlight=false` 顺序执行，缺少异常路径的 `try/finally`。B0 必须先做窄化 SaveManager 健壮性修复，确保 `_doSaveAll` 抛错时 `_saveInFlight` 仍复位且 dirty 不被误清，再用失败注入锁定；这不是“发现反例后再看”的可选项。

## 5. 协议草案

### 5.1 路由

建议正式入口：

```json
{
  "panel": "workbench",
  "source": "nativehud",
  "initData": {
    "profile": "battlebox",
    "view": "build"
  }
}
```

Host 只接受冻结枚举：

- `profile=warehouse`：仍只允许 storage；
- `profile=battlebox`：允许 storage、tuning、build；
- `view=build` 只能来自明确白名单 source；B4 前不由 `EQUIP_UI` 生产发起。

角色数据不放 initData。panel 打开、Web mount 并取得 Host 盖章 `panelInstanceId` 后，再向 AS2 拉 snapshot。

### 5.2 业务 envelope

沿用现役严格形状：

```js
{
  type: "panel",
  panel: "workbench",
  domain: "loadout",
  cmd: "snapshot",
  callId: "character-build.<nonce>.1.17",
  panelInstanceId: "workbench.instance.42",
  payload: { v: 1 }
}
```

业务字段只能放 `payload`；Host 按命令白名单重建 AS2 请求，不透传未知键。`callId` 沿用 `PanelRequestMux` 的字符串 generation/sequence 形状，不能改成可跨会话撞号的裸整数。每个 loadout 请求、业务回包和 panel-control close/cancel 都必须回显并 exact 校验 `panelInstanceId`。全局 close 仍是独立 panel-control envelope，不伪装成 loadout 命令。

### 5.3 最小命令表

| Web cmd | 写？ | 核心输入 | 成功核心 |
|---|---:|---|---|
| `snapshot` | 否 | `v`；对账时带显式 reconcile watermark | 完整 `CharacterBuildSnapshot` |
| `candidates` | 否 | `slotKey` 或 `drugSlot`、expected revisions | 结构匹配候选、disabled reason、背包 source lease |
| `equipEquipment` | 是 | 目标装备键、背包 source ref、expected loadout revision | 完整 loadout + affected backpack snapshot |
| `unequipEquipment` | 是 | 目标装备键、expected revision | 完整 loadout + 背包落位 snapshot |
| `equipDrug` | 是 | `drugSlot 0..3`、背包 source ref、expected drug revision | 四槽药剂 + affected backpack snapshot |
| `unequipDrug` | 是 | `drugSlot 0..3`、expected drug revision | 四槽药剂 + 背包落位 snapshot |
| `flushLive` | 条件写 | expected loadout revision | `changed`、live/loadout revisions、clean state；用于进入 stats |
| `finalize` | 条件写 | expected loadout revision、当前 session generation | live flush 证明 + persistence phase（本地 `flushNow` true 或 global-clean no-op）；用于正常 close |
| `statsSnapshot` | 否 | expected clean live revision | 结构化分组 stats；`liveRefreshDirty=true` 时拒绝 |

Equipment tuning 仍走既有 `domain=equipment_tuning` 命令；只扩它的 source descriptor 和响应组合，不把 tuning cmd 复制到 loadout。

active `panelInstanceId` 下的首次 `snapshot` 建立或绑定 AS2 `sessionGeneration`；该值随 snapshot 返回，之后的 candidates/write/flush/stats/finalize payload 都必须 exact 携带。Host 不自行铸造它，AS2 对缺失或 stale generation fail-closed；reconnect/reopen 必须先取得新 snapshot，不能续用旧值。

### 5.4 snapshot 最小形状

```js
{
  v: 1,
  sessionGeneration: 4,
  loadoutRevision: 12,
  liveRevision: 10,
  liveRefreshDirty: true,
  drugRevision: 31,
  equipment: [{
    slotKey: "手枪2",
    label: "副手手枪",
    occupied: true,
    item: { /* InventoryPanelService 的安全展示投影 */ }
  }],
  drugs: [{
    slot: 0,
    keyLabel: "1",
    ready: false,
    totalSteps: 90,
    currentStep: 42,
    remainingMs: 1600,
    occupied: true,
    quantity: 3,
    item: { /* 安全展示投影 */ }
  }],
  portrait: {
    gender: "男",
    equipment: {},
    appearance: {}
  },
  stateHealth: "ok",
  diagnostics: []
}
```

数值只是示例，不是 fixture。真实 schema 必须保持：

- 11 个装备槽和 4 个药剂槽完整、稳定有序；
- 空槽显式 `occupied:false`，不靠缺键猜；
- item 只含安全展示投影，不泄漏 BaseItem 引用、内部 token 或规则对象；
- portrait 复用现有 renderer 输入，不把 Canvas 结果回传；
- `drugs[].keyLabel` 来自 AS2 `DrugInputService` 的现役键位解析链，不从 portrait 或 Web 默认键映射推导；
- corrupt/unknown state 只读可展示，写 fail-closed。

### 5.5 写状态与对账

Host `CharacterBuildTask` 与 Web session 均使用：

```text
idle → write_pending → idle
                    ↘ needs_reconcile → post-write snapshot → idle
```

- 确定成功采用响应内完整快照；
- 确定失败保持旧权威快照并恢复可操作；
- browser bridge 在 Host 接受前明确返回的同步 `not_sent` 是确定未投递，可恢复 idle；Host 已接受写后，backend `TrySend(false)` 的 `DeliveryUnknown`、timeout、断线、畸形/不完整成功才进入 `needs_reconcile`；
- 普通旧 snapshot 不得清未知写；沿用 Skill 已验证的 `writeEpoch + reconcileId/reconcileAfterCallId` 或同等显式水位；
- 不自动重放 equip/unequip/tuning 等 mutation；unknown `flushLive/finalize` 只按 §4.2 的 post-watermark 证明或同 generation 幂等显式重试收敛；
- pending/recent call 有上限，close/rebind 不得靠清字典伪装已定局。

## 6. Launcher / Web 最小落点

### 6.1 Web 模块

建议新增三个窄模块，而不是继续扩大 `inventory-workbench.js`：

| 模块 | 职责 | 明确不做 |
|---|---|---|
| `character-build-session.js` | loadout mux、snapshot/revision、write/reconcile、Inventory external-write、flush/canClose | DOM、装备规则、通用全局 arbiter |
| `character-build-view.js` | 纸娃娃/槽/候选/stats DOM、焦点与可访问性 | Host 请求跟踪、AS2 规则 |
| `character-build.js` | mount/rebind/route/cleanup 薄 facade，组合 tuning/Inventory | 复制 shell、tuning 或 inventory runtime |

只有 reducer/filter 实际让 view 超过审计阈值时再抽 `character-build-model.js`。现阶段不创建“所有 workbench 业务通用 coordinator”。

复用要求：

- `DressupDollRenderer` 只创建一个实例，view unmount 时销毁，正确处理 resize/pixelRatio/reduced-motion；
- `build → storage` 只卸载角色构筑 DOM/纸娃娃；`character-build-session.js` 与 Host `CharacterBuildTask` 保持 active，直到 exact panel close/finalize 才销毁，确保 storage 中关闭仍能结算原 dirty；
- 候选卡、tooltip 与 pointer primitive 使用 workbench 现有组件；键盘方向导航在 B0 抽取窄 `RovingGridFocus`，以现役 inventory 私有语义为参考，不虚构已有共享 Grid primitive；
- `EquipmentTuningView` 增加可配置 source/copy/focus restore，CSS 去除只认 `data-workbench-view=tuning` 的硬绑定；
- `inventory-workbench.js` 只增加 view dispatch、header/close 组合，不粘贴角色业务；
- lazy registry、release audit、required assets 和 harness 入口同轮更新。

### 6.2 布局 profile

本文把 45/55、左侧复合纸娃娃、右侧决策区称为**拟议 `character-build` semantic profile**。在 B0 静态 harness 证明稳定前，不把它写成已实现 profile；进入 B1 同轮必须：

1. 更新 [workbench UI system](../agentsDoc/workbench-ui-system.md) 的 profile 目录与最低视口；
2. 增加 atlas 主态、stats/secondary、键盘焦点和长中文样本；
3. 保持固定 1024×576 设计画布、48px header、无嵌套横滚。

### 6.3 Host

最小 Host 形态：

- 一个 `CharacterBuildTask`，组合共享 pending tracker，负责 strict envelope、writeEpoch/reconcile、session clean gate；
- TaskRegistry/WebOverlay 增加 `domain=loadout` 路由和 AS2 `loadout_response → panel_resp`；
- Router 先只增加受控 build route，不切 `EQUIP_UI`；
- PanelHost same-instance view switch 不生成新 panelInstanceId；
- close observer 在 active workbench/build session 不 clean 时拒绝视觉关闭或进入明确等待；
- pending lazy-cancel/force-close 必须携并验证 active exact `panelInstanceId`；缺失或 stale 在 Host 入口拒绝，回包也必须保留 binding 供 Web mux 复核；
- socket disconnect 保留 CharacterBuildTask 对账状态，同时依赖 AS2 本地 detach fallback，不能按普通 generic panel 立即 unpause。

不在 B0 建通用 Host return stack 或新 close-barrier registry。

### 6.4 AS2 文件方向

拟增/改范围，最终以 B0 spike 为准：

- 新 `CharacterBuildService.as` + 测试；
- `EquipmentInventory.as` 的最小 transaction/revision 能力；
- `PlayerInfoProvider.as` 增加结构化 snapshot，legacy populate 改作 adapter；
- 现役 WebView/root bridge 注册 loadout actions；
- `ServerManager.onSocketClose` 与 `webPanelUnpause` 增加显式 CharacterBuild barrier；
- `EquipmentTuningService.as` 增加 loadout source adapter；
- `InventoryPanelService` 只复用/补窄的 external snapshot/lease API，不加入装备/药剂容器。

`.as` 修改必须保持 UTF-8 with BOM；新增类按项目约束从现有 `.as` 复制后改名。实际编译目标按触及文件归属选择，不能把所有 `.as` 修改笼统称为编主文件。

## 7. 关键转移与失败矩阵

| 场景 | 允许动作 | authority 行为 | UI/关闭行为 |
|---|---|---|---|
| 候选 hover/focus | tooltip/摘要 | 零请求或只读 | 不换装；首版不驱动 doll |
| 候选 click/首次键盘确认 | 固定预览 | 零写 | 单 Canvas 预览，显示 CTA；同候选第二次 Enter 走同一 CTA gate |
| equip 成功 | 采用完整快照 | 背包/装备原子写、revision/dirty | 清预览，恢复槽/焦点 |
| equip 确定失败 | 可重选 | 零部分写 | 显示原因，保持页面 |
| equip 未知 | 仅对账 | 禁止自动重放 | 锁写/切页/关闭，直到 post-write snapshot |
| drug cooldown 未完成 | 可查看 | AS2 拒绝装配写 | disabled + 剩余时间；预计结束后 fresh read |
| 进入 tuning | 撤销候选预览 | 签发/绑定当前 worn source | 右栏钻取，左栏 current-only |
| tuning 未知 | 仅 tuning/loadout 对账 | token 不重放 | 禁止返回 storage/stats/close |
| 进入 stats | wait + flush | `liveRefreshDirty=true` 时恰好一次刷新；否则 no-op | 成功后切全宽 SecondaryPage 才显示准确属性 |
| 进入 storage | wait，不 flush | session dirty 保留 | 同 panel 切 view；返回 fresh all |
| 正常 close | wait/reconcile/finalize | live clean 且 persistence phase 成功（actual flush true 或 clean no-op）后才允许 release | 显示“正在应用并保存当前构筑…” |
| finalize 未知 | 同 generation 幂等显式重试 | fresh snapshot 只可证明 live 部分；不得冒充 persistence success | 不发 close、不释放 pause |
| socket detach | AS2 本地 fallback | exact session finalize/lease proof | Host 视觉关闭不等于已解暂停 |
| flush 失败 | 可重试/诊断 | dirty/live revision 不变 | pause 保持；不得静默回游戏 |
| 外部签名漂移 | fresh snapshot | revision 推进、旧 token/lease 失效 | 丢预览，提示状态已更新 |
