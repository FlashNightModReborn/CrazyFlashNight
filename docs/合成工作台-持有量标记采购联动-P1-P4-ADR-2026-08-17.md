**状态**：ACCEPTED / FROZEN<br>
**决策日期**：2026-08-17<br>
**最后核对代码基线**：上游 commit `06651650f03e3705ec32ce6fb050730b66c43ca8` 与本 ADR 同轮施工树（2026-08-17）
**实施状态**：P1–P4 工程实施已落入当前未提交工作树，自动闭包已通过；P4 最终观感与真实操作采用本文短人工旅程验收，当前不得称 `e2e_verified`，不含 runtime promotion 或标准入口发布。

## 1. 背景与目标

玩家在合成环节有三个高频认知断点：同屏可见配方过少，无法快速确认产物在背包/装备/战备箱中的总持有量，材料不足后离开工作台会丢失采购目标。本决策将“看得多—知道已有—记住要做—到商店买对东西”闭合为一条链，同时保留 AS2 对存档、任务、容器、配方与商店的业务权威。

主要收益是降低重复合成和遗漏第二件双持武器的概率，减少在配方与商店间反复查找，并让进行中任务和个人合成计划共用一套可解释的高亮规则。

## 2. 冻结决策

### P1：密度与持有量

- 配方目录使用独立偏好 `cf7.itemgrid.mode.crafting-recipes`；首次默认为“完整”，与材料档案 `crafting-materials` 首次默认“紧凑”彼此隔离。
- 完整卡保留 78px 信息节奏，紧凑卡为固定每行 10 个的 54px 图标优先网格，使常见五件套按两组对齐；两种模式都保留持有量和已标记角标，切换后同步键盘列数、选中与焦点。
- 每条配方的 `owned` 由 AS2 实时投影。装备总量为背包 + 已穿戴 + 已解锁战备箱前缀；堆叠品额外包含药剂快捷栏；材料/情报使用收集品栏。真实仓库和战备箱未解锁尾部明确排除。
- 完整模式的右栏显示总量及容器拆分；紧凑模式只保留角标，不把密度收益抵消掉。
- 产物名称下方只保留一条元数据行：装备为“需求等级 · 持有位置 · 非默认强化”，堆叠品为“产出数量 · 持有位置”。默认强化 `+1` 不显示，避免玩家误以为合成会额外强化；只有权威 preview 得到 `>1` 时才以青色“强化 +N”强调真实结果。分类 note 中同样不重复默认 `+1`。
- 产物图标保留 68px 检视命中区，但不绘制第二层外框；真实普通/分层图标在其中统一放大到 64px，检视角标独立覆盖右下角。不得让共享 `.kshop-icon` 的 40–42px 默认尺寸重新压小合成产物。

### P2：稳定标记与任务需求

- 12 个 authored 配方文件的 282 条配方全部拥有唯一且不可变的 `recipeId`；产物名称不可作身份，因为存在同产物的多个 occurrence。
- 存档唯一写入面是 `_root._saveExt.procurementPlans = {v:1,revision,recipes:{recipeId:plannedCrafts}}`。`setPlan` 要求 exact `{v,recipeId,plannedCrafts,expectedRevision}`，`plannedCrafts=0..99`，并以 revision OCC 防止迟到写覆盖新状态。
- 右栏以单层 26px 分段控件 `− / 待合成 ×N / +` 直接编辑 0–99 件计划量；中间按钮仍保留“一键标记 1 件 / 清空”的快捷语义，每次增减都走同一 OCC 写入，不在 Web 侧暂存第二份计划真值。
- 合成成功后按实际 `craftCount` 冲减对应标记，归零即删除；preview 失败、commit 失败或未知写不冲减。
- 采购需求只聚合已标记配方和 `_root.tasks_to_do` 中的进行中任务。`submit` 为消耗求和，`contain` 为并发保留需求取最大值，情报始终保留；装备 `#` 继续表示强化门槛，`##` 才表示数量。
- 权威派生区分 `obtainMissing`（真正尚需获得）与 `relocateMissing`（总量足够，但在装备栏/战备箱中需取回），同时携带 `equippedOwned / battleBoxOwned` 与两处各自的最高强化度，并附带去重后的配方/任务原因及 NPCShop/KShop 来源 occurrence。Host/Web 必须闭合总量与来源计数，展示层不得反猜位置。

### P3：商店高亮与受控跳转

- NPCShop 与 KShop catalog 行可选携带 AS2 派生的 `procurement`；Host 和 Web 按封闭 schema 递归验证。只按 exact `itemName` 高亮，锁定、售罄或已达限购的商品仍显示需求原因，但不绕过商店本身的购买权威。
- `obtainMissing>0` 使用金色“需购”引导；仅 `relocateMissing>0` 使用蓝色准备指引，并按权威位置明确显示“合成前需要从战备箱取出”或“合成前需要卸下装备”。单件且两处都有合格装备时优先提示战备箱，避免无谓卸装；确需两处共同提供时分别显示动作与数量。可见文案本身必须表达这是合成前置条件，项目浮层再说明不会自动移动装备；两类状态都更新卡片 aria-label，不依赖颜色传达。
- 配方材料行统一为 48px 双行信息卡，并冻结三类可见语义：堆叠材料只显示紧凑的 `持有/需要`（例如 `0/90`，不再重复“缺 90”）；完全没有装备显示“缺少装备”；只有已经持有但强化不足时才显示 `+当前最高/+要求`。缺口行不再额外显示容易被误解为商店状态的右侧“不足”，只有满足项保留 `✓`。数量使用金色、强化使用青色，缺失/满足另有文字状态与 aria，不能只靠颜色区分；完整采购原因保留在项目 `PanelTooltip` 中，不使用浏览器原生 `title`。
- 材料图标与来源操作统一为 28px 单层方形；材料行直接放置实际图标元素，不再使用另一个有边框的 34px 容器。来源按钮本身就是精确 NPC 头像或 K 标识，不再在按钮内嵌第二层头像边框。常见两个 NPCShop 加一个 KShop 可在单行内完整显示，不挤压材料正文。精确 NPCShop 来源只按 authored `shopId` 查既有 exact manifest；缺失时在同一按钮内保留首字占位，不猜别名。目的地名称与可达状态进入项目浮层和 aria。两类入口都不自动选购、加入购物车、preview 或购买。
- 配方→NPCShop/KShop 比材料档案→NPCShop 更严：必须当前持有“摩托车”或“越野车”基建，自行车不解锁该路由。
- 点击跳转时，Web 直接消费当前权威 preview 的精确采购来源，分别发送 exact `open_procurement_shop` 12 字段或 `open_procurement_kshop` 13 字段路由；两者都不携 `materialSnapshotId`，也不额外请求 `materials/materialDetail`。Host 以最新已采用 preview 建立 transition deadline/settlement lease，AS2 点击时重新证明基建、`recipeId + category + recipeIndex`、配方仍需该前置物，以及 raw/live 商店 catalog 仍为同一 occurrence。配方前置物可以是装备，不要求存在于材料档案；任一 preview、配方或 catalog 漂移都 fail closed 并保留原配方。材料档案自身的普通商店路由仍保持 frozen v2 snapshot/source proof。
- 导航成功后 NPCShop/KShop 只定位并高亮商品；“返回合成配方”使用独立 exact reverse route，恢复 category/recipeIndex/craftCount=1。KShop 返回前先保存既有购物车；普通关闭不伪装成返回。
- 配方材料如果本身是其他配方的产物，AS2 preview 为该材料投影 `craftingSources[]`，每项使用 exact `{category,recipeIndex,recipeId,title}`。来源索引只按 authored `_root.改装分类顺序` 与各分类物理 recipe occurrence 建立；当前 282 条配方形成 93 条嵌套依赖边，其中同分类 73 条、跨分类 20 条、环与自环均为 0。产物名相同的多个 producer 不合并，分别显示为 28px 单层扳手入口并以项目浮层解释目的地。
- 同分类入口不发新请求：先清除本地目录筛选，再在当前权威 snapshot 中同时匹配 `recipeIndex + recipeId + output.name`，选中、滚动并聚焦目标卡后请求 preview。跨分类只复用现有只读 `snapshot {v:1,category}`；回包同时匹配 `category + recipeIndex + recipeId + output.name` 才在同一 panel instance 内切换。任一来源漂移都留在原配方；两条路径都不自动标记、合成或写存档。

### P4：证据分层与完成边界

| 层 | 必须证明 | 不能代签 |
|---|---|---|
| 数据/协议 | 282 个 recipeId 唯一闭包；23 个 Panel command 跨层登记；93 条嵌套 producer occurrence 边可精确复现；请求/回包封闭 schema | 浏览器排版、Flash 行为 |
| AS2 | 持有量范围、标记存档/OCC/冲减、任务聚合、载具门、装备前置物与 live catalog 复证 | WebView2 真实交互 |
| Host | owner/instance、pending/write/reconcile、路由 lease/timeout、AS2 回包后条件 | 玩家可见性 |
| Web harness | 1024×576 / 1366×768 / 1920×1080 密度、焦点、持有量、标记、高亮、跳转/返回 | 真实 Flash↔Host↔WebView2 |
| isolated candidate / 人工实机 | 实际 Flash + WebView2 中可见、可操作的功能旅程；自动候选须额外绑定进程路径/build identity/payload closure | promotion、正式 runtime 或 `standard_entry_verified` |

P4 的工程实施以数据、AS2、Host、Web 四层自动闭包为完成边界；布局观感、真实焦点和跨面板可见结果由维护者执行短人工旅程，避免继续为一次性感知判断扩建 runner。人工旅程完成前只能报告“工程实施完成 / 人工验收待完成”；自动候选若中途受旧坐标或存档条件阻断，只能报告 `candidate_executed / 旅程未闭合`，不得用 mock 补签。

## 3. 权威与数据流

```text
authored recipes + active tasks + live inventories + live shops
                         |
                         v
            AS2 ProcurementPlanService
             |       |             |
             |       |             +--> NPCShop/KShop optional procurement
             |       +----------------> Crafting snapshot/material demand
             +------------------------> _saveExt.procurementPlans (only persisted input)
                         |
                  exact Host validators
                         |
              Web display / explicit intent only
```

Web 不自行扫描任务或背包，Host 不重算缺口，商店不因高亮而改变售价、限购、锁定、余额、容量或提交规则。这使标记系统只增加“意图与解释”，不成为第二个交易权威。

## 4. 风险、成本与缓解

| 风险 | 影响 | 冻结缓解 |
|---|---|---|
| 以产物名保存标记 | 同产物多配方串扰 | 数据层 authored `recipeId`，282 条 exact-set/unique gate |
| 跨容器数量误导 | 把锁定战备箱或仓库误当可用，或不知道该取出还是卸下 | AS2 按真实可访问容量分开 `usable/total`，并投影装备栏/战备箱计数及来源强化上限；UI 区分购买、战备箱取出与卸装 |
| 任务数据过宽 | 历史/已完成任务污染高亮 | 只消费 `_root.tasks_to_do`，保留 submit/contain/情报/装备语义 |
| 商店/合成 snapshot 增大 | 开面板派生成本上升 | 每次 snapshot 只建一次采购来源索引与一次跨容器持有索引，理由上限 64、来源上限 32，无需求行不携带字段；不跨 snapshot 缓存 live 权威 |
| 高亮变成隐式购买 | 玩家失去交易决策 | 只定位/解释，不 synthetic click、不自动 preview/commit |
| 导航时配方或商店已变 | 跳到错误商品 | latest-preview Host lease + AS2 stable tuple/raw-live catalog 双层复证；材料档案普通路由另保留 frozen v2 proof |
| 标记写与合成写竞争 | 缺口回退或重复冲减 | exact owner + 单飞写门 + OCC；未知结果先 reconcile，不重放 |
| 紧凑模式丢失可读性 | 只见图标不知物品 | 完整模式作默认；紧凑保留 tooltip/aria/状态角标 |
| NPC 头像缺失或身份漂移 | 玩家被错误目的地误导 | 只按 AS2 authored `shopId` 查 exact manifest；失败保留 NPC 文字与占位，跳转仍使用原精确元组 |
| 同产物存在多个合成来源 | 静默选首项会把玩家带到错误配方 | 每个 producer occurrence 独立扳手按钮；Host/Web 校验 exact category/index/recipeId/title，重复 occurrence fail closed |
| 嵌套来源在打开后漂移或未来形成环 | 定位错误、返回链混乱或递归自动操作 | 每次导航复证 exact snapshot；只做一跳定位，不递归展开、不自动合成；数据 gate 记录环/自环并要求人工裁决 |
| 旧存档不含标记 | 升级后解析失败 | 缺少/非法 store 按空 v1 读取，不修改旧存档其他字段 |

引入成本主要是 282 个稳定 ID 的长期数据治理、三消费面的封闭 validator，以及需要真实存档条件的 P4 旅程。回报是跨面板的一次权威派生可以同时服务合成、任务和两类商店，后续新商店只需消费同一 `procurement` 投影，不复制缺口算法。

## 5. 明确不做

- 不自动购买、不按需求修改购物车、不绕过锁定/余额/容量/限购。
- 不将仓库或战备箱未解锁部分计入可用持有量。
- 不把已接取以外的任务、任务奖励预测或未来任务纳入高亮。
- 不因 KShop 直达自动加入或修改购物车，不绕过既有结算权威。
- 不将 isolated candidate 证据外推为 runtime promotion、正式入口或发布完成。

## 6. P4 短人工验收

按当前开发入口使用一份具备摩托车或越野车、且至少有一个缺料配方的存档，约 5 分钟完成：

1. 打开合成，确认配方首次为完整模式；切换紧凑后每行恰为 10 个、常见五件套按两组对齐，重开仍保持，且不改变材料档案自己的紧凑偏好。
2. 选择一件已持有产物，确认完整卡与右栏同一行的等级、总数、背包/装备/已解锁战备箱拆分符合存档；锁定战备箱与仓库不计入。普通 `+1` 产物不再重复显示强化；选择会产出更高强化的配方时仍显示“强化 +N”。
3. 用 `+` 把一个缺料配方标记为 2 件，再用 `−` 调回 1 件；关闭重开后数量和缺口仍在。若现场完成一次合成，计划数量应按实际合成数冲减。
4. 确认所有材料卡高度一致：数量缺口只显示 `持有/需要`，无装备显示“缺少装备”，已有但强化不足才显示 `+当前/+要求`；装备只在战备箱时显示“合成前需要从战备箱取出”，只在装备栏时显示“合成前需要卸下装备”，不再显示模糊的“需取回装备”，且悬停项目浮层明确说明这里只是指引、不会自动移动装备。多个金币商店头像与 K 标识均为单层方块，在一行内排列且材料文字不被挤断。悬停使用项目浮层显示准确 NPC 名称而非浏览器原生提示。再分别跳转 NPCShop 与 KShop，确认目标材料以配方原因定位高亮、没有自动选购/加购/购买；两边“返回合成配方”均恢复原配方，KShop 的既有购物车不丢失。
5. 选择一个以另一件合成装备为材料的配方，确认缺失材料旁显示扳手入口；同分类来源点击后不重开面板，直接清除筛选并定位、聚焦目标卡。再验证一个跨分类来源，确认切换分类后仍精确落在目标卡。若有多个来源，每个入口都能通过项目浮层辨认且不会静默选择第一项；全程不自动标记或合成。
6. 若当前有相关进行中任务，确认任务原因与配方原因合并显示；取消标记或完成需求后，相应原因消失。
