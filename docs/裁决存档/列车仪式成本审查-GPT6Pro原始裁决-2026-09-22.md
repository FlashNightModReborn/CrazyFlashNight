# CF7 issue #78｜R1 独立裁决

**结论：有值得消除的重复返工，但证据不足以把现役发布安全链整体判成“流程腐败”。推荐 B′（仅发布入口、复用既有能力、成本受限的前置检查）为主线；A′（两次常规候选窗口的软性攒批）为条件性试行；C 只随主线顺带收敛，不单独立项；不支持无期限 D。原样“每次提交加硬门”的 B 和“强制每日一趟”的 A 均不采纳。**

这份裁决是路线建议，不是施工、发车、部署或看板状态变更授权。

## 证据与复算说明

下文引用均指附件原始文件及行号：**M** 为 `01-列车仪式成本审查-审阅材料.md`；**P** 为 `02-数据备查/runtime-build-reproducibility.md`；**S** 为 `02-数据备查/analyze.py`；**G** 为 `02-数据备查/git-log.txt`。Actions JSON 用文件名和 run ID 定位。

已通读主材料、955 行协议及 issue/Epic 摘录，检查统计脚本，并对所附日志、JSON、CSV 做复算。在隔离副本中重放原 `analyze.py`，得到的统计摘要与附件一致，两份输出 CSV 也逐字节一致。**所以关键问题不是“脚本无法重放”，而是可重放的分类规则和统计解释存在错误。** 历史执行结果以下均按包内记录引用，不冒充本次重新执行或签名验证。

## Q1｜是否值得行动，选择哪条路线？

### 裁决：处理重复返工，不拆安全链

应把成本分为三类：首次正确发布必须支付的信任链成本、可通过准备顺序减少的失败重来、以及现有记录无法量化的人力等待和注意力成本。不能把这三类统称为浪费。

附件足以证明第二类确实存在。例如，任务播报、三维选关、报告恢复的记录都能对应到已经启动的旧云构建，随后因派生闭包问题停用；另一方面，多份记录显示旧 request 已在本地阻断，根本没有产生旧云构建。这证明可以针对“失败发现太晚”优化，但也证明现役前置阻断已经有实际效果。〔P:416–420、470、510、530、585、621〕

| 选项 | 明确结论 | 理由与可计入的收益 |
|---|---|---|
| **B′：发布入口前置检查** | **首选路线，但限于复用现有工具、有限成本验证；不做全提交 hook。** | 至少识别出 3 个派生问题相关旧云 run，合计 15.47 分钟工作流挂钟。存在可提前发现的机会，不等于已证明未来净收益。 |
| **A′：常规窗口软性攒批** | **允许作为条件性试行，不强制每日一趟。** | 同日多次 promotion 很常见，但缺少 ready 时间、紧急程度和可合并性证据。建议先两窗口，而不是直接追求 55% 的账面削减。 |
| **C：提交瘦身** | **不单独立项；将配置一次写对、可合并的记录随 B′顺带处理。** | 显性 tag 指针桶 6 条、发布审计文档桶 2 条，共 8/534＝1.50%；即使减少提交，也不自动减少构建和验收。 |
| **D：保持现状** | **不作为无期限结论；可以作为暂缓工程投入的限时状态。** | 现有数据不能证明人力成本不可接受，也不能证明已经可接受。已确认的反复失败不应被错误统计掩盖。 |

这里的“首选”是基于风险和证据的优先序，不是已经证明某组合具有最高货币收益。78 个云构建的工作流挂钟总和仅为 **385.4 分钟，约 6.42 小时**；不能把它夸成足以支持大型治理工程的已量化损失。177 个 Audit run 合计 486.8 分钟，但它们也不能直接摊成 63 趟列车各自必付的同一笔费用。〔`cloud-builder-runs.json`、`audit-runs.json`；S:91–110〕

**安全边界全部保留：**双 signer／双 faultDomain、不可变 source tag 与远端 ruleset、strict v2 production receipt、唯一 promotion writer 的原子写入、独立事后 Audit，以及禁止 v2→v1 降级。现有小包下载、CAS 复用、身份批量计算、promotion 校验去重，不再重复认领为新收益。〔M:62–67、94；P:17–25、138、199–217〕

Epic 本身要求“拆掉经常性成本”，不允许只增加流程。因而 B′若必须扩成新的完整审计系统、额外人工审批链或精细台账，就超出本裁决支持的范围。〔`issue-78-与Epic26-原文.md`:19〕

## Q2｜40% 与 23.8% 的分歧，是否影响立项正当性？

**影响立项理由的强度，但不取消调查与小幅优化的正当性。更重要的是：23.8% 也不是已经清洗干净的窄口径。**

按包内同一 534 条窗口日志重算，宽口径是 **218/534＝40.82%**；原脚本窄口径是 **127/534＝23.78%**。主材料引用的约 210/522 旧快照没有作为独立快照附入，因此不能核验其旧统计时刻和组成，只能以当前所附日志重算。〔M:35–38；G；S:33–43〕

窄口径正则只要遇到“冻结”就会命中，至少存在两条明确反例：

- `b994d87b0545` 是佣兵装备托管功能，“冻结”指背包装备的业务语义，却被归入 `ceremony-freeze-derive`。〔G:490〕
- `96c7be5f7a69` 是 NativeHud 功能迁移，“冻结”出现在“面板打开期间会冻结、关闭后显示”的交互说明中，也被计作仪式。〔G:530；P:873〕

此外，`c07760a977db`、`e434434596e1`、`678cb32cdea1` 等“冻结协议／架构／方案”的文档提交也被同一规则收入。这些词不能证明发生过发布冻结。由于没有逐提交 diff，本次不把标题人工修正包装成完整真值分类。〔G:50、354、362、442；S:39–40〕

仅把上述两条明确业务反例从仪式桶排除，比例就会变为 **125/534＝23.41%**；这只是反证，不是最终校准值。它已经足以推翻“真实值必在 23.8%—40% 之间”的下界说法。

另外，即便暂时接受 127 的原始计数，其中 **63 条、约 49.6% 是部署落盘**；剩下 64 条也包含必要的首次冻结和真实派生更新，不是 64 条可删除浪费。提交数更不等于人时、机器费用或注意力消耗。把其余 407 条全部放在 `business-or-other`，也无法证明仪式是“最大的单类非业务开销”。〔M:40；`commit-classification.csv`〕

因此，立项理由应改写为：

> **现有记录显示若干重复出现、可能前移发现的发布准备失败；需要在不削弱信任链的前提下减少失败重来，而不是因为“约四成提交是仪式”就认定四成产能被浪费。**

## Q3｜攒批有没有客观节奏建议？

### 统计支持“值得试”，不支持“每日一次最优”

63 次 consensus 变更、28 个发车日及其日分布可以复算；22/28＝**78.6%** 的发车日有至少两次变更。但主材料已说明 63 包含同一业务的 v1→v2 重部署：9 月 5 日至少有“焦点诊断”和“存盘／领奖反馈”两组。它们不应直接当成可互相合并的独立业务批次。〔M:25–26；`train-inventory.csv`；P:679–685、702–704〕

以下只是在“当日所有变更均可合并、没有紧急豁免、无需追加回归”的理想假设下计算：

| 理想日上限 | 按原 63 次计数 | 仅扣除已知两次同业务重部署后 |
|---|---:|---:|
| 每日一趟 | 63→28，少 35 次，55.6% | 61→28，少 33 次，54.1% |
| 每日两趟 | 63→50，少 13 次，20.6% | 61→50，少 11 次，18.0% |

61 不是已经完整去重的业务列车总数，扣除两次也不表示那两次重部署本身不必要。表中数字仅用于剥离“返工”和“独立发车”混计的影响；**都不是可兑现节省量。**

主材料的 `35×(云5分钟＋尾部16分钟)` 不能成立为人时或同一条关键路径的节省：所谓 16 分钟从云 dispatch 开始，已经包含云构建，不能再加一次云时长；它也没有测量人是否一直盯着屏幕。云任务资源占用和发布周转时间可以分别报告，但不能相加包装成总收益。〔M:20、58、74；S:135–145〕

即使进一步假设每少一次 promotion 恰好少一次平均云构建，35 次也只是约 **173 分钟云工作流挂钟**；去除已知重部署后的 33 次约为 **163 分钟**。这两项仍没有扣紧急豁免、合并回归和延期成本，也不是账单金额。

### 建议的初始节奏：每天两个常规候选窗口，紧急随发

**常规发布：**窗口与维护者、测试员共同可用时段对齐；没有 ready 候选就不发空车。只合并已具备现有发布资格、兼容且能解释回退边界的变更，不为等待未完成项目拖住已经 ready 的项目。窗口只是发车机会，不是必须一天发两趟，也不是要求把不兼容变更合成一趟。

**紧急豁免：**正在造成存档／资产损坏、安全风险、核心流程不可用，或者存在早于下一窗口的既有明确现场诊断／验收时限，可以随发。仅“代码刚写完”“想同步源码与部署”不构成紧急；协议本来就允许 `source-ahead`。豁免只改变时机，不豁免任何正式门或既有授权。〔P:46、225–239〕

**批次边界：**共用一次发布不等于共用一个未经区分的验收结论；各专项未完成的验收仍保持未完成。包内 K 店批量领取与多包开礼包、SafeExit 与 ArchiveTask 已有组合发布记录，所以“每趟只能一个业务”不是不可动协议。需要保留的是清晰的身份、范围和验收边界。〔P:721–727〕

我建议把“非紧急 ready 项原则上不因攒批超过 24 小时”作为试行约束；**两窗口、24 小时都是本次建议的政策参数，不是日志推导出的最优值**。附件没有共同值守时段、ready 时刻、紧急标记或回归工作量，不能据此指定某个钟点或承诺人验成本下降。

## Q4｜冻结前派生门的净收益是否为正？

### 先否定问题中的前提：没有已测得的“37% 浪费主因分布”

原脚本把“云 run 的 source SHA 没有匹配正文里特定写法的 `release source`”直接当成“废弃源”。**未被正则识别不是未部署。**〔S:80、91–99〕

对原来被列为“浪费”的 29 个 run，完成下列有明确锚点的保守核对：

| 在原 29 个 run 中的类型 | 数量 | 工作流挂钟 | 应如何解释 |
|---|---:|---:|---|
| 正文记载为最终采用，但正则漏识别 | 3 | 14.65 分钟 | 不能计为废弃构建。 |
| 正文明确记载曾本机 promotion，随后同业务重部署 | 2 | 9.55 分钟 | 属于实际使用过的中间部署，不是“从未使用”。 |
| 本次逐条对应到明确未部署／退役记录的子集 | 6 | 30.47 分钟 | 确有未用于部署的构建；不代表全部属于可避免派生错误。 |
| 其余本次不作废弃认定 | 18 | 86.80 分钟 | 保留未分类，不能静默并入浪费或成功采用。 |
| 合计 | 29 | 141.47 分钟 | 是原正则未匹配集合，不是已证明浪费总额。 |

前三个漏识别的最终采用 run 是 `35672805431`（9 月 22 日世界光照）、`33255138023`（8 月 29 日启动前门）、`33220240979`（8 月 29 日关卡转场复活）。正文分别用了“最终冻结源”“release source commit”“该 commit 是最终 release source”等不同写法。〔P:943–951、757–760、769–772〕

两个中间本机 promotion 是 `33957634090` 和 `33945207841`。文档明确记载 v1 曾本机部署，只是没有分别推到 main，不能改写为 `NOT_DEPLOYED`。〔P:685、704〕

六个明确未部署记录对应 `34745615347`、`34702454701`、`34641981631`、`34455545619`、`34376555533`、`34097840213`。这里既有派生问题，也有样式门和测试修复。**6/78 只是已核对的一个子集，不是把真实浪费率重新定为 7.7%。**〔P:371、387、416–420、470、510、595–604〕

同样，世界光照 v1、理发店早期 request、地图撤退早期 request 等记录都明确“未 dispatch 云构建”。它们可以贡献重冻结成本，却不能贡献旧云构建成本；只改 policy 的情况又可能复用本地 CAS，不能对称追加一次 114.8 秒本地构建。〔P:951、530、585、138〕

因此，**“37% 云浪费”“派生占其一半”“B 能把它降到18%”均不具备可接受的事件级依据。** 包内没有可用于这个推断的完整首因分布；全史词频也不能代替本窗口的逐 run 归因。

### 原样 B 的净正收益不能确认；全提交 hook 不采纳

能明确识别为派生闭包问题的三个旧 run 是：

| 事件 | 旧 run | 挂钟 | 原文锚点 |
|---|---:|---:|---|
| 报告恢复的图标／材料／商店闭包 | 34641981631 | 5.05 分钟 | P:416–420 |
| 任务播报的材料与商店来源 | 34455545619 | 5.10 分钟 | P:470 |
| 三维选关合并上游后的头像来源 | 34376555533 | 5.32 分钟 | P:510 |

合计 **928 秒＝15.47 分钟**。这证明存在前移检查的候选机会，不证明未来一定重现，也不证明所提检查一定能够全部拦住。

仅作预算算术：假设三个机会全部被消除、把不同机器的挂钟暂按等权比较、暂不计实现维护及误报成本，那么新增检查平均耗时的收支点为：

**平均新增检查秒数 < 928 ÷ 实际检查次数。**

放到 534 次普通提交上，收支点只有 **1.74 秒／次**；若举例只检查 63 次发布入口，则是 **14.73 秒／次**。注意 63 是 promotion 代理数，不是实测冻结尝试数，真实入口次数必须另按既有记录确定。这些值只是对已识别三个机会的条件性算术，不是实际费用 ROI，更不是整个 B 的总收益上限。

“四域 hash 已秒级”不能证明完整派生检查也秒级；“字节幂等”只表示重复运行不制造内容变化，绝不等于运行成本近零。检查耗时、误报、修复人时、当前是否还会重现这些历史问题，都没有实测，因此不能裁定原 B 净收益为正。〔M:81；P:42、76；`candidate-stage-seconds.json`〕

### 支持的是 B′：检查点少、复用现役语义，不另造完整门

**冻结前：**把派生一致性和“本轮 sourceRef 配置已进入待冻结源码”纳入已有发布准备入口；不要拦普通业务提交、方案文档或合法 `source-ahead`。派生器若只因时间戳制造 diff，应按既有协议修门，不能要求维护者反复提交时间漂移。〔P:46、64–76〕

**dispatch 前：**复用现有的本地 preflight 优先顺序和 source tag 精确解析检查。冻结前只能检查配置准备，不能冒称已验证一个尚不存在的远端 tag；创建 tag 后仍须由现役 helper 验证 tag→source commit。〔P:140、146〕

**最终证明：**production policy、双构建证明与原子 promotion 全部保留。前置 PASS 不代替最终 receipt；不得为“更稳妥”给每次发布再加一遍无独立需求的完整 `promote -VerifyOnly`，协议已经明确避免这种重复验证。〔P:199–215〕

B′的停止条件也应明确：若它变成昂贵全量生成、维护第二套依赖清单、反复误拦合法开发，或无法通过少量既有发布记录显示减少了重复失败，就不升级成普遍硬门。地图工作台“policy 已 40/40、后因测试等待问题再冻结”和 9 月 5 日“首次部署后上游又变化”，本来就不是一个派生自检能够消灭的全部问题。〔P:604、702〕

## Q5｜若选择全部暂不行动，什么阈值触发复审？

**D 只能是有边界的预算选择，不能解释为“成本已证明可接受”。**以下是本裁决建议的管理阈值，不是从附件估计出的自然临界点；触发只意味着复审，不自动授权施工或减门。

| 观察项 | 建议复审阈值 | 触发后的方向 |
|---|---|---|
| 已确认可提前发现的同类失败 | 14 天内至少 2 次；或最近 20 个云 run 中至少 3 个可明确归因为此类失败的未采用构建 | 复审对应发布入口 B′；未映射 run 保留未知，不能当作“无返工”。 |
| 纠偏后的仪式提交代理 | 连续两个完整 ISO 周均 ≥30%，且每周总提交 ≥30 | 拆分部署、首次准备、重复修正和业务误收；不能直接减安全门。 |
| 真正可攒批的分开发车 | 14 天内至少 3 天，出现至少两项发布前已经 ready、非紧急且回退边界兼容的独立发车 | 复审 A′；不把同业务返工或现场止血混进去。 |
| 周转时间异常 | 至少 10 条能一一对应的云 run→promotion 记录，P75 超过 30 分钟 | 定位队列、验证、操作编排的变化；仍不将挂钟冒充人的持续注意力。 |

按第一条，包内 9 月上中旬已至少出现可复核的派生失配重复事件。所以无限期“全不动”不能以“没有具体问题”为理由；最多是暂缓投入，并接受复审。

时间上建议 D 最长保留一个 **14 天观察周期**；以包内 UTC+8 日期 2026-09-22 为起点，复审节点为 **2026-10-06**。复审只复用现有 request／worker／promotion 阶段记录和 issue 关闭说明，不为本议题新建精细台账或每次人工工时报表。阶段 sidecar 在协议中已有定义，但其实际记录没有附入本包，本次未读取。〔P:123；`issue-78-与Epic26-原文.md`:19〕

正式门的真实失败仍按原协议处置，不等待成本阈值，也不通过重跑或豁免把红灯洗掉。
