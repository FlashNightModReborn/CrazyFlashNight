## 总裁决

**本轮证据支持把调查重心移到“提交路径早退、存储后端既存状态、当前对象图”上，但不足以改判为“AMF0 编码失败”。** 尤其不能把“循环引用、函数、类实例、embedded NUL”直接列为会使 FP20 原生 `flush()` 返回 `false` 的编码杀手。

同时，本轮排除链仍有两处必须撤回的过度结论：

* **“PML 子串零命中”尚未严格证明八次调用期间零文件系统事件。** 包内的窗口闭合方法把字符串出现次数当成了事件次数，还没有完成时间、PID 与操作类型的对应。
* **即使真正证明调用期间零 I/O，也只能排除“这几次调用中发生的、应被捕获的文件操作失败”，不能排除此前初始化失败、缓存的不可写状态，或文件系统调用之前的用户态拒绝。**

下面 Q1 按你要求接受强前提作条件裁决；Q5 再攻击这些前提的实际证明力度。本文没有运行 FP20，也没有独立重放 PML：附件中只有相关报告，没有原始 PML、旧 SOL、注入 JSON、解析器实现或播放器二进制。源码定位均指本包 `code/SaveManager.as`。

## Q1：哪些机制可以产生原生 Boolean false，且调用期间零 I/O？

### 1. 先把“已知语义”与“候选实现机制”分开

Adobe 的 AS2 文档明确规定：用户禁止当前域或全部域存储时，`flush()` 可以直接返回 `false`；允许存储但需要申请更多空间时，返回 `"pending"`；其他无法保存的情况也归入 `false`。**这个公共接口并不公开内部每个失败分支，更没有规定所有失败都必须先尝试打开文件。** ([Open Flash][1])

因此，可以列出覆盖本案观测的机制分类，但不能把下面所有候选都冒充“已经确认存在于该 FP20 构建中的具体返回分支”。

以下排序是**调查优先级**，不是可由当前材料估出的概率。

| 优先级 | 机制                                              | 为什么与零 I/O 相容                    | 最有区分度的反证或观测                                                            |
| --- | ----------------------------------------------- | ------------------------------- | ---------------------------------------------------------------------- |
| 1   | **有效存储策略直接否决**：按域、全局拒绝，或实际生效的硬限制                | 策略可能已经在内存中，无须每次读取配置             | 同一进程、同一 SWF 存储上下文中，独立 SO 写入小 nonce 成功，可否定“该上下文一概禁止写入”；不能因此排除大小相关限制     |
| 1   | **SO／本地存储后端此前初始化失败，后续沿用不可用状态**                  | 失败可以发生在捕获前；后续调用只检查已有状态          | 从进程创建、首次 SO 取得开始观察；同一 SO 的可用状态与首次失败之间建立时间关系。若能证明后端此前正常建立且状态未失效，此分支明显削弱 |
| 2   | **目标 SO 或其存储身份的特定问题**：目标上下文、缓存状态、路径派生或原生对象状态不成立 | 可能在路径构造、对象状态检查阶段结束，尚未发出文件操作     | 同上下文中，小载荷与完整载荷均能存到新 SO，唯独原目标失败，支持目标相关问题；但还需排除原目标独有残留数据                 |
| 2   | **载荷遍历、编码或资源预检失败，并被原生实现转成 false**               | 遍历／分配／编码可以先于文件提交；但具体顺序和返回方式需要验证 | 在同一环境、同一诊断 SO 中，故障跟随某个载荷子集稳定出现；最小化后同时确认“正常返回 false、无异常、无崩溃、无 I/O”      |
| 3   | **用户态兼容层、注入或 API 包装提前拒绝**                       | 被截断的调用未必进入 ProcMon 能观察的文件系统操作   | 必须绑定故障 Flash PID 的模块、调用栈或具体拦截行为；仅全系统出现 `apphelp.dll`、SDB 不够            |
| 4   | **特定播放器构建或运行时缺陷**：状态损坏、内部错误等                    | 内部错误处理可以直接结束                    | 固定载荷、上下文和输入顺序，交叉比较精确相同二进制；缺陷随构建或可复现的状态演变迁移，才有辨识力                       |

第二至第四类目前是**待验证的机制假设**。不能为了填满清单，给它们编造 FP20 内部标志位、固定阈值或确定的返回路径。

### 2. 本轮最容易漏掉的是“此前失败，现在早退”

下面这条链**并未被现有证据排除**：

```text
进程启动／首次取得 SO
    → 存储初始化遇到问题
    → 原生层保留失败或不可用状态
    → 游戏通过 launcher JSON 正常载入
    → 后续八次 flush 检查既存状态，直接 false
```

它同时解释“游戏可玩”“设置面板可打开”“后续调用零 I/O”。这不是断言 FP20 一定这样实现，而是说明：**你们现在没有观测覆盖能够否定它。**

本包的 protocol 2 快路径尤其重要：

* `1398–1416`：`snapshot` 分支缓存 launcher 快照后直接返回；
* `1440–1442`：`empty` 分支同样直接返回；
* 上述两处都没有取得原生 SO。

所以，“加载成功”没有替原生 SO 初始化作证。`loadFromMydata()` 里的“游戏本地读取成功”也是业务消息，不是原生文件读取证明，见 `2521–2564`。

### 3. 哪些东西不能混进这份 false 清单？

**`getLocal()` 返回 null、原生调用抛异常、播放器崩溃，以及 `"pending"` 后收到失败回调，是不同的观测结果。** 例如文档中的“舞台太小，无法显示扩容对话框”，对应的是先返回 `"pending"` 再报告失败；不能拿来解释已经确认的直接 Boolean `false`。本地内容也不能机械套用浏览器第三方存储禁令。([Open Flash][1])

你们代码在 `3501–3503` 调用后，才会于 `3517–3520` 输出 `result=...`。在执行代码与包内代码一致的前提下，**一个直接逸出的编码异常，不会自然产生这条“原生结果为 false”的日志。** 候选必须解释“为什么变成正常返回值”，不能只解释“为什么可能出错”。

**条件排序结论：H2 与“此前后端初始化／目标状态失败”处于第一梯队；H1 保留，但应改成“当前对象图或资源边界”，而不是以孤立代理项、循环引用为中心。H3 尚缺进程级证据；H4 不能靠 git 跟踪状态收尾。**

## Q2：AMF0“编码杀手”清单应如何改写？

### 1. 逐项裁决

| 候选                   | 有依据的判断                                                    | 能否据此断言本案 FP20 返回 false？            |
| -------------------- | --------------------------------------------------------- | ---------------------------------- |
| **普通循环引用／共享子对象**     | AMF0 的对象引用机制就是用于表达共享身份和避免循环展开                             | **不能。应从通用杀手清单删除**                  |
| **函数值**              | Ruffle 的 AVM1 兼容实现直接跳过对象属性中的函数，而不是让整个对象编码失败               | **不能。省略属性与提交失败不是一回事**              |
| **普通类实例**            | 未注册类型可以按匿名对象编码；注册类型可带类名编码                                 | **不能。类实例身份本身不是禁区**                 |
| **MovieClip 等显示对象**  | 不能按普通可持久化显示对象保存；兼容实现使用 `undefined`                        | **不能。不能因遇到显示对象便推断整次 flush false**  |
| **孤立 UTF-16 代理项**    | 不是有效 Unicode 标量，严格 UTF-8 编码无法原样表示；具体编码器可能替换、丢弃、采用非标准行为或报错 | **尚无该 FP20 构建的直接 false 证据**        |
| **超深嵌套／异常原型链／超大对象图** | 应调查实现资源边界，而非 AMF0 类型是否合法                                  | **有调查价值，但异常、卡死、崩溃和 false 必须分开实测**  |
| **长字符串**             | 字符串值超过短字符串容量可使用 Long String；属性名、类名仍有各自长度字段约束              | **“超过 64KB 必死”不成立；超长键名更值得单列测试**    |
| **embedded NUL**     | NUL 是合法字符；AMF 字符串按长度编码，不是 C 字符串终止协议                       | **不是格式层面的通用杀手；FP20 是否有具体实现缺陷仍需实测** |

循环、类实例、长字符串及长度编码的判断来自 Adobe AMF0 规范；函数、显示对象的具体降级处理来自兼容实现，**后者不能充当 FP20 二进制行为的最终证明**。([SRS][2])

这里还要严格区分：

> **“不能完整保存这个值的语义” ≠ “不能编码包含这个值的对象” ≠ “flush 正常返回 false”。**

这是 H1 当前最大的概念混用。

### 2. 孤立代理项：值得查，但不能靠“严格编码器报错”定罪

严格 UTF-8 不允许把 `U+D800–U+DFFF` 当作独立字符编码；但 `U+FFFD` 本身是合法字符，不是非法编码。**历史上出现过 FFFD，只说明某处可能发生过替换或已有该字符，不能推出当前存在孤立代理项。** ([RFC 编辑器][3])

另一方面，JSON 的转义语法可以容纳孤立代理项；RFC 8259 特别提醒过这类数据的互操作风险。因此，“JSON 能解析”和“解析后字符串是有效 Unicode 标量序列”也不是同一个条件。([RFC 编辑器][4])

但要把它升级成这次故障的原因，仍须接上完整证据链：

```text
当前真实载荷中确有该 code unit
→ 本案播放器对此不能正常编码
→ 失败被转为 Boolean false
→ 删除／替换这一处后故障消失
```

目前四环都没有完整闭合。

**构造原生测试时，不要仅相信源代码里的转义写法。** 应运行时构造，并记录长度与 `charCodeAt()`：

```actionscript
var loneHigh:String = String.fromCharCode(0xD800);
var embeddedNul:String = "A" + String.fromCharCode(0) + "B";

// 先确认 loneHigh.length == 1、charCodeAt(0) == 0xD800。
// 再分别测试字符串值、属性名；不要把两者合成一个样本。
```

这个提醒不是抽象顾虑。我检查到 Ruffle 的一个现成 AMF0 测试虽然将字段命名为 `p_str_unpaired_surrogate`，其预期输出却是 `%5CuD83D`，网络字节也包含 `5C 75 44 38 33 44`——**那是反斜杠加字母的文本，不是真正孤立代理项的测试证据。** 不能直接引用该用例给 FP20 下结论。

### 3. 环和“活性对象”必须拆开

普通的数据环不是重点。真正应查的是：

**持久化字段是否意外连接到了远超预期的运行时对象图。**

例如 `mydata.ext` 指向 `_root._saveExt`，而其中某个字段又连接了服务对象、缓存、其他运行时状态。即使引用机制避免了重复展开，**首次遍历的不同节点、属性、字符串和原型相关行为**仍可能超出预算。

本包直接支持这个调查方向：

* `2378`：直接挂入 `_root.killStats`；
* `2388–2394`：同伴、技能表、基建均包含直接引用；
* `2399–2410`：任务、宠物、商城直接引用；
* `2425`：直接挂入 `_root._saveExt`；
* `2359–2368`：依赖多个未附实现的 `toObject()`。

所以 `packGameState()` 不是“已证明只产出普通、封闭、可持久化树”的边界。

另外，**不能套用 `JSON.stringify` 的直觉，认定 AMF 编码必然执行 getter，再吞异常返回 false。** Ruffle 的兼容实现恰恰注明 getter 不求值、写为 `undefined`。这不足以证明所有 FP20 情形，但足以否决把“getter 抛异常”当成无须验证的既定路径。

**Q2 最终裁决：目前没有一项已被证明是“本案 FP20 必然直接 false”的杀手值。优先检查对象图规模、意外引用和超长键名；Unicode 做精确 code-unit 审计，但不要先全量清洗存档。**

## Q3：不编译 SWF，严格 AMF0 重编码能验证到什么程度？

**能做有效的离线排雷，不能替代“当前 AVM1 内存对象能否由该 FP20 编码”的验证。**

### 1. 你们持有的 JSON，不是实际 flush 载荷

按本包代码，真正关系是：

```text
注入 JSON
  → 解析、迁移、unpack、业务副作用
  → _root 运行时状态
  → packGameState()
  → 覆盖原 so.data 的部分字段
  → flush 整个 so.data
```

关键不是只有“JSON 丢失类型”：

**第一，`mydata` 只是 SO 的一个字段。** `1211–1226` 取得既有 `so.data`，覆盖 `test` 和七个顶层镜像，只删除 `_deleted`；没有清理其他旧顶层键。因此潜在问题可能位于：

> **“不在 launcher 当前快照里，却仍在原生 SO 内存中的残留字段”。**

**第二，加载后还会执行副作用。** `2554–2560` 调用任务、佣兵等业务逻辑。离线重新编码注入前 JSON，没有覆盖这些变化。

**第三，JSON 不携带完整对象身份、原型及属性特征；组包又会重新引入共享引用。** 将所有内容再 JSON 往返一次，不是无损取得原载荷，而是生成了另一份实验样本。

因此：

```text
自制编码器能编码 JSON    ⇏    FP20 能编码实际 so.data
自制编码器拒绝 JSON      ⇏    FP20 会正常返回 false
```

### 2. 现在就能做的离线工作

建议把现有两套解析器用于下面三个交付，而不是做一个笼统的“AMF0 编码通过”绿灯。

**A．原始字节与字符串审计。** 对旧 SOL、实际发送的 JSON 分别记录哈希；区分原始字节解码与 JSON 转义解码，报告孤立代理项、NUL、FFFD、最长键名、最长字符串的**完整路径与 code unit／字节证据**。不得默认替换坏字符后再宣称原样通过。

**B．类型和图结构审计。** SOL 解析成保留对象 ID、引用目标、AMF 类型、键名与数组信息的中间表示，再检查转 JSON 时发生了什么。重点看数组／对象互换、别名展开、数字键、空数组、重复键与转换后的体积变化。JSON 重复键和超范围数字本身就有实现差异风险。([RFC 编辑器][4])

**C．资源预算报告。** 给出节点数、边数、最大深度、属性数、字符串总字节、最长属性名、数组长度及实际元素数。扫描器使用显式栈和预算上限，避免审计工具先递归溢出或按巨大稀疏数组长度展开。

这能回答“输入含哪些风险”“你们的格式转换是否自洽”，但仍不能覆盖原生策略、后端状态、当前堆资源，以及真实导出器生成的对象图。

### 3. 真正逼近原生编码问题，需要什么入口？

不编译 SWF，并不意味着不能调用原生能力；但必须**已经有能在目标 AVM1 上下文执行诊断的入口**，或使用受控的原生调试。包内没有证明 XMLSocket 支持任意表达式执行，不能把通信通道擅自当成调试控制台。

已有合适入口时，`so.getSize()` 是值得增加的观测：Adobe 文档说明它会遍历数据属性估算大小，且可能耗时。**正常返回可削弱部分遍历失败假设，但文档没有保证它与 flush 走完全相同的编码路径，不能把它当成充分证明。** ([Open Flash][1])

进一步仍应做受控载荷比较：

| 对照                   | 作用                   |
| -------------------- | -------------------- |
| 同上下文、独立诊断 SO、小 nonce | 检验最基本的原生提交能力         |
| 同一诊断 SO、完整实际载荷       | 检查失败是否跟随载荷；控制大小与配额影响 |
| 与已经观察到的原目标失败比较       | 区分载荷相关与目标 SO／身份相关    |

这里有两个实施陷阱：

**不要写 `tmp.data = payload`。** Adobe 明确说明这种赋值会被忽略；需要写入其数据属性。([Open Flash][1])

**不要把顶层复制称为对象图完全保真。** 若某个节点反向引用原 `so.data`，简单逐键复制会让该引用仍指向原根，而不是新根；深克隆、JSON 克隆又会改变其他身份或类型。诊断必须记录所采用的复制语义。

只持有当前列出的三类离线材料、又没有原生执行或观测入口时，**能交付候选证据和最小测试输入，不能交付“当前内存对象已被证明无法编码”的裁定。**

## Q4：E-a／E-b／E-c 如何安排？玩家只能再做一个动作选什么？

**选受控的 E-a：真正空槽的新角色首存。** 它比一次 git 状态或 Layers 查询提供更直接的功能区分，但你们当前写法需要收紧。

### E-a：能区分“是否依赖旧档”，不能直接区分“JSON 是否致病”

在 `1440–1442` 的 `decision == "empty"` 分支，确实不会采用完整旧档快照。因此真正空槽可以避开**旧角色存档快照的恢复**。

但“新角色完全不经过 launcher JSON”说得过头了：

* 新建仍可走 protocol 2 的控制消息；
* `2099–2108` 接受外部 `initialState`；
* 后续仍使用同一套导出器、设置及存储路径。

更具体的污染风险是：`resetPerCharacterMemory()` 虽清理大量角色状态，**没有在该函数中重建 `_root.键值设定`**，而 `2345` 又把它放进新档。同一进程里先加载旧角色再建角，并不是最干净的实验。

因此，本次 E-a 应满足：

> **同一正常启动入口、新进程、真正没有原生 SOL／shadow／恢复来源的空槽、简单 ASCII 名称，并核对实际 `decision=empty` 与原生首存结果。**

不要为了制造空槽先删除任何有价值的角色。上述条件由开发侧准备和核对，不让玩家反复清配置、切模式。

还有一个源码边界：`2064–2077` 区分了旧时间轴入口和 Web 建角流程；“Web 应调用 `flushNow()`”出现在约定中，**实际 CharacterCreationService 调用方没有附在本包里**。必须用此次操作的实际日志证明进入了提交，不以“角色出现在界面上”替代。

结果解释应写成：

| E-a 结果                         | 可以支持什么                                    | 不能推出什么               |
| ------------------------------ | ----------------------------------------- | -------------------- |
| 新角色原生首存并实际落盘成功                 | 故障更依赖旧角色数据、体积、原目标 SO 或恢复路径；“所有存储都被禁止”明显削弱 | 不能单独证明 JSON 往返致病     |
| 新角色也正常返回 false，且结构化捕获确认无相关 I/O | 共用环境、后端、运行时或共用导出逻辑的优先级上升                  | 不能排除所有新旧角色共用的坏字段／导出器 |
| 未观察到原生首存调用                     | 实验没有命中问题                                  | 不能归入“新档也失败”          |
| UI 显示成功，或仅同进程重读成功              | 只有业务／内存层成功迹象                              | 不能证明 SOL 已持久化        |

### E-b：保留，但从“git status”升级成“执行身份核对”

`git ls-files` 的 `H` 表示一种被跟踪文件状态，**不是玩家当前执行文件的内容哈希证明**。干净工作树也只相对于当地提交，不保证与开发机是同一提交。([Git][5])

应直接核对：实际 Flash 进程映像路径、命令行、播放器字节哈希、主 SWF／asLoader 等执行模块哈希、运行时版本及发布构建。**AS 源码一致、EXE 被跟踪、正在执行的字节码一致，是三件事。**

这属于开发侧便宜的身份核对，不值得独占玩家仅剩的一次功能实验。

### E-c：Layers 不是 H3 的“收尾”

本轮日志 `628` 已经记录一个 Layers 项，但目标是：

```text
resources\CRAZYFLASHER7MercenaryEmpire.exe
raw=~ HIGHDPIAWARE
```

它不是日志 `633` 所指的 `Adobe Flash Player 20.exe`。不能拿启动入口的 DPI 兼容项证明 Flash 的存盘调用被拦截。

同样，Layers 没有条目，也不足以排除其他兼容数据库或用户态注入。**先绑定 Flash PID 和实际模块，再决定查哪个机制；不要从“装了腾讯软件”跳到“腾讯拦了 flush”。**

**实际顺序：开发侧先结构化复核现有 PML、核对执行身份；玩家唯一动作留给 E-a；根据其结果决定是否深入 H3。**

## Q5：再次攻击整个假设框架

### 攻击一：“零 I/O”的证明方式尚未闭合

`evidence/捕获分析记录.md` 有三处不能成立为严格推导：

**`launcher.log` 子串出现 35 次，不等于 35 条写盘事件，更不等于恰好写入八次 flush 日志的那批事件。**

**MP3 路径出现六次，不直接证明六次属于目标 Flash PID、落在指定时间段的文件读取。**

**seed-shadow 路径缺席，不能单凭缺席把捕获起点定位到 17:09:00.110 之后。** 你们尚未排除捕获、保留、保存或解析层面的其他原因，且最后又用这个推断证明捕获覆盖，形成了相互依赖。

这不是说 PML 中一定有漏掉的 SOL 事件，而是说：**报告目前证实的是二进制扫描结果，还不是结构化事件集合的完备性。**

ProcMon 本身提供操作级事件、进程身份和调用栈，原始日志也可重新加载。应由开发侧打开现有 PML，导出带时间、PID/TID、操作、路径和结果的记录，核对实际保留范围与过滤／丢弃设置；不必先让玩家再抓一次。([Microsoft Learn][6])

另外，“没有相关文件操作”与“整个进程没有文件操作”也必须分开；你们自己已报告流式音频读取。

### 攻击二：“零 I/O → 编码先失败”没有逻辑必然性

即使 Q1 强前提成立，仍有：

```text
先检查策略 → false
先检查后端状态 → false
先构造／验证目标身份 → false
先编码 → false
用户态存储调用被提前拒绝 → false
```

**观测只能定位到“没有出现所监控的提交活动”，不能替你决定内部顺序。**

因此，H1 中“flush 先完整 AMF0 编码、随后才开文件”目前仍是需要验证的实现假设。也不能反向声称八次失败已经完成了全部编码成本。

### 攻击三：V5 的“系统 Flash 从未安装、没有配置入口”被包内材料自己削弱

SysWOW64 截图可见 `FlashAuthor.cfg`、`FlashInstall32.log`、`flashplayer.xpt` 和 `FlashPlayerTrust`；System32 截图也有 `FlashInstall64.log`、`FlashPlayerTrust`。这至少证明存在旧组件／配置痕迹，不能称为从未有过 Flash 痕迹的干净环境。 

更直接的是当前会话日志 `632`：

```text
[FlashTrust] Already trusted (not leased):
...\#Security\FlashPlayerTrust\cf7me.cfg
```

**你们已经有明确的用户级 Flash 配置路径，却在 H2 中写“缺少配置入口”。这句话应撤回。**

不过，Trust 文件存在不等于禁止存储，更不能据此认定它是根因；旧插件文件存在也不等于独立播放器加载了它们。正确动作是记录实际配置与上下文，而不是删除这些文件。

### 攻击四：设置面板健康，不等于目标 SO 健康

V7 最多证明某一设置界面能展示某个上下文的限额和用量。它不能单独证明：

**目标 SO 与该界面使用完全相同的存储身份；目标对象的写入后端正常；用量是在失败后新算而不是已有状态；当前完整载荷只需要旧文件那 37KB。**

你们的 `getSO()` 只有：

```actionscript
SharedObject.getLocal(_root.savePath);
```

没有显式 `localPath`。Adobe 文档说明默认位置依赖创建 SWF 的路径，本地内容的权限上下文也可能对应不同的存储位置。因此 **savePath 字节干净只验证了名称，未贯通完整的存储身份**。([Open Flash][1])

这里不应凭空指认 asLoader 改变了身份；但实际创建者 SWF、上下文和目标位置必须有证据，不能由 launcher 找到某个旧 SOL 代替。

### 攻击五：V1 的引用验证报告，还不能称作彻底独立验证

报告明确写了：

```text
every Reference marker found (6 total)
```

而简报写“5 引用全部合法”。准确表述应是：**六个引用，其中五个双写字段完成了同名结构对应；宠物字段未完成同名对应。**

更重要的是，“原始引用值比自建表下标大一”不自动等于“Flash 使用一基引用”。AMF0 规范规定引用索引从零开始。一个需要检验的解释是：**实际引用表包含了你们展示表没有计入的隐式根对象。** ([SRS][2])

应核查 SOL 容器层如何注册 `so.data` 根，再用已知身份关系的真实播放器样本验证，而不是让两个解析器共享 `raw-1` 规则后互相背书。

这不意味着旧 SOL 已被证明损坏；意味着目前适合写：

> **旧 SOL 可由现有解析器完整走通，所检查的引用关系与业务结构相容。**

还不适合写“已排除全部原生解码差异”。此外，金钱／等级相同只验证了几个投影字段，不能替代整份快照或运行时图一致性的证明。

### 攻击六：“日志里的 false”与“已验证原生 Boolean false”还差一层身份记录

当前 `3514–3515` 的 `flushFalse` 统计把所有非 true、非 pending 结果放入同一个桶；`3519` 又是字符串拼接，没有记录 `typeof result`。

在正常原生调用前提下，`result=false` 很有说服力；但当你们已经把“API 被改写、构建不一致、注入”纳入 H3/H4，就不该又把调用身份当作已证明。

后续诊断至少应同时记录：

```text
typeof result
result === false
result === true
result === "pending"
调用是否抛出异常
SO 对象与方法是否符合预期
实际执行构建／SWF 身份
```

不需要重新怀疑已经排除的测试钩子；需要承认：**排除一个测试字段，不等于验证了整个动态调用链没有替身或版本漂移。**

## 最终执行裁决

**不要进入“批量剔除 AMF0 杀手值”的修复阶段。** 现在既没有锁定杀手值，也没有证明失败发生在编码器；贸然清洗可能改变对象图、掩盖故障并损坏有效数据。

下一步应收敛为：

**先把现有 PML 从字符串报告升级为事件证据；玩家唯一动作做受控空槽首存；随后按结果区分“共用存储上下文”“旧载荷／体积”“原目标 SO”。只有失败能跟随一个受控载荷迁移时，才值得把主要工程投入转向编码最小化。**
