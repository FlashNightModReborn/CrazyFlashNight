## 总裁决

**现有排除链不能把根因收敛为“代码、内容、配额都已排除，只剩玩家机器环境”。其中 E2 的核心语义判断有明确反例；E1、E4、E5 也不成立；E3、E6 只能保留范围很窄的结论。**

另外，两份调查报告里有三处需要撤回或降级：

* **“Flash 先挂死，Guardian 显示它时被拖死”尚未证明。**日志只能定位显示操作附近发生了停滞，不能确定两个线程的阻塞先后。
* **“会话 #4 被上一实例的 Ghost 拖住，切走后立即恢复”与原始时间线不吻合。**
* **“GetWindowText 对任意窗口都同步发送 WM_GETTEXT，因此应统一替换为 SendMessageTimeout”是错误的 API 概括。**对其他进程的窗口标题，`GetWindowText` 专门避免依赖对方窗口过程。([Microsoft Learn][1])

我建议把下一次现场取证的目标改成：

> **确定真实 Flash 进程在首次失败保存时，使用哪个 SharedObject 身份、访问哪个路径，以及失败发生在原生文件访问之前还是之中。**

我已核对原始日志、三份源码、报告及嵌套存档；没有在 Windows/FP20 上运行复现。下文包内证据按原文件行号定位，末尾附可下载的核对摘录。

## Q1：逐条证伪 E1–E6

### 1. 排除链裁决

| 排除项                     | 裁决              | 依据的问题                                                                                             |
| ----------------------- | --------------- | ------------------------------------------------------------------------------------------------- |
| **E1：排除存档内容致病**         | **撤销排除**        | F1 检查的是旧磁盘样本；真正写入的是本轮 `packGameState()` 重新构造的状态。F4 又是从同一 SOL 派生的 JSON，不是独立验证。F5 同时换了机器和存档，不是控制实验。 |
| **E2：排除配额／授权拒绝**        | **撤销排除，语义前提错误** | “空间不足且允许继续询问”与“存储已被禁止”是不同分支。后者可以直接返回 `false`，无需先出现 `pending`。                                     |
| **E3：排除文件损坏／截断**        | **仅窄范围保留**      | 可以显著排除**所提供主 SOL 样本**的截断及报告已检查的 AMF 结构错误；不能推广为实际写入目标、Flash 设置文件、内存对象均正常。                          |
| **E4：排除只读／属性问题**        | **撤销广义排除**      | 归档属性没有 `R`，只说明归档中记录的 DOS 属性。它不是原路径、原进程令牌下的有效访问检查，更不是 NTFS ACL、共享模式或安全软件策略的检查。                     |
| **E5：排除 launcher 版本缺陷** | **撤销排除**        | 他机正常只能排除“该版本在所有条件下必坏”。特定快照、路径、令牌、文件句柄生命周期、窗口时序触发的缺陷均未排除。                                          |
| **E6：排除多实例僵尸锁**         | **只保留时间顺序结论**   | 会话 #3 遗留实例不可能解释更早的 #2 失败；但没有其他 Flash，不等于没有 launcher、扫描器、同步程序或其他进程持有冲突句柄。                          |

文件的读写访问与共享模式是两套约束：另一个进程即使只是持有读取句柄，也可能因为没有允许共享写入或删除，而阻止后续写入、替换或重命名。不能用“没有第二个 Flash”排除这一整类问题。([Microsoft Learn][2])

### 2. E2：`pending` 不是一切存储失败的必经状态

Adobe 的 AS2 参考明确区分：

| 情形                   | AS2 接口语义     |
| -------------------- | ------------ |
| 允许存储，额度足够，保存成功       | `true`       |
| 允许存储，但需要用户交互决定是否增加额度 | `"pending"`  |
| 已禁止该域或全部域存储          | 可以直接 `false` |
| 无法保存对象的其他原因          | `false`      |

因此，“没有 `pending`”只能削弱**正在请求增加用户额度**这条路径，不能排除**持久拒绝、全局拒绝或其他不可保存状态**。([Open Flash][3])

几个细分不能混为一谈：

**曾经点过一次“拒绝”，不等于此后永远直接 `false`。**需要核实它是否形成了持续生效的禁止策略；“不再询问”的实际状态也必须对应这次调用。截图 05 中该复选框看起来未勾选，所以不能反过来断言玩家必然开启了它。

**`mms.cfg` 必须查，但不能假装已经确认 FP20 的具体分支。**Adobe 管理指南列出的 `LocalStorageLimit` 是枚举，不是直接填写容量：

```text
1 = 禁止存储
2 = 10 KB
3 = 100 KB
4 = 1 MB
5 = 10 MB
6 = 用户决定上限
```

它定义的是每域硬上限，用户不能通过界面突破。此次可核查的管理指南是 FP32 版，而不是这台 FP20 独立播放器的实现证明；**该 exe 实际读取哪份配置、硬限命中时的具体返回路径，仍须现场确认**。但不能继续以“必然 pending”把它排除。([Open Flash][4])

**小视口不能直接拿来解释当前全部 `false`。**AS2 参考专门说明：需要扩容、但显示区域不足以容纳授权界面时，接口可以先返回 `pending`，再通过 `onStatus` 报失败。你们日志中记录的是原始 `result=false`，不只是包装层的失败布尔值；不能把两个情形偷换。([Open Flash][3])

但还差三个连接：

**第二，37,858 字节是旧磁盘样本，不是这次准备写出的完整 `so.data`。**

源码实际执行：

**第三，H1 中“全局禁止不体现在站点滑块上”本身仍是待验证说法。**不能为了推翻 E2，就把这个尚未核实的界面行为升级为新事实。

### 4. 比配额更重要的漏证：你们证明了 C# 能读，没有证明 Flash 读写的是同一处

组合日志：

```text
696：    using launcher snapshot source=sol
```

而 AS2 的常规入口只有：


——`SaveManager.as:3476–3478`。

**“游戏本地读取成功”这条提示，当前证明的是 launcher 快照成功进入游戏，不是原生 Flash 成功读取了你们正在检查的 SOL。**

SharedObject 身份还涉及来源 SWF 路径及安全上下文，不只是 `savePath` 字符串。([Open Flash][3])

注意：**“身份不同”本身不必然导致 `false`；它与目标不可访问结合才是失败机制。**但身份未贯通之前，检查某个目录的权限可能从一开始就检查错了对象。

下面是**调查优先级排序，不是有统计依据的概率百分比**。前两组目前很接近。

### 两个容易误排的细分

**“能新建 txt”不等于“能保存旧 SOL”。**

新建文件、截断已有文件、替换文件、删除／重命名，是不同的访问请求；已有文件也可能有不同于父目录继承结果的 ACL。记事本还不是同一个可执行程序。这个测试阴性有信息，阳性却只能排除很有限的一部分。([Microsoft Learn][2])

**“玩家安装了很多腾讯软件”不能提高某个具体拦截机制的证据等级。**

尤其要把“第三方安全软件拦截”与“Defender CFA 拦截”分开。CFA 是否启用、该路径是否实际受保护、是否有对应拦截事件，都需要验证；`AppData\Roaming\Macromedia` 并不在微软列出的默认受保护目录中，额外配置才可能把它纳入。([Microsoft Learn][6])

### 内容原因不能用“循环引用”笼统代替

不要把“对象图里有引用／循环”直接写成失败原因。你们旧 SOL 已经存在合法 AMF 引用。真正需要测试的是**当前对象图**的异常体量、深度、资源需求或播放器编码缺陷，而不是把所有非树结构定性为不合法。

本轮完整对象还应包含顶层遗留字段，而不只是 `mydata`。只把 launcher JSON 重新序列化一遍，不能完整代表 Flash 真正提交的 `so.data`。

### 另有一个廉价但应补上的观测漏洞

这不是原生 Flash 的失败路径，而是**“是否真的执行了原生 flush”**的证明缺口：

```actionscript
var result:Object = _flushResultOverrideForTests !== undefined
    ? _flushResultOverrideForTests
    : so.flush();
```

——`SaveManager.as:3501–3503`。

初值确实是 `undefined`，但存在公开测试配置入口。报告里“生产为 null/undefined”的说法不严谨：**只有 `undefined` 会回到真实调用，`null` 不会。**

当前日志也没有输出 `typeof result`。建议一次性加：

```text
nativeCalled / overrideEnabled / typeof(result) / result / attemptId / lane
```

我不把误开测试钩子列为首嫌；但它是低成本就能封死的取证歧义。接受 F9 所述“生产未注入”为真时，直接从候选中移除即可。

## Q3：体检清单如何排序，哪项能一锤定音？

**原清单没有任何一项，单独做完就能普遍“一锤定音”。**最应该补进来的不是第八种猜测，而是**一次真实失败调用的文件访问记录**。

### 推荐流程

| 顺序    | 动作                                            | 目的及边界                           |
| ----- | --------------------------------------------- | ------------------------------- |
| **0** | **保全现场**：备份原 SOL、shadow、设置；若仍有挂死进程，先取两进程 dump | 杀进程前保留 Q4 的唯一强证据；之后不再把正在运行的存档改名 |
| **1** | **清除本游戏残留实例，确认下一次只有一组 launcher＋Flash**        | 去掉会话 #4 的混杂因素；这属于建立实验条件，不是证明根因  |
| **2** | **启动前开始捕获，覆盖首次 `result=false`**               | 首先确定实际进程、实际路径和失败层级              |
| **3** | **按捕获结果检查空间、策略、ACL、安全软件或句柄**                  | 不再让玩家无差别地逐项改设置                  |
| **4** | **做同上下文的原生 SO 小探针／完整 payload 对照**             | 区分全局写入能力、数据规模和原目标特异性            |
| **5** | **做同存档跨机与同机控制存档实验**                           | 补齐 E1、E5 缺失的控制实验                |
| **6** | **最后才考虑改名／重建原槽**                              | 它会同时改变多个因素，且容易污染原始证据            |

没有开发者协助、只能执行原有人工清单时，我会排为：

> **保全现场 → 原 1 清场 → 原 3 空间 → 原 4 全局设置 → 原 5 mms.cfg → 原 6 拦截记录 → 原 2 记事本 → 原 7 改名。**

但前半段尽量先**查看并记录**，不要一口气修改多个设置后再启动。否则即使恢复，也不知道什么起了作用。

### 最有价值的新增探针

由本地 Agent 在**同一个游戏 SWF 上下文**中创建独立诊断 SO，不覆盖原存档：

```text
A：几十字节 nonce
B：当前准备提交的完整保存对象
C：原来的主 SO
```

记录调用阶段、返回值类型、耗时、`onStatus`，并在新进程中回读 nonce，避免把内存缓存当落盘成功。

解释应当是：

* **A 也失败**：优先查该上下文的策略、目标路径、权限或运行时；主存档具体内容不再是首嫌。
* **A 成功、B 失败**：优先查大小、有效额度、对象图或编码资源。
* **B 成功、C 失败**：原目标文件／路径特异性显著上升。

这些结果仍不是绝对互斥证明，但比“记事本能写”和“新建白档能存”强得多。

### 原清单第 7 条的结果解释必须改写

> “改名后恢复＝文件被针对；仍失败＝系统级”

**这两个等号都不成立。**

改名重建可能同时改变对象内容、文件 ACL、目标是否存在、元数据与加载分支。恢复既可能是文件问题，也可能是旧内容触发了特定构造；仍失败也可能是每次启动都重新生成相同的坏对象，不能直接归为系统故障。

而且，SharedObject 还有原生自动写入行为；显式调用点审计并不等于覆盖了全部磁盘写入。不要在 Flash 仍持有对象时改名原文件，再拿结果做干净的因果实验。([Open Flash][3])

## Q4：会话 #3 最可能怎样挂住？现有三个候选如何评级？

### 1. 先修正“Flash 在 reveal 后约一秒就被证明 hung”

原始组合日志的顺序是：

| 时间             | 实际观测                                         |
| -------------- | -------------------------------------------- |
| `17:11:08.750` | 原始 `flush failed (result=false)` 及后续保存日志已经输出 |
| `17:11:08.795` | 开始 reveal                                    |
| `17:11:08.910` | `bootstrap_hide` 完成                          |
| `17:11:09.118` | 仍收到一条 socket JSON；可能有缓冲，不能据此精确判断执行进度         |
| `17:11:10.721` | 首次报告 Guardian UI tick 停滞                     |
| `17:11:14.741` | 首次采样到 `flash=True guardian=True`             |

——`launcher-20260917-1710+1711.log:700–720`。

这支持：

> 停滞发生在 `bootstrap_hide` 完成后、`flash_show` 完成日志之前的执行区间。

但不支持：

> Flash 已先挂死，Guardian 随后恰好向它发送某条确定的同步消息。

`IsHungAppWindow` 本身采用消息泵响应的超时判断，文档描述的是约五秒量级，不是实时的“线程刚刚死掉”信号。([Microsoft Learn][7])

源码区间定位也不等于原生堆栈定位。`Visible=true` 期间的窗口调用、布局、事件回调或重入都还没有区分；包内没有包含报告引用的完整 `WindowManager.cs` 等实现，不能把报告中的调用链都视为本轮独立确认。

### 2. 我会把新增候选放在首位：跨进程窗口关系引出的相互等待／重入

这是**工作假说，不是定案**：

```text
Guardian 显示／布局／激活
    ↔ 跨进程 parent-child 窗口关系
    ↔ Flash 窗口处理与可能的同步回调
    → 一个等待环或消息处理停滞
```

微软明确说明，跨线程的 parent/child 或 owner/owned 关系会**隐式连接输入队列，而且具有传递性**。跨进程 reparent 并没有保持原本直觉上的 GUI 隔离。([Microsoft for Developers][8])

这解释了一个被原报告漏掉的方向：

**可能是显示操作本身使双方进入坏状态，而不是显示操作撞上一个事先已经坏掉的 Flash。**

现在证据足以把这一类问题列在前排，但不足以指定是 `WM_SHOWWINDOW`、窗口位置更新、焦点处理还是某个业务回调形成的等待环。

### 3. 对现有三个候选的评级

**原生设置面板：保留，中等嫌疑，但缺少会话 #3 的直接关联。**

简报能证明的是玩家在 `17:12` 拍摄过设置页；会话 #3 的关键窗口在 `17:11:08`。这不是同一个已绑定的观测。

还必须区分：等待授权回调、暂停部分游戏逻辑、设置界面存在、Win32 消息泵失去响应。这四件事不能互相替代。尤其不能从 `pending` 的异步语义推出“所有设置交互绝不影响窗口时序”，也不能从“设置界面打开”推出 GUI 必然 hung。

判别需要在保持同一启动／握手流程的条件下，对照**嵌入与不嵌入、设置页开启与关闭、reveal 前后开启时机**。不要另起一个不同来源的最小 SWF，就宣称复现条件一致。

**Slow script：保留，低于窗口交互候选。**

当前没有脚本超时提示、脚本栈或持续 CPU 占用证据。隐藏提示确实可以作为待验证方向，但不能仅凭“日志停了”把它当成结论。

**存盘风暴：作为会话 #3 的直接原因降到较低。**

会话 #3 只记录到一次保存失败，且它已在 reveal 前返回。会话 #2 的“一秒六次保存”是真实的，但不能搬来解释 #3。

这里还有两处 P3 报告需要修正：

**其一，“每次失败前必完成整份 AMF 编码，并且这是主要成本”未获证明。**源码能证明进入了 pack，也能证明调用了原生函数；不能证明闭源 Player 内部是先完整编码再检查策略。直接拒绝路径可能较早返回。性能定案应分测 pack 与 native flush 耗时。

**其二，“每次点 X 都重跑一次 recoverDetach 和 AS2 flush”被包内代码反驳。**

`CharacterBuildTask.DetachRecovery.cs:283–293` 在 `fatal_blocked` 状态直接返回失败。对应日志中，`16:55:55–16:56:01` 连续关窗失败并没有逐次配对新的原始 flush。

因此更准确的放大链是：

> 初次恢复可能触发保存；之后重复关窗可以只是反复报告已知失败并追加 toast。重试按钮造成的真实保存风暴，要与 toast 风暴分开治理。

### 4. 会话 #4 的 Ghost 叙述也需要撤回

原始日志显示：

```text
17:11:50.177  flash_show 完成，随后进入 Activate
17:11:52.253  前台为 0xB0B2C，即本次 Guardian
17:11:55.281  才记录 Ghost 0xA08AC
17:12:02.305  前台已变为 0x30484
17:12:12.370  前台仍为 0x30484
17:12:14.132  Activate 才返回
```

——组合日志 `953–963`。

所以目前不能证明 Ghost 属于上一个实例；它也可能是当前 Guardian 停滞后出现的代理窗口。**更不能说“切离 Ghost 后立即解冻”——日志至少提前约十二秒就已观察到另一个前台 HWND。**

`23955 ms` 接近若干个五秒，仅是数值相似，不是“四五次 hung timeout 链”的证据。

### 5. Q4 真正缺的是双进程线程证据

下次挂住时，应尽量同时保存 Flash 与 Guardian 的线程栈／dump，并隔几秒再取一组，区分：

* 双方是否相互等待；
* Flash 是否在持续执行脚本或渲染；
* Guardian 是否阻塞在窗口调用、业务回调或其他锁中。

ProcDump 支持 hung-window 触发及进程转储；这里只取 launcher 的 dump 不够。([Microsoft Learn][9])

## Q5：三个 P2 修复方向的设计评审

### 1. `IsHungAppWindow` 预检：可作为拒绝执行的条件，不能承诺消灭挂死

它能减少“目标早已明显失去响应，还继续执行风险操作”的情况，但有两个无法消除的窗口：

**检查时还没达到 hung 超时；检查通过后，操作本身才形成等待。**

所以正确定位是**熔断信号之一**，不是安全证明。原报告“预检能消灭永久挂死”的表述应删除。([Microsoft Learn][7])

同理，超时监控不能依赖同一 UI 线程正常运行，否则最需要它时它也停了。

### 2. `GetWindowText` 统一替换为 `SendMessageTimeout`：不批准按当前理由施工

微软文档明确区分：

* **其他进程的窗口标题**：`GetWindowText` 取得标题，不依赖对方响应 `WM_GETTEXT`。
* **本进程窗口**：可能发送 `WM_GETTEXT`，行为不同。([Microsoft Learn][1])

所以统一改成显式消息，可能把本来不需要对方执行的诊断操作，改成真正的跨窗口通信。

更合理的是：

> 外部窗口只需标题时保留相应查询；本应用标题优先使用缓存；诊断优先记录 HWND、PID、TID、类名。确实需要读取外部控件文本时，另走有预算的诊断路径。

`SendMessageTimeout` 也不是通用强隔离：文档明确指出，接收窗口与调用线程属于同一队列时，窗口过程被直接调用，超时值会被忽略。结合你们的跨线程窗口关系，不能宣传“加 200 ms 就一定封顶”。([Microsoft Learn][10])

### 3. 前台为 Ghost 时跳过 `Activate`：可以保留，但应让激活整体退出关键完成路径

这个规则可以作为减少干扰的启发式，但无法覆盖本次所有可能路径，因为 Ghost 可能在调用之后才出现。

我更倾向于：

> **画面可用／交接完成不依赖抢到前台；焦点激活是可以失败、可以延后的附加动作。**

也不批准“每次丢给一个用完即弃 worker”的建议。直接在线程池操作 WinForms 对象有线程归属问题；不可返回的原生调用并不会因为业务上“不再等待”就消失，重复调用还会积累挂住的线程。专用线程可以限制损害，但跨进程窗口父子关系仍可能把主 UI 拉进依赖链。

适用处可以评估 `ShowWindowAsync` 等异步原语，但其成功只代表操作已开始，不代表窗口已经成功显示；它也不替代整个嵌入协议的完成确认。([Microsoft Learn][11])

### 4. 比这三个补丁更直接的源码问题

**A. reveal 执行权与完成状态混在一起。**

`GameLaunchFlow.cs:2621–2623` 在实际执行前已经：

```text
_revealPerformed = true
取消 FlashRevealWatchdog
取消 FrontdoorSceneWatchdog
```

然后 `2630` 才调用 `DoPerformReveal()`。

即使这是为了领取一次性执行权，也必须另有**实际完成状态与完成期限**。建议区分：

```text
Scheduled → Revealing → Revealed
                      ↘ Failed / TimedOut
```

领取执行权不能等价于成功；超时也不能直接无脑重放已经部分执行的窗口副作用。

**B. BGM 释放排在两个可能阻塞的操作之后。**

`2667` 显示、`2671` 激活，之后才到 `2678–2686` 释放前门 BGM。这为“视觉交接卡住，旧音频仍然存活”提供了直接的源码解释。音频所有权应有独立、幂等的失败收束路径，不应无限等待一次成功激活。

**C. 当前 shadow 不是独立故障备份。**

`SaveManager.as:1285` 的 `ok && socket` 意味着原生提交失败时，第二份数据也不更新。与此同时，退出栅栏在没有 CharacterBuild binding 时可直接通过：`DetachRecovery.cs:264–268`。

这不是 native `false` 的根因，却是“环境小故障变成整段进度丢失”的明确设计缺口。

不要直接删除 `ok &&`，把未提交状态冒充权威 shadow。更安全的是单独定义**未提交恢复快照**，附 attempt／revision／提交状态，不能自动授予奖励提交或安全退出成功；同时把存储故障告警与保护提升到全局，而不是只在开过装配面板后才拦下。

## Q6：只能让玩家做一件事，做什么？

**让玩家完成一次“从启动前开始，到首次存档失败后停止”的 Process Monitor 原生 PML 捕获。**

不是先改额度，不是先删文件，也不是先关闭安全软件。

由开发者准备好与玩家 Windows 版本兼容的工具和捕获说明，玩家只需完成一次受控复现。保留**实际 Flash 进程与本游戏 launcher**的事件、准确失败时间及对应 launcher 日志；不要只导出错误行截图或简化 CSV。Procmon 能保留文件访问、配置读取、进程身份及操作参数，适合先把当前泛化的 `false` 落到具体系统行为。([Microsoft Learn][12])

重点看的是**与该次保存对应的必要操作**：

| 捕获结果                      | 下一步                                               |
| ------------------------- | ------------------------------------------------- |
| 必要写入／替换步骤 `ACCESS DENIED` | 分辨 ACL、进程身份与安全产品拦截；不能直接等同“杀毒软件”                   |
| `SHARING VIOLATION`       | 查冲突句柄，尤其 launcher 自己                              |
| 空间／用户配额失败                 | 查实际目标卷及该用户可用额度                                    |
| 实际访问路径与被检查 SOL 不同         | 先修正身份／路径调查，再讨论文件权限                                |
| 过滤与时间窗口确认正确，却没有相关落盘 I/O   | 回到内部策略、真实 native 调用是否发生、当前对象与运行时问题；**不能自动认定全局禁用** |

还要避免把正常探测当错误：例如首次打开不存在的诊断 SO，出现一次 `NAME NOT FOUND` 并不异常；关键是后续必要的创建或提交有没有成功。

**这一个动作不能保证所有分支都直接定出最终原因，但它最可能一次消除最多错误假设。**P1 的原生保存失败应先拿这份访问轨迹；P2 的挂死则需要双进程 dump，两者不要强行用同一条未经证明的故事串起来。
