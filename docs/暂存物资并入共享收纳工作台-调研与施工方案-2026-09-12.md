# 暂存物资并入共享收纳工作台：调研与施工方案

**状态：调研完成；产品方向已对齐；目标实现未施工。** 本轮只沉淀调查结果与接手方案，不代表代码、测试、编译、候选运行或发布已经完成。后续择机施工，不能把额度重置视为自动开工或发布授权。

**最后核对代码基线：commit `e66c9f73859a1779f4c1a16c6e66d4e2b6727981`（2026-09-12）及调查时工作区增量。** 工作区同时进行 NPC 菜单与原生注释迁移，涉及共享物品视图、暂存视图、Host 与 AS2。本文按当前文件核对，不能当作该 commit 的纯净树审计。接手时按第 9 节刷新差异。

现役暂存功能与存档事实以[统一奖励暂存 ADR](统一奖励暂存与非阻塞领取-ADR-2026-09-11.md)为准；共享界面规范以[双栏工作台 UI 系统](../agentsDoc/workbench-ui-system.md)为准；本文负责本次收敛的决策、差异和施工顺序。

## 1. 已对齐的决定

用户希望降低玩家学习成本与多套实现的维护成本，明确倾向直接对齐战备箱，并接受在共享层补足体验的方向。下一轮交付按以下目标执行：

1. 暂存物资接入现有 `InventoryStorageWorkbench`，与背包—战备箱、背包—仓库共用同一收纳工作台。左侧仍是背包，右侧为当前可访问的收纳来源。
2. **UI、CSS、格子、工具栏、分页、密度、详情展示、键盘焦点、拖拽与批量控制器都以战备箱的现役实现为基准。** 不复制一份再改颜色、间距或按钮，也不为暂存设计独立的新版视觉。
3. 暂存仅取出；不能存入、交换回填、丢弃暂存条目，不能直接供制作、交任务或战斗使用。限制由能力与领域校验共同表达。
4. 数量选择、批量结果、容量反馈等通用改进进入共享层，战备箱也使用；暂存的持久化、来源身份与领取路由由业务适配承担。
5. 先完成共用与旧实现退役。额外视觉打磨、跨页多选、全文搜索、复杂排序、极端库存完整保存优化可分别推进，不能成为首次收敛的前置大工程。

**判断是否复用的标准是依赖同一份生产代码，而不是截图相似或引用了同一个物品格函数。** 后续改一次共享按钮、密度或交互反馈，各来源都应获得改进。

## 2. 当前体验差的原因与覆盖范围

现役暂存确实复用了 `OwnedInventoryViewShell`、`ItemGrid`、物品格、分页等基础资产，但外层布局、详情区、数量输入、选择集合、批量执行和反馈循环仍自行实现。历史 ADR 中“复用战备箱”描述的是这些已复用部分，不代表整个收纳工作台与控制器已经共用。

| 已知问题 | 当前证据与玩家影响 | 正确迁移后的覆盖 |
| --- | --- | --- |
| 布局与视觉另起一套 | `character-build-stash-view.js` 自建工具栏、网格与右侧详情；`character-build.css` 保留独立 `.character-build-stash` 布局。占用同一工作台却形成另一种操作空间 | 同一工作台和 CSS 可直接消除这类分叉 |
| 看不到接收背包 | 暂存页面右侧显示详情，没有战备箱页面的可操作背包；玩家不能边看空位、边整理、边领取 | 接入真实双容器视图可直接解决可见性；容量判断仍须权威回执 |
| 相同物品采用不同操作 | 暂存仅绑定点击与 Enter/Space，未接收纳页的拖拽与详情交互绑定；`exportOffer()` 返回空、目标拒收。已有 Ctrl 整项取出和数量按钮，但不是同一控制链 | 共享交互可覆盖机械操作；定点投放、数量与单向限制要补领域能力 |
| 筛选、翻页、选择与焦点不连贯 | 暂存每次 `render()` 清选择，固定 32 项 offset 分页，无全局类别查询；方向键按固定六列计算，完整密度下实际网格可为五列 | 共用工具栏、真实列数和焦点管理可修一部分；刷新保留策略及全局查询仍需实现 |
| 批量结果不透明 | 当前视图未逐项呈现 `accepted`，只记录 `blocked`；随后刷新用总数覆盖状态。全部取出会随扫描切页，玩家难以区分执行、跳过与完成 | 共享结果区、稳定浏览位置和操作反馈需要一起补齐 |
| 数量与容量反馈不足 | 超过最大值时按钮仍可点击，处理器直接返回；背包空间不是所有物品的真实目的地，单靠“空几格”不能说明为何可领或受阻 | 共用数量控件可覆盖输入校验；可领量、去向与失败原因仍由领域返回 |

按上述六类归纳，约两类可随正确共用直接覆盖，四类需要共享控件和领域适配配套完成；这不是已完成比例，也不能换算成可靠的体验提升百分比。

另有独立性能问题：原暂存 ADR 已记录 4096 件极端库存完整保存仍有秒级停顿。共用 UI 可以减少布局与操作负担，不能据此承诺消除 AS2 候选复制和完整 SOL 保存成本。

本次证据包括生产源码和沿用现役组件的隔离浏览器夹具。夹具观察到翻页后选择清空、受阻提示被刷新覆盖、越界数量无反馈、完整密度方向键跨行错位；夹具使用模拟领取回执与占位图标，不能证明真实 WebView2 输入、AS2 写入、当前美术效果或保存重启旅程。实际页面高度也受 Character Build 父布局影响，不能从独立夹具外推生产占高。

## 3. 共用边界：一份工作台，两个领域适配

以下是目标职责划分，不是已存在的新 API：

```text
InventoryWorkbench（面板、导航、密度、会话与关闭协调）
  └─ InventoryStorageWorkbench（同一双栏 UI 与机械交互）
       ├─ 普通库存适配：背包、战备箱、仓库
       │    └─ InventoryCoordinator → InventoryTask → InventoryPanelService
       └─ 暂存来源适配：稳定条目、查询、取出与回执
            └─ 复用 ItemUse 领取链 → RewardStashService → RewardStashStore
```

不要为暂存注册新 Panel、创建第二个 Shell 或建立独立缩放方案。现有 `1024×576` 逻辑画布、`PanelScale`、头部和 density 状态继续由工作台拥有。原暂存入口应导航到同一工作台内的收纳视图；返回恢复原子页上下文。

如需切换收纳来源，使用现有标题或导航插槽与共享控件，仅列出当前入口已授权的来源。接入暂存不扩大仓库或战备箱的场景访问权限，不把暂存入口变成任意地点打开仓库的捷径。

| 部分 | 应共用的现役实现 | 暂存适配负责的差异 |
| --- | --- | --- |
| 页面骨架 | `InventoryWorkbench`、`InventoryStorageWorkbench`、现有 transfer-pair 样式 | 标题、已授权来源、单向能力、条目总数 |
| 格子与详情 | `InventoryWorkbenchOwnedView`、`OwnedInventoryViewShell`、现役物品详情绑定 | 暂存条目到共享 ViewModel 的投影与详情请求 |
| 选择与执行 | `QuickTransferController`、`InteractionBroker`、`PointerDragController` | 稳定来源引用、允许的动作、取出命令与结果 |
| 数量与反馈 | `WorkbenchComponents.QuantityControl`、共享命令栏与状态区 | 权威数量上限、合法去向、受阻原因 |
| 查询与分页 | 同一类别工具栏、pager 与焦点恢复 | 暂存全局查询和有界页面，不伪造普通库存槽位 |
| 写入与恢复 | 工作台已有写占用、关闭协调和刷新机制 | ItemUse 暂存事务、原操作查询、提交状态与旧版恢复 |

只抽出确有两个消费者需要的接口；优先在现有 ports 中增加来源引用、能力和结果适配，不先造一套通用插件注册器或第二套事务框架。

## 4. 施工前必须解决的实际差异

### 4.1 来源身份不是同一种槽位

普通库存用 `containerId + physicalSlot + expectedLease`；暂存用 `storeId + commitRevision + entryId/revision`，分页位置随删除、合并而变化。现有 `QuickTransferController` 的 key 和访问函数依赖物理槽位，不能直接把第 N 条暂存记录当成第 N 个普通槽位。

共享选择、拖拽和异步详情应拿到适配器提供的稳定引用。暂存仍以条目身份提交；背包目标仍用当前物理槽位及 lease。异步查询、详情与写后刷新同时绑定面板代际、来源和查询版本，旧页面响应不得覆盖切源后的新页面。

### 4.2 会话生命周期不能靠搬 DOM 解决

当前 `Program.cs` 将 `CharacterBuildTask.IsExactSession` 传给 `ItemUseTask`；AS2 的 `CharacterBuildService.validateItemUseContext()` 同样检查活动会话、generation 与非 stale 状态。暂存 transport 依附 `CharacterBuildItemUse.Controller`，在角色构筑获取会话后绑定。

切到收纳页时，导航会调用 `CharacterBuildController.suspend()`，其中关闭前端 ItemUse 控制器。与此同时，`CharacterBuildSession.suspendView()` 只取消视图读取，**并不等于 Host / AS2 会话被 finalize 或关闭**。因此实际障碍是前端领取通道的所有权和生命周期交接，而非“切页必定销毁全部后端授权”。

建议先复用仍有效的会话机制，把需要跨子页存活的领取通道交由工作台协调，视图挂载与通道关闭分开。必须同时验证从角色构筑进入、直接从收纳入口进入、返回以及关窗；直接入口可能尚未建立 Character Build generation。

优先验证能否以不挂载人物渲染器的方式复用现有会话服务。若必须改变会话归属，设计最小的工作台会话接入，并保持 Host 与 AS2 精确身份校验；不要保活整个隐藏构筑页面，也不要删去 generation 校验。具体接口由首个跨栈纵切确定，不在调研文档中伪定一套新 wire。

### 4.3 背包与暂存同时可操作后，要协调冲突写

现有 `InventoryCoordinator.beginExternalWrite()/completeExternalWrite()` 已能占用库存写入并在完成后刷新。暂存领取使用独立 ItemUse 写状态。接入双栏后，领取、背包整理、拖拽、丢弃和切源必须纳入工作台的同一次操作协调，不能出现领取未定而另一个控制器已经解锁的状态。

可复用现有 external-write 接口，但需证明提交结果、暂存页与受影响库存快照的采用顺序；未知结果先核对原操作，期间保留冲突写保护。已确认的“没有可领项”可回到可操作状态，未知写不能伪装为失败并换 operationId 重发。

这是新增双栏并存带来的接入要求。本次没有据此断言现役系统存在跨域并发漏洞；Host 与 AS2 的共同写准入需在纵切中连同调用入口核对。

### 4.4 数量与目标位置需要真实领域支持

现役暂存 `stashTake` 支持条目数量，但不接收目标格；现役普通库存 move/merge/swap 与自动转移操作按整项处理。共享 `QuantityControl` 已存在，但尚未接入这条普通库存转移链。不能把“有数字输入控件”写成“已有部分转移能力”。

目标交互沿用战备箱：Ctrl 点击与批量操作自动安置；对能够进背包的物品，拖到明确格位时尊重该格位。装备保留完整实例；暂存不允许以 swap 把背包物品换回暂存。目标被占用、类型不兼容或 lease 过期时明确拒绝并保留可恢复选择，不能悄悄投到别处。

指定数量保留，并作为共享转移能力补齐。非堆叠装备只允许整实例；堆叠物品的最大可选量、部分可接受量与目标合并限制由领域校验。数量输入即时反馈整数、正数和上限，禁用不能提交的按钮并说明原因。

材料、情报等沿原权威路由进入对应持有区；部分消耗品还可能优先进入装备中的手雷槽或既有药剂槽。当前 `ItemUtil.require/acquire` 决定去向，不能把所有成功都写成“已放入背包”。这些物品不显示虚假的定点背包投放能力；自动领取结果说明真实去向。

### 4.5 两种批量结果不能硬套

当前普通库存 `autoTransferBatch` 最多 50 项，按选择顺序提交可成功前缀，在第一个无法安置的条目处停止；现有控制器校验 `completedCount` 和 `failure.index` 的前缀关系。暂存 `stashTake` 最多 32 项，遇到受阻条目可继续尝试后续条目，返回逐项 `accepted/blocked`。

例如背包满时，前面的装备可能受阻，后面的材料仍可领取。把这次结果压成“成功前 N 项”会误报完成对象；把暂存改成第一项失败就停，也会退化现有领取能力。

共享 UI 区分执行所选与尽量取出，适配层保留各领域已经确认的结果语义。通用结果应能表达每个稳定来源的已取数量、剩余数量、去向及受阻原因；这是建议的内部结果模型，不要求直接改写现役全部协议。普通库存 v1 前缀契约先保持，若增加尽量转移能力，应另行明确命令意图和测试。

显式批量继续是一批一次有界事务，不能退回 N 次单项调用。每个来源保留自己的批次上限；全部取出跨批循环时只在确认上一批后继续，让出界面帧，停止只取消后续批次。处理游标与玩家正在浏览的页分离，避免整页跟着自动执行跳动。

完成反馈至少显示本次已取、未取及原因；保存或响应未知时展示核对状态。刷新不能用库存总数覆盖本次结果。受阻条目保留在暂存，不能把整体 `success:true` 当作全部已取。

### 4.6 查询、整理与选择状态要分清

暂存目前只有固定 32 项 offset 页面；全局类别筛选属于必补能力，不能只筛当前页导致玩家误以为其他页没有目标物品。分类口径应复用现役物品分类规则，由权威查询或受其约束的索引完成；列表和页码 DOM 继续有界，不把全部条目拉到 Web 来补筛选。

普通库存工具栏的 `sortAndMerge` 会实际整理物理槽位，并非只改变显示顺序。暂存来源不能把同一按钮误接成库存物理整理；不适用的能力不提供，若以后新增显示排序，则在共享工具栏声明该语义。全文搜索和复杂排序可留待共享升级。

首轮沿用战备箱的页内选择：翻页、切类别或切来源时明确退出批量模式并提示选择已清除。普通刷新仍按稳定身份恢复当前焦点与可保留选择；执行完成后按结果移除已完成项，对受阻项保留清晰反馈。跨页选择是后续共享能力，不为暂存私造一套。

网格方向键使用当前布局的实际列数，完整/紧凑只改呈现，不改变动作能力。空页回退、最后一项领取、重开和返回都需要确定的焦点落点。

## 5. 必须保留的业务边界

- 保留现役 `_saveExt.rewardInbox` v2 库存权威、稳定条目与已提交前像；本次 UI 收敛不要求新建第二份暂存库存或迁移现有 v2 存档。
- 页、详情、角标和容量说明保持纯读；打开空暂存不创建存档扩展，不触发 ACK、迁移或保存。
- 取出是内部移动，保持 `ownershipDelta:0` 等现役资产语义，不重复记获得或重复结算奖励。
- 暂存删除、接收库存、命令回执与保存结果仍属于同一 Reward 候选提交。定点、数量与批量扩展不得绕过这条链。
- 旧 v1 根事务、K 店 legacy 行和领取恢复保持原身份、证明和迁移顺序；共用界面不代表可以删除旧存档恢复能力。
- 写后同步受影响背包、暂存页、角标及其他实际接收区域。返回角色构筑需重新采用权威快照，但单纯浏览不得重建人物并清除瞬时 Buff。
- 极端规模保存性能单列。可测每批请求数、保存次数、快照数和耗时，不以“批量 UI 更快”代替存档成本证据。

## 7. 推荐施工顺序

每步完成必要验证后继续，不把步骤拆成必须反复请用户确认的流程。以下是后续实施建议，本轮没有执行。

| 顺序 | 工作与可交接结果 | 该步消除的不确定性 |
| --- | --- | --- |
| 1. 刷新基线并验证最小纵切 | 核对并行迁移；在同一收纳页读暂存，再完成一件普通装备的权威取出、背包刷新和返回；覆盖直接入口及构筑入口 | 会话、导航、写占用、lazy 依赖能否成立；先证明共用路线可运行 |
| 2. 收敛共享交互 | 抽出来源身份与能力接点，接上同一 owned view、详情、拖拽、QuickTransfer、QuantityControl；普通库存接入适用的数量能力 | 确实共用控制器，且战备箱/仓库行为得到保持或升级 |
| 3. 补齐暂存能力 | 全局类别查询、合法定点目标、数量、逐项结果、尽量取出与有界多批；保持原保存和恢复边界 | 解决“组件共用但业务语义缺一半”的问题 |
| 4. 替换入口并退役旧实现 | 原暂存入口导航到共享收纳；删除专属 UI/CSS/加载引用，迁移测试；与现役原生详情通道对齐 | 防止两套实现继续维护、隐藏入口回流或冷启动缺模块 |
| 5. 完成适用验证并报告边界 | 跑第 8 节对应检查；更新实现涉及的 canonical 文档；取得同候选的真实输入和保存读回证据 | 证明实际玩家旅程，而不只证明 DOM 与静态引用 |

可以在同一施工批次完成多步。首个纵切只作内部验证，不把缺少数量、结果或恢复的临时页面当作最终交付。若会话方案需要扩大到全工作台协议重构，应先比较更小的既有服务复用途径，再确认实质产品或范围变化。

浏览器至少覆盖：空暂存、少量混合物品、超过一页、背包满与可合并目标、真实长名称/装备详情、完整与紧凑密度。规模夹具使用有界列表；纯占位图标截图不足以确认密度与可读性。

玩家体验验证集中为三条可完成的旅程：

1. 打开暂存，直接看到背包；查看同一件装备并拖到指定空格；返回再打开，位置、剩余量和焦点一致。
2. 背包接近满时，领取指定数量和一组混合物品；看懂哪些已领取、哪些留在暂存及原因；整理背包后继续，操作与战备箱一致。
3. 暂存、战备箱与构筑之间往返，包含一轮多批领取停止；正常保存退出后重启核对物品总量、装备实例与暂存余量。

真实异常恢复用隔离存档和既有故障门验证，不让测试员靠破坏正常存档来制造未知写。AS2 编译遵守 GUI CS6、UTF-8 BOM 与新鲜 trace 规则；业务注入默认核对 `asLoader`，测试使用 `TestLoader`，不因修改 `.as` 就默认编主 XFL。实际编译和 runtime 构建须等当前占用作业协调结束。

只有源码/夹具通过时就报告对应层级；不能称真实输入或保存重启通过。后续若授权正式发布，沿用[现役 runtime 发布流程](runtime-build-reproducibility.md)，本方案不建立新的发布门，也不代替专项体验证据。
