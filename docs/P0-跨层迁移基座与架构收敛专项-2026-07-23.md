## 1. 结论与专项使命

后续仍有大量 AS2 UI 待迁。继续让每个领域分别实现 Web session、C# pending/timeout/callId、AS2 revision/token、断线清理和未知写对账，会重复制造物资箱已经暴露的组合度爆炸。

P0-F 只消除其中 **transport lifecycle** 这一维的重复组合；领域因果关系、业务写状态和 reconcile 政策仍由各领域承担。F3 新页面必须用显式终态门证明这些领域状态可收敛，但本专项不把它们抽成公共状态机。

长期路线把 P0 分为两个独立工作包：

- **P0-S 稳定性止损**：冻结物资箱协议继续泛化，完成 `force_flush`、安全退出和 shadow/SOL 窗口加固；它必须由独立窄 ADR / 施工记录推进，不属于本文 F0–F4，也不得随 P0-F “顺便施工”。
- **P0-F 迁移基座收敛**：只收口已被多个真实消费者证明重复的跨层机械代码，并让一个后续写面板原生复用。

P0-F 的唯一业务价值指标是：

> 新增一个持久写 Panel 时，领域代码只实现命令映射、payload/回包校验、业务规则和领域 reconcile，不再自建 pending、timer、callId mux、迟到回包和 transport cleanup。

本文同时是本轮高强度跨层开发的收尾边界：先把已经取得的契约、runtime、事务和测试成果变成可维护接缝，清点仍在场的临时路径，再开始下一轮高风险纵切；不以“趁热再迁一个页面”扩大范围。

纯展示/纯本地页面继续沿用现有 `Panels`，不进入本专项。工作流 `crazyfs-p0f-20260723` 在 Preflight–F4 期间曾暂停 F3 之外的新持久状态/经济写页面，且没有产生具名例外。F4 的终局裁决是“采用已证明基座继续”：未来领域仍须逐项登记真实命令绑定、业务裁决与验证，并在冻结 Web-only 的同轮删除旧机械；不恢复批量施工，也不自动重启 P0-F。

## 4. P0-F 最小范围

### 4.1 机器契约最小演进

优先演进现有 `panel-contracts` 和 validator，不平行新建完整 Domain Registry。P0-F 只需要表达：

- `domain`；
- `query | transaction` 能力；
- command 级 `businessDecisionOwner`（暂名，由 F1 冻结）；
- command access / 读写级别；
- handler binding；
- 现役消费者真正要求的 identity。

上述字段均是需求级暂名，精确 schema 由 F1 在现有机器契约中裁决。这里的 owner 只表示某条命令当前由哪层作业务裁决，不是持久 aggregate 的完整 `authorityMode`。不在 P0-F 登记持久化布局、Bootstrap editor/save-repair 门控、未来 StateCore backend、价格或特性恢复 key；现役聚合级权威仍由架构 canonical doc 管理，未来若启动存档 v4 则另立独立 ADR。

是否需要升级为 v2、拆引用文件或只扩充 v1，必须由现行 strict validator、兼容性和唯一 source of truth 要求裁决；不得为了少改版本号静默改变 v1 含义，也不得先造第二份表。

### 4.2 固定现有 Web Runtime Profile

不创建新的“Panel SDK”。新 Query/Transaction Panel 默认组合：

```text
Panels + panel-runtime + workbench-lifecycle
+ 按需的 focus / primitives / components
```

P0-F 只补至少两个真实消费者都缺少的 primitive。checkpoint、write gate 或 reconcile 即使名称相同，也必须先证明实现形状同构才能抽取；共享故障分类和测试向量优先于共享状态机。

### 4.3 Host 窄 transport helper

以 `NpcShopTask` 与 `CraftingTask` 为当前首选候选；F0 冻结两个参考消费者后，只从它们的同构部分提取组合式 pending-call primitive：

- backend callId；
- pending/timer 生命周期；
- 现役保守投递分类；
- 迟到/重复回包；
- disconnect/dispose cleanup；
- Web response 回送所需关联信息。

领域 Task 继续负责 command 白名单、payload 重建、严格回包校验、token、write gate 和 reconcile policy。尤其是 `writeState` 转移、某个回包是否 definitive、哪一种领域读请求可以解除 reconcile，以及严格校验所需的归一化请求等领域挂载数据，都不得进入公共 helper；helper 只保存 opaque correlation state，并把领域裁决回调给 Task。

当前 `XmlSocketServer.TrySend(false)` 同时覆盖未连接和 `Write/Flush` 异常，不能证明“确定未投递”。P0-F 对写请求的 `TrySend=false` 一律在 helper 内部保守归为 `DeliveryUnknown`，但保持现役 wire 的 `error="disconnected" + requiresReconcile=true` 不变。未来若要改变 wire 或细分结果，必须以窄 `TransportSendResult` ADR、协议文档和独立测试推进，不能把未经证明的分类暗含在 pending helper 中。

若接入第二个消费者时公共 helper 出现 `npcshop/crafting/skill/loot` 等领域分支，应立即缩回更小 helper，而不是增加 capability flag。

### 4.4 AS2 与可观测性

P0-F 不建设 AS2 adapter 层，也不横扫所有服务加入 `authorityMode` guard。只复用 `PanelRequestEnvelope`/现有领域服务，并完成 writer 清单与静态审计接缝。writer 清单是 F0 临时审计工件，F4 必须删除或把稳定事实回流唯一 canonical；静态审计只能落入现有契约 validator 或一个具名 lint 脚本，若成为活动验收入口则同轮路由到 `testing-guide.md`，不得再形成长期平行文档。

公共关联先复用现役字段；没有两个消费者的 `contextEpoch/authorityEpoch/idempotencyKey` 不提前进入 wire。P0-F 只实现 Query/Transaction 所需的迟到、重复、断线、close 和未知写故障向量；execution lease、场景 teardown、角色热切换留给 RogueRun ADR。

### 4.5 明确不做

- Authority Router、StateCore backend、`mydata v4` 或 SOL 退役实现；
- 新数据库、进程、事件存储、DI 框架、代码生成或反射式插件系统；
- 万能 Panel renderer、万能 domain model、巨型 `BaseTask`；
- 新增跨进程 hop 或 Host 每帧裁决；
- 批量重写稳定旧面板；
- 强迫 Skill/Loot 接入公共 helper；
- 为未来假设预留未使用 schema 字段。

## 6. 反过度设计硬门

一个“轮次”是一次完整阶段交付尝试，加适用的验证和审阅；只有发生代码、契约或生产配置变化时才要求对应构建与定向回归。F0–F3 的每个阶段退出门最多尝试两轮；同一退出门连续两轮未通过即停止功能施工并进入 `CleanupRequired`。F4 是强制 cleanup，不受两轮上限约束，必须持续删除/回退未证明改动、同步 canonical truth，直到现场可进入 terminal 或遇到明确的外部流程断裂。专项计划窗口固定为 2026-07-23 至 2026-09-17（八个日历周，包含 Preflight）；到期仍未完成必须按已有证据进入 F4 清理，再以 `Partial` 或 `Rejected` 关闭；不得在本文内续期，重启必须另立 ADR。

terminal 判定是：

- `Closed`：F0–F4 全部通过，包含 F3 第三个消费者证明；它只表示本专项治理闭合，不表示 Launcher runtime 已 promotion、部署或达到 `standard_entry_verified`；
- `Partial`：F4 清理、canonical 回流和替代治理入口已完成，保留的成果均已证明，但缺少至少一个后续证明；
- `Rejected`：公共抽象不保留，F4 已完成删除、必要事实回流和替代治理入口。

状态转移固定为 `Preflight → Active(F0–F3) → CleanupRequired(F4) → Closed | Partial | Rejected`。任一阶段失败、两轮耗尽或到期都只会转入 `CleanupRequired`，不能直接进入 terminal；任何 terminal 都必须经过 F4。F4 自身未清理完成时保持 `CleanupRequired`，冻结功能施工并继续回退未证明改动，不能用 `Partial` 标签掩盖现场。

公共原语必须同时满足：

1. 至少两个生产消费者存在同构机械重复；
2. 同轮删除或禁止复制对应旧机制；
3. 不包含领域 payload、错误政策或特性分支；
4. 有独立测试、owner 和可删除边界；
5. 不增加 IPC hop；
6. 不要求无关稳定面板适配。

触发任一条件即停止抽象：

- 第二个消费者迫使 helper 增加领域 `if`；
- F2 结束仍保留新旧 pending/timer 双轨；
- 公共字段或状态没有两个真实调用点；
- 测试必须模拟尚不存在的 StateCore/双 backend；
- 新 Panel 仍需自建同类 transport 状态机；
- 公共组件比复制前更难读，且无法由删除量和故障覆盖解释；
- 同一退出门连续两轮未通过。

触发后转入 `CleanupRequired`，删除未证明的公共代码；F0 审计结论按 F4 回流 canonical，临时清单随专项清理。机器契约成果只有在同轮进入现有契约 canonical 与 validator 后才可保留，否则一并删除。清理完成后再以 `Rejected` 或 `Partial` 关闭。证明“不值得抽”也是合法成功结果。
