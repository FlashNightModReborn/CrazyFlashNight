## 1. 决策摘要

1. 将后续工作定义为“怪物知识库与美术导演管线”，不是给现有头像正则补更多关键词。
2. 顺序冻结为：**事实证据 → 简介式档案 → 全语料归纳标签 → 受控美术语言 → 玩家侧投影**。不先发明一套标签再逼所有怪物套入。
3. 模型只能基于带来源的 evidence packet 生成 `canonical / inferred / creativeProposal` 三类不同权限的内容；缺少证据时必须明确未知，不能补写成既成世界观。
4. 内部制作档案与玩家可见简介分离。玩家文案按进度逐步披露，不能让领养、竞技场或图鉴绕过主线剧透门。
5. 怪物身份、换皮别名、状态变体、关卡实例和展示主题是不同实体，不得因为共用头像就合并剧情身份，也不得因为同一怪物换姿态就制造多个知识档案。
6. 美术导演输出受 palette、motif、frame、ambient、motion 和 prohibition 白名单约束；模型提出语义和组合，确定性编译器生成最终 CSS / SVG 配方。
7. 选中、危险、锁定、稀有度等 UI 状态色与怪物身份主题正交；Boss 不能简单等同于红色。
8. 头像工程已证明 Luna CLI worker、独立 shard、digest、Edge 人审和单一 controller 的技术路线可复用，但新工作负载仍需自己的质量、并发和成本 pilot。
9. 模型必须可替换。未来更强模型只重跑推理层，证据包、schema、人工编辑、黄金集和评测回执继续保值。
10. 所有玩家可见正史文案和新增世界观设定必须有人类签署；模型通过、A/B 共识或自动 grader 不能直接 promotion。

## 3. 目标与非目标

### 3.1 目标

- 为每个稳定怪物身份建立简短、可查证、可逐步补充的内部档案。
- 从全体档案归纳一致的阵营、叙事、战斗与视觉词表，而不是依赖名字 substring。
- 让头像框、图鉴、竞技场、领养页和未来消费者共享同一语义，但按 context 使用不同展示配方。
- 把维护者的修改、取舍和创作偏好沉淀为版本化数据，供后续模型批次与 challenger 复用。
- 支持未来模型无损替换：同一 evidence digest、同一 schema、同一黄金集上盲比，不重做身份和来源治理。

### 3.2 非目标

- 不在设计储备阶段新增正式怪物设定、补写剧情或发布玩家文案。
- 不让模型直接编辑 `enemy_properties`、任务对白、生产 manifest、Web CSS 或透明头像。
- 不从数值高低单独推断 Boss、剧情重要性、性格或阵营。
- 不把头像裁剪偏好误当作完整角色审美；现有反馈只证明小尺寸可识别度、焦点、留白和方向偏好。
- 不声明 Luna 已被训练或微调；atlas 是检索与提示输入，不是训练证明。
- 不押注未公开模型或发布时间来替代当前 schema、证据和评测建设。

## 4. 数据权威与分层

| 层 | 建议职责 | 写入权限 | 禁止承载 |
|---|---|---|---|
| 身份映射层 | `enemyId / Identifier → profileRef / portraitRef / variant` | 人工维护、schema 校验 | 长文案、CSS、素材坐标 |
| 原始事实层 | 属性、关卡、任务、对白、动作、素材的原始路径与 hash | 现有各 source of truth | 模型总结、推断标签 |
| evidence manifest | 逐身份提取结果、定位器、证据片段、缺口、source digest | 确定性生成器 | 未标来源的自由文本 |
| 怪物档案层 | 人审后的内部简介、结构化语义、正史状态 | 人工 promotion | 运行时实例状态、任意 CSS |
| 推理候选层 | Luna/Sol/未来模型的档案、标签和美术提案 | 隔离 shard，不可直接生产 | 生产权威 |
| 人审与评测层 | 决定、编辑、冲突、剧透问题、黄金集、grader 结果 | reviewer + controller | 静默覆盖原输出 |
| Web 展示层 | context preset、主题 token、花纹和动效配方 | Web 配置 / 编译器 | 正史事实、来源 provenance |

继续沿用头像工程的边界：稳定身份指针可以进入 `enemy_properties`，生成 provenance 进入 manifest，展示规则进入 Web 配置。未来档案正文是否进入新的 `data/monster_profiles/`，须在 pilot 后冻结，不能把模型输出直接堆进敌人属性文件。

## 5. 实体模型：必须先区分的五种对象

| 对象 | 示例 | 规则 |
|---|---|---|
| 知识身份 | 黑白无常、方舟妖姬 | 一份核心档案，表达剧情和战斗身份 |
| 资产身份 | `portraitRef + variantKey` | 可与知识身份一对一、共享或多变体，不反向决定正史 |
| 状态变体 | 武装 JK orange / white | 同一知识身份下的可选视觉/状态分支 |
| 换皮 / 别名 | 拟态投影复用方舟妖姬头像 | 可共享资产，但知识身份是否合并必须独立人工裁决 |
| 关卡实例 | 同一兵种在不同波次、称号或主线阶段 | 继承知识身份，可带 encounter override，不复制整份档案 |

还需预留“形态转换”关系：若一个角色的不同形态具有显著不同机制和玩家认知，可共享 `characterRef`、拥有不同 `profileRef`；是否拆分不能由素材文件名自动决定。

## 6. Evidence packet 的来源与最小合同

### 6.1 来源维度

| 来源 | 可提取内容 | 主要风险 |
|---|---|---|
| enemy properties | 数值区间、抗性、掉落、性别/重量、设计标识 | 数值不是叙事事实，默认模板会造成假特征 |
| stages | 首次/重复出现、地图、波次、同伴、称号、实例参数 | 调试关、挑战关和主线不能混为同一叙事权重 |
| tasks / dialogues | 阵营、关系、事件、玩家已知信息 | 文本可能有历史版本、说话者视角和剧透 |
| AS2 / 配置 | 攻击距离、技能、召唤、位移、特殊状态与死亡行为 | 代码名不等于玩家可见招式名 |
| XFL / SWF | 动作标签、姿态、武器、轮廓、多主体、特效 | 素材存在不代表已实装或属于该身份 |
| portrait manifest / 人审 | 身份焦点、方向、关键结构、错误姿态和负例 | 只反映头像构图，不足以证明剧情和完整美术风格 |
| 维护者补充 | 制作意图、未落盘关系、创作选择 | 必须形成明确人类回执，不能只留在聊天记录 |

### 6.2 每条证据必须记录

- `sourceType`；
- 仓库相对路径；
- 可复现 locator：XML node、JSON pointer、symbol/frame、函数或行标签；
- 文件 hash / inventory digest；
- 提取器版本和时间；
- 原始值与最小必要片段；
- `supports / contradicts / contextualizes` 关系；
- 是否可能剧透；
- 是否只构成缺失证据，而非否定事实。

模型收到的是经确定性提取和限长的 packet，不直接漫游整个仓库后自由总结。packet 必须保留 unresolved、conflict 和 missing，不为追求闭包而编造字段。

## 7. 怪物档案的讨论维度

### 7.1 正文与正史权限

| 字段组 | 建议内容 | 初始优先级 |
|---|---|---:|
| `internalSynopsis` | 面向制作组的身份、剧情作用、战斗体验和视觉记忆点简介 | 必需 |
| `publicSynopsisByDisclosure` | 按玩家认知阶段投影的短简介 | pilot 必需 |
| `canonicalClaims` | 有明确仓库证据支持的事实列表 | 必需 |
| `inferences` | 从多项证据推断、允许被推翻的结论 | 必需 |
| `creativeProposals` | 可供制作组选择的新设定或美术展开 | 可选，永不自动发布 |
| `unknowns / conflicts` | 证据不足、互相矛盾或需要维护者裁决的事项 | 必需 |

简介不是一段无结构 prose。建议先生成事实型内部简介，再派生玩家文案；玩家文案不能成为反向证明内部事实的来源。

### 7.2 叙事与关系

- 阵营、组织、地域和时代来源；
- 物种、改造/感染/机械/超自然起源；
- 剧情身份：路人、守卫、猎手、干部、首领、关键人物、隐藏角色；
- 与其他身份的上下级、同型、宿敌、召唤者、载体、换皮或形态关系；
- 首次引入事件、后续变化和结局状态；
- 正史置信度与维护者裁决状态。

### 7.3 关卡与遭遇

- 首次可见、首次战斗和重复出现位置；
- 主线、支线、挑战、竞技场、彩蛋或未实装；
- encounter tier：普通、强化、精英、Boss、唯一、剧情保护目标；
- 单体/群体、伴随单位、波次职责和地形关系；
- 玩家在该阶段应当知道什么，不应知道什么。

### 7.4 战斗身份

- 近战/远程/混合、有效距离和移动方式；
- 坦克、突击、狙击、控制、召唤、支援、爆破、处决等战术角色；
- 标志性招式、攻击节奏、预警信号和核心威胁；
- 防御、抗性、霸体、闪避、阶段变化和死亡机制；
- 玩家识别与应对要点；
- 招式名称是内部代码名、玩家可见名还是模型概括。

战斗标签需要代码/配置证据与关卡语境共同支持，不能只按最高属性或角色名字推断。

### 7.5 视觉身份

- `primaryVisualAnchor`：头/脸、面具、核心、武器、引擎、多头、多身体等第一识别点；
- `secondaryVisualAnchors`：在主焦点较弱时共同构成身份的结构；
- 轮廓、体型、姿态、朝向、对称/非对称与数量关系；
- 材质：肉体、骨骼、布料、装甲、机械、能量、烟雾、液体等；
- 主色、辅色、局部高亮和不可被背景吞没的色域；
- 动作与特效母题；
- 必须保留、允许受控裁切和禁止突出的位置。

头像人类反馈可以为视觉锚点提供强证据，但不能独立决定完整角色设定。

### 7.6 美术导演

- palette family 与对比关系；
- motif：电路、扫描线、符文、轨道、余烬、裂纹、雾、血脉、爪痕、军武模板等；
- frame topology：角框、圆环、破损、机械接缝、有机边缘、双主体结构等；
- ground / ambient：地面光、阴影、粒子、烟雾、光晕；
- motion：呼吸、扫描、脉冲、余烬、漂浮、故障、震颤；
- intensity：普通、精英、Boss、唯一剧情单位的装饰强度；
- prohibitions：不得遮脸、不得制造不存在的武器、不得使用会与 UI 危险/锁定状态冲突的色义。

美术导演是“语义到有限配方”的映射，不是为每个身份生成任意 CSS。个体差异通过 token 组合和有据可查的 override 表达。

### 7.7 剧透与披露

建议至少讨论以下状态，最终名称由消费者协议决定：

```text
unseen → encountered → defeated → recruited/adopted → post_arc
```

每个 claim 和 public synopsis 都声明最低披露阶段；消费者只能请求当前阶段允许的投影。未解锁身份可以显示剪影、通用称谓或零信息卡，不得仅因资产已经存在而显示真名、完整头像、阵营反转或后期形态。

### 7.8 Provenance 与质量

- evidence digest、profile schema version、prompt digest；
- model、effort、service tier、worker/controller hash；
- claim 级 evidence refs、confidence 和 canonicality；
- human decision、编辑前后文本、reviewer receipt；
- superseded 输出和负例；
- promotion 与 consumer verification 状态。

## 8. 为什么先写简介、再归纳标签

预先定义的标签容易复刻当前 `portrait-resolver.js` 的名字正则问题：`马尾`误判为兽类、`火凤`漏掉凤凰、所有“方舟”单位被压成同一主题。推荐使用两轮过程：

1. 为黄金集生成尽量丰富但有证据边界的内部简介和开放词汇特征。
2. 把全语料放到 corpus-level 归纳阶段，聚合同义词、层级和共现模式。
3. 人类冻结 controlled vocabulary、互斥字段、多选字段和例外规则。
4. 使用冻结词表重新标注全部身份；旧开放标签只作推导证据，不直接进入消费者。
5. 统计未覆盖项和过度宽泛标签；必要时迭代词表，而不是给单个怪物塞临时 substring。

建议至少把标签拆成独立维度，而不是一个扁平数组：

```text
faction / origin / species / narrativeRole / encounterTier /
combatRole / mobility / threatPattern / visualMotif / material /
signatureAnchor / artIntensity / disclosureRisk
```

`Boss`、`机械`、`红色`、`远程`分别属于遭遇、起源/材质、视觉和战斗维度，不能混在同一枚“主题标签”里。

## 9. 美术语言如何由标签展开

确定性 art recipe compiler 的输入应是人审后的档案和受控标签，输出是 consumer-neutral 的主题意图，再由 Team、Arena、图鉴各自映射尺寸和动效预算。

建议分三层：

1. **阵营基底**：保证同组织的视觉亲缘，例如基础色域和主纹样。
2. **战斗/身份修饰**：狙击、爆破、召唤、Boss、唯一角色增加对应结构和强度。
3. **个体签名**：只使用该身份有证据的核心、武器、面具、多主体或招式母题。

示意组合：

```text
方舟阵营基底 + 护士/支援节奏 + 医疗十字与脉冲扫描
亡灵基底 + 重装坦克 + 裂纹装甲与低频地面震颤
机械基底 + 车载爆破 + 车尾发动机热光与警戒模板
```

最终 CSS/SVG 只能引用白名单 token。模型输出未知 token、任意颜色值、任意滤镜或与 UI 状态冲突的组合时，编译器必须拒绝。

```json
  "provenance": {
    "evidenceDigest": null,
    "humanReviewReceipt": null,
    "status": "draft"
  }
}
```

实现前必须决定 XML、JSON 或“人类可维护真源 + 生成投影”的格式；字段名和枚举目前均可修改。

---

## 11. 模型职责与可替换性

建议把一次身份处理拆成不同职责，而不是让一个上下文同时做事实、创作和自审：

| 角色 | 输入 | 输出 |
|---|---|---|
| evidence summarizer | 单身份 evidence packet | 事实、未知和冲突，不创作 |
| gameplay analyst | 属性、行为、关卡证据 | 战斗身份与应对体验 |
| narrative editor | 事实摘要、任务对白、披露门 | 内部简介和分阶段玩家文案 |
| art director | 视觉帧、头像反馈、已审语义 | 视觉锚点和受控 art recipe |
| corpus taxonomist | 全体已审简介和开放特征 | 标签层级、同义词与例外提案 |
| independent critic | 原始 packet + 候选输出 | 证据缺失、矛盾、剧透和越权创作 |

初期可以让 Luna Max 承担高吞吐草稿和独立复核，复杂冲突再升级到旗舰模型或未来 challenger。但模型选择是运行配置，不进入档案语义；每轮都记录 provenance，禁止因模型升级覆盖人类已审内容。

头像工程的 Fast6 selection 只证明特定视觉选帧负载的调度能力。知识 pilot 应从 8–12 身份/作业、2–3 个并发开始记录 token、墙钟、schema 失败、证据遗漏和人工修改率，再决定是否升到 Fast6；不能直接继承视觉定位的并发结论。

---

## 12. 人类参与与偏好数据

建议决定状态：

| 状态 | 含义 |
|---|---|
| `pass` | 事实、简介、标签和披露边界均接受 |
| `edit` | 身份正确，人类已直接修改 |
| `insufficient_evidence` | 证据不足，保持未知或补采集 |
| `identity_conflict` | 别名、换皮、形态或来源映射需要裁决 |
| `canon_violation` | 把推断/创作写成正史 |
| `spoiler_violation` | 低披露阶段泄露后期信息 |
| `art_direction_revision` | 语义可用，美术组合需调整 |

每一次人类编辑同时保存原输出、最终文本、修改类型和适用维度；后续批次检索当前正例和 superseded negative。不能只保存最终文案，否则无法判断模型究竟在哪类推理上持续出错。

继续沿用头像工程的人类时间合同：页面不限制六行；批次规模按 `下一批身份数 × 预计需复议率 ≤ 6` 调整。公开正史文案仍要求逐身份或按严格同源族群完成显式人审，不能用低异常率跳过签署。

## 13. 分阶段实施建议

### P0：维度和权威冻结

- 决定 §17 的必需问题；
- 选择 24–32 个跨阵营、战斗角色、剧情等级和视觉结构的黄金身份；
- 人工写或深度审定黄金档案；
- 冻结 claim canonicality、披露阶段和 reviewer 状态。

### P1：确定性 evidence extractor

- 建立身份/别名/variant/关卡实例图；
- 从属性、关卡、任务、对白、行为和素材生成限长 packet；
- 绑定 locator、hash、提取器和 conflict/missing；
- 不调用模型、不写正式档案。

### P2：模型档案 pilot

- 在黄金身份上分别运行事实摘要、玩法分析、简介和美术提案；
- 记录质量、耗时、使用量、修改率与 common-mode error；
- 形成 reviewer 页面和第一批人类偏好；
- 只有 pilot 通过后才批准全量草稿。

### P3：全语料标签归纳

- 先生成开放特征，再做 corpus-level 聚类和同义词归一；
- 人类冻结 controlled vocabulary；
- 重新标注全部身份并检查覆盖、互斥和例外；
- 不让模型自行新增生产标签。

### P4：美术 recipe pilot

- 选择 12–20 个代表身份生成受控 recipe；
- 同时渲染 Team 完整/紧凑、80px、Arena 和未来图鉴预览；
- 分离怪物身份主题与 UI 状态色；
- 通过人审后再扩展全量。

### P5：档案与 recipe promotion

- 完整 schema、source、review 和 artifact closure；
- 单一 controller 原子 promotion，可回滚；
- 公开文案、内部档案和 Web 展示配置分别发布，不互相冒充验收。

### P6：消费者接入

- 图鉴/百科、Team、Arena、领养页逐个消费允许的投影；
- 每个消费者独立验证剧透、fallback、尺寸、动效和性能；
- 一个入口通过不等于所有消费者通过。

---

## 14. 状态阶梯与验收边界

```text
identity_resolved
→ evidence_extracted
→ profile_drafted
→ taxonomy_proposed
→ human_reviewed
→ art_recipe_compiled
→ promoted
→ consumer_verified
```

- `identity_resolved`：身份和别名闭合，不等于有剧情证据。
- `evidence_extracted`：packet 完整且可复现，不等于简介正确。
- `profile_drafted`：模型 schema 合法，不等于正史或可发布文案。
- `taxonomy_proposed`：全语料归纳完成，不等于词表已冻结。
- `human_reviewed`：当前 digest 的必审项已处置，不等于写入生产。
- `art_recipe_compiled`：白名单配方可渲染，不等于艺术验收。
- `promoted`：经回执的档案/recipe 已写入正式位置。
- `consumer_verified`：指定入口的披露、视觉和 fallback 已验证；不能跨消费者外推。

## 15. 存储方案候选（未决）

| 方案 | 优点 | 风险 |
|---|---|---|
| 直接扩展 `enemy_properties` XML | AS2 现有加载链直达 | 长文案、数组、provenance 和 pet-only 身份会污染数值权威 |
| 新建 `data/monster_profiles/*.json` | Web/工具友好，结构清楚 | AS2 若消费需新增加载/投影；JSON 注释和人工维护体验需治理 |
| 新建 `data/monster_profiles/*.xml` | 符合现有 list.xml 模式 | 深层结构和多语言正文较笨重，XMLParser 单值/数组陷阱明显 |
| 人类真源 + 生成 XML/JSON 投影 | 可同时服务 AS2/Web并保留 provenance | 引入新生成器和双产物一致性门，必须明确唯一 source of truth |

当前倾向：`enemy_properties` 只保存稳定可选 `profileRef`；人审后的档案进入独立 `data/monster_profiles/` 真源；evidence/model/review provenance 进入工具生成闭包；Web 美术 recipe 进入独立展示配置。具体文件格式必须由 24–32 个黄金档案的维护体验决定。

## 16. Pilot 开工门

只有同时满足以下条件才从文档讨论进入实现：

1. 用户明确授权 P0/P1，而不是只要求继续讨论；
2. 冻结一期身份范围和 profile/asset/encounter 的映射原则；
3. 冻结内部与玩家简介的受众、长度和披露阶段；
4. 冻结 `canonical / inferred / creativeProposal` 的 promotion 权限；
5. 选出黄金身份并有人类基准；
6. 决定 canonical 存储候选和生成投影边界；
7. 定义 evidence packet schema、locator 和 digest；
8. 定义 reviewer 状态、导出/回执和 stale/partial 门；
9. 重新 probe worker/model/service tier；
10. 明确 pilot 不写生产数据，失败可整批丢弃。

## 17. 尚待讨论并冻结的问题

1. 一期覆盖 214 个 enemy identity，还是 221 个 consumer identity 并集？
2. `拟态投影` 等头像别名是否拥有独立知识档案；什么条件下允许共享？
3. 不同战斗形态何时拆 profile，何时只作 variant/encounter override？
4. 玩家简介首先服务图鉴、Team、Arena 还是新的百科页？
5. 披露阶段如何映射现有主线进度、任务链、击败和领养状态？
6. 制作组允许 Luna 提出多大范围的新世界观；谁有权把 creative proposal 晋升为 canonical？
7. 简介的文风、长度、多语言和专名规范是什么？
8. 战斗体验是只陈述机制，还是允许给玩家明确 counterplay 提示？
9. 标签词表采用几层层级；哪些字段必须互斥，哪些允许多选？
10. 阵营基底、战斗修饰和个体签名各自允许覆盖哪些美术 token？
11. 所有玩家文案是否逐条人审，还是先只发布高价值身份？
12. profile 真源使用 XML、JSON，还是人类真源 + 双投影？
13. 未来 Arena/图鉴是否需要不同披露和 art recipe 预算？
14. 何时建立跨模型盲测；黄金集如何防止被提示输入污染？

这些问题没有答案前，本文只能作为讨论底稿，不应被引用为已经冻结的产品合同。

---

## 18. 建议的下一步

下一次只讨论并冻结 §17 的前六项，随后确定 24–32 个黄金身份名单和档案模板。不要同时实现 extractor、全量调用模型和接入消费者。

当维度讨论完成后，第一段施工应是 **P1 确定性 evidence extractor + 无模型 fixture**；只有 evidence packet 能被人工复核、重复生成和 digest 闭合后，才启动 Luna pilot。
