# Audio v2 治理失控与人类注意力预算复盘（2026-08-15）

**文档角色**：事故复盘 / human-care 反例语料；不是 canonical 流程、发布授权或验收状态。
**最后核对代码基线**：commit `539fa306181da40d092c03508afdbddef18eff8d`（2026-08-15）。
**事件列车**：正式 Source `48c312234ab189b16f9edd2f5f7b0b2e78fc1407`，promotion receipt 见 [`docs/evidence/audio-v2/audio-v2-emergency-owner-promotion-2026-08-15.json`](evidence/audio-v2/audio-v2-emergency-owner-promotion-2026-08-15.json)。

## 1. 复盘问题

这次失败不是“有没有认真验证”，而是验证与治理没有持续回答三个问题：

1. 当前步骤是否会改变产品或发布决策？
2. 机器能否无人值守完成？
3. 它是否比更早的真实构建更有信息价值？

结果是 Audio 专项状态机逐渐从风险控制工具上升为施工主体，人类被迫充当 hash、receipt、设备动作与阶段状态之间的同步总线。

## 3. 时间与价值拆账

以下是按独立根因和墙钟窗口做的保守区间，部分机器任务与人工窗口重叠，不能机械相加：

| 类别 | 估算 | 判断 |
|------|------|------|
| 实质代码 / 缺陷修复 | 86–120m（约 17–23%） | 包含 Audio 修复、Ordinal、dependency allowlist、content sniff、materialization closure |
| 必要机器构建 / 策略 / promotion | 35–60m（约 7–12%） | 双 builder、policy、strict verifier、原子部署 |
| 可避免的合同、文档、重复准入与绕行 | 4h45–5h30（约 55–64%） | 四轮 proposal / acceptance、重复证据准备、紧急旁路施工 |
| 人类真实产品操作 | 动手约 8–15m；在线窗口约 35m | 听感、TWS / Realtek、休眠 / 唤醒具有真实价值，但时序过早 |

Audio 的物理性解释了“为什么仍需要一次人类验收”，不能解释“为什么人类必须跨多个小时持续复制粘贴”。最终 emergency 路径已经证明：工程完整性可以无人值守完成，产品听感可以诚实后置且不伪造通过。

## 4. 明确反例

### 反例 A：小修使整套人工 acceptance 失效

Ordinal 排序、`global.json` allowlist、content sniff 都是小而明确的工具修复，却分别触发 R5、R6、R7 proposal 与逐字 H1。commit / hash 变化被错误地等同于“人类风险决定变化”。

**约束**：目标、权限、风险与不可逆性不变时，既有 owner 决定持续有效；新 Source / request 由机器重新绑定，不重新索取人类原文。

### 反例 B：先做 35 分钟物理验收，后做 3 分钟可证伪构建

物理 A6 完成后没有产生新的 Audio runtime 修复；正式构建随后很快发现 source bundle 漏 39 个必需输入。

**约束**：先做 materialization dry closure 与真实构建，再占用人耳、人眼或设备切换；物理验收默认在最小可运行候选后，只有当前授权和既有 release contract 允许时才可作为部署后 canary。

### 反例 C：人类成为机器状态总线

逐字 acceptance、hash、runId、设备阶段和 request link 被拆成多轮同步动作。信息本来都能由仓库、进程和构建产物读取。

**约束**：机器标识与证据由持久 orchestrator 传递；一次独立风险决定最多请求一次人类回复。

### 反例 D：为修流程继续叠流程

原 Audio 状态机无法满足“先部署、验收后置”的 owner 决定后，又临时新增数百行 emergency 旁路。它解决了当晚部署，也证明原流程缺乏简单的风险分层。

**约束**：不要为例外复制完整状态机；保留 immutable request、双 signer / faultDomain、production policy、strict verifier、atomic rollback，体验证据可独立标记 pending。

### 反例 E：验证器变成主要缺陷来源

Closure 排序、根路径 allowlist、内容嗅探和 JSON / EOL 边界先后阻塞证据装配；多数问题属于 qualification 工具，而不是 Audio 产品行为。

**约束**：同一 gate 进入第三轮修正时必须停止机械新增 revision 并独立审查根因。可选、低价值 gate 才可在风险权威同意后合并或移出关键路径；安全、权限、完整性与真实性硬门不因次数放宽。验证工具的正确性不能靠同一 helper 自证。

### 反例 F：持续状态播报占用主上下文

长构建本可由 run id、resume 和日志无人值守等待，却产生大量“仍在运行”的同步消息。

**约束**：状态只在 blocker、实质变化和完成时进入主上下文；心跳留给 monitor。

## 5. 哪些门仍然是硬门

本复盘不主张“为了快而不验证”。以下控制直接保护交付真实性和可恢复性，仍应 fail-close：

- immutable Git-tree request 与 source-tag 绑定；
- 两个真实 signer 与 fault domain；
- build identity / payload closure 一致；
- production policy、strict bundle / consensus verifier；
- atomic promotion 与 rollback；
- 对未完成产品验收诚实标记，不把 `promoted` 冒充 `standard_entry_verified`。

应移出关键路径的是重复的人类确认、纯机器证据搬运、不能改变行动的证明，以及在真实构建前完成的高成本体验验收。

## 6. 治理验收用例

以后新增或修改工程流程时，用以下反例做审查：

1. 用户说“部署优先、体验验收后置”后，小修与新 commit 不得再次索取同一决定。
2. 用户说要睡觉后，安全且已授权的 build / wait / verify / promote 应继续；不能要求其定期回来复制状态。
3. request 前必须证明 build manifest 所需输入属于 materialized source closure。
4. 第一次真实 build 必须早于非安全、非阻断的完整物理验收。
5. 人类只填写机器无法知道的产品判断，不填写 hash、tree、runId 或 schema 模板。
6. 同一 gate 第三次阻塞时，默认审查 gate 本身，而不是创建下一 revision；次数本身不授权删除或放宽保护门。
7. human-care 不得产生任何 receipt、状态位、时限或签字要求。
8. 如果新治理会多出一次同步回复、一次等待或一份重复文档，它必须证明减少了更大的不可逆风险；否则拒绝。

## 7. 结论

这次工程失控的主因不是 Audio 天生无法自动化，而是产品验收、发布完整性和流程整洁度被串成单一线性状态机。正确结构应是：发布完整性由机器硬门无人值守完成；产品体验由人类在最有信息价值的时点做一次集中判断；流程自身持续接受成本审查。
