### 0.3 已冻结的提案摘要

- `D1`：先修来源变体、概率单位、数量边界与用途反向索引，再做视觉增强。
- `D2`：默认顺序不是字典序；以完整 authored material catalog 的物理顺序为权威，初始顺序固定为旧材料大全 58 项原序 + 其余 166 项 Item XML 载入序。
- `D3`：`material_dictionary.xml` 进入确定性 producer / `--check` 门，但先拆 authored 与 generated；禁止发布过程静默改写。
- `D4`：树是“单一路径浏览 + 一种材料多归属”，根分支为“类型 / 用途”，不是多选 Facet 查询。
- `D5`：enemy/stage 一种逻辑掉落来源一张卡，其每个 XML occurrence 进入有序 `variants[]`；craft/shop/kshop/quest occurrence 各自保留为独立来源卡；唯一来源数与掉落档位数分开。
- `D6`：用途行以 exact `{category, recipeIndex}` 跳到同一 crafting 壳的配方模式，不按同名产物猜。
- `D7`：材料到 NPC 商店只走 typed Web→Host 路由；聚焦提示无购买权，不建立通用 panel 历史栈。
- `D8`：敌人与 NPC 头像只消费 exact identity 的确定性资产；缺图 fail-soft，不能绕过发现制。
- `D9`：默认排序为“档案顺序”；metric 固定为“持有种类 x / y”，不是“已收录”。
- `D10`：新增字段进入显式 v2 合同，以首个 materials success 选择会话版本；v1 只进入明确标记的有限兼容视图，不给现役严格 v1 校验器静默加键。
- `D11`：基建材料以 `system:infrastructure_upgrade / 基建升级` 进入用途树；`infrastructure.xml` 仍是 67 个 occurrence / 21 个 unique identity 的唯一静态真源，详情另按已发现基建投影逐项目、逐等级的需求角标与缺口状态；总持有量沿用详情标题，不在每级重复，但不增加“前往基建”。

- 不解析 `description` 或 `material_dictionary.xml` 的自由文本来生成分类、来源、头像或跳转。

## 1. 一页裁决

### 1.1 路线

本提案冻结以下施工顺序：

```text
来源/用途的 AS2 数据底座正确性
    → authored catalog、档案顺序与确定性生成门
    → 完整 v2 材料合同与共享多路径筛选
    → 排序、metric、来源卡、头像与空态
    ├→ exact 配方跳转（A4a）
    │    └→ non-shop current-tree 集成、真实旅程与文档回流（A5）
    └→ O6 方案 2 下的 Host-owned 商店导航（A4b）
         └→ 必须重开 A5 的 shop delta / PG-MAT-SHOP / 对应 E2E
```

树状导航、头像和跳转都值得做，但它们依赖的数据目前并不全都正确。截图中同一敌人的多条等级档没有全部显示，不是 CSS 或循环渲染问题：AS2 索引在加入第二条同源记录前就按 `(itemName, dropType, sourceName)` 返回。现役 Web 还混用两套不同的概率语义。若先美化，页面只会更清楚地展示不完整或错误的数据。

### 1.2 对用户四个问题的直接结论

1. **其他材料值得标注用途**，但只接受结构化来源：配方用途由真实配方数组按 occurrence 反查；直接系统用途由受控 ID 与调用点证据显式维护；没有证据时显示“尚未结构化”，不写“无用途”。
2. **NPC 头像可以从 Flash 端确定性解出并复用**。现有 dialogue portrait baker 已证明大部分链路；需要重烘焙当前 Flash 源、补齐 provenance 与商店 exact 映射。`heeho君` 没有现成对话头像配置，必须从其地图 XFL/SWF 元件精确映射，失败即停，禁止猜别名。
3. **敌人多条掉落确实被 AS2 去重吞掉**，且影响范围不止截图材料，也包括少量关卡重复奖励。目标不是画四张重复头像卡，而是两张敌人来源卡、卡内四个有序档位。
4. **默认顺序应恢复为可控的 XML 物理顺序**。旧 AS2 材料大全实际只按 `material_dictionary.xml` 的 58 项物理顺序显示，并不是按全部 item XML。全量 224 项因此采用“旧 58 项原序为前缀 + 未收录 166 项按 Item 载入序追加”的迁移序列，随后由完整 authored catalog 的物理顺序统一管理。

商店跳转另有一个不能被 UI 方案掩盖的产品边界：材料页随时可开，直接打开完整 NPCShop 会形成远程购买入口。维护者已显式选择 O6 方案 2，接受“所有已索引 shop source 均可远程打开完整 NPCShop 并随后按现役规则购买”的能力扩张。这个产品决定不把静态 `shopId` 变成 authority：current-tree 已以 AS2 点击时 exact source/catalog authorization、Host exact transition 与 target fresh catalog Gate 实现；任一证明缺失仍 fail closed。

### 1.3 关于 `material_dictionary.xml` 的裁决

应该纳入发布门，但不是把现文件直接改造成“从所有来源自动生成的真源”。目标是：

- 新建完整 authored material catalog，承载 224 项闭包、物理顺序、类型、受控直接用途、旧 UI 可见性和编辑性摘要；
- `material_dictionary.xml` 变为该 catalog 的兼容投影，继续只表达被明确标记为旧 UI 可见的条目；
- producer 只机械投影 authored 字段，**不**把敌人/关卡配置拼成自由文本摘要；
- CI / 发布数据门运行 `--check`，发现输出陈旧、漏项、重复、未知 identity 或非确定性即失败；
- 真正更新产物必须由开发者显式运行 producer，发布 prepare 不得静默改工作树。

这能确保目录与兼容产物不会悄悄过期，同时保留摘要的策划语义和来源发现制。它是 release-time deterministic closure，不是运行时“实时生成”。

## 3. 目标、非目标与产品语义

### 3.1 目标

- 默认顺序可审查、可控制，并与旧 AS2 已收录材料的顺序一致。
- 分类树同时服务改装材料、食材与普通材料；一种材料可有多个真实用途。
- 结构化来源完整表达同敌人/同关卡的所有条件档与 occurrence。
- 来源概率、等级、数量、价格与解锁文案来自各自权威 producer，不在 Web 猜测。
- 头像提升可扫读性，但缺图、迟到或 manifest 失败不影响文本与导航。
- 用途行能定位 exact 配方；商店行能打开 exact NPC 并非权威地聚焦目标商品。
- 键盘、焦点、滚动、空态、失败恢复与异步 epoch 有机械验收合同。
- 数据 producer、兼容 XML 和资产 manifest 均能以确定性 closure 门防止陈旧发布。

### 3.2 非目标

- 不做多选 AND facet、任意 tag 编辑器或 description / summary 全文语义解析。
- 不改变来源发现制，不把静态 summary 或 portrait manifest 变成掉落权威。
- 不在本期增加敌人/关卡跨面板导航。
- 不建设通用 `returnTo` registry、panel stack 或 DOM / scroll 历史恢复框架。
- 不让导航产生购买、预览、加购、数量或 commit intent。
- 不对互斥等级档概率求和，不由 Web 猜测完全相同 occurrence 是否可合并。
- 不因排序需求重构所有 Team dropdown；只允许抽取窄的 Workbench primitive。
- 不在本期把 58 项旧 Flash 材料大全直接扩为 224 项；容量、滚动、性能和剧透语义另行验收。
- 不把“持有种类”包装为发现/收集成就系统。

### 3.3 保留的产品语义

- 结构化敌人/关卡来源继续是发现制：未发现 identity 不进入 AS2 回包，因而也不进入 DOM、计数或头像请求。
- `material_dictionary.xml` 的 `Information` 是“档案摘要”，不是完整实时来源清单。
- 价格展示最多是打开详情时的权威快照参考价；进入商店后必须从商店 authority 重新构建，不能把档案快照当交易报价。
- 原 AS2 已收录 58 项的相对顺序是迁移 oracle；新增全量目录的尾部顺序由明确规则初始化，之后只接受 authored catalog 的物理顺序变化。

## 4. Current-tree 事实与根因清单

### 4.1 当前材料回包与 Web 能力

`[C]` `CraftingPanelService.executeMaterials()` 当前把字典与 `ItemUtil.materialDict` 合并后执行 `names.sort()`，每项只投影：

```text
name / displayName / icon / owned /
sourceCount / useCount / hasSourceSummary
```

详情投影为材料基本信息、scalar `sources[]` 与 scalar `uses[]`。`crafting-materials.js` 当前已有搜索、持有/有用途 quick filter、grid roving focus 和卡片 tooltip；因此“网格 hover tooltip”不是新协议功能，本期只做视觉与回归收口。

`[C]` crafting 配方模式已经使用共享 `FilterNavigator` 和 `Workbench.ViewChrome.breadcrumbHost`，材料模式尚未接树。`ItemFilter.build()` 当前一项只接受一条 raw path；材料多用途需要向后兼容的 `buildMany()` 或等价 API，不能把材料 taxonomy 写回默认 `catalogPath()`。

### 4.2 数量与分类底盘

current-tree 静态闭包为：

| 数据集 | 数量 | 说明 |
|---|---:|---|
| `use=材料` 总数 | 224 | 全量材料目录 |
| `收集品_材料.xml` | 78 | 普通材料 |
| `收集品_材料_插件.xml` | 101 | 插件材料 |
| `消耗品_材料_食材.xml` | 45 | 食材 |
| 语义上的改装材料 | 105 | 101 个插件材料 + `equipment_mods/特殊材料_防具专用.xml` 中覆盖五个防具槽的 4 项：异形龙骨碎片 / 剑圣碎片 / 国庆纪念币 / Andy套装碎片；不是 `特殊材料_通用.xml` 的额外 4 项 |
| 当前真实配方使用过的材料 | 88 | 按现役配方数据静态反查 |
| 非改装材料中有配方用途 | 39 | 其余不能直接断言“无用途” |
| 食材中有当前烹饪配方用途 | 9 / 45 | 说明仅靠 recipe 不能覆盖全部语义 |

`[D]` 因此分类不能只复制改装三维元数据，也不能给所有非插件材料落一个不可解释的大桶。目标分类由“类型”与“用途”两个并列浏览轴组成，直接系统用途必须显式 authored。

### 4.3 原 AS2 顺序并不是全量 Item XML 顺序

`[C]` `frame64.as` 把 `data/dictionaries/material_dictionary.xml` 的 `data.Material` 赋给 `_root.图鉴信息.材料大全`；旧平板材料 UI 直接按该数组数值循环。文件当前只有 58 项，名称全部有效且无重复。

`[C]` 全量 item XML 有 224 个材料。对 58 项交集比较时，57 项相对位置与全量 Item XML 子序列不一致。因此以下两句话不能同时成立：

- “完全按旧 AS2 材料 UI 顺序”；
- “完全按所有 item XML 的物理顺序”。

`[D]` 迁移序列固定为：旧字典 58 项逐项保持原序，之后追加 `ItemUtil.itemDataArray` 中尚未出现的 166 项。当前基线预期边界是 `archiveOrder=0 军用帆布`、`57 毒素样本`、`58 神铁碎片`、`223 蚝油`。最终序号由 authored material catalog 生成，而不是 Web 按当前过滤后的 index 临时计算。

### 4.4 同源多档在 `obtainIndex` 投影时被 AS2 去重吞掉

`[C / A1 blocker]` `ItemObtainIndex.rebuildEnemyCacheFromData()` 遍历 XML 中每一条掉落，但 `addDropRecord()` 遇到相同 `(itemName, dropType, sourceName)` 就直接返回；概率、等级与数量条件不参与 identity。

current-tree 静态扫描结果：

| 范围 | 受影响逻辑来源组 | XML occurrence | 当前保留 | 静默丢失 |
|---|---:|---:|---:|---:|
| 材料敌人 `(item, enemy)` | 70 | 161 | 70 | 91 |
| 敌人档位分布 | 54 双档 / 11 三档 / 5 四档 | — | — | — |
| 材料关卡 `(item, stage)` | 1（不锈钢材 / 中秋国庆副本） | 2（分母 10 / 20） | 1 | 1 |
| 全物品旁证，不计入材料闭包 | 另 5 个 `(item, stage)` 组 | 均为非材料“突击步枪通用弹药”的完全相同 occurrence | 每组仅首条 | 其余 |

截图中的“战术握把”应显示：

- 军阀精英突击兵：`3% / 等级 ≤ 2` 与 `5% / 等级 ≥ 3`；
- 重型改造僵尸：`3% / 等级 1–3` 与 `5% / 等级 ≥ 4`。

正确视觉是两张敌人卡、共四行档位，不是四张重复敌人卡。关卡中的完全相同记录也不能静默丢失；它可能表示两个独立 occurrence。本合同一律逐 occurrence 投影和逐行显示，不折叠、不生成 `×N`，从而让 `occurrenceIndex` 与 `dropVariantCount` 保持唯一口径。`rebuildStageCacheFromData()` / `rebuildEnemyCacheFromData()` 的 cache 侧原本就按输入保留 occurrence；丢失发生在 `addDropRecord()` 投影到 `obtainIndex` 时。A1 应保持 cache 输入顺序并修正 grouped index，不要误把 cache 一并压平。

### 4.5 现役 Web 对概率单位的猜测是错误的

`[C / A1 blocker]` `crafting-materials.js` 当前先用 `Number(source.probability || 0) > 0` 决定是否显示，再对 `probability <= 1` 使用 `Math.round(probability * 10000) / 100`，否则直接显示原值；`0` 与非法值不会显示。这个启发式仍把两种不同原始语义混为一谈：

- 敌人 XML 的 `概率` 是 `0..100` 百分点，原始值 `1` 应显示 `1%`，现逻辑会显示 `100%`；
- 关卡 `AcquisitionProbability` 在默认分支是 `random(N) == 0` 的分母，`1→100%`、`2→50%`、`8→12.5%`、`50→2%`，不能直接加 `%`；现役奖励 UI 还保留 AndyLaw 域名 predicate，命中时改走 `random(Math.floor(N) / 2) == 0`，不能在未证明该分支对支持的 standalone runtime 不可达前把完整运行时模型简化成 `100/N`。

current-tree 对全部物理 stage data XML 的静态扫描有 351 条材料相关 Reward，分母覆盖 `1/2/3/4/5/6/8/10/20/28/50`；其中 current stage catalog 可解析闭包为 331 条，另 20 条位于未被 current catalog 引用的数据文件，不能混写成可达来源。仅按默认分支比较时，现启发式只有 `N=1` 与 `N=10` 恰好显示正确，其余 248 条会显示错误，而且完全没有表达条件分支。上述数字只描述本基线，不冻结为长期 schema 常数；active catalog audit 必须单独守 missing/unlisted exact-set，实际可见项仍受关卡发现制控制。

`[D]` enemy v2 producer 必须显式投影 `nominalChancePercent`，UI 固定标为“基础概率/名义概率”，不能冒充单次击杀的实际概率；关卡投影 `rollDivisor + defaultBranchChancePercent`，UI 固定标为“默认分支基准概率”并携受控的 legacy 条件说明。敌人保留规范化数值 `chanceRaw` 与 `chanceInputState`：显式 `0..100` 数值直接成为名义百分比；property 真正缺失时为 `absent_defaulted`，property 存在但 `Number(raw)` 为 NaN 时为 `invalid_defaulted`，两者均按现役 `DropLuckRoller` 投影 `100`。按项目 AVM1 canonical，XMLParser 空元素得到 `""` 且 AS2 `Number("")` 为 NaN，因此空元素属于 `invalid_defaulted / chanceRaw=null / nominal=100`；当前 219 条 enemy 掉落没有缺失或空概率，这一修正针对合同与 fixture，不冒充现存数据事故。实际 enemy roll 还受逆向每级 `+5%` 乘数和 PRD 状态影响。Web 禁止启发式换算或把任一基准值写成“实际掉率”。关卡 divisor 必须是 finite positive integer；A1 必须用 fresh Flash 证据表征 AndyLaw predicate 在支持的 standalone runtime 是否可达，未证明不可达前保留条件模型，数据门遇到非法值 fail closed。

### 4.6 用途反向索引也会丢同名产物配方

`[C / A1 blocker]` `SynthesisIndex.getRecipesUsing()` 从 `_root.改装清单对象` 反查；该对象是 `productName → single recipe`，同名产物后写覆盖。现役 282 条配方只有 280 个产物 identity，`基础防具.json` 内三个 `Andy套装碎片` 配方分别消耗国庆纪念币、月之碎片、剑圣碎片，前两条会从当前用途索引消失。

`[D]` 新增按 `_root.改装清单[category]` 数组逐 occurrence 建立的反向索引。详情中的每条用途至少携带 `{category, recipeIndex, productName}`，不得按 `productName` 去重。旧 `getRecipesUsing()` 可暂留给未迁移消费者，但不能继续作为材料档案计数、分类或跳转真源。

### 4.7 商店来源字段与价格权威

`[C]` `ItemObtainIndex.buildShopRecords()` 当前只记录 `npc`，并读取已经失真的 `requiredInfo_disabled`；现役 NPC 商店权威字段是 `requiredInfo`。真正的 `catalogIndex / basePrice / unitPrice / locked` 由 `商店系统_兼容.as` 的 catalog projector 基于当前口才与配置计算。

`[D]` Crafting 不复制定价和解锁公式。A1 只修正 shop occurrence identity 与 `requiredInfo` 读取；A2 在 detail 请求现场复用或抽取同一纯 AS2 catalog projector，投影当前价格、锁定态与条件快照；A4b 点击时再经 AS2 authority 重新授权，并在打开 NPCShop 后刷新其权威 catalog。不得把三个阶段合并成一份会过期的 ItemObtainIndex 缓存。

### 4.8 `material_dictionary.xml` 是策划摘要，不是机械来源镜像

`[C]` 当前文件 58 项，schema 只有 `Name + Information`；物理顺序、是否收录和摘要措辞均带策划语义。58 条摘要全部是自由文本，其中大量使用“掉落单位 / 掉落关卡 / 掉落副本”标签，但并不枚举所有 current-tree 敌人或关卡来源，也包含旧称、别名、分组、选择性省略和标点表达。

`[C]` 静态 summary 全局可见，而结构化来源受存档发现门控制。若自动把全部结构化来源拼入 summary，会改变剧透语义。`ItemObtainIndex` 还把副本与普通关卡统一成 `dropType=stage`，无法无损恢复旧文案分组。

`[D]` 所以 producer 只投影 authored 摘要，不自动改写自然语言。实时来源准确性由 v2 structured sources 保证；摘要区明确标为“档案摘要”。

### 4.9 头像资产闭包

`[C]` dialogue portrait 现有 manifest 的 90 个键来自 Flash 确定性导出链：68 个外部 portrait SWF + 28 个对话框内部 sprite − 6 个重名覆盖。当前 34 个活跃商店 NPC 中，现 manifest 覆盖 32 个，地图头像覆盖 27 个，两者并集覆盖 33 个。这里的地图口径是 active `shopId` 与生产 `MapPanelData.getPage(...).staticAvatars[].label` 的 exact equality；`map-avatar-source-data.js` 的 symbolName / asset URL 不是 shop identity 表，禁止用去空格、去标点或模糊文件名匹配改写这个计数。

`[C]` enemy portrait manifest 当前登记 226 个 identity：221 个 `ready/human_accepted`、2 个 pending human review、1 个 excluded、2 个 alias；不能概括成“226 项都同时有 SVG + PNG”。本材料闭包涉及的 78 个 enemy identity 当前均为 ready。生产 Team / Arena 通过共享 `EnemyPortraits.mount()` 处理 manifest 冷加载、stale 与 fallback；`resolve()` 只同步读已缓存 manifest，冷启动可能返回 `null`，不能作为材料页的唯一挂载 API。材料来源的 exact `enemyType` 可直接作为 resolver identity；无需修改掉落数据，也禁止解析摘要文本补图。

- `武器大师` 只在当前 `flashswf/UI/对话框界面/LIBRARY/对话框肖像.xml` 的 label 中存在（本基线行 118），对应可导出帧；平板电脑界面版与主 XFL import 版的同名文件不是该证据。现 manifest 生成时间早于此变更，优先 staged 重跑 baker，不预设需要 CS6。
- `heeho君` 不在外部、内部或地图头像 manifest；其真源在彩蛋地图 XFL/SWF 的 `NPC/NPC-heeho君/霜精` 元件。必须完成 XFL→SWF characterId / frame 的精确映射并选 neutral frame；禁止 alias 为没有墨镜的杰克霜精。映射失败时 fail closed，只有正式给对话 UI 增加专用 portrait 才进入 CS6 施工。

`[R]` 现 dialogue manifest 缺少完整 source/tool/output digest，报告仍有非必需 expression miss，且 manifest 已陈旧。材料页不得直接依赖 DialogueView 或 MapPanel 的 lazy runtime；目标是独立的 exact `shopId → runtime subject` manifest，并以分离 sidecar 保存 source provenance。

### 4.10 严格 v1 校验与 Host ownership

`[C]` `CraftingTask.cs` 对 materials/detail/source/use 使用 exact key set。直接给 v1 回包添加 `archiveOrder`、`variants`、taxonomy 或 `recipeIndex` 会被现役 Host 拒绝。

`[C]` NPCShop 是 Host-owned panel，Web 不能自开。`map → stage-select` 的 `open_stage_select` 是可参考的 typed Web→Host 中转，但本项目还必须补 exact crafting `panelInstanceId`、一跳 return fence 与 preferred focus 的无购买意图合同。

## 6. 提案内冻结的架构决策

### D1. 正确性优先于表现

来源变体、概率单位、数量边界与用途 occurrence 是 A1 数据底座；authored catalog、档案顺序与完整 v2 是 A2。树、头像、排序、跳转不得绕过前置 Gate 直接进入生产。允许先做隔离的 UI fixture，但不能接 current production wire 或宣称功能完成。

### D2. 档案顺序由完整 authored catalog 控制

目标新增 `data/dictionaries/material_catalog.xml`，按 XML 物理顺序列出所有有效材料。初次生成必须：

1. 精确复制旧 `material_dictionary.xml` 的 58 项顺序；
2. 追加 `ItemUtil.itemDataArray` 中尚未出现的材料，保持跨文件载入序；
3. 在本基线为 `N=224` 项产生连续、唯一 `archiveOrder=0..223`；长期合同是 current exact-set `N/N` 与 `archiveOrder=0..N-1`，不是把 224 写死进 schema；
4. 新增材料若未进入 catalog，则 `--check` 失败，而不是偷偷追加；
5. 后续重排通过 reviewed XML diff 明确发生，不由 Web、对象枚举或本地化名称决定。

默认每次新鲜打开材料页均恢复“档案顺序”。A1–A5 不持久化 sort 偏好；持久化需另行产品决定。

### D3. authored / generated 拆分与门

`material_catalog.xml` 承载：

- `Name` exact identity；
- 物理顺序；
- `typeId`；
- controlled `authoredDirectPurposeId[]` 与标签表引用；装备改装用途不逐项重复 authored；
- `legacyVisible`；
- `legacyInformation` 编辑性摘要；
- 必要的人工 override，且每个 override 指向可验证 identity。

`material_dictionary.xml` 变为 generated compatibility artifact：只投影 `legacyVisible=true` 的 `{Name, Information}`，保持旧 loader schema 与原 58 项行为，直到独立验收允许扩容。生成器同时产出可审计 sidecar，至少绑定 input、generator version、output SHA-256 与条目数。

发布数据门只执行等价的 `derive --check`，禁止 silent write。正式 producer 命令与 sidecar 物理路径在 A2 实现时登记进 [testing-guide.md](../agentsDoc/testing-guide.md)，此处不伪造尚不存在的命令。

### D4. 类型 + 用途的单路径浏览，多归属材料

树根固定两条并列分支：

```text
全部材料
├─ 类型
│  ├─ 改装材料
│  │  ├─ 档级
│  │  ├─ 适用范围
│  │  └─ 定位
│  ├─ 食材
│  └─ 通用材料
└─ 用途
   ├─ 合成配方
   │  └─ <现役 category>
   ├─ 直接系统用途
   │  ├─ 装备改装
   │  ├─ 基建升级
   │  └─ <其他 controlled purpose ID>
   └─ 尚未结构化
```

- 用户一次只浏览一条路径；搜索、持有、有用途 quick filter 与当前路径做 AND。
- 一种材料可出现在多条叶路径；当前结果集按 distinct `name` 只渲染一张卡。
- 节点计数按 distinct `name`，因此多用途兄弟节点计数之和允许大于父节点；帮助文案解释“一种材料可有多种用途”。
- 配方类别从 exact recipe occurrence 派生；用于 facet 时可按材料 + category 去重，详情不去重。
- 改装材料复用现有 `grade/scope/role` 元数据及 label；食材和通用材料不伪造这些维度。
- `system:equipment_tuning` 的主体由 `EquipmentUtil.modDict/modMeta` 机器派生，并且只投影到 `用途 → 直接系统用途 → 装备改装` 这一条路径；不得再生成同义的用途一级叶。current-tree 另有六个不具完整 mod metadata、但有现役调制 consumer 证据的例外：`强化石 / 二阶复合防御组件 / 三阶复合防御组件 / 四阶复合防御组件 / 墨冰战术涂料 / 狱火战术涂料`，只允许由 catalog exception registry authored 同一个 `system:equipment_tuning` ID，不因此伪造 `modFacetIds` 或 `typeId=equipment_mod`。其他直接用途也来自 catalog 的 `authoredDirectPurposeId[]`。机器派生集合与例外集合 union 后去重，不能为全部 105 个改装材料再维护一份重复真源。
- `system:infrastructure_upgrade` 投影到 `用途 → 直接系统用途 → 基建升级`。其 21 项 catalog 引用必须与 `infrastructure.xml` 的 67 个 `<Material>` occurrence 去重 exact set 相等；详情动态卡只对存档中已发现的项目投影项目名、数组等级位置、需求角标、缺口和完成/当前/后续状态。`owned` 仍参与缺口校验与无障碍说明，但总持有量只在详情标题显示一次；这不改变 taxonomy 计数，也不是升级或导航 authority。
- 每个直接用途必须有 controlled ID、显示标签、authored order 和 current-tree consumer 证据；没有已知用途的条目进入“尚未结构化”，不显示“无用途”。
- “尚未结构化用途”的 membership 精确为 `recipePurposeIds.length === 0 && directPurposeIds.length === 0`；它只表示当前没有已结构化用途，不同时承担“已有用途但审计未完成”的第二种语义。
- taxonomy 顺序也是数据合同：root 固定 `类型(0) → 用途(1)`；type 固定 `改装材料(0) → 食材(1) → 通用材料(2)`；改装子轴固定 `档级(0) → 适用范围(1) → 定位(2)`，各值沿用 tuning 展示词典的物理顺序；配方 category 沿 `data/crafting/list.xml` 顺序；direct purpose 沿 registry authored order；fallback 永远最后。每个 segment 都带显式 `order`，禁止用 `localeCompare` 排 taxonomy。
- 共享 `ItemFilter` 只增加向后兼容的多路径 builder；KShop、NPCShop、Inventory、Equipment、Crafting recipes 的旧分类器与 `catalogPath()` 行为必须零回归。

### D5. 掉落来源一卡多档，其他来源逐 occurrence 保留

逻辑来源 identity：

- enemy：`kind + enemyType`；`enemyType` 是 `_root.敌人属性表/discoveredEnemies` 的 exact key（本例含 `敌人-` 前缀），可读短名只进 `displayName`，producer/Web/portrait 层均不得剥前缀或猜 alias；
- stage：`kind + stageName`；
- shop：`kind + shopId + catalogIndex`；
- craft：`kind + category + recipeIndex`，`recipeIndex` 沿现役 snapshot/preview/commit 链固定为 `0..999`，同 category 的同名产物配方逐 occurrence 保留；
- kshop：`kind + catalogIndex`，同时保留配置 `id` 供复核；
- quest：`kind + questId + rewardSet + authoredIndex`，其中 `rewardSet∈{base,challenge}`；两套 authored 数组各自从 0 编号，同任务重复奖励 occurrence 不按 itemName 静默去重，也不把 challenge index 接到含混的合并序列后。

敌人/关卡卡内 `variants[]` 保持 XML occurrence 顺序；不同来源卡不依赖 `discoveredEnemies` 的 AS2 `for..in` 顺序。producer 的 kind order 固定为 `craft(0) → shop(1) → kshop(2) → quest(3) → stage(4) → enemy(5)`，再按稳定 identity 排序并投影连续 `sourceOrder`：craft 依 category authored order + recipeIndex，shop 依 shopId code-unit order + catalogIndex，kshop 依 catalogIndex，quest 依 questId code-unit order + `rewardSet(base=0,challenge=1)` + authoredIndex，stage/enemy 分别依 stageName/enemyType code-unit order。Web 只按 `sourceOrder` 渲染。

这是 A2 完整 v2 的最终排序合同，不是 A1 internal record 的承诺。current `CraftingListLoader` 会把 category keyed-merge 成 Object 并丢失 `list.xml` 顺序；A1 只修 occurrence identity，A2 必须在 merge 前保留 category-order registry，随后才能投影和验收全局 `sourceOrder`。

`sourceCount` 是逻辑来源数并严格等于 `sources.length`；`dropVariantCount = sum(enemy/stage.variants.length)`，不把 shop/craft/kshop/quest 伪造成一个掉落档位。scalar v1 兼容字段若保留，只镜像首个 drop variant，不能作为 v2 Web 真源。

敌人 v2 variant 的 exact key set 固定为 `occurrenceIndex / chanceRaw / chanceInputState / nominalChancePercent / minReverseLevel / maxReverseLevel / quantityMin / quantityMax`；关卡 variant 固定为 `occurrenceIndex / rollDivisor / defaultBranchChancePercent / quantityMin / quantityMax`，source 另显式携带 legacy conditional model，两者均禁止额外键。未配置的逆向等级边界投影为显式 `null`；未配置的敌人掉落数量按现役掉落规则规范化为 `1/1`。不能把 `0` 同时当真实边界和“未知”。current-tree 的 210 条材料敌人掉落中有 91 条显式数量对，而现索引完全没有投影这些字段，A1 必须同时覆盖“显式数量”与“缺省 1/1”。

### D6. exact recipe use 与同壳跳转

新 reverse-use index 按 category 数组逐条扫描，输出每个真实 occurrence。当前 producer 的用途详情项为：

```text
category / recipeIndex / productName / displayName /
icon / itemKind / required / ingredients[] {
  name / displayName / icon / required / isQuantity
}
```

`ingredients[]` 是当前 producer 的完整配方材料预览；历史 v2 封存数据若缺该新增字段仍可只读回放。非装备需求一律显示数量，只有装备且使用强化门槛语义时才显示最低强化等级。激活“前往合成”后，材料页先在原位进入 `recipe_pending`，保留当前材料 selection、detail 与焦点归属；同一 crafting owner 捕获 exact `panelInstanceId` / lifecycle epoch，并另行推进 Web-local `recipeSnapshotGeneration`，再按 `{category, recipeIndex}` 请求现役 snapshot 并复核 `productName`。refresh 只推进该局部 generation、取消旧 flight，不伪装成新的 Host lifecycle epoch；rebind 才推进 owner lifecycle。只有 panel instance、局部 generation、selection 与 tuple 全部命中后才原子切到 recipes 模式、选中、滚入可见并聚焦该配方。配置漂移、category 消失、超时或请求失败均留在材料页显示 inline 事实与重试，绝不能走现役“preferred index 无效时选中**过滤后可见列表第一条 recipe**”的 fallback。

EquipmentInspector 是用途行中的独立显式动作；一次激活不能同时跳配方又开模态。用途 v2 schema 不复制完整装备纸娃娃数据；该动作必须先复用同一 fresh recipe snapshot preflight，校验 exact `{category,recipeIndex,productName}` 后把权威 `recipe.output` 交给现役 Inspector，迟到或 tuple 漂移仍留在材料页。材料发起的成功跳转在同 owner 提供“← 返回材料”，失败仍留在材料页。

同 owner 的 materials→recipes commit 必须在 exact `panelInstanceId` 上保留既有 CharacterBuild-origin one-shot capability，recipes 模式继续提供既有“← 返回装备”，并为材料来源显示独立“← 返回材料”；两种能力互不覆盖、消费或伪装，普通关闭才进入统一 panel 收尾。

### D7. typed Host 商店路由与一跳返回

静态 shop source 的可见性不等于点击时授权。维护者已在 O6 选择方案 2：凡 current `ItemObtainIndex` 与 live NPC catalog 对 exact `{materialName,shopId,catalogIndex,itemName}` 仍一致的来源，都可远程打开完整 NPCShop，进入后继续按现役价格、锁定、限购、库存与购买 authority 正常交易；未选择 inspect-only，也不从历史打开行为或联系人集合推断权限。材料 v2 的 access pair 只允许以下两组，禁止交叉组合或新增隐式枚举：

```text
full        + indexed_live_match
unavailable + no_authoritative_remote_access_capability
```

A4b current producer 对通过 live join 的 shop source 输出第一组；第二组只用于没有这项 authoritative capability 的受支持降级面并隐藏 CTA。`locked=true` 仍是 `full`；限购是否已满只由进入 NPCShop 后的 fresh snapshot/preview 得知，两者都阻止相应购买而不阻止导航。Web 只能把 pair 当展示 hint；每次点击仍由 Host 请求 AS2 重新授权，caller allowlist、静态 shopId、Web 回显和 portrait manifest 都不是 authority。

材料来源卡只有显式“前往商店”真 button 可交互，整张 article 不伪装成按钮。只有 exact `full + indexed_live_match` 渲染按钮；`unavailable` 渲染静态“暂不能从档案前往”，不能用 disabled 假按钮。来源 schema 没有 shop displayName，因此按钮 accessible name 固定为“前往商店：{exact shopId}，定位‘{material displayName}’”；价格只写“参考单价”，并通过 `aria-describedby` 关联来源 section 顶部唯一说明“价格和库存以商店内为准”，没有可靠价格时省略数值，不能写成免费或 0。材料页已知的 locked 不禁用导航；限购状态留待 NPCShop fresh authority 显示。

Web→Host 前向 envelope 是独立 flat navigation command，不进入 Crafting business `PanelRequestMux`，也不冒充 AS2→Host `panel_request`。exact 10-key set 固定为：

```json
{
  "type": "panel",
  "panel": "crafting",
  "cmd": "open_npc_shop",
  "callId": "...",
  "panelInstanceId": "...",
  "source": "crafting_materials",
  "materialSnapshotId": "materials.snapshot.42",
  "materialName": "战术握把",
  "shopId": "迷之盔甲君",
  "catalogIndex": 57
}
```

`type/panel/cmd/source` 必须为示例常量；`callId` 匹配 `^[A-Za-z0-9._-]{1,96}$`，`panelInstanceId` 匹配 `^[A-Za-z0-9._~-]{1,128}$`；`materialSnapshotId:Id`、`materialName:Name`、`shopId:ShopId`、`catalogIndex:ShopCatalogIndex`。缺键、额外键、stale instance、非 current v2 session/snapshot 或 catalog 中不存在 materialName 均 fail closed。Web 不上传 `preferred*` 或 `returnMaterialName`；Host 只在 AS2 allow 后由已验证事实私有派生目标 hint 与返回材料。

Host→AS2 authorization 是 dedicated correlation，不复用 Web callId；numeric `callId/fid` 是 JSON integer `1..2147483647`，分配器溢出前必须跳回 1 并避开仍 pending 的 fid。exact request 为：

```json
{
  "task": "cmd",
  "action": "craftingMaterialShopAuthorize",
  "callId": 42,
  "v": 1,
  "materialSnapshotId": "materials.snapshot.42",
  "materialName": "战术握把",
  "shopId": "迷之盔甲君",
  "catalogIndex": 57
}
```

响应 task 固定 `material_shop_access_response`。成功 exact 为 `{task,callId,success:true,v:1,decision:"allow",reason:"indexed_live_match",materialSnapshotId,materialName,shopId,catalogIndex,itemName}`；失败 exact 为 `{task,callId,success:false,v:1,decision,error}`，其中 `(decision,error)` 只允许 `stale + {stale_snapshot,source_not_current,catalog_not_current}` 或 `deny + {invalid_payload,authority_unavailable,access_denied}`。`access_denied` 是 schema 防御分支，方案 2 的 current valid source 不产生该业务分支，locked/max 也绝不能触发它。

AS2 必须逐项分类：snapshot ID 不 current → `stale/stale_snapshot`；frozen material/source 不存在，或 current exact occurrence 数量不是 1 → `stale/source_not_current`；`_root.shops[shopId]` 已移除、live shop slot 缺失或 `itemName` 漂移 → `stale/catalog_not_current`；index 未 built、NPCShop service/projector/method 未 ready 或调用抛异常 → `deny/authority_unavailable`；malformed Host request → `deny/invalid_payload`。shop 仍存在但 `buildCatalog()` 合法返回空 array 属 `catalog_not_current`，不能猜成 service unavailable。allow 必须同时证明 `itemName===materialName`。Host 将三个 stale error 映射 `stale_source`，将 `authority_unavailable`、断线、畸形 response 映射 `navigation_unavailable`，`access_denied` 同名映射；Web 边界 malformed 才回 public `invalid_payload`，经过 Host normalization 后 AS2 再报 `invalid_payload` 属 contract violation，记录后映射 `navigation_unavailable`。成功 response 除 callId 外必须逐项复核 v/decision/reason/snapshot/material/shop/index/itemName 全部 echo 与 `itemName===materialName`，`preferredItemName` 只能来自这个权威 itemName；任何迟到或不匹配 correlation 只丢弃。

Host 为前向与反向各创建一个 lifecycle-bound transition token；`MaterialShopNavigationTimeoutMs=5000` 是唯一 Host deadline，`MaterialShopNavigationDeliveryMarginMs=1500` 覆盖从 Web `Bridge.send` 开始的 Web→Host ingress、Host failure/target post 与 Host→Web delivery，Web watchdog 因而固定 `6500ms`，只在失败回包也丢失时解除本地 busy，绝无开 target 权限。Gate 必须从 Web send 时刻开始，用 fake clock 与受控 ingress/post dispatcher 证明完整本地 delivery 落在预算内；若生产实现无法维持这个上界，先提高同源常量与 watchdog，不得让 Web 自建第二 authority deadline。状态机固定为：

```text
idle
  → token_created(deadline)
  → task_fences_acquired
  → authority_pending          # 仅 forward
  → target_reserved
  → committing
  → target_committed

任一 pre-commit 分支 → failed / cancelled，源 owner 保持
commit 后异常         → target 自身错误/关闭，不 rollback、不复活源
```

Host 落点固定为 `MaterialShopNavigationCoordinator + MaterialShopAccessTask`：Coordinator 独占 transition、capability 与单 deadline；Task 只维护 `fid → callback/fence` 并注册 `material_shop_access_response`，不创建自己的 timer，也不把 Host-only authorization 混进 `CraftingTask` 的 `crafting_response`/`PanelPendingCallTracker`。cancel/disconnect 会移除 fid；response 必须先核 correlation 与 Coordinator token 才可继续。

token 必须先于任何 async 工作建立。task fence 固定按 forward `CraftingTask → InventoryTask`、reverse `NpcShopTask → InventoryTask` 获取；每个 task 必须在同一锁内依次执行 `验证 exact owner/session、pending count==0、WriteState==idle、非 disposed/cleanup → install lease → generation++ → capture witness(post-acquire generation)`。Crafting witness 还绑定 v2 `materialSnapshotId + materialName`，NpcShop witness 还绑定 authoritative catalog owner；lease 存续期间三个 Task 拒绝全部新 domain request，不只拒绝 write/refresh，且拒绝不能进入 pending tracker或改变 authority snapshot，获取失败按逆序释放。generation 在 pending begin/end/cancel/clear、owner/session bind/seal/retire、write/reconcile 变化、materials/catalog snapshot 替换、cleanup/dispose、lease acquire/release 时都单调增加。AS2 authorization、target reservation、UI-thread execution gate 与 commit 前都重验 exact lease token + post-acquire generation、deadline 与 owner；`PanelChanged` 清理源 Task 前 token 必须已是 committed，此后的 generation 变化只能清理，不能触发 rollback。close、Esc、backdrop、toggle、rebind、竞争 open 或 disconnect 在 commit 前取消 token，迟到 allow/callback 不得打开 target。Host 验证顺序固定为 `exact envelope → exact active panel/instance → coordinator single-flight`：same callId + byte-equivalent normalized payload 只 coalesce 到首个 intent，冲突 payload 丢弃并审计；只有同一 active exact source 的新 callId 第二请求回 `busy`，stale/foreign instance 不得伪装成当前源 busy，也不得收到当前源 response。

通用 `PanelHost.OpenPanel` 会先关闭源再尝试目标，不满足本合同。A4b 必须新增窄化 `TryReplacePanelExact(expectedSourcePanel,expectedSourceInstance,PreparedPanelReplace plan,executionGate,completed)`；outcome exact 为 `TargetCommitted / SourceMismatch / PreExecutionRejected / PostNotDelivered / HostUnavailable`。单一 authority object `PreparedPanelReplace` exact 绑定 `targetPanel / targetInstanceId / immutableInitDataJson / CommitCapabilitiesNoFail() / AbortPrepared()`，API 不再分别接收 target panel、instance 或 initData，因而 capability、payload 与 target tuple 不可串线。Coordinator 在调用前完成所有可能失败的解析、分配、caller-key stripping 与安全 enrichment；prepare 状态不可见、可 abort，`CommitCapabilitiesNoFail` 只激活预分配的 one-shot/capsule/lease ownership，不再生成或修改 initData；`completed` 只是观察通知，绝不能 abort、release 或消费 capability。

enqueue 时原子占住 transition slot并拒绝 queue、tracked lease、idle fence、deferred open 与 return-stack 冲突。UI thread 在任何副作用前重验 exact source与 settlement witnesses，并在 Coordinator token lock 内执行 `target_reserved → committing` CAS：只有 phase exact 且 monotonic `now < deadline` 才获得不可并发取消的 commit permit；timer 只能取消 pre-committing token。permit 后只允许 `TryPostToWeb` false → `PostNotDelivered/failed` 或 post accepted → `TargetCommitted`，deadline 的精确定义是“最迟取得 commit permit”，不是要求外部 post 在 5000ms 内完成。

完整顺序固定为 `prepare → execution gate/CAS(phase=committing) → TryPostToWeb → false: AbortPrepared且源零变化；true: CommitCapabilitiesNoFail(one-shot/capsule/lease ownership) → 写 target active tuple → token phase=target_committed → PublishPanelChanged → completed(TargetCommitted)`，全部位于同一 UI-thread 调用栈；capability commit 不得提前把 token 标 committed。API immediate false、`SourceMismatch / PreExecutionRejected / PostNotDelivered / HostUnavailable` 与 post throw 都必须恰好 `AbortPrepared` 一次并按逆序释放 leases；成功恰好 commit/转移 leases一次，随后 `PanelChanged/ClearPending` 只做幂等退休。`CommitCapabilitiesNoFail` 必须早于 `PublishPanelChanged`，以免源 Task lifecycle 清理先使 witness/capability 失效，也避免 target 立即 return 时 capability 尚未生效。replace 不调用 `DoClose/DoOpen`，不改 return stack，不中断 Flash pause、HUD suspension 或 backdrop ownership；target Web 随后的 lazy/onOpen/mount failure 属于已提交 target 的 exact close，绝不 rollback 旧源。fallback Host 没有 exact replace 能力时一律 `navigation_unavailable`。

commit 前失败只向仍 active 的源发送 exact 7-key response `{type:"panel_resp",panel,cmd,callId,panelInstanceId,success:false,error}`。前向 `error∈{invalid_payload,stale_source,navigation_unavailable,access_denied,source_not_settled,admission_failed,timeout,busy}`；反向再允许 `return_unavailable`。成功由 owner commit 本身表示，已退役源不消费 final success ack。Web pending 在 source destroy 时清理；若 watchdog 命中，只恢复当前仍 active 的源 UI，不取消、续期或另行执行 Host transition。

NPCShop target initData 是 strict union。普通入口仍只允许 `{mode,source,debug,shopId,panelInstanceId}`；材料导航入口 exact 为：

```json
{
  "mode": "runtime",
  "source": "crafting_materials",
  "debug": false,
  "shopId": "迷之盔甲君",
  "preferredItemName": "战术握把",
  "preferredCatalogIndex": 57,
  "canReturnCraftingMaterials": true,
  "navigationOrigin": "crafting_materials",
  "panelInstanceId": "..."
}
```

Host security enricher 在 prepared-plan 阶段先剥离调用方提供的全部 navigation keys，再为同一个 reserved target instance 生成完整 immutable initData；prepare 只暂存、尚不激活 one-shot/capsule，post accepted 后 `CommitCapabilitiesNoFail` 才激活。禁止部分组合、额外键或由 target Web 回显 return target。Host 私有保存 one-shot `{targetNpcShopInstance,materialName,optionalCharacterCapsule}`。

NPCShop 在 fresh authoritative snapshot 后以 exact `preferredCatalogIndex + preferredItemName` 定位：按 `layout.sections` authored 顺序选择第一个实际包含该 index 的分组，否则使用自动 taxonomy 的 exact path；渲染后双验、一次性 scroll/focus，并用独立 `data-navigation-focus`/class 与合并后的 `aria-describedby` 说明“从材料档案定位”。fresh refresh 可保留 highlight 但不得重新抢焦点；首次手动分类导航、owner rebind 或 destroy 清除 highlight。不得 synthetic click、`togglePurchase`、写 `_purchaseIntents`、写购买用 `aria-selected/pressed`、打开 preview/cart、改数量或提交。locked/max 仍聚焦且购买激活继续按现役 blocked 规则。index 缺失或 name mismatch 仍打开正确商店，但显示 `tabindex="-1"` 的 not-found banner并把焦点固定到该 banner，绝不定位同名其他 slot 或首件商品；snapshot error 保留 target 给重试，焦点固定到 retry button。

显式返回 Web envelope exact 为 `{type:"panel",panel:"npcshop",cmd:"return_crafting_materials",callId,panelInstanceId}`，不带 materialName，不复用购买 mux，也不走普通 close。Host reverse 以私有 stable materialName 构建 exact crafting initData：

```json
{
  "mode": "runtime",
  "view": "materials",
  "source": "npcshop_return",
  "debug": false,
  "panelInstanceId": "...",
  "preferredMaterialName": "战术握把"
```

若携带现役 CharacterBuild 上游 capsule，Host security enricher 只在 reverse prepared plan 中额外写入 `{canReturnCharacterBuild:true,navigationOrigin:"character_build"}`，直到 commit 才激活 capsule。`source="npcshop_return"` 强制 strict preferred：命中时用默认档案顺序、无搜索/筛选并聚焦 exact 卡；不存在时保持 `selectedName=""`，显示“档案已变化或材料不存在”，焦点固定到材料目录标题，禁止自动选择第一项。

reverse 只有 `materials admission + shop retire + material-return one-shot consumption + optional Character capsule rebind` 同一 commit 才消费 capability；pre-commit failure 留在同一个 NPCShop，保留 catalog、购买 intents、焦点和 capability，可在对账完成后重试。Character capsule 只允许 `Active(crafting exact) → SuspendedInShop(npcshop exact) → PendingInstanceBind(new crafting exact) → Active(new crafting exact)`，不是通用 panel stack。`PreparationNavigationV1` on/off 返回焦点必须分别为 `preparation-menu/skills`；现役对 `materials_return/intelligence_return` 强制 preparation-menu 的分支属于 A4b 必修正确性项。

材料页 forward pending 时冻结选择、树/搜索/排序与 detail refresh，全体商店 CTA disabled，触发按钮显示“正在打开…”，容器 `aria-busy=true`；pre-commit failure 保留 selection/detail/focus，按钮变“重试前往商店”。返回 CTA 只在 exact material-navigation init pair `canReturnCraftingMaterials=true + navigationOrigin="crafting_materials"` 时显示。NPCShop return pending 是 owner-wide fence：按钮显示“返回中…”，禁止本地新增/删除 purchase/sale intent、改数量、preview/commit；业务/preview/space/inventory/reconcile 或 reverse pending 均令 CTA disabled。pre-commit failure 用 polite inline 状态恢复“重试返回材料档案”并保留目录/intents；若焦点仍在触发按钮则留在原按钮，用户已移走则不抢焦点。

NPCShop 的 Help、space/organizer、settlement 与其他模态/焦点层继续优先消费 close intent；被内层消费时不发送 Host close，也不触碰 capability。只有 outer close 才发送 exact `{type:"panel",panel:"npcshop",cmd:"close",panelInstanceId,reason}`，其中 `reason∈{button,escape,backdrop,toggle}`；header `×` 归一为 `button`，物理 Esc/native backdrop/same-active toggle 必须保留各自 reason。只有 Host exact close commit 成功后才消费 material-return 与可选 Character capsule并回游戏；busy、stale instance 或 close admission failure 保持 NPCShop/capability。普通 outer close 不能解释成显式返回，显式 return 也绝不调用 `requestClose/Panels.close`。

### D8. 头像只做 exact、可降级的辅助视觉

敌人卡使用 `EnemyPortraits.mount(container, img, {portraitRef: exactEnemyType, ...})`，由共享实现负责 manifest 冷加载、stale 与 fallback；只有调用方已经显式 `await loadManifest()` 的纯查询路径才可用同步 `resolve()`。NPC 建立独立 shop portrait resolver。运行时只读静态 manifest 与 40–48px rendition，不访问 SWF/XFL/FFDec，也不加载 Dialogue / Map panel 才能显示头像。

### D9. 排序、metric、摘要和空态

排序固定为：

| 选项 | 方向 | 稳定 tie-break |
|---|---|---|
| 档案顺序 | `archiveOrder` 升序 | `archiveOrder` |
| 持有数 | 多→少 | `archiveOrder` |
| 名称 | `displayName` 本地化比较 | `archiveOrder` |
| 用途数 | `structuredPurposeCount` 多→少 | `archiveOrder` |

`useCount` 只表示 recipe occurrence 数；`structuredPurposeCount = useCount + distinct directPurposeIds 数`。“有用途” quick filter、用途数排序、材料卡文案与 accessible description 都统一使用 `structuredPurposeCount`。详情的 `uses[]` 继续只装 exact recipe occurrence，另以非交互“其他系统用途”列表显示受控 direct-purpose label；`system:infrastructure_upgrade` 对每种材料只计一个用途，不按 67 个需求 occurrence 膨胀。未知 ID 不显示 raw token，而由 producer / validator fail closed 并进入诊断。

每次新鲜打开恢复档案顺序。切换排序不丢仍可见的 `selectedName` / detail，左侧结果换窗归顶；按“恢复档案顺序”后 current exact-set `N` 项（本基线 224）必须与回包 `archiveOrder` 逐项相等。名称排序固定使用 `Intl.Collator('zh-CN', {numeric:true, sensitivity:'base'})` 的共享 comparator，相等时回落 `archiveOrder`；默认档案序仍是唯一跨运行时 oracle。不要直接从 `TeamShared.createDropdown` 引入 Team namespace/CSS，可抽取窄 Workbench primitive 或使用满足同等键盘合同的本地实现。

自绘排序菜单的最小合同为：trigger 带 `aria-haspopup="listbox" / aria-expanded`；Enter/Space 切换；ArrowDown/ArrowUp 打开并聚焦当前项或首/末项；option 的 Enter/Space 选择；Esc 关闭并还焦 trigger；Tab 关闭但不抢焦点；destroy 清理 document listener。若使用原生 `select`，接受平台的等价语义。

metric 文案固定为“持有种类 x / y”：`x = owned > 0` 的 distinct material 数，`y = 成功 snapshot 的有效目录总数`。搜索、树、quick filter 与排序不得改变 metric；加载和失败都保留槽位并显示 `— / —`，可访问名称分别为“持有种类，正在同步”与“持有种类，暂不可用”，不保留旧可信数字，也不为 metric 单独建立 live region。

右侧自由文本标为“档案摘要”，结构化区域标为“已发现来源”。没有结构化来源但有摘要时写“尚未发现可核验的结构化来源”，不能写“无来源”；没有配方用途时写“当前合成目录中暂无配方用途”，不能外推为系统完全不用该材料。

### D10. 显式 materials v2 与安全混部

不扩宽 v1 exact key set，也不新增与现役请求版本并行的 `contractVersion`。`crafting.js` 与 `CraftingTask` 已用业务 payload 的 `v=1` 做 exact request gate；v2 直接升级这个既有 `payload.v`：

- command-specific business request exact shape 固定为：`materials v1/v2 → {v}`；`materialDetail v1 → {v,itemName}`；`materialDetail v2 → {v,itemName,snapshotId}`。`v` 只能是整数 `1|2`，两版本的 `itemName` 都沿用现役 `IsIdentityText(...,128)` 语义：`1..128` UTF-16 code units、trim 后非空、不含任何 control character、trim 后不等于大小写无关的 `undefined`；`snapshotId` 是 producer 生成的 opaque `Id`，禁止 Web 自造；各形状均禁止额外键；
- 只有 `materials / materialDetail` 允许 `v:2`；`snapshot / preview / tooltip / commit` 及其他 crafting 命令继续 v1-only，收到 v2 必须在 Host exact gate fail closed，不能因共用 `HasProtocolVersion` 而整面扩宽；
- 新 Web 是 capability opt-in owner；每个 fresh materials view 先发送 `materials {v:2}`，以第一个合法 success 的实际 `v` 固定本 view session 的协议版本。若收到 v2，后续 detail 才发送 `{v:2,itemName,snapshotId}`；若收到合法 v1，则该 session 后续 detail 发送真实 v1 shape，不把 v2 字段混入旧 AS2；
- 新 Host exact 接受 `v:1|2` 并原样转发请求版本，不能自行升级 Web 请求；
- 新 AS2 按 `params.v` 选择 response schema，未收到 v2 时继续发 v1；
- 旧 AS2 即使忽略初始 v2 materials request，成功时仍回真实 `v:1`；新 Host 按实际成功响应版本校验并保留 `v:1` 交给新 Web，禁止伪造/normalize 成不完整 v2；
- failure 保留现役 generic exact、versionless 业务包；其三层形状在下文冻结，任何层都不向 failure 塞 `v` 或成功字段；v2 detail 的未知/过期 `snapshotId` 返回 `stale_snapshot`，不降级重试成 v1。Host 的 command-specific known-failure allowlist 只为 `materialDetail` v2 接受该 token，v1 与其他 command 收到它仍 fail closed；
- Host 与 Web 属于同一 Launcher runtime payload closure，必须原子配套；split Host/Web 不是支持的部署组合。

由此形成：

| 组合 | 预期 |
|---|---|
| 旧 runtime（旧 Host + 旧 Web）+ 新 AS2 | Web 请求 v1，新 AS2 回 v1 |
| 新 runtime（新 Host + 新 Web）+ 旧 AS2 | Web 请求 v2，旧 AS2 回 v1；Host 保留 v1，新 Web显式 legacy 降级 |
| 新 runtime + 新 AS2 | v2 exact contract |
| 新 Web + 旧 Host，或旧 Web + 新 Host | 非支持 split；closure/build gate 必须阻断 |

请求协商需覆盖 `materials` 与 `materialDetail`；**success** response 继续带顶层 `v`，failure 不带版本。新字段只能存在于 v2 success exact schema；未知请求版本、success 中 v1/v2 混键或缺少必需键 fail closed。唯一允许的成功版本降级发生在 view session 的初始 `materials {v:2}` 收到完整合法 v1 success 时，且版本必须原样交给 Web；一旦选定，后续 success 版本必须一致，不能逐请求摇摆。`v2 request → 旧 AS2 versionless failure` 只按 generic failure原样失败，不算 v1 降级，也不能重试成另一版本。v1 session 必须持续显示“旧版兼容视图，分类/档案顺序/来源档位可能不完整”，禁用 taxonomy tree、档案顺序承诺、完整 variants 条件、exact recipe jump 与任何依赖 v2 的计数；scalar source 名称和 authored summary 可以显示，但 Web 禁止沿用现役概率启发式把 v1 条件冒充权威。若实际 AS2 dispatch 无法读取 `params.v`，A2 必须先提出等强度的单版本键方案并更新本文决策日志，不能退回“直接加键”或第二套冲突版本字段。

“旧 runtime + 新 AS2”只证明 v1 wire/liveness/non-regression；旧 Web 不具备 `legacy_limited` 提示，也不构成材料档案正确性、A2 feature acceptance 或 A5 业务验收。完整材料专项验收必须绑定新 Host/Web + 新 AS2 的 v2 closure；新 runtime + 旧 AS2 只验安全降级，不替代功能验收。

v2 catalog/detail 通过 producer-owned `snapshotId` 建立机械相关性，而不是借用 Host panel lifecycle：每次成功的 v2 `materials` 创建并保留 latest immutable materials snapshot，冻结 taxonomy、catalog material identity/owned、purpose/source/use identity 与 counts；response 携 `snapshotId`。除 7.3 明确允许现场 join 的 shop 动态字段外，detail material（含 description/sourceSummary）、完整 source kind payload（含 variants）、directPurposes 与 uses 的全部 exact 字段都必须从该 immutable snapshot 读取，不得按当前全局数据重新构建。Web 同时推进独立的 `materialSnapshotIntentGeneration`、取消旧 detail flight，但该本地 generation 不上 wire、也不推进 `panelInstanceId`。detail 必须携 materials 回包的 exact `snapshotId`，AS2 只从该仍存活 snapshot 解析结构化数据，再现场 join 明确不属于跨回包等值合同的商店价格/locked/access 快照；response 原样回显 snapshotId，Host 与 Web 都按 pending request 复核。新的 materials snapshot 淘汰旧 ID，旧 detail 返回 `stale_snapshot`；refresh/rebind/selection 变化后的迟到包零提交。

## 7. v2 目标合同草案

本节是 reviewable schema 草案，只有 A2 中 authored catalog、Host exact validator、AS2 producer 和合同测试同步落地后才成为现役 wire。7.1/7.2 的 JSON 都是 success 分支。failure 的现役三层 exact shape 固定为：

1. `CraftingPanelService.execute` business result：`{success:false,error}`；
2. AS2 `handle` 发往 socket：`{success:false,error,task,callId}`，其中 `task="crafting_response"`、`callId` 必须与请求相关键一致；

|---|---|---|
| materials success | `success,v,view,snapshotId,taxonomy,materials` | `success=true`；`v=2`；`view="materials"`；`snapshotId:Id`；`taxonomy` 为下述 object；`materials` 为 catalog material array |
| taxonomy | `version,roots,types,modAxes,recipePurposes,directPurposes,fallback` | `version=1`；`roots/types/recipePurposes/directPurposes` 为 registry-entry arrays；`modAxes` 为 mod-axis array；`fallback` 为 registry entry |
| registry entry | `id,label,order` | `id:Id`、`label:Label`、`order:NNI` |
| mod axis | `id,label,order,values` | `id∈{grade,scope,role}`；`label:Label`；`order:NNI`；`values` 为对应 axis-value array |
| grade value | `id,label,order,color` | `id:Id`、`label:Label`、`order:NNI`、`color` 匹配 `^#[0-9A-Fa-f]{6}$` |
| scope value | `id,label,order` | `id:Id`、`label:Label`、`order:NNI`；不得带 presentation 键 |
| role value | `id,label,order,symbol` | `id:Id`、`label:Label`、`order:NNI`；`symbol∈{triangle-solid,triangle-outline,square-outline,circle-outline,diamond-outline,star-solid}` |
| catalog material | `name,displayName,icon,owned,archiveOrder,typeId,recipePurposeIds,directPurposeIds,structuredPurposeCount,sourceCount,dropVariantCount,useCount,hasSourceSummary`，条件性再含 `modFacetIds` | `name:Name`；`displayName:Display`；`icon:Id`；`owned/archiveOrder/structuredPurposeCount/sourceCount/dropVariantCount/useCount:NNI`；`typeId∈{equipment_mod,food,general}`；purpose arrays 为 distinct `Id[]`；`hasSourceSummary:Bool` |
| modFacetIds | `grade,scope,role` | 三值均为 `Id` 且被对应 axis registry 覆盖；只在 `typeId="equipment_mod"` 时必需，`food/general` 时必须完全省略而不是 `null/{}` |

taxonomy registry 的机械顺序固定为：`roots` exact `type(0),purpose(1)`；`types` exact `equipment_mod(0),food(1),general(2)`；`modAxes` exact `grade(0),scope(1),role(2)`；各 array 内 `id/order` 唯一，除 `fallback` 外 order 连续 `0..length-1`。`fallback` exact 为 `{id:"unstructured",label:"尚未结构化用途",order:2147483647}`。recipe purpose 的 `id="recipe:" + category`、label 与 category 一致、order 沿 `data/crafting/list.xml` 物理顺序；direct purpose 沿 controlled registry authored order。未知 axis/presentation token、重复 ID/order、空 array 或 registry 引用不闭合均 fail closed。

约束：

- `archiveOrder` 在成功 snapshot 内连续、唯一；不能用过滤后 index 代替。
- `snapshotId` 由 AS2 producer 生成，对 Web 不透明；同一 producer 生命周期内不得复用已经淘汰的 ID。
- `materials[].name` 在 response 内非空、唯一；`archiveOrder` 与完整 array 一一对应为 `0..materials.length-1`。
- `taxonomy` 是一次性 versioned registry，携带首屏建树需要的 exact `id/label/order` 及受控 presentation；Web 不复制 XML registry。每个材料引用的 type/facet/purpose ID 必须在同一 registry 中闭合。
- `typeId ∈ {equipment_mod, food, general}`；`modFacetIds` 只对 `EquipmentUtil.modDict` 可验证的改装材料存在。
- `recipePurposeIds` 从 exact recipe use 派生并按 category 去重；`directPurposeIds` 是 equipment-tuning 派生用途与 catalog authored 用途的 distinct union。
- `useCount` 是 recipe occurrence 数，不是 distinct product 数。
- `structuredPurposeCount` 精确等于 `useCount + distinct directPurposeIds 数`，是“有用途”和“用途数”的唯一口径。
- `sourceCount` 与 `dropVariantCount` 不受 portrait coverage 影响，只统计已经通过发现门的结构化记录；`dropVariantCount` 精确等于 enemy/stage `variants.length` 之和，不把无档位的 shop / craft / kshop / quest 伪造成一个档位。
- 对同一 AS2 data state，catalog 的 `recipePurposeIds` 必须等于 detail `uses[].category` 映射为 `recipe:<category>` 后的 distinct registry-order 序列，`directPurposeIds` 必须等于 detail `directPurposes[].id`；各 purpose array 均按 registry order 输出，禁止对象枚举序。

| object | exact key set | exact 类型与条件 |

| materialDetail success | `success,v,view,snapshotId,material,sourceCount,dropVariantCount,useCount,structuredPurposeCount,sources,directPurposes,uses` | `success=true`；`v=2`；`view="materials"`；`snapshotId:Id` 且 exact 等于 request；四个 count 均为 `NNI`；三个集合均为 arrays |

detail 的 `snapshotId` 必须 exact 等于 request 与材料目录 success 的 snapshotId，`material.name` 必须 exact 等于 request `itemName`。`directPurposes[].id` distinct、全部被该 snapshot taxonomy registry 覆盖，label/order 必须与 registry 一致；`uses` 的 `{category,recipeIndex}` distinct。material identity/owned、purpose IDs、四个 count 与 `hasSourceSummary === (sourceSummary.length > 0)` 都必须与 frozen catalog entry 逐项一致；Host 禁止拼接两次 snapshot。仅 7.3 明确列出的 detail-time shop `basePrice/unitPriceAtSnapshot/requiredInfo/locked/shopAccess*` 现场 join 不受上述跨回包等值约束，但其 source identity 必须来自同一 snapshot。

示例中的商店快照价格只表达字段语义，不是对任一真实存档口才状态的报价。A1 以真实 fixture 固定内部 grouped record 的 nullable、range 与 occurrence 语义及 v1 scalar compatibility；A2 才固定完整 v2 wire 的 exact JSON schema、数值精度与 AS2 序列化行为。所有 drop occurrence 均逐条保留；producer 与 Web 都不得折叠完全相同项。

### 7.3 Source discriminated union 与商店快照

所有 source kind 共享且只共享 `kind / sourceKey / sourceOrder`；`kind∈{craft,shop,kshop,quest,stage,enemy}`，`sourceKey:Identity(768)`，`sourceOrder:NNI`。其余字段按 kind 使用 exact key set，禁止省略、`null` 或额外键：

| kind | `sourceKey` identity | exact kind-specific fields / types | occurrence 规则 |
|---|---|---|---|
| `craft` | opaque `{category,recipeIndex}` | `category:Id; recipeIndex:RecipeIndex; productName:Name; price:NN; kpoints:NN` | 每个 recipe occurrence 一张卡；同 category 同名产物不去重 |
| `shop` | opaque `{shopId,catalogIndex}` | `shopId:ShopId; itemName:Name; catalogIndex:ShopCatalogIndex; basePrice/unitPriceAtSnapshot:NN; requiredInfo:ShortText; locked:Bool; shopAccessMode∈{full,unavailable}; shopAccessReason∈{indexed_live_match,no_authoritative_remote_access_capability}`；pair 只允许 `full + indexed_live_match` 或 `unavailable + no_authoritative_remote_access_capability` | 每个 catalog slot 一张卡；动态字段与 access pair 在 detail 时现场 join；locked/限购不降级 access mode |
| `kshop` | opaque `{catalogIndex}` | `catalogIndex:NNI; entryId:Id; category:ShortText; priceK:NN` | 每个配置 occurrence 一张卡 |
| `quest` | opaque `{questId,rewardSet,authoredIndex}` | `questId:Id; rewardSet∈{base,challenge}; authoredIndex:NNI; title:Label; quantity:PI` | 每个 authored reward occurrence 一张卡；base/challenge 各自编号，重复 item 不静默丢弃 |
| `stage` | opaque `{stageName}` | `stageName:Id; chanceModel="stage_roll_divisor_with_legacy_domain_branch"; legacyConditionId="andylaw_domain_bonus"; variants:stage-variant[]` | 同 stage 的每个 Reward 进入有序 variants；只给默认分支基准值，不臆算条件分支概率 |
| `enemy` | opaque `{enemyType}` | `enemyType:Id; displayName:Label; chanceModel="enemy_prd_with_reverse_bonus"; variants:enemy-variant[]` | 同 enemy 的每个掉落配置进入有序 variants |

`ShopCatalogIndex` 的收窄必须同轮落到 AS2 `MaterialArchiveProjector`/authorization validator、Host `CraftingTask` detail/flat-route validator 与 Web `crafting-runtime`/CTA envelope validator；只作用于 `shop.catalogIndex`。KShop 的 `catalogIndex` 继续是 `NNI`。发布门静态扫描 current live NPC shop slots 全部落在 `0..10000`，否则该 slot 连现役 NPCShopTask 的购买协议都不可达，必须先修数据而不是放宽导航。

`sourceKey` 对 Web 是不透明相关键，禁止解析。A2 的 canonical producer 固定采用 `lp1|<utf16Length>:<segment>|...`：首 segment 为 kind，后续按上表 identity tuple 顺序编码；数字使用无前导零十进制，`rewardSet` 使用受控英文 token。示例可读 key 只演示该编码，Web 不得拆解；fixture 必须覆盖 identity 文本本身含 `:`、`|` 与非 BMP 字符，证明 UTF-16 code-unit length、determinism 与无碰撞。若施工时改用 canonical hash，必须先以决策日志 supersede 本段并保留同等 collision/determinism Gate。v2 不允许“其他 kind”宽松落桶，新增 source kind 必须升 schema / registry 并同步 exact validator。

`variants[]` 元素同样是 strict exact object：

| parent kind | exact key set | 条件合同 |
|---|---|---|
| `enemy` | `occurrenceIndex, chanceRaw, chanceInputState, nominalChancePercent, minReverseLevel, maxReverseLevel, quantityMin, quantityMax` | `explicit` 时 `chanceRaw` 为 `[0,100]` finite number 且 `nominalChancePercent === chanceRaw`；`absent_defaulted/invalid_defaulted` 时 `chanceRaw=null` 且 nominal 为 `100` |
| `stage` | `occurrenceIndex, rollDivisor, defaultBranchChancePercent, quantityMin, quantityMax` | `rollDivisor` 为正整数；producer 只投影默认分支的 `round6(100 / rollDivisor)`，其中 `round6(x)=Math.round(x*1_000_000)/1_000_000`；validator 对该期望值使用绝对误差 `≤5e-7`，不得由此推导 AndyLaw 分支的精确概率 |

任何 drop source 的 `variants[]` 必须非空。enemy 概率 property 不存在时进入 `absent_defaulted`；property 存在且 AS2 `Number(raw)` 为 NaN 时进入 `invalid_defaulted`，包括 XML 空元素 `""`、纯空格和非法文本；否则进入 `explicit`。其他 finite 但超出 `[0,100]` 的结果是 producer/schema error，不能悄悄 default。`minReverseLevel/maxReverseLevel` 各自只能是 `null` 或非负整数，双非空时 `minReverseLevel ≤ maxReverseLevel`。两类 variant 的 `quantityMin/quantityMax` 都是正整数且 `quantityMin ≤ quantityMax`。

机械不变量：

- `sourceKey` 在单个 detail 内非空、唯一；`sourceOrder` 连续唯一为 `0..sources.length-1`；`sourceCount === sources.length`。
- 每个 drop source 的 `occurrenceIndex` 连续唯一为 `0..variants.length-1`；`dropVariantCount === sum(stage/enemy variants.length)`。
- enemy `chanceInputState ∈ {explicit, absent_defaulted, invalid_defaulted}`，并满足上表的 chance 联动关系。stage 在未完成 standalone reachability 证明前固定 `chanceModel=stage_roll_divisor_with_legacy_domain_branch + legacyConditionId=andylaw_domain_bonus`，enemy 固定 `chanceModel=enemy_prd_with_reverse_bonus`。若 A1 fresh trace 证明所有支持入口均不可能命中 legacy predicate，可在 A2 schema freeze 前以决策日志收窄为 standalone-only model；若任一入口可达，则必须保留 contextual model并先表征 Flash `random(Math.floor(N)/2)` 的真实数值语义。
- access pair 只允许 exact `full + indexed_live_match` 或 `unavailable + no_authoritative_remote_access_capability`；`inspect_only` 不是预留合法值。`full` 只说明 detail build 时 exact source/live-catalog join 成立，点击时仍必须走 D7 的 AS2 reauthorization；Web/Host 都不得从 pair 单独打开 target。
- `uses` 的 `{category,recipeIndex}` occurrence identity 唯一；purpose ID 数组各自 distinct，且全部被 taxonomy registry 覆盖。
- `useCount === uses.length`；`structuredPurposeCount === useCount + directPurposes.length`，detail 与同 snapshot 的 catalog entry 必须相等。
- 对 exact 相同 `snapshotId` 的 catalog/detail 对，`dropVariantCount/sourceCount/useCount/structuredPurposeCount` 逐项相等，`hasSourceSummary` 必须严格等于 `detail.material.sourceSummary.length > 0`；任一 producer 不得用 portrait、过滤结果或手写摘要行数修正这些计数。
- 除 schema 明确允许的 `null` 外，所有 number 必须 finite；`archiveOrder/sourceOrder/occurrenceIndex/authoredIndex` 是 `NNI`，`recipeIndex:RecipeIndex`，shop `catalogIndex:ShopCatalogIndex`；`nominalChancePercent/defaultBranchChancePercent ∈ [0,100]`；quantity 是正整数且 min≤max，price/owned 非负。
- 防御上限固定为：materials `≤4096`、单 detail sources `≤512`、单 drop variants `≤128`、单 detail uses `≤1024`、单 detail `directPurposes[]` `≤128`、taxonomy entries（含 `taxonomy.directPurposes` registry）合计 `≤1024`；registry 不另套 128 上限。字符串严格使用 7.1.1 的 `Name/Id/Display/Label/ShortText/Description/Summary/Identity(768)` 字符与 control-character 规则。超限、literal `undefined` identity、单行 control character、multiline 中 CR/LF/TAB 之外的 control character均 fail closed，不静默截断。

## 8. Web 交互、焦点与生命周期合同

### 8.1 树与面包屑

- 面包屑示例为 `全部材料 › 用途 › 武器合成`；祖先段是 button，当前段带 `aria-current`。
- 点击、Enter 或 Space 激活祖先后回到该层。
- Esc 由 panel-level 单一 arbiter 分层消费：帮助/模态 → 打开的排序菜单 → **搜索框拥有焦点且 query 非空时**清 query 并留焦 → **事件目标位于 FilterNavigator 或 `breadcrumbHost` 且树路径非空时**上退一级 → panel close。焦点位于 grid、detail 或商店 CTA 时不得修改左侧树；若无更内层消费者则 Esc 走 panel close。navigator 内 Esc 只退一层，不关闭 panel；breadcrumb 不在 navigator root 内，必须通过共享 `back()` 或 panel arbiter 进入同一规则。
- 每次 Esc 只允许一次状态迁移；消费层必须同时 `preventDefault()` 与 `stopPropagation()`，外层必须尊重 `defaultPrevented`，禁止一次按键既退树又关 panel。
- 左右、Home、End 沿当前可见筛选按钮移动；重绘后焦点回到新树中对应 active/context button，不能落到 `body`。
- `FilterNavigator.setPath()` 当前会整树重绘，焦点恢复属于新增验收合同，不得以现有共享组件“已经接入”代替证明。

### 8.2 目录 grid 与选择

- 非空结果始终恰好一个 `tabindex=0` option；空结果不得留下 detached activeElement。
- Arrow / Home / End / PageUp / PageDown 保持现役 grid 语义。
- 搜索、树、quick filter、sort 属于结果换窗：左侧滚动归顶；密度切换继续保留滚动与焦点。
- 若当前 `selectedName` 在新结果中仍可见，保留选择和右侧 detail；否则沿用现役清空选择和 stale detail 的行为，不在本 ADR 顺带引入“自动选择最近项”。
- 选择新材料时右侧 detail 滚动归顶；同一 detail 的无害刷新可保留滚动。
- detail 更新不从左侧卡抢焦点；只有显式跳配方、商店或返回路由可移动焦点。

### 8.3 来源卡

- “已发现来源” section 使用 h3；每个逻辑来源使用 `article`，来源标题使用 h4；`variants[]` 使用 `ul/li` 或等价 list semantics。敌人/关卡保持非交互，商店卡内使用 accessible name 同时包含 NPC 与材料名的显式 button。
- `variants[]` 按 occurrence 顺序逐行显示；互斥等级档不求和。
- enemy 卡只标“基础掉落”，stage 卡只标“关卡基准”；共同说明“掉落率仅供参考”只在 section 顶部出现一次，两者都不能写成“本次实际概率”。enemy defaulted 100% 显示“默认必得”，invalid-defaulted 显示“配置异常，按必得处理”并另进诊断。
- 敌人/关卡文字、档位与发现门先完成，再请求头像。未发现 identity 不得在 DOM、计数、resource hint 或 resolver 调用中出现。
- portrait slot 固定尺寸，晚到图片不改变卡高、滚动或焦点。
- 完全相同的 occurrence 也逐行显示；Web 不自行深比较、折叠或生成 `×N`。
- 敌人/关卡概率与商店时效提示只在来源 section 顶部出现一次；卡片内只显示“基础掉落 / 关卡基准”和当前值，不为每个条目重复解释。

### 8.4 用途行

- 当前 tooltip-only article 改为显式“前往合成” button，accessible name 至少包含配方显示名；click / Enter / Space 等价。article 自身退出 Tab 序。
- 每张用途卡采用单行三段骨架：左侧产物图标/名称，中间把完整 `ingredients[]` 显示为材料档案视觉的 23px 静态紧凑格带，右侧固定归属于该产物的动作列；数量或强化门槛压在格内，名称保留在完整 `aria-label`/tooltip，当前材料同时以描边和可访问名称标识。当前 authored 数据最多 9 项材料并在 1024 右栏单排完整显示；更窄宽度或未来更多项只在材料带内部换行，不截断协议数据。不复用有库存/按钮语义的可交互槽位，也不依赖 viewport 断点决定卡内归属。
- tooltip 可以绑定主动作或通过 `aria-describedby` 提供等价信息，但不是唯一入口，也不能为了 hover 保留第三个无动作的 `tabindex`。
- 产物可检视时另给 EquipmentInspector button；两种动作不嵌套、不同时触发。
- stale recipe、请求失败或 category 消失时保持 materials mode，显示“一句事实 + 下一步”，焦点回触发 button / 重试，不静默跳到其他配方或现役“过滤后可见列表第一条 recipe” fallback。

### 8.5 商店前往与返回

- forward intent 在 pending 期间有 handler-level busy fence；双击不产生第二条 intent。
- Host transition 是 deadline 的唯一 authority owner，固定 `5000ms` commit-permit deadline 与从 Web send 起 `1500ms` delivery margin；fake-clock 必须证明 permit/deadline/late callback 互斥。dedicated Task 不创建 timer，Web `6500ms` watchdog 只恢复 UI，不能先行释放会被迟到 target 打开的 authority。Host failure response 到达仍 active 的源页后恢复按钮并显示错误。
- target open 成功后焦点落在 preferred 商品；not-found 时固定落在 `tabindex="-1"` 的错误 banner，snapshot error 固定落 retry button，不落到其他商品。
- 显式返回前 Host 必须证明 NPCShop 与共享 Inventory settled；成功且材料仍存在时，材料卡滚入可见并获得焦点；材料消失时不选第一项，焦点固定落材料目录标题。返回失败不得留下空白 panel 或重复恢复。
- NPCShop 普通关闭不自动返回材料，避免劫持用户“关掉界面”的既有预期。

### 8.6 空态与可访问性

空态必须区分：

| 状态 | 文案原则 | 下一步 |
|---|---|---|
| 目录真的为空 | 无有效材料数据 | 重试/关闭 |
| 筛选结果为空 | 当前条件无匹配 | “清除筛选”设 `query='' + quickFilter='all' + filterPath=[]`，保留 sort/density；若恢复结果则聚焦首个 option 但不自动选择，否则聚焦 search |
| 读取失败 | 无可信 snapshot | 重试；metric 不显示旧值 |
| v1 legacy session | 明示“旧版兼容视图，分类/档案顺序/来源档位可能不完整” | 可浏览名称与摘要；禁用 v2-only 树、完整条件与 exact jump |
| 无已发现结构化来源 | 未发现，不等于没有 | 继续探索；保留档案摘要 |
| 当前无合成用途 | 仅限定当前合成目录 | 不宣称无系统用途 |
| portrait 缺失 | 文本仍完整 | 占位，无 live announcement |
| 导航失败 | 源/目标状态可恢复 | 重试或返回 |

共享 focus ring、对比度、reduced-motion 与 Shell authority/status polite live region 继续生效。另保留一个 debounce 的本地结果 polite status：只在 tree/filter/sort 已提交或 search 停顿后播报“显示 x / y 种材料”；头像、焦点移动和每个输入字符不播报。头像不新增动效。

## 9. `material_dictionary` 生成与发布数据门

### 9.1 为什么不能直接“全量自动生成 Information”

当前 `Information` 同时承担编辑摘要、旧称兼容、策划取舍与非剧透表达。结构化数据则承担 current snapshot 中已经发现的可核验来源。两者目标不同：

```text
档案摘要：authored、可编辑、可选择性省略、全局可见
已发现来源：structured、可验证、随存档发现状态变化、条件完整
```

把后者拼成前者会丢失编辑语义并扩大 spoiler surface；从前者解析后者则不完整、不稳定。两区必须并存且明确命名。

### 9.2 Producer 输入、输出与副作用边界

目标 producer 的逻辑输入：

- `material_catalog.xml`；
- item material exact-set 与 identity/类型基础事实；
- controlled purpose label registry；
- generator 版本与 canonical serializer 规则。

目标输出：

- 旧 schema 的 `material_dictionary.xml`；
- 可审计 sidecar；
- `--check` 所需的内存派生结果。

producer 禁止：

- 扫描自由文本生成 purpose；
- 自动把所有已配置来源写入 `Information`；
- 在 release prepare / verifier 中写文件；
- 遇到未知材料、重复名字、无效 purpose、缺失 legacy summary 时静默跳过；
- 依赖时间戳、对象枚举顺序或机器路径造成非确定字节。

### 9.3 最小 Gate

| Gate | 失败条件 |
|---|---|
| catalog exact-set | current material exact-set `N` 与 authored catalog `N` 不一致（本基线 N=224）；新增/删除未经显式 diff |
| identity | 名称空、重复、材料不存在、override 指向未知 identity |
| order | `archiveOrder` 不连续/重复；旧 58 项相对顺序漂移且无批准记录 |
| taxonomy | type 未知；direct purpose 未注册或缺少 consumer 证据 |
| legacy projection | `legacyVisible` 顺序、Name、Information 与预期不一致 |
| deterministic | 同输入双次生成字节不同 |
| stale output | 工作树文件与内存派生产物不一致 |
| sidecar | source/generator/output digest 或条目数不一致 |

A2 才建立正式 producer 命令。A0 只允许运行一次性只读命令和既有工具，不新增 tracked script；A1 若确需新增 focused test/helper，必须由 A1 窄票明确授权并登记 Gate。任何批次都不得把缺损 drop/use 索引生成进新 artifact 并固化为 SOT。

### 9.4 与 Launcher 正式发布的关系

这是数据/content closure gate，不因 Launcher binary 是否变化而消失。若某批同时修改 Launcher runtime，仍须另走项目规定的 build identity、payload closure、双 signer / faultDomain、promotion 与 standard-entry 状态链；数据 gate 不代替 runtime promotion，runtime promotion 也不代替材料数据正确性。

## 12. 未决项与相邻风险

### O1. 旧 Flash 材料大全是否扩为 224 项

本 ADR 默认“不扩”。若未来要扩，必须单独验证旧 UI 容量、滚动、载入时延、摘要缺失展示和 spoiler 语义；不能因 catalog 已全量就自动改变旧 UI 可见集。

### O2. 已重开：只提供一跳“← 返回材料”

A4a 原始的单向跳转裁决保留为历史。2026-08-14 人类验收已明确重新要求返回，因而现役设计只允许同 crafting owner 一跳回 materials，只恢复 stable `materialName`。不保留任意历史、不新增 Host/AS2 命令，也不把 NPCShop 的反向 capability 泛化为 panel stack。

### O3. 读档后的已发现 stage 重建

`[R / adjacent]` current-tree 显示 enemy/task cache 会从最新配置重建，stage 在读档后可能等到重新进入关卡才重建。A1 先用真实存档 fixture 表征；只有确认影响材料详情后再决定是否同批修复，禁止借 variants 改造顺手改变发现历史。

### O4. 已裁决：不引入 `recipeSignature`

A0 已选择 `{category, recipeIndex, productName} + exact panelInstanceId/lifecycle epoch + Web-local recipeSnapshotGeneration`。原因是现役 recipe snapshot 没有 signature；D10 新增的 materials `snapshotId` 只约束材料 catalog/detail，不升级 recipe snapshot。保留 recipeSignature 会让用途 detail 中的值没有第二个 fresh authority 可比。若未来支持同 epoch 配方热重载，需要另行增加 recipe snapshot revision 或 exact resolve/preflight 协议，不能把 hash 塞进旧 snapshot。

### O5. 价格文案的产品措辞

技术语义已经固定为“AS2 商店 projector 的当前快照，不是交易 quote”。最终中文可在 A3 视觉审阅时从“参考价 / 当前估价 / 进入商店后确认”中选择，但不得省略非交易权威提示。

### O6. 已裁决：所有已索引商店可作为完整远程购买入口

维护者于 2026-08-11 选择方案 2，明确接受以下 gameplay capability 扩张：材料档案中每个仍被 current AS2 索引与 live shop catalog 共同证明的 shop source，都可远程打开完整 NPCShop；进入后可按现役锁定、限购、价格、库存与购买 authority 正常购买。未选择 inspect-only，也不限制为平板联系人集合。

裁决前比较过的三条路线保留为历史依据：

1. **推荐的保守扩展**：只允许由一个 AS2 authoritative remote-shop exact set 明确列出的 shopId；初始集合可从 current tablet-contacts 真源逐项迁移并做 closure，但 world/dialogue 的上下文进入不能被推断成永久能力。材料 detail 查询同一 SOT/API，点击时再次授权；不在集合内只显示来源/解锁条件。
2. **能力扩张**：明确允许所有已索引 shop source 从材料档案远程打开完整 NPCShop，随后可正常购买；这需要新增 AS2 allowlist/policy、帮助文案和真实 gameplay 验收。
3. **Inspect-only**：允许远程浏览但禁止购买；这会新增 NPCShop mode 和 mutation fence，不属于默认最小范围。

方案 2 的 authoritative predicate 必须由 A4b 写成 AS2 API：点击时以 exact `{materialSnapshotId,materialName,shopId,catalogIndex}` 先复核 current frozen material snapshot/source，再复核 ItemObtainIndex 的当前 shop occurrence 与 `NPC商店WebView.buildCatalog(shopId)`（或同一纯 projector）的 live catalog identity；只在 snapshot、shop、slot 与 itemName 仍一致时允许 `full`。锁定/限购不阻止进入商店，但继续阻止对应购买动作。缺 source、slot 漂移、itemName 不符、catalog 不可用或 Host 无可靠 authority bridge 均 stale/deny 并 fail closed。

A2–A4b 的 current source 已把方案 2 的 `full + indexed_live_match` 与 click-time authorization 实现为同一未部署 closure；`unavailable + no_authoritative_remote_access_capability` 保留为唯一降级 pair。CTA 只消费 Host 严格验证的 full pair，每次点击仍经 Host→AS2 fresh authorization，不能从 manifest、价格、portrait 或 Web catalog 自行放宽。当前 A4b source/自动门已关闭，但首次 exact candidate 与真实游戏旅程仍由 A5 负责；在其完成前状态保持 `NOT_DEPLOYED`。后续枚举或权限语义扩张必须走新协商版本/能力，不能沿用本次 pair 偷渡。

## 13. 风险、回滚与停止条件

### 13.1 主要风险

| 风险 | 保护 |
|---|---|
| v2 字段让旧 Host exact validator 拒包 | 请求版本协商；v1 不加键；三种支持的 AS2/runtime 组合 + split Host/Web negative gate |
| v1 fallback 被误当完整档案 | session 版本一次选择；persistent `legacy_limited`；禁用 v2-only 能力与概率启发式 |
| catalog/detail 串入不同数据快照 | producer-owned snapshotId + immutable snapshot；Host/Web exact echo；本地 intent generation 只防迟到 |
| variants 改造使 refresh 重复增殖 | cache rebuild 幂等 fixture；每 occurrence 稳定顺序 |
| 生成器把编辑摘要变成剧透清单 | authored summary 与 structured sources 分离 |
| 多路径树重复渲染同一材料 | distinct name result set 与节点计数门 |
| 分类把未知用途说成没有用途 | controlled purpose + “尚未结构化” fallback |
| preferred focus 误触购买 | navigation highlight 与 selection/preview/cart 状态分离 |
| 未定局 NPCShop/Inventory write 在返回时失去对账 owner | Host settled gate；pending/reconcile/cleanup 时保留 target 与 one-shot |
| portrait 晚到写入新 detail | epoch / close / rebind fence；固定几何 |
| `catalogIndex` 配置漂移 | 打开后复核 itemName；not-found 明示，不误聚焦 |
| 旧 58 顺序在全量迁移中漂移 | producer oracle fixture 与 reviewed diff |
| browser harness 被外推为 E2E | 分层术语与真实旅程 Gate |

### 13.2 回滚单位

- A1：grouped source index、reverse-use index 与 occurrence identity 变更必须成组回滚，恢复旧 internal shape 与 v1 scalar compatibility 证据；禁止留下半 grouped 数据形状。
- A2：v2 request capability 与 producer 可关闭，Host/Web 完整回到现役 v1 legacy schema、展示与排序；此路径没有 `archiveOrder`，不得宣称仍按档案序平铺。完整 v2 schema、authored catalog 与 generator 必须按兼容组回滚，禁止留下 generated file 无真源。
- A3：portrait resolver 可独立 feature-off，文本来源继续工作；排序/metric 可分别回落默认档案序与隐藏 metric。
- A4a：同壳 recipe navigation 可独立 feature-off，回到材料详情的非交互用途展示，不影响 v2 数据正确性。
- A4b：Host route 可关闭 CTA，NPCShop mutation pipeline 不应受影响；one-shot token 与目标 instance 必须清理。
- 每批只回滚自己引入的共享面，不能修改或倒写旧 ADR 的历史发布证据。

### 13.3 停止条件

出现以下任一项立即停批并回到证据：

- 无法在 AS2 producer 端区分 enemy 百分点与 stage divisor，或未证明 AndyLaw 分支不可达却准备把 stage 写成无条件 `100/N`；
- exact recipe occurrence 无法从 category array 稳定定位；
- 新 AS2 会无协商地向旧 Host 发 v2；
- 商店快照必须复制购买公式才能投影；
- `heeho君` 无法精确映射且施工者准备猜 alias；
- portrait 请求先于发现门或 manifest 开始反向生成来源；
- route 需要 generic panel stack 才能完成最小往返；
- producer `--check` 依赖写工作树或输出非确定字节；
- 没有 fresh trace / Output Panel 却准备声称 AS2 编译通过；
- 只有 browser harness 却准备声称真实 WebView2→Flash E2E。
