### 2.0 前置调研：按存档的「最小增量覆盖」数据层（2026-10-11 调研完成，施工前必读）

> **用户裁定（2026-10-11）**：按存档隔离**不得全量复制数据文件**，每个存档只存变化的部分，
> 按可行的最小单元写入；游戏加载与大模型查询时由后端/宿主自动完成覆盖合并，消费者拿到的
> 仍是一整份完整数据；**大模型对文件完全无感知**（只从合并后的最终数据里查和改），
> 增量文件的读写全部由后端负责。本节是该裁定的可行性结论与必须在施工前定死的口径，
> 目的是避免阶段四（对话联动）才发现方案不符预期而重构。
>
> **同日追加的四条裁定**：① **Agent 任务是文件级的**（每个存档一个独立 task 文件 + 一个独立 text 文件，
> 该文件下的任务只归这个存档）——因为各存档的 Agent 任务数量不一致，不存在「按 id 覆盖基础数据」的语义；
> ② 增量修改主要针对**任务对话**（按 `get_conversation`/`finish_conversation` 各自的 `$占位符` key 改）
> 与 **NPC 日常对话**（改按组 id，追加由后端自增组 id、大模型不给 id）；
> ③ **大模型不改 Agent 任务的对话**（只在发布时生成一次，属一次性任务），后续对话修改一律跳过 Agent 任务；
> 要改的是游戏原有 NPC 日常对话，以及**当前存档进度尚未完成的任务**的对话，这两类纳入检索范围；
> ④ 按存档的全部内容放在**一个独立文件夹**里，不与正式数据混放，且该文件夹整体 ignore、不进 git。
> **性能是硬约束**：游戏读数据本身性能敏感，增量层不得引入频繁开销；热更新虽只在文件变化时触发一次，
> 但发生在玩家游玩过程中，不能卡太久（参照系：Agent 任务改非全量更新后卡顿已消失，那个量级可接受）。

#### 2.0.1 结论：需求合理且可行，但三类数据的隔离粒度本来就不同

| 数据 | 隔离粒度（用户裁定） | 真实结构（已核实） | 稳定 key | 合并语义今天是否已存在 |
|---|---|---|---|---|
| **Agent 任务** | **文件级**（每存档独立 task 文件 + 独立 text 文件，不覆盖基础数据） | 顶层 `{"tasks":[…]}`；文本平铺一层 dict | 任务＝整数 `id`；文本＝`$KEY` | **已存在**：任务侧数组拼接（`ListLoader.concatField("tasks")`）、文本侧 dict 覆盖（`ListLoader.dictMerge()`，`ListLoader.as:208-215`） |
| **既有任务的对话文本** | **key 级**（只写被改的 `$KEY`） | `data/task/text/*.json` 平铺 dict，任务对象用 `get_conversation`/`finish_conversation` 指向 `$KEY`（实测 `logistics_tasks.json:11,14`） | `$KEY` 字符串本身 | **已存在且天然成立**：AS2 `dictMerge()`、后端 `task_text_registry.py:24-35` 与 `loader.py:232-242` 都是「后到覆盖同名 key」——覆盖层文件只放改动的 `$KEY`，**无需任何新合并代码** |
| **NPC 日常对话** | **组级**（一组连续对话＝一个单元；可改可追加） | `data/dialogues/*.xml` 按阵营分 13 个文件（`list.xml` 登记）；层级＝`<Dialogues><Name>NPC名</Name>` + N×`<Dialogue id="k">`，组内含 `<TaskRequirement>`（挂**组**层）与若干 `<SubDialogue>`（`Name/Title/Char/Text`） | **（NPC名, `<Dialogue id>`）** | **不存在**，需新建（见 2.0.4：只需改 C# 一处） |

**对话侧 key 的实测数据（本节结论的地基，2026-10-11 取证）**：全库 370 个 `<Dialogue>` 组、91 个不同 NPC 名；
**每个组都带 `id` 属性、零缺失**，且 **（NPC名, 组id）组合零重复**、没有任何 NPC 名出现在两个 `<Dialogues>` 块里。
每 NPC 的组数 1–11、中位数 4。
**⚠ 但裸组 id 只在 NPC 内唯一，跨 NPC 大量重复**：370 个组去重后只有 **11 个 id 值（0–10）**，
其中 `id="0"` 出现 91 次（＝91 个 NPC 各有一组）、`id="1"` 88 次、`id="2"` 77 次。
所以任何按组 id 的定位都**必须带 NPC 名**，且追加组的 id 分配是**按 NPC 作用域**的（见 2.0.3）。

#### 2.0.2 落点（用户裁定）：统一放 `data/rag/agent_saves/<slotKey>/`，一个独立文件夹装全部内容

用户要求按存档的内容集中在**一个独立文件夹**里，不与正式数据混放，并整体 ignore。
定稿路径＝`data/rag/agent_saves/<slotKey>/`，槽位目录下放该存档的全部增量文件：

```
data/rag/agent_saves/<slotKey>/
  agent_tasks.json          # 该存档独有的 Agent 任务（文件级隔离，见 2.0.1）
  agent_text.json           # 上述任务的文本（$AGENT_* key）
  task_text_overrides.json  # 对既有任务对话文本的 key 级覆盖（只含被改的 $KEY）——阶段四
  dialogue_overrides.json   # NPC 日常对话的组级覆盖（replace/append）——阶段四
```

**为什么是 `data/rag/` 而不是 `data/task/`、`data/dialogues/` 下各开一个子目录**（三条实测理由）：

1. **它已经是本功能专用目录**：现有 `data/rag/sync_state.json`（exe→游戏轮询通道）、`data/rag/npc_state_db.json`（NPC 状态）、`data/rag/launch_cfn_rag.bat`，性质一致＝后端运行时产物，不是游戏正式数据。
2. **三方读取都已验证可行**：
   - **AS2 今天就在读 `data/rag/`**——`scripts/通信/通信_aka_Agent联动.as:11-13` 已有三个 `REL_*` 相对路径常量，并用 LoadVars 逐个探测存在性（`:43-69`「先检测 npc_state_db.json，不存在则检测 sync_state.json」）。这正是按存档文件需要的「探测失败即静默跳过」模式，可直接照抄。`PathManager.as:28` 的 `allowedBasePaths` 限制的是**根前缀**（`resources/`、`CrazyFlashNight/`、`flashNight/`），不限制其下子目录，故 `data/rag/...` 无障碍。
   - **C#** 用 `_projectRoot` 拼相对路径即可（`DataCache.cs:105` 已有同款写法 `Path.Combine(_projectRoot,"data","dialogues","enemy_dialogues.xml")`）。
   - **后端** `find_resources_directory()` 返回游戏仓根（`services/game_data/paths.py:79-112`），拼 `data/rag/agent_saves/<slot>/` 即可。
3. **它不在语料指纹目录列表里**（`_FINGERPRINT_SOURCE_DIRS`＝`data/dialogues`、`data/task`、`docs/story`、`data/intelligence`、`data/intelligence_h5`、`data/glossary`、`data/stages`、`data/items`，`loader.py:61-70`）——所以按存档文件的每次写入**不会**自动触发全库索引重建，重建与否由我们显式决定（见 2.0.7）。放在 `data/task/` 下则相反：指纹是 `rglob` 递归的，每次发布都会误触发重建。

**⚠ 这个落点有一处结构性代价，必须在施工时正面处理**：任务数据今天是**靠 `data/task/list.xml` 登记才被宿主读到的**，而 list.xml 的条目名正则是 `\A[\p{L}\p{N}_. -]+\.json\z`（**不含路径分隔符**）、条目上限 128、重复引用即报错（`MapTaskCatalog.cs:37-43`），文件路径由 `folder + name` 拼死在 `data/task/` 或 `data/task/text/`（`:34,42`）。所以**按存档的任务文件在结构上无法登记进 list.xml**，宿主也就读不到它。两条路：

- **选定方案**：给 `MapTaskCatalog.Load` 增加一个「显式额外源文件」入口（相对路径清单，在 list.xml 条目之后读取），让这些文件同样进 `SourceBytes`——这样 `ChangedSources`（`:65-75`，按 key 并集逐文件比字节）会自然把它们纳入热重载变化清单，不必另造机制。`Load` 已有的 `overrides` 形参（`:20,44`）**不能直接用于此目的**：它只能替换 list.xml 已枚举出的文件，不能新增文件。
- 被否的替代：把槽位写进文件名（`agent_tasks_<slot>.json`）留在 `data/task/` 下——可省掉上面这处改动，但违背用户「不与正式数据混放」的裁定，且换存档要增删 list.xml 登记行（churn + 128 条上限）。仅在额外源文件入口实施受阻时回退，回退须重新征得同意。

**`.gitignore`（同轮改，用户裁定整目录 ignore）**：现有 `# agent` 段是三条**单文件**规则（`data/task/agent_tasks.json`、`data/task/text/agent_text.json`、`data/rag/sync_state.json`，`.gitignore:104-107`）。改动＝**新增一条目录规则 `data/rag/agent_saves/`**，**三条既有规则全部保留**——前两条对应的共享文件在 standalone（未绑定存档）下仍然会写（见 B2-2），不能因为按存档文件迁走就删掉。注意 `data/rag/npc_state_db.json` 目前是**被 git 跟踪的**（`git ls-files` 可证），本轮不动它——是否改为 ignore 属独立裁定。

#### 2.0.3 对话的 key：修改用组 id，追加由后端自增（大模型不给 id）

- **数组下标不能当 key**：下标随基础文件的插入/删除漂移，覆盖层与基础文件各自演化后必然错位；而对话覆盖是长期存在的按存档数据，一旦错位就是**静默的内容串档**（某 NPC 说出别人的话，且无任何报错）。
- **也不必退回到「把整个 NPC 的对话数组搬到新文件」**：磁盘上 `<Dialogue id>` 已经存在、零缺失，且（NPC名, 组id）组合唯一。组级增量的真实成本不是重新设计标识，而是让**读取方把已有的 id 属性保留下来**（今天被丢弃，见 2.0.4）。
- **句级（单个 `<SubDialogue>`）不可行，与用户判断一致**：`<SubDialogue id>` 实测**不唯一**——`data/dialogues/npc_dialogue_成员.xml:69-87` 里 NPC「王道」的同一个 `<Dialogue id="0">` 内出现两个 `<SubDialogue id="0">`。且一句话脱离上下文没有意义、后续难读。故单元固定为「一组连续对话」。
- **多组隔离成不同单元可行**：合并后每个 NPC 是「组数组」，组与组之间无交叉引用（`TaskRequirement` 也挂在组层），故 `replace` 按 (NPC名, 组id) 逐组替换、`append` 追加新组，互不影响。
- **追加的组 id 由后端分配，大模型只提供对话内容**（用户裁定）。分配口径沿用阶段四已冻结的 `agent_*` id 段（G4-4），并补齐取号规则：
  - **按 NPC 作用域**取号（不是全局，因为裸 id 只在 NPC 内唯一）；扫描范围＝该 NPC 在基础文件里的全部组 id ∪ 该存档覆盖层里已分配的 `agent_*` id；
  - 形态＝`agent_<n>`（n 从 1 起自增），**与基础数据的纯数字 id 永不相撞**——这比「从数字高位段起」更稳，因为不必假设基础数据将来不会用到高位数字；
  - `<Dialogue id>` 是 XML 属性、消费侧按字符串处理，今天两侧加载器都丢弃它（见 2.0.4），故引入非数字 id **不影响任何现有代码**；
  - 分配后**写回覆盖层文件**（见 2.0.8 的 `group_id` 字段），使后续读取与二次修改都按稳定 id 定位，不依赖数组顺序。

#### 2.0.4 运行时路径与合并点：谁必须改、谁零改动（本轮调研最重要的纠正）

**NPC 日常对话的生产路径只有一条，且在 C#。** 上一轮调研写的「两侧加载器都要保留组 id」**是错的**，据此纠正：

- **唯一活路径**：`scripts/逻辑/关卡系统/关卡系统_lsy_地图元件.as:395-413` 在 NPC 初始化时调
  `DataQueryService.query("npc_dialogue", {key: NPC名, taskProgress: _root.主线任务进度}, cb)`
  → C# `DataQueryTask.QueryNpcDialogue`（`launcher/src/Tasks/DataQueryTask.cs:74-99`）
  → `DataCache.GetNpcDialogues()` → 过滤 `TaskRequirement > taskProgress` → **只返回每组的 `SubDialogues`**（`result.Add(g.SubDialogues)`，组身份在返回值里本来就被抹掉）
  → AS2 `_root.组装单次对话(response.result[i])` 存到 MC 的 `默认对话` 上。
- **AS2 侧的两套对话装配都是死代码**（已核实无生产调用方）：
  - `_root.加载并配置NPC对话`（`通信_fs_lsy_XML数据解析.as:411-438`，自解析 XML 写 `_root.NPC对话`）——全仓**只有定义、没有调用点**；
  - `NpcDialogueLoader`（`gesh/xml/LoadXml/NpcDialogueLoader.as`）——`getInstance()` 只出现在 `ListLoaderTest.as:397` 与该文件末尾**被注释掉的示例**（`:202-222`）里；
  - `通信_fs_lsy_XML数据解析.as:478-496` 的注释也明说「NPC对话现在通过 Launcher npc_dialogue 查询按需获取」，并把整套生命周期 API 留成 no-op 存根。
  - ⚠ 顺带发现一处**注释与实现不符**（既有偏差，非本轮引入）：`DataQueryTask.cs:71` 注释称「数据加载失败 → Flash 走 legacy fallback」，但实际调用点 `关卡系统_lsy_地图元件.as:409-411` 失败时只发一条服务器消息，**没有任何 fallback**。也就是说 C# 加载失败＝NPC 没有对话。
- **结论**：对话覆盖层的合并**只需在 C# 一处做**，返回结构不变 → **AS2 零改动**（不必给 AS2 加 id 保留、不必新建对话热重载通道）。C# 侧唯一的数据结构改动＝`DialogueGroup`（`XmlDataLoader.cs:13-17`）加一个组 id 字段，用于在「某 NPC 的组列表」里定位要替换的那一组；`XmlDataLoader` 读它只需照抄同文件已有的 `subElem.GetAttribute("id")` 写法。
- **合并必须发生在 `_cache.GetNpcDialogues()` 之后、过滤 `TaskRequirement` 之前**，这样 `QueryNpcDialogue` 的返回结构逐字不变，符合用户「游戏拿到的还是一整份数据，只是里面某一段被替换好了」。

**任务文本（`$KEY` 级覆盖）的生产路径在 AS2，且合并语义已经现成。**

- `TaskTextLoader`（`gesh/json/LoadJson/TaskTextLoader.as`）按 `data/task/text/list.xml` 的 `<text>` 条目并行加载，用 `ListLoader.dictMerge()` 合并成一个大 dict（`:59-75`）；`dictMerge` 就是 `acc[key] = childData[key]`（`ListLoader.as:208-215`）→ **后合并的文件覆盖同名 key**，正是我们要的 key 级增量。
- 已有增量热重载 `reloadFiles(names, …)`（`:109-135`）：只重读宿主判定变化的文件，其余用 `sources` 缓存按 list.xml 原序 `_remerge`；缓存不全时退回整目录 reload，「不猜半份数据」。
- **两处必须处理的接缝**（因为覆盖层文件不在 `data/task/text/` 下）：
  1. `ListLoader.ownedEntries(names, basePath, entries)`（`ListLoader.as:105-117`）会**按 `basePath` 前缀过滤**变化清单，且只认 list.xml 已登记的条目名 → `data/rag/agent_saves/<slot>/…` 的变化会被直接丢掉。处理方式＝在领域 loader 里**单独判断覆盖层路径**，不走 `ownedEntries`；
  2. `entries` 是合并顺序的权威，而覆盖层不能登记进 list.xml。处理方式＝把覆盖层当作 `_remerge` **之后**的一次额外合并（`dictMerge` 语义，覆盖层最后 → 它总是赢），由领域 loader 显式持有覆盖层路径，不塞进 `entries`。
- `TaskDataLoader`（任务对象侧）同理：Agent 任务文件是**整份追加**，走数组拼接而不是 key 覆盖；同样需要在 list.xml 之外显式增读一个文件。
- 入口不变：`_root.重新加载任务数据(onSuccess, onError, changedFiles)`（`通信_鸡蛋_任务系统.as:6-71`），`changedFiles` 缺省即整目录重载。

**大模型侧「对文件无感知」今天已天然成立**：语料只有一个装配入口 `load_corpus()`（`services/retrieval/loader.py:972-1018`），进 prompt 的只有 `node.text`（`services/retrieval/hybrid.py:472-529 _nodes_to_text`），`source_file`/`id` 全仓无任何 prompt 侧消费方。要改的是**装配阶段**：`load_dialogue_nodes`（`loader.py:127-191`）、`load_task_nodes`（`:224-293`）、`GameDataRegistry.load_all`（任务校验/候选池/文本解析口径，`registry.py:53-63`，且它启动时一次加载、**运行期无 reload 调用点**，换槽位后必须显式重建）。
**⚠ 对话节点的 `character` 不等于 NPC key**：`character` 取组内第一句非 `$PC` 的 `<Name>`（`loader.py:162-176`），实测 **370 组里有 14 组与 `<Dialogues><Name>` 不一致**（如块名「酒泡氤氲-啤酒」而 `character`＝「酒保」）。游戏查询用的 key 是 `<Dialogues><Name>`，故**覆盖层必须按 `<Dialogues><Name>` 定位，不能按 `character`**；`character` 只继续用于检索侧过滤。

#### 2.0.5 修改范围（用户裁定）：跳过 Agent 任务对话，只改日常对话与「未完成任务」的对话

- **Agent 任务的对话不进入「后续修改」范围**：它只在任务发布时由大模型生成一次，属一次性任务；后续任何对话修改流程都**跳过 Agent 任务**，避免额外开销（也避免改坏已发布任务的接取/完成对话）。
  - 注意区分：Agent 任务的对话**仍然要进检索语料**（模型要能引用自己发布过的委托，2026-10-10 五轮链路走查已验证这条联动），只是**不可被修改**。
- **可修改的两类**：① 游戏原有的 **NPC 日常对话**；② **当前存档进度尚未完成的任务**的对话（`get_conversation`/`finish_conversation` 指向的 `$KEY`）。已完成任务的对话不改——改了玩家也看不到，且会污染「已发生的事」。
- **「未完成」的判定口径（已核实）**：`_root.tasks_finished` 是 `{任务id: 完成次数}`，**值是次数不是布尔**（`ObjectiveEvaluator.as:58` 有显式警告注释「⚠ tasks_finished 值=完成次数非布尔（可重复任务自增），显式 >=1，禁 ==true」）。故未完成＝ key 不存在 **或** `Number(值) < 1`。bind 载荷的 `progress` 已计划携带 `tasks_finished`（G2-1），后端据此筛选可改任务集合。
- **检索范围随之收窄**：只有上述两类进入「可改」候选池。这是一个**新增的筛选逻辑**，今天不存在（当前语料把全部任务与对话都装配进去）；施工时要决定筛选发生在语料装配阶段（进索引的就只有可改的）还是检索之后（索引全量、只在修改工具侧过滤）。**建议后者**——索引内容不该随存档进度变化，否则每完成一个任务就要重建索引（见 2.0.7 的代价）。

#### 2.0.6 性能口径（用户硬约束：不得引入频繁开销，热更新不能卡太久）

分四处，每处给实测体量与建议做法。**总判断：游戏侧的增量成本可以压到玩家无感，真正的代价在后端索引重建，而那不在游戏渲染线程上。**

1. **C# 对话缓存：base 缓存不必失效，只清覆盖层（阶段四 G4-4 已定的做法，本节确认它同时解决了性能问题）。**
   - 现状 `DataCache`（`launcher/src/Data/DataCache.cs`）double-checked locking 延迟加载，`_npcAttempted` 一旦置 true **永不复位**，且**加载失败也永久缓存失败状态不重试**（`:23` 注释原文 `non-null = 加载失败（永久缓存，不重试）`）。
   - **这个「永不失效」在本方案里不构成障碍**：G4-4 定的合并位置是「base 查询结果之后应用覆盖层」，且**覆盖层单独按 `(savePath, 文件版本)` 缓存**，base 缓存不动（§4.5 风险预检也已明写「覆盖层失效只清覆盖层，不得误清 base 缓存导致全量重读抖动」）。所以换存档/改覆盖层都**不会**触发 330KB XML 的重解析。
   - 体量实测（供判断「万一要重建」的成本）：`data/dialogues/` 13 个 XML 共 **330KB**，最大单文件 51KB（`npc_dialogue_成员.xml`），最小 57B（模板）；解析发生在 **ThreadPool**（`DataQueryTask.HandleAsync` → `ThreadPool.QueueUserWorkItem`），不阻塞渲染，进程内今天只解析一次。
   - 覆盖层本身是小文件（单文件条数上限 200，附录 B-5），解析与合并成本可忽略；失效＝丢弃一个小缓存对象（O(1)）。
2. **⚠ AS2 的对话绑定是「一次性」的，这是热更新的真实边界，必须先定口径。**
   - `关卡系统_lsy_地图元件.as:390` 是 `if (目标.默认对话 == null)` 才发查询，结果存在 MC 上（`npcRef.默认对话 = assembled`，`:406`），并置 `NPC对话已绑定 = true`；`通信_fs_lsy_XML数据解析.as:480` 也明说对话「存储在 MC 上，随 MC 销毁」。
   - 所以**覆盖层更新后，当前场景里已初始化的 NPC 不会自动拿到新对话**——C# 缓存失效只保证「下一次查询」拿到新数据。可选口径：① 接受「下次 NPC 初始化时生效」（重进场景/读档即生效），零额外代码；② 加显式重绑（清 `默认对话` 与 `NPC对话已绑定` 后重查）。任务侧已有同类先例可参照（`task_reload_owed` 欠账标记，只在真收敛后推进版本号）。
   - **建议阶段四采用 ①**（对话不像任务那样有「立刻要看到」的诉求，且 ② 要遍历场上 NPC、有额外开销与竞态）；若作者要 ②，需单独评估遍历成本与「玩家正在对话中被换掉文本」的竞态。
3. **任务文本／任务对象的增量热重载：已有机制，覆盖层是小文件，量级不变。**
   - `TaskTextLoader.reloadFiles` 只重读变化文件、其余用 `sources` 缓存重合并（见 2.0.4）；覆盖层文件今天量级很小（`agent_text.json` **12.7KB**、`agent_tasks.json` **3.5KB**），合并是一次 `dictMerge`（浅层 key 赋值）。
   - 宿主侧成本＝`MapTaskCatalog.Load` 多读一个十几 KB 的额外源文件，相对现有目录重读可忽略；`ChangedSources` 逐文件比字节，覆盖层没变时不会进变化清单 → **不会触发无谓的游戏侧重载**。
   - 用户已确认的参照系：Agent 任务改成非全量更新后卡顿消失，这个量级可接受。本方案在此之上**只增加小文件**，不改变量级。
4. **后端索引重建：这是唯一的重成本，但不在游戏进程里。**
   - **索引只能全量重建**：`services/retrieval/store.py` 无任何 cache/incremental/partial 机制，`VectorStore.build` 一次 `embedder.encode(texts, batch_size=32)` 算完全部向量（`:142-165`）。当前索引 **4883 节点**，落盘 `tools/vector_index_v3`（`vectors.npy` 5.0MB、`meta.json` 2.87MB、`bm25.pkl.gz` 1.71MB）。
   - 重建发生在**后端 exe 进程**（独立于游戏），不占游戏渲染线程 → **玩家游玩不会因此卡顿**；代价是 CPU/内存占用与「改完到能被检索到」的延迟。
   - 缓解口径（2.0.7 展开）：① 覆盖层不放进 `_FINGERPRINT_SOURCE_DIRS`，重建由我们**显式**触发而不是被 mtime 误触发；② 节点 id 改稳定标识，为将来做「只重算被覆盖节点」的增量向量化留门（今天不支持，属独立改动）；③ 语料范围按 2.0.5 收窄。

#### 2.0.7 语料发现与索引重建口径（施工前必须定死，否则会静默丢数据）

- **⚠ 今天的两处发现口径本来就不一致**：指纹 `compute_corpus_fingerprint` 用 `base.rglob("*")` **递归**扫 `_FINGERPRINT_SOURCE_DIRS`（`loader.py:106-110`），而 `load_task_nodes` 用**非递归** `task_dir.glob("*tasks*.json")`（`:224-293`）；后端 `parsers.py:120-144 iter_files` 又是「有 list.xml 就只认登记项，没有才递归 glob」。**覆盖层不能指望任何一侧的自动发现**，必须显式按当前 bind 的 `slot_key` 拼路径读取。

- **索引重建的成本口径（用户已裁定，2026-10-11）**：覆盖层一旦纳入指纹，每次改动＝全库 4883 节点重建。裁定采纳本节建议：**阶段二只把任务侧覆盖层纳入语料（量小、且本来就要迁），对话覆盖层留到阶段四再纳入**（阶段二不改对话）；各类覆盖层按「各自最小化覆盖」原则预留结构（最小单元与落点见 §2.0.2/§2.0.8），对话侧不与阶段四冲突。若将来重建太频繁，再考虑「覆盖层单独建小索引叠加」或实现增量向量化，而不是把它排除出指纹（排除＝模型看不见改动）。

  `{"overrides":[{"base_dialogue_id": string|null, "group_id": string, "action": "replace"|"append", "npc": string, "subdialogues":[{"Name","Title","Char","Text"}], "reason": string, "source_task_id": number|null, "source_trigger": string, "created_at": string}]}`

  - `action:"append"` 的 `base_dialogue_id` 为 `null`，**大模型不提供 id**；后端按 §2.0.3 分配 `agent_<n>` 后写回 `group_id`。

### 2.5 风险预检

- 换存档热切换：若现役流程总是「回标题→读档」，unbind/bind 挂在标题返回与读档完成两点即可；若存在同进程热切换，须补槽位变化事件——施工前在 `SaveManager`/`fs_bootstrap` 确认实际路径并记录。
- 面板常开期间的时效：exe 投影以最近一次推送为准；对话改写等关键判断都在事件触发当刻进行（数据总是当刻推送），展示性字段可能滞后到下一次落盘/事件，属可接受口径（见需求 FR-4 时效口径）。

### 3.0 用户裁定（2026-10-12）：施工口径以此为准，覆盖本节原有设想

- **开关**：非游戏打开（standalone）时设置面板给「跨对话长期记忆」复选框，**放在「Agent 能力」下面**，默认关闭；
  **游戏内打开（embedded）恒定启用、前端不给这个按钮**，后端也不受理关闭请求。
- **作用域**：绑定存档＝槽位键，每个存档一份自己的长期记忆；未绑定＝独立作用域键 `__standalone__`，
  与各存档互不混淆。落库时带来源窗口 id（`source_session_id`）。
- **结构**：一个作用域内某 NPC ＝ **一条基础长期记忆**（玩家与 NPC 的整体关系情况＋NPC 对玩家的整体印象）
  ＋ **至多 20 条追加长期记忆**（关键事件或信息，提示词口径 100 字以内）。
  基础印象的字数口径分两段（2026-10-12 复核追加）：**首次写入 100 字以内**（信息少时一句即可，
  给后续补充留空间），**已有印象的更新仍是 300 字以内**。
  入库统一上限 500 字，超出截断（后端校验比提示词宽松）。
- **触发时机**：基础长期记忆在**滚动摘要那一轮同时产出**（同一次 LLM 调用：摘要走 `content`、
  基础印象走 tool_calls）；追加长期记忆由**聊天 Agent 随时触发**。
- **与摘要隔离**：摘要轮把长期记忆作为**独立块**下发，并写明长期记忆不参与「摘要」的撰写。
  提示词里的实际称呼＝**「摘要」**（不是"模糊记忆"，那是用户的口头叫法）。
- **满 20 条**：工具**只剩调整能力**。模型视角下**完全感知不到另一个分支里"无需编号的追加"**——
  该形态的工具名、描述、参数表里零处出现「追加」「新记一条」「留空」等字样；
  业务上仍能记新事＝把不重要的那条**改写**成新的。
- **尚无基础长期记忆时**：聊天侧工具改成**必须同时给出基础印象与一条关键记录**（两个参数都必填）。
- **任务发布**：一般小任务不改长期记忆（A 兵团元老本就经常发任务）；只有重要任务才记，且记的是「已发布」状态。
  后端每轮实时读 Agent 任务完成情况，命中「本 NPC 发布且当前存档已完成」就把**完成对话原文**拼进提示词；
  该 NPC 已有关键记录时再追加一句「把它更新为已完成」。
- **一个对话窗口可存的长期记忆条数上限**：用户提出未来可能要，本阶段不做。

## 4. 阶段四：任务完成后对话联动

**目标**：完成 Agent 任务 → 对话完善 Agent 产出按存档覆盖条目 → 游戏对话查询合并生效。

### 4.0 用户补充口径（2026-10-13 逐条给定，施工以此为准，覆盖 §4.1/§4.2 原有设想）

本节是用户在本轮施工前补齐的全部需求口径，登记在此避免后续遗忘。**与下文冲突处以本节为准。**

#### 4.0.1 子 Agent 的定位：独立链路，绝不影响主链路

- 对话修改子 Agent 是**完全派出去的独立 Agent 链路**：自行做搜索、修改的全链路与判断权限。
- **绝对不影响主链路**，也**不能打断模型输出的主链路**（前台聊天照常出字）。
- **委派上限放宽一点，先保证功能实现**（成本控制放在「注册闸 + 首次有效」上，见 §4.0.4）。

#### 4.0.2 三个触发（触发口径全部由用户给定）

1. **重要任务（发布时挂标记，完成时自动委派）**
   - 发布任务时挂**两个字段**进任务表：「这个任务很重要，要触发对话重写」＋「重写的指示」。
   - 任务完成推过来时看标记**自动发起子 Agent**，贴给它的材料＝该 NPC 的一堆资料提示词、该任务详情和对话、
     **发布这个任务的对话的摘要 + 摘要后的精确对话**、这个工具/SOP 流程的各种介绍、模型记录的指示。
2. **好感度跨档**
   - 拼提示：「你的关系从 xx 变为了 XX（不管是上升还是下降），可以考虑调用对话修改的子 Agent，调整你的对话措辞」。
   - 模型没调用就**持续 3 轮**（用户裁定）。
   - **一旦模型调用了，立刻去掉这个提示词**，换回原来那种「如无必要，不要调用」的思路。
3. **聊天中主动调用（主用途＝日常聊天里的长期影响；任务只是兜底）**
   - **主用途（2026-10-13 用户补充，本条原先只写了任务，是写窄了）**：日常聊天中发生**很重要的对话、
     导致产生很长期的影响**时，由模型主动调用子 Agent——即 §4.0.4 更改类型里的**关键信息**与
     **态度变化 / 关系重大变化**这两类。这两类**没有别的路径会自动委派**（触发一只覆盖任务、
     触发二只覆盖好感度跨档那一刻），只能靠模型在聊天中自己判断，所以本触发主要是为它们而存在。
   - **任务只是「顺便兜底遗漏」**：任务主要走触发一（发布时挂标记 → 完成时自动委派）。
     本触发里提任务，**只为兜住「重要任务在发布时没有打标记」的遗漏**——没标记就不会自动委派，
     只能靠模型在聊天中补一次调用。
   - **任务表述的条件闸（必须实现，不是可选优化）**：本工具的提示词按当轮上下文**二选一**——
     - **完全排除掉任务，只要求看关键信息和重大变化**（任务相关表述整段移除）：当
       ① 当前（已完成任务提示词里的）任务**有标记**（已自动触发，模型本就不该重复调用），或
       ② 当轮**没有已完成任务的提示词拼接**时。
     - **才保留任务兜底表述**：仅当当轮有已完成任务提示词拼接、且其中存在**未标记**的重要任务时。
       （推导：混合场景按「存在未标记任务」处理——用户口径是兜「发布时没标记」的遗漏，有遗漏就得提；待复核。）
     这与 §4.0.4 的注册闸同一精神：**给了才提，不该给就一个字都不提**。
   - 原拟的工具提示词（**只在上面「保留任务兜底」那一版里用**）：「当你首次获知某任务已经完成，
     且该任务非常重要时，你可以在确保说完聊天对话的同时，主动调用该子 Agent，并给出指示」。
   - **兜底提醒**（属已完成任务提示词拼接那一侧，不属本工具的提示词）：发布时已标记的任务，
     明确提醒「该任务已自动触发对话修改的子 Agent，请勿因该任务而重复调用」；
     **即使这个任务被完成了、把完成信息提供给模型时，这句话也一直保留**；未标记的任务不加这句。
   - 要有字段说明「这是因为已完成任务而提的」→ **必须给任务 id**，故已完成任务信息里也要明确给任务 id。

#### 4.0.3 子 Agent 固定流程（轮数上限由流程定死，不靠提示词自觉）

- 第一步先**决定要不要改**；要改再**查询**（范围多选）；查询结果**拼在最后面返回、都编好号**。
- 模型**只能按编号整组按格式修改**。
- **只提供、也只允许修改 `npc 名` 和 `对话` 两项**；`title` **既不拼接给模型，也不让模型写**，
  由后端自动用 npc 名带入。
- 「如果模型只需要改其中一句，其他不需要修改的就**原样保持**。只有需要的时候再做修改。
  **只输出其中有需要修改的组**，可以改台词，可以向后加台词。」
- 「大概这样**三轮固定轮**我感觉就够了。」第二轮可再查一次；**最多查两次**，达到上限后
  **不注册查询工具和对应提示词**，只要求模型做修改——轮数上限用流程定死。

#### 4.0.4 防呆与成本控制

- 调用时**必须传更改类型**（关系变化 / 态度变化 / 关键信息 / 重要任务）；**重要任务必须传任务 id**。
  - 与触发的对应关系：**关系变化 / 态度变化 / 关键信息**主要由触发二、触发三产出（都靠模型在聊天中判断）；
    **重要任务**主要由触发一产出（发布时挂标记 → 完成时自动委派），触发三只在兜「发布时漏标记」时才会带上它
    （且带不带受 §4.0.2-3 的条件闸控制）。
- 任务 id「**只有首次传有效，后续再传就静默跳过**」。
- **注册闸**：「注意**注册工具和给提示词是完全同步的**，注册了才给，不注册就完全不给、完全不提及，
  一点相关内容都没有。」当前唯一约束＝**后台有该子 Agent 在跑的期间，模型完全不注册这个子 Agent**（避免并发调用）。

#### 4.0.5 对话数据层六条口径（本轮 BACK 数据层的施工依据）

1. **任务对话中，首先必须是有这个 npc 说话的组才在候选**，没有就不在。
2. 任务对话修改时要**明确要求**：只能改语气态度或补充额外信息、新增对话，**不能删除原有信息**。
3. **通常不建议选择任务全量**，而是建议**日常全量 + 较多关键词**（给模型的选项注释逐字口径见下面第 ⑤ 条）。
4. 新增「**任务近期**」范围＝后续最近的主线支线，**取最近 10 组对话（主线 5 组 + 支线 5 组）**，可修改。
5. **四种查询范围**：日常全量（推荐）、任务近期（推荐）、关键词（可选）、任务全量（不推荐）。
   - **⚠ 这里是多选，不是单选**（2026-10-13 用户补充）：给模型的参数说明里**必须写明「多选」**，
     一次查询可以同时选多个范围（结果按范围分桶拼接后统一编号）。
   - **「任务全量」的注释必须连理由一起写全，不能只留「不推荐」三个字**（2026-10-13 用户补充：
     「这里不能只有一个不推荐，不然这个选项会让模型觉得很奇怪」）。**逐字口径**：
     「不推荐。除非是非常重大的关系变化、导致所有对话都必须全部修改时，才选中任务全量；否则不建议选。」
   - **任务近期和任务全量冲突**，二者都选时**采用任务近期**。
   - **关键词是在剩下的里面搜**，这里也有上限，**30 组对话**。
   - **已完成的都排除，任务 Agent（委托）都排除**。
   - 单次**文本上限 30000 字符**（用户口径：「15000 应该也差不多，放宽到 30000 也行」，取 30000）。
6. **任务对话新增＝只能在本组内新增对话条数**（实际上还是改本组，只是可以加条数）；
   **日常对话允许直接不断增加一组新对话，也可以修改已有组**——这是两者的另一个区别。

## 7. 待开发设计：Agent 任务的「回接取 NPC 领奖」两段式配对（用户提出 2026-10-08，调研已完成，未授权施工）

### 7.1 用户裁定与目标形态

**裁定前提**：任务**完成对话必须是玩家与完成 NPC 的对话**，不能是与接取 NPC 的对话——玩家点的是完成 NPC，此时接取 NPC 不在画面中。这与现有实现一致（`TaskRewardCommit.as:141` 在完成时播 `finish_conversation`；`通信_鸡蛋_任务系统.as:206` 在接取时播 `get_conversation`），因此**不改**这条语义，只在其之上补配对能力。

**衍生问题**：传话类任务（A 发布 → 送到 B）若奖励由 B 给，一个任务即可；若奖励必须由 A 给，就要两个连续任务。用户目标形态：

- **任务一（把话带到）**：接取 NPC = A，完成 NPC = B；奖励**固定写死 `经验值#1000`**（象征性），不需要大模型输出两种奖励；完成对话里 B 与玩家说话，随后**自动接取任务二**。
- **任务二（回去领奖）**：接取 NPC = B（== 任务一完成 NPC），完成 NPC = A（== 任务一接取 NPC）；**真正的奖励挂在任务二**；接取对话一般是玩家自言自语「该回去找 A 领报酬」（说不出称呼就直接说「该去领任务报酬了」），或由 B 提醒玩家回去找 A。
- **启用条件**：**仅当完成 NPC 与接取 NPC 不同**时，大模型才可选择是否启用第二段。不启用即一个任务，与现有逻辑完全无区别。
- **大模型只额外输出一个开关 + 一组对话**：`是否回到接取 NPC 领取奖励`（布尔）；启用时必须同步给出任务一接取对话、任务一完成对话、任务二接取对话、任务二完成对话——即对话由一组变两组，**开关与第二组对话固定搭配、不可省略**，保证启用时一定有对应对话。第一组任务数据仍在原参数里输出。
- **硬约束（任何时候都成立）**：接取对话只能与接取 NPC 聊，完成对话只能与完成 NPC 聊。
- **分工原则不变**：任务数据的大量填写工作由后端完成，大模型只输出后端无法自动填写的必要信息。

### 7.2 调研结论：对话连播**不需要**新机制（好消息）

用户担心的「完成对话之后还要接第二段的接取对话」已被现有代码覆盖：`_root.对话赋值到对话框`（`UI交互_lsy_对话文本.as:12-24`）是 **push 追加**，不是覆盖（覆盖走 `SetDialogue(arr, true)` → `对话覆盖赋值到对话框`）。`TaskRewardCommit.as:141-142` 的既有次序就是「先播完成对话 → 再触发自动接取」，自动接取成功后 `通信_鸡蛋_任务系统.as:206` 播接取对话，两段自然接在同一个对话框里。主线任务今天就是这么跑的。

已知瑕疵（**非本次引入，主线同样存在**）：追加时 `对话进度 = 0` 会把阅读位置重置回第一条。若验收时体感明显再单独处理，不在本节范围。

### 7.3 四个实打实的缺口（施工必须一并解决）

**缺口一：Agent 任务的自动接链当前是死的。** `MapNpcTaskProjection.cs:24` 只认 `chain` 形如 `链名#序号` 且 `序号` 可解析为整数的任务，否则整条链被 `Where` 过滤掉、`autoAccept` 里根本没有条目。而后端 `task_tools.py:472` 把 `chain` **硬编码成裸串 `"委托"`**，现有 5 条 Agent 任务与 46 条佣兵任务全是裸串形态（其余任务文件都用 `链名#序号`，如 `主线#1`、`后勤#3`）。所以「完成任务一自动接任务二」这条路径对 Agent 任务**从未生效过**。

**推荐做法：新增显式配对字段，不动 `chain`。** 理由是给 `chain` 编号会连带两个副作用：① `通信_鸡蛋_任务系统.as:386-400` 的 `提交任务完成状态` 在 `chain[1]` 可解析时会往存档写 `task_chains_progress["委托"]`，凭空多出存档状态；② `TaskUtil.ParseTaskData:110` 是 `task_chains[链名][序号] = id`，独立生成的多组任务复用 `委托#1/#2` 会互相覆盖。保持 `chain` 为裸串则走 `isNaN` 的 else 分支，`tasks_finished[id] = 1`，本来就是对的。配对字段由 `MapNpcTaskProjection` 消费以生成 `autoAccept` 条目，并复用其现有的同 NPC / 同地点判定（`MapNpcTaskProjection.cs:33-40`：无 `finish_endpoint`/`get_endpoint` 时要求 `next.get_npc == finished.finish_npc` 且 hotspot 为空或同地点）。**字段名与 schema 冻结位置待定，施工时先定名再落代码。**

**缺口二：任务二的 `get_requirements` 必须包含任务一的 id。** Agent 任务不带 `*_npc_hotspot` 字段，而 `MapNpcTaskProjection.Names:52-53` 对空 hotspot 的判定是「任意同名现场都算」；同时 `_root.taskAvailable`（`通信_鸡蛋_任务系统.as:245-261`）在 `get_requirements` 为空时**无条件可接**。两者叠加的后果：玩家不做任务一，也能在任意地图从 B 那里直接接到「回去领奖」。当前 `get_requirements` 只由阶段的 `unlock_condition` 推导（`task_tools.py:211-250`），配对时必须追加任务一 id。

**缺口三：固定的 `经验值#1000` 过不了 V7 校验。** `_compute_reward_value_range`（`validator.py:183-250`）的下界是 `阶段 × REWARD_STAGE_BASE_MIN(=10_000) × 类型倍率 × 好感度系数(≥0.9)`，阶段 1 即 ≥9000；而经验值单价恒为 1（`pricing_rules.py:63`，1 点经验 = 1 金额），1000 远低于下界。需要给「配对中的中间任务」开豁免（V2/V7/V8 三处相关），或改成**把配对当一个整体校验**、真实奖励只在任务二上算——后者更贴近用户「奖励只有一份」的原意，倾向采用，施工时定。

**缺口四：写盘必须原子地产出两条任务。** `write_confirmed_agent_task_files`（`task_tools.py:457-500`）现在只 append 一条、只 bump 一次版本。配对需要：两个连续 id（区间 200001–300000，取 max+1，见 `task_tools.py:337-348`）、两条任务同时 append、8 个文本键（两组 title/description/get/finish）、**且只 bump 一次** `task_publish_version`，避免游戏侧热重载读到半套数据。

### 7.4 用户提的「打回重试」落点：confirm 阶段目前**不重试**

用户要求「大模型写错了可以带上具体报错和修改建议打回重试 1 次，但首先保证提示词里有明确说明、指引和约束」。现状分两截：

## 8. 提示词信息供给（NPC 场景块 / 传话问候选人指引 / 选关类关卡怪物）（用户提出 2026-10-11，同日调研＋施工完成；状态见 §8.6，2026-10-12 追加批见 §3.6）

### 8.1 需求与格式（用户给定；下列文本即提示词内容，实现时按此逐字拼接）

- **优化点 1：发布后若干轮内持续供给任务达成要点。** 现状＝选关类的关卡与怪物块只出现在草案摘要与发布当轮（§8.1、§8.5），再往后的轮次里这些文本随对话窗口滚出；玩家忽然回头问「那关有什么怪」「打完交给谁」时模型只能靠检索或含糊作答。目标＝任务发布后的几轮（含发布轮）内，把该任务的达成要点（要提交/获取的物品、要打的关卡与关卡怪物、完成 NPC 及其场景）持续拼进提示词。待定口径＝保持几轮、是否只在被问到时才拼、与既有已完成委托块及检索块的去重边界。
- **优化点 2：绑定存档时的「进行中委托」说明。** 现状＝只有已完成（`tasks_finished`）会拼给模型，玩家在游戏里接了还没打完的委托对模型完全不可见；玩家说「我正在打」时模型无从呼应，甚至可能重复发布同一委托。目标＝embedded 绑定存档时，按投影里的进行中任务（bind 载荷 `progress.tasks_active`，已带 `requirements.stages`，见 §附 B-1）在共享 user core 里补一段「你发布的委托尚在途中，未完成」，与已完成委托块同构：同一 NPC 过滤、每轮实时算、不记账、不落 status 字段。
- **共同落点与纪律**：两项都只动 BACK 单仓（`services/agent_tools/` 新增拼接 ＋ `services/orchestrator/context.py` 装配 ＋ `services/orchestrator/prompts.py` 块序），GAME/WEB 零改动；受 §0.2-3 命名冻结与 §0.2-7「提示词只写本轮要用的信息」约束。开工前须先定三件事：进行中判定（`tasks_active` 与 `tasks_finished` 的次数口径见 §2.0.5）、进行中块体积上限（已完成块现每轮 3 条）、以及「几轮」的计数落点（按会话轮次还是按存档内轮次，跨会话怎么续）。

  `{"overrides":[{"base_dialogue_id": string|null, "group_id": string, "action": "replace"|"append", "npc": string, "subdialogues":[{"Name","Title","Char","Text"}], "reason": string, "source_task_id": number|null, "source_trigger": string, "created_at": string}]}`（键序即落盘键序）；单文件条数硬上限 200，超出**最旧 append 条目先淘汰**（replace 不淘汰）。
  **`group_id` 定稿口径（2026-10-13）**：**每条条目都带 `group_id`**（＝合并视图里的组 id），不再是「仅 append 有值」。
  `action:"replace"` 时 **`group_id == base_dialogue_id`**（都填基础 XML 的 `<Dialogue id>`）；
  `action:"append"` 时 **`base_dialogue_id` 恒为 `null`**（大模型不提供 id）、`group_id` 存后端分配的 `agent_<n>`
  （**按 NPC 作用域**自增，扫描该 NPC 基础组 id ∪ 覆盖层已有 `group_id`，取 `agent_` 最大序号 +1）。
  消费方**按数组顺序应用、并按 (`npc`, `group_id`) 去重**：`group_id` 已存在即整组替换而非追加，
  故**对某个 `agent_*` 组的二次修改写成 `action:"append"` + 同 `group_id` 就是就地更新**（不产生重复组，见 §4.0.5-⑥ 与 §4.2 B4-2-2）。

  **`Char` 必须是非 null 字符串**（AS2 `_root.组装单次对话` 会对它执行 `.split("#")`），玩家行三个占位符口径见 §4.0.7。
- **B-6 `data/rag/agent_saves/<slotKey>/task_text_overrides.json`**（2026-10-13 新增，用户裁定「任务对话可改，同批做任务文本覆盖」，见 §4.0.6）：
  **平铺 `{"$KEY": [ {"name","title","char","text", …附加字段} ]}`**——顶层没有 `overrides` 包裹、没有版本号、**不加任何元数据键**
  （元数据键会被 `dictMerge` 当成文本 key 污染游戏侧文本表）。数组项用**小写键**，与基础 `data/task/text/*.json` 完全同形，
  基础文件里出现过的附加字段原样保留（实测 973 个 key 全部以 `$` 开头，唯一附加字段是 `imageurl`，出现 96 次；
  `char` 可带表情后缀如 `Andy Law#微笑`）。
  生效语义＝**覆盖层里有这个 key 就整份替换**基础/任务增量的同名 key 值（复用 `TaskTextLoader.mergeOverlayText` 的既有 `dictMerge`），
  故一次修改必须写全该 key 的全部台词行（与 §4.0.5-② 「不能删除原有信息」同一口径）。消费方见 G4-7。
