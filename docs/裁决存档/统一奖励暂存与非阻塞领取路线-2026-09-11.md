裁决：选择受控 B，现在实施；角标修复与统一暂存合入同一候选、同一次部署列车

采用“一个当前暂存库存＋分来源原子入账＋独立、有界的恢复信息”。 已可靠保存的物资不再占用领取会话，也不再阻止任务、关卡或正常返回流程；只有资产写入结果未定时保留必要的互斥与恢复保护。

不选 A：仅统一界面、释放会话，仍不能解决现有收件箱的非空条目上限、普通条目对完整装备实例的表达不足，以及单个关卡 pending 阻塞后续关卡的问题。把这些补齐后，本质上已经进入 B。不选 C：目前没有新库存规模下的实测，足以证明必须同时重做全局持久化架构。

B 的成立条件是：来源消耗／来源结束、目的库存、必要去重结果必须写入同一完整存档；未确认保存不能发布成功；旧 root 不改变恢复语义；新格式读写与回退能力随同一个候选交付。 不满足这些条件时暂停整列车，不默认拆出角标单独发布。

二、最小数据模型与权限边界
2.1 升级现有扩展域，不永久叠加第二套收件箱

将 _saveExt.rewardInbox 升级为 v2 当前库存。 v1 只作为兼容读取、旧 root 恢复和迁移输入保留；同一角色不允许 v1 批次写入器与 v2 库存写入器同时经营同一批物资。

最小持久化内容如下：

内容	最小字段与约束
库存头	v、角色库存身份 storeId、单调提交修订、单调 ID 分配序号。序号不得回绕或超过安全整数。
当前条目	entryId、条目修订、完整 BaseItem.toObject() 数据。零数量条目删除，ID 不复用。
新命令去重	最近一次提交的操作身份、规范化请求指纹、前后修订、精确结果。结果与资产后像同一次保存，不额外形成逐条历史账。
兼容恢复	尚未退役的旧 receipt、旧 root／terminal 原有身份及必要字段；不得为了“统一”改写其语义。
有界迁移标记	已完成的固定迁移版本、已关闭的旧写入协议代际。不是按每件物品追加的永久日志。

新协议的在途 before/after 描述符保留在运行时；不另加一次“新 root admission”落盘。 新命令提交的磁盘后像必须已经包含完整资产结果和去重结果，不产生新的磁盘半提交状态。旧版 root 的持久化描述符与 admission 继续按旧协议处理。

来源完成证明仍放在能够解释该来源的领域内：任务完成状态、关卡 settlement 身份、地图来源代际、在线补给发放键等。不得为了统一库存再复制一份永久“奖励来源总账”。

2.2 合并规则必须是类型规则，不是字符串拼接

**可堆叠物：**以真实物品标识及影响游戏语义的变体字段为键，允许跨来源、跨批次、跨运行合并。来源名称、领取时间、原批次编号不进入合并键。只有经白名单确认没有独立实例语义的数值型物品才能这样合并。

**装备：**一条记录对应一个实例，保留强化、进阶、射击次数、模组及其他完整字段，不按同名合并。lastUpdate 也不能在迁移时随意重建。现有 BaseItem 已明确区分装备对象值与其他物品数量值。〔item/BaseItem.as:11–55、125–130〕

**旧格式尤其要防止数量误译：**普通奖励条目通过 BaseItem.create(itemName, remaining, …) 重建装备时，数值会解释成强化等级，不能把 remaining=5 迁成五件装备。存在冻结 itemData 的条目优先使用该完整数据；不存在的按旧解码语义迁移，不凭空补造原本未保存的模组。〔item/RewardInboxService.as:363–399、item/BaseItem.as:31–55〕

所有数量运算先检查有限、整数、正值及增量是否超出余量；不得先相加再检查，也不得经过位运算截成 32 位。2^53−1 是表示边界，不是取消物品自身数量、情报持有量等约束的许可。

旧 root 引用的 entryId、冻结 descriptor、lease 和指纹，在该 root 收敛前全部禁止改写。新条目修改不应无条件轮换所有兄弟条目的身份，避免重演“部分成功后幸存条目无法通过证明”的问题。〔docs/存盘风暴止血-Reward相邻durable-cut桥接与存盘次数回归门-ADR-2026-09-03.md:27–28〕

2.3 库存、浏览会话、资产写入权限必须分开

执行以下边界：

**角标／预取：**只返回库存摘要、修订和独立的恢复提示。不创建 authority，不自动 ACK，不推进 root，不调用可能规范化并写回的 ensureFeature。加载规范化属于加载阶段，不属于查询。

**浏览暂存：**建立只读视图；分页、排序、关闭均不取得资产写锁。显式取出时才创建绑定角色、会话、条目身份和修订的写意图。

**结果未定：**冻结冲突的资产写入、切档、破坏恢复上下文的场景终止，以及会覆盖候选状态的保存。只读查看可继续；不能把实际仍会产生掉落、消耗和保存的战斗继续运行称作“无冲突”。

**已提交但客户端没收到结果：**只查询原操作，不重建新操作。普通报告未读、库存未整理、终态等待客户端确认，不应被直接解释成全局资产未决。

角标修复不能只删除 AS2 的 materializeAuthority 调用：现有 Web 打开逻辑依赖查询返回的 inbox.authority，必须一起改为显式打开／写入握手，并修改 Host 的 handoff 与关闭语义。Host 清掉本地缓存不等于 AS2 已释放权限。〔launcher/web/modules/character-build/character-build-item-use-channel.js:159–189、launcher/src/Tasks/ItemUseTask.cs:427–469〕

三、提交协议：新命令原子批次，旧 root 保留 F1′
3.1 新暂存取出采用有界原子命令

新建版本化的暂存取出命令，不把 v2 取出套进旧版逐 child durable-prefix 协议。

首版单次取出最多规划 32 个条目，这是可调的操作规模参数，不是库存上限或已测得的性能保证。命令流程为：

校验身份与修订 → 基于当前目标库存纯规划可接收子集 → 一次应用该子集全部变更 → 保存“暂存减量＋目标增加＋操作结果” → 确认后返回。

容量不足的条目不进入本次接受集合；一旦集合确定，提交结果只能是整个接受集合已提交，或者尚未确认／未提交，不能在保存前逐项宣布成功。

“一键领取”是多个这样的命令，在已确认保存的命令边界让帧、刷新或停止；不生成一个横跨几千条目的同步大 root。重复查询和重复成功请求不新增资产、不再次保存；陈旧请求不能在忘记详细结果后被解释为新命令。

旧协调器会在目的写入后将源槽整格置空，因此只能复用其精确观察、目的规划等局部能力，不能原样承担共享堆叠条目的部分数量扣减。〔item/LootClaimCommitCoordinator.as:51–115〕

3.2 旧版 root 不降级，也不偷偷改批次语义

已有 v1 root 继续遵守 F1′：正常推进 N 个条目为 N+1 次可靠保存，首次 terminal ACK 另加一次。 bridge 保存确认前不执行下一 child；pending 响应不混合旧 root 进度和未确认的新资产快照。〔docs/存盘风暴止血-Reward相邻durable-cut桥接与存盘次数回归门-ADR-2026-09-03.md:45–79〕

新 v2 命令的一次保存不是复活历史上被否决的 F2：它从一开始就没有承诺逐 child 成功前缀，而是一个版本化原子命令。 必须同步修改 AS2、Host、Web 对该命令的结果理解，不能只在 AS2 批尾少存几次。

尚在推进的旧 root 查询可能产生合法保存；“查询零保存”只适用于纯摘要、纯结果重放等不推进状态的路径，不能机械覆盖恢复查询。

3.3 必须补齐“保存失败”和“回滚成功”之间的缺口

这是本轮新增写路径的硬前置，不是可后置清理。

当前 _doSaveAll 在 flush 前已经写入 so.data，并双写任务、商城等顶层镜像；_root.mydata 在失败后仍会被赋值，mydata.ext 又直接引用 _root._saveExt。开包回滚仅恢复运行时背包、奖励扩展和 dirty，没有恢复这些组包位置。〔SaveManager.as:942–976、2124–2136、item/ItemUseService.as:786–794〕

因此裁定：

不能照抄“flush 非 true → 恢复运行时对象 → 立即允许重新执行”的模式。 为本轮领域提交增加狭窄的保存结果分类与候选状态管理，保留其他调用方现有 Boolean API，不顺带改造成全局异步存档。

保存结果	允许行为
能证明尚未进入物理提交，或已确定无写入且候选已完整撤销	恢复完整 before-image，包括运行时资产、任务、扩展域、组包对象和顶层镜像；之后才允许重试。
pending、调用中异常、无法判定是否已落盘	保留同一完整候选和原操作；不得重新抽取、重复扣除、清掉来源或混入其他资产保存。只允许解析／重试该候选的提交结果。
本地提交明确成功	发布成功和可选效果；之后回包、音效、窗口关闭或 shadow 通知失败，不得把资产退回未提交态。

冻结实现确实把 "pending" 与其他失败压成同一个 false，其内部统计虽有区分，但新领域调用方目前拿不到足够的决策信息。〔SaveManager.as:3173–3209〕

保证范围是既有本地 SOL 提交契约下的防丢防重，不是同步双副本提交，更不是磁盘损坏时绝对不丢。 当前 shadow 发送在本地成功之后发生，不能把本地 true 描述为 shadow 也已可靠写入。〔SaveManager.as:997–1008〕

四、四条业务链的实施序列
4.1 任务：只消除背包容量拒绝，不承诺任何错误下都成功

统一 NPC 与 Web 的领域入口，重新验证当前任务实例、交付资格和提交物。不能只信数组下标，也不能把迟到的 taskId 请求重绑定到删除后重新接取的另一实例。

提交顺序固定为：

校验当前任务 → 构造扣交付物后的候选状态 → 规划奖励去向 → 应用完整资产及任务变更 → 可靠保存 → 返回结果与播报。

规划规则：

货币、经验、技能点等标量直接更新原领域。

材料、情报沿用原领域规则和合法性检查，不因“非背包物品”跳过上限。

药剂、手雷及其他物品使用同一份候选背包／药剂槽／装备槽状态规划；能接收的直接接收，仅因空间不足的余量进入暂存。

装备保留原奖励解析中的强化、数量与进阶语义，不改变 #／## 的含义。〔item/ItemUtil.as:615–798〕

这解决两种情况：交付物释放的空间可以立刻利用；释放后仍放不下的奖励也有可靠去处。禁止通过临时替换 _root 再调用带事件的真实 acquire 来假装纯规划。

**同一保存必须覆盖：**交付消耗、直接奖励、暂存增量、经验／技能点、任务移除、完成次数、任务链进度，以及本次必然产生的持久化成长结果。PAT 在明确保存成功后才发布相应提交通知；其 commit() 不是保存门。〔任务系统.as:331–349、393–470、644–657、item/PlayerAssetTransaction.as:241–266〕

升级不能简单归入“可失败的音效类后置效果”。包内只有调用点，没有实际升级函数实现；必须补查其持久化写集：等级、属性、技能点等确定性变更纳入同一提交，动画与界面更新后置。自动接后续任务继续作为独立、幂等的后续动作，不失败回滚前一任务，也不重新发前一任务奖励。

同时修复错误映射：TaskPanelService 当前把 FinishTask=false 一概回为 inventory_full，新路径必须区分条件不满足、数据非法、提交未定、保存失败和上下文过期。〔scripts/类定义/org/flashNight/arki/task/TaskPanelService.as:371–398〕

4.2 关卡：返回保存门内完成保管，到达后报告只读

新结算默认全部有效物资进入暂存，随后展示本轮报告。 玩家不用先领取或点击“延期”，便可继续当地交互及下一关。

新路径尽量复用现有返回保存门：

冻结本轮唯一奖励 manifest → 规划暂存入账 → 同时形成来源已保管终态 → 在现有返回门完成可靠保存 → 场景跳转／到达 → 展示非阻塞报告。

需要明确纠正：persistPreparedSettlement() 只写 _saveExt 并标脏，不是一次可靠保存；真正的返回保存门在 onReturnBaseStarted()。同样，clearPersistedSettlement() 自身也不能当成已落盘的来源结束证明。〔scene/StageRunSession.as:613–647、760–762、971–1011〕

新增明确的 stashed 终态或等价的版本化“已保管”语义，更新 AS2、Host、Web 全部终态验证器，不冒用 abandoned 表示保存成功。该终态解除物资保管对关卡放行的依赖；报告未读不再维持 rewards_pending。

旧存档已有 prepared 或部分领取结算时，只迁移经旧协议核对后的剩余 manifest，不重新生成原奖励。已经冻结的奖励保存失败继续使用同一份结果。

既有 64 格生成规则、情报截断及其他掉落规则本轮保持，不借暂存悄悄扩大掉落经济。〔scene/StageRunSession.as:1217–1277〕

4.3 地图实体箱：开启后保管，不是扫图自动收走

仅处理授权成功、属于此接入链的已开启实体箱：

验证开启条件和来源身份 → 冻结本次掉落 → 保存“暂存增量＋来源已消费证明” → 确认后执行实体结束及展示。

现有 LootMaterializationPlanner 不是纯规划器：resume() 内部会调用 commitTotalsAndDetachSource；其 journal 又挂在目标对象上，是进程内状态。必须将来源修改纳入新提交边界，不能直接调用完它再补一次“转存”。〔item/LootMaterializationPlanner.as:8–12、29–63、185–199〕

地图箱接入的硬条件是可恢复的来源身份：持久化的运行／场景实例代际＋箱体实例标识，或能证明等价的既有身份机制。来源消费标记在该实例可能恢复期间保留；只有整个实例代际不可再恢复、旧请求也被拒绝后才能清理。

不能仅用 MovieClip 引用、物理槽位或本次进程的 getTimer() 作为跨重启去重证明。必须覆盖这一反例：

暂存保存已成功，实体死亡动画尚未执行就崩溃；重启恢复同一个箱体后再次开启。

默认成功后只给低优先级提示。“立即收取”也应变成从已入账暂存中取出的另一命令，不能再次从原箱体发奖。关闭、Esc、切场景只结束展示；若提交未定，仍不得销毁恢复上下文。旧版已经打开但尚有余量的箱体，在关闭／切场景前先完成余量转存，不能仍走普通过期丢弃分支。〔item/LootContainerService.as:500–555、1517–1575〕

未开启箱体、未通过开启条件的箱体、其他地面拾取链保持原样。

4.4 背包礼包：保留一次命令一次提交，取消自动跳页

单开和 openMany 改为：

校验原背包物品身份 → 按原顺序冻结抽取结果 → 规划合并 → 扣包＋暂存增加＋精确结果一起保存 → 提示完成，停留当前页。

保留现有 openMany 的 2～64 包命令边界，不退回每包一次保存；拒绝非法数量和超出单次计算／写入预算的操作。〔item/ItemUseService.as:175–269、727–731〕

随机语义作如下裁决：

已可靠提交后永不重抽。

同一未决提交只恢复原候选，不重抽。

明确未提交并完整撤销后的新尝试，继续允许既有的重新抽取语义；本轮不新增持久化随机数总账，也不承诺失败重试必然同奖。

取消 Web 成功后自动 _openRewardInbox() 的逻辑，但保留用户主动打开入口。〔launcher/web/modules/character-build/character-build-item-use-channel.js:213–236〕

此外必须接线两个现有生产者：在线补给发放与旧手雷槽恢复。 前者保留原发放键去重，后者保留迁移标记及“清旧槽与新入账同提交”。不接这两处，v2 上线后仍会有人向废弃的批次结构写物资。〔item/RewardInboxService.as:124–239〕

4.5 “拥有”和“可消耗”分别定义

可靠进入暂存即归玩家所有。获得播报、获得类成就／任务计数只在首次取得所有权时发生；暂存与背包之间移动不重复触发。

凡会改变存档的获得类消费者，其变更必须进入同一提交或由持久化状态幂等重建，不能仅靠保存后的易失通知实现。音效、浮字和界面刷新可以保存后执行，失败不回滚资产。

本轮不扩展 ItemUtil.contain、交付、配方或使用的消费范围，也不开放战斗中的远程暂存取物。具有总持有量上限的物品，首次入账检查必须计入暂存所有权；内部取出则不得再次按“新获得”计数。否则情报等物品会出现暂存绕过上限，或取出时重复截断的问题。

5.2 必须处理三个兼容陷阱

第一，空数组只修已知空形状。 当前奖励规范化器会把非数组的 batches、receipts 等直接替换为 []；新迁移不能继承这一宽松行为。只对已知版本的合法空 {} 作定点修复；非空错误对象隔离并保留。装备 mods 等嵌套字段也遵循这一原则。〔item/RewardInboxService.as:1683–1709、item/BaseItem.as:47–54〕

第二，嵌套数据与顶层镜像同时更新。 Host 的迁移读取会合并顶层任务／商城数据，并在部分情况下优先使用非空顶层。因此只清嵌套来源，会使旧已购行或任务被读取链重新带回来。〔launcher/src/Save/SaveMigrator.cs:65–100〕

第三，关闭旧写入协议，才能有界清理历史证明。 receipt 不是无限保留，但也不能“过期后当没发生”。新协议依靠持久化修订拒绝陈旧写；旧协议在代际关闭后只提供结果兼容或明确过期，绝不把查不到历史结果回成可重新执行的 not_started。

5.3 reader-first 在一个候选内完成，不要求两次发布

同一候选必须同时包含 AS2、Host、Web、SOL／shadow 读取与修复路径的 v2 支持。启动时先完成版本和能力检查，再允许该角色第一次 v2 写入；这是逻辑顺序，不是另开一次部署。

迁移前保留可恢复的旧存档副本；但必须准确区分：

**第一次 v2 写入前：**可以回退旧程序及未迁移存档。

**v2 写入后：**安全回退是关闭新生产入口、保留 v2 读取／恢复／取出能力，进行前向修复。

**禁止：**裸换旧程序继续保存，或恢复迁移前备份后宣称没有丢失迁移后的收益。

**降级转换：**仅在能证明所有物资、完整装备和恢复状态均可无损表示时允许。超过旧条目容量或含旧格式无法表达的数据时必须拒绝。

只有发现无法随同更新、仍可自动写入该角色存档的旧实例／外部读写路径，才构成必须调整上线方式的具体理由。首先处理其停写和准入，不能用泛化的“reader-first 更稳妥”强行拆两列车。

七、验证边界、性能门槛与防丢防重证明
7.1 用完整存档前后像证明，不以 UI 或同进程 reset 代替

本轮需要证明三条不变量：

**来源入账：**重启读到旧完整镜像时，来源仍有合法执行资格且目的增量不存在；读到新完整镜像时，目的增量、来源已完成状态和去重结果同时存在。

**内部转移：**暂存减少与目标增加处于同一镜像。数值物品按同一语义键总量守恒；装备按完整实例多重集守恒，而不是只比较名称或格数。

**请求重放：**同一请求重放原结果或明确过期；不得再次执行。不一致参数使用同一操作 ID 必须拒绝。回包丢失、关闭页面、换槽和客户端重启都不能改变这一点。

7.2 保存次数是结构门，耗时门从目标机实测得出

无故障成功路径采用以下结构断言：

操作	保存预算
角标、分页、排序、关闭纯视图、结果重放	0
新任务交付／新来源入账／单开／一次 openMany	1 次可靠完整提交；不能再由 PAT 或后置通知重复强存盘
新 v2 暂存取出一个有界批次	1 次可靠完整提交
新关卡保管	与既有返回保存门合并；报告打开／关闭不再另存一次
旧 v1 root 恢复	保持 N+1，首次 terminal ACK 再加 1
首次迁移	单独计数，按实际原子迁移块计算；不能混入日常操作预算掩盖重复保存

同时统计领域调用数与实际 packGameState、flushSO、JSON、shadow 发送次数，不能靠 wrapper 计数假通过。

规模测试使用空库存、64、256、1024、4096 条当前记录，包含大量完整装备、少量超大数值堆叠和混合物品。这些是测试点，不是对外承诺容量。

分别记录：存档字节数、组包／克隆／序列化耗时、最长连续主线程停顿、P95／P99、物理保存次数、Host 消息体、Web 排序和图标开销。相同机器、相同存档主体和相同动作，比较旧基线与候选。

实现上的最低要求：

加载时建立一次条目及合并索引；正常查询不反复全库物化 BaseItem。

分页只传当前页及必要摘要，不把完整库存作为每次响应附件。

不在每处理一个条目时深拷贝整个库存、重扫全部剩余条目。

接受每次完整保存仍有 O(总存档体积) 成本；分页无法消除这一项。

正式字节预算与允许停顿，应根据最低支持机器、现有超时／暂停边界和上述数据确定；本包没有实际新库存样本，不能凭空给出跨机器毫秒门。

超过已测安全预算时，允许的退化是：拒绝新的增量写入并保留来源、缩小可拆分命令、继续允许减少库存的取出。不得删除旧库存、自动销毁装备、静默截断，也不得先宣称保管成功再等以后保存。 物资保管可以没有时间期限，但不能承诺无限条目或存储失败时无条件接收。

如果目标积压规模在这些狭窄优化后，单次全量保存仍超过实际可接受边界，则 B 的现有全量保存前提不成立；届时以测量结果重审持久化子问题，不悄悄降低可靠性，也不通过拆出角标发布掩盖它。
