## 2. S4 的实际缺口

探针的上下文资格条件：前台窗口属于本进程；OpenInputDesktop 取得请求权限；活动与线程 desktop 名称一致；非交换鼠标配置；Raw Input 注册仍指向该观察窗口；双快照及观察前缀一致、相关输入队列没有待处理消息。这是实验中的采样前提，**不是完整连续性或重新准入证书**，尤其不能由此认证已安装 hook 此刻仍接收所有事件。

| 对照 | 本机观察 |
|---|---|
| CUA 鼠标点击 | LL mouse 2 个边沿、injected=true，Raw mouse 也有 2 个记录；Raw Input 的出现不能单独证明硬件输入 |
| CUA Ctrl / Shift | Raw 修饰键 4 个记录；LL 键盘回调未出现。早期过滤器不采 generic VK，补采并加入所有键盘回调的无内容计数后仍为 0 |
| 明确 Win32 SendInput 虚拟键 | 调用报告 sent=2，Raw Ctrl Down/Up，键盘回调 0 |
| 明确 Win32 SendInput 扫描码 | 再次 sent=2，Raw 中 scan=29 的 Ctrl Down/Up，键盘回调仍 0 |
| 固定 passive 入口 | 本轮实际启动并正常停止，identity 为 injectedControl=false，冷启动出现一致快照，不发出业务 grant |

直接 Win32 的有效对照在 `tmp/r9-input-observer-scan/evidence`；CUA 对照及调试过程分别保留于 `tmp/r9-physical-probe/automated`、`tmp/r9-physical-probe-human/automatic-control`、`tmp/r9-input-observer-candidate/automatic`。曾有 debug 窗口遇到 computer-use 的 no-monitor 设置错误；仅核对 PID/path 后停止本轮 exact probe，保留不完整记录，不将其算有效输入对照。后续已固定可见启动位置，并在没有其他窗口测试并行时重跑。

**原因未确定。** 不能据此说键盘钩子失效就是旧玩家焦点问题的根因，也不能靠“安装返回非零＋快照全松开”忽略缺口。底层返回、Raw、LL、具体业务输入仍是不同证据。下一步需明确的人操作样本来区分注入路径差异和真实操作时的观测行为；是否改用其他来源、怎样恢复连续性，随后依据数据实施。

平台条件依据：[GetAsyncKeyState](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getasynckeystate)、[Raw Input overview](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-raw-input)、[OpenInputDesktop](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-openinputdesktop)。这些文档没有替本机异常归因。

## 3. 本次人工只做来源采样

固定入口：仓库 `tmp/r9-physical-input-candidate-20260923-v2/开始输入采样.cmd`。入口校验四份候选产物及 runner 哈希，不重编、不启动游戏；每轮 evidence 目录独立。具体二进制/编译源码身份在该目录 `candidate.json`，本轮运行身份在各 evidence 的 `identity.json`。

1. 启动前放开按键；打开后等约 2 秒，不需要按遍五个鼠标键。
2. 在观察窗口内按住鼠标左键，Alt-Tab 切到其他窗口，在外面释放左键，再切回。
3. 普通点击左右键，各短按一次 Ctrl、Shift、Alt。
4. 用窗口关闭按钮结束，回报“采样完成”；无需截图、抄计数或解释日志。

只保存鼠标按钮/修饰键的状态、来源及时间等诊断；普通键和文字不留内容。人工入口不带 `--injected-control`。记录自动落在候选的 `evidence/时间戳/`；机器负责复数、来源比对与判定。**这轮不是 C1 人验，不要求重测 R6/R7，也不能用“看起来正常”放行 C1。**
