## 一、外部建议与实际采纳范围

GPT-6 Pro 的原建议是「B′ 优先、A′ 条件性试行、C 顺带、D 仅限时暂缓」。本地核验接受其**统计纠错和保留安全链**的主轴；维护者没有把四项建议直接转成施工与运营规则。

| 外部选项 | 本次决定 | 理由与边界 |
|---|---|---|
| B′ 发布入口前置检查 | **条件性候选，暂不立实施卡** | 先核实现役 prepare、policy 与云 dispatch 的真实先后、漏检点和新增检查成本；不做全提交 hook、第二套清单或重复完整审计。 |
| A′ 攒批 | **只顺势合车** | 多项工作已 ready、兼容且回退边界可解释时共用一趟；不采用每日两窗口、24 小时等待规则或固定钟点。 |
| C 提交瘦身 | **不单独立项** | 提交条数不是人时、云成本或可删除步骤数；随实际相关施工减少无谓重复即可。 |
| D 限时暂缓 | **不设自动复审日或新台账** | 当前不投入新工程；只有后续事件显示同类缺口或可合并的分开发车时，才用既有记录重新判断。 |

不可动边界：双 signer / 双 faultDomain、immutable tag + ruleset、strict v2 receipt、唯一 promotion writer、CI 事后 Audit、禁止 v2→v1 降级。前置检查即使通过也不代替最终生产证明。

## 四、维护者决定与后续触发条件

1. **先核实 B′ 的增量**：只在下一趟已另获正式发布授权的列车中，复用现有 request、policy、云 run 与 promotion 记录，核对派生检查与 dispatch 的实际先后、是否还有同类缺口，并测量少数现有定点检查耗时；这是顺带取证，不增加发车门、人工回执或强制等待。`prepare-launcher-release-assets.ps1` 的 16 项输出不含这三次历史问题所涉的材料/商店头像；production policy 已有相关检查，云端 helper 也已在 dispatch 前核对 source commit 与受保护 tag。须先分清未运行、运行太晚与确实缺检，不为本次审查另发列车。
2. **发现可复现的净节省后才立窄卡**：若同类失配仍越过现役准备步骤，且复用既有检查能低成本提前拦截，再按主交付物选择 Epic #26（清除经常性返工）或 #28（通用可靠性）立一次范围明确的施工卡。拒绝全提交 hook、第二套依赖清单、重复跑完整 policy、绕过最终 receipt；无缺口或收益不明则不立卡。
3. **发布节奏只顺势合并**：两个及以上已 ready 的独立变更在回退、测试与授权边界兼容时，可共用一次发布；不能因等批次拖住已 ready 的工作。没有启用每日两窗口或 24 小时制度，紧急发布仍走原协议与既有授权。
4. **不设置强制复审日**：外部建议的 2026-10-06 与四条阈值属于 D 方案的管理参数，本次没有采纳为日常计时或新台账。未来出现已确认的同类晚发现、实际可合并却分开发车等事件，再依据既有记录复审。

本卡完成的是**纠正错误成本口径并排除无依据的新增流程**；尚未拆除任何已存在的发布步骤，也无证据表明云构建、人时或正式发布次数已经下降。若未来确有具体施工卡，Epic #26 要求的经常性成本收益应由那张卡另行验证。
