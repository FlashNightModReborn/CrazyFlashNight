### 两特效的关键设计决策（踩过坑，勿回退）

1. **眼睛画月牙不画圆点**：参考图是水平纺锤白光斑；圆点在 1x 下变"两个白圆"，不像漫画眼白发光
2. **流光的起点必须在月牙轮廓之外**（≥ 轮廓 1.04 倍）。早版让光丝穿过主体 → 整体糊成"刮痕"，已废
3. **太极图用「整圆打底 + 一条 S 形鱼覆盖」**，不是画两条鱼轮廓。
   两条鱼的边界在多边形表示里必然留缝或被奇偶填充漏出背景三角，试了两版都失败。
   标准构造：`大圆左半 + 下小圆左半 + 上小圆左半`（小圆 r=R/2，圆心 (0,∓R/2)）
4. **圆环一律用扇形段拼**（`_ring_segments`），不能用"外圈正走+内圈倒走"——
   Flash 与 Pillow 都用奇偶填充，那样会被填实
5. **不要用弧带做光晕**（1x 下露齿轮缝）。改用**整圆叠层**，由外到内变亮
6. **帧 2→3 尺寸要衔接**：帧2 太极+光晕外径 ≈ 帧3 余环外径，否则"啪"地缩一下

## 天启大封印 · bug 1/2 修复（元件不播放 / 位置没锁在法阵）

用户反馈两条：①元件卡住不播放；②位置没像法阵一样严格锁定，无敌人时落在玩家脚底。
关键前提（用户澄清）：**光柱美术直接画在 `天启大封印` 元件里，不嵌套**；元件只有一句帧脚本
「第 30 帧 `gotoAndPlay(16);`」；元件是整条时间轴（爆发 1~15 一次性 → 16~30 循环）。

### bug 1 根因：`封印()` 里的 `宿主.stop()`

`attachMovie` 后立刻 `stop()` → 停在第 1 帧 → 爆发段不播、永远进不了 `gotoAndPlay(16)` 的循环。
**已删除该 stop()**，改为让元件自由播放（SealDomain 只读宿主坐标、挂 onUnload，与播放头无关）。

### bug 1 二次保险：`SealDomain.确保播放(宿主)`

删除 `stop()` 只解决了「代码主动停」这一路。若**元件自身帧脚本里循环 stop()**，
同样的卡死会复现。新增 `确保播放()`：给宿主挂一个**空的 `onEnterFrame`** ——
AVM1 里空 onEnterFrame 就等于「每帧被访问一次」，足以打破 stop 冻结。

- 只在 `宿主.onEnterFrame == undefined` 时挂 → 不与元件自身处理器冲突
- 由帧任务包装函数 `帧任务本体` 每帧调用（在 `每帧(状态)` 之后）
- 只挂空实现，不写业务逻辑

### bug 2 根因：落点算错（三处不一致）

①`落成子弹` 用 `自机._x/_y`（施术者脚下）；②`每帧` 只在 `目标名` 查到活敌时才吸附；
③`落成` 先 `撤法阵` 再建宿主，事后读不到法阵坐标。

**修复**：新增 `取落成位置(自机)`（与 `建上下文` 的兜底公式逐字一致：
`施术者._x + 法阵兜底距离 × 朝向, 施术者._y`）；`落成()` 在**撤法阵之前**把
`上下文.法阵._x/_y` 存进 `落点`，再传给 `_落成核心(容器, 落点)` / `落成子弹(容器, 落点)`。

**`SealDomain.每帧` 的吸附逻辑（279-285 行）确认正确、不需改**：有敌人吸附到敌人
（与法阵重合），没敌人停在落点（= 法阵兜底位），两种情况都对。

## 天启大封印 · 定位语义变更（宿主不再吸附 + 逐单位独立计时）

用户需求：释放后宿主不再吸附敌人（吸附是法阵的活），法阵最终位置 = 封印释放位置；
释放时封印一次范围内的敌人；宿主随后静止。可选：每秒判定一次，把后续进入法阵的
敌人也封印，但**强度从各敌人被封印那一刻起各自累计**，而非从技能开始统一累计。

用户明确回答：`天启大封印` 元件里**没有 onEnterFrame**，只有素材 + 第 30 帧一句
`gotoAndPlay(16)`。

### SealDomain.as（568 行）改动

1. **删掉 `每帧` 里的宿主吸附整段**（原 306-313 行）→ 宿主落成后静止。
   中心 = `封()` 当帧的 `宿主._x/_y`，之后不变（`封()` 的 JSDoc 已写明调用方
   必须保证宿主已落在法阵消失前的坐标上）
2. **强度累加/额度判定下移到 `记录` 级**：`记录` 新增 `强度: 0` / `已存续帧: 0`；
   `每帧` 里对每条记录 `记录.强度 += 每秒强度 / 率`，判定改 `记录.强度 >= 记录.额度`

6. **新增 `挂卸载回调(目标, 回调)`**：`封()` 里原本裸写 `宿主.onUnload = …`。

### 关键认知（跨会话有效）

- **`记录` 才是强度的正确粒度**。`状态.强度` 是全局单一累加器，晚进来的敌人会
  "白嫖"前面攒的进度，与「从被封印开始累计」的需求直接冲突
- **`_挂宿主收尾` 覆盖 `确保播放` 无害**：自毁 handler 本身确保每帧被访问，
  播放头照常推进。两处都写 `onEnterFrame` 但顺序上后者胜出，功能等价

**② 调度器修复方案推倒重做 —— 第一版有真 bug**

⚠ **第一版用「节点反向持有 Task 引用」做归属校验是错的**：
`SingleLevelTimeWheel` 的 `delayTimerByNode`(378) / `rescheduleTimerByNode`(411) 会在
**节点仍然存活**时调用 `node.reset(node.taskID)`（原地换槽位复用），
`reset()` 一旦清掉那个引用，**正在跑的合法任务就会被误判成残留而跳过执行 → 任务停摆**。
即修 bug 引入了更严重的 bug。**教训：`reset(非 null)` 是「原地复用」语义，不能清附加状态。**

**② 改用「占用代次 epoch」方案（最终版）**

| 文件 | 改动 |
|---|---|
| `naki/DataStructures/TaskIDNode.as` | 新增 `public var epoch:Number = 0`；`reset()` 里**仅当 newTaskID == null 时**清零（池回收才作废，原地换槽位保留） |
| `neur/TimeWheel/SingleLevelTimeWheel.as` | 新增 `_epochCounter`；`acquireNode` 末尾 `node.epoch = ++_epochCounter` |
| `naki/DataStructures/FrameTaskMinHeap.as` | 新增 `_epochCounter` + 私有 `acquireNode(taskID)` 统一取用入口；3 处取用点全部改走它 |
