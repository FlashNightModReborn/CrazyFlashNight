## S1 时序与性能裁决

选择 `coarse-deadline-v1`：短期精确，秒/分钟向上量化，溢出精确；同帧依次为
single、heap、second、third，每个 lane 保持注册顺序。例如 phase 0 的 1830 帧仍在 3600 帧执行。
本次没有切换到 exact-deadline-v2。ID 为不透明字符串，陈旧 label 创建新 ID；scope 与参数数组仍持有
原引用，addSingleTask 非正间隔仍同步，其他零任务使用入表顺序与阶段入口快照。
负 label 间隔统一到零阶段，与 addTask/addLoopTask 的既有规则一致。

每次真实调用消耗一次有限 repeatCount，包括 self-delay/self-upsert。delayTask 继续累加保存的
pendingFrames，不改为剩余墙钟；100ms/300ms 等毫秒用 Math.ceil 换帧，不再用 int32 截断。
暂停项只留权威表，不占 heap。取消、跨任务改期、当前任务 override 使用稳定 Task，没有可复用节点别名。
真实旧实现的 cancel/delay 反例保留；新实现两者的 D 均只在 frame 31 执行，自延迟 A 继续执行。

Server 心跳传递 frame token，TaskManager 拒绝重复/递归推进。clear/destroy 更新 generation，
旧分发栈停止，旧 unload 捕获普通 label 字典和 generation，不能重新解析并误取消新 MovieClip owner。
回调异常仍向外传播，只恢复未调用的快照项和自身所有权；不代签外层 EventBus 后续业务已执行。
watchdog 使用 TaskManager 的标量诊断，不假冒旧时间轮内部结构。全局任务不因一般场景切换自动清空。

纯直接堆首次 FP20 负载达到旧内核 2～3 倍耗时，优化后仍显著较慢，因此未接受。
最终使用短期直接 Task 槽链、长期索引堆，长期密集到期可复用数组/native sortOn/一次堆修复。
没有节点池、第二/三级轮对象、TaskIDNode/List、deadline bucket map 或每回调 try/catch。
