## 1. 完整目标

为主角建立可持续存在、可替换姿态的持枪表现结构：站立与移动共用持枪容器，射击、换弹和举枪/放枪在容器内部协调；新姿态按注册入口接入，减少对主角大时间轴的重复编辑。

终态应同时满足以下要求：

1. **状态与表现解耦**：保留外部业务需要的攻击模式和逻辑状态；在显示侧收拢持枪帧。站立、移动、射击、换弹不因显示帧组织方式而无谓重建整个持枪身体。
2. **三组部件组织**：按原讨论的「头＋主手及武器」「副手及其武器」「剩余身体（含下身）」组织视觉。三组在同一持枪表现空间内协调，支持瞄准到放下的遮挡变化，以及主副手分别对应现有射击/换弹流程的视觉姿势。
3. **统一下身与武器位置**：共用默认站立/行走动作；手持、腿侧挂枪、副手刀和刀鞘按各自角色决定显示与装扮加载，不因“装备存在”就在错误位置显示。
4. **纸娃娃提供共同能力**：装扮系统能够识别部件拥有者与武器显示角色，处理加载、关闭、重新开启、换装和引用失效；减少明确不需要显示的武器 attach 尝试。
5. **扩展与兼容可证明**：新姿态可接入；现有射击、换弹、枪口、装备特效与共享消费者保持预期行为。源码重组、性能改善和真人观感分别验证。

三组部件是本次要验证的结构目标；能否用恰好三个视觉元件覆盖所有目标动作，需由样板证明。若特定动作要求额外内部遮挡层，应指出具体动作与原因，不能预先宣称三件结构已覆盖一切。

## 3. 原会话中需要修正或收窄的判断

### 3.1 原三期计划已经被后续讨论改写

早期建议是「复制四套上身容器，保留腿和状态帧；以后再统一下身」。后续用户提出三部件、放枪遮挡、全局纸娃娃门控后，目标已成为持枪身体的组合结构。应先在一套样板上验证最终结构，再推广四种枪态，避免先复制四套上身、随后全部拆件返工。

原会话中的方案建议仍是设计候选；用户提出评估问题、Kimi 回答“成立”，不等于完成了运行验证或批准全部施工细节。

### 3.2 共用纸娃娃存在多处层级假设

[手枪素材](../flashswf/arts/things0/LIBRARY/主角肢体素材/手枪.xml) 的 load 脚本先用 `_parent._parent._parent` 读取装扮，再调用配置接口。
[DressupReferenceManager](../scripts/类定义/org/flashNight/arki/unit/UnitComponent/Dressup/DressupReferenceManager.as) 的 `attach` 同样按固定深度找 unit；`pruneInactiveManBranchEntries` 还按 `movieClip._parent._parent === unit.man` 判定当前视觉分支。

因此，增加部件层之后至少需要核对三件事：装扮读取属于谁、注册到谁、谁是当前活动 man 分支。仅将 `attach` 改成向上寻找 unit，不能完成适配。显式传入拥有者、在新部件中传播拥有者、受约束的祖先解析，均可比选；不预先采用“遇到兵种/攻击模式字段就认作 unit”的猜测规则。

### 3.3 枪口路径配置是共享的

[ShootCore](../scripts/类定义/org/flashNight/arki/unit/Action/Shoot/ShootCore.as) 的 `primaryParams`、`secondaryParams`、`subweaponParams` 是静态共享对象；
[ShootInitCore](../scripts/类定义/org/flashNight/arki/unit/Action/Shoot/ShootInitCore.as) 使用它们绑定行为。

不能为了新容器嵌套层级直接全局改写 `gunPath`，同时声称旧模板不受影响。样板阶段应选定实例适配或稳定接口方案，并验证缓存与卸载后的引用失效；“射击核心零改动”不设为先验承诺。

直接路径也在适配范围内：[LongGunSubWeaponCore](../scripts/类定义/org/flashNight/arki/unit/Action/Shoot/LongGunSubWeaponCore.as) 的 `getMuzzlePosition` 和 [铁枪](../scripts/逻辑/装备函数/铁枪.as) 的射击事件处理均读取 `man.枪.枪.装扮`。只调整配置字符串会漏掉副武器就绪判断与铁枪枪口切换，须在 P2 长枪推广时一并验证。

### 3.4 gate 必须支持持久 holder 的完整开关

原建议“关闭时不注册，等跳帧重建再加载”，依赖 holder 被重建；终态恰好希望减少重建，两者存在冲突。

共同门控至少应说明：

- 关闭已有显示时，怎样处理旧皮肤、规范引用及消费者的失效通知；仅提前 `return null` 不能保证旧皮肤消失。
- 关闭后再次开启时，怎样重新找到仍存活的 holder；不能依赖它必然存在于当前只记录已 attach 对象的注册表。
- 换装时角色仍关闭，保持关闭；恢复时使用最新装扮。
- 同一武器的手持与挂载位置使用明确的显示角色，不能共用同一个引用名后只做布尔反相。
- `#N` 并存引用与 alias 仍要匹配基础角色，不因溢出命名绕过门控。
- 未接入新显示策略的旧单位保留既有行为；共享能力新增不自动改变所有旧素材的显示规则。

P0 的最小接口表需列出「角色 → holder → 装扮字段 skinKey → 对外规范引用写者 → 发布/关闭语义」。仅给腿侧挂枪改一个引用名，会使 `skinKeyOverrides` 之外的名字落入字段名推导；也可能令原来订阅 `手枪_引用/长枪_引用` 的装备生命周期失去当前可见武器。角色名与对外规范引用不能混为一项。

门控状态必须在 holder 更换后仍可恢复，但不预定只能存进 unit 的某张新表；可采用拥有者状态或已有权威的派生策略。开关判断应覆盖首次 attach、已有显示关闭、`refreshAll`、holder 重建后的重新接入。稳定 holder 可由容器直接持有引用，跨帧重建的 holder 则需重新接入；恢复入口按实际存活范围选择，不预定新建全局索引。

主动关闭与短暂 detached 也应区分：[DressupSubscriber](../scripts/类定义/org/flashNight/arki/unit/UnitComponent/Dressup/DressupSubscriber.as) 记载的消费者可能把旧坐标作为短暂失效时的回退。应对实际采用门控的消费者验证关闭信号与缓存，不直接把它套成“皮肤仍活着但 `_visible=false`”，也不直接全局清空所有旧引用。刀类消费者在 P3 随对应角色接入验证。

副手“没有武器”也不意味着整个副手肢体应隐藏；手臂、手与武器的显隐须分别保持正确。

### 3.5 真实装备皮肤与刀的语义需要保留

现有挂枪使用的手枪素材，其 load 已读取 unit 的 `手枪_装扮`。因此不能把“挂枪显示真实装备皮肤”一律排到以后当新功能；迁移应先保持现有装扮读取与显示能力。

[DressupInitializer](../scripts/类定义/org/flashNight/arki/unit/UnitComponent/Initializer/DressupInitializer.as) 中，`刀2_装扮` 和 `刀3_装扮` 来自同一刀装备的 `dressup2/dressup3`。它们不能直接理解为两件独立库存武器。副手刀、空鞘、带刀鞘等角色应按实际素材和动作定义，不预先用“刀3＝主刀掏出状态反相”概括所有装备。

### 3.6 非人形外观不代表未接入装扮系统

[二足型机器人](../flashswf/arts/new/原体融合生物/LIBRARY/敌人-二足型机器人.xml) 明确设置 `hasDressup = true`、`enableShoot = true`，并采用长枪攻击模式；其攻击动作复用主角长枪素材。原会话末轮“没有人形装扮字段，所以仍静默跳过”的推断不能作为兼容依据。

本轮对 XFL 的直接 `libraryItemName="主角肢体素材/…"` 扫描命中 things0、体育老师、原体融合生物。这个集合只描述直接素材引用，不是全部 API 消费者。[T800 记录](终结者T800-托管长枪与射击核心-施工-2026-08-22.md) 与当前 things1 `Symbol 248` 仍须按共用装扮/射击链审查。

### 3.7 性能与时序结论保持证据边界

XML 中的关键帧数量、同名素材实例数量，不能直接换算为运行时 load 或 attach 次数。`DressupReferenceManager` 注释中的 0.5–2 ms 是经验值，其记录的 benchmark 使用 mock attachMovie；它们不是本方案或目标机器的实测收益。

已有 [load 时序契约](../agentsDoc/as2-load-timing.md) 区分 placement 就绪与 load 写入字段就绪。新容器必须验证自己的函数绑定、皮肤、枪口和双枪部件就绪顺序；不以“函数存在”独自判定可射击，也不默认取消既有重试或冷却保护。

### 3.8 输入控制与换弹控制仍有时间轴合同

[主角行走状态机](../scripts/逻辑/单位函数/单位函数_lsy_主角行走状态机.as) 的持枪与双枪入口不同，当前由 [主角-男](../flashswf/arts/things0/LIBRARY/主角-男.xml) 的控制块按帧区间绑定。收拢显示帧时需同步确定模式切换后的输入入口；容器正确显示，不代表 R/F、副武器和双手输入已绑定正确。持枪入口有就绪检查与意图重试，双枪入口存在直接调用，不能假定它们有同等保护，也不能据静态代码认定今天必然丢输入。

[双枪上身](../flashswf/arts/things0/LIBRARY/移动射击动画层/双枪上身.xml) 与 [ReloadManager](../scripts/类定义/org/flashNight/arki/unit/Action/Shoot/ReloadManager.as) 通过数值帧、顺播换手、`_currentframe/nextFrame`、帧上标签及 `_root.主角函数.双枪*` 胶水共同驱动换弹。P1 优先验证保留根 man 控制时间轴、只重组视觉部件的方案；拆件不自动要求改局部帧号或重写换手 API。若必须改动控制时间轴，再明确手位、帧号、提交点和门禁的等价映射。

本次视觉独立继续保留现役换弹期间的双手射击封锁、主副手续换与库存提交语义；并行换弹或一手换弹另一手射击属于另一个产品行为变更。P1 应覆盖两手续换、单手结束、缺弹匣失败及打断，不只检查动画能播放。

初始化还要覆盖模式提交顺序：现役双枪帧先记住初始化函数，再调用会因攻击模式不匹配而早退的初始化入口。新容器须保证模式先就绪，或提供明确的重新初始化入口；不能让未完成初始化的实例被当作长期可复用对象。

## 4. 建议分期

以下是计划分期与技术出口，不新增逐阶段的形式审批。当前仅完成范围整理，所有实现及运行出口均未完成。

| 阶段 | 交付内容 | 阶段出口 |
|---|---|---|
| P0 最小接口与基线方法 | 列出逻辑状态/显示帧、输入绑定、部件/武器角色、拥有者、枪口、装卸、ready 与换弹控制合同；确定共享消费者和重建/attach 计数方法 | 足以驱动 P1 的保留/替换、恢复和旧接口选择；不以全量性能盘点或全部消费者实机验收阻塞最早样板 |
| P1 一套双枪样板 | 在同一套素材上先验证保留原控制时间轴的持久容器，再验证三部件、统一下身、双手/腿侧角色与接口适配；对外保留单一 `unit.man` | 同状态重复请求、站走、射击、两手续换/单手结束、放枪遮挡、显示重开、换装、旧动作退出/返回均有对应证据；首发枪口与输入正确，无重复提交、残留任务或引用接管错误 |
| P2 覆盖四种持枪模式 | 推广至手枪、手枪2、长枪、双枪；收拢主角持枪显示帧，保留外部业务所需逻辑状态；打通旧全身动作进入/退出 | 四种模式与原行为对照成立；站走切换按保留策略运行；换枪、跑跳、受击、倒地、死亡、近战/技能切换后能正确清理和恢复 |
| P3 补齐纸娃娃武器角色 | 在 P1 已验证的共同能力上，补齐刀、副手刀、刀鞘等实际规则；核对基础引用、并存引用与换装生命周期 | 本次定义的武器位规则均可测试；无武器、已有武器但不显示、重新显示、换装、旧单位未启用策略等情况行为明确且通过验证 |
| P4 多姿态接入与整体收口 | 接入一个额外姿态，证明选择/注册入口成立；完成受影响消费者回归与新旧性能对比；沉淀新增姿态的资产接口 | 增加姿态无需重铺主角状态帧；默认动作、遮挡与装备外观获得真人确认；性能结论只覆盖已测场景，并列出尚未生产的新美术 |

P1 保留双枪作为完整样板，因为它覆盖主副手、换弹协调与挂枪角色；其内部按两步执行：

1. 复用现有上身控制时间轴，在最小候选中验证持枪族内部保留、离开后清理、返回后重建与 ready 顺序。现役上身没有直接导出的 linkage，候选仍需必要的资产包装/导出和真实 CS6 验证，不能称作零资产成本。
2. 在同一套素材上拆分三组视觉件，加入统一下身、角色开关与遮挡。优先保持原控制时间轴语义，让失败能归因到新增的视觉/装扮适配。

这两步是内部实验顺序，不增加新的正式阶段或两套生产资产。仅在具体证据表明双枪样例不能隔离某个机制时，才补更小的临时夹具；不预先要求再制作一套手枪拆件样板。实际 attach/重建基线随第一步收集，而非另起一个前置性能工程。

P3 的“补齐”只扩大接入的武器角色；共同 gate 的关闭、恢复与换装能力必须在 P1 成立，不能拖到 P3 才补。每次修改共享 API 后立即运行对应消费者回归，不能把兼容风险全部留到 P4。

P0–P2 持续比较 attach 与重建行为；若数据表明仍有实质热点，再单独选择去重或结构优化。没有证明收益的优化不阻塞功能收口，也不宣称已经带来提速。

## 5. 建议保留的设计边界

### 对外单一 man，内部独立职责

目前 [状态切换计划](../scripts/类定义/org/flashNight/arki/unit/UnitComponent/Routing/StateTransitionPlan.as)、
[容器挂载](../scripts/类定义/org/flashNight/arki/unit/UnitComponent/Routing/ContainerAttachAction.as) 和射击/换弹消费者都围绕单一 `unit.man` 工作。
建议继续将它作为兼容入口；主副手部件在内部表达不同状态。暂不引入与 man 平级的 man2，也不把“不增加 man2”解释成主副手必须永远播放同一个帧号。

统一协调者决定射击、换弹与下身步态的映射；主手动作不能无意重置副手换弹，下身行走也不能推动上身射击时间轴。具体使用标签映射、动作轨道还是其他轻量实现，由 P1 验证，不能先假定所有部件逐帧锁死即可兼容双枪。

“持久”默认限定在可兼容的持枪族状态内部。技能、近战、受击等需要接管同一 man 槽位时，射击容器可以退出，返回时重新创建；本方案不要求跨所有动作永驻，也不默认引入多个缓存 man 槽位。P1 需验证退出后的任务清理、旧回调失效及返回后的重新就绪。

退出时区分射击任务、姿态表现与单位字段的清理责任；对实际经过的旧动作检查 `倒地/无敌` 等字段恢复，不能把技能专用的 `skillEnd` 广播等退出副作用直接套到射击容器。枪口与部件引用默认从当前活动分支重新取得；引入缓存时须验证拥有者/代次与关闭语义，单凭旧 MovieClip 引用相等或仍有 `_parent` 不足以证明它仍属于当前姿态。

### 逻辑状态与显示帧分别处理

[StateTransitionCore](../scripts/类定义/org/flashNight/arki/unit/UnitComponent/Routing/StateTransitionCore.as) 已有逻辑状态与显示帧解析入口，但当前状态改变仍可能触发动态 man 移除。
收拢显示帧不要求同步删掉全部旧逻辑状态名；需要新增的是持久容器的保留/更新/替换策略，并覆盖相同显示帧下的逻辑变化。

现行 `StateTransition.apply` 在判断 `plan.transition` 前已执行动态 man 移除，因此“重复请求同一逻辑状态”也须单列验证。装卸入口还应覆盖路由结束、换枪及现役直接跳帧；[刷新人物装扮](../scripts/逻辑/单位函数/单位函数_fs_aka_玩家模板迁移.as) 当前直接跳回 `safeFrame` 后执行 `refreshAll`，已经避开旧 XFL 的“刷新装扮”帧。须沿这个实际入口检查重初始化与角色恢复，不凭旧帧脚本认定现役换装必然失败。

### 共享改造保持明确的采用边界

兼容目标包括体育老师/大学相关模板、二足型机器人、T800、瓦巴杰克 dominator，以及实际复用主角模板或相同 API 的佣兵/战宠。最终清单按引用与加载链收敛，不能仅按外形或是否命中共享库文件名决定。

若新解析方式使旧单位原先未显示的素材开始显示，这属于行为变化，应明确判断是否纳入修复；不能自动将其称作“修好了”而跳过兼容决策。

### 人体姿态与武器机械动画分别维护

[枪械射击动画](../scripts/逻辑/装备函数/枪械射击动画.as) 当前按成功 `processShot` 推进武器内部运动，并通过 placement 同步视觉。
姿态容器应保持这些事件和引用合同。注册一个人体姿态不意味着重写 QJZ171、M134、激光等已有装备动画/特效；有实际兼容缺口时才在相应层修复。

## 6. 验证与完成判据

| 证据层 | 需要证明的内容 |
|---|---|
| 静态与资产审计 | linkage/Include/依赖闭合；共享层级与枪口路径均有明确消费者；AS2/BOM 与生成输入符合既有规范 |
| focused 行为回归 | 同状态幂等、容器保留/替换、输入换绑、门控开关/恢复、角色与规范引用映射、双枪换弹提交/门禁、换装与退出清理 |
| 真实 CS6/Flash 执行 | 新容器与 holder 的 load/ready 时序、首发枪口、真实时间轴切换与卸载；mock 不替代这些行为 |
| 角色与装备兼容 | 主角四枪态，以及实际受影响的共享模板；非人形外观也按 API 能力验证 |
| 人工观感 | 站走连续性、举枪/放枪遮挡、双手换弹、挂枪与刀鞘外观；不以静态截图或编译成功代签 |
| 性能 | 在记录环境与场景下比较重建、attach、时间开销；结构减少与净性能收益分别报告 |

完成本方案意味着核心范围、扩展样例与对应证据闭合；仅复制四个容器、仅通过编译，或仅完成一套样板，均不能表述为整项迁移完成。跑跳等保留旧全身表现的范围、新姿态美术生产和未覆盖单位需明确列出。

验证工具与发布目标沿用 [AS2 验证](../agentsDoc/testing-guide.md#as2)、[美术装配](../agentsDoc/art-asset-assembly.md) 及 [XFL 工具](../scripts/tools/xfl/README.md)。新增独立库才按其源链接入；不把“新增元件”自动等同于“必须新建独立库”。正式 runtime 发布仍是独立授权路径。

## 7. 下一步的具体切口

本草案建议用 P0 的小接口表驱动 P1 两步实验，再推广四种枪态。首批必须交代保留/替换与实际跳帧入口、输入绑定和 ready、换弹控制时间轴、部件拥有者与武器角色、枪口及规范引用兼容。P0 只定足以开始样板的选择与验证方法，不追求先完成所有实现设计。

默认先以现有素材证明结构和行为，再安排新姿态美术；纸娃娃共同能力保留为完整目标。大规模性能优化按实际测量另定，不挤进一期承诺。
