# 军阀战术演习 3D 沙盘 UI ADR（2026-08-24）

状态：`PHASE_B_2_UI_HUMAN_ACCEPTED / PHASE_C_SOURCE_FLASH_PUBLISH_AND_LAUNCHER_XUNIT_PASSED / PET_IDENTITY_AND_ECONOMY_OBSERVATION_CONNECTED / PHYSICAL_E2E_REOPENED_AFTER_HOST_RESUME_ROUTE_FAILURE / RESUME_FIX_SOURCE_VERIFIED / HUMAN_RETEST_PENDING / NOT_DEPLOYED / UNCOMMITTED_FOR_MERGE_COMPETITION`

## 背景

原 Web Demo 已证明九节点军阀战棋玩法成立，但其 SVG 地图、三栏数据墙和全量重绘 UI 只服务规则验收。当前目标是在不改变确定性规则核心的前提下，改造成以沙漠军阀基地为背景的 3D 指挥沙盘，并复用已经完成人类验收的八张单位头像。

Phase A 在隔离 worktree 完成并取得维护者对视觉方向和逐轮交互改进的确认。Phase B.1 已同步最新 `main`，串行接入 Launcher registry、Host 生命周期、测试菜单和共享验证入口；Phase B.2 根据首次真实 WebView2 人类验收修复全屏内缩、相机/规划遮挡和高节点数行动栏可达性，并已获维护者明确验收。Phase C 已完成 AS2 战斗权威的源码接线候选，由 Flash CS6 fresh publish 生成配套 `asLoader.swf`，在仓库精确 .NET SDK 下通过 Release 源码编译与 Launcher xUnit。首次真实候选旅程已进入并完成 AS2 战斗，但 Host 没有重新打开战旗页面；该失败已作为 E2E 重开证据，修复源码门通过，替代候选人类复验、连续第二场、最终回基地、正式存档经济与部署仍保持独立门。

## 决策

### 1. 单文档 classic facade + ESM runtime

采用 classic `warlord-panel.js` 同步 `Panels.register`，在 `onOpen` 动态导入版本化 ESM entry。ESM 直接挂载现有 panel DOM，CSS 全部以 `.warlord-*` 命名空间隔离。

不采用同源 iframe：它会引入第二套 DOM、焦点、缩放、消息桥、截图和销毁生命周期，且 portrait resolver、PanelScale、Host 精确关闭都需要额外桥接。

不采用手写 UMD/多脚本 Three 全局链：它增加加载顺序、全局污染和生成闭包成本。若真实 WebView2 证明动态 ESM 不可用，再把同一 ESM runtime 生成单 IIFE 作为回退，而不是维护第二套业务实现。

### 2. 3D 只承担呈现

Three.js 使用低角度正交相机，绘制程序化地表、十二条路线、九个六角节点、语义地标与一体化战术徽章。节点拾取只回传 `NodeId`，棋子拾取只回传 `pieceId`，Shift 框选只回传同一节点的有序 `pieceId[]`；移动动画只从旧/新 `PieceState.nodeId` 插值。

所有战略命令仍先由 `validateCommand` 裁决；非战斗命令继续进入 `applyCommand`。产品态交战命令改由会话冻结后交给 Host/AS2，只有验收通过的 receipt 才单次写回战略态，绝不先运行 JS resolver。Three 场景没有 AP、容量、战斗、占领、生产或 AI 公式。HUD 使用 DOM，以保证 1024×576 字体清晰、键盘可达和 WebGL 失败时仍能完成对局。

### 3. 头像 identity-first

八张卡本身就是 `data/merc/pets.xml` 中 id `12/13/14/15/82/83/84/85` 的战宠，`cardId` 即 `petId`；产品战斗身份以 `petId + Identifier` 为联合权威，旧 `unitTypeId` 仅保留 Demo 审计，不能参与 AS2 生成。DOM 使用 `EnemyPortraits.mount()`；Three 先 `loadManifest()`，再 `resolve({portraitRef: identifier})`，纹理优先采用 manifest PNG，失败依次回退 SVG/legacy/识别牌。红蓝差异只画在棋子底座与边框，不染色头像。

Phase A.7 不再把透明全身头像直接插在圆柱上，而是用运行时 CanvasTexture 生成阵营徽章背板和裁切遮罩，再与短连接座、八边形低底盘、阴影和选择环组合。头像仍使用同一 texture identity，点击仍命中同一 `pieceId`；新增程序化几何与遮罩不进入 `GameState`，也没有复制正式头像资产。

### 4. 固定逻辑画布与生命周期

沿用项目 1024×576 逻辑画布和 `PanelScale`。全屏在这里严格表示 Host 全 anchor 与 Web `#panel-content { inset:0 }`，再由逻辑画布等比铺满；不得继承通用 `4% 6%` 卡片内缩，也不改成按物理像素重排业务组件。Three renderer 的 DPR 上限为 1.5；空闲时不持续刷新，只在 resize、状态变化、纹理到达或棋子过渡期间请求 rAF。

关闭必须使 generation 失效，并释放 facade/session/scene 所有资源。强制 WebGL 失败路径提供九节点 DOM 操作面，不创建第二套规则核心。

### 5. 相机是独立战术指挥能力

沙盘相机不再绑定九节点首屏构图。它拥有独立的 authored-bounds fit、光标锚定缩放、拖拽平移、键盘/按钮等价入口、当前据点定位与边界钳制；节点点击延后到 pointer-up，只有未越过拖拽阈值才提交选择，避免大地图浏览时误下命令。

相机 DOM 控件采用渐进披露：空闲态只保留 `全图 / 定位`，占用约 108×30px；悬停、控件聚焦或沙盘刚发生指针、滚轮、快捷键与按钮操作时，短暂展开缩放百分比、中心坐标、LOD 与 `− / +`。四个按钮始终存在于 DOM，键盘聚焦可展开完整操作面；披露只改变 presentation，不进入相机状态或规则状态。Phase B.2 将该控件固定在沙盘右上保留槽，规划条只占其左侧明确边界；两者在空闲和展开态都不允许重叠。

地图投影保持固定世界单位密度，仅把原点改为 authored node bounds 中心。这样当前九节点世界坐标逐值不变，而未来更大的坐标场会自然形成更大的 Three 世界，再由相机 fit/zoom/pan 浏览，不会压缩成同一张小沙盘。相机输出 `overview / operational / tactical` detail tier，作为后续节点标签、棋子聚合和路线批处理的 LOD 契约。

边界据点允许在战术缩放时居中聚焦。节点和棋子采用独立缩放级别补偿。Phase A.8 根据人类验收反馈把棋子由近似恒定屏幕尺寸改为 `sqrt(cameraZoom)` 渐进增长：220% 时约为 1.483 倍，极端近距封顶 1.8 倍。由此放大确实展示头像、包边和底盘细节，而编队间距仍按完整相机倍率扩张，避免重新压成头像墙。重复棋子底盘、连接座、阴影与选中环共享 geometry；这些准备不替代百节点下必须实施的 instancing、route batching 与性能预算。

100 节点合成测试只验 presentation camera math。当前规则的 `NodeId` 联合、地图拓扑、生产锚点和战斗编制没有擅自泛化；营/连级产品地图仍须另立规格，冻结通用 identity/schema、图加载版本、空间索引、虚拟导航、instancing/route batching、聚合符号和性能预算。

### 6. 节点导航是有限上下文，不是全图按钮墙

底部导航默认从当前节点按拓扑广度展开，最多投影 6 个局部节点；维护者可切换到每页 6 个节点的全域索引。页面只创建当前窗口的按钮，选中节点可映射回其所在页。导航总高固定 48px，节点名与兵力/归属合并为两层排版，同时保留至少 40px 的按钮命中高度以及完整辅助文本。100 节点合成契约验证窗口上限、页数和末页边界，不再让卡片宽度或 DOM 数量随地图节点线性膨胀。

这只是当前层级的键盘/精确选择补面。百节点情报系统仍需要小地图、名称/类型检索、编制树、告警与虚拟化，不把 17 页线性翻页当成最终 UX。

### 7. 节点地标与地图主题均为呈现策略

`NodeKind` 分别映射指挥掩体、补给箱、双储罐、关门、雷达和军需帐篷六类低多边形地标；地标只共享节点所有权材质和活动信标，不创建新规则状态。`MapTheme` 统一提供地表、纹理、雾、背景、光源、网格、等高线、路线和中立节点色。

默认 `desert` 保持军阀沙漠基地的成本优势；`tundra` 仅作为同拓扑的迁移预览，证明呈现层可以更换地域视觉而不复制规则核心。主题参数不进入 `GameState`、录像或模拟摘要；未来正式主题包仍需独立资产预算、来源和性能验收。

### 8. 生产采用默认自动调度、可退回精确槽位

原生产槽是 FIFO：只有队首推进，`waiting_deployment` 会因据点驻军容量或实际人口上限不足而堵塞后续订单。旧 UI 把整条队列压成一行 radio 文本，玩家必须先选择生产据点、再选择槽位、最后点击兵种，既隐藏堵塞原因，也把常用操作拆成三步。

新 UI 以右侧生产台直接投影队首头像、进度、后续订单链和阻断原因。默认 `AUTO` 在所有稳定、激活的己方生产据点中选择合法槽位：未受阻优先，其次比较剩余工期、队列长度、部署余量，最后用 node/slot identity 保持确定性。玩家从任何地图节点点击兵种即可完成选址和入队，回执明确报告真实 node/slot。

Phase A.7 增加独立于“当前检查据点”的全网订单头像带。每个可见单元包含 portrait identity、node/slot、queuePosition、进度与撤销/阻断状态；点击单元只把生产检查面定位到其真实槽位，不改变 `AUTO/EXACT`，也不提交命令。队尾订单同样显示头像。头像带最多创建 6 个单元；超过上限时保留 5 个确定性订单与一个 `+N` 聚合，不让 DOM 高度或宽度随总订单线性增长。该聚合不是百级生产网络的搜索/告警/虚拟化替代品。

`EXACT` 模式保留生产据点下拉选择和逐槽锁定，任何槽位点击都会显式切入精确控制。两种模式组合 `ENQUEUE_PRODUCTION`；合法性仍逐次来自 `validateCommand()`，写入仍只经 `applyCommand()`。仅选择槽位不会下单。

Phase A.6 增加受限 `CANCEL_PRODUCTION`：只能在该阵营尚未提交的结算规划中撤销从未获得生产进度的订单，判据为 `status=building` 且 `remainingRounds` 仍等于卡牌完整工期。合法撤销按 exact node/slot/order identity 移除订单，全额返还冻结金币并释放预留人口；可以精确撤销队尾而不影响队首。任何已推进或等待部署订单均锁定。节点失稳的系统取消继续沿用原语义：金币不退、只释放人口。UI 同时投影上一单快捷撤销与订单内按钮，但不直接改金币、人口或队列。

该扩展把规则身份提升为 `wargame-demo-v0.1.1`，并显式记录 `baseRulesVersion=wargame-demo-v0.1` 与 `rulesExtensionVersion=phase-a-production-cancel-v1`，避免含取消命令的录像被旧引擎误认兼容。战斗、AI、经济、生产推进和部署公式未改；仍不提供拖拽重排、跨槽迁移、已开工取消或自动部署。

为后续大地图避免第二个节点卡片墙，生产据点只在下拉框中列出，页面仅展开当前检查据点的槽位。百级生产节点若真实出现，仍需另行评估搜索、告警和虚拟化，而不是把当前下拉框冒称最终生产网络界面。

### 9. 选择建立命令意图，节点点击直接执行

无棋子选择时，节点点击仍是只读检查；存在同节点红方编组时，节点点击改解释为命令意图。Three 节点、底部上下文节点卡和右侧路线按钮共同调用同一会话入口，再由 `buildActionPreviews -> validateCommand -> applyCommand` 完成邻接、AP、进攻宽度、失败重入锁和友方容量裁剪。非法或非相邻目标不得清空编组，必须保留选择并显示 canonical 原因。

点击己方棋子单选，修饰键点击只在同一节点内增减；双击己方棋子选中本节点全组。Shift 左键拖拽与普通平移手势分离，框选策略只接受红方棋子并只选择一个 origin：若既有 origin 命中则优先保持，否则以命中数量降序、node identity 升序确定。由此不会创造规则核心不存在的跨节点平面编组。容量裁剪必须在节点卡、路线预览和执行回执中显示实际生效 `X/Y`。

命令写回后，会话只继续选择 validator 决定的 `actualPieceIds` 中仍存活的棋子，并跟随它们的实际节点；未进入容量的棋子、阵亡棋子和未收到命令的原选择不混入后续链式指挥。该跟随只是 presentation selection，不进入录像或 `GameState`。营/连级扩展仍需编制树、命令层级和聚合符号，不能把同源框选扩张成直接操纵数百枚 raw piece。

### 10. 高节点数行动栏使用滚动正文与固定终止动作

右侧行动栏的标题和“结束红方行动”属于阶段控制，不随可选节点数量滚动。合法/非法节点按钮、紧凑生产监控和战况流共同进入可聚焦的原生纵向滚动正文，使用浏览器滚轮、触控板与键盘滚动；栏底终止动作始终留在可见命中区。禁止通过隐藏后续节点、缩小按钮或让整个面板滚动来规避高度压力。浏览器门会注入 14 个额外压力节点，要求正文产生真实 `scrollTop`，同时终止按钮的屏幕位置保持不变。

### 11. 卡牌按战宠身份投影，经济只做双刻度观测

Phase C 不把卡牌临时映射成 `units.json` 的 `兵种N`。Host 从冻结战略态读取棋子的 `cardId`，再以 `PetCatalogLoader` 复验 `pets.xml` 的 `petId + Identifier + RosterType`；AS2 也用 `_root.宠物库` 再次核对联合身份，并直接用该 `Identifier` 创建真实 MovieClip。`units.json` 中可能重复的 `spritename` 和旧 `unitTypeId` 均不得取得产品生成权。

战旗卡牌等级直接投影为隔离战宠等级。已购升阶必须是该战宠 `Promotion` 中三段体质链的合法前缀：普通兵为“基础训练→强化药剂→超级血清”，精锐可从 `pets.xml` 指定的更高档起步。AS2 只构造新的 `宠物属性` 副本并重放真实进阶钩子，不读取 `_root.宠物信息`、玩家战宠属性、托管装备或存档引用；`常驻淬毒` 等含货币副作用的方案禁止进入演习投影。战斗生成继续关闭掉落与经验写入。

每个 accepted receipt 附带 `warlord.pet-economy-observation.v1`，同时记录两套不可混用的刻度：棋子冻结的 `piece.productionGoldValue` 是战旗经济，`pets.xml Price/KPrice/IncreasePrice` 是玩家战宠目录的基础定价。观测明确声明 `mode=observe_only / settlementPolicy=none / writesPlayerState=false / currentAs2SessionPriceSampled=false`，并分别汇总双方暴露与损失价值。它用于后续胜率、存活率、战场贡献和造价比调参，不扣玩家金币/K 点、不改变领养价、不结算战宠损失，也不把 XML 基础价冒充 AS2 会话内涨价后的当前价。若未来要形成真实经济结算，必须另立有版本的权威价格采样、写入、存档与对账协议，不能复用本观测回执暗中加写。

## Phase C 真实 AS2 战斗权威

### 结论

已按异步 handoff 实现源码候选，而不是把 Web resolver 替换成同步调用。`WarlordBattleTask` 冻结并复验 exact 战略请求，扩展后的 `ArenaCalibrationService` 在专用 Flash 场景创建真实战宠 MovieClip、运行 AI、子弹、伤害和帧循环，再返回逐单位 receipt。产品态不再调用 JS resolver；JS 战斗只由显式 `battleAuthority=fixture` 的开发 harness 和规则测试使用。首次真实候选已证明 AS2 场景生成、战斗和逐单位 receipt 成立，但恢复阶段因误用不支持 Warlord 的通用路由而失败，故不能称完整 AS2 战斗旅程已验收。恢复现改为内部专用能力并通过源码回归，仍需替代候选人类复验。

### 已确认约束

- 所有正式 `OpenPanel` 都会取得 `_webPanelPauseLease`；竞技场 runner 则依赖 `onEnterFrame`。沙盘保持可见时，当前 Flash 战斗不会正常推进。
- runner 是场景全局单实例，默认以真实墙钟帧推进并可能到 5400 帧 timeout；一回合多个节点同时交战时，必须先串行排队并给玩家明确过场，不能假设百节点地图可瞬时并发求解。
