## 总裁决

**R6 悬停窄修补可以独立进入受限人验；当前“持键切出后取消并重新准入”的实现不通过。C1 的非交互合成准备可以继续，但涉及旧 Flash 域与其他端点的真实输入交接，不能以 native cancel ACK 作为放行条件。**

同时，**现有反例没有证明“保留当前 Flash 宿主就不可能安全取消”**。我建议先验证一个有源码依据、尚未被当前实验覆盖的最小 native 假设：**虚拟 capture 的撤销是否缺失了对应的失捕获通知**。若这条路径失败，再转入一个完整交互域的 AS2 显式取消与手势分发，而不是继续堆叠 Windows 消息或立即迁移全部 UI。

已重算输入包清单中的 **33 个文件，全部匹配**。以下结论来自源码审阅和原始日志静态复核，没有在本环境重跑 Windows／Flash，也没有修改生产代码。

## 一、反例成立，但应把结论限定在“取消与重新准入合同失败”

### 1. 这不是“Up 没送到”的问题

最终记录可以串成一条完整链：

| 边界                        | 原始记录                                                |
| ------------------------- | --------------------------------------------------- |
| 旧 Down 进入 Flash 原 WndProc | `seq=199, epoch=24`，有 enter／return                  |
| AVM1 响应旧按下                | AS2 `seq=602, frame=1523`，`press A`                 |
| Host 发起撤销                 | `owner_deactivate`，epoch 提到 25                      |
| 失焦与取消处理                   | `WM_KILLFOCUS` 将 localFloor 提到 26；随后有原取消返回的 stage 7 |
| 取消数据包与旧 Up                | 两者均因 stale 被拒绝                                      |
| 返回后的新 Down／Up             | `seq=204/205, epoch=26`，都进入并返回原 WndProc             |
| AS2 实际结果                  | `seq=629, frame=1600`，只有 `release A`，没有新 `press`    |

依据：`evidence/final/host.log:L441–L470`、`evidence/final/as2.jsonl:L602–L629`。

旧 press 和后面的 release 之间仍有递增帧号的 sample；已附 AS2 序列没有中间缺号。因此，“整个 VM 停住了”或“恰好中间丢了一条回执”不是当前最有支持的解释。同进程那轮也保留了相同形态的失败。

**可以高置信度拒收当前取消路径；但还不能声称已经直接确认 Flash 某个私有 pressedTarget 没清，也不能据此排除按键查询、虚拟捕获、消息顺序和重入等机制。**

### 2. 当前 ACK 确实只到原生调用层

`CancelEndpoint()` 的流程是：

> 清本桥的 enabled／buttons／captured／activeGesture → 调原 `WM_CANCELMODE` → 按需释放真实 capture → 写 `cancelledTicket`。

没有 AS2 取消请求或业务回执参与。`completedSeq`、`heldButtons`、`quiescedTicket` 也都是传输、窗口调用或桥接本地状态，不是 AVM1 按钮或业务任务的证明。

依据：`src/InputBridge.cpp:L153–L165`、`src/InputBridge.h:L47–L62`。

因此必须分开三个命题：

**旧包不能再进入 ≠ AVM1 旧手势已复位 ≠ 旧业务动作已失去提交资格。**

Windows 文档对 `WM_CANCELMODE` 的默认处理只承诺标准滚动条、菜单及鼠标捕获等处理，并没有承诺第三方 AVM1 按钮状态复位。([Microsoft Learn][1])

### 3. 有几处证据口径需要收窄

**`focus_loss_no_button_commit` 名称过强。** 夹具只检查没有 `release`，没有检查 `releaseOutside` 或真实业务提交。最终原始切出记录里确实也没有看到 `releaseOutside`，但断言本身不能证明任意业务无副作用。两个按钮的处理器只是 emit；拖出测试还明确产生了 `releaseOutside`。依据：`src/HoverHost.cs:L193–L203`、`src/HoverProbe.as:L22–L28`。

**“无后台夺回前台”目前是两个时点的检查。** 不能排除瞬时抢焦或误消费外部输入。返回步骤由 `Activate(); FocusFlash()` 完成，因此是“真实 Flash 上的模拟刺激”，不是人工返回验收。依据：`src/HoverHost.cs:L196–L210`。

**测试总量不能代签。** 包内原生日志可核到 27 PASS，G1 可核到 55 PASS；Host 的 5714 pass／4 skip 没有附完整日志。未采纳的 pre-down 实验也只有摘要，不能据此充分排除某种按键查询或事件顺序假设。

下一轮最少补四类观测：capture 家族调用前后值；贯穿 Host/native/AS2 的刺激与手势身份；按 callback 与模拟业务提交分别计数的“有副作用计数器”按钮；同版本、同 SWF 的直接原生宿主对照。

## 二、保留当前宿主的安全取消：有可验证路线，但当前没有已证可用实现

### 1. 先做虚拟 capture 的最小判定，不预先认定它就是根因

源码中，映射生效时的 `SetCapture` 可以只把本地 `captured` 设为 true，并不调用真实 Windows `SetCapture`。取消时却先把它清掉，随后只有 `realGetCapture()==target` 才执行真实释放。

依据：`src/InputBridge.cpp:L89–L105,L153–L165`。

这产生一个值得验证的缺口：

> **如果 Flash 实际取得的是虚拟 capture，清一个布尔值并不自动产生与真实 capture 丢失对应的通知。**

四组已附 trace 都没有记录 `WM_CAPTURECHANGED`，而源码确有该消息的观测分支。不过，当前缺少 capture 调用级日志，所以还不知道这次失败手势是否真的请求过虚拟 capture。

微软说明，窗口失去真实 capture 时会收到 `WM_CAPTURECHANGED`，包括自己调用 `ReleaseCapture` 的情况；这个约定不会自动适用于桥接层自行维护的 bool。([Microsoft Learn][2])

我建议的实验严格限定为：

先记录直接原生 Flash 的 capture 获取／撤销顺序，并保留当前失败版本作对照。**只有确认该手势确实持有虚拟 capture，才测试一次与该所有权对应的、目标 UI 线程上的 capture-lost 撤销路径。** 与 `WM_CANCELMODE` 的顺序、重入、重复通知必须固定并记录。

取消期间还要明确 Flash 读到的按键与 capture 视图。现在先设 `enabled=false` 会回落到真实查询，不能把本桥 `buttons=0` 当成 Flash 必然读到“未按下”。

这一实验不得实际夺取外部应用 capture，不得补 Up，不得调用按钮 release，不得抢焦。**没有捕获事实、没有改善、产生副作用或只对特定目标有效，就停止这个候选；不是继续扫一串消息直到按钮看起来正常。**

即使成功，也只能授予已验证 projector／bridge／控件类型的兼容能力，不能直接升级成“任意旧 SWF 都能透明取消”。

### 2. 另有一个独立缺口：普通取消把物理持键账本清空了

`CancelPointer()` 提升 floor 后，会把 `_physicalButtons`、`_postedButtons`、`_openGesture` 清零，**却没有像 `Rebind()` 那样进入 `_awaitRelease/_awaitFreshDown`**。

依据：`src/WorldCompositionSurface.cs:L95–L141,L264–L284`。

因此存在以下**源码可达风险，尚未宣称实测出业务后果**：

> 旧 Down 已到 Flash → 持键时发生几何变化／显式取消 → Host 升 epoch 并清账 → 没有发生 `WM_KILLFOCUS` → 玩家松开 → 旧物理 Up 被贴上当前 epoch → native 把它记为 unowned release，但继续转交原 WndProc。

最后一步来自 `src/InputBridge.cpp:L264–L289`：unowned release 是**计数后继续转交**，不是拒绝。

最终切出用例中的旧 Up 被挡住，是因为 localFloor 恰好比 Host epoch 多升了一档。**不能拿这一特定失焦顺序证明所有取消原因都安全。**

必须把“物理按钮还按着”和“逻辑手势已撤销”分开维护。业务撤销不能伪造物理已抬起；普通取消也需要重新准入门禁，而不是只有 session 续代才有。

### 3. 最小状态机

```text
READY_FOR_FRESH_DOWN
    └─ 新真实 Down → HELD(g)

HELD(g) / UNKNOWN_DIRTY
    └─ 取消 → REVOKING
               关闭准入、提升 floor、不可逆撤销 g
               ├─ 证明不足／超时 → BLOCKED
               └─ 原生退场 + 本域取消证明 → WAIT_NEUTRAL

WAIT_NEUTRAL
    ├─ 仍持键／物理状态未知 → 保持关闭
    └─ 确认相关物理按钮全部抬起 → READY_FOR_FRESH_DOWN
```

开放必须同时满足：

**原生退场成立 + 当前交互域的取消能力成立 + 物理基线合格 + owner／source／实例身份未变 + 下一次 Begin 来自新的真实 Down。**

这里的“取消能力”有两种，不能混用：

* 对未迁移的原生回调域，需要证明 VM 手势确实复位。
* 对完整迁移的 AS2 协议域，可以证明旧 VM 回调已经无法触及业务；不必伪称 VM 私有状态清零。

仅拒绝旧 release、却吞掉首击，是活性失败；恢复首击、却补出具有业务作用的 releaseOutside，是安全失败。**两者都不能通过。**

物理基线也不能仅凭一次 `GetAsyncKeyState()==0`：该 API 在非活动桌面或访问受限等情况下可能返回失败零值。无法确认时保持关闭，而不是等待固定时间后默认已松开。([Microsoft Learn][3])

### 4. 必须保留的反例矩阵

| 组别      | 必测条件                                                  |
| ------- | ----------------------------------------------------- |
| 已有行为    | 保留最终 34 项；补逐次目标、事件顺序、额外 outside、左上角控件                 |
| 持键切出／返回 | 同进程、独立进程；外部松开后返回、仍持键返回；返回 A、B、空白；快速往返                 |
| 无失焦取消   | 持键时 geometry／resize／DPI／隐藏／显式撤销／队列溢出／发包失败             |
| 生命周期交错  | 重复取消、嵌套回调、迟到 ACK／Up、session 更新、端点或 SWF 重建             |
| 业务入口    | press、release、releaseOutside、拖动、键盘替代激活、延后提交分别设置可观察计数器 |
| 跨域覆盖    | 主／子 SWF、动态加载、卸载重载、同名实例、未知端点、双向交接                      |
| 外部所有权   | 外部窗口保持打开；记录前台与 capture 变化，以及 LL 是否误消费外部输入             |

当前失败版本必须继续让 oracle 判败；故意绕过业务门禁，也必须使对应的模拟提交计数判败。

透明 native 路线必须修复原来的 raw fresh-press 断言。AS2 完整迁移路线则应保留该原生断言的实际结果，另证新的逻辑 Begin／End 与提交语义，**不能把旧失败断言改名变绿**。

## 三、需要 AS2 协作时，最小单位不是全局 Mouse listener，而是完整交互域

### 1. 最小协议应表达“谁的哪一个手势，被撤销到哪里”

建议身份至少包含：

```text
session + scopeIncarnation + ownerEpoch
+ gestureId + button + beginSeq + targetIncarnation
```

可以复用现有身份字段，不要求为本次裁决扩位；但不能用同名 MovieClip、路径或 HWND 代替实例身份。

协议至少包含：

**REGISTER**：声明实际覆盖的交互根、内容版本、实例代次、覆盖版本和能力。
**CANCEL**：携带精确 ticket／身份／撤销边界，关闭本域准入，清理临时拖动、预览、预留，并使旧延后任务不可再提交。
**CANCELLED**：只确认这次 ticket 和覆盖版本中，已无可提交的旧手势义务。它不是“AVM1 内部一定清零”的声明。
**READY**：覆盖稳定、物理基线合格后，允许下一次新真实手势。
**BEGIN／UPDATE／END**：携带明确的手势和目标身份，每个 Begin 最多一次合法终结。

包内 XMLSocket 只证明 AS2→Host 回传，没有给出生产命令入站和取消屏障实现。施工前必须证明双向通道与排序，不能假设现成存在一个可任意同步调用 AS2 的接口。

### 2. 只加 canceled 标记，不能修复当前首击反例

若仍靠原生 `onPress` 建立手势，再让 `onRelease` 检查 canceled：

> 旧 release 可能被挡住，但返回后的新 press 仍然没有发生。

所以它最多是安全子集修补，不是恢复完成。

完整迁移模式中，业务 Begin／End 应由**带身份的新真实输入边缘协议**驱动，业务函数从原 handler 中抽出。旧 `onPress/onRelease/onReleaseOutside` 不能继续独立写业务，也不能和新 dispatcher 双重提交。

不能临时把“当前 epoch”放进全局变量，就把随后到来的旧 AVM1 release 解释成新手势；也不应通过手工调用 `.onPress()`／`.onRelease()` 补齐。命中、遮挡、坐标、拖动和实例有效性仍须由 AS2 适配器验证。

如果关键视觉或拖动仍依赖那个未复位的原生按下状态，也必须迁移相应状态，不能只保证提交正确却让控件继续卡住。

### 3. 迁移状态必须明确分级

**完整迁移域：** 所有相关回调、按下行为、键盘替代入口、定时／帧延后任务和最终副作用函数均受同一资格约束。可以出本域 `CANCELLED`。

**仅加保护域：** 拦了部分 release，但仍依赖原生 press。只能声明实际覆盖到的安全改进，不能声明首击恢复。

**未迁移／未知域：** 不能出 AS2 语义取消 ACK。只能使用已证适配该类型的 native 取消能力，否则需要取消或重入时保持关闭。

全局 Mouse listener、遮罩、遍历当前实例替换方法，都不是覆盖所有旧按钮的证明。必须清点动态 handler、元件时间轴动作、工厂／原型、运行时重新赋值、全局监听，以及真正的业务提交函数。

### 4. 跨 SWF 必须有注册与覆盖版本

以实际加载实例注册，不假定所有 SWF 的 `_root`／`_global` 自动共享同一个取消权威。注册必须早于交互启用。

取消时冻结覆盖版本；父域只有在该版本内所有参与端点都撤销完成或确认退出后，才能聚合 ACK。取消期间新加载内容默认关闭；卸载重载必须换实例代次，旧 ACK 和闭包不能转移到新实例。

**这不要求先迁完整个游戏，但要求所选交互岛确实隔离。** 若未知旧按钮还能收到会触发业务的原生事件，或从其他入口绕过资格检查，就不能只迁两个新按钮便宣布整个 Flash 域安全。

还有一条提交边界必须写清：取消不能撤回已经执行的 onPress 扣款、发物品或存盘。异步 Cancel 也不能抢占任意正在执行的 AS2 handler。若合同要求“Host 撤销时刻之后绝不提交”，最终副作用入口必须与 Host 撤销共享可验证的资格／顺序；仅通知 AS2 不足以保证这一点。

## 四、R6 可以受限人验，但 C1 要分开“画面准备”和“输入交接”

### R6：准许窄修补独立观察，不准许据此发布

隔离映射期间源 F 的 `WM_MOUSELEAVE`，以及保留 P 离开的负坐标哨兵，有独立证据，没必要因取消失败而全部推翻。

但人验仅限**已核对没有持久化副作用的悬停、普通完整单击、纯 UI 操作**，或者使用隔离测试档／禁用写盘环境。不能因操作名称叫“NPC 取消”就默认不会保存剧情或状态。主游戏相关源码不在包内，此处不能代签。

候选应保持 exact 配对，不能混入未采纳的 pre-down 实验；最终状态仍是 **33/34，humanAcceptance=PENDING**。一旦出现持键失焦、孤立 release、首击丢失或额外副作用，应停止该交互路径并留证，而不是重复点到恢复。

### C1/B：新增的是取消依赖，不是重开整体架构

| 工作                       | 裁决                                     |
| ------------------------ | -------------------------------------- |
| C1 非交互捕获／合成、只读面板准备       | 本反例不否定这些工作，可在原授权范围内继续                  |
| C1 涉及 Flash 与宿主面板的真实输入交接 | 必须先证明旧域安全失去业务资格，再允许新域接收独立手势            |
| 面板关闭、返回 Flash            | 同样执行交接合同，不能只测去程                        |
| B 扩大统一输入／接管范围            | 纳入范围的端点和双向边界都要有取消能力、失败关闭与人验；鼠标小样不能代签键盘 |
| 正式发布                     | 仍需构建闭包、阶段验收、性能收口和明确授权                  |

**新面板可以先画出来，但不应在旧域仍可能执行业务时先吃输入。**

同进程的 Flash↔Web／Native 切换可能不经过本案相同的 `WM_KILLFOCUS` 链，因此尤其不能依赖 localFloor 恰好多升一档。交接原因本身就应主动进入取消状态机。

正式分阶段计划只有引用、没有随包提供，所以这里不重新裁定历史授权或阶段通过状态。B0-05 的旧性能缺口也没有在本轮被重测；R6 不替它签字。

## 五、推荐的最小路线与硬停止条件

推荐路线为：

**冻结失败与加强 oracle → 补普通取消的准入关闭 → 做虚拟 capture 的单机制对照 → native 成功则限定兼容域；失败则迁一个完整 AS2 交互域 → 做 C1 双向输入纵切 → 再讨论 B 扩围。**

首先不动主游戏，在独立 fixture 中补 capture 调用轨迹、真实输入身份及业务计数器，加入“持键、无失焦、取消后旧 Up”的反例。当前 fresh-click 失败必须保持可重现。

随后只验证有依据的 native 生命周期候选。通过不仅意味着首击恢复，还意味着没有取消期业务、没有 outside 副作用、没有抢焦，并且返回其他目标、仍持键返回、无失焦撤销都成立。

该候选失败，就转主／子 SWF 的完整协作小样，再选择一个非持久业务交互域落地。不要用仅加 guard 的结果冒充完整迁移，也不要把成功域的 ACK 借给未知旧按钮。

以下任一情况都是硬停止条件：

* **取消产生未授权业务，或安全了但第一新手势仍不能独立完成。**
* **没有有效新 Begin，却出现 End／commit；旧回调或旧 ACK 被新 epoch／同名实例重新合法化。**
* **物理仍持键、状态未知、取消确认缺失或覆盖变化，却重新开放输入。**
* **恢复依赖补 Up、重放、固定延时、反复抢焦、夺取真实 capture、重载游戏或修改真实存档。**
* **以减少断言、缩回悬停小样、增加无关测试总量或“维护者看起来正常”替代失败证据。**

停止的含义是保持该输入域关闭、保留仍可显示的画面与诊断；不是擅自重启后把问题记作恢复。

---

**最终落点：保留 R6 悬停窄修补，拒收当前取消与重新准入。先证明旧端点已经不能再提交旧手势业务，再让 C1 接走输入。**

本轮未核验 Windows／Flash 实际重跑、主游戏旧按钮及跨 SWF 全量覆盖、未附二进制与构建闭包、Host 全量日志或正式人验。源码成立、native 返回、桥接 session 更新以及画面继续出帧，都不能替代上述取消证明。
