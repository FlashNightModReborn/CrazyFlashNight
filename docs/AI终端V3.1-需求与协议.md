## 1. 目标与不做事项

本版让 NPC 在终端与游戏插话中获得一致的查询、任务状态与记忆能力，尤其不能把日常插话作为缩水入口。

必须覆盖：终端无草案／有草案、日常插话无草案／有草案／索取待处理、任务前／任务后插话；各入口保留原有发布、委派、交易权限边界，只读能力不借此扩大写权限。总 Agent 开关仍按各入口原合同生效。

本版不做：历史会话迁移或来源回填、新向量库、聊天记录向量化、地图重新建模、玩家操作中打开选关截图、移除游戏真实接取守卫、为了暂不可接而新增生成后拒绝、未经授权的正式 runtime 发布。

`V3.1` 是开发范围标识。本轮文档和第 4 项修复不自动修改运行时版本号、exe 文件名、Release/tag 或发布资产。

## 2. 一个查询入口

扩展 BACK 现有 `route_search`，不要为每种查询各注册一个聊天工具。模型一次调用可以提交若干独立查询项，程序按类型执行，统一返回资料与出处。

### 2.1 参数形状

目标参数为 `requests`、`deep_search`、`query`、`ui_hint`：

| 字段 | 类型与约束 | 含义 |
|---|---|---|
| `requests` | 非空数组，工程初值最多 8 项 | 本次查询项；同类项目共享该类的结果预算 |
| `requests[].kind` | 下表枚举 | 查询类型 |
| `requests[].keywords` | 字符串数组，工程初值最多 6 个非空关键词 | 多关键词模糊匹配；名称、区域类不强制填写 |
| `requests[].npc_names` | 字符串数组 | 立绘支持多个 NPC，工程初值最多 4 人；NPC 对话资料一次指定 1 人 |
| `requests[].region` | 第 4 节的区域枚举 | 仅地图使用 |
| `requests[].cursor` | 可选不透明字符串 | 仅继续读取已返回 next_cursor 的文本资料页；绑定同槽、同类型、同目标与关键词，不允许自行构造扩大范围 |
| `deep_search` | 布尔，缺省 false | 文本是否交搜索 Agent 进一步核对 |
| `query` | 可选字符串，工程初值最多 160 字 | 深搜的目的与指示；深搜文本项需要，图片项不使用 |
| `ui_hint` | 沿用现有最多 12 字 | NPC 视角的等待提示 |

枚举及字段合法性由应用边界校验。模型不得提供 SQL、任意文件路径、外部图片 URL、存档槽位或当前 NPC 身份来扩大读取范围。槽位和当前 NPC 由当前回合绑定注入；目标 NPC 名只用于立绘和指定 NPC 资料。

| kind | 数据源与返回语义 | 深搜 |
|---|---|---|
| `knowledge` | 现有世界观、剧情、台词、任务对话向量检索 | 可用 |
| `items` | 现有物品结构化查询 | 可用 |
| `stages` | 现有关卡结构化查询 | 可用 |
| `stage_map` | 指定区域的默认视角地图图片 | 忽略 |
| `npc_portraits` | 一个或多个 NPC 的当前游戏立绘 | 忽略 |
| `npc_history` | 当前存档、当前 NPC、其他 session 的交流记录 | 可用 |
| `player_history` | 当前存档、跨 NPC、仅 user 发言 | 可用 |
| `npc_dialogues` | 指定 NPC 全部日常对话＋关键任务对话，可加关键词 | 可用 |

原有向量查询已覆盖的零散台词、任务台词，不再另外增加同义工具。`npc_dialogues` 的用途是按人取得成组资料，不等于再建一个台词搜索器；日常部分按组保留说话人，任务部分按关键词及当前进度相关性选片段，不能把数据顺序的前六行称为关键对话。

### 2.2 历史检索

- `npc_history` 固定当前 NPC，排除当前 session；命中片段可带同会话邻近上下文。
- `player_history` 跨 NPC，但仅返回 user 发言正文及时间、会话和交流对象等出处，不夹带 assistant 回复。
- 绑定时只查当前槽位；未绑定只查独立终端会话范围，不能混入任意游戏存档。
- 多关键词取并集；优先级为命中的不同关键词数、字面／模糊匹配强度、时间。重复一个词不能无限抬高分数。
- 排序后合并重叠片段和重复结果，按类型块预算取优先部分；返回 `total_matches`、`returned_count`、`has_more`，不把未返回部分说成不存在。
- 模糊匹配采用本地文本算法，不为排序额外调用 LLM，也不把历史写入向量库。
- SQL 使用参数绑定，用户关键词中的通配符作为文字处理；检索只读，不触发摘要、任务写入或记忆维护。

### 2.3 other_npc 的角色归属

基线 `services/dialogue_interject/sessions.py:72` 的 `map_played_line` 将其他 NPC 写为 user，正文为 `【名字：台词】`。V3.1 将该分支直接改成 assistant，正文包裹格式不变；它是当前 NPC 叙述中的他人发言，不是玩家发言。

不新增历史来源字段、不迁移或猜测修复旧库，不因少量旧数据引入兼容层。`player` 保持 user，`npc`／`ai` 保持 assistant，`other_npc` 改 assistant；同组转录、finalize 幂等与终端展示测试一起改。由玩家角色承载的现有原作台词仍按 player 归 user，本版不进一步区分键盘输入与剧情玩家台词。

## 3. 普通查询与深度搜索

首次查询永远由程序执行；不能先启动搜索 Agent，再让它重复决定首次查什么。

1. 图片结果直接送主交流 Agent，不受 `deep_search` 影响，不多启动一次搜索模型。
2. 文本且 `deep_search=false`：首查结果直接拼到主交流 Agent 后续回复轮。
3. 文本且 `deep_search=true`：已有资料＋首查结果＋查询关键词和指示送搜索 Agent；它可直接选择原文返回、整理总结返回，或继续查询后返回。
4. 混合查询的图片仍保留并送主交流 Agent，文本单独走深搜；不能因分流而丢附件。
5. 搜索 Agent 的补查复用相同只读执行器与作用域，不递归委派另一个深搜 Agent，不因此取得发布／交易／记忆写工具。
6. `return_mode=raw` 配 `result_ids` 表示原文选择；`return_mode=summary` 配 `text` 表示总结。原文由程序按编号取回，不要求模型抄写。最终结构和可见文案见提示词合同。

### 3.1 字数与完整性

取消现有搜索 Agent 的“必须 400 字结论”和 `_FINDINGS_MAX_CHARS=1000` 截断，不在 findings、汇合层或最终资料拼接层重新设置总字数切片。

预算只在各类来源块内部执行，并在所有同类型查询／补查间共享；增加深搜轮次不能重复叠加无限份同类块。按完整条目／片段填充、明确剩余数量，避免尾部机械切断句子。已有 knowledge 3600、items 1200、stages 1200 的分块预算可保留。

历史类与 NPC 资料块的初值由开发计划列出，是可调工程参数，不是生成后拒绝模型输出的条件。NPC 日常资料遇到块预算时按完整组分页，保留继续读取位置，不静默把部分日常称为全部。搜索 Agent 最终原文选择取去重后的块；总结不额外强制固定字数。

## 4. 地图与立绘图片

图片能力是多模态内容，不是给模型一个本地文件名。统一查询和任务自动附图共用图片装配链。

### 4.1 地图范围与产物

底图规格为 **1280×720（720p）、WebP、游戏默认总览镜头**。同一套真实 Web 渲染器负责构图，随后按存档叠加可见地点标签、锁定状态和任务目标。

AI 地图查询枚举与烘焙白名单完全一致，仅以下八页：

1. 基地门口
2. 基地车库
3. 黑铁会总部
4. 基地房顶
5. 诺亚前线基地深处
6. 雪山
7. 雪山内部
8. 试炼场深处

排除地下2层、诺亚前线基地深处第二层、雪山第二层、雪山内部第二层，以及沙漠虫洞、亡灵沙漠、异界战场、坠毁战舰。排除页不烘焙、不进入 AI 地图查询枚举、任务也不自动附这些页的地图；保留其既有文字资料。此范围不删除玩家真正的选关页，也不凭图片范围否决其他已解锁关卡的有效任务。

- 三维页复用当前模型，其余白名单页复用现有二维背景，无需补建 3D。
- 构建时使用独立空浏览器存储，避开个人取景预设；禁止导入／保存来修改玩家镜头。
- 不能把现有 allUnlocked 测试截图直接当玩家视图；锁定名称沿真实显示规则处理。
- 默认总览下高亮目标，不打开检查器、不移动镜头、不触发进关。
- 生成 manifest 记录资源输入、镜头、分辨率、节点投影、图片哈希；缓存键必须包含相应地图版本与存档状态，防止串档图或旧标记。
- 新资源文件名固定，版本写在 manifest 内容里，不按每次版本号改资源路径。

### 4.2 自动附图

具体关卡已经出现在草案、当前任务上下文或未完成委托资料中时，解析结构化关卡需求自动补地图；不等模型再调一次查询工具。原有关卡名称、简介、需求、难度、怪物信息仍保留。

建立 `stage_name -> [{region, node_id}]` 映射，不能假设一关一个节点；同一区域合并目标、只发一图。图片说明明确每个标记对应哪条任务、哪个关卡。无节点或不在白名单时只保留文字，不伪造地图位置。新增任务或更换目标后使旧标记缓存失效。

### 4.3 多图消息与能力

立绘按现有 manifest 查表；请求多个 NPC 时各图紧邻相应人名说明。图片挂在后续 user 多模态消息的 image_url part，不写进台词正文或 tool JSON 字符串，不把大段 base64 放进日志。

终端与插话两端都检查 `ChatRequest.send_image`、消息组装和最终回复轮。目前插话明确 `send_image=False`，这一点必须接通才能称为图片功能已实现。继续使用当前模型 profile／既有图像不支持处理，不擅自切换视觉模型；只有实际包含图片 part 的请求才称为已送图，纯文本不能让 NPC 声称看过图片。

程序已明确模型无视觉能力时，只给文字查询类型及其说明，不让模型自行判断能否看图；能力未知时沿现有尝试发送和不支持处理。两种情况下均不额外切模型。

## 5. 同档 NPC 委托概览

同一个存档中由该 NPC 发布的未完成委托，无论在哪个 session 发布，都必须在终端和插话中可见。

### 5.1 现状与目标

基线 BACK `services/agent_tools/finished_tasks.py`：

| 基线块 | 当前来源 | 当前内容 | 本版处理 |
|---|---|---|---|
| 已完成委托 | 当前存档完成 ID，非仅本会话 | 名称、简介、报酬、接取对话、达成内容、完成对话 | 保留完成事实，可留接取对话，省略完成对话 |
| 已接未完成 | tasks_active，最多展开三条 | 名称、简介、报酬、达成内容、物品、完成 NPC、关卡怪物；没有任务对话 | 不新增任务对话；改同档全量简要概览 |
| 刚发布 | 当前 session 的短期记录 | 同未完成块，没有任务对话 | 常驻状态不再依赖该会话计数；发布当轮即时回执仍可保留 |
| 插话 | 自己的 context，不复用前三块 | 长期记忆、RAG、本组转录、草案、当前任务上下文 | 接入共享委托概览，覆盖日常与任务插话 |

未完成每条必有：任务 ID／名称、简介、要求。要求必须保留物品名与数量、关卡名与难度、完成／交付 NPC，不可只写“帮忙跑腿”等抽象总结。报酬可紧凑列出；物品详细介绍与怪物长段落按当前相关性展开。

### 5.2 状态与作用域

- 已完成 ID 命中：完成态优先，不再列未完成。
- active ID 命中且未完成：已接未完成；不凭玩家一句“完成了”改变状态。
- 本档发布记录存在、未完成且不在 active：已发布未接取；若是回访后续段，附等待前段的事实，不能冒充立即可接。
- 未发布草案独立展示，不进入已发布集合。
- 同档当前 NPC 以任务 `get_npc` 归属为准；不要按正在对话的发布 session 反推归属，代别人发任务也按实际接取 NPC 呈现。
- 绑定范围只读当前存档 Agent 任务，不让共享独立终端任务或其他槽污染本档概览；未绑定保留现有独立终端语义。
- 所有未完成任务都列出简要信息，不能只给三条加“还有 N 条”来代替其余名称与要求。
- 概览只是只读投影，不复制一份持久任务状态表；同轮去重、稳定排序。

## 6. 长期记忆：程序选择互斥分支

继续沿用一个基础印象＋最多 20 条关键记录，以及 `update_long_term_memory`，不重做数据库。

| 已知状态 | 给模型的能力 | 不能出现的另一分支说明 |
|---|---|---|
| 无基础印象、关键记录未满 | 同时写首次基础印象＋一条有效记录 | 满额后替换规则、让模型判断是否满额 |
| 有基础印象、关键记录未满 | 无关新信息新记；相关信息按编号融合 | 满额后才启用的按重要性淘汰规则 |
| 关键记录已满 | 必填编号，给出完整改写；重要性替换或同类压缩融合 | 追加、新记一条、留空编号等说明 |

未满时记录玩家产生、已有设定／检索资料未提供的有效信息或关系变化，不要求重大；没有新信息的寒暄和重复资料仍不记。无需为了写一条记忆强制额外检索。满额时再按重要性替换较不重要记录，或压缩同类信息后补入更重要内容。

分支由程序的实时记录数决定；不是一篇提示词中同时写“未满时……满时……”。工具 schema、description、system 指南与 user 记忆块保持一致。首次基础印象 100 字、后续基础印象 300 字、关键记录期望 100 字及现有存储上限沿用；基础印象仍由摘要轮维护，不顺带改为每轮重写。

终端记忆工具使用终端的 meta／台词前缀；插话使用 JSONL add／closing 等本入口格式，不能把终端 meta 规则原样塞进插话。重要性属于提示词选择，不新增后端“重要性不足”拒绝。

## 7. 绑定任务候选与前置修复

优先修正常候选供给，不用生成后的资格拦截把有效任务变成生成失败。

### 7.1 必须达到

- 已绑定存档：候选从实际已解锁关卡中取得，不能用七档进度上限替代关卡准入；覆盖普通关卡、掉落关联关卡及副本入口的有效候选路径。
- 继续推导玩家阶段，用于原有势均力敌等判断。阶段早期、本阶段可选关卡不足时允许只把选关匹配阶段退一档；不能因此把未解锁关卡放进池。
- 第一段任务写出的前置 ID 必须来自当前玩家已完成任务。关卡 UnlockCondition 是任务链进度阈值，不是任务 ID，禁止原值转换或截到 77 当作 ID。
- 关卡刚解锁即可正常生成相关委托，不能因为错误要求“完成该关对应主线任务”而接不到。
- 两段式回访的第二段按设计以前一段为前置，属于明确的延迟接取例外，不移除该依赖。
- 未绑定场景没有真实资格事实，继续原有按阶段推荐，不冒称当前存档保证。

### 7.2 不新增的行为

不新增“当前不能接所以拒绝发布”、不新增落盘后撤销、不开额外模型校验轮，不要求为每次生成做一次游戏端远程预检。已有合法结构／名称／数量校验和游戏真正执行接取时的守卫保留。

模型意外选择有效但暂不可接的对象时，不把当前可用性升级成新的生成失败原因；重点是正常情况下让它只看到已解锁候选。没有候选时返回真实的空候选与既有换类型指引，不用锁定关卡补满。

### 7.3 已确认的错位例

游戏 `data/stages/基地门口/__list__.xml` 的地铁站 UnlockCondition 为 21；`data/task/tasks1.json` 的任务 20 对应 `主线#21`，任务 21 对应 `主线#22`。任务 20 完成后地铁站已开，但基线后端把 21 写入 Agent 委托 get_requirements，导致过度前置。

修复不得只把所有阈值减一；任务 ID 与任务链序号并非普遍相邻。必须使用真实任务表映射并与完成集合相交，或者用已完成的合法前置锚点；不存在适用前置时不伪造一个 ID。

## 8. 验收边界

- 所有入口用同一 fixture 对比查询工具、任务概览和记忆分支，不能只测终端。
- 改动后新写入的 other_npc 归 assistant，user 检索不混入这些新记录的其他 NPC 台词；不新增迁移，不要求修复旧行。
