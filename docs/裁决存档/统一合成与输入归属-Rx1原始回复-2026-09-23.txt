## 裁决结论

**选择路线 1：保留紧凑数据包，实行“不回绕的有界输入会话”，以完整的撤销、排空、恢复及 broker 退出握手续接。**

但批准的不是“加一个计数上限，快到上限就 Dispose/Start”，而是两个必须同时成立的保证：

> **会话内：所有比较值始终处在同一个严格小于半范围的数轴区间。**
> **会话间：旧会话彻底失去执行能力以后，新会话才能取得输入权威。**

只满足第一条，会把误拒输入变成到点断输入；只满足第二条而没有可执行上限，仍然会重现 RCE-2。

当前状态应保持为：

| 项目                | 本次裁定                        |
| ----------------- | --------------------------- |
| RCE-2／G1          | **阻断，尚未解决**                 |
| G2 检测逻辑与负控        | 保留已成立的有限证据                  |
| G2 真实 Guardian 装配 | **未完成，不能由 Probe 代签**        |
| 新候选正式人验、C1 晋级     | **暂不开放**                    |
| 整体架构              | 不重开；保持既有 S/P/F、业务权威和显示／光照配对 |

完整交接材料已整理为：[裁决正文](sandbox:/mnt/data/CF7-RCE2-裁决-20260923/裁决.md)、[证据索引](sandbox:/mnt/data/CF7-RCE2-裁决-20260923/证据索引.md)，以及包含只读复核脚本和结果的[完整回包](sandbox:/mnt/data/CF7-RCE2-裁决与回归门槛-20260923.zip)。下文 E 编号对应证据索引中的包内路径与行号。

## 一、反例成立；现有绿项不能抵消它

### 1. 故障发生在“长期比较下界”，不是等到计数器最终溢出

`InputBridge.cpp` 同时检查 `shared.minEpoch` 和 `localFloor`，但 `lastEpoch` 前进不会自动推动这两个下界。持续前台且不取消时，两者可以一直为零。

因此：

```text
StaleEpoch24(0x800000, 0)
= ((0x800000 - 0) & 0xFFFFFF) >= 0x800000
= true
```

这在 **8,388,608** 就发生，不必等到 24 位计数器绕过 `0xFFFFFF`。有限在途队列并不能限制“当前代次距一个长期停在零的下界有多远”。包内长会话原始输出确实是：

```text
epoch：   1，4194304，8388607，8388608，8388609
交付增量：1，1，      1，      0，      0
RESULT FAIL failures=2
```

默认自测的 19/19 与它不矛盾：默认 wrap 用例主动推进了 floor，没有覆盖这里的持续前台零下界情形。**不能保留默认绿项，却删掉或改写长会话反例来宣布通过。**〔E03–E04〕

同时，报告对因果边界的克制是正确的：这是生产端点的加速逻辑反例，**不能据此倒推它就是此前短会话人验故障的根因**。

### 2. G1 的 46/46 有价值，但释放和恢复仍有缺口

跨进程夹具确实证明了几件重要事情：旧 Down 已成功入队但未被端点看见时，端点失焦或 Host 撤销可以使其随后被拒绝；Cancel 自身投递失败，也不必使旧包重新获得准入资格。〔E08〕

但这里存在两个不能跨越的证明边界：

**第一，S3 测的是“尚未交付 Down 的撤销”，不是“已经交付 Down 后的释放”。**
已经进入原处理器的 Down，随后 Cancel 投递失败，而且之后再没有任何输入包，这一情形仍需单独证明能够清理。抬高 floor 只能阻止旧输入继续准入，不能自动撤销原处理器已经建立的按下状态。

**第二，readmit 预先执行了 `FocusChild`。**
夹具 Surface 的 focus 回调也只是记录 `focus_cb`。它能证明代次重新准入，不能证明实际 Guardian 的返回首击、焦点回调和恢复资格链正确。〔E08〕

## 二、为什么选择有界会话，而不选择长期大代次绑定

路线 2 不是错误路线，但它需要同时解决：所有长期 floor/high-water 的表示、每个短 wire 包与完整代次的不可变绑定、未处理旧包的生命周期、描述符回收、序号回绕，以及跨进程发布顺序。

尤其不能在旧包出队时，用“现在的 `issuedEpoch` 高位”解释它。那是在用新状态重新命名旧事件。

| 路线             | 本次结论   | 理由                          |
| -------------- | ------ | --------------------------- |
| 单纯扩位           | 否决     | 推迟同构问题，没有消除长期下界歧义           |
| 定期推 floor／遇零特判 | 不采纳    | 尚无覆盖旧在途包、失焦和重准入的完整证明        |
| 完整长期代次＋短包绑定    | 可行，但不选 | 改动与证明面扩展到逐包身份和回收机制          |
| **有界会话＋完整续接**  | **选定** | 可以保留紧凑数据通道，把新增责任限制在输入会话生命周期 |

这里的“最小”是**最小可靠责任面**，不是最少改动行数。当前关闭链不完整，因此不能将其视为已经存在、只差调用的能力。

## 三、会话上限必须写成这样的生产合同

推荐固化以下保守数值：

```text
H = 2^23       = 0x800000
L = H - 3      = 0x7FFFFD

普通输入及常规取消代次：1 … L
终止保留代次：          至多 L+1 = 0x7FFFFE
派生比较值：            至多 L+2 = 0x7FFFFF
新会话初始 floor：      0
```

这样，同一会话内所有参与比较的数值都属于：

$$
[0,H-1]
$$

任意两者之差的绝对值最多是 \(H-1\)，因此在这个域内，现有环序谓词与普通整数的 `epoch < floor` 等价。**即使两个 floor 一直为零，也不会跨入半范围歧义。**

这项保证必须覆盖全部比较操作数，而不是只限制 Down：

`wire epoch`、Host 发号器、`shared.minEpoch`、`shared.issuedEpoch`、`lastEpoch`、`localFloor`，以及 `lastEpoch+1`、`max(lastEpoch,issued)+1`。

### 必须落实的细节

**统一 checked 发号入口。** 新 Down、普通 Cancel、无手势时的 Cancel、失活、hidden、queue_full、source_gone、target_rebuilt、投递失败，都必须纳入预算；在递增和掩码之前检查。当前 `CancelPointer` 即使 `had=false` 也递增，所以“限制点击次数”并不充分。〔E05〕

**高水位不得倒退。** `issuedEpoch` 应表达已签发高水位，不能因为发送一个较老缓存包而覆盖成更小值；两个 floor 同样不倒退。这里可以使用普通整数 max，前提是数值域合同已经成立。

**终止控制不能是一条碰运气的普通 Cancel。** 它只能撤销和释放，不能开启新手势；也不能因为 localFloor 再抬升一次，就被普通数据门永久挡住。

**接收端独立拒绝非法域。** 零值和超过普通许可域的数据包，不得先更新 high-water 再处理。Host 的正确性不能替代接收端边界。

**序号另立合同。** 当前 `consumedSeq` 是低 32 位、有符号读取，不能用 `>=` 作为长期完成判断。建议同步设置独立的每会话序号上限 `0x7FFFFFFD`，移动包也计算在内；完成 ACK 使用会话绑定的 ticket 和明确状态，不借这个收件计数排序。这里的上限与 epoch 的 `0x7FFFFD` 不同，必须分别命名。

**只在上限拒绝，并要求玩家重启，最多算止血，不算本轮可靠修补完成。** 正常响应的端点必须能够通过生产续接继续服务。

## 四、当前 Dispose/Start 不能承担续接；必须补齐关闭协议

### 1. 当前实现有明确的续接缺口

`NativePointerBridge.Dispose()` 发一次 `0xFF` 后立即释放 Host 映射，没有等待排空、恢复确认或 broker 退出。

`InputBridge.Restore()` 没有确认全部 WNDPROC/IAT 恢复成功，且在当前回调尚未返回时就写 `stopped=1`。

broker 关闭等待超时后仍会卸 hook、删属性并退出；启动路径没有独占安装保护。与此同时，旧 `0xFF`、`0xFC` 在普通输入门之前处理，`InputHook` 又可能由任意协议消息触发初始化。〔E06–E07〕

因此，立即重建至少可能引入：

> 旧包被新会话解释；旧 Stop 关闭新桥；旧回调触达新全局态；旧 broker 删除后继属性；两个安装者相互覆盖。

这些不是要求重开架构，而是选择“会话续接”后必须补上的局部责任。

### 2. 建议的状态机

```text
Active
  → Quiescing
  → Revoking / Draining
  → Restored
  → BrokerExited
  → Binding
  → AwaitFreshDown
  → Active
```

另设 **ClosedUnconfirmed**：停止新输入、保留显示、记录恢复未确认，**禁止热接后继**。

#### Quiescing：先停新手势，不吞合法结束边

正常接近上限时，提前预约续接。已经准入的手势在旧会话内完成 Up/Cancel，并等待端点完成。

Host 队列为空或 `IsDragging=false` 不足以证明端点已经完成；它们没有覆盖 Windows 队列、已取出未分派的消息，以及原处理器正在执行的调用。

失焦、故障或硬上限到来时，应显式取消旧手势，不在长按中偷偷换代次。被拒绝的旧 Down 不暂存、不重放。物理按钮仍按住时，新会话等待真实释放，再接受新的物理 Down。

#### Revoking：撤销资格与清理按下状态分开确认

先发布当前会话的 closing/stop 和终止 floor，再执行仅具撤销能力的端点清理。

对撤销线性化点之后才尝试准入的旧包，必须拒绝。对之前已经进入原处理器的调用，不能声称追溯撤销；应计入待完成集合，随后清理其输入状态。

清理至少包括虚拟鼠标按钮、捕获、`activeGesture`，以及原处理器自身需要的取消处理。**不得合成 Click、Down 或默认 WebMouseUp。**

当前 `buttons=flags` 还把 Shift/Ctrl 位存入按钮状态，`up && !buttons` 因而不一定清除 `activeGesture`；焦点分支也未清该字段。新的空闲证明应按真实鼠标按钮位 `0x73` 判定并统一清理，不能直接沿用现有字段含义。〔E04〕

目标一直挂死时，只能保持关闭并报告未确认，不能伪造“已释放”或“已恢复”。

#### Draining：排空不是发一个哨兵消息

必须封住所有发包者：Host 普通发送、MOVE 合并槽、已排程的 Drain、repaint 任务，以及 broker 的 Init/Stop 重试。延后回调绑定旧实例，不能转而使用新实例字段发送。

排空同时包含：

* 队列中的旧数据和控制消息；
* 已取出但未分派的消息；
* 正在执行、重入的原处理器调用；
* 可能访问旧上下文的 Hook/IAT 包装器回调。

**`consumedSeq` 不是完成 ACK。** 它在拒绝门和原处理器执行前就已经写入。PostMessage 成功也只说明入队，没有等待处理完成；消息可以先取出再分派，过滤可以跳过通常的 FIFO 顺序。因此，一个 WM_NULL、一次 Stop 成功或固定等待若干毫秒，都不足以证明退休完成。〔E04、E06〕([Microsoft Learn][1])

如果 ACK 在处理器内部写入，必须区分“恢复准备完成”和“这个控制调用已经返回”。不能用当前 `Restore` 内的 `stopped=1` 证明它自身已经退出。

#### Restored／BrokerExited：确认恢复，再允许后继

只有确认 WNDPROC/IAT 仍由本桥持有并成功恢复，才能报告 restored；不能覆盖其他后继包装器。卸精确 hook，删除仍属于本次 mapping/atom 的属性，停止控制重试，并观察本次 broker 真正退出。

broker 安装前必须取得**跨版本、目标 projector 进程实例级**独占资格。当前桥是进程全局单 target 状态，仅按 HWND 或协议版本分锁不够。Host 同时串行化 Start/Stop，并拒绝迟到的 Start completion。

放弃的 mutex、broker 突然退出、旧映射打不开，都不等于桥已经恢复。没有关闭证明时，只能拒绝后继；原目标进程真正退出、旧窗口全部失效后，才可按新身份重建。

控制／共享协议建议升至 v4，Host、broker、bridge 配套。**数据包可以继续紧凑，但不能因此省略控制消息的会话归属验证。**

### 3. 共享页需要补同步合同，而不是继续用“不撕裂”代替

当前注释从对齐 32 位写和后续 PostMessage 推导跨进程可见性，证明不充分。微软文档明确区分“原子读写”和“同步访问”；Interlocked 可以作用于不同进程共同映射的共享内存，并提供规定的同步／屏障语义。〔E06〕([Microsoft Learn][2])

这里应明确 stop、floor、issued、ACK 的原子发布与读取，以及映射释放时机。**这是合同缺口，不是我已经复现了跨核错读。**

### 4. 续接不能拆掉显示和释放路径

输入续接不得走 Controller 的整体 `StopCapture → native.Dispose → owner.Close` 路径。可以让 Surface 持有稳定的输入会话槽，替换已经闭合的 sink，保持输出 HWND、P 和既有光照合成不变。〔E11〕

桥暂不可用时，也不能让已经归 World 的按钮边漏到 Native/Web 再消费一次；同时保留物理鼠标移动、其他窗口合法输入及既有键盘释放能力。不新增业务命令、存档写入、暂停权威或自动杀游戏恢复。

## 五、必须通过的回归：既要证明安全，也要证明能续上

### 2. 新发现：声明 ROI 与记录的实际 F 矩形不完全一致

`flash.json` 中：

```text
fRegionScreen：  (109, 212, 640, 320)
f.windowRect：  (109, 213, 640, 320)
```

下一步只需定点补证：在同一几何版本中，把实际 F 客户区映射至统一物理屏幕坐标，逐项核对 crop、P 输出和覆盖关系，无需重开捕获架构。

另外，`ownedFlashExitedNormally=false` 与源码的超时强制清理路径一致。它不推翻之前的内容 proof，但**不能被用来认证正常退出或恢复链**。

最终仍应保留这些限定：full ROI 证明离散采样的 RGB 变化与 Present 前 GPU 输出，不证明逐帧连续性、屏幕扫描、业务 ACK、输入延迟或性能收益。原 JSON 也明确写着 `inputForwarding=NOT_IMPLEMENTED`、`humanAcceptance=NOT_PERFORMED`。〔E09〕

## 七、恢复 G1/G2、进入人验的具体门槛

### Gate A：有限补丁及机器回归闭合

必须具备数值域证明、完整关闭协议、失败分支、成套版本及上述相关回归。

**通过 A，只能恢复 G1 的技术候选资格，不代表真实游戏已经通过。**

### Gate B：同一真实 Guardian 候选完成 G1/G2 装配取证

G2 的 raw 1:1 零误差诊断也不能直接套给含光照、缩放的生产输出；生产变换应按其实际语义验证。

**只有 Gate B 完成，才能将整体 G1/G2 恢复为同一候选的 PASS。** 必要的人工进入场景属于采样配合，不等于正式人验签字。

### Gate C：短人验

沿既定三组，不扩张范围：

**切出后释放与返回首击；真实 surgery 中文输入／取消，不付费、不提交业务；缩放、最小化及恢复。**

各组分别记录 PASS／FAIL／NOT_RUN，并绑定同一候选。任何失败都停止晋级，不通过强制焦点、增加盲重试或放松撤销边界把脚本刷绿。

**通过这些门槛，只意味着具备继续既定有限 C1 路线的条件；不等于 C1 已完成、B 已开放或已获发布授权。**

## 八、复核范围

本轮已独立核对包内 **61 项 manifest 文件的大小与 SHA-256，一致**；核对 G2 声明的 managed/native DLL 哈希与 `executed-artifacts.json` 一致；检查原始日志、JSON 和关键生产／测试源码，并以自写只读脚本复核长会话反例及上述数值域性质。
