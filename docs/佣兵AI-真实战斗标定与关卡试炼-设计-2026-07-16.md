## 0. 决策摘要

### 0.1 已决

1. 先验证**策略是否有有效核心**，再调参数；实验顺序固定为“策略消融 → 粗参数扫描 → 小规模组合 A/B”。
2. `arena_calibration` 保持干净、对称、无正式关卡副作用的微观战斗场；真实关卡复用另建 `stage_trial`，两者共享批次编排、专用存档、JSONL 和分析器，不共享场景职责。
3. `stage_trial` MVP 只复用真实关卡的**地图/碰撞/安全元件/出生点/Wave/Enemy Parameters**，按指定 `SubStage` 独立运行；清场后经过短暂收尾窗口，直接清理并切下一测试场，不走正式关卡完成与奖励链。
4. 第一阶段只建设**参数与预编译策略选择的热调**，不建设任意 AS2 代码热替换。参数默认只对下一局新建佣兵生效；局中变更使样本失效。
5. 每条结果必须冻结代码、场景、构筑、人格、AI 配置与实际应用参数的 hash；只记录 profile 名称不足以复现。
6. 胜率不是单一裁判。结论必须同时考虑清场时间、HP/资源残值、伤害利用率、无决策、卡死、目标切换和最坏场景退化。
7. 完整“佣兵代理主角自主通关”不属于 MVP；出口导航、压力板、交互目标、剧情回调和多 SubStage 任务规划另立项目，不用其失败反推战斗 AI 无效。
8. 人形标定不另造简化 actor。复用现役 `MercLibrary tuple → 主角-男 → 初始化玩家模板 → HeroCombatBehavior` 生产链；`MecenaryBehavior` 是场景可雇佣 NPC 的非战斗行为，不得因命名相似误用。
9. 大规模 A/B 前先完成 `U0` 跑批正确性加固。当前 runner 按 case 连续执行 repeat，尚不满足本文要求的配对交错实验；现役 timeout、补跑和 JSONL 恢复也不能直接承担自动策略裁决。
10. `stage_trial` 首版每 case 创建并完整销毁一个 gameworld；不在同一 gameworld 上反复 `initStage()`。若仍不稳定，再降级为一进程一 case。

### 0.2 待短原型验证

1. 同一 Flash 会话内按“每 case 新 gameworld”连续运行不同真实 `SubStage`，跑几十场后是否仍无 actor、dispatcher、时钟、DepthManager 和场景引用污染。
2. 人形佣兵结构化伤害/决策遥测在标定开关关闭时能否保持零或近零常驻成本，开启时能否避免 JSON/字符串构造压垮战斗帧。
3. 真实关卡中的脚本型 `Instance` 能否可靠静态分类；分类不明时必须 fail closed，不得为了覆盖率默认执行。
4. 同一佣兵更换装备时，现有技能缓存键未含 loadout，是否会复用上一 case 的技能表；在修正缓存键前，实验必须隔离或显式清理缓存。

上述四项不能靠文档宣称通过。每项使用半天至一天的 disposable spike，失败则回到本文的降级路线。

## 1. 为什么拆成两种真实运行态

### 1.1 `arena_calibration`：微观、可归因

职责：固定场地、出生距离和双方构筑，回答“策略 B 相对策略 A 是否改变纯战斗表现”。现役服务已能生成双边兵种、清理玩家/同伴、监控污染并输出胜负、帧数、HP 和阵型审计，但 manifest 仍只接受 `兵种N + level`，结果也没有佣兵 AI 的结构化遥测。

后续扩展方向：允许一侧或双方使用固定人形佣兵构筑，并为每个新建 actor 注入冻结后的 `aiProfile`。现役普通角斗场已经存在 `MercLibrary tuple → 加载游戏世界人物("主角-男") → 完整装备/脸型/发型 initObject` 的生产路径；S1 应抽取共享 factory 或等价复用，不重新模拟 MovieClip。不要让竞技场读取正式任务、奖励、触发器或关卡回调。

人形 actor 的 AI 类型必须沿 `使用人形怪AI → Hero → HeroCombatBehavior` 分流。不得显式写 `unitAIType="Mecenary"`：显式类型优先级更高，会把战斗佣兵导向门口寻路/漫游 NPC 行为。

### 1.2 `stage_trial`：中观、场景化

职责：回答“已经通过微观 A/B 的 AI，在真实地形、真实出生点和真实波次压力下是否仍合格”。它不是正式关卡副本，也不评价剧情任务自主性。

两者关系：

```text
离线仿真/静态回归
  -> arena_calibration（同构 A/B，判断策略和参数）
  -> stage_trial（真实关卡战斗切片，判断泛化）
  -> 少量人工完整关卡观战（只作定性复核）
```

只有前一层通过的候选才进入后一层。这样可以把“策略无效”“参数不合适”“地形泛化失败”“不会完成任务目标”分开。

## 2. `stage_trial` 场景契约

### 2.1 MVP 复用白名单

从真实关卡 XML 选择一个明确的 `stagePath + subStageIndex`，复用：

- `BasicInformation.Background`；
- `BasicInformation.Environment` 与环境默认值合并结果；
- 地图边界、碰撞箱和纯视觉背景元素；
- 经安全分类的 `Instances.Instance`；
- `SpawnPoints`；
- `Wave/SubWave/WaveInformation/EnemyGroup`；
- `Enemy` 的 Type、Level、Quantity、Interval、Parameters 及 WaveSpawner 已正式支持的字段。

解析继续复用现有 `StageXMLLoader/StageInfo/StageManager/SceneManager/WaveSpawner` 语义，不另写一套“近似关卡解析器”。但执行必须走 trial 专用分支，不能先完整启动正式关卡再临时删除副作用。

### 2.2 MVP 禁止项

默认忽略或拒绝：

- `Rewards`；
- `Pickups`；
- `CallbackFunction`；
- 正式 `Event` 中会写任务、成就、经济、存档或剧情状态的动作；
- `Trigger` 与依赖 `HeroMoved` 的压力板；
- NPC、商店、剧情交互和任务物品；
- 正式 `StageFinished/StageFailed/FinishStage/NextStage`；
- 自动存档、shadow save 和 dirtyMark 持久化；
- 正常多 `SubStage` 串行转场；
- 不能证明为纯视觉/纯碰撞的脚本型地图元件。

“忽略”必须写入 compatibility report，不能静默。含禁止项不必一律拒绝整个关卡：若被忽略内容不影响选中 SubStage 的刷怪与清场，可以标为 `combat_slice`；无法证明则标为 `unsupported`。

### 2.3 地图元件分级

| 等级 | 含义 | MVP 行为 |
|---|---|---|
| `safe_visual` | 背景、装饰、无脚本显示实例 | 加载 |
| `safe_collision` | 固定障碍、地形、纯碰撞元件 | 加载 |
| `reviewed_combat` | 已人工确认只影响局内战斗的机关 | 显式 allowlist 后加载 |
| `scripted_unknown` | 带脚本但副作用未知 | 拒绝或跳过并标 `unsupported` |
| `progression` | 任务、剧情、经济、存档、门/压力板推进 | MVP 禁止 |

施工时应先做静态 compatibility analyzer，输出每个关卡/SubStage 的分类、被忽略字段和拒绝原因。首批场景从 `safe_visual + safe_collision + Wave` 的简单样本挑选，不以覆盖全部 212 个关卡为目标。

### 2.4 单场生命周期

```text
validate case + freeze hashes
  -> create fresh gameworld
  -> load selected Stage XML / SubStage
  -> build trial scene from whitelist
  -> spawn frozen merc build(s)
  -> arm telemetry
  -> start WaveSpawner
  -> wait for terminal condition
  -> settle 30~60 frames
  -> snapshot result
  -> close trial stage without formal Clear/StageFinished
  -> SceneManager.removeGameWorld
  -> contamination audit
  -> next case
```

终态优先级：`contamination/error/aborted/timeout` 高于有效清场。清场不得只看某一帧敌人数为零：必须同时满足 Wave 已结束、已知敌对 actor 为零、无待执行阶段刷新，并经过 settle window。settle 期间发现新召唤则取消收尾并恢复运行。

场间切换不调用正式关卡结束链。最后一个敌人死亡的同帧不得直接卸载，否则容易丢失死亡事件、召唤、HP 归零和最终伤害记账。

`StageManager.closeStage()` 只关闭 spawner/event handler 并断开部分引用，不负责删除地图元件、单位、拾取物、碰撞层、dispatcher 和 DepthManager；完整销毁职责属于 `SceneManager.removeGameWorld()`。因此首版禁止“清空同一 gameworld 后直接 init 下一场”。正式 `WaveSpawner.finishWave()` 会进入 `StageManager.clearStage()` 并发布 `Clear/StageFinished`，trial 必须提供专用完成回调，不能先走正式完成链再补救。

同理，不得直接复用会解析奖励并更新掉落索引的顶层正式载入函数。trial loader 必须在产生任务、奖励、拾取物和 `HeroMoved` trigger 之前完成白名单裁剪。

### 2.5 佣兵不是完整任务主角

MVP 可以定义 `leaderMerc` 作为镜头、阵营和失败条件的逻辑锚点，但不把它伪装成完整 `_root.控制目标`。若现有系统必须读取 hero，可使用 trial-only 适配门面；不要让不可见主角代理参与索敌、受击、胜负或遥测。

不在 MVP 解决：

- 主动寻找出口并换图；
- 选择压力板、开关或交互目标；
- 理解护送、防守点、拾取、撤离等任务语义；
- 执行剧情 Callback；
- 跨 SubStage 规划资源和目标。

### 2.6 人形 actor 契约与已知不对称

人形 case 建议使用判别联合，避免继续把所有参赛者压成 `兵种N + level`：

```text
monster = { kind: "unit", type, level, parameters }
human   = { kind: "merc", mercTuple, aiConfig }
```

`mercTuple` 至少冻结等级、名字、ID、身高、脸型、发型、完整装备、性别和元数据；同时记录 linkage、实例名、技能/被动快照、人格 seed、最终人格向量、profile、pipelineSpec 和 loadout hash。实例名必须唯一且不得等于 `_root.控制目标`。

S1 必须分别处理以下实验语义，不能混成一个“公平互殴”指标：

- 友方非主控佣兵存在 MP 缩减，并会读取全局命令/集中攻击目标；敌方人形不完全对称。正式佣兵验收以“佣兵在友方、怪物在敌方”为主口径；若做双方人形比较，必须 side crossover 并单列阵营效应。
- 普通生产路径可能在同步 attach 初始化完成后才赋 `佣兵参数`，而技能/被动初始化会读取该字段。标定必须明确选择“复现现役时序”或“验证完整预期构筑”，并写入 case hash。
- 无真实主角时，人形 AI 丢失最后目标后可能进入跟随/等待再索敌。标定服务可预置首个攻击目标，但仍应把失去目标后的无决策时间单列，不能直接归因于寻路。
- 技能缓存键当前只含名字、等级和技术档位，不含装备。任何跨 loadout A/B 都必须先隔离缓存，长期应把 loadout hash 纳入缓存键。

## 3. 参数热调，而不是代码热替换

### 3.1 当前基础与边界

现有玩家模板会创建确定性人格，调用 `_root.计算AI参数`，再按 `profileId` 覆盖人格；`personality.aiSpec` 可选择 PipelineFactory 的 mods、posts、sources 和 filters。PipelineFactory 也支持预编译 factory 注册。这些机制足以承载参数实验和有限策略消融，但当前仓库尚未发现正式 `_root.佣兵AI模板` 注册表初始化或 `PipelineFactory.register*()` 消费接线，不能把“具备扩展点”写成“已有可直接切换的正式 profile 库”。

`ActionArbiter` 在构造时一次性按 `aiSpec` 建立 pipeline，已有 `unitAI` 的 actor 重进初始化也不会自动重建。因此 next-run 不是单纯治理偏好，而是当前对象生命周期的正确边界。

现有 HTTP `/console` 可经作弊码执行 `#get/#set`，适合人工诊断，不适合作批量实验真源：它没有白名单、配置 hash、局次边界和结果关联。不得用一串 console 命令冒充可复现的热调协议。

### 3.2 建议控制面（拟议，尚未实现）

新增专用快速控制 task/gameCommand，例如：

```json
{
  "task": "ai_tuning",
  "action": "stageProfile",
  "profile": {
    "profileId": "retreat-b",
    "personalitySeed": 142857,
    "params": {
      "retreatEnterThreshold": 0.58,
      "kiteThreshold": 0.82,
      "safeReloadDistMult": 2.1
    },
    "pipelineSpec": {
      "mods": ["StanceAffinity", "RangePressure", "SurvivalUrgency"],
      "posts": ["Momentum", "FreqAdjust"],
      "sources": {
        "engage": ["BasicAttack", "SkillCandidate"],
        "retreat": ["PreBuff"]
      },
      "filters": ["AnimLock", "Interrupt"]
    }
  }
}
```

实际 wire shape 在施工切片中再定；一旦落地，必须同步 `launcher/README.md`、`agentsDoc/data-schemas.md`、`agentsDoc/testing-guide.md` 和协议测试。本文示例不构成现役协议。

### 3.3 参数治理

- 仅接受显式白名单标量和 PipelineFactory 已注册 key；拒绝任意属性路径和函数体。
- 服务端与 AS2 双端校验有限数值、范围、枚举和未知字段；禁止 NaN/Infinity 静默进入人格。
- 参数合并顺序固定为：确定性基础人格 → profile 覆盖 → `_root.计算AI参数` → 实验参数覆盖 → clamp → 冻结快照。
- 不直接修改共享 `_root.佣兵AI模板` 后让旧 actor 半热更新；每局创建独立快照。
- 默认 `next_run` 生效。当前局已开始后收到新 profile，只进入 staging slot。
- 若开放 `active_run` 仅供人工调试，该局立即标记 `invalidatedByLiveMutation=true`，不得进入 A/B 统计。
- Pipeline 结构在 ActionArbiter 构造时固化；切换 pipeline 必须重建 actor/arbiter，优先通过下一局自然重建完成。
- 消融配置由工具从冻结 baseline 生成“仅删一个 key”的完整 `pipelineSpec`，并在双端校验差异集合恰为一个模块；不依赖人工手抄列表。
- 标定模式必须强制关闭全量 `DecisionTrace`。当前源码默认开启 AI 调试且日志级别为 FULL 级别，逐 tick 字符串与服务器输出会改变墙钟耗时；批量统计改用 actor-local 数字计数器，结算时一次聚合。

### 3.4 不做任意代码热替换

第一阶段不接收 AS2 源码、函数字符串、外部 SWF 任意模块或运行时 class 覆盖。原因：AVM1 无可靠运行时源码编译，旧实例/原型/静态单例难以替换，asLoader 生命周期会放大幽灵状态，且结果无法证明实际执行版本。

结构性新策略继续走正常流程：实现 class → AS2 测试/Flash smoke → 发布 asLoader → 重启运行态。若重启耗时后来成为主要瓶颈，再以测得数据单独评估“预编译策略包版本切换”，不能预先扩张到通用热更框架。

## 4. A/B 实验协议

### 4.1 固定实验单元

一个可比较 run 至少冻结：

- `buildCommit/codeBuildId`；
- `arenaCaseHash` 或 `stagePath + subStageIndex + stageHash`；
- 佣兵身份、等级、装备、技能、人格原始向量与 seed；
- 敌人 roster 或真实 Wave 配置 hash；
- 出生位置、阵型、难度、timeout；
- `aiProfileId + appliedParams + pipelineSpec + aiConfigHash`；
- 遥测 schema 版本。

除待测因素外，其余字段必须相同。随机性未全链路统一 seed 前，采用交错/分块顺序降低时间漂移：`A1,B1,B2,A2...`，不能先跑完全部 A 再跑全部 B。

这是尚未实现的硬门。现役 C# runner 按 case 遍历并连续跑完该 case 的全部 repeat；把 A、B 写成两个 case 会实际得到 `A×N → B×N`。AI 实验必须先把 run plan 展开为显式顺序，并给每局写入 `experimentId/blockId/pairId/arm/orderIndex`。二臂采用等量 `AB/BA` 或 `ABBA/BAAB` block；多档粗扫采用平衡轮转。崩溃后补跑整个不完整 block，或在分析时排除该 block，不能只保留成功的一臂。

### 4.2 实验顺序

#### 阶段 A：策略消融

以当前完整 pipeline 为 baseline，每次只禁用一个可独立门控模块：撤退、风筝/走位、主动闪避、安全换弹、武器切换、技能候选、预战 buff、群体压力感知、决策噪声/温度等。

解释规则：

- 禁用后稳定退化：该模块是有效核心；
- 禁用后无显著变化且触发率近零：未接线或不适用；
- 禁用后无显著变化但触发率高：可能冗余或指标不敏感；
- 禁用后稳定改善：实现或默认参数存在问题，进入阶段 B；
- 只在单一场景改善：标为场景专用，不直接升为全局默认。

消融只证明“该模块在当前组合中的边际贡献”，不能独立证明无潜力。禁用后改善先标为 `default_harmful_or_mistuned`；无差异也可能来自替代模块、指标失真或触发机会不足。

#### 阶段 B：粗参数扫描

只扫描阶段 A 证明有贡献、疑似失调或场景专用的模块。每参数包含 `disabled sentinel + 当前默认 + 3~5 个宽档`，观察连续趋势和有效区间；不在第一轮做高维密集网格。只有某个参数区间同时优于默认与禁用、相邻档方向连续，并在新批次复现，才升级为 `promising_mistuned`。

#### 阶段 C：小规模组合

只组合有机制关联且单因素已有证据的项，如“撤退 × 安全换弹”“风筝 × 武器射程”“包围感知 × 缺口突围”。没有单因素证据的组合不进入批次。

### 4.3 分类口径

| 分类 | 证据要求 | 后续动作 |
|---|---|---|
| `effective_core` | 多类场景稳定改善，消融明显退化，无严重最坏场景回归 | 保留，进入窄范围调参 |
| `promising_mistuned` | 宽扫描存在连续改善区间，默认值不在合理区间 | 调默认值并复测 |
| `scenario_specific` | 只在明确场景族改善，其他场景中性或可控 | 做 profile/条件门控 |
| `redundant_or_inactive` | 消融无差异，且触发率低或结果被其他策略支配 | 检查接线，必要时移除 |
| `no_potential` | 接线和触发机会已证实；禁用、默认和可信宽范围均覆盖；区间估计已足以排除预设最小有意义收益，且无稳定场景专用收益 | 停止投资 |
| `harmful` | 多数场景退化或显著增加卡死/无决策/资源浪费 | 回退或重做机制 |

具体显著性阈值不在无 baseline 方差时拍脑袋。pilot 先估计每类指标方差，再在 analyzer 配置中冻结最小效应量、置信区间/自举口径和严重回归阈值；修改判据必须版本化，不能为让候选通过而临时放宽。

### 4.4 AI Experiment Protocol v1

每个实验在执行前提交一张冻结实验卡：假设、唯一待测因素、tuning suite、holdout suite、主指标、护栏指标、最小有意义效应、最大 block 数、停止规则和定性 rubric。禁止跑完后再选择裁判。

最小流程：

1. **接线验证**：证明模块有触发机会，禁用/换参数会改变候选、选中动作或机制计数；未接线不能进入“无潜力”判断。
2. **方差 pilot**：每个代表场景先跑约 8~12 个完整 block，只估计方差、失败模式和运行成本，不给最终结论。
3. **确认批**：冻结参数与判据后，用新 batch、完整 block 和未参与选择的 holdout 重跑。暂未做功效计算时，可沿用 30~100 的经验范围，但统计单位是完整 block，不是单局。
4. **配对分析**：arena 以 block 内差值为主；stage trial 按独立 SubStage 聚类。同一地图重复 100 局只降低局内噪声，不等价于覆盖 100 个场景。
5. **盲化定性复核**：抽取中位局、最坏局和 A/B 方向相反的 discordant block，隐藏 arm 标签，按接敌、目标选择、脱困、撤退、资源浪费和视觉可接受性评分。定性结果可否决明显坏行为，但不替代定量主指标。

全局默认候选至少在三类战斗压力中各有 tuning 场景，并在未参与调参的 holdout SubStage 上保持收益；只在单图有效的候选归为 `scenario_specific`。

## 5. 遥测与结果契约

### 5.1 结果分层

1. **每局 summary**：批量统计的主入口，体量稳定。
2. **每单位 summary**：定位哪名佣兵贡献或退化。
3. **稀疏事件流**：只记录动作切换、伤害、死亡、卡死、异常等事件，不逐帧 dump 全状态。
4. **DecisionTrace 诊断**：只在抽样或失败复盘时开启 FULL；不把现有长字符串直接当统计仓库。

现役 result schema/analyzer 只能按 `caseId|caseHash` 做粗聚合，分析时读取的 git commit 也不等于 Flash 实际执行构建。AI A/B 至少新增独立的 result v2 语义，每局落：

```text
experimentId, blockId, pairId, arm, orderIndex,
runtimeBuildId, arenaOrStageHash, mercBuildHash,
personalitySeed, aiConfigHash, appliedParams,
telemetrySchemaVersion
```

失败率、桥接异常率和有效配对数量分开报告；error/timeout 不得混入胜率分母后仍叫“有效样本”。

### 5.2 最小指标

| 维度 | 指标 |
|---|---|
| 结果 | winner/clear、frames、timeout、双方 start/alive/remainHp |
| 输出 | damageDealt、actualHitCount、killCount、effectiveCombatFrames |
| 生存 | damageTaken、deathFrame、healUsed、remainHpRatio |
| 决策 | selectedActionCounts、noDecisionFrames、candidateEmptyCount、targetSwitchCount |
| 移动 | stuckCount、unstuckCount、boundaryEscapeCount、移动/静止帧、平均接敌距离 |
| 资源 | reloadCount、reloadInterrupted、ammoSpent/remain、healItemSpent |
| 健壮性 | NaN、防御断言、contamination、actor/clock/listener 残留 |

`actualHitCount` 必须沿真实 DamageResult 语义统计，普通 MISS、联弹全段 MISS 和直感等无实际命中不能计入；伤害链若复用 `DamageResult.hasActualHit()`，只在标定 gate 开启时做聚合，禁止给普通战斗热路径增加 JSON 或字符串分配。

指标还需满足：`actualHitCount` 与有效伤害并看，避免奖励低伤多段；`targetSwitchCount` 按存活目标/击杀机会归一化；`noDecisionFrames` 只除以可决策帧，排除动画锁；清场时间把失败/timeout 作为封顶成本或竞争结果处理，不能只统计成功局。

### 5.3 结果解释防线

- 胜率提高但卡死、无决策或资源浪费显著增加，不自动判优。
- 清场更快但只来自人格/构筑漂移，样本不可比。
- stage trial 失败若原因是 `unsupported_trigger/progression_required`，不计为战斗 AI 失败。
- timeout 必须至少区分 `combat_timeout`、`bridge_timeout`、“无法接敌/卡死”和“关卡等待脚本”。`frames == null` 的桥接超时是基础设施异常，必须补跑，不能算作有效战斗完成。
- 对平均值之外必须报告 p50/p90 或分位数；少量极慢局不能被均值掩盖。

## 6. 施工切片与止损门

现有无人值守链值得复用：C# 已有批次串行、manifest 冻结、逐行 JSONL、status/abort；Node runner 已有专用存档、冷启动 ready gate、轮询、重启与缺行补跑；AS2 arena 已有逐局清单位、加载 hook 恢复和召唤污染监控。本地存在 45 局连续 finished 的普通兵种结果，可证明“同一 arena host 连跑”基础成立，但尚无足够长期证据证明“冷启动—崩溃—自动恢复”全链可靠。

因此无人值守佣兵 A/B 复用外层框架，不重写 runner；`stage_trial` 只复用 Launcher/存档/轮询/JSONL/重启框架，不复用 arena 的场景生命周期实现。

### S0：文档与离线契约（本轮）

- 建立本文；
- 在斗兽架构与 UnitAI ROADMAP 挂接边界；
- 不修改现役协议和测试入口。

完成门：文档治理巡检通过；所有“已实现/拟议”口径清晰。

### U0：跑批正确性加固（0.5~1.5 天）

- C# 区分 `combat_timeout` 与 `bridge_timeout`，墙钟等待加入固定 grace 和可配置降帧系数；
- runner 补跑时深拷贝完整 frozen case，只修改补跑身份/repeat；补跑前后验证 case/profile hash 不变；
- JSONL reader 容忍并显式隔离“仅末尾未写完的半行”，正文坏行继续 fail closed；
- 引入显式 block run plan，支持平衡 `AB/BA` 与不完整 block 恢复；
- result v2 记录实际 runtime build/profile/seed/config hash。

完成门：人为断 socket、制造慢帧、杀 Flash 后，基础设施失败不进入有效样本；恢复只补异常/缺失 block，且补跑实验配置 hash 不变。U0 未通过，不启动无人值守大样本 AI 裁决。

### S1：人形佣兵竞技场 spike（0.5~1 天）

- 从现役普通角斗场抽取或等价复用 merc tuple → `主角-男` initObject 生成路径；
- 固定一名友方人形佣兵对固定怪物，确认进入 `HeroCombatBehavior`、能够索敌和正常结算；
- 在 actor 创建前注入两个仅差一个因素的冻结 `pipelineSpec/profile`；
- 标定模式强制关闭全量 DecisionTrace，连续跑 8~12 个完整 `AB/BA` block；
- 输出最小 per-unit summary。

止损门：若人形初始化依赖正式玩家/存档状态过深，抽 `MercCombatActorFactory`，不在 ArenaCalibrationService 内复制完整玩家模板；若必须伪装 `_root.控制目标` 才能战斗，停止并先设计 trial-only hero facade。S1 只证明接线、隔离和可观测性，不产出策略优劣结论。

最小 S1 仍按 0.5~1 天估计；若同轮纳入正式 profile 注册、技能缓存隔离、双方人形 side crossover 和完整结构化遥测，则按 1.5~3 天估计。

### S2：结构化遥测 spike（0.5~1 天）

- 只覆盖 actual hit/damage、selected action/no decision、卡死/脱困；
- 测量 telemetry off/on 帧耗与结果体量。

止损门：若逐事件出站过重，改为 AS2 局内数值聚合，只在结束时回 summary；原始事件仅失败抽样。

### S3：真实 SubStage 连跑 spike（0.5~1 天）

- 选择 2~3 个无脚本简单关卡；
- 只装环境、碰撞、安全元件和 Wave；
- 先以一进程一 case 建立正确性基线，再在同进程内每 case 新建 gameworld；
- 清场 settle 后执行 trial close + `SceneManager.removeGameWorld()`，循环 20~50 次；
- 审计 actor、dispatcher、clock、WaveSpawner、SceneManager/StageManager/DepthManager 引用。

止损门：若同进程、每 case 新 gameworld 仍不稳定，MVP 降级为“一次进程跑一个 stage case”，保留无人值守重启/补跑；不测试同一 gameworld 反复 init，也不要为追求零重启先重构全部 StageManager 生命周期。

### S4：A/B MVP（约 4~7 工程日，不含 U0 与采样时间）

- manifest/profile/schema；
- next-run 参数 staging；
- 人形佣兵 spawn factory；
- JSONL + analyzer；
- 3~5 个消融项、少量 pilot 场景；
- C#/Node/AS2 验证与文档同步。

完成门：接线验证、完整配对 block、失败/超时分层、holdout 复核与严重回归门均可由 analyzer 复现；现役 `benchLevel` 粗判不得直接充当 AI 自动裁决器。

### S5：stage trial MVP（约 5~8 工程日，不含场景人工分类）

- compatibility analyzer；
- trial service 与场景生命周期；
- 单 SubStage 连跑、settle、污染检测；
- 代表性真实场景矩阵；
- 与 arena 结果联合报告。

该估算只对简单白名单场景、并接受“一进程一 case”降级时可信；若要求同会话高可靠连续换图，需另行预留生命周期排障时间。

完整代理主角预估至少 15~25 工程日且有持续特殊关卡适配成本，不进入 S5 顺手施工。

## 7. 首批场景与验收矩阵

首批不追求按剧情覆盖，按战斗压力正交选样：

| 场景族 | 主要回答 |
|---|---|
| 开阔、低密度 | 基本接敌与输出是否正常 |
| 狭长走廊 | 射程、拥堵、边界和追击 |
| 远近程混编 | 目标选择、风筝、换弹安全 |
| 双侧/多出生点 | 包围感知、转向和重定位 |
| 高密度蜂群 | 脱困、资源消耗、生存 |
| 高韧性/Boss | 技能、武器选择、长战稳定性 |
| 多波耐久 | 血包、弹药、状态跨波管理 |

每个候选至少先通过 arena 同构 A/B，再进入其中 3 类 stage trial。任何全局默认改动必须给出最坏场景变化，不能只展示最好样本。

场景集合在查看候选结果前拆成 `tuning suite` 与 `holdout suite`。每个无人值守批次在开头、中间、结尾插入固定 baseline anchor，用于识别热机、会话漂移和状态污染；人格 seed 必须明确命名为 `personalitySeed`，在全链 RNG 尚未统一前不得宣称为可复现 `runSeed`。

无人值守佣兵确认批还需在人为强杀一次 Launcher/Flash 后满足：结果无重复 run、实际 profile/config/build hash 可复核、`frames=null` 的有效 timeout 为零、恢复只补缺失/异常 block、专用存档运行前后关键 section hash 不变。
