这仍然不是赌场阶段。当前阶段不引入赔率、下注盘、胜负返奖或长期经济闭环。它是竞技场玩法的一种，同时复用标定战斗内核，服务玩家测试群、开发调试和后续平衡基准讨论。

## 结论摘要

- 入口应归入正式竞技场面板：在 `DEATH MATCH` 面板中新增 `定制赛` 或 `定制死亡竞赛` 模式，而不是另开一个外置测试工具。
- 产品设定可以解释为“玩家出钱定制死亡竞赛”：费用用于场地和委托，不代表赌博赔率，也不从战斗结果返奖。
- 工程上仍应隔离内核和结算：UI 可复用 `arena-panel.js`，但长时间战斗运行、日志、无掉落/无经验规则不应直接混进现有标准竞技场入场流程。
- P1 已完成 `怪物 vs 怪物` 的定制赛入口：导入/编辑赛程代码，生成双方 roster 和标定 case。
- P2 已选择低风险后台路径：Web panel 发送 inline single-case，C# 包装成 `arena-calibration.case-manifest.v1`，复用 `ArenaCalibrationTask` 和 AS2 `ArenaCalibrationService` 运行。
- P3a/P3b 已把定制赛推进到二级可视化编辑器和产品化日志：单位浏览器由 `data/units/units.json` 全量派生，`is_hostile` 只作为 UI 标签，手动 roster 编辑仍回写赛程代码，`startSingle` 结果写入 `logs/arena-custom/`。
- 配置分享应以“赛程代码”为核心交互物。玩家可以复制、粘贴、同步测试同一组怪物；群内仍以口述反馈为主，不强迫填写结构化报告。
- 单位选择必须以 `data/units/units.json` 的数字 ID 为规范身份，而不是 `name` 或 `spritename`。现有单位存在大量重名和同素材变体，仅显示名称不足以复现配置。

## P1 施工契约

P1 的目标是把“定制死亡竞赛”变成竞技场面板内可见、可复制、可验证的低改动入口，并固定赛程代码格式。P1 不承诺真实开战，不扣费，不写后台日志。

### P1 范围

- 只支持 `mode=mvm`，即怪物 vs 怪物。
- 在竞技场面板新增 `定制赛` tab。
- `定制赛` P1 只渲染一张入口卡，包含赛程代码输入、导入、待标定组合预设、随机抽取、复制代码、双方摘要、估算场地费和 `生成赛程`。

- 不修改 AS2 `ArenaCalibrationService`。
- 不做 `pve` / `player=current`。
- 不做正式扣场地费、次数限制、冷却、返奖或赌场赔率。
- 不做完整单位浏览器；P1 只使用赛程代码和样例，后续按方案 B 扩展。

## P2 施工契约

P2 的目标是让 `定制赛` 从“生成赛程”进入真实后台 single-case 运行。P2 仍不引入正式经济扣费、赔率、返奖或完整单位浏览器。

### P2 范围

- UI 主按钮改为 `开始委托`。
- Web panel 新增 `custom_start` / `custom_status` / `custom_abort` 三个 arena panel cmd。
- `custom_start` 携带 canonical 赛程代码和 parser 生成的 `calibrationCase`。
- `ArenaTask` 将三类 custom cmd 委托给 `ArenaCalibrationTask`，并回 `panel_resp`。
- `ArenaCalibrationTask` 新增 `startSingle` 控制面：接收 inline `calibrationCase`，包装成单 case manifest，写入 `tmp/arena-calibration/batches/<batchId>/case_manifest.json`，再走原 `RunBatch`。
- `custom_start` 成功后回 `closePanel:true`，前端走现有 `requestClose({dismissReturnStack:true})` 退出 Web panel，让后台战斗按正常游戏视野运行。
- `ArenaTask` 记录定制赛 batchId；`ArenaCalibrationTask` 到达终态后回调，Host 通过 `RequestOpenPanel("arena", ..., initData.mode="custom_result")` 重新打开竞技场面板并显示独立结算页。
- AS2 `ArenaCalibrationService` 在 no-player 标定场景中使用动态交战热点驱动 `斗兽标定镜头`，由 `HorizontalScroller.switchFollowTo` 永久跟随该虚拟镜头；优先追最近交战对，死亡/亡语 pending 单位仍参与热点，避免自爆或血腥死阶段镜头提前离场。
- P2 日志短期继续写入 `logs/arena-calibration/<batchId>-results.jsonl`；P3b 起 `startSingle` 定制赛结果拆到 `logs/arena-custom/<batchId>-results.jsonl`，批量标定仍保留原目录。
- UI 在启动前显示后台状态、batchId、完成进度和 resultPath，并可请求中止；主路径关闭面板后不再持续轮询，`custom_status` 保留为调试和 fallback 查询。

### P2 不做

- 不新增独立 `arena_custom_match` task；现阶段复用 `ArenaCalibrationTask`，减少 AS2 和 C# 长任务重复。
- 不扣真实场地费，不写存档，不做次数限制或冷却。
- 不做 `pve` / `player=current`。
- 不做 Web 面板内的实时观战流式过程；P2 主体验是启动后关闭面板，玩家看 Flash 战斗视野，后台完成后回开 `custom_result` 独立结算页。

## 背景

基准标定数据需要玩家测试群多轮讨论和迭代。等待正式基准收敛期间，竞技场内可以先提供一个可解释为正式玩法的定制赛入口，让测试用户按特定配置观察战斗表现：

- 玩家选择模式：`怪物 vs 怪物` 或 `玩家 vs 怪物`。
- 怪物配置来源：从 `data/arena/meta_teams.json` 派生的关卡元战队待标定组合、从该预设池整局或单侧随机抽取、从本地保存的单侧配置读取、手动从 `units.json` 逐个添加。
- 用户通过复制赛程代码分享组合，其他人粘贴后运行同一配置。
- 反馈以群内口述为主，工程侧只记录最小运行事实，避免让测试者负担过重。

这个功能与最终赌场阶段共享底层战斗内核，但目标不同：定制死亡竞赛服务于调试、观察、玩家交流和基准讨论；赌场阶段才涉及赔率、下注、返奖和长期经济闭环。

- 单位数据：[data/units/units.json](../data/units/units.json)
  - 当前本地探查共有 449 个单位条目。

  - UI 必须显示 `兵种ID + name + spritename + 默认等级 + 关键统计`，否则测试者很难确认选中的是哪一个变体。

### 不应直接复用为核心的部分

- 标准竞技场入场结算流程
  - 现有 `ArenaTask` 更偏正式竞技场面板即时请求，超时窗口和语义都较短。
  - 定制死亡竞赛需要可观察的战斗运行、状态查询、中止和独立日志，更接近标定任务桥。
  - 即使 UI 放在竞技场面板内，长任务控制也不应简单塞进现有标准挑战 `enter` 语义。

- 经济字段进入赛程代码
  - 玩家可以支付场地费，但费用应由当前版本和规则计算，不由玩家分享的赛程代码指定。
  - 赛程代码只描述战斗配置和复现信息，不携带 `money`、`reward`、`drop`、`loot`、`exp` 等结算字段。

## 需求草案

### 模式

- `mvm`：怪物 vs 怪物。首期优先，最接近现有标定内核。
- `pve`：玩家 vs 怪物。用于体验和压力观察，不纳入怪物基准统计。
- UI 标签建议：`标准模式`、`堕落模式`、`爬升模式`、`定制赛`。
- 产品文案建议：`定制死亡竞赛`、`赛程代码`、`场地费`、`开始委托`、`观战`。

### 怪物配置来源

- 预设组合：由 `tools/derive-arena-custom-presets.js` 从 `data/arena/meta_teams.json` 派生，蓝方默认使用 `thief-lv30x4` 对照阵容，红方使用关卡拆解元战队；当前因赛程代码单侧上限为 20 体，超大波次暂不进入 Web 预设池。
- 随机组合：整局随机仍从待标定预设池抽取完整赛程；单侧随机从同一预设池抽取关卡元战队 roster，可分别放入蓝方或红方，用于对比红蓝位置是否影响效能；按等级区间、阵营、数量、强度档位生成的新随机器留给后续扩展。
- 手动选择：从 `units.json` 搜索、过滤、逐个添加，显示完整身份信息。
- 本地配置：蓝方和红方都可把当前单侧 roster 保存到浏览器 localStorage，并读取到任意一方；这是测试便利配置库，不进入赛程代码协议，也不代表跨机器共享。
- 交换配置：配置总览页可一键交换红蓝 roster，用同一组合验证红蓝出生位置、AI 朝向或镜头因素是否影响战斗结果。
- 粘贴导入：从赛程代码恢复同一局或同一组阵容。

### 赛程代码

赛程代码是定制赛最重要的交流载体。建议采用版本化、可读、可校验格式：

```text
CF7ARENA:v1;mode=mvm;seed=83621;blue=u164@60x1;red=u11@1x1
CF7ARENA:v1;mode=mvm;seed=90210;blue=u44@30x2,u48@30x1;red=u164@60x1,u11@10x1
CF7ARENA:v1;mode=pve;seed=3307;enemy=u164@60x1,u11@10x1;player=current
```

字段建议：

- `CF7ARENA:v1`：格式魔数和版本号。
- `mode`：`mvm` 或 `pve`。
- `seed`：配置生成种子。首期只承诺复现随机选怪，不承诺完全锁定战斗随机数。
- `blue` / `red`：怪物对战双方，单位 token 为 `u<ID>@<level>x<count>`。
- `enemy`：`pve` 模式的怪物侧。
- `player=current`：使用当前本地玩家状态。
- 可选字段：`arena`、`timeout`、`rules`、`difficulty`。

解析后内部应规范化为现有 AS2/C# 已接受的 roster：

```json
{
  "mode": "mvm",
  "blueRoster": [{ "type": "兵种164", "level": 60, "count": 1 }],
  "redRoster": [{ "type": "兵种11", "level": 1, "count": 1 }]
}
```

约束：

- token 的规范身份是 `u<ID>` / `兵种<ID>`，名称只用于展示。
- 解析器必须拒绝未知单位、非法等级、非法数量和重复或冲突字段。
- UI 粘贴后先展示归一化摘要，再允许开局。
- 每次运行保存原始赛程代码、归一化配置、配置 hash、运行时间和结果摘要。
- 首期不允许经济字段进入赛程代码。场地费由规则计算，不由代码指定。

## 推荐架构

### 分层

- Arena Panel UI：正式竞技场面板，承载 `定制赛` tab、赛程代码、阵容编辑和开局确认。
- Custom Match Adapter：把 UI 配置转换成规范 roster、规则和运行请求，计算场地费，保存赛程代码。
- Battle Kernel：单位生成、站位、死亡观察、胜负判定、超时、中止。现阶段由 `ArenaCalibrationService` 承担。
- Calibration Layer：批量 manifest、JSONL 结果、分析报告、下一批规划。继续保持无人值守标定用途。
- Casino Layer：赔率、下注、奖励、经济平衡。等标定和定制赛稳定后再接入。

### P1 已落地路径

1. 在竞技场面板内新增 `定制赛` tab 和一张低改动入口卡，参考方案 A。
2. 新增赛程代码 parser / serializer，并为其补单元测试。
3. 将 `mvm` 赛程代码转换成一条 `arena-calibration.case-manifest.v1` case。
4. 在 UI 侧提供导入、复制、随机、摘要显示和场地费估算。
5. P1 阶段点击 `生成赛程` 时只发送 harness 可验证的 debug 消息，不调用正式竞技场 `enter`，也不调用 `arena_calibration startBatch`。

这条路径固定了前端入口和配置契约，不需要立即改 AS2 战斗流程，也不把未定稿的后台运行方式提前写死。

### P2 已落地路径

P2 已从 `生成赛程` 进入真实 `开始委托` 后台链路，优先覆盖 `mvm` 单局：

- Web 面板提交 inline single-case，不直接接触本地 manifest 路径。
- C# `ArenaCalibrationTask.startSingle` 负责规范化、冻结 manifest、运行、状态查询、中止和终态通知。
- P2 明确短期继续写 `logs/arena-calibration/`；P3b 已把定制赛 single-case 拆到 `logs/arena-custom/`。
- Web `custom_result` 回开后进入独立结算页，显示胜负、帧数、耗时、双方剩余血量、赛程代码和 resultPath；玩家确认后返回定制赛配置。
- AS2 no-player 标定场景使用动态交战热点虚拟镜头：最近交战对优先，活跃质心兜底，死亡/亡语 pending 单位继续参与热点；`HorizontalScroller.switchFollowTo` 的永久跟随语义已修正为同步更新默认跟随目标。
- harness 覆盖 `custom_start` / `closePanel` / `custom_result` 回开 / 独立结算页 / 确认返回；`custom_status` 保留为诊断查询。C# xUnit 覆盖 inline case、panel 委托和结算回开 initData。

### P3a/P3b 已落地路径

P3a/P3b 覆盖二级 `mvm` 阵容编辑器、预设组合和产品化日志，不触碰 `pve`：

- P3a：定制赛入口卡只保留当前对阵、状态、场地费、编辑配置和委托确认；赛程代码导入/复制、待标定预设、随机抽取和阵容工作台迁入三层编辑页，蓝/红 roster 可添加、删除、改等级、改数量；单方阵容页的单位浏览器从 `arena-unit-catalog.js` 搜索 `ID/name/spritename`。
- P3a：`arena-unit-catalog.js` 从 `data/units/units.json` 全量派生，不再用 `is_hostile` 阻断暴露；非敌对单位只在 UI 中标记，便于复现过去修改器直读全单位的斗兽测试流程。
- P3 UI/UX 打磨：入口卡按方案 A/C 的产品路径重排，当前对阵成为主体，赛程代码/预设/导入/复制移入配置总览；确认态改为独立确认摘要，避免在 1024x576 固定画布内和配置内容重叠。
- P3 UI/UX 打磨：三层编辑页补充单侧阵容编辑、添加目标切换、敌对/非敌对过滤、单侧清空、数量步进、单侧随机组合、本地保存/读取和红蓝交换，降低测试玩家从全量单位目录组队与复测位置因素的操作成本。
- P3 UI/UX 修正：入口卡内 `调整蓝方` / `调整红方` 会带目标阵营进入单方阵容编辑页，不再只是打开编辑器。
- P3a：怪物图标资产仍未储备，UI 明确使用 `u<ID>` 占位符；后续真实图标只需替换占位渲染，不改变赛程代码。
- P3a：点击主按钮先进入确认区，确认后才发 `custom_start`。
- P3b：预设组合从 `data/arena/meta_teams.json` 派生到独立 `arena-custom-presets.js`，默认覆盖 1969 条可落入当前单侧 20 体限制的关卡元战队；`ArenaCustomPresetsMeta.skippedCount` 记录超限组合数量。
- P3b：`ArenaCalibrationTask.startSingle` 根据 frozen manifest 的 `planner.name == "arena-custom-match"` 写入 `logs/arena-custom/`；`startBatch` 标定仍写 `logs/arena-calibration/`。
- P3b：`launcher/build.ps1` 派生 `arena-unit-catalog.js` 和 `arena-custom-presets.js`，并把 unit catalog、presets、match-code、arena panel 纳入 Web runtime asset 检查。

## 结果与反馈

定制赛不要求玩家填写结构化报告。工程侧建议自动记录最小数据：

- 赛程代码。
- 归一化 roster。
- 模式、seed、timeout、rules。
- 场地费计算结果和是否实际扣费。
- 胜负、帧数、耗时、存活单位摘要。
- 错误、超时、中止状态。
- 本地版本号或构建标识。

这些数据足够用于开发者回看问题，也不干扰玩家在群内用自然语言反馈“哪个组合离谱”“哪个怪物表现不符合印象”。

## 风险和注意点

- 不要把 `hp == 0` 当成最终死亡。原版亡语、血腥死、自爆和素材帧依赖仍可能影响战斗结果，定制赛应等待原死亡流程完成或由内核确认生命周期结束。
- 配置 seed 首期只能保证随机选怪复现。Flash 侧战斗随机源若未统一注入 seed，不能承诺完全确定性回放。
- `pve` 模式结果受玩家当前装备、技能、操作、难度和存档影响，应与 `mvm` 标定结果分表或分 schema。
- 单位 ID 是唯一复现依据，展示名称不是。
- 定制赛可以收场地费，但不能把赔率、下注和返奖提前混入。未来接赌场时也不能反向依赖测试用自由配置。
- UI 放入正式竞技场面板后，玩家会把它视为正式玩法，首版必须明确费用、无掉落、无经验和观战/参战规则。
