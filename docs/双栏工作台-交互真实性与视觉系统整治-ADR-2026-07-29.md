## 0. 决策摘要

现在已经到了应当先写 ADR、再开始下一轮施工的阶段。

这轮问题不是一组互不相关的“美化建议”，而是五类跨页面、跨层重复出现的系统性缺陷：

1. **界面没有如实投影当前能力**：可见按钮会静默无效，隐藏属性与实际可见性不一致，帮助入口和业务能力被玩家误认为有关联；
2. **用户所选对象、当前浏览对象、权威写入源混在一起**：候选数量、候选详情、候选调制和左栏来源标记缺少统一语义；
3. **决策区与导航栈没有稳定合同**：唯一主 CTA 会滚出视野，Esc 会跨层跳转，空态、错误态、不可执行态没有给出符合直觉的下一步；
4. **整备信息架构跨入口漂移**：技能等装备相关能力散落在刘海“游戏”行和 Character Build 直达按钮中，历史共同分类、现代 owner 边界与右侧常驻入口没有形成一致合同；
5. **视觉与动效规范部分停留在文档层**：布局 profile、颜色 token、字号下限、滚动条、named layer 和 reduced-motion 在生产 feature 中仍有明显 drift。

本轮采用以下总决策：

- **先修交互真实性，再做视觉统一**。任何可见控件必须真实可用，或以可读原因明确禁用；禁止静默 no-op。
- **接通现有能力，不再引入一套 UI 框架**。可复用 UI 边界仍只新增 Inventory header 状态投影与 `DualPaneShell` 封闭 profile；整备导航只扩展 feature-local 菜单呈现和 exact Character Build 关闭后固定目标意图，不建设通用导航 registry / DSL。
- **复用现役 primitive**：`HelpAction`、`ChoiceGroup`、`QuantityControl`、`PanelTooltip`、`CommitBar`、`FocusScope` 和现有 Equipment Tuning inventory source 能力优先。
- **把“浏览焦点、用户选择、权威来源、动作目标”分型**，不再用一个模糊 `item` 或 `_build` 是否存在推断行为。
- **主 CTA 永不进入内容滚动层**；阻断原因保持正文对比度，禁用态只压低控件能量，不把“为什么不能做”一起淡化。
- **把装备、战备箱、装备调制、技能、材料、情报统一为“整备”信息架构**。刘海分组与 Character Build 的整备菜单共享同一成员、命名和顺序；只统一玩家入口，不抹平同实例 view 与跨 owner panel 的生命周期差异。
- **右侧常驻 HUD 的条件槽只承担上下文说明、可操作通知或事务决策之一**。它不复制六项整备导航，也不与任务通知、SafeExit 共用时同时争夺命中区。
- **颜色、字号和动效采用触碰模块清零 + 总债务只降不升的 ratchet**，不把 1332 处存量色值和 P0 交互修复塞进一个巨型改动。
- **K3 最高思考强度完整异构对抗是本 ADR 的接受门**。只读审阅完成、逐条由主线复核并裁决后，文档才能从“候选”转为“已接受”。

## 1. 范围与非目标

### 1.1 本轮覆盖

- Character Build、Storage、Stats 与嵌入式/独立 Equipment Tuning；
- KShop、NPC Shop、Crafting、Loot、Skills 中采用工作台语言的页面；
- Native `NotchWidget`、fallback `NotchOverlay` 的“游戏 / 整备”分组、右侧 `RightContextWidget` 条件槽，以及 Host 固定整备导航意图到工作台的入口一致性；
- `DualPaneShell`、header action、EntityTile、HelpAction、QuantityControl、CommitBar、SecondaryPage、PanelTooltip；
- 工作台 CSS token、profile、排版、颜色、滚动条、状态层、动效层与 visual atlas；
- 与候选计数、候选 tooltip、候选调制、Ctrl+滚轮相关的 AS2 / Host 接缝；
- 真实 WebView2 内的焦点、缩放、Esc、滚动与玩家文案。

### 1.2 本轮不做

- 不新建动态组件注册表、action DSL、统一领域状态机或万能卡片；
- 不新建可注册的全局 NavigationRegistry、任意 `panelName/initData` 路由协议、最近使用入口、split button 或多级 mega-menu；
- 不把所有领域 preview/reconcile 合并成一个可配置大组件；
- 不一次性重写 `skins.css`、重排全部 cascade、拆完 legacy class 并同时改任务流；
- 不为了减少字面量给每个独特色值、间距或 z-index 都造 token；
- 不把帮助、tooltip、close、preview 变成业务 capability；
- 不把右侧常驻 HUD 条件槽改造成第三套整备导航；不让 hover 才出现的子菜单承担唯一入口；
- 不修改 Flash 资产或 SWF；若后续跨层施工触及 `.as`，仍须遵守 UTF-8 with BOM 和 Flash CS6 fresh trace 验证要求；
- 不把本 ADR 称作功能完成、编译通过、部署完成或 `standard_entry_verified`。

因此施工前第一道门不是“开始大规模重构”，而是先恢复可相信的基线：修正共享 action hook 与 harness 合同，让后续回归能区分真实失败和测试漂移。

### 2.2 “假按钮”的确切根因

`inventory-workbench.js` 已按 view 给 storage action group 设置 `hidden`，但 `inventory.css` 的 `.inventory-workbench-mode-actions { display:flex; }` 覆盖了浏览器 `[hidden] { display:none; }` 的表现。结果是：

- Stats 中出现本应隐藏的“返回构筑”“装备调制”；
- Character Build 中出现本应隐藏的同一组按钮；
- handler 又正确拒绝当前 view 下无意义的请求，于是玩家看到“能点、没反应”的假按钮；
- “返回构筑”还与同屏箭头返回形成重复语义。

这不是单个按钮漏绑事件，而是一个必须上升为共享约束的问题：**语义 hidden 必须在 computed style、命中区和可聚焦性上同时为真**。只断言 DOM attribute 存在不够。

### 2.3 视觉与动效债务快照

对 `launcher/web/css/workbench/*.css` 的当前扫描快照：

- 裸颜色共 1332 处：1046 个 hex，286 个字面量 `rgb/rgba`；
- 分布最重：`skins.css` 460、`skills.css` 203、`equipment-tuning.css` 187、`inventory.css` 165、`core.css` 134；
- `9px` 共 148 处，其中存在长中文、错误原因和主标签错误降级；
- 多个 feature 重复定义滚动条，代码中只有局部规则移除 Chromium 箭头；主线人工查看的反馈截图也出现白色系统滚动条，但该截图不作为仓库长期证据；
- motion token 已存在，但仍有 `.08s`、`.1s`、`.12s`、`.25s`、`.28s`、`.75s`、`1.8s` 等野生时长；
- reduced-motion 同时使用 `.001s`、`.001ms` 和 `none`，壳外 tooltip 与 JS RAF 还没有统一策略；
- `components.css` 的 SecondaryPage 使用 `opacity/transform/visibility`，KShop/NPC 的 unlayered `display:none/display:grid` 会让退场直接消失，实际绕过共享 structural motion。

这些数字是排序和 ratchet 的基线，不构成“一次性全部替换”的授权。

### 2.4 布局与 atlas 的证据边界

现行 canonical doc 定义了六种语义 profile，但生产实现仍不完整：

- `DualPaneShell` 还不接收 `profile`；
- 目前只有 Loot 写入 `data-profile="transfer-pair"`；
- 其余双栏比例仍主要散落在 feature CSS；
- 现役 48 场景 atlas 使用同一套合成 shop/catalog DOM，并在三个 16:9 viewport 中切换 density、focus、reduced-motion 和 SecondaryPage；
- 它能证明共享 primitive 的一组组合，不足以证明 Skills、Tuning、Storage、Character Build、Loot 等真实 DOM 和真实 overflow fixture。

本轮不否定 atlas，而是补足证据分层：共享 atlas 继续存在，profile 和领域特例必须增加真实 feature fixture / harness。

### 2.5 整备信息架构与现役路由真值

旧 Flash 的稳定心智不是某个永远不变的页签顺序，而是“装备相关功能共处一个 Hub、平级一步切换”：

- 旧版 Hub 已有物品装备、个人信息、技能三个实装成员和一个“未实装”占位；装备与技能从旧版起就是一步平级切换；
- 最新 `flashswf/UI/物品与技能相关界面/LIBRARY/新版物品栏界面.xml` 才进一步把材料、情报纳入同一时间轴，五个入口仍全部一步直达；个人信息的相对位置同时发生变化，说明不能把某个历史顺序当协议；
- 主 XFL 中承载后勤战备箱的通用仓库界面是物品栏的 sibling 窗口，不是上述 Hub 页签；但 `InventoryIcon.quickMoveToTarget()` 明确支持背包与仓库/战备箱双向搬运，属于强邻接工作流；
- 现代“装备调制”统一承接旧强化、强化度转换和插件改装能力；旧组件原本嵌在物品栏帧中，背包装备可拖入并热切。它有强邻接依据，但不是旧版顶级页签。

因此本轮复刻的是**共同分类、熟悉命名和一步直达**，不是把旧 Flash owner、帧层级和顺序原样搬到 Web。

现役实现又有四个必须先承认的差异：

1. Character Build **Build view** 的意图集合是 `storage | stats | skills | help | close`；Stats 另有 `back-build`。截图中的额外“装备调制”来自 §2.2 的 hidden 泄漏，不是合法基线；
2. Build → Storage 是同一 Workbench instance 的局部 view 切换；Build 分支当前只接受 `storage`，不能直接进入独立 `tuning`；
3. Build → Skills 已有 exact-instance close/finalize/visual-retire/coordinator-settled 的严格交接；
4. Materials 在 Character authority 仍绑定时会明确拒绝，Intelligence 只有 Native HUD → Host 的固定生产入口；二者目前都不是可从 Web header 安全直达的目标。

刘海实现目前也把战备箱、情报、材料、技能与战队、平板、商城全部塞在“游戏”行。Native `NotchWidget` 已有“游戏 / 辅助 / 系统”分组，legacy `NotchOverlay` 仍是扁平工具栏；下一轮必须让两条渲染路径消费同一整备分类真值，不能只改截图所对应的一条路径。

## 3. 用户反馈逐项裁决

### F1：进入具体装备分类前看不到背包各分类数量

**裁决：接受，属于信息架构缺口。**

当前 `CharacterBuildService.as` 只在选择目标槽后扫描背包并返回候选，没有投影始终可见的 category facet counts。玩家为了回答“我有没有这类装备”必须反复进入“刀 / 长枪 / 手枪”等目标，操作成本过高。

决策：

- Character Build 初始状态应能显示与构筑槽分类一致的候选数量；
- 数量是权威快照的只读 facet，不是 Web 本地按名称猜 taxonomy；
- `0` 也必须显示，不能用“没有角标”同时表示未知和零；
- facet counts 与当前筛选、权限和候选口径一致，写后随 snapshot 刷新；
- 计数只做 `CountBadge` 的 CSS/data slot，不新建 JS 组件体系。

### F2：角色构筑候选没有 tooltip，必须去收纳查数值

**裁决：接受，属于跨页面信息断裂。**

Character Build 候选当前只绘制图标、名称与少量 delta，没有接入共享 `PanelTooltip`。但候选 payload 已携带 exact inventory source，现有 Inventory Workbench 也已有 scoped async tooltip 样板。

决策：

- 为 Character Build 增加领域 tooltip adapter / endpoint；
- Web 直接复用现役 `PanelTooltip.createScope().bindAsyncHover(...)`；
- pointer 与键盘 focus 信息等价；
- tooltip key 必须含 exact candidate identity 和会话 fence，迟到结果不得复活 detached binding；
- tooltip 只负责说明，不持有选择、装备或调制 capability。

### F3：只能调制已装备物，不能调制当前候选

**裁决：接受，属于现有能力未接通。**

共享 Equipment Tuning View 已支持 `inventory` 与 `loadout` 两种 source；Character Build adapter 却硬编码 `sourceKind:"loadout"`。候选 payload 已含 `containerId / slot / expectedLease`，因此不需要玩家先穿上再调制。

决策：

- 选中可调制候选时，Character Build 将 exact inventory ref 交给现有 Tuning View；
- 不新建通用“来源选择总线”；
- 调制写入后必须刷新 exact candidate lease、候选 snapshot、tooltip cache 和当前选择；
- 候选已移动、过期或被装备时 fail closed，并以玩家语言解释，不对 stale intent 自动重放；
- 返回后恢复同一候选的语义 focus key；实体已不存在时使用明确的相邻回退规则。

### F4：不打开“调制说明”似乎不能拆装配件

**裁决：症状成立，因果推断不成立。**

代码中配件安装、替换、卸下并未由 info panel 解锁；帮助只负责解释。真实问题是：

- “安全 / 快速”命名不能表达提交行为；
- 默认模式下点击会生成 preview，但唯一确认按钮位于可滚的 `.equipment-tuning-preview` 内；
- preview 最大高度 172px，材料和差异较多时 CTA 会滚出视野；
- 缺少明确的“已生成预览，请在此确认”注意力迁移；
- 玩家于是把“打开说明后才成功”误认为能力门。

决策：

- 帮助打开与否永远不得改变 capability，并加入负向断言；
- “安全 / 快速”改为更接近行为的“逐次确认 / 单件快捷”；
- 旁边常驻一句短说明：“批量、连锁与卸下全部始终需要确认”；
- preview detail 与固定 `CommitBar` 分离，主 CTA 不进入滚动层；
- 生成 preview 后更新状态、把确认区带入可见范围并迁移语义 focus，但不抢走正在编辑的输入焦点；
- 不为此新造万能 `StagedCommandBar`。

### F5 / F6：Stats 与 Character Build 顶栏出现重复、无作用按钮

**裁决：P0，属于交互真实性缺陷。**

根因见 §2.2。决策：

- 先加 `.workbench-shell [hidden]` 等价的共享不变量，确保 hidden 在 computed style 上为 `display:none`；
- header action 状态由一个窄的 `InventoryWorkbenchHeaderProjection` 纯投影生成；
- 输入仅限 `{view, statsMode, returnTarget, buildAvailable, tuningAvailable, tuningState, busy, preparationAvailability}`；其中 `tuningAvailable` 是当前实例能否进入 tuning 的窄 capability，`preparationAvailability` 是 §5.6 固定目标键的窄状态记录，不把领域 profile、handler 或任意 destination descriptor 交给 presenter；
- 输出每个 action 的 `visible / disabled / pressed / label / reason`；整备菜单项额外输出 `current / destinationKind`；
- handler、领域路由与业务 authority 继续由 facade 持有；
- 同一语义不允许同时出现文字按钮与图标返回；
- 每个 view 的 header action 集合必须由状态表完整枚举并自动验证。

该状态表是 feature 内封闭的字面量映射，不是可注册 descriptor、action DSL 或跨面板 registry。

### F7：“安全 / 快速”不可理解，“卸下全部”仍需二次确认

**裁决：接受，属于模式命名和反馈错误。**

“快速”当前只适用于一部分单件 install / replace / detach；批量、cascade、enhance、conversion、“卸下全部”仍应预览确认。玩家按日常语言会把“快速”理解为所有动作立即执行，当前命名违反直觉。

决策：

- 使用 `ChoiceGroup` 承担选择机械，领域继续决定哪些 operation 可 quick commit；
- 标签采用“逐次确认 / 单件快捷”；
- 独立 battlebox 与 Character Build 嵌入态都投影同一个 confirmation mode 与同一份持久偏好；嵌入态在自身 PaneChrome/决策区呈现 ChoiceGroup，不把更多动作挤进全局 header；
- 常驻短说明必须直接位于选择器附近，详细矩阵放 HelpAction；
- 选择器不改变领域安全边界；
- “卸下全部”始终确认不是异常，必须在触发后立即显式生成并展示确认区；
- busy 期间选择器 visibly disabled，原因仍可读。

### F8：Ctrl+滚轮会改变 UI 大小，且没有提示或操作锁

**裁决：接受，属于 overlay/Host 输入不变量。**

`WebOverlayForm` 当前没有冻结用户浏览器缩放。该问题不能靠每个页面各绑一次 `wheel` listener 解决。

决策：

- 在 WebView2 / overlay 根层一次性禁止浏览器 Ctrl+滚轮缩放，并守住 `ZoomFactor`；
- 保留普通滚轮、工作台滚动区、纸娃娃 inspection wheel 和系统 DPI / `PanelScale` 正常路径；
- Ctrl+滚轮后 CSS viewport、WebView2 ZoomFactor 和命中坐标必须不变；
- 如需提示，只在首次拦截时给短提示；帮助页补充说明，但提示不是安全边界；
- Host 侧增加自动断言，真实 WebView2 再做人工 smoke。

### F9：装备相关入口分散，刘海“游戏”行过长，Character Build header 又同时承担跨页跳转

**裁决：接受，但不是把“收纳 / 技能配置”两个按钮机械藏进下拉。**

如果修复 §2.2 后只剩两个跨页动作，下拉会把两个一键入口都变成两步，收益不足。用户进一步确认旧 Flash 装备界面本就包含技能，而本轮目标还包括战备箱、独立调制、材料与情报；当六个目标都有真实路由后，一个单层、可见标签为“整备”的 section switcher 才成立。

canonical 成员与顺序固定为：

```text
装备 → 战备箱 → 装备调制 → 技能 → 材料 → 情报
```

顺序先放穿戴、物品来源和改造，再放能力配置与资料类页面；它不声称复刻某一版 Flash 的具体排列。外部统一短标签为“装备”，页面标题可以继续使用“角色构筑”；菜单当前项写作“装备 · 角色构筑”并标记“当前”。

刘海分组调整为：

```text
游戏：战队 / 平板 / 商城
整备：装备 / 战备箱 / 装备调制 / 技能 / 材料 / 情报
辅助：点歌机 / 地图开关 / 修改器 / 帮助
系统：全屏 / 日志 / 其他
```

Character Build 的目标 header 为：

```text
角色构筑                         [整备 ▾] [个人信息] [?] [×]
```

菜单为单层固定 allowlist：

```text
装备 · 角色构筑        当前
战备箱与背包
背包装备调制
技能配置
材料
情报
```

“装备 · 角色构筑”当前项使用 `aria-current="page" + aria-disabled="true"`，可聚焦并显示“当前”，激活零业务调用；它是导航定位状态，不是 §5.1 所禁止的可点外观 + silent no-op。“个人信息”保留一级直达。它虽然也曾在旧 Flash Hub 中，但现役实现是当前 Character session 的本地 SecondaryPage，使用频率与返回语义都不同；这是有意的现代化差异。Help 和 Close 永远直接可见。菜单中的“背包装备调制”与候选/槽位上的“调制当前装备”是不同动作，禁止共用模糊的“调制”文案。

生产菜单不能显示尚未接通的“未来项”冒充完整功能。施工期间可在 dev fixture 以 capability gate 验证缺失目标；正式启用六项菜单前，材料与情报必须完成 §5.6 的 exact handoff。运行时暂时 busy/reconcile 与结构上尚未实现是两种状态：前者保留菜单项并显示阻断原因，后者在生产不可见。

## 4. 沿同类问题继续发现的真实缺陷

### 4.1 Esc 消费链不完整

嵌入 Character Build 的 tuning 会先让“调制说明”消费 Esc；独立 Inventory Workbench tuning 退出路径没有调用同一个 info panel Esc consumer。结果可能是说明仍开着，页面却退出 tuning；若 `_build` 曾实例化，还可能直接跳回构筑。

**约束**：Esc 必须由显式的 view / overlay stack 决定，不得由“某对象是否曾创建”推断返回目标。

统一顺序：

1. 输入草稿、modal、inspection 等最内层瞬态；
2. tuning info；
3. 当前 tuning；
4. storage；
5. build；
6. panel / game。

一次只消费一层。普通右上 `×` 与 native backdrop 始终执行当前 owner 的普通关闭，不伪装成“返回上一页”。Storage 只有在显式从 Build 进入时才返回 Build；独立打开时关闭到游戏。Crafting 内嵌整理背包继续遵守其既有“显式返回合成、普通关闭关闭 crafting owner”合同。

### 4.2 权威操作源没有持续可见标记

独立 tuning 会自动选择或点击选择左侧背包装备，但除 conversion 等个别场景外，卡片没有持久、可访问的 current source 标记。玩家看得到高亮变化，却无法确认右侧操作究竟绑定哪一件。

**约束**：

- browse focus、selected candidate、authority source、action target 是四个不同状态；
- source 必须同时有视觉轮廓、可见短标签和 ARIA current/selected 语义；
- debug 信息可含 exact ref，玩家层只显示名称、位置和当前操作；
- source stale 时撤销可提交性，不保留“看似仍选中”的旧高亮。

### 4.3 候选空态混淆四种含义

Character Build 右栏当前把“未选择目标”“正在加载”“确实无候选”“请求失败”压成同一条“选择一个装备或药剂槽”。

**约束**：最少区分：

| 状态 | 玩家文案 | 下一步 |
|------|----------|--------|
| `unselected` | 先选择左侧槽位 | 指向可选择区域 |
| `loading` | 正在查找可用装备 | 禁止旧候选提交 |
| `empty` | 此槽位暂无可用候选 | 提供收纳/获得来源提示 |
| `error` | 暂时无法读取候选 | 提供安全重试 |
| `ready` | 候选与数量已同步 | 正常浏览 |

空态统一的是语义合同 `{kind, statement, nextStep}`，不是万能状态组件。

### 4.4 Crafting 数量控件重建导致丢焦点，帮助与实物不一致

Crafting 当前在每次核算后清空详情并重建 `− / output / + / 最大`，点击后 DOM identity 和键盘焦点丢失；帮助却声称存在数字直输，实际只有 `<output>`。唯一确认按钮还与材料详情一起放在 `.crafting-detail-body` 的滚动层内。

**决策**：

- 迁移到现役 `QuantityControl`，复用节点并保持草稿、焦点与滚动；
- 帮助文案必须与实际输入能力一致；
- 材料/状态详情可滚，固定 `CommitBar` 不滚；
- `data-title` 伪 tooltip 必须同时响应 `:hover` 与 `:focus-visible`，中文说明不得继续使用 9px；
- 一次合法 intent 对应一次 preview，旧回包不得重建控件或覆盖新草稿。

### 4.5 “可查看”与“可执行”被混为 disabled

共享 EntityTile 的 disabled 会移除 tabindex 并阻断 activation：

- NPC 锁定商品因此无法由键盘查看“为什么锁定”；
- Tuning / Character 的 blocked 卡又可能仍可点击，但点击静默 no-op；
- Tuning 的 `.equipment-tuning-candidate.blocked` 会把整卡 opacity 降至 `.42`，恰好把卡内阻断原因也压暗；Character Build blocked 卡没有这条 opacity 问题，但仍存在激活静默 no-op。

**约束**：

- `inspectable` 与 `actionable` 分离；
- blocked 实体通常仍可聚焦、查看和听到原因；
- blocked activation 只解释原因，不发送业务请求；
- 真正 interaction disabled / busy 只禁用 CTA；
- 阻断原因保持正文级对比度，不能继承整卡低 opacity；
- 自动门检查 blocked reason 的 computed opacity / contrast 和键盘可达性。

### 4.6 KShop 切到物品管理后，帮助与关闭语义仍停留在商城

KShop 的 HelpAction 和 close aria 在创建时固定；`showInventoryMode()` 只更新标题、slots 和 skin。切换后玩家看到的页面与帮助、关闭读法不一致。

**约束**：同壳子路由切换必须原子更新 title、help spec、close label、action projection 和 focus return target；不能只换 body。

### 4.7 Loot 缺少 HelpAction，并泄漏技术词

Loot 的拖拽、双击、Ctrl+单击、Ctrl+A 主要藏在 ARIA 中，鼠标用户没有可见入口；正文还出现 `TRANSFER-PAIR / MAP CHEST`、“权威瞬态容器”“权威版本”“等待权威快照”“重放”“水位”等实现词。

**决策**：

- 补唯一 HelpAction 和常驻短提示；
- 保留玩家需要的动作、数量、来源和恢复动作，删除 revision 等无决策价值指标；
- “权威 / 对账 / 重放 / lease / token / revision / epoch / wire”等进入玩家文案静态词表门；
- “重新同步 / 重新核对”可作为玩家恢复语言，但领域 handler 仍保持不同语义，不抽 `RetrySyncAction`。

### 4.8 帮助入口实现分裂

Crafting、Inventory、KShop 已使用 `HelpAction`；Skills 自绘 `?`，NPC 有自己的 guide / secondary page，Loot 缺失。当前 `HelpAction` 还缺 harness 需要的标准 action hook。

**决策**：

- `HelpAction` 增加稳定 `data-header-action="help"`；
- Skills、Loot 和适合的 NPC 主入口迁移到现役 HelpAction；
- 领域正文继续分别维护；
- 暂不造 onboarding / tour 引擎；
- 只有 KShop 与 Storage 出现第二、第三个真实“一次性提醒”消费者后，才考虑仅负责 versioned localStorage 的小型 `GuideOnce` helper。

### 4.9 共享 structural motion 被 feature cascade 绕过

SecondaryPage 的共享 210ms 入退场依赖 `visibility` 延迟，但 KShop / NPC 的 unlayered `display:none / display:grid` 优先，退出时立即 `display:none`。Skills / Entity 的 unlayered focus 规则也可能覆盖共享 focus ring。

**约束**：motion 和 focus 统一必须以 computed style / 行为断言为准，不能以“token 已定义、selector 已存在”判定完成。

### 4.10 SecondaryPage 露出已经 inert 的底层顶栏

`SecondaryPage` 会把宿主中除自身和 modal portal 外的兄弟设为 `inert + aria-hidden`。KShop 结算、NPC 结算/帮助却只从 48px header 下沿覆盖 body，导致底层 Help、模式、密度和 `×` 仍保持“可操作外观”，实际已经不能点击或聚焦。现役视觉 fixture 还把这种构图固化成了看似正常的截图。

**约束**：

- SecondaryPage 取得焦点所有权时，底层不可操作区域不能继续呈现 enabled control 外观；
- 优先覆盖、隐藏或明确弱化底层 action strip，并在 SecondaryPage 内投影必要的 Back / Help / 普通 Close；
- 如果设计决定保留外露 action，它就不能属于 inert underlay，且必须真实可用；
- Back、Esc、native backdrop 与普通 Close 继续保留各自语义，不为了省按钮合并成一个动作。

### 4.11 OwnedInventoryPane 的父级 disabled 没有如实投影到子控件

`OwnedInventoryPane.setDisabled()` 只更新根状态；Inventory、NPC Organizer、Loot Organizer 的多个 EntityTile 仍以 `disabled:false` 和“点击转移”文案呈现，handler 在 busy / refreshRequired / returning 时却直接拒绝。Loot 的丢弃按钮也存在同类锁投影缺口。

**约束**：

- Pane、EntityTile 和 nested action 从同一份局部 `{inspectable, actionable, reason}` 投影消费状态；
- 祖先 `aria-disabled` 不能代替子控件的视觉、ARIA 和动作真实性；
- blocked 卡可继续查看详情，但必须移除转移/丢弃 affordance，激活只解释原因且业务调用数为零；
- Inventory、NPC Organizer、Loot Organizer 共用状态语言，不因此抽一个跨领域状态机。

### 4.12 Equipment Tuning 的锁状态没有覆盖所有控制族

强化数字框、步进、range、等级 marks 和“升至上限”没有把 `_needsReconcile` 纳入 disabled；tabs 与已安装阶级入口也没有完整覆盖 detaching、refresh retry 等锁。handler 随后静默 return，形成另一组可见 no-op。

**约束**：

- Tuning View 形成一个领域本地 `interactionLocked / reason` 投影；
- tabs、已安装阶级、强化 input/stepper/range/marks/cap 都消费同一投影；
- `needsReconcile` 时只保留“重新核对”主动作；
- detaching / refresh retry 时其他操作隐藏或 disabled，并显示“先完成同步”；
- 这是 feature 内状态收敛，不新增共享组件。

### 4.13 右侧常驻 HUD 的条件槽缺少稳定角色

`RightContextWidget` 顶部已有“地图 / 任务 / 装备 / 设置 / 暂停 / 退出”六入口；其下方同一几何槽位目前会承担工具 hover 文案、任务通知，并为独立 `SafeExitPanelWidget` 预留“存盘中 / 存盘成功 / 取消 / 退出游戏”事务区。装备 hover 时只重复显示“装备”，信息增量接近零；若直接把六项整备按钮再塞入该槽，又会形成第三套导航、扩大 GDI hit-test/键盘模型，并与通知和 SafeExit 争夺同一位置。

**约束**：

- 条件槽在任一时刻只允许一种角色：`contextHint | actionableNotice | transactionDecision`；
- 优先级固定为 `transactionDecision > actionableNotice > contextHint > hidden`，高优先级出现时低优先级不保留 hitbox；
- `NativeHudOverlay`（或同一组合 owner）必须持有一个封闭 `RightContextSlotOwner` 仲裁结果并同时投影给 `RightContextWidget` 与 `SafeExitPanelWidget`；现役 `_externalStatusSlotActive` 单一布尔值不能作为最终合同，因为它只保留高度、不会自动抑制 notice 绘制与命中；
- `contextHint` 只提供一行有信息增量的说明，例如装备入口使用“打开角色构筑；其他整备功能在刘海或装备页”，不重复按钮标签；
- `actionableNotice` 最多一个明确下一步，例如任务可交付；不得扩成任意动作列表；
- `transactionDecision` 由 exact SafeExit owner 持有，状态与取消/退出/重试按钮同一行，其他 widget 不复制命中区；
- 不在此槽复制完整整备导航。游戏态任意整备入口由刘海“整备”行承担，面板内相邻跳转由 Character Build 的“整备”菜单承担；
- pointer hover 与可访问名称/测试探针表达同一说明；不得让只有 hover 才出现的文字成为理解顶栏按钮的必要条件。

## 5. 交互真实性架构约束

### 5.1 可见控件合同

任一玩家可见 control 必须满足以下二选一：

1. 激活后产生可观察、与文案一致的效果；或
2. visibly disabled，并在同一上下文给出可读原因。

禁止：

- 可点外观 + handler 静默 return；
- `hidden` attribute 存在但 computed display 仍可见；
- 透明或被遮挡控件仍保留 hitbox / tab stop；
- 帮助、tooltip 或 hover 成为业务动作的隐藏前置；
- disabled 同时隐藏阻断原因。

自动验证至少检查：

- computed `display / visibility / opacity / pointer-events`；
- `getBoundingClientRect()` 是否仍形成命中区；
- Tab 序列和程序化 focus；
- pointer、Enter、Space 的等价结果；
- 可见 control 的 action trace 或 disabled reason。

### 5.2 四种对象身份

| 身份 | 含义 | 允许影响 |
|------|------|----------|
| `browseFocus` | 当前键盘/指针浏览位置 | tooltip、焦点摘要 |
| `selection` | 玩家显式选中的候选或批量项 | 本地 preview intent |
| `authoritySource` | 当前权威操作精确绑定的 inventory/loadout ref | preview/commit envelope |
| `actionTarget` | 当前动作将影响的目标槽、容器或 operation | CTA 文案与结果 |

这四者可以指向同一实体，但不能因此合并字段。视觉上必须让玩家知道当前 source 和 target；协议上 inventory ref 与 loadout ref 始终分型。

### 5.3 帮助与能力分离

- `HelpAction` 只呈现说明；
- 打开、关闭、从未打开帮助，得到的业务 capability 必须完全相同；
- 帮助正文随 view 更新，但不发业务消息、不持久化“解锁态”；
- 隐含操作同时需要常驻短提示；不能把全部可发现性压力推给 modal。

### 5.4 决策区合同

- 每个决策面只有一个主 CTA；
- 主 CTA、当前状态和阻断原因放在不滚动的 CommitBar；
- 可滚层只放差异、材料、返还、历史和长说明；
- preview 生成后 CTA 必须进入视野，不能要求玩家猜测要向下滚；
- pending 时旧 preview 明确失效；
- unknown result 进入 reconcile，不自动重放写入；
- blocked reason 保持正文对比，CTA 自身才进入 disabled/busy 表现。

### 5.5 明确导航栈

每个 view change 记录：

- `viewId`；
- `origin`；
- `returnTarget`；
- `focusKey`；
- 是否有未提交 draft；
- 当前最上层 Esc owner。

Esc 按栈逐层消费；header `×`、native backdrop 和 Host 普通关闭不读取这个返回栈。不得再用 `_build` 是否非空、DOM 是否曾 mount 等实现偶然性决定玩家去向。

若“整备”popover 已打开，它临时成为最上层 Esc owner：第一次 Esc 只关闭菜单、阻止冒泡并把焦点还给触发器；下一次才进入输入草稿/modal/inspection → tuning info → tuning → storage → build → game 的既有顺序。进入 modal 或 SecondaryPage 时菜单必须预先关闭，因此两者不能同时声称最上层 owner。

### 5.6 整备导航：统一入口，不统一生命周期

#### 5.6.1 目标分型

| 目标 | 类型 | 必须采用的路径 | 禁止 |
|------|------|----------------|------|
| 装备 · 角色构筑 | 当前 Build view | `aria-current="page" + aria-disabled="true"`、可聚焦并显示“当前”，激活零业务命令 | 再发 `EQUIP_UI`；现役重点击会触发 `panel_esc` |
| 战备箱与背包 | 同 Workbench instance | `_build.prepareLeave()` 后切换 `storage`；保留 Character session、pause lease 与 exact instance | finalize Build、打开第二个 workbench |
| 背包装备调制 | 同 Workbench instance | `_build.prepareLeave()` 后直接建立/恢复 inventory scope 并切换 standalone `tuning` | 先假点 Storage 再模拟按钮；复用 loadout source |
| 技能配置 | 跨 owner | 继续使用现役 `requestClose("navigate_skills")` 严格交接 | `Panels.open("skills")`、乐观卸载 |
| 材料 | 跨 owner | 新增 exact-instance、固定目标 `navigate_materials` 关闭后意图；settled 后启动带 Host opaque requestId 的材料专用 opener，并等待 exact panel admission | 活动 Character authority 下直接 `RouteMaterialUi()`；把 `openMaterialUI` 发送成功当成目标已打开 |
| 情报 | 跨 owner | 新增 exact-instance、固定目标 `navigate_intelligence` 关闭后意图；settled 后使用 Host 固定生产 initData | Web 传任意 panel/initData；直接普通 `OpenPanel` |

Build → Storage/Tuning 是局部 view change，不进入 Host post-close intent。二者返回 Build 时保持同一 `panelInstanceId`、Character session 和 pause owner，不重新打开装备服务；显式从 Build 进入的 Storage 与 standalone Tuning 都显示唯一“返回构筑”，Esc 一次只退当前局部 view。独立从刘海打开的战备箱/调制仍普通关闭到游戏，不因 `_build` 曾存在而伪造返回。

若 Build 正处于“调制当前装备”的嵌入态，选择“背包装备调制”必须先 exact detach loadout source，再建立 inventory source；不得继承当前 selection、lease、preview、`_returnState` 或迟到回调。菜单中的 standalone tuning 始终表达“从背包选装备”，嵌入态始终表达“当前穿戴物”。

#### 5.6.2 跨 owner 固定目标意图

材料和情报复用 Skills 已验证的关闭屏障思想，但不抽通用 panel router：

1. Web 只能从固定 reason 集合发送 `navigate_skills | navigate_materials | navigate_intelligence`；
2. Host 在关闭屏障前复验 exact active/bound Character Build instance，只保存 `{exactWorkbenchInstance, enumTarget, lifecycleEpoch}`；
3. Character Build 完成本地 finalize；Host 等待 exact visual retire、AS2 detach/persistence proof、pause release 与 coordinator settled；
4. exact coordinator settled 时，Host 原子地把 armed close intent 转为 target-open wait / admission state，携带原 `exactWorkbenchInstance + generation + lifecycleEpoch` 并销毁 arm timer，再按固定 `switch(enumTarget)` 打开一次目标。异步目标必须先安装 target wait 再发命令，避免同步回包抢在 wait 之前；
5. Skills 保留 nonce/preflight 与既有 `SkillOpenTimeoutMs`；Materials 生成 Host opaque `openRequestId`，经 `openMaterialUI({openRequestId})` → `CraftingPanelService` 原样回显，只消费 exact wire `{task:"panel_request", panel:"crafting", source:"nativehud_materials", initData:{view:"materials"}, openRequestId}` 与对应 Host admission；该相关路径的顶层和 `initData` 都按封闭 shape 校验，`view` 错层、额外导航字段、错误 source/view/requestId 一律拒绝；Intelligence 使用 Host 内建 production initData，在 settled 后直接走 exact admission；
6. `CharacterBuildPreparationNavigationTimeoutMs` 只覆盖 arm → exact coordinator settled。超时原子清除 armed intent 和 arm timer，迟到 settled 零打开；它不观察 `panel_request`，也不复用为目标打开计时器。现役 Skills 正向 arm 尚无这层 timeout，本轮必须补齐；
7. settled 后 Skills 与 Materials 分别由 `SkillOpenTimeoutMs` 和新的 `CharacterBuildMaterialOpenTimeoutMs` 管理 target-open wait；迟到或 near-match `panel_request` 由 wait 的 generation / lifecycleEpoch 拒绝。Intelligence 是同步 exact admission，不安装或复用 arm timer；
8. competing intent、实例变化、visual-not-idle、detach/finalize 失败、目标 admission 拒绝或任一阶段超时都取消对应状态；迟到 callback 不得打开目标。若失败发生在 Build finalize / visual retire 前，则保留或恢复当前 Build 并按当前生产 header 的固定 action 恢复焦点；若 destructive close 已发生，则进入与目标打开失败相同的至多一次 Character Build 回滚，回滚也失败才停在游戏并给出可操作提示；
9. `returnFocusAction` 是封闭枚举：迁移期 parser 只接受 `skills | preparation-menu`。B4 至 B6 的旧 header 生产期，Host 仍只发 `skills`；B7 必须把 Build header 切换、Host 改发 `preparation-menu` 与 Web 固定 action 映射作为同一 rollout 单元。最终所有 Skills 返回与三目标失败回滚只投影 `preparation-menu`；Web 不能把值解释为 selector；
10. Materials/Intelligence 的 `×`、Esc 和 native backdrop 继续遵守自己的普通关闭语义。本轮不为它们新增“返回构筑”，也不把 Skills 已有的返回能力推广成通用跨面板返回栈。

Web 不得传 `panelName`、任意 `initData`、回调脚本或 return target。Host 不得复用 Crafting → Storage 的 `_returnTarget`，也不把 Storage/Tuning 纳入 post-close intent。这个边界是“Character Build 离开时的三目标白名单”，不是全局导航服务。

`WebOverlayForm` 的 workbench close envelope validator 只扩充上述三个 exact reason，并继续要求 exact `panelInstanceId` 与封闭 key shape；foreign instance、未知 reason、额外 target/initData 字段一律在 arm 前拒绝。三种 reason 只是 enum 编码，不授权 Web 选择任意目标。

材料的老 HUD 无 nonce 路径只可在**不存在 armed material intent，也不存在 material target-open wait**时继续普通 idle 打开；任一 material wait 存在时，missing nonce 请求必须拒绝、零打开并给出“正在打开材料”的可操作状态，不得旁路、消费或隐式 supersede 当前 intent。只有 Host 生成、AS2 原样回显、长度/字符合法且与当前 generation/lifecycleEpoch 完全一致的 requestId 才能完成相关导航。`TrySendGameCommand("openMaterialUI") == true` 只表示命令已投递，不表示 Crafting panel 已准入；target-open timeout、near-match、重复、错层/额外字段、错误 source/view 或 Host admission 失败都走 §5.6.2 的阶段化回滚/提示合同。若该回显触及 `.as`，必须同步协议 canonical doc、保持 UTF-8 with BOM，并完成 focused Flash fresh trace。

#### 5.6.3 Header 与菜单状态投影

修复 G0 后，菜单改造前的 Build exact-set 应先恢复为：

```text
storage | stats | skills | help | close
```

菜单启用后的最终 exact-set 为：

```text
preparation-menu | stats | help | close
```

Stats exact-set 保持：

```text
back-build | help | close
```

Stats、纸娃娃放大页或其他 SecondaryPage 取得 FocusScope 后，底层 `preparation-menu` 必须 hidden/inert，不得只保留可点击外观。Storage/Standalone Tuning 使用自己的局部 header projection，不复制“整备”菜单。

`InventoryWorkbenchHeaderProjection` 输入增加一个**固定键集合**的 `preparationAvailability`，只允许 `equipment / battlebox / tuning / skills / materials / intelligence`，每项投影 `{visible, disabled, reason}`；输出菜单项增加 `{current, destinationKind}`。canonical identity 使用 `battlebox`，只有 handler 内部把它映射为 Workbench `view:"storage"`，不得让 `storage` 变成第二个玩家路由名。它不是 descriptor 数组，不携带 handler、panelName 或领域对象。所有 handler 和 authority 判断仍由 facade / Host 持有。

触发器在 Build 中始终可打开，即使所有目的地暂时被 write/reconcile/pending 阻断；玩家需要在菜单内读到具体原因。当前 `equipment` 项固定 `current:true / disabled:true / reason:"当前"`。结构上尚未实现的目标不进入生产投影，运行时暂时不可执行的目标使用可聚焦 `aria-disabled` 项并显示正文对比度原因。锁状态在菜单打开期间变化时原位更新，不关闭菜单、不移动当前焦点。

#### 5.6.4 菜单交互与视觉合同

- 触发器可见标签固定为“整备 ▾”，带 `aria-haspopup="menu"` 与真实 `aria-expanded`；点击只展开，不执行最近目标；
- Click、Enter、Space、ArrowDown 打开；键盘打开后优先聚焦带 `aria-current` 的装备项，即使它是 `aria-disabled` 也可被朗读；只有当前项结构不存在时才聚焦首个可用项；
- ArrowUp/Down 循环，Home/End 到首尾，Enter/Space 激活；
- Esc 只关闭菜单、阻止继续冒泡并归还触发器；下一次 Esc 才交给 view stack；
- Tab/Shift+Tab 关闭菜单并按正常 header 顺序继续，不建立 focus trap；外部点击只关闭菜单；
- 切换 view、进入 Stats/SecondaryPage、打开 modal、开始 close、rebind、deactivate、destroy 都必须同步关闭菜单并清理 document listener；
- 不使用 hover-open、split button、最近目的地、自适应主按钮、多级菜单、图标徽章墙或二级说明卡；
- popover 单列，约 190–220px，不能挤动 header；1024×576 下不越出 viewport、不遮挡 Help/Close；
- 普通态只消费 shared structural motion；reduced-motion 直接显隐，不做位移；
- 中文使用现役 UI 字体栈，不继承 Consolas-first 的模式按钮排版。

#### 5.6.5 刘海独立装备调制入口

刘海“整备”行中的“装备调制”是用户要求的独立生产入口，不是 Character Build 菜单局部切换的别名。新增固定 command key `EQUIPMENT_TUNING`：

```text
Native/legacy HUD EQUIPMENT_TUNING
→ Host 生成 exact native tuning open intent / opaque openRequestId
→ AS2 openInventoryWorkbench(
     profile="battlebox",
     view="tuning",
     source="nativehud_equipment_tuning",
     openRequestId=Host-owned
   )
→ panel_request 原样回显
→ Host exact tuple + generation + admission 校验
→ 打开 standalone workbench tuning
```

禁止复用 `agent_control`、dev/test source、直接 `PanelHost.OpenPanel` 或 Web `Panels.open`。Host send 成功不等于打开成功；timeout、nonce/source/profile/view 近似匹配、重复回显和 admission 拒绝都必须清除 pending intent并提示，不得留下 pause/HUD/backdrop 残余。已有 active panel 或相同 tuning instance 时拒绝重复打开，不把它实现成 `EQUIP_UI` 那样的重点击关闭。

独立 tuning 与“战备箱与背包”仍是同一 Workbench instance 的兄弟 view，可以双向切换且不创建 Character Build session。Tuning 顶栏的兄弟切换文案使用中性的“战备箱与背包”，不能写“返回收纳”，因为从刘海直接进入时并没有先前的收纳页；只有显式从 Build 进入时才额外显示“返回构筑”。独立入口的 `×`、Esc 与 native backdrop 普通关闭到游戏。

“装备调制”不因当前背包没有可调制装备而隐藏；页面负责呈现可解释空态。只有游戏/服务尚未 ready、入口 progression gate 未满足或现有 owner 不能准入时显示 disabled reason。

## 6. 组件与抽象裁决

原则：只有两个及以上消费者因**相同原因**变化，才上收共享边界；仅 DOM 相似不构成抽象理由。

| 候选 | 决策 | 最小边界 | 明确拒绝的扩张 |
|------|------|----------|----------------|
| `InventoryWorkbenchHeaderProjection` | **新增** | 纯函数投影 header action 与固定整备菜单项状态；不发请求 | 通用 action DSL、动态 toolbar/navigation registry、handler descriptor |
| Inventory feature-local menu presenter | **扩展既有 header 模块** | 单层 DOM、ARIA、focus、outside-click 与确定性销毁 | 跨面板路由、authority、最近目标、多级菜单、全局组件 |
| Character Build post-close intent | **扩展现役 Skills 屏障** | exact instance + `skills/materials/intelligence` 固定枚举，settled 后一次目标打开/一次失败回滚 | 任意 panelName/initData、通用 return stack、Storage/Tuning 跳转 |
| Native tuning open intent | **新增固定入口** | `EQUIPMENT_TUNING` + Host opaque requestId + exact battlebox/tuning tuple | 复用 agent_control/test source、直接打开 Web/Host panel、通用 opener registry |
| `DualPaneShell({profile})` | **扩展** | 校验封闭枚举并写 `data-profile` | 动态 `LayoutProfileRegistry`、JSON 布局系统 |
| `HelpAction` | **推广现有** | 标准入口、spec update、modal 委托、销毁；补 action hook | 业务 capability、教程引擎 |
| `ChoiceGroup` | **推广现有** | “逐次确认 / 单件快捷”的 pressed/disabled 机械 | 调制规则和 quick-commit 判定 |
| `QuantityControl` | **推广现有** | Crafting 复用稳定 DOM、A/E、键盘与草稿 | 价格、材料、容量判断 |
| `PanelTooltip` | **推广现有** | Character 候选领域 adapter + scoped async binding | 新 `ItemTooltipBinding` 万能组件 |
| `CommitBar` | **推广现有** | Tuning/Crafting 固定 CTA 与状态 | `StagedCommandBar` 大组件 |
| `CloseAction` | **只允许轻量 factory** | type、glyph、class、audio、action hook | canClose、回滚、pending、领域文案状态机 |
| Empty State | **语义合同 + CSS** | `{kind, statement, nextStep}`，可选无状态 helper | 通用空态业务组件 |
| `CountBadge / StateChip` | **CSS/data slot** | 视觉角色、ARIA、命中避让 | JS 配置对象体系 |
| Context Hint | **CSS 角色** | 字号、间距、长文案与键盘等价 | 全局引导编排 |
| Scrollbar | **CSS utility/token** | track、thumb、hover、button、corner | `ScrollSurface` DOM/JS 组件 |
| Authority Preview | **架构模式** | browse → preview → commit → reconcile + CommitBar | 接收 lease/token/price/capacity 的通用组件 |
| Retry / Sync | **不抽组件** | 共享 warning 样式与玩家词表 | 模糊不同 reconcile 语义 |
| Guide Once | **推迟** | 满足多消费者后仅抽 versioned preference helper | tour、步骤注册表、跨面板 onboarding 状态机 |
| `escapeHtml` | **窄工具** | 优先 `textContent/setAttribute`；必要时分 text/attribute escape | “万能 sanitizer”或错误复用三替换版本 |
| Ctrl+滚轮 | **Host 根约束** | overlay 一次性冻结用户缩放 | 每页 `WheelGuard` |

共享组件不得接收 lease、token、revision、price、capacity 等领域字段。共享层变化必须验证 DOM identity、focus、scroll、tooltip scope 和 listener 清理，而不是只比较代码行数。

整备菜单的 DOM/ARIA/focus 机械能力放入现有 `inventory-workbench-header.js` 的 presentation 域，或在该域内按行数门拆一个无业务权力的窄文件；`inventory-workbench.js` 只编排固定目标 handler，且总体应通过搬移逻辑净减行。菜单模块不得自行监听 Bridge、持有 Character session 或直接调用 Host panel。

## 7. 布局与信息架构决策

### 7.1 profile 落实

`DualPaneShell` 接受以下封闭 profile：

- `catalog-decision`
- `archive-reference`
- `transfer-pair`
- `library-action-strip`
- `library-decision`
- `character-build`

profile 只决定壳级网格、FlowRail 角色、最小列宽和 footer 结构。领域内部特殊构图仍可使用受控 token，但不得在 feature 中静默创造第七种结构。新增 profile 必须先改 canonical doc、说明消费者与最小视口，并增加真实 fixture。

- 所有生产 `DualPaneShell` 都必须显式声明合法 profile；
- 双栏宏观 `grid-template-columns/rows` 只由 profile CSS 持有，feature 只负责 pane 内部构图；
- density 只改变实体格密度，默认不得改变双栏 split；确有领域理由时必须定义受控 profile variant，并进入本文和真实 atlas；
- 当前**独立** Equipment Tuning 在 compact 下从 `52:48` 跳到 `42:58` 的行为应退出，不能让“看紧凑图标”同时改变整页构图；Character Build 嵌入态仍保持自己的 `character-build` 55:45 profile，不按这条选择器误改。

### 7.2 header action budget

- 同一视图只保留一个 Help、一个 Close；
- “返回上一层”与“关闭到游戏”图形和文案必须不同；
- 不同时出现重复的文字返回与箭头返回；
- action 按 `context / preference / help / close` 分组，领域主动作与全局关闭不混排；
- 1024×576 下 action group 单行、无横向滚动；
- 次要设置优先收拢为 ChoiceGroup / overflow，不得压缩主标题和关闭命中区；
- view 切换必须原子更新 action projection，不保留上一 view 的可见按钮。

### 7.3 整备分类的跨入口一致性

- canonical route 顺序固定为 `equipment / battlebox / tuning / skills / materials / intelligence`；
- 玩家短标签固定为“装备 / 战备箱 / 装备调制 / 技能 / 材料 / 情报”；Character Build 菜单可在不改变 route identity 的前提下补充“角色构筑 / 与背包 / 配置”等消歧文字；
- C# 的 Native/legacy HUD 共享一份 frozen route tuple；Web 保留一份同形 frozen tuple，并由跨栈测试比较 exact identity/label/order。禁止为跨语言“单源”引入运行时 JSON registry，也禁止三处无测试手抄后逐渐漂移；
- 右侧常驻“装备”按钮是 `equipment` 的 pinned alias，保持一键打开 Character Build；它不拥有独立 route identity，也不改成必须先展开分类；
- 技能正式归入“整备”，不得同时留在刘海“游戏”行；“游戏”行缩为战队、平板、商城；
- “个人信息”是装备内部本地 SecondaryPage，不进入刘海整备行，也不进入下拉菜单；它继续作为 Character Build header 一级动作；
- 进入游戏后六个整备成员保持结构可见；progression/warehouse/service 未满足时显示 disabled 与具体 reason，不再像现役 `RequiresWarehouse` 一样从某入口静默隐藏。Character Build 菜单与两套 HUD 对同一 gate 的 visible/enabled/reason 必须一致；
- Native `NotchWidget` 的目标是四个有标签行“游戏 / 整备 / 辅助 / 系统”。新增第四行后，expanded height、width、hover/click rect、动画 union bounds 与低分辨率裁切必须从可见行数推导，退出现役固定 `*3` 与手写 `Max` 链；
- legacy `NotchOverlay` 不必补齐 Native-only 的整个“辅助”产品面，但至少把游戏与整备渲染成两条可辨识、无裁切的 production action 行。其 active-region/WM_NCHITTEST、toolbar height、绘制 Y、按钮 rect 与 expanded width 必须消费同一行几何；退出单行高度和 600px cap 可裁掉按钮的假设；
- legacy 与 Native HUD 可以有不同绘制实现，但游戏/整备可见成员、顺序、enabled reason 和 command route 必须一致。

### 7.4 右侧条件槽的状态优先级

| 槽位角色 | 内容 | 是否可交互 | 退出条件 |
|----------|------|------------|----------|
| `transactionDecision` | SafeExit 存盘状态与取消/退出/重试 | 是，由 SafeExit exact owner 命中 | 事务完成、取消或安全超时 |
| `actionableNotice` | 单一任务/系统通知与明确下一步 | 仅在确有动作时 | 动作完成、状态失效或通知超时 |
| `contextHint` | 当前 top tool 的一行说明 | 否 | hover/focus 离开或更高优先级出现 |
| `hidden` | 无信息增量 | 否 | 有上层状态 |

右侧条件槽不做常驻空框；没有地图、通知、事务和 hover/focus 上下文时整个视觉槽 computed hidden、零 hitbox。外部状态必须给出 exact slot owner，而不是只声明“高度被占用”；不能留下“保留了高度但没有任何 owner 绘制”的空白。`CompositeBounds` 为 hover tooltip 预留的透明 union 仅是鼠标进入/重绘边界，不算可见条件槽，不得因此生成背景或命中 action。装备提示必须解释入口与相邻整备位置，不能只重复“装备”。

### 7.5 空态与计数

- counts 在能降低试探成本时前置，不让玩家逐个打开分类确认是否为空；
- `0 / loading / unknown / error` 是四种不同投影；
- empty 文案采用“事实；下一步”，不使用只有“无”的死端；
- routine ready 不占底部，blocked/error/reconcile 才持续占位。

### 7.6 tooltip 与常驻摘要

- compact 模式隐藏正文时，tooltip 和可见当前浏览摘要共同补齐信息；
- tooltip 不替代错误原因、主 CTA、当前 source 和关键模式说明；
- 长中文说明不使用 9px、等宽字体或过度字距；
- 壳外 tooltip 同样服从主题 token、viewport gap 和 reduced-motion。

## 8. 视觉系统决策

### 8.1 排版角色

新增或收敛为少量角色 token，而不是给每个 selector 建 token：

| 角色 | 建议下限 | 用途 |
|------|----------|------|
| `badge` | 9px | 短数字、英文缩写、角标；不承载长中文和错误 |
| `body` | 10px | 中文正文、条件、阻断原因、帮助正文 |
| `label` | 11–12px | 卡片名称、按钮、主标签 |
| `pane-title` | 15–17px | pane 标题 |
| `shell-title` | 约 20px | 工作台主标题 |

约束：

- 8px 玩家文字直接禁止；
- 9px 中文只允许极短角标，不允许帮助、错误、条件和物品主名；
- Consolas/等宽字体只给数字、短状态和仪表，中文字体栈明确回落到现役 UI 中文字体；
- letter-spacing 收敛为少量角色，不在 9–10px 中文上叠高字距；
- 触碰模块中的违规字号必须归零，存量总数只降不升。

### 8.2 颜色与 skin

- 新增和触碰行只使用 `--dls-*`、`--theta-*`、`--wb-semantic-*`、`--wb-accent-*` 及 `color-mix` / `rgba(var(--*-rgb), alpha)`；
- 不为每个旧颜色机械制造一一对应 token；
- token 必须表达 surface、line、text、muted、accent、focus、success、warning、danger、disabled、economy 等稳定视觉角色；
- skin 只允许覆盖 token；本轮首先禁止 skin 改写 `display / grid / overflow / hitbox / focus / state priority`，再逐段迁移旧结构规则；
- 经济琥珀与 warning 语义分开，不能用同一种颜色同时表示价格和危险；
- accent 只用于 selected/source/focus/pending/主决策，不能让每块 pane、每行和 header 都常亮同等粗边；
- 颜色之外继续使用轮廓、图标、文字与形态表达重要状态。

执行顺序按债务密度拆为 CSS-only 原子批：

1. `skins.css`
2. `skills.css`
3. `equipment-tuning.css`
4. `inventory.css`
5. `core.css`

每批只处理一个视觉角色或一个文件域，不与任务流重构、named-layer 全迁移同时进行。

### 8.3 滚动条

共享低 specificity scrollbar utility 只统一：

- 轨宽；
- track / thumb / hover token；
- `::-webkit-scrollbar-button` 去除；
- corner；
- reduced-motion 下的 hover 结果。

`overflow`、`max-height`、滚动窗口身份、焦点恢复和 scroll restore 仍由领域负责。验证必须使用 `scrollHeight > clientHeight` 的真实 fixture。

utility 同时统一 `scrollbar-gutter:stable` 和滚动区 focus-visible，但不自动给任意容器添加 `tabindex`；滚动区是否进入 Tab 序列仍由领域的信息可达性决定。

### 8.4 状态对比与层级

- blocked reason 不继承整卡 opacity；
- disabled 控件可降低饱和度或强调度，但文字原因维持 body contrast；
- surface 与间距建立大分组，柔线建立内部层级，accent 不作为默认边框；
- z-index 只为跨 stacking context 的 page / modal / tooltip / drag ghost 建语义层；局部 `0/1/2` 不机械上收。

### 8.5 玩家词汇

静态审计应拒绝常态玩家层出现：

- lease、token、revision、epoch、wire、callId；
- “权威瞬态容器”“重放写入”“协议水位”等实现词；
- 无玩家决策价值的版本号和诊断英文 eyebrow。

保留玩家真正需要的：

- 当前来源；
- 正在核对 / 重新同步；
- 是否可能已成功；
- 下一步安全动作；
- 可复制的脱敏诊断入口。

## 9. 动效语言决策

### 9.1 语义时长

| 角色 | token | 时长 | 用途 |
|------|-------|------|------|
| micro | `--wb-motion-micro` | 90–120ms | hover、focus、press |
| standard | `--wb-motion-standard` | 140–180ms | 选择、状态切换 |
| structural | `--wb-motion-structural` | 180–220ms | SecondaryPage、决策区切换 |
| reject | `--wb-motion-reject` | 约 250ms，最多两次 | 明确拒绝 |
| busy | `--wb-motion-busy` | 900–1200ms | 权威等待 |
| ambient | `--wb-motion-ambient` | 1200–1800ms | 每面板最多一个环境核心 |

工作台内不再新增裸时长。既有 `.08s/.1s/.12s/.25s/.28s/.75s/1.8s` 按语义迁移，不能只按最接近数字机械替换。

### 9.2 属性与职责

允许的过渡属性：

- `opacity`
- `transform`
- `color`
- `background-color`
- `border-color`
- `outline-color`
- `box-shadow`
- `visibility`，且只用于延迟离场

禁止：

- `transition:all`
- 宽高、grid/flex 几何与会推动布局的动画；
- 普通可用控件的无限循环；
- feature 自己定义新的时长/缓动体系。

JS 只写数值和切 class，不拥有时长与 easing。拖拽、inspection camera 等直接操纵路径必须在操纵期间 `transition:none`。

### 9.3 reduced motion

- 提供共享 `prefersReducedMotion()` 给 JS RAF / 数字滚动等非 CSS 动画；
- 根级工作台关闭非必要 pulse、shake、travel 和 transform；
- tooltip、drag ghost 等壳外 surface 单独纳入；
- 删除 `.001s/.001ms` 伪关闭，合法结果只有 `animation:none/transition:none` 或明确的静态补偿；
- reduced 模式保留静态 outline、图标和文案，不能把状态本身一并删掉。

### 9.4 cascade 与真实生效

SecondaryPage、focus ring 和 state motion 的验收读取 computed style：

- inactive page 仍保持结构 grid，但 `visibility:hidden`；
- active page 的 opacity / transform / visibility 符合 structural contract；
- 退场完成后不可聚焦、不可命中；
- feature / skin 不能用 unlayered `display:none` 绕过共享离场；
- focus-visible 的最终 outline 是角色 token，而不是被 feature 静默覆盖；
- button、EntityTile、input、select、range 和可聚焦 scroll region 都有对应 focus 证据；
- selected 与 focus 可以叠加辨认，不能用同一条轮廓互相覆盖；
- legacy `kshop-pulse` 等 keyframes 移入共享 motion 域并改为领域中立命名，消费统一 busy token。

### B：整备导航纵切

该纵切必须按下列顺序形成独立可验证、可回退提交；不能与 Header CSS、全量 Notch 重绘或其他 Character Build 能力混在一起：

1. **B1 信息架构与 HUD 几何**：在默认关闭的 `PreparationNavigationV1` rollout gate 后落 C# frozen tuple、Native 四行、legacy 游戏/整备两行、统一 progression reason；fixture 可验证新几何，生产 HUD 仍保持现役布局。右侧条件槽可独立加入单 owner 仲裁和有信息增量的 hint，但不新增整备子按钮；
2. **B2 独立调制生产入口**：新增 `EQUIPMENT_TUNING` 的 exact AS2 opener/nonce/admission，证明 standalone Tuning ↔ Battlebox、普通关闭到游戏和重复请求拒绝；handler 转绿前，B1 gate 下的“装备调制”不得在生产可见；
3. **B3 局部 Workbench view**：Build → Battlebox / standalone Tuning 保持 exact instance/session/pause；嵌入调制切 standalone 时完成 exact detach；两条路径都能显式返回 Build；
4. **B4 固定 post-close 基座**：把 Skills intent 收敛为三目标 enum 结构，补独立 arm→settled / target-open 两阶段 timeout、lifecycle epoch、一次消费/取消与 `returnFocusAction` 双值 parser；仍只启用现役 Skills，且旧 header 生产期 Host 继续发 `skills`；

6. **B6 Intelligence**：加入固定 prod initData 的 exact post-close open 与一次失败回滚；
7. **B7 原子生产切换**：在 G0 原始 exact-set、dev-gated 菜单、六目标真实路由和两套 HUD 全部转绿后，以同一 rollout 单元打开 `PreparationNavigationV1`：Native/legacy HUD 切换游戏/整备分组，Build 切为 `preparation-menu | stats | help | close`，Host 从 `returnFocusAction:"skills"` 改发 `"preparation-menu"`，Web 同步启用其固定 action 映射；随后删除旧 storage/skills 直达按钮。任一部分失败都整体关闭 gate，不允许生产出现半套 IA 或无目标 action。

在 B5/B6 通过前，生产 Build 与 HUD 都继续保留现役布局，不发布只有部分真实目标的“整备”分类。允许先合并 presenter、projection、HUD geometry 与 dev fixture，但 `PreparationNavigationV1` 默认关闭；不能用 disabled “即将开放”项目替代闭环。

`PreparationNavigationV1` 是一个 Host-owned、全开或全关的**临时 rollout gate**，只仲裁新旧呈现切换，不参与 route authorization；不得派生六个 destination flags、远端配置表或运行时 registry。标准入口验收和约定回退观察窗结束后，应删除旧呈现分支与该 gate，避免双实现长期并存。

## 12. 风险、回退与非决策

### 12.1 主要风险

- 候选 tooltip 与候选调制会扩大 exact ref、lease 和迟到回包矩阵；
- header 投影若顺带重写 facade，容易把窄修复扩大成路由重构；
- CSS token 化若与 named layer 同时进行，视觉差异难以定位；
- Ctrl+滚轮若在 document feature 层拦截，会误伤正常滚动和 inspection；
- profile 迁移若只改 data attribute、不补真实 fixture，会制造“文档上完成”的假绿；
- disabled/inspectable 分离若没有 aria 与 intent 断言，可能重新出现点击静默无效；
- 整备菜单若先于 Materials/Intelligence handoff 发布，会出现“当前构筑已关闭、目标却未打开”的高破坏性假导航；
- Materials 若没有 Host-owned requestId 回显，或 pending wait 仍准入无 nonce ordinary open，迟到/旁路 `panel_request` 可能错误消费新的 post-close intent；若 arm 与 target-open 复用同一 timer，则 exact settled 会与刚建立的目标 wait 竞态；
- 独立 `EQUIPMENT_TUNING` 若复用 agent_control/test source 或缺少 exact admission，会把生产入口绑到自动化特权路径；
- B1 几何、B2 opener、B7 header/focus 若不受同一生产 gate 约束，会短暂暴露无真实目标或无焦点落点的半套 IA；
- 把局部 Storage/Tuning 与跨 owner Skills/Materials/Intelligence 塞进同一通用 router，会丢失 exact instance、pause 与 rollback 边界；
- 刘海新增一行若只改按钮数组，可能让 expanded bounds、hit rect、legacy fallback 和视觉宽度发生漂移；
- 右侧条件槽若同时承载整备按钮、任务通知和 SafeExit，会产生重叠 hitbox 与错误破坏性操作 owner。

### 12.2 回退策略

- Web-only 原子批按 feature 回退，不回退共享 authority 契约；
- 跨层三条纵切分别版本化，不共享一个巨大 payload switch；
- candidate tuning 写失败回到只读候选状态，不自动改穿戴或重放；
- profile 按消费者逐个迁移，未迁移 feature 保持旧比例直到自己的 computed-style 对照通过；
- CSS ratchet 允许按文件回退，不允许通过放宽全局阈值掩盖失败；
- Host zoom 变更若误伤 inspection，只回退输入策略，不在各页面临时打补丁；
- B1–B6 的底层实现可分别回退；一旦 B7 已切生产，任一 HUD/header/focus 成员需要回退时必须整体关闭 `PreparationNavigationV1`，同时恢复旧 HUD、`storage | stats | skills | help | close` 与 `returnFocusAction:"skills"`，不留下半套入口；
- Materials/Intelligence handoff 在 B7 前可按目标独立回退，不影响已验证的 Skills 屏障或 Storage/Tuning 局部切换；B7 后若某目标结构性撤除则整体关总 gate，只有运行时暂时不可用才保留项目并显示 reason；
- 右侧条件槽改造失败时恢复纯提示/通知/SafeExit 现役路径，不把整备菜单临时移入该槽。

### 12.3 明确非决策

- 不新增 `HeaderToolbar` 通用 descriptor DSL；
- 不新增全局 `PreparationNavigationRegistry`、任意 panel intent 总线或跨所有面板复用的 header menu；
- 不让生产 `EQUIPMENT_TUNING` 复用 agent_control/test source，也不抽 Native opener registry；
- 不新增 hover-open、split button、最近目的地、动态主动作、多级菜单或“未来功能”disabled 预告项；
- 不把右侧条件槽改造成第二个刘海/第三套整备导航；
- 不新增 `LayoutProfileRegistry`；
- 不新增 `StagedCommandBar`；
- 不把 `AuthorityPreview` 变成领域参数容器；
- 不新增 `ScrollSurface` DOM/JS；
- 不新增 `RetrySyncAction`；
- 不在本轮建立 tour / onboarding 引擎；
- 不把 1332 处颜色一次性清空作为 P0 完成条件；
- 不把 z-index 全部机械替换成四个全局值；
- 不为了“统一”让 HelpAction、tooltip 或 modal 参与业务授权。

| M4 `_externalStatusSlotActive` 只占高度，不能仲裁 notice/SafeExit | `RightContextWidget` 仍可能绘制 notice，SafeExit 在同一矩形另画 | **接受** | §4.13/§7.4 新增单一 `RightContextSlotOwner` 仲裁与绘制/hitbox 互斥 |

### 14.7 补充审计后的主线新增发现

并行代码核对还发现两项 K3 摘要没有单独列出的施工空洞：

1. 刘海六项中“装备调制”尚无独立生产 command/admission；§5.6.5 已冻结 `EQUIPMENT_TUNING`、Host opaque requestId、exact battlebox/tuning tuple、standalone 关闭与兄弟 view 文案；
2. Materials 的现役 `openMaterialUI` 只证明命令发送，AS2 回来的 `panel_request` 没有与 post-close intent 相关的 requestId；§5.6.2/B5 已要求 material-specific opaque nonce 原样回显与 exact admission。

两项都使用固定目标协议，不据此建立通用 opener、NavigationRegistry 或 return stack。
