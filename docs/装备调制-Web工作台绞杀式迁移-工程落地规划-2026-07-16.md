## 0. Compact 后从这里恢复

### 0.1 一句话结论

装备调制是合适的下一个绞杀切片：它是高频、与已完成背包高度相邻、对角色活体副作用较少的功能；先迁它能把旧装备 Hub 的第一块业务权威掏空，并给后续装备槽/穿脱提供自然前置流程。它不是“直接做一个 Web 强化页”，而是“先消灭旧 UI 的直接写权限，再允许 Web 成为新主入口”。

### 0.2 已冻结决策

| ID | 决策 |
|---|---|
| D1 | 采用绞杀式迁移；先抽 AS2 `EquipmentTuningService` 权威，再接 Web，再重定向旧入口，最后才谈删除资产。 |
| D2 | Web 仍使用 `panel=workbench`，增加 `view=storage\|tuning`；不新建另一套顶层背包面板。 |
| D3 | 业务总线使用独立 `domain=equipment_tuning`；不得把强化、进阶、插件规则塞进 `inventory` domain。 |
| D4 | v1 只允许 `_root.物品栏.背包` 内的武器/防具作为主装备；不接受已穿戴装备、仓库或战备箱来源。 |
| D5 | 强化、转换、进阶、插件安装/拆卸都必须走 AS2 预览计划 + opaque token + 单次原子提交；Web/C# 不重算规则。 |
| D6 | 权威抽取完成后，旧 AS2 调制 renderer 只能委托同一服务；禁止保留第二套直接写实现作为 fallback。 |
| D7 | Web 主入口与旧 renderer 回退可用 feature flag 切换；业务权威不得回退到旧直接 writer。 |

| D9 | `EQUIP_UI` 暂不整体改道。旧 Hub 仍承载装备槽/属性等未迁功能；本切片只逐步接管其中“装备调制”责任。 |

### 0.3 开生产代码前必须冻结的决策

| ID | 待定点 | 本文建议 | 不冻结的风险 |
|---|---|---|---|
| D10 | 等级相同的强化度转换 | 明确为成功 no-op：不改值、不涨 revision、不标脏、不记成就 | legacy 当前会显示成功但实际无变化，难以写稳定测试 |

## 1. 可行性与排序裁决

### 1.1 为什么适合作为下一个目标

| 维度 | 评价 | 证据与含义 |
|---|---|---|
| 玩家热点 | 高 | 强化、转换、进阶、插件会在装备生命周期内反复发生，不是一次性配置。背包可打开时，玩家就有检查和调整新掉落装备的理由。 |
| 与已迁基建的邻接度 | 高 | 输入装备当前就来自背包；Web 工作台已有 owned inventory、分页、tooltip、slot lease、write gate 与动态右 View。 |
| 与其他旧 UI 的正交性 | 中高 | v1 限定背包装备后，不涉及穿戴角色的动画、活体属性刷新、换装或战斗状态；主要交集是背包、材料、成就和存档。 |
| 绞杀收益 | 很高 | 旧装备 Hub 中最有状态、最常操作的一组责任可先失去直接写权；其余装备槽/属性仍可留在旧 UI，适合逐块掏空。 |
| 规则复用成熟度 | 中 | `EquipmentUtil`、`TierSystem`、`TagManager` 已有大量领域判断；但旧 UI 仍持有进阶顺序、费用与直接写流程，尚未形成事务服务。 |
| 事务成熟度 | 低 | 原地变更不推进容器 revision，材料扣除与 dirty/achievement 偶然耦合，转换缺显式 dirty；这是主要成本，不是 Web 绘制。 |
| 资产/发布冲突 | 中高 | 调制 renderer 位于独立 `物品与技能相关界面.xfl`，当前 Skill fallback 也触及这一旧 Hub；必须串行施工。 |

总体判断：**适合作为下一目标，但必须把“业务权威抽取”视为主体工程，把 Web 页面视为后半段。** 若只按界面工作量估算，会严重低估原子性与持久化风险。

### 1.2 与“先迁装备槽/属性”的比较

| 项目 | 先迁装备调制 | 先迁装备槽/属性 |
|---|---|---|
| 输入是否已在 Web | 是，背包已完成 | 部分；需要新建穿戴槽和角色投影 |
| 角色活体副作用 | v1 基本无 | 高：equip/unequip、外观、属性、被动与运行态刷新 |
| 可独立切走的责任 | 高 | 中，容易牵出玩家信息/HUD/换装 |
| 旧 UI 掏空效果 | 先移走高频编辑责任 | 先移走展示与穿脱责任 |
| 对下一切片的帮助 | 调制完可直接进入穿戴流程，减少旧 UI 往返 | 穿戴后仍需回旧调制页配置装备 |
| 失败回退 | 可回旧 renderer，但仍走新服务 | 回退常涉及活体状态重新对账 |

“玩家通常先调制、再穿戴”不是所有玩家路径的严格事实，因此不能当成数据依赖；但它是很强的体验顺序和工程顺序。背包卡片上的“调制”动作可以自然进入右栏工作台，完成后再进入未来的“穿戴/比较”。这会让装备槽迁移建立在已经稳定的装备编辑权威之上。

### 1.3 成本—收益结论

收益主要来自三层：减少背包与旧 Hub 往返；复用背包高出场率扩大 Web 工作台价值；让旧装备 UI 首次发生可计量的事实退役。代价集中在 AS2 事务语义，而不是布局。

| 切片 | 相对成本 | 主要产出 |
|---|---|---|
| T0 探索/ADR | 中，已完成 | 行为冻结、缺口地图、目标架构、停线 |
| T1 AS2 权威服务/测试 | 高 | 四类操作只有一个 writer，修正 dirty/revision/原子性 |
| T2 协议 + C# Task | 中高 | preview/token/commit/reconcile 闭环和写状态机 |
| T3 Web tuning View | 中 | 复用背包与双栏壳，新增调制组合层与 harness |
| T4 legacy 委托/入口改道 | 中高 | 旧 UI 失去业务权威；独立 XFL 精确发布 |
| T5 观察与事实退役 | 中 | 正常路径零 legacy 直接进入，保留可控兼容回退 |
| T6 资产删除 | 暂缓 | 只有整个旧 Hub 其余责任迁完后才有价值 |

和装备槽切片相比，本方案前期事务成本更高，但迁移杠杆也更高。它值得做，因为这些事务缺口无论哪天迁移都必须解决，而越早集中成服务，旧 UI 与后续 Web 都越少继续制造分叉状态。

## 2. 现役旧 UI 拓扑与绞杀边界

### 2.1 旧 Hub 不是单一装备页

独立资产入口是：

- XFL：`flashswf/UI/物品与技能相关界面/物品与技能相关界面.xfl`
- 发布产物：`flashswf/UI/物品与技能相关界面.swf`
- 主符号：`LIBRARY/新版物品栏界面.xml`
- 嵌套调制符号：`LIBRARY/新版装备强化界面.xml`，实例名 `装备强化界面`

`新版物品栏界面` 同时承载物品栏、个人信息、技能、材料、情报等帧；`新版装备强化界面` 内再分强化装备、强化度转换、插件改装。因此本切片不能粗暴把 `EQUIP_UI` 整体换成 Web：那会截断仍未迁移的装备槽/属性和其他旧责任。

现役入口 `openEquipUI` 仍把 `_root.物品栏界面` 置为可见并跳到当前界面；Launcher 的 `EQUIP_UI` 仍发送该游戏命令。当前只应新增“从 Web 背包进入 tuning”和“旧调制入口重定向到 tuning”，而不是提前退役整个 Hub。

### 2.2 本切片包含

- 强化装备：选择目标强化度、费用预览、提交。
- 强化度转换：两个背包装备之间交换强化度。
- 装备进阶：二阶/三阶/四阶及特殊材料候选、预览、提交。
- 插件改装：候选可用性、安装、拆卸单个、级联依赖返还、全部拆卸。
- 背包卡片到调制 View 的上下文动作与热切换。
- 旧 renderer 委托新权威服务、入口改道、fallback 与观察指标。

### 2.3 本切片不包含

- 穿戴槽、equip/unequip、角色属性总览、角色外观或活体刷新。
- 从仓库、战备箱或已穿戴槽直接调制。
- 装备数值公式重做、平衡调整或材料命名迁移。
- 存档结构迁移、坏档自动修复、历史装备全量归一化。
- 删除旧 Hub、XFL 帧、linkage 或 `EQUIP_UI`。
- 将装备调制业务下沉到通用 Shell、Grid、OwnedInventoryView 或 InteractionBroker。

## 3. 当前行为冻结

以下是 T0 从生产源码核出的现状，不代表所有行为都应原样保留；有意改变处必须在 T1 测试中显式记录。

### 3.1 来源与选择

- `InventoryIcon` 只允许 `_root.物品栏.背包` 中的武器/防具进入调制主槽或转换目标。
- 主装备变化时，旧 UI 会按当前 tab 重建预览；转换候选按同一 `item.getData().use` 高亮。
- 旧调制 UI 只监听物品移除；强化度、tier、mods 等原地变化不触发移除事件。
- 因此 v1 保持 backpack-only，不能借 Web 已能查看仓库就扩大写入来源。

### 3.2 强化装备

| 项 | 现状 |
|---|---|
| 强化上限 | 主线进度 `>129 → 13`；否则 `>74 → 9`，其余 `7`。铁匠功能开启且等级 `>=10` 时，非 13 上限分支再 `+1`。 |
| 默认目标 | 当前强化度 `+1`；超过上限则截到上限。 |
| 调整按钮 | 旧资产提供 `+1`、`-1`、直接 `13`、直接 `2` 等操作，最终仍受预览 clamp。 |
| 材料 | `强化石`。 |
| 每级成本 | 对每个目标级 `i` 累加 `floor(multiplier * (i - 1)^3 + 1)`。 |
| 折扣 | 铁匠被动形成 `multiplier=max(1-level*0.05, 0)`；展示节省值使用 `ceil((1-multiplier)*(i-1)^3)`。 |
| 当前提交 | `singleSubmit("强化石", cost)` 后直接写 `item.value.level=target`，再记录 `装备强化次数` 并刷新图标。 |

目标服务必须从现有权威状态读取上限与折扣依赖，token 至少绑定主线进度、铁匠开关/等级、装备 lease/状态和强化石精确数量。C#/Web 不复制上述公式。

### 3.3 强化度转换

| 项 | 现状 |
|---|---|
| 候选 | 与主装备 `use` 相同；不能是同容器同槽。 |
| 成本 | 无。 |
| 结果 | 直接交换两个 `value.level`。 |
| 相同等级 | 旧 UI 会警告“无效果”，但仍可走成功反馈。 |
| 副作用缺口 | 不显式 dirty、不推进两个槽的 mutation revision、不写 item timestamp、无专属生命周期事件。 |

目标实现需要两个独立 slot lease，并把交换视为一个不可拆分的多槽事务。D10 建议把相同等级冻结为成功 no-op。

### 3.4 装备进阶

`TierSystem.isTierMaterialAvailable()` 只回答装备静态配置是否支持某材料/默认低级防具资格，不负责当前 tier 到下一 tier 的顺序。现有进阶顺序实际被旧 UI renderer 硬编码：

- 无 tier：锁定三阶/四阶，允许配置支持的二阶或特殊冰/火等材料。
- 当前二阶：只开放三阶。
- 当前三阶：只开放四阶。
- 其他状态或四阶：全部锁定。

提交路径却只再次调用较弱的 `isTierMaterialAvailable()`，随后扣材料并直接写 `item.value.tier`。这意味着若 Web 直接复用该函数，会绕过旧 UI 的进阶顺序。**T1 必须把合法 transition 收回 `EquipmentTuningService`/领域层，Web 只消费候选与拒绝原因。** 不应在 Web 复制硬编码材料名。

### 3.5 插件改装

插件规则的现有领域权威较完整：`EquipmentUtil` 聚合配置，`TagManager` 判断槽位、重复、tag 依赖/冲突、blocked tag、武器类型、子弹与安装条件。现有可用性状态包括：

| 状态 | 含义 |
|---:|---|
| `1` | 可安装 |
| `0` | 未知/不可识别 |
| `-1` | 插槽已满 |
| `-2` | 重复插件 |
| `-4` | 技能/特殊武器冲突 |
| `-8` | 同 tag 冲突 |
| `-16` | 缺少前置依赖 |
| `-32` | 拆卸会破坏依赖 |
| `-64` | blocked tag |
| `-128` | 子弹类型不兼容 |
| `-256` | 安装条件不满足 |
| `-512` | 子弹要求不满足 |

旧提交路径：

- 安装：校验候选、扣一个插件材料、`mods.push()`、记录 `安装插件次数`。
- 拆单个：计算直接依赖者；若插件 `detachPolicy=cascade`，一并移除并返还，否则拒绝或只返还当前插件。
- 全拆：逐个返还材料后 `mods=[]`。

静态数据扫描（2026-07-16）得到 104 个插件、10 个 provider、24 个 consumer、6 个 `detachPolicy=cascade`、18 个 install condition；忽略 use 约束时有 101 条可能 provider→consumer 边，当前数据没有 provider→consumer→consumer 的二级链。直接依赖计算因此覆盖当前数据，但新服务仍应使用 fixed-point 或提交后全量有效性检查，避免数据扩展后漏掉级联链。

只读 snapshot 遇到非数组 `mods` 必须 fail closed 并给出结构化错误；不得借读取路径偷偷把存档改为 `[]`。现役 `BaseItem.createFromObject` 已会把大多数加载态坏形状归一为数组，这不构成新协议可以静默写档的理由。

## 4. Writer 与副作用地图

### 4.1 已确认的直接 writer

| 操作 | 当前装备写 | 材料写 | 成就 | 显式 dirty | 容器 revision |
|---|---|---|---|---|---|
| 强化 | `value.level=target` | `ItemUtil.singleSubmit` | `装备强化次数` | 无；依赖成就记录间接标脏 | 无 |
| 转换 | 交换两个 `value.level` | 无 | 无 | 无 | 无 |
| 进阶 | `value.tier=tierName` | `ItemUtil.singleSubmit` | 进阶相关记录 | 无；依赖成就记录间接标脏 | 无 |
| 插件安装 | `mods.push(name)` | `ItemUtil.singleSubmit` | `安装插件次数` | 无；依赖成就记录间接标脏 | 无 |
| 插件拆卸/全拆 | splice 或覆写 `mods=[]` | `ItemUtil.acquire` 返还 | 无 | `acquire` 会标脏 | 无 |

关键事实：`ItemUtil.acquire` 末尾显式 dirty，`ItemUtil.submit` 不 dirty；`AchievementMetrics.record` 会 dirty。因此强化、进阶、安装是否持久化，当前偶然依赖成就子系统。转换没有这条间接链。新服务必须显式拥有存档脏标记，不再把 achievement 当 persistence primitive。

### 4.2 lease 与 revision 的现状

`ArrayInventory` 已有 `mutationRevision`、事务写与事务替换；add/remove/sort 等结构变化会推进 revision。直接修改 `BaseItem.value.level/tier/mods` 不会推进 revision。

`InventoryPanelService` 的 lease confirm projection 已包含强化度、tier、mod signature 等字段，所以旧 lease 在原地调制后大概率会校验失败；但容器 `containerVersion` 仍不变化，事件订阅与缓存更新语义不完整。不能把“旧 lease 恰好失败”当成事务实现。

T1 应提供明确的 in-place touch transaction：

- 强化、进阶、插件提交触碰一个槽；转换原子触碰两个槽。
- 先校验全部 lease、规则、材料与回收容量，再进行任何写。
- 一个业务 commit 只产生一个逻辑 revision 批次。
- 所有装备值与材料写完成后再发布生命周期事件。
- 成功后返回受影响背包 snapshot；Web 的 `InventoryCoordinator.completeExternalWrite(true)` 强制刷新并轮换 lease。

### 4.3 材料集合缺口

材料栏使用 `DictCollection`，当前没有与 `ArrayInventory.mutationRevision` 对等的 revision/批事务。`add/addValue/setItems` 会直接改变集合并派发生命周期事件。拆卸又是“先返还材料、再改装备”的现状顺序；一旦中途失败，没有统一 rollback 和延迟事件发布。

D12 必须在 T1 做选择和测试。最低正确性要求：计划阶段精确计算所有材料 delta 与返还结果；提交前全量 revalidate；失败零写；成功时监听器不能把中间态当最终态。若现有同步事件阻碍该不变量，就新增材料批事务，而不是在 `EquipmentTuningService` 里堆脆弱的反向补偿。

## 5. 目标架构

### 5.1 分层

```text
Web panel=workbench
  ├─ 左：既有 Backpack owned view / InventoryCoordinator
  └─ 右：view=tuning / EquipmentTuningRuntime + View
             │ domain=equipment_tuning
Launcher EquipmentTuningTask
             │ gameCommand / equipment_tuning_response
AS2 EquipmentTuningService
  ├─ InventoryPanelService：slot lease / affected snapshot
  ├─ EquipmentUtil / TierSystem / TagManager：领域规则
  ├─ ArrayInventory / DictCollection：计划式原子写
  ├─ AchievementMetrics：成功后 exactly-once 记账
  └─ `_root.存档系统.dirtyMark`：显式 persistence ownership
```

边界原则：Shell 只管理 View 生命周期；InventoryCoordinator 只管理背包窗口、lease 与共享写门；EquipmentTuningRuntime 管理调制请求状态；所有“能否强化/进阶/安装、扣多少、拆哪些依赖”的答案都来自 AS2 服务。

### 5.2 为什么复用工作台而不新开面板

现有 `DualPaneShell` 已支持注册、挂载和替换右侧 View；`inventory-workbench.js` 已让一个 `InventoryCoordinator` 独占背包与右栏库存窗口。目标只需把右栏从 storage View 换为 tuning View，并保留左侧背包筛选、分页和选择上下文。

目标入口形状：

```text
panel=workbench
profile=battlebox|warehouse
view=storage|tuning
```

当前 AS2 `InventoryPanelService.handlePanelRequest` 和 C# `OpenInventoryWorkbench` 只白名单 `profile=warehouse|battlebox`，尚不接受 `view`。T2 必须让 AS2、C#、Web 三端对 `view` 使用同一显式白名单；未知值回 `storage` 或结构化拒绝的选择也要有测试，不能透传任意字符串。

### 5.3 背包与调制的交互接缝

- 正常 storage View 保持现有跨栏 InteractionBroker 与拖拽语义。
- 进入 tuning View 时，取消在途拖拽并停用“背包↔右库存”的 transfer intent；背包卡片点击改为选择/热切换主装备。
- 转换 tab 可进入第二候选选择态，但仍由调制组合层解释，不污染通用 owned inventory 组件。
- 背包卡片“调制”按钮由 `inventory-workbench.js` 组合层追加；共享卡片壳只暴露通用 action 插槽/事件，不认识装备规则。
- 切回 storage 时恢复原右栏、页码与已选 profile；不得重复创建 ResizeObserver、pointer handler 或拖拽镜像。

现有 `InventoryCoordinator.beginExternalWrite(owner)` / `completeExternalWrite(needsRefresh)` 已被其他领域提交复用。调制 commit 采用同一接缝：开始时 `beginExternalWrite('equipment_tuning.commit')`，期间禁止 sort/discard/move；确定成功或 reconcile 完成后 `completeExternalWrite(true)`，刷新背包并轮换 lease。

## 6. 协议草案与事务不变量

### 6.1 命令面

协议字段名在 T2 实现前做一次最终冻结；操作集合不再扩张：

| cmd | 读写 | 用途 |
|---|---|---|
| `snapshot` | 只读 | 按背包 source lease 投影装备、cap、材料、tier/plugin 候选和拒绝原因 |
| `preview` | 只读 | 对某 operation 生成 before/after、材料 delta、依赖拆卸集和 opaque `tuningToken` |
| `commit` | 写 | 只接收 `expectedTuningToken`，执行服务端缓存计划 |
| `tooltip` | 只读 | 仅补调制候选特有 tooltip；装备主体尽量复用 inventory lease-bound tooltip |

`operation` v1 白名单：`enhance`、`convert`、`install_tier`、`install_mod`、`detach_mod`、`detach_all_mods`。

请求示意：

```json
{
  "v": 1,
  "domain": "equipment_tuning",
  "cmd": "preview",
  "operation": "enhance",
  "source": {
    "containerId": "背包",
    "slot": 7,
    "expectedLease": "opaque-inventory-lease"
  },
  "targetLevel": 9
}
```

转换额外带 `target` slot ref；插件/tier 只带服务端 snapshot 已返回的候选 key。Web 传来的 target level、候选名和 slot 都是不可信意图，AS2 必须重新校验。

### 6.2 token 绑定内容

opaque token 对应的 AS2 内部 plan 至少绑定：

- tuning session/open generation、operation、一次性消费状态和短生命周期；
- 主装备 container/slot、对象引用 lease、调制 confirm projection；
- 转换目标的独立 lease/projection；
- 精确材料 before count 与 delta；
- 强化 cap 的主线/铁匠依赖；
- tier transition、mod candidate、依赖闭包和相关配置签名；
- 预期 after projection、成就 delta、受影响槽集合。

commit 不接收价格、公式结果、after item、依赖拆卸列表或材料 delta。成功、确定失败、过期都会消费 token；超时/断连由 Host 进入 reconcile，不自动猜测 token 是否可重用。

### 6.3 原子提交不变量

1. `snapshot`/`preview` 零写：不改装备、材料、revision、dirty、achievement 或时间戳。
2. commit 开始时重新验证 token 会话、全部 slot lease、参与字段、规则依赖和材料精确数量。
3. 任一预检失败：零装备写、零材料写、零事件、零 revision、零成就、零 dirty。
4. 成功：装备字段、材料 delta、item timestamp、容器 touch、领域事件、成就与 dirty 形成一个逻辑 commit。
5. 转换同时触碰两槽；插件级联返还与 mods 新数组同时生效，不存在半提交。
6. 成就只在成功后记录一次；dirty 由服务显式触发，不依赖成就或 `acquire` 的副作用。
7. 回包包含受影响背包 snapshot、更新后的 tuning snapshot 和可诊断但不含内部 token 数据的 transaction id。
8. 确定 no-op 遵循 D10：成功但无任何持久化副作用。

### 6.4 Host 写状态机

新增 `EquipmentTuningTask`，沿用现有领域 Task 的 pending request 与 write gate 形状，但不把 panel 名当 domain：

```text
idle → write_pending → idle
                 └→ needs_reconcile
needs_reconcile → structurally-valid snapshot/new preview → idle
```

timeout、send failure、断连、callId/cmd 不匹配或畸形成功回包进入 `needs_reconcile`。已知的权威业务拒绝可直接回 idle。reconcile 只允许读取并要求玩家重新预览，不重放原 commit。

`WebOverlayForm` 需要新增 `equipment_tuning_response` 路由和 Task 注入；路由至少校验当前 active panel 是 workbench，最好同时校验当前 view/session generation。所有错误响应仍由 Host 盖回可信的 `domain/cmd/callId` 关联字段。

## 7. 旧 UI 绞杀与事实退役状态机

| 阶段 | 旧 AS2 renderer | Web | 业务 writer | 可回退性 | 放行门 |
|---|---|---|---|---|---|
| R0 当前 | 主入口，直接写 | 无 tuning | 多处分散 | 高，但语义分叉 | 本文 T0 |
| R1 权威抽取 | 仍为主入口，全部委托服务 | 无主入口 | 只有 `EquipmentTuningService` | renderer 可回退；writer 不回退 | 行为测试、writer scan、asLoader/TestLoader 证据 |
| R2 双前端 | 可选 fallback | workbench tuning 实验入口 | 同一服务 | feature flag 切主入口 | Host/Web harness + 真机事务/回读 |
| R3 正常路径改道 | 调制按钮优先打开 Web；Launcher 不可用才留旧 renderer | 默认主入口 | 同一服务 | 有受控兼容回退 | 入口/关闭/断连/重开真机 Gate |
| R4 事实退役观察 | 正常入口为零，保留冷 fallback | 稳定主入口 | 同一服务 | 可应急启用旧 renderer | 观察窗、来源指标、无 reconcile 积压 |
| R5 资产删除 | 只在整个旧 Hub 责任清空后删除 | 完整替代 | 同一服务或后续域服务 | 不可回退 | 装备槽、属性、材料、情报等其余责任均退场 |

这里的“不太好回头”应只发生在 R1：旧 UI 永久失去直接写权限，这是值得接受的单向门。R2/R3 的 UI 路由必须可回退，因为 WebView/Launcher 可用性是运行环境问题；回退时仍调用新服务，所以不会重新产生两套业务语义。

建议记录入口来源与结果：`workbench_item_action`、`legacy_tuning_redirect`、`launcher_unavailable_fallback`，以及 operation、success/rejected/reconcile。事实退役的判断是正常路径 legacy renderer 使用量归零且 fallback 只在明确环境故障出现，不是“代码已经存在 Web 页面”。

## 12. 最终裁决

将装备调制作为下一个目标是合适的，而且比先迁装备槽/属性更符合当前工程成熟度。它把背包这个高出场率入口转化为实际编辑工作台，同时用一个边界清晰的切片启动旧装备 UI 的事实退役。

真正应当单向推进的是 **writer 权威收口**：一旦旧 renderer 全部委托 `EquipmentTuningService`，就不再允许退回分散直接写。Web 是否默认开启则继续可逆，直到事务、断连、重启回读和真实入口观察都通过。这样既实现绞杀式重构，又保留玩家在迁移期完成全套装备流程的安全退路。
