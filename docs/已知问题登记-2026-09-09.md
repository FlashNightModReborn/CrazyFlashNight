## 问题 1：焦点在 SWF 内按 Alt，游戏画面卡死

**状态**：预防性修复已部署（`promoted / FIELD_REVALIDATION_PENDING`），正式入口效果待复验。功能契约见[焦点诊断 §9.14](焦点管理-诊断与卡顿排查-2026-05-24.md#914-2026-09-10裸-alt-菜单防护与嵌入菜单清理)，发布身份和部署状态见 [runtime 发布记录](runtime-build-reproducibility.md)。

### 现象

- EXE 启动进游戏，**只有焦点在 SWF 内时**按 Alt 才会卡死；焦点在 Web 面板或其它窗口时按 Alt 无此现象
- 卡死后再按任意键，SWF 立刻恢复
- 卡死期间：Web（WebView2）动画仍正常播放，但鼠标 hover 等交互不触发；SWF 完全冻结
- 按字母键时曾听到系统提示音。单凭提示音不能确认菜单归属，也不能证明它与卡顿互相独立。

### 定位边界：疑似菜单模式，不能只归因于 Flash 的系统菜单位

Flash 是独立进程（`Adobe Flash Player 20.exe`），被 `SetParent` 成子窗口嵌入 Guardian，且 `WindowManager` 会主动把键盘焦点交给它。旧代码两处样式掩码均保留 `WS_SYSMENU`，但这只能证明存在未清理的菜单入口，不能证明原事故的循环必定发生在 Flash 线程。

```
裸 Alt / F10 松开
  → 默认键盘消息处理可向顶层窗口发送 WM_SYSCOMMAND / SC_KEYMENU
  → 顶层 Guardian 原本也会继续交给默认处理
  → 可能进入菜单模式；实际 menuOwner / capture 与停顿线程须从现场确认
```

Windows 的 [WM_SYSKEYUP 契约](https://learn.microsoft.com/en-us/windows/win32/inputdev/wm-syskeyup)明确包含向顶层窗口发送 `SC_KEYMENU`。WebView2 有独立 renderer / GPU 进程，因此“Web 动画继续”不能排除 Guardian 消息处理受阻，也不能单独证明 Flash 抢走了 capture。现有 `FocusWindowSnapshot` 的 `guiFlags`、`menuOwner`、`capture` 和窗口 style 可用于复现期间区分这些路径。

## 问题 6：调度器池化节点的陈旧残留可顶掉合法任务（`TaskIDNode` 归属歧义）

**状态**：**仅登记，未修复**。分析结论与候选方案已给出，对应代码改动已于 2026-09-12 **全部回退**（见文末「回退记录」），当前代码与 HEAD 一致。

**与问题 4/5 的区别**：问题 4/5 是用户可见的功能缺陷；本问题是**调度器内部的正确性隐患**，尚无已被确认的现场事故样本。"整个游戏啥事件都无法触发"的现象曾一度被怀疑与本问题相关，但该推测**未获证据支持**，不作为本条的定性依据。

---

### 现象与触发路径

`org.flashNight.neur.ScheduleTimer.TaskManager` 的分发循环按 `node.taskID` 从 `taskTable` 取任务执行：

```as2
var taskID:String = node.taskID;
var task:Task = this.taskTable[taskID];
if (task) { /* 执行 */ }
```

**问题**：`TaskIDNode` 是**池化复用**对象，`taskID` 字符串同样会被复用。节点从池中被取出给新任务时，`taskID` 被重写为新任务 ID，于是：

- 若某个节点是**上一次复用留下的陈旧残留**、仍挂在调度结构的链表上，它的 `taskID` 就可能与**另一个正在运行的任务** ID 相同；
- 该残留节点被 tick 提取到分发循环时，会按 `taskID` 命中那个**合法任务**并**再执行一次**（重复执行）；
- 更严重的是 `removeTask` / `rescheduleTaskByNode` 等按节点操作的路径，会用这个陈旧节点去操作 `taskTable`，**顶掉并发的合法任务**。

也就是说：**"`node.taskID` 等于我的 taskID" 并不能证明这个节点是我这一轮占用的。**

### 相关既有脆弱点（同一区域）

| 位置 | 说明 |
| --- | --- |
| `TaskManager.removeTask` | 从 `taskTable` 删除 task 后**未清 `task.node`**。该 task 若被再次重新调度，会拿一个已被回收（甚至已被别的任务复用）的节点去 `taskTable` 里顶掉并发的合法任务 |
| `TaskManager.updateFrame` 分发循环 | 回调内若删除了"本链表中位于当前节点之后"的节点，`node.list.remove(node)` 会改动那些节点的 `prev`/`next`，此处缓存的 `nextNode` 可能已解链（`nextNode.next` 变为 `null`），继续沿缓存走会**丢掉本帧剩余的全部任务** |

### 关键约束：`reset(非 null)` 是「原地复用」语义

这是本问题**最容易踩的坑**，也是候选方案第一版失败的根因：

`SingleLevelTimeWheel.as` L390 / L423 会在**节点仍然存活**时调用

```as2
node.reset(node.taskID);   // 原地换槽位复用，节点并未作废
```

调用方是 `rescheduleTimerByID` / `rescheduleTimerByNode`，而 `CerberusScheduler.rescheduleTaskByNode` 走的正是这条路径（`removeTaskByNode` 分派到 `removeTimerByNode` / `minHeap.removeNode`）。

> **铁律**：`reset(null)` = 回收到池、节点作废；`reset(非 null)` = 原地复用、节点仍有效。
> **任何附加在节点上的状态都不能在 `reset(非 null)` 路径上被清掉**，否则正在跑的合法任务会被误判为残留而跳过执行 → **任务停摆**。

### 候选方案：`TaskIDNode.epoch` 单调计数器

| 层 | 改动 |
| --- | --- |
| `TaskIDNode.as` | 新增 `public var epoch:Number = 0`；`reset()` **仅当 `newTaskID == null`** 时清零 |
| `SingleLevelTimeWheel.as` | 新增 `_epochCounter`；`acquireNode` 里 `node.epoch = ++_epochCounter` |
| `FrameTaskMinHeap.as` | 新增 `_epochCounter`；抽出统一 `acquireNode`（3 处取用点全改走它）；两个 `reschedule*ByNode/ID` 在 `removeNode` 后**补分配**代次 |
| `Task.as` | 新增 `public var nodeEpoch:Number = 0`（快照） |
| `TaskManager.as` | 分发时 `if (task && node.epoch != task.nodeEpoch) task = null;`；**14 处** `task.node = ...` 赋值点全部跟一句 `task.nodeEpoch = task.node.epoch` 快照 |

**语义**：`epoch` = 节点「这一轮占用」的身份，由 `acquireNode` 分配，与 task 的持有关系一一对应；`node.epoch != task.nodeEpoch` 即判为陈旧残留，跳过执行并做防御性回收。

### 候选方案的自查结论（若将来实施，这些坑必须一并处理）

实施期间做双向穷举，抓出 **3 个必须处理的遗漏**与 **1 条铁律**：

1. **`addSingleTask` / `addLoopTask` 必须补快照**。这两个是最常用入口，漏快照 = 这两个入口的任务**全部停摆**。
2. **`FrameTaskMinHeap.rescheduleTimerByNode`**：`removeNode` 内部已 `reset(null)`（epoch 归零 + 归还堆池），随后的 `insertNode` **不会**补分配 → 节点以 `epoch=0` 回链 → 被误判为残留。需在 `removeNode` 后补 `node.epoch = ++this._epochCounter`。
3. **`FrameTaskMinHeap.rescheduleTimerByID`**：同上，且中间多一次 `node.reset(taskID)`（此刻 epoch 已是 0，救不回来），同样需补分配。
4. **铁律**：`reset(非 null)` 路径上不得清任何附加状态（见上节）。

**双向穷举结果**（若按上述实施）：误跳过（8 条场景）全部封死；误执行也封死 —— 残留节点要通过校验需 `node.epoch == task.nodeEpoch`，但 acquire 是独占的，一个节点同一时刻只被一个 task 持有，故不可能与旧 task 的代次相等。
