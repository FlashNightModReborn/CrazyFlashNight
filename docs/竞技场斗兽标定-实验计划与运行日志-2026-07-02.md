## 2. 后续会话最短交接流程

新会话接手时先读本文，再按以下顺序执行：

1. 确认没有其他任务占用标定专用槽或 arena runner。
2. 读取 [automation/README.md](../automation/README.md) 的现役 arena unattended 入口；不要硬编码端口或手工构造无授权 `/task`。
3. 读取 campaign checkpoint / exception inbox；本文“当前候选池”和“下一批计划”只保留历史兼容记录。
4. 接收用户的 `raw_submission`，由系统生成 candidateId、配对、side swap、预算和 `case_manifest.json`。
5. 运行现役 `run-unattended.js`；由授权 client 执行 `startBatch` 并轮询 `status`。
6. 批次结束或崩溃后，只以已经落盘的 JSONL 为准生成 summary。
7. Campaign 自动写运行索引、候选状态和剪枝 receipt；人类只处理异步 exception inbox、PVE packet 和正式 recommendation bundle 批准。

PowerShell 运行前置：

```powershell
chcp.com 65001 | Out-Null
```

状态查询和 `startBatch` 由 `tools/arena-calibration/run-unattended.js` 内部的授权 client 完成。F8 后 standard normal 与 explicit legacy HTTP automation 互斥；本实验不得恢复固定端口扫描、未授权 `Invoke-RestMethod` 或 standard Agent Runtime 中的 `/console` 旁路。

下列分析命令只用于 Campaign Gate B 前的兼容 / 诊断流程；Gate B 后由 Supervisor 自动运行，不要求人类逐批执行：

```powershell
node tools/arena-calibration/analyze-results.js `
  --input logs/arena-calibration/<batchId>-results.jsonl `
  --summary tmp/arena-calibration/batches/<batchId>/summary.json `
  --summary-md tmp/arena-calibration/batches/<batchId>/summary.md

node tools/arena-calibration/plan-next-batch.js `
  --summary tmp/arena-calibration/batches/<batchId>/summary.json `
  --output tmp/arena-calibration/batches/<batchId>/next_batch.json `
  --planner rule
```

无人值守入口（推荐用于离开机器后的冷启动到 batch 全链路）：

```powershell
node tools/arena-calibration/run-unattended.js `
  --slot cf7_agent_arena_calibration `
  --seed-slot crazyflasher7_saves2 `
  --manifest tmp/arena-calibration/batches/<batchId>/case_manifest.json
```

该命令会自动把 manifest 规范化到 `tmp/arena-calibration/batches/<batchId>/case_manifest.json`，必要时通过 `automation/start.ps1` 启动 Launcher。启动前 runner 会把专用槽从 `--seed-slot` 或最新有效 shadow 存档播种，备份目标槽位 JSON/SOL 并删除目标 SOL 残留；默认拒绝 `crazyflasher7_saves*` 正式槽与 `--fresh`。进入 Flash 后，runner 通过 agent 入口执行原“确认存档进入游戏”动作，等待 `readyForArenaCalibration`；该状态必须包含安全 snapshot 决议和 AS2 `agent_runtime_status` 的 `saveRuntime.loaded=true`。之后再调用 `arena_calibration startBatch/status`，最后写 `tmp/arena-calibration/unattended/<timestamp>-<batchId>/summary.*` 与 `run-report.*`。如果结果不完整或出现 `aborted` / `bridge_lost` / `error` 等异常行，会生成新的 rerun manifest（默认在 `tmp/arena-calibration/batches/<rerunBatchId>/case_manifest.json`）；`--max-recovery-attempts` 默认为 1，表示首轮失败后自动关闭 Launcher、重启进档并补跑一次剩余 case，所有 attempt、补跑 manifest、失败清单和建议都归档到 `run-report.*`。如只想生成最小 pilot，显式使用 `--generate-pilot --batch-id <id>`；不要让脚本默认选择正式玩家存档。

构建 / 编译门禁：

- 默认 `--build-gate arena-tools`，只跑斗兽标定 Node 工具自检。
- 改 Launcher/C# 后用 `--build-gate launcher`（等价 `launcher-build,launcher-tests`）。
- 改 AS2 标定 runner 后按触及层用 `--build-gate as2-publish` 或 `--add-build-gate as2-test`；成功表述仍必须符合 `testing-guide` 对新鲜输出、SWF 刷新和 trace 的要求。
- 除 `arena-tools` 外，runner 会先尝试关闭已有 Launcher，再跑 gate；gate 失败会在 `run-report.*` 里记录命令、退出码和输出尾部，并停止，不继续启动游戏。
- 自动恢复只用于 runner 自己生成的 rerun manifest，不负责自动改数值、改 AS2 业务逻辑或无限制重编译；需要重编译时应显式选择对应 build gate。

## 3. 组合征集格式

测试群或维护者提交的是 `raw_submission`，允许直接提供表格行、名单、JSON 或工作簿中的可定位记录。每条组合只要求：

| 字段 | 必填 | 说明 |
|---|---|---|
| `combination` | 是 | 待标定组合；可以是 roster、表格单元格或现有配置引用 |
| `source` | 是 | 提供者、工作簿行、已有关卡或人工锚点 |
| `claimedTier` | 否 | 提供者的主观档位，只形成弱先验 |
| `notes` | 否 | 已知技能、召唤、远程或异常风险 |

roster 单位格式：

```json
{ "type": "兵种44", "level": 30 }
```

示例：

```json
{
  "source": "manual-anchor",
  "claimedTier": "mid",
  "combination": [
    { "type": "兵种44", "level": 30 },
    { "type": "兵种45", "level": 30 },
    { "type": "兵种48", "level": 30 },
    { "type": "兵种49", "level": 30 }
  ],
  "notes": "提供者认为接近中档"
}
```

`schema`、`submissionId`、摄取时间和 hash 由 intake adapter 自动注入，不是提交者字段。系统再生成 `normalized_candidate`、稳定 ID / hash、完整参数、默认值、风险标签、anchor / bridge / side swap 和采样预算。人类不负责填写 `caseId`、双方配对、repeat、timeout、阵型或内部 manifest。只有会改变组合语义且无法从源数据推导的歧义，才按 `dedupeKey` 汇总到异步 exception inbox 后批量询问。

## 4. 批次执行策略

### 4.1 崩溃容忍

批次设计必须默认游戏、Flash、launcher 或通信链路随时可能崩溃。

- JSONL 是唯一可信进度源；未写入 JSONL 的 run 视为未完成。
- 每个 batch 保持可恢复，不依赖聊天记录判断进度。
- 崩溃后不手工改 JSONL；生成补跑 manifest。
- 补跑 manifest 只包含缺失 run 或需要追加样本的 case，并使用新 `batchId`。
- 单个 batch 不宜过大，避免一次崩溃损失过多排队状态。

### 4.2 批次规模

| 阶段 | 建议规模 | 目标 |
|---|---:|---|
| smoke | 1 到 5 run | 验证游戏已连通、场景可跳转、JSONL 可写 |
| exploration | 30 到 100 run | 探索新组合、发现明显偏向、验证稳定性 |
| stability | 300 到 1000 run | 无人值守稳定性、崩溃恢复、异常频率统计 |
| confirmatory | 每个候选 30 到 100 run | 对接近平衡组合做独立复核 |

首批结果 45 run 用时约 519 秒，可粗略估算 1000 run 为数小时级别。真实耗时取决于单位组合，召唤、远程拉扯、零血不死检测会显著影响耗时。

### 4.3 timeoutFrames

- 常规探索批默认 `1800`。
- 已知长僵持组合可以提高到 `3600` 或 `5400`，但必须记录原因。
- timeout 不等于普通错误；应单独统计为稳定性和战斗设计信号。
- 若 timeoutRate 明显升高，不要直接拿胜率做平衡结论。

## 5. 剪枝与追加样本规则

规则只在批次结束后应用，不在单局中途改变计划。

| 条件 | 动作 | 说明 |
|---|---|---|
| 样本 < 10 | `append_repeat` | 不做最终判断，只追加样本 |
| blueWinRate <= 0.2 且样本 >= 10 | `drop_or_counter` | 明显红方强；若是关键档位，保留反向/邻近档复核 |
| blueWinRate >= 0.8 且样本 >= 10 | `drop_or_counter` | 明显蓝方强；同上 |
| 0.35 <= blueWinRate <= 0.65 且 timeoutRate 低 | `promote_candidate` | 进入候选池，追加到 30/50 样本 |
| 0.2 < blueWinRate < 0.35 或 0.65 < blueWinRate < 0.8 | `adjacent_probe` | 做邻近等级、人数或 side-swap 探索 |
| timeoutRate > 0.2 | `stability_investigate` | 先处理稳定性或战斗僵持，不直接判强弱 |
| errorCount > 0 | `stability_investigate` | 查 schema、spawn、bridge、stage、AS2 runtime |
| ZeroHPDetector 频繁出现 | `stability_watch` | 结果可用但要标注风险，长批次单独计数 |

side bias 处理：

- mirror case 默认要求 side-swap 或追加样本。
- 非 mirror 但人数组合反转后应存在对应 case，例如 `2v4` 与 `4v2`。
- 若同强度 mirror 长期偏向红方或蓝方，不直接用单侧胜率做 benchLevel 结论。

## 10. 置信度与复核策略

探索批只负责缩小空间，不给最终结论。

候选进入 confirmatory 的最低条件：

- 样本数 >= 30。
- timeoutRate 接近 0，或 timeout 已有明确解释。
- errorCount = 0。
- 胜率不一边倒，且 HP 残余分布支持“接近均衡”的解释。
- side-swap 或反向组合没有暴露明显出生点/阵营偏置。

最终抽样复核：

- 从 `promote_candidate` 中抽样复跑独立 batch。
- 从 `drop_or_counter` 中抽样复核明显强弱结论，防止早期剪枝误杀。
- 从 `stability_watch` 中抽样复核 `ZeroHPDetector` 或 timeout 频率。
- 复核批应使用新的 `batchId`，不要复用探索批 manifest。
