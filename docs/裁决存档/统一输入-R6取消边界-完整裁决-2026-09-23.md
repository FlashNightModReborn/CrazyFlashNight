# R6：AVM1 持键切出后的安全取消与 C1 施工顺序裁决

日期：2026-09-23  
性质：独立裁决与下一轮验证路线；不是施工授权、发布许可或运行时修复回执。

## 总裁决

**R6 悬停窄修补可以进入受限人验；当前持键取消不能通过验收，不能据此重新开放旧 Flash 端点，更不能以 native cancel ACK 作为 C1 跨端点交接完成条件。**

反例已经证明“native/传输层结束”与“AVM1/业务手势结束”发生分离，但尚未证明所有保留当前 Flash 宿主的无 Up 取消路径都不存在。当前最值得先做的最小判定，是补齐虚拟 capture 生命周期的观测和对照；这是一条有源码根据的未验证假设，不是已查明根因。

推荐顺序：**关闭不安全重新准入 → 强化真实 Flash oracle → 做一次有边界的虚拟捕获撤销实验 → 成功则按已证兼容范围采用窄 native 修补；失败则停止 native 消息试探，转入一个交互域的 AS2 显式取消/手势协议 → 通过该域双向交接，再进入 C1 的交互纵切。** C1 的非交互合成准备可与上述验证分开；B 的扩大覆盖不得越过取消门禁。

本裁决不要求重开 S/P/F 合成架构，也不要求为了画面准备先迁完全部 AS2 UI。但任何正式跨端点交接，都必须证明**原输入域已经安全失去业务执行资格**，而不是仅证明新 Web/Native 面板工作正常。

### 1.2 native ACK 为什么不能作语义证明

`CancelEndpoint()` 在 `InputBridge.cpp:L153–L165` 做的是：先清本桥的 enabled/buttons/captured/activeGesture，调用原 `WM_CANCELMODE`，按需释放真实 capture，然后写 `cancelledTicket`。它没有调用或等待 AS2 取消回执。

`InputBridge.h:L47–L62` 的 `cancelledTicket`、`completedSeq`、`heldButtons`、`quiescedTicket` 均属于桥接/原窗口调用层。`ControlQuiesce` 检查队列和本桥状态；它不能证明 Flash 的按钮状态、已排队 AS2 回调或业务延后任务都消失。`NativePointerBridge.RaiseMinEpoch()` 返回 true 也只说明成功发布了 floor 和持久取消请求，不是取消已完成。

微软对 WM_CANCELMODE 的默认处理描述为标准滚动条、菜单及 mouse capture 的取消；没有为第三方 AVM1 按钮状态给出承诺。[W1]

### 1.4 下一轮所需的最小观测

## Q2｜保留当前 Flash 宿主，能否证明无业务 release 副作用的取消？

### 2.1 三个不同问题，不能合并回答

**对当前未改 AS2 + 当前 native 实现：不能认定存在已证可靠取消。** 当前候选已经失败，必须拒收。

**对任何保留当前 Flash 宿主的方案：本案不足以证明不可能。** 有一个应优先验证的 native 生命周期缺口；AS2 协作也可以建立逻辑取消，不需要替换 Flash runtime。

**对任意未迁移旧按钮/跨 SWF：不能给“全局、透明、无副作用”的通用保证。** 没有覆盖所有可能提交入口，任何恢复资格都只能按已证输入域发放。

这里还要分开 safety 与 liveness：拒绝旧 release 可以改善安全，但首击被吃仍是活性失败；首击恢复但补出 releaseOutside 则是安全失败。两者必须同时满足，不能拿一种换另一种。

### 2.2 优先 native 判定：虚拟 capture 有没有丢失对称撤销通知？

源码 `InputBridge.cpp:L89–L105` 将 SetCapture/GetCapture/ReleaseCapture 虚拟化。映射生效时，SetCapture 可以只设置本地 `captured=true`，不真正调用 Windows SetCapture。取消又在 `L157` 先抹掉这一事实，然后只在 `realGetCapture()==target` 时释放真实 capture。

如果压根没有取得真实 capture，就不能假定真实 ReleaseCapture 会生成某个原生失捕获通知。本案四组已附 trace 均未记录 `WM_CAPTURECHANGED`，虽有该消息的观测分支 `L339–L340`。这足以提出**值得优先试验**的假设，但没有调用级 capture 记录，尚不能确认 Flash 在这次 press 中实际请求了虚拟 capture，更不能认定补一条消息一定修复。

微软说明，窗口失去 capture 时会收到 WM_CAPTURECHANGED，包括自己调用 ReleaseCapture 的情形；该文档说明的是 OS capture，并不为此桥自行维护的 bool 提供通知。[W2]

最小实验规定：

1. 保留当前失败版本，另做真实原生 Flash 对照，记录真实按下/失焦时完整 capture 撤销顺序。
2. 只有确实观察到该手势曾持有**虚拟 capture**，才实验一条与该虚拟所有权相配的撤销路径：入口先封住，采用明确无按键的取消查询视图，完成 virtual capture 从持有到无持有的单次转换，并在目标 UI 线程发出与它对应的 capture-lost 通知。该通知与原 WM_CANCELMODE 的先后及重入必须固定、追踪、做对照。
3. 不实际夺取外部窗口的 capture，不为“制造通知”而先 SetCapture 再 ReleaseCapture，不补 MouseUp，不调用按钮 release 方法，不抢焦。若原调用引发重复 capture 撤销，必须证明幂等/不会重复进入。
4. 取消期的 GetKeyState/GetAsyncKeyState/GetCapture/GetCursorPos 视图要明确。当前 `enabled=false` 会回落到真实查询，不能把“本地 buttons=0”说成 Flash 读到的按键必然为 0。坐标仍需尊重 DPI 与明确 outside 的语义。
5. 用下文矩阵同时证明取消期无 release/outside 业务和之后第一真实点击独立成立。失败就保留反例并停止此 native 候选，不追加延时、空点、Up 或消息扫表来凑通过。

这是一轮**候选机制判定**，不是预先指定可以合入的修复。没有观察到 virtual capture，或通知未改善、产生副作用、只能对 A 有效，都应结束这条解释，而不是把“capturechanged 应该有用”提升成事实。

即使实验成功，也只可绑定“固定 projector/bridge/SWF 交互类型与版本”的已测取消能力；原 native ACK 不自动变成无条件的 AS2 ACK。新增 Button、加载内容或处理器类型必须进入兼容/覆盖清单。要承诺任意业务无副作用，仍需业务层覆盖证据。

### 2.3 当前源码还存在一个独立的重新准入缺口

`WorldCompositionSurface.CancelPointer()` 在 `L267–L283` 发布 floor 后，将 `_physicalButtons`、`_postedButtons` 和 `_openGesture` 清零，但没有像 `Rebind()` 那样设置 `_awaitRelease/_awaitFreshDown`。`IntakePointer()` 因而可能把尚属旧物理手势的后续 Up 重新标成当前 epoch。

静态可达反例：旧 Down 已到 Flash → 持键时发生 geometry_changed、hidden 或显式取消 → Host 升到 epoch e+1 并清账 → 取消返回 → 不发生 WM_KILLFOCUS，因此 localFloor 没有再升一档 → 玩家此时才松开 → Up 被打成 epoch e+1，仍高于 shared floor → native 将其作为 unowned release 计数但继续转交原 WndProc。

此可达路径由 `Surface:L95–L117,L267–L283`、`Controller:L326–L352`、`InputBridge.cpp:L235–L289` 共同决定；**这里没有声称已经在真实 Flash 重现了它的业务后果**。本轮移动/resize 是在前一个点击结束后测的，未覆盖这一持键交错。

最终失焦用例之所以拒绝 seq=201，是 localFloor 恰好比 Host epoch 高一档，不能用它代证所有取消原因。必须分别维护“物理仍按住”与“业务所有权已撤销”两个账本；业务清账不能伪造物理已抬起。

### 2.4 状态机与证明义务

建议给当前输入域增加以下最小状态，而不是重写整个架构：

```text
READY_FOR_FRESH_DOWN
  └─ 合格的新真实 Down → HELD(g)
HELD(g) / UNKNOWN_DIRTY
  └─ 取消原因 → REVOKING（关闭业务准入、抬 floor、撤销 g）
REVOKING
  ├─ 取消能力/确认不足或超时 → BLOCKED
  └─ 原生退场 + 本域取消证明成立 → WAIT_NEUTRAL
WAIT_NEUTRAL
  ├─ 物理仍按住 / 状态来源不可确认 → 保持关闭
  └─ 已确认全部相关物理按钮抬起 → READY_FOR_FRESH_DOWN
```

取消确认与物理抬起可以并行发生；开放必须取两者交集，不必强制等待固定时间。显示画面、AS2 普通帧推进不需要因此停止。

开放条件至少为：

```text
native retirement/quiescence confirmed
AND cancellation semantics certified for this exact scope/incarnation
AND neutral physical baseline qualified
AND current owner/source/content identities still valid
AND next Begin is a genuinely new physical gesture
```

“取消语义成立”分两种：旧式 native 回调域必须证明 VM 手势确实复位；完全迁移、以独立协议驱动业务的域可以证明旧 VM 回调不能触及业务，并不宣称 VM 私有状态已清零。不能把第二种能力颁给未迁移按钮。

撤销须幂等；被取消 g 不能因后续 `gateOpen=true` 复活；当前 ACK 不能覆盖新发生的取消；原生 original 调用/AS2 协作期间不得在 LL hook 或 UI 线程跨线程同步阻塞等待。

物理基线查询也不能盲信一个零值。GetAsyncKeyState 在非活动桌面/UIPI 等访问失败时可以返回零，且物理左右键与逻辑映射需要区分。[W3] 无法确认时保持关闭，等待合格的真实输入边界；不以超时当作已经松开。

| 故障恢复 | Flash 卡顿、进程退出、通信断开、计数边界、取消回执丢失 | 有界失败后输入关闭；不通过重载、夺焦、重放或补 Up 冒充恢复 |

需要负控：原始当前版本必须仍能触发 fresh-click 失败；故意绕开业务门禁时，“有毒”release/outside/延后提交必须让 oracle 判败。不能把仅存在日志、按钮换色、native handler 返回当作通过。

两条路线的通过口径不得偷换：透明 native 路线必须修复原有 raw `fresh_click_after_focus_return` 断言。完整 AS2 协议路线保留该原生断言的实际结果，不将其改名变绿；另行验证每次新的真实手势恰有一个逻辑 Begin/End 和至多一次授权提交，并明确不再承诺未复位的原生回调语义。该域若仍依赖旧原生按下状态驱动关键视觉/拖动，也必须一并迁移或继续拒绝准入。

## Q3｜需要 AS2 协作时，最小协议与旧按钮/跨 SWF 覆盖

### 3.1 先声明取消能撤销什么

取消撤销的是**尚未合法提交的手势资格和临时状态**，不是撤回已经执行的 onPress 业务。若旧按钮在 press 中已发物品、扣钱、存盘，再晚的取消也不能凭空消除既成事实。应把“按下预览/预留”和“确认提交”拆开，或明确那类按钮的 press 本就是提交边界；不能用事后回滚掩盖非法 release。

建议把线性化点设在同一个权威提交域的取消处理处。已经线性化提交的动作单列记录；不能声称可抢占任意正在执行的 AS2 handler。如果承诺从 Host 撤销时刻就禁止提交，最终副作用入口还必须读取/验证与 Host 撤销一致的资格，或把提交纳入同一权威序列。仅发送异步 AS2 Cancel，不能抹平跨线程竞态。

### 3.2 最小身份与消息合同

建议身份元组：`session + scopeIncarnation + ownerEpoch + gestureId + button + beginSeq + targetIncarnation`。字段可以复用现有 session/epoch/sequence，不要求为了本裁决扩位；有界计数耗尽时仍执行已定义的安全退役，不能回绕复用。

64 位 session 传 AS2 时用十六进制/十进制字符串，不作为大整数 Number 参与等值身份判断。内容/实例 incarnation 不能只用 `_name`、路径或 HWND。

| 消息 | 最小字段/效果 |
|---|---|
| REGISTER | protocol、session、scopeIncarnation、contentBuild、coverageRevision、capabilities；声明实际覆盖的根与控件类别 |
| CANCEL | exact session/scope、ticket、撤销到的 ownerEpoch/gesture、lastAdmittedSeq、cause；先关门，撤销 ledger、拖动/预览/保留、失效延后任务 |
| CANCELLED | 回同一身份/ticket/coverageRevision，说明 gateClosed、canceledThrough、剩余可提交旧义务为零；不得伪称“AVM1 内部必清零” |
| READY | 在覆盖清单稳定、物理基线合格后确认可接新的真实 Begin；不能由任意迟到 ACK 开门 |
| BEGIN / UPDATE / END | 仅来自新真实输入边缘的顺序化意图；携带 gesture、beginSeq、targetIncarnation；每个 Begin 最多一个终结 |

`CANCELLED` 的“零”不是要求游戏停止所有 onEnterFrame，而是被撤销手势的任务已完成或被不可逆失效，之后没有路径能提交它们。控制消息重复应幂等；乱序、错 session、错实例、旧 ticket 的 ACK 只能被拒绝。通信失效或异常保持禁用。

包内 XMLSocket 只证明 AS2→Host 事件回传，没有给出生产 AS2 命令入站、消息排序及ACK实现。实际施工须先证明可用的双向管道和取消屏障；不能假设现有 projector 暴露了随意同步调用 AS2 的接口，也不能在 WH_MOUSE_LL 内阻塞等待。

### 3.3 “加一个 canceled 标记”只能解决部分安全问题

若只是包装旧 `onPress` 记录 gesture，再让 `onRelease` 在 canceled 时返回，那么取消后首击没有 press 的反例仍然存在：旧 release 可以拒绝，但新手势依旧没建立。这个补丁不能以“没有误提交”宣布恢复第一击。

要同时得到 safety 与 liveness，在完全迁移模式中，业务 Begin/End 必须由有身份的**新真实物理边缘协议**驱动，而不是等待 AVM1 再次发出 onPress。原 `onPress/onRelease/onReleaseOutside` 仅作可视兼容/诊断或被完整业务门禁屏蔽，不能与新 dispatcher 双重提交。

不得把当前 Down 的 epoch 临时放进全局变量，就把紧随其后的旧 AVM1 release 重新解释成新点击。没有原手势身份的旧 callback 不能借新 ownerEpoch 合法化。也不通过手工调用 `.onPress()`、`.onRelease()` 补业务事件。这条路径是对当前真实输入的一次分发，不是补发系统 Up 或重放已经丢失的点击。

最小迁移单位应是一个完整交互域/按钮工厂，加其真实提交入口；业务函数从原 handler 中抽出，只接受该域的有效 gesture。命中、坐标变换、遮挡、drag 与目标实例销毁必须由 AS2 侧适配器验证，Host 不得凭屏幕矩形猜测一定命中了旧按钮。

### 3.4 旧按钮分级，不能一刀切成“已协作”

**M：完整迁移。** 所有相关 callback、按下行为、拖动、键盘替代激活、定时/帧延后提交都经同一资格检查。取消有独立 cleanup，不转调 release/outside。旧 raw callback 永远不能直接写业务。具备本域 CANCELLED 能力。

**G：仅加保护。** guard 能拦部分旧 release，但仍依赖原生 onPress 建立新手势。只可证明实际覆盖到的安全子集，不能宣称第一击恢复，也不能冒充 M。

**U：未迁移/覆盖未知。** 不能出 AS2 语义取消 ACK。只能使用已经证实适配该类型的 native 取消能力，或者在需要安全取消/重入时保持该域关闭。不能给它自动补 Up、吃掉第一击后偷偷恢复或默认沿用 M 的资格。

全局 Mouse listener、遮罩、根 MovieClip.enabled、遍历当前实例替换方法，都不是“可拦所有已编译 Button/on() 回调”的证明。需要按源码/导出动作清点并修补：动态属性 handler、元件时间轴 on(release/releaseOutside/press)、原型/工厂、后续脚本重新赋值、全局 Mouse、跨 SWF 直接调用和真正副作用函数。

如果一个旧按钮任意代码仍可直接修改物品或存档，那么只在外层加 Host 通知没有完成迁移。这也是为什么本轮两个 MovieClip 不能代签真实修改器、NPC 和其他 SWF。

### 3.5 跨 SWF 最小规则

以实际加载根/实例 incarnation 注册，不假定每个 SWF 的 `_root` 或 `_global` 是同一取消权威。通过明确的 coordinator 引用/消息域对接；覆盖 `_levelN`、loadMovie/loadMovieNum 和动态实例生命周期。

注册必须先于交互生效。取消冻结一个 coverageRevision，父域只有在其中所有参与端点已撤销或已确认退出后，才能聚合 CANCELLED。取消期间新加载交互根默认关闭；同名重载必须产生新 incarnation，旧 ACK/闭包不能对应到新实例。

未注册子 SWF、不受控沙箱、无法列出的提交入口，均意味着覆盖未知；不能因父域响应了 Cancel 就宣布全 Flash 可重新开放。卸载旧实例也不自动证明 VM capture/排队 callback 已无影响，仍需 native 退场及 token 失效证据。

这不要求一次迁完整个游戏，但要求 C1 实验选取的交互岛**确实隔离**：残留未知旧按钮不能继续收到会触发业务的 raw 边缘/通知，也不能通过其他入口绕过提交资格。做不到隔离时，就不能只迁新面板两个按钮而放行旧 F 域。

## Q4｜R6 窄修补的人验与 C1/B 的顺序约束

### 4.1 R6 可独立受限人验，但“可测”不等于“已安全发布”

保留映射生效时隔离源 F 的 WM_MOUSELEAVE，以及明确 P 离开哨兵为负坐标的窄修补。它们有独立于持键取消的证据。源 LEAVE 与 P 的映射 leave 本来就是不同的输入边界；官方 TrackMouseEvent 对原窗口通知的定义与此解释一致，但修复效果以本案 before/fixed/final 回执为准。[W4]

受限人验只覆盖已确认无持久化写入的悬停、普通完整单击和纯 UI 关闭；或者使用隔离测试档/禁用写盘环境。**不能因为测试者“只点页签/NPC 取消”就默认不会触发自动存盘或剧情写入**，真实源码未附的动作须先核对。不得改真实存档，不发物品、不购买，不用真实高价值动作验证取消。

使用 exact 配对候选，确认未混入 pre-down 试验，保留最终 33/34 的失败状态。`inputTestCap=0` 只是记录未启用会话压力上限，不能解释成输入被禁用或业务已隔离。`entry-observed.json` 中的 PENDING 不应被本裁决改写成人验通过。

一旦出现持键失焦、持键几何切换、孤立 release、额外副作用或首击丢失，停止当前交互路径并保留日志；不重复点击“试到正常”，不自动重启/重载继续。当前包没有实现完整语义隔离，所以受限人验是已知风险下的小范围观察，不是对取消安全性的保证。

### 4.2 C1 应按“画面准备”和“交互交接”安排依赖

| 工作 | 本裁决给出的门禁 |
|---|---|
| C1 非交互捕获/合成准备、只读面板外观、Native 只读样本 | 不被本反例本身否定；可在原授权范围内独立准备，不扩大本次授权 |
| C1 涉及 Flash 与宿主面板（如 Web/Native）的双向输入切换 | 必须先有原输入域安全撤销证明、物理 neutral 和新 fresh Begin 合同；当前 native ACK 不够 |
| 在未迁移 F 上打开新面板 | 新面板正确不等于旧 F 已安全；不能把漏出的旧 Up 交给新控件，也不能回到旧 F 后借首击清尾 |
| B 扩大统一输入/正式接管 | 所有纳入范围的端点及双向边界均有取消合同、故障关闭和真实人验，才能推进；鼠标 fixture 不代签键盘等未测输入 |
| 正式 runtime 发布 | 还需匹配构建闭包、阶段验收与发布授权；源码成立、模拟刺激、小样、人验体验均不能单独代签 |

C1 的新端点可先绘制并显示为不可交互，不必因旧端点取消延迟而停住画面合成。但业务所有权的 handoff 必须等待旧域释放资格；不能先让新域吃输入，再等旧域慢慢取消。

例如，同进程内从 Flash 切 WebView2/Native 不一定经过与本案完全相同的外部失焦链，尤其不能依赖 WM_KILLFOCUS 恰好把 localFloor 再升一档。交接原因应主动进入同一取消状态机；面板关闭返回 F 也同样执行，不能只验证去程。

新协议是补足输入取消合同，不是把正在独立收口的光照、动态分辨率或整个 UI 改写混为一轮。`02-report.md` 引用的正式分阶段施工计划没有随包提供，本裁决不重新签署其历史授权/通过状态，只明确这次反例增加的依赖。

B0-05 的 100.2569ms/100ms 缺口在本包仍是历史未闭合记录，没有重新测试；不能借 R6 新矩阵替它签字。战斗 #119、存档故障、所有其他焦点问题也不在本轮被宣布解决。

## Q5｜最小施工路线与停止条件

### 第一步：固定现状与 oracle，不动主游戏

冻结本包身份，保持当前失败为红。强化 capture 调用、LL 刺激、AS2 callback/模拟 commit 和覆盖身份观测；补直接原生宿主对照。先把“正常 CancelPointer 后仍持键”的物理账本与重新准入关闭要求写入测试。

这一阶段只做 disposable fixture 与必要诊断/小范围准入逻辑，不以测试需要调用真实存档/修改器业务，不对当前候选自动发布。

### 第二步：只做一轮有明确依据的 native 取消判定

测试前述 virtual capture 对称撤销/neutral 查询候选，并同时跑当前失败负控。若不能确认 virtual capture 曾存在，或无法解释通知顺序，先停止该假设，不继续罗列任意 Windows 消息。

通过条件：原 34 项全部成立；新增有毒按钮、持键无失焦取消、返回不同目标、仍持键返回及双向边界均满足；没有补 Up、重放、抢焦或额外业务回调；固定 projector/bridge 及覆盖控件清单可以复核。只有这样才可申请把这条窄 native 修补纳入对应域的人验候选。

### 第三步：native 判定失败就转一个 AS2 协作交互域

不要求马上改完所有按钮。先在 disposable 的主/子 SWF 中实现完整 M 类协议，再选一个非持久业务域落地；未迁移端点保持 U 类，不借用成功域的 ACK。默认不修改真实存档。

只做 guard 的 G 类结果可以单独作为安全改进记录，但若第一新点击仍无独立 Begin，不能据此解锁 C1 的正常交互。要么补成完整的受控分发域，要么继续关闭该域。

### 第四步：C1 双向纵切，然后再谈 B

针对实际 C1 源/目的端点运行 hold→handoff→release、release→return→fresh Down/Up、无失焦显式撤销和异常中断。每次成功都要能看到旧域的已证取消条件与新域独立 Begin/End，不以新面板打开或像素继续出帧代替。

重新开放某一域的最小证据组合是：**身份一致的 native 退场记录 + 本域取消能力/ACK + 覆盖清单 + 物理抬起基线 + 新手势业务轨迹 + 明确人验记录**。之后仍需原用户授权，不能从本裁决自动推导施工/发布许可。

### 硬停止条件

出现以下任意情况，停止该候选的重新准入或交互放行：

- 取消产生未授权 press/release/releaseOutside 或其他提交；反向地，只恢复了安全而首击仍被吞，也不得通过。
- 没有新有效 Begin 却收到业务 End/commit，或者旧 callback/ACK 被当前 epoch、同名实例、重建 HWND 重新合法化。
- 物理仍持键、状态来源未知、ACK 缺失/错误/乱序、覆盖清单变化，却开放新域。
- 为恢复需要补 Up、自动重放、固定延时、反复抢焦、真实 capture 夺取、重载游戏或真实存档修改。
- 未迁移按钮、时间轴动作、跨 SWF 或延后业务没有覆盖证明，却被宣称全局安全。
- 为取得通过而删除失败断言、缩成悬停切片、以原生/Host 测试总量或人类“看着正常”替代 AS2 业务证据。

停止意味着保持输入关闭、保留仍可显示的画面和必要诊断、由人明确决定后续处置；不把异常退出/重启本身当成成功恢复，也不擅自扩大施工范围。
