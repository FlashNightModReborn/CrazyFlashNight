## 1. 结论摘要

军阀战棋不应继续作为一个只能从测试菜单直开的孤立小游戏，也不应伪装成 Animation 节点。目标形态是：

1. **军阀战棋是 GameStage 内一种正式的 SubStage driver**。单独的战棋关卡仍是完整 GameStage XML，只包含一个 Warlord SubStage；关卡进入、返回、失败、奖励、结算和存档继续复用普通关卡基建。
2. **混合关卡允许 Action → Warlord → Action**。进入下一张动作图、播放路径动画、切到指挥视角是同一 SubStage 序列里的不同 driver，但不共享含混的 Animation 语义。
3. **每次动作交战创建全新的可变游戏世界和场景**，战斗结束后完整销毁。只允许经过明确生命周期管理的只读资源缓存跨战斗复用，不能复用上一次的贴图挂载、单位、事件、深度、相机或临时状态。
4. **战略层支持 N 个阵营，单次节点交战保持二方结算**。Demo 2 使用玩家与三名 Boss 共四个战略阵营、三个胜利组；行动按玩家优先、其余 AI 依 XML 固定顺序逐方完整执行。
5. **一枚可操作棋子代表当前最小独立受令的 CommandElement，而不是固定人数**。V1 不做逐层下钻；通过正式编制树、临时任务编组、部分拆分、同节点零 AP 重组和阵型配置，在宏观规模与操作密度之间取得平衡。
6. **Demo 1 锁定保留现有九节点教程地图**。空间逼仄不是需要修复的规模缺陷，而是首次教学的主动约束：它压缩观察范围、行军距离和同时战线，让容量、攻宽、编组与交战反馈能在很短的命令链内被理解。Demo 1 同时承担迁移回归，但必须运行在新的通用 N 阵营核心上，不保留九节点专用规则分支。
7. **Demo 2 使用 64～120 节点的大战役地图目标带**。首张代表性候选已在建议带内冻结为 80 节点“厚 ×”：四角基地拥有本土纵深，四条战线向中央高价值工业环汇聚，同时用臂间绕行避免单点卡死；约 100 节点产品夹具和 128 节点以上纯压力夹具仍各自保留。节点数本身不等于规模达标，必须同时检查图直径、独立战线、分支度、集结空间、阵营纵深和性能预算。
8. **作者只配置有设计意义的字段**。规则内核派生 AP、容量、交战成本、拓扑索引和 digest；不把实现细节、脚本、任意表达式或渲染对象生命周期暴露给关卡策划。
9. **胜负目标采用封闭、类型化规则，不做通用逻辑 DSL**。指挥所被攻占、敌对胜利组消灭和可选回合上限是首批明确类型；技术未知态永远不能被映射成游戏失败。
10. **玩家语义以“零英文、零战棋基础”为阻断性契约**。生产 UI 必须用简短中文回答“我要做什么、为什么不能做、做了会怎样、怎样胜负”；帮助界面需要让没有外部讲解的玩家独立完成首轮核心操作。开发者速记、内部 ID、英文缩写和只靠颜色表达的信息都不能成为理解前提。
11. **先建设 XML 契约、严格校验器、无头模拟和浏览器预览，再考虑 GUI 工具**。至少有 2～3 个真实场景、经历两轮稳定 schema 后，再决定可视化编辑器的最小范围。

## 2. 背景与设计驱动

当前测试反馈已经证明核心游玩体验具有继续投资价值。下一阶段的主要风险不再是“战棋是否有趣”，而是：

- 规则是否仍被红蓝、九节点和静态地图写死；
- 策划能否把它当普通关卡维护，而不是依赖开发者修改代码；
- 大地图、N 阵营和编制变化是否会破坏确定性、AI、回放与 AS2 战斗交接；
- 同一动作场景被反复复用时，是否会残留贴图、单位、事件和镜头污染；
- 沙盘皮肤、3D 模型、节点拓扑和规则是否会互相绑死；
- 大量可见棋子是否真的降低了 AS2 实时混战压力，还是把压力转移成未经预算的节点交战；
- Demo 测试入口是否与未来 NPC 副本入口走同一产品路径。

投资战棋系统的核心理由，是用低成本的静态战略投影承载营、连级叙事规模，同时把每次实际动作交战限制在节点容量和 EncounterBudget 内。这样可以呈现数十乃至上百个战略单位，而不要求 AS2 同时运行数十至上百个实时战斗单位。

## 3. 当前实现事实与边界

下表保留 2026-08-31 施工前基线事实，不代表当前 Slice 3 工作树；后续增量以 3.2～3.4 为准。

| 领域 | 当前事实 | 对重构的约束 |

| 地图 | NodeId 是九个固定值，地图为九节点、十二边静态数据 | 必须改为版本化 MapDefinition 和不透明字符串 ID |

### 3.2 2026-08-31 Slice 1 历史实现与当前折叠

### 3.6 2026-09-01 Slice 5 产品桥、2026-09-02 折叠与 2026-09-03～04 r12/r13/r14 持续战斗修复

产品 Program 不再把 `ArenaCalibrationTask` 注入 vNext Warlord battle。Host 经 Socket 发送 exact `warlord_action_encounter_start`；`StageManager` 校验 outer run 后把冻结 encounter 物化成临时普通 `StageInfo`，并独占两次标准 `wuxianguotu_1` 淡出跳帧：进入 frame 209 复用普通 `initializeStageWorld` 创建动作 world，返回 frame 209 清空临时槽并交付 exact terminal。`SceneManager` 只执行标准时间轴触发的物理 `init/remove`，不保存 Warlord generation、owner lease 或 teardown receipt；`StageRunSession` 不建立 inner run；`WarlordSubStageRunner` 不裁决内层场景；`WarlordActionEncounterService` 只负责冻结输入、生成/控制/相机、收集战斗事实和释放自身引用。普通演员 attach 后先保持 AI hold；只有 exact world parent、`__unitInitializedVersion === version`、dispatcher、collider、shield 与正尺寸齐全，且普通单位另有 `unitAI`，才视为纸娃娃视觉就绪。全部演员在 90 帧上限内就绪、淡出到 runtime frame 36 并连续稳定 6 帧后，service 才统一解除 hold、绑定目标并 prime；场景 reveal 总上限为 180 帧，超时 fail closed。`warlord.action-encounter-control.v2` 继续把当前玩家主角固定为 `commander.player / character.player-avatar / player` 的 `player_avatar`，并保持头像、纸娃娃与宠物投影边界；结算快照另冻结 `encounterProjectionKind`，因此真实主角必须显示“我方主角/主角指挥官”与纸娃娃，不能再降级为 cardId 83 的精锐狙击替身。Host 只接受 exact binding/terminal、做 correlation/idempotency 并把 accepted result 交回 Web；Web 仍是唯一战略写入者，隔离演员的可变状态不写回玩家存档。

r10 真人证据补出了普通演员门未覆盖的玩家专属时序：`_root.加载游戏世界人物` 返回不代表嵌套玩家模板已经完成，后续帧的 StaticInitializer、DressupInitializer 和 UpdateEventComponent 仍以 `_root.控制目标` 是否等于实例名选择一次性主角分支。r11 因此在玩家生成前绑定 exact 实例名，整个延迟初始化期只用 `_root.控制目标全自动=true` 冻结输入；战棋相机通过 `HorizontalScroller.switchFollowTo` 独立跟随，不再占用控制身份。所有投影演员都从 attach initObject 起携带 AI hold，即便异常误入普通 AI 分支也不能抢跑。玩家还必须满足 `操控编号=0`、`hasDressup=true`，并由 `RuntimeEquipmentProjection.getStatus` 相对当前 `_root.物品栏.装备栏` 的 11 槽返回 `aligned`，才允许统一武装与解冻。不得读取 `__runtimeEquipmentProjectionV1` 私有字段，也不得修改正常游戏的性别、装备或纸娃娃初始化路径。

r11 真人持续战斗证明上述主角修复至少能跨 25 次完整 Action 往返，但第 26 次只完成 Web/Host 侧 exact close，没有进入 AS2 start admission。Flash 当时仍约 `29.8 FPS`，因此“面板已关且 Flash 活着”不能推导 Action 已被 AS2 接纳；日志中缺少第 26 组 transition/frame 209/world/terminal/resume，也不能反向命名为 GameWorld 创建失败。旧链路把 socket `Write + Flush` 的本地返回当成足够交付信号，又把从开局起不断增长的 `battles`、`commandHistory`、`eventLog` 和已结算伤亡一并发送，使第 26 次请求的 UTF-8 体积逼近 Host `512 KiB` 硬门，并扩大单个巨型消息的丢失面。

r12 保持战略态与 wire schema 的现有权威边界，只缩小 AS2 handoff 投影并补 exact admission。Web 交战请求清空历史 `battles/commandHistory`，只保留 `eventLog` 尾 32 条与未结算 `casualtyLedger`，而 `strategicRound`、`commandSequence`、`battleOrdinal` 等单调身份继续保留；请求按 `TextEncoder` 得到的真实 UTF-8 字节数接受 `384 KiB` 软门。该投影足够 Host 独立复验当前战斗，却不伪造完整历史：replay 导出看到历史缺口必须 fail closed。

面板 exact close 完成后，Host 只捕获一次当前 ready socket generation，并以一个 `warlord_action_encounter_start` 命令同时授权 AS2 释放 Web pause 与开始 Action。Host 不再把成功写入当作接纳；它等待 exact `warlord.action-encounter-admission.v1`，未收到时每 1 秒用相同 binding、相同 generation 重发，首次加重试总计最多 4 次。超限仍未确认时只关闭所捕获 generation，不能误伤随后连接。AS2 handler 在任何 pause/StageManager 副作用前先检查 binding 级吸收 terminal，再调用只读 inspector：同 binding duplicate 直接回当前 phase admission，已冻结 terminal 直接重投；只有 fresh 才释放既有 `webPanel` pause 并调用 `StageManager.beginWarlordActionEncounter`。若 B 已 active，同 generation 内迟到的旧 A 被 inspector 以 `encounter_active` 拒绝后只作为 stale 丢弃，不合成 A terminal、不占 terminal absorption，也不冻结或污染 B。terminal absorption 不因上次 send 返回成功而退休，同 binding retry 始终优先重投原 terminal，且不创建第二个临时 `StageInfo`。

r12 的 handoff 修复通过机器门并在标准入口实际执行，但人类首战播放到 `7/7` 时，合法阵容内容超过 battle dialog 的可视预算：编队、事件与 footer/controls 都按自然高度排版，而对话框用固定 `510px` 上限配合 `overflow: hidden`，最终把底部操作区确定性裁掉。该按钮仍在 DOM 中，所以只检查 selector 存在或用脚本 `.click()` 的旧浏览器门没有发现真实命中失败。与此同时，战斗弹层虽然完全遮住沙盘，场景 rAF 仍在播放期反复重启并继续进入 update；维护者观察到 Intel iGPU 约 `93%`。这只能界定为播放期渲染预算故障，不能外推为关闭弹层后的永久 rAF 泄漏。

r13 保持战斗与战略规则不变，仅把 battle dialog 设为行受约束的 grid，让编队区内部滚动，并在 modal 时 suspend/cancel 沙盘 rAF。真人首战仍在结算卡死、核显持续高负载并随后非正常重启，故其 `199/199` Web、`26/26` Edge/CDP 与 candidate 执行均只能作为失败历史。r14 继续保持规则不变，把战斗交接、结算 modal 与 panel-close intent 收敛为沙盘图形资源的即时退休，resume 只呈现最终静态结算，Bootstrap game reveal 后单向退休 WebView2；移动与返回镜头的 rAF/timeout 走同一 exact-once 收尾。该修复的 Web `201/201`、Edge/CDP `29/29`、Launcher 全量及真实根入口恢复/首场 Action 已通过，只把状态推进到 `R14_SOURCE_MACHINE_VERIFIED / R14_CANDIDATE_EXECUTED / HUMAN_ACCEPTANCE_IN_PROGRESS / NOT_DEPLOYED`；结算稳定性、连续战斗与真实 GPU 仍须人类复验。

外层 `warlord.stage-outer-attempt.v1` 的 `not_started` 是吸收性父 GameStage 启动失败，不能显式重试；可能已启动或终态身份漂移一律进入 Suspended/Unknown 冻结诊断，也不自动重放或恢复。父 GameStage 退出、返回基地、重启、重新初始化或 setup/admission/calibration failure 时，唯一 retirement 路径是独立 `warlord_stage_outer_cancelled` + `warlord.stage-outer-cancellation.v1`；它携 exact 六字段 outer binding，仅让 Host 幂等退休 owner，不能借取消生成战果、写战略态、操作场景或耦合 `stage_outcome`/Action cancellation。内层 Action 的确定 `not_started` 语义保持不同：玩家回到同一战略态后可重新选兵，AI 有界结束一次当前行动；而无 admission 只表示交付未确认，Host 仅做同 generation 的 1 秒有界重发，不能据本地 write 结果伪造 `not_started` 或按新身份重开。现役旧 Phase C 仍保留兼容构造与已部署 Arena 旅程，不能把它的证据写给 vNext。通用 `scenePoolRef/directorRef/EncounterBudget`、逐成员 DeploymentPlan 和专门的“战术胜/战略败”内容剧本继续留作后续扩展。

## 4. 决策强度

本文使用三种强度：

- **LOCK**：进入施工前必须按此建立接口；修改需要更新 ADR。
- **PROVISIONAL**：方向已确定，数值或具体命名需通过原型收敛。
- **DEFERRED**：明确不进入首版，schema 可以保留扩展点，但不得预先实现复杂度。

## 5. 关卡架构

### 5.1 Warlord 是 SubStage driver，不是 Animation

**LOCK**

Animation 的语义是播放当前路径内的表现，不拥有独立战略状态、回合、AI、冻结恢复和类型化战果。把战棋挂到 Animation 会导致：

- 动画节点被迫承担规则生命周期；
- 失败、暂停、返回和结算无明确权威；
- 后续 Action → Warlord → Action 需要特殊分支；
- 工程工具无法区分纯表现资源与可失败的子关卡。

当前折叠结构由现役 `StageManager` 依次调度，不增加第二套场景 coordinator：

~~~text
GameStage
  └─ StageManager（唯一场景生命周期所有者）
      ├─ SubStage(Action) → 普通 StageInfo 路径
      ├─ SubStage(Animation)
      ├─ SubStage(Warlord) → WarlordSubStageRunner（仅 outer binding/result）
      │                    └─ encounter → 临时普通 StageInfo 路径
      └─ SubStage(Action) → 普通 StageInfo 路径
~~~

Warlord driver 负责装载一份 WarlordScenario、运行战略状态机，并将类型化结果交回外层。它不直接发放整关奖励，也不自行跳转下一关。

### 5.2 单独战棋关卡仍是完整 GameStage

**LOCK**

单独入口不是第二种顶层关卡类型，而是一个只包含单个 Warlord SubStage 的正常 GameStage：

~~~xml
<!-- PROPOSED：名称只表达边界，不是已实现 schema -->
<GameStage>
  <BasicInformation>...</BasicInformation>
  <Rewards>...</Rewards>
  <SubStage id="warlord_tutorial" driver="Warlord"
            scenarioRef="warlord_tutorial_v1" />
</GameStage>
~~~

首片沿用当前直接 `SubStage` 形状，避免同时迁移全部普通关卡 loader；`id/driver/scenarioRef` 仍是待实现 schema，不表示通用 `XMLParser` 已经严格校验这些字段。稳定、不随本地化变化的 `stageId` 需要与现役 `StageInfo.Name` 分离。完成后，测试入口和未来 NPC 副本任务都只调用同一条 EnterGameStage 链；当前测试目录以精确 StageInfo 名称交接，稳定 `stageId` 仍留待正式入口施工。入口来源只影响可见性、返回位置和分析标签，不得改变规则、seed、奖励和存档语义。

### 5.3 外层权威唯一

**LOCK**

StageRunSession 继续是整关运行、生命、收益损失、复活/返回、完成和奖励的唯一外层权威。Warlord SubStage：

- 不创建嵌套 StageRunSession；
- 不直接写整关奖励；
- 不调用 NextStage；
- 不自行完成整关存档；
- 只返回 CompleteSubStage、FailStage 或技术性 Suspended/Unknown。

胜利时外层继续执行后续 SubStage；失败时 V1 整关失败。结构化战棋结果要保留在内部 receipt 中，但 V1 不根据它分叉后续动作关卡。

## 6. 运行时权威与场景生命周期

### 6.1 权威链

**LOCK**

~~~text
父关卡：GameStage XML → StageManager → StageRunSession（只拥有父 run/生命/结算）
                         └→ WarlordSubStageRunner（只拥有 outer binding/result）
场景面：StageManager → 临时普通 StageInfo → 标准 wuxianguotu_1 / frame 209
                                      └→ SceneManager（只做物理 init/remove）
战斗面：Host exact command → WarlordActionEncounterService（只产战斗事实）
结果面：AS2 exact terminal → Host 校验/关联/幂等 → Web 单次战略提交
~~~

所有战略写入先经过同一 validator。玩家、AI、测试驱动和未来自动演出都不能绕过 validator 直接改 GameState。

### 6.2 每次交战使用新鲜动作世界

**LOCK**

每一次需要进入 AS2 动作战斗的节点交战都必须：

1. 冻结战略快照、命令、outerRunId、encounterId、requestId、inputDigest 和权威上下文；
2. 关闭或暂停沙盘交互；
3. `StageManager` 先建立单一临时 Action 槽，把受校验 encounter 物化为普通 `StageInfo`；该槽不创建第二个 `StageRunSession`；
4. 仅通过标准 `_root.淡出动画.淡出跳转帧("wuxianguotu_1")` 从战略世界切换到动作世界；标准淡出时间轴负责清除旧 world、跳帧并在 frame 209 回调 `StageManager.initStage()`；
5. `StageManager` 在 frame 209 识别临时槽，复用普通 `initializeStageWorld` 创建单位、相机、事件订阅和临时挂载；`SceneManager` 只做该标准路径要求的物理 `init/remove`；
6. `WarlordActionEncounterService` 只持有冻结输入、生成/控制/相机与结果事实；动作终态由 `StageManager` 冻结后，再经同一标准淡出跳帧返回战略 world，服务不得直接加载/删除 world 或 `swapDepths`；
7. 返回 exact `warlord.action-encounter-terminal.v2`；Host 只做格式、关联和幂等校验，Web 只对 accepted terminal 提交一次同一战略 checkpoint。

`P` / `A` 只是战略与动作语义标签，不另建物理身份系统。PREFER_B 的验收预算锁定为 `owners=4 / clocks=1 / leases=0 / terminal rewrites=0`：四个逻辑 owner 分别是 `StageRunSession` 的父 GameStage、`WarlordSubStageRunner` 的 outer binding/result、`StageManager` 的场景/临时 Action 生命周期、`WarlordActionEncounterService` 的战斗事实；`SceneManager` 只是 `StageManager` 标准路径下的物理 init/remove 机制，不成为第五个 Warlord owner。唯一时钟是标准 Flash 时间轴。禁止恢复 r8 的 generation、owner token、teardown receipt、跨 root tick 审计或 scene-level 90-frame ownership pending，也禁止任何层在 terminal 定稿后改写其 status/reasonCode/result。r10 的 90 帧 actor visual-ready 上限只保护单次 Action world 内的纸娃娃初始化，既不跨跳帧，也不形成新的 scene owner/lease。

标准淡出时间轴中的 `SceneManager.removeGameWorld()` 仍是 canonical 普通过图步骤；禁止的是 Warlord service、Host 或 Web 旁路调用它并形成第二套生命周期。跨跳帧只能保留不可变业务 binding 和 `StageManager` 的临时 `StageInfo` 槽，不保留 `_root.gameworld`、dispatcher、单位、相机或其他 MovieClip 句柄。

禁止复用上一次战斗的可变场景。允许跨战斗共享的对象必须同时满足：

- 只读或以不可变 key 缓存；
- 不保存当前关卡 MovieClip、单位、事件回调或相机引用；
- 有显式引用计数或清理策略；
- 在场景 teardown 后可以证明没有遗留可变挂载。

内层 Action timeout、断线、非法 terminal 或 binding 漂移继续进入 Unknown，不能自动重打；若 Action world 已经存在，仍由 `StageManager` 冻结终态并走 canonical 返回跳帧。只有内层 Action 明确 `not_started` 时，玩家才能在原战略态重新选兵；这不复活 outer GameStage。整局不再提供“恢复演习”或 revision+1 reopen。父 GameStage clear、返回基地、restart、reinitialize 或启动失败时，AS2 发送 `warlord_stage_outer_cancelled`，以 `warlord.stage-outer-cancellation.v1` 的 exact 六字段 binding 让 Host 幂等退休 outer owner；它独立于内层 Action cancellation 与通用 `stage_outcome`，不生成结果、不恢复 Web、不改场景且不写战略态。

### 6.3 同时只运行一个动作交战

**LOCK**

Demo 2 即使拥有百级战略节点，V1 也不并发运行多个 AS2 战斗。战略命令按照阵营行动顺序逐条立即结算；每次 encounter 完成并提交后，才处理下一条命令。这样“大地图”扩张的是战略图和静态棋子，不是实时 AS2 并发量。

## 7. 配置分层

### 7.1 文件职责

**LOCK**

不把所有内容塞进一个巨型 XML。建议按稳定引用拆分：

| 配置 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| GameStage XML | 入口、SubStage 顺序、外层奖励、关卡失败/完成生命周期 | 战棋内部拓扑和 AI 细节 |
| WarlordScenario XML | 阵营、行动顺序、初始节点控制、初始部署、关系、目标、经济与规则 profile 引用 | 3D 文件路径和动作场景细节 |

| OrganizationDefinition XML | 编制树、成员、可拆分模板、CommandLoad、DeploymentSize | 当前任务编组 |
| UnitTemplate XML | 战略数值、AP 贡献、战术投影、AI/能力 profile 引用 | 场景内临时 HP 对象 |
| FormationProfile XML | 阵型语义、槽位角色、约束、部署策略 | 固定屏幕像素或世界绝对坐标 |
| ControllerProfile XML | 战略 AI 目标权重、风险、合法命令预算 | 任意脚本 |
| EncounterProfile XML | 动作场景池、交战预算、双方出生与导演策略 | 整关奖励 |
| MapVisual / Theme XML | 地表、雾、灯光、路线、LOD、地标映射 | 规则容量、胜负和随机 |
| AssetCatalog XML | 模型/贴图引用、hash、比例、轴向、pivot、LOD、来源 | 场景实例状态 |
| PlayerText / HelpProfile / TutorialProfile | 中文显示名、统一术语、原因文案、玩法帮助和固定教学步骤 | 规则计算、任意脚本和调试日志 |

MapDefinition 必须保持 faction-agnostic：它可以被不同 Scenario 复用，不能引用 scenario-local factionId。初始节点控制和驻军部署都由 WarlordScenario 通过 nodeRef 写入 InitialState。表现引用也只能沿 MapVisualDefinition → nodeRef 的方向建立；MapDefinition 不得反向引用 MapVisual、Theme、visualAnchor 或 assetId。

AI 和特定棋子行为应该可配置，但只通过已登记的 profile 和能力 ID。策划选择 “aggressive_flanker” 或 “hold_command_post”，引擎拥有其实现和版本；XML 不嵌入代码。

### 7.3 ID、版本和 digest

**LOCK**

- 所有 stage、scenario、map、node、edge、faction、controller、victoryGroup、organization、member、formation、profile 和 asset ID 都是稳定、不透明字符串。
- 不依赖 XML 读取器对数字样式 ID 的自动转换；禁止用 007 这类需要保留前导零的裸数值身份。
- 所有可重复子项在解析层统一归一化为数组，不能让单个节点和多个节点产生不同运行时结构。
- Scenario 必须记录 schemaVersion、rulesVersion、configDigest 和 mapDigest。
- 规则 digest 与 presentation digest 分离。换沙盘皮肤、LOD 模型或灯光不得改变规则 replay identity。
- 运行时 GameState 是由作者配置实例化的状态，不回写到作者 XML。

## 8. 地图规模与拓扑合同

### 8.1 不同规模档不是一个数字放大

**MIXED：Demo 1 LOCK；其余规模档 PROVISIONAL**

| 用途 | 目标节点带 | 定位 | 是否产品内容 |
| --- | ---: | --- | --- |
| demo_01_tutorial | 9，保留现有拓扑 | 以受控、逼仄空间完成首次教学，同时锁定旧规则迁移 | 是，Demo 1 |
| topology_bridge | 约 24 | 暴露九节点到大战图之间的拓扑、AI 和 UI 扩展断点 | 否，工程夹具 |
| operational_large | 64～120，首图建议 72～96 | 四阵营、多战线、排级编组、连级总体规模 | 是，Demo 2 |
| scale_stress | 128～144 或更高 | 渲染、AI、序列化和导航压力 | 否 |

Demo 1 继续使用现有九节点地图。其可机动空间少、战线集中、路线短，恰好限制了初次游玩的信息量：玩家不需要先学习大地图检索和多线调度，就能快速看到移动、容量、攻宽、交战和据点变化的因果。它不负责证明纵深机动或大战场能力。

九节点数量和现有拓扑属于 Demo 1 内容锁定，不代表规则 schema 可以写死九节点。迁移后，同一通用 MapDefinition 解析、N 阵营状态机、AI、digest 和 UI 投影必须配置出原有 Demo 1。约 24 节点只作为非产品的中间工程夹具，用于在直接跳到 72～96 节点前暴露线性扫描、邻接索引和布局假设。

Demo 2 不为了“百节点”机械填满 100 个同质节点。首张代表地图已在 72～96 建议带内收敛为 80 节点；独立约 100 节点验收夹具仍负责证明产品通路没有隐含九节点上限，不能拿同一张内容图同时冒充拓扑设计与规模压力证据。

### 8.2 规模必须由图指标共同描述

**LOCK**

地图校验报告至少输出：

- 节点数和边数；
- 连通分量；
- 平均、最大节点度；
- 图直径与各指挥所之间最短路径；
- articulation/cut 节点及单点断路风险；
- 可并行推进的独立战线或路径数量；
- 各阵营初始领土、边界长度和战略纵深；
- 前线附近可用于拆分、汇合、预备队和绕行的集结节点数；
- 节点类型与 EncounterProfile 分布；
- 初始与最坏活跃 CommandElement 数；
- 每个节点最坏 DeploymentSize 和 EncounterCost；
- 预计可见对象、路线段、标签和 DOM 窗口数量。

节点必须承担至少一种设计职责：路线选择、集结、争夺、阻滞、经济、指挥、演出或节奏缓冲。纯粹为了达到计数而添加的无差异节点，应由地图审查标记。

### 8.3 原型拓扑目标

以下是内容与原型目标，不是通用 schema 的节点数硬验证；Demo 1 属于内容锁定，Demo 2 属于原型调优：

Demo 1：

- 保留现有九节点拓扑和紧凑战场，不为展示扩展性而加节点；
- 利用少量路线和短反馈链，让玩家一次只处理有限命令选择；
- 将逼仄节点用于直观教授驻军容量、攻宽、编组与窄阵地，而不是同时教授跨战区导航；
- 新增编制能力时采用逐步解锁或明确教学提示，避免把 N 阵营、外交、指挥所和全部编制规则一次灌入；
- 新核心必须在该九节点配置上保持可回归、可确定重放，不能保留旧专用分支。

Demo 2：

- 当前候选采用 80 节点“厚 ×”：四个角各 14 节点本土纵深、双独立出口，基地到前线约 4～6 跳；
- 16 个臂节点形成四条内向战线，中央 8 节点组成高价值工业环；
- 臂间横向绕行让局部失守仍有改道空间，整图无 articulation/cut node，不让四方挤在中央一个 choke；
- 独立 Boss 与二 Boss 同盟从不同角落进入战场，固定关系与空间方向共同形成不同威胁；
- 玩家可以在局部战术获胜的同时，因为指挥所、调度或战线失衡而战略失败；
- 已提供跨战区定位、中文检索、告警和最多六节点的虚拟导航窗口，不能退回逐页盲翻十余页按钮。

## 9. Demo 2 的大地图技术门

### 9.1 规则与数据

**LOCK**

- NodeId 不再是 TypeScript 固定联合，而是经 MapDefinition 校验后的 opaque ID。
- MapDefinition 建立 nodeById、edgeById、adjacencyByNode、sector index 等只读索引。
- 合法命令枚举只扫描当前阵营的可行动元素和局部边界，不做所有棋子 × 所有节点的全图笛卡尔积。
- AI 和玩家共用 enumerateLegalCommands 与 validateCommand；AI 不能拥有捷径。
- 序列化、digest、replay 和排序全部使用稳定 ID 与显式顺序。
- MapDefinition 全量装入内存可以作为 V1 目标；不在未测量前引入地图分块和流式状态复杂度。

### 9.2 呈现与导航

**LOCK FOR DEMO 2**

现有 overview / operational / tactical detail tier 继续作为基础，但 Demo 2 至少需要：

- authored bounds 全图适配；
- 小地图或战区总览；
- 当前行动、交战、指挥所受威胁和生产阻塞的可跳转告警；
- 按战区或前线聚合的局部导航；
- 节点名称/类型检索或等价快速定位；
- 虚拟化节点列表，不让 DOM 数量随节点总数线性增长；
- overview 下聚合棋子和标签，tactical 下才展开独立 token；
- 节点与棋子 instancing、路线 batching、纹理/材质共享；
- 视锥或空间索引驱动的标签、拾取和更新范围。

六节点分页可以保留为局部精确选择补面，但不能作为百节点地图的唯一导航。

当前 80 节点候选已经把上述合同落为战区/局部导航、中文节点名称与类型检索、当前行动/威胁/生产阻塞告警，以及最多 6 张节点卡的虚拟窗口；战区抽屉默认收起并由导航栏按需展开，`Esc` 收起后恢复触发按钮焦点。底部 8 张普通兵牌可从 `120px` 折为 `32px`，把 `88px` 高度交还沙盘；指挥官卡不挤入该区域。四阵营同时使用颜色和边框线型表达身份。浏览器机器门验证 14 个页面可以覆盖全部 80 节点和固定画布的无溢出约束，但这种覆盖证明的是可达性，不代签玩家能否迅速读懂多战线态势。

### 9.3 性能预算

**PROVISIONAL**

第一轮施工必须先添加观测，再冻结数值门。至少测量：

- MapDefinition 解析、语义校验和 digest 时间；
- 创建新战略会话、保存快照和恢复时间；
- 每个 AI faction 的合法命令枚举、排序和整回合时间；
- 24、96、128 节点下的 Three 对象数、draw call、纹理数和显存估计；
- overview 平移/缩放、战术聚焦和大量棋子状态更新；
- 虚拟导航实际 DOM 数；
- AS2 encounter 创建、销毁和连续多次交战后的残留对象/监听器。

当前 scene-perf 机器门已锁定对象数与 draw-call 结构：Demo 2 的 136 条路线从逐边理论 272 次绘制收敛到最多 4 个批次，overview 普通节点由 2 个 InstancedMesh 承载，高亮节点保持可拾取的详细对象；Demo 1 不启用这条 LOD 分支。`4/4` 通过只证明结构预算与资源 teardown，没有伪造毫秒、FPS 或目标设备体验；最终性能阈值和真人观感仍须在 Slice 6 候选上独立验收。

## 10. 棋子、编制与阵型

### 10.1 一枚棋子的语义

**LOCK**

沙盘上一枚可操作棋子表示当前最小可独立受令的 **CommandElement**。它可以是一名角色、一个班、一个排或临时分队，取决于当前编制和任务编组；它不保证固定人数，也不等同于 AS2 中一个动作单位。

V1 暂不做 “点击排 → 下钻到班 → 再下钻到个人” 的多层战棋。不同层级通过聚合和拆分在同一战略平面表达。

### 10.2 三类结构

**LOCK**

- **OrganizationDefinition**：正式编制树，说明谁属于谁、允许怎样拆分。
- **TaskGroup**：运行时任务编组，是玩家当前在地图上实际指挥的聚合。
- **FormationProfile**：阵型语义，说明前卫、侧翼、火力、预备等槽位与约束。
- **DeploymentPlan**：某次交战里成员实际落到哪些动作场景出生位。

FormationProfile 可与斗兽竞技场共享语义词汇和槽位角色，但不共享屏幕像素、世界绝对坐标或场景 MovieClip 引用。

### 10.3 分区不变量

**LOCK**

任一存活的底层 member 在当前战略状态中必须：

- 恰好属于一个 active CommandElement；
- 不能同时以父编制和子编制两种 token 出现在地图；
- 拆分、合并后保留稳定 memberId、HP、能力、装备/身份、伤亡和指挥官身份；
- 不能因为聚合而复制 AP 贡献、人口、部署体积或战术投影。

### 10.4 V1 重组规则

**LOCK**

- 允许 “抽出一个班，剩余两个班继续保持组合” 的部分拆分；
- 只允许同一节点、己方行动阶段、未在交战/运输/Unknown 状态的元素参与；
- 重组本身消耗 0 AP；同节点限制、模板限制和后续移动成本已经构成操作代价；
- 合并只允许满足 OrganizationDefinition 或显式 TaskGroupTemplate 的组合；
- 重组后可以立刻下令，但不能借重组刷新 AP、能力冷却、伤亡或生产状态；
- V1 不允许跨节点远程编组，也不允许任意拖拽创建非法编制。

### 10.5 CommandLoad、DeploymentSize 与 EncounterCost

**LOCK**

三个量必须分开：

- **CommandLoad**：战略命令消耗。聚合可以降低总 CommandLoad，表达整编行军更省指挥成本。
- **DeploymentSize**：占据节点容量和进攻宽度。聚合前后必须守恒。
- **EncounterCost**：开发者维护的动作战斗性能成本估计，可能包含实际 AS2 actor 数、复杂能力和特效成本。

移动或过境的 AP 成本：

~~~text
edgeCount × sum(selected CommandElement.CommandLoad)
~~~

聚合不应让三个班从占用三个容量点变成一个容量点；它只减少操作和指挥负担。

## 11. AP、容量、战线宽度与预备队

### 11.1 AP 快照

**LOCK**

每个阵营开始行动时生成一次规范化 AP ledger：

~~~text
BaseAP =
  ScenarioBaseAP
  + 存活底层 member 的 APContribution 总和
  + 已控制节点的 APBonus 总和

FieldBonusAP =
  当前亲临一线且有效的 Commander APBonus 总和
~~~

APContribution 按底层 member 计算，不按可见 token 数计算，避免拆分/合并制造 AP。阵亡或控制变化影响下一次本阵营 AP 快照；当前回合已经花掉的 AP 不回滚。

消费时先扣 FieldBonusAP，再扣 BaseAP。指挥官阵亡或撤离前线时，尚未消费的 FieldBonusAP 立即清零；重新部署不会在本回合凭空补发，下一回合仍在前线才重新获得。

ScenarioBaseAP 或其他普通来源必须保证阵营不因失去指挥官而永久零 AP。

### 11.2 节点作者字段

**LOCK**

V1 节点只向策划暴露：

- garrisonCapacity；
- attackWidth；
- defenseBonus；
- 可选 nodeAPBonus。

隐藏或移除独立 defenseWidth。V1 所有驻军都参与防守；进攻方只允许选择不超过 attackWidth 的 DeploymentSize。没有被选中的进攻元素留在原节点，构成自然预备队。

约束：

- attackWidth 不得大于目标节点 garrisonCapacity，除非未来规则版本明确允许；
- 驻军 DeploymentSize 总和不得超过 garrisonCapacity；
- selected attackers 的 DeploymentSize 总和不得超过 attackWidth；
- EncounterProfile 的最坏攻击方和全部防守方 EncounterCost 必须同时落在 AS2 战斗预算内。

V1 不做独立防守预备队、多波增援和边级宽度。若之后确有第二个消费场景，再扩展，不提前增加作者字段。

## 12. N 阵营、行动顺序与外交

### 12.1 战略 N 方，交战二方

**LOCK**

战略 GameState 支持 N 个 Faction。一个节点只能有一个驻军阵营；一次攻击命令只形成 attacker 与 defender 两方 encounter。其他阵营不在同一 AS2 场景中共同驻防或即时参战。

同盟 V1 只影响过境和胜利组，不提供共同驻军、联军战斗或数值支援。

### 12.2 行动顺序

**LOCK**

- 玩家阵营总是第一个行动，便于理解和实现；
- 其余 AI 按 Scenario XML 中固定、显式顺序行动；
- 每个仍存活的阵营完成一个完整 block phase；
- 阵营内部命令按提交顺序立即结算；
- 已彻底失败的阵营在后续轮次跳过；
- 所有顺序进入规则 digest 和 replay。

V1 不做同步行动、速度插队、反应回合或动态 initiative。

### 12.3 固定对称关系

**LOCK**

关系仅有 allied、neutral、hostile，必须对称并在载入时闭包校验。这里的 “中立 Boss” 指独立政治阵营，不代表它对其他阵营的关系是 neutral；Demo 2 的独立 Boss 可以对所有其他方保持 hostile。

Demo 2 的目标关系矩阵：

|  | Player | Independent Boss | Pact Boss A | Pact Boss B |
| --- | --- | --- | --- | --- |
| Player | self | hostile | hostile | hostile |
| Independent Boss | hostile | self | hostile | hostile |
| Pact Boss A | hostile | hostile | self | allied |
| Pact Boss B | hostile | hostile | allied | self |

角色映射已冻结：`boss-pact-a = 吴豫 / Itinerant / cardId 111`，`boss-independent = 袁望 / Surveyor / cardId 113`，`boss-pact-b = 阎凝儿 / Gazer / cardId 112`。Independent 表示袁望在政治上独立；为了保持四方战役可完成，本局关系仍配置为他与玩家及两支盟约军全部 `hostile`，不能把“政治独立”误写成关系矩阵的 `neutral`。

### 12.4 同盟过境

**LOCK**

V1 只允许原子两边路径：

~~~text
己方起点 → 一个 allied 中间节点 → 己方或无主终点
~~~

规则：

- allied 节点不能成为终点；
- hostile 或 neutral 节点不能作为本规则的中间点；
- 最多两条边；
- 必须在提交时一次性验证整条路径、AP、关系、终点容量和落点合法性；
- 中间节点不写入驻军、控制权或停留状态；
- AP 必须足够支付完整 edgeCount × CommandLoad；只有走到 allied 节点的 AP 时命令非法；
- AI 使用同一 validator；
- V1 不提供同盟数值支援。

## 13. 指挥官、玩家主角与指挥所

### 13.1 身份分离

**LOCK**

必须区分：

- Faction：规则阵营；
- Controller：玩家或 AI 的决策者；
- CommanderElement：可参战、可编组的指挥官成员；
- PlayerAvatar：玩家主角的动作角色身份；
- CardRegistryEntry：唯一角色卡的生产/存活/排队状态。

指挥官是完整棋子，能移动、占容量、进入 Formation、受伤和阵亡。指挥官 memberId 在拆分时只能进入一个结果，不能复制。

### 13.2 Boss 指挥官

**LOCK**

Boss 指挥官战败后真实阵亡，但其阵营继续行动。唯一角色卡可以在自己的指挥所重新生产，代价和周期高到不能把 Boss 当消耗品。

同一个 characterId 在任何时刻最多处于 available、queued、alive 中一种状态。重新生产后保持 characterId，但生成新的 pieceInstanceId；旧实例永不复活。

### 13.3 玩家主角

**LOCK**

玩家主角状态：

~~~text
Fielded
  → Downed
    → Revived → Fielded
    → EvacuatedToRearCommand
      → RedeployedFromOwnCommandPost → Fielded
~~~

- 关内复活是主角能力 profile，不是所有指挥官通用规则；
- 玩家放弃或无法复活时，视为被抬回后方指挥，不是角色真正死亡；
- 后方指挥仍可继续操作战略层，但主角不占驻军、不能参加战斗，也不提供亲临一线 AP 加成；
- V1 允许重新部署，但只能从仍由己方控制、有效且未受争夺的指定指挥所；
- 重新部署不能发生在敌方攻击过程中，不是反应式增援；
- 建议部署本身 0 AP，部署后的移动照常消耗 AP；
- 重新部署当回合不补发 FieldBonusAP，下一回合仍在前线才恢复；
- V1 不提供玩家主动召回传送。只有 Downed 后选择撤离进入后方状态。

主角复活延迟、HP 和次数属于 PlayerAvatarAbilityProfile。首版建议至少跨到下一战略轮，最终数值在 Demo 2 调优时冻结。

若主角在动作交战中撤离而己方其他单位仍存活，首版建议由同一个权威 AS2 encounter 继续 AI 控制剩余单位；表现层可以快进，但不切换到第二套自动结算器。

### 13.4 指挥所

**LOCK**

每个启用指挥所败北规则的 Faction 都在自身配置上显式引用 commandPostNodeRef，不能只凭 NodeKind 推断。指挥所承担：

- 指挥官卡牌生产与重新部署；
- 玩家主角从后方重新部署；
- 斩首与战略失败目标；
- 地图上的高价值防守与突袭路线。

玩家指挥所被合法攻占时，立即整关失败。AI 指挥所被攻占时，该阵营立即彻底失败并执行投降清理。

## 14. 占领、阵营失败与胜负目标

### 14.1 占领条件

**LOCK**

accepted encounter receipt 只结算伤亡并把进攻方幸存元素移动到目标节点，不能在战斗回执应用栈内改写节点 owner、激活节点或触发指挥所胜负。节点染色只有两个互斥的权威边界：

- **行动结束驻点直占**：当前阵营执行 `END_ACTION` 时，扫描每个非本方节点；只有该节点存在且仅存在当前阵营这一种存活驻军时，才批量改为本方颜色。无驻军、双方/多方争夺均不直占。
- **下一行动方开始前包围占领**：确定下一名仍存活阵营后、把行动权交给它之前，冻结本次写入前的全图 owner 快照；任一非本方且 `degree > 0` 的节点，只有全部直接相邻节点在快照中都严格属于该阵营时，才进入同一批包围改色。联盟颜色不合并；本批新染色不能继续传播形成第二层；节点上的敌方驻军不因染色被删除。

同一批 eligible 节点必须先全部改色，再记录事件并统一处理指挥所目标，避免较早枚举到的总部胜负截断同批后续节点。新占节点仍从下一战略回合起激活。首行动阵营在统一结算后获得新回合行动权前，也必须执行同一包围判定。

**PROVISIONAL FOR REVIEW**

双方全灭时建议节点变为 uncontrolled，攻击方不占领，原防守阵营也不保留驻军。该语义能避免 “尸体替原主人守住控制权”，并让结果可见、可继续争夺；若评审选择保留原 owner，必须在实现前锁定，不能让不同 resolver 自行决定。

### 14.2 阵营彻底失败

**LOCK**

指挥所被占领后的投降清理：

- 该阵营所有棋子立即消失；
- 生产、重组、移动和未执行命令全部取消；
- 其控制节点变为 uncontrolled；
- 不向攻击者继承棋子、队列或资源；
- 投降消失不计为击杀、掉落、经验或玩家战利品；
- 后续轮次不再为该阵营分配行动阶段。

### 14.3 VictoryGroup 与封闭目标类型

**LOCK**

Demo 2 使用三个 VictoryGroup：

- Player；
- Independent Boss；
- Pact Boss A + Pact Boss B。

首批目标只允许登记过的封闭类型，例如：

- AllHostileVictoryGroupsEliminated；
- VictoryGroupEliminated；
- CommandPostCaptured；
- optional RoundLimitScore。

目标求值必须是纯函数，输入为规范化战略状态，输出稳定 reason code 和确定顺序。禁止：

- 通用任意 AND/OR 表达式 DSL；
- XML 中嵌入脚本；
- 调用 root 全局函数；
- 由目标直接发奖励、写存档或跳关。

技术 Unknown、receipt 校验失败或通信中断只能进入可恢复/需处理的技术状态，永远不能伪装成玩家失败。

### 14.4 外层结果

**LOCK**

内部 WarlordResult 需要从一开始结构化并版本化，至少保留：

- outcome；
- winningVictoryGroupId；
- reasonCode；
- roundIndex；
- surviving factions；
- captured command posts；
- commander states；
- accepted receipt digests；
- optional metrics summary。

V1 外层只做简单映射：

- victory → CompleteSubStage；
- loss 或规则 draw → FailStage；
- technical unknown → Suspended/Unknown，不结算。

后续线性关卡需要分叉时，再增加由 GameStage 消费结构化结果的明确规则；本轮不扩大到通用剧情分支系统。

## 15. 动作关卡、经济与时间

### 15.1 动作体验复用

**LOCK**

`StageManager` 物化的临时普通 `StageInfo` 应复用普通推关的：

- 玩家控制与装备；
- 单位和场景内容加载；
- 战斗、掉落与主角受伤体验；
- 关内复活能力；
- 物理战利品进入外层 StageRunSession 的既有生命周期。

它不能启动第二个顶层 GameStage、inner `StageRunSession`、嵌套奖励或二次结算。对玩家来说 “进入下一张动作图” 与 “从沙盘切入节点交战” 的操作体验应尽量一致，差异只在返回目标是原战略会话。

### 15.2 双经济严格隔离

**LOCK**

- WarlordGold、战略生产和战略补给只存在于战棋 Scenario；
- 玩家金币、K 点、物资、装备和物理掉落继续由普通关卡/存档权威处理；
- 不把战棋造价映射为玩家扣款；
- 不因战略棋子阵亡直接删除玩家拥有的角色、宠物或装备；
- 现有 pet economy observation 继续只读，不能暗中升级为结算入口。

玩家亲自参加动作交战时获得的实际掉落，仍按普通推关进入同一个外层关卡生命周期；它与 WarlordGold 无关。

### 15.3 时间

**LOCK**

战棋默认使用战略轮，不消耗普通实时 TimePool。线性关卡中需要严格短时限的内容仍留在 Action SubStage；战棋负责长期、多线和多视角演出。

V1 不做耐久 checkpoint/continue。必须先保证单次运行内的冻结、动作交战、恢复和失败退出正确；正常推关尚未形成继续能力时，不为战棋单独建设另一套。

## 16. 沙盘皮肤、3D 素材与资产治理

### 16.1 规则与表现完全分离

**LOCK**

MapDefinition 只描述与阵营无关的规则拓扑和节点语义；WarlordScenario 通过 nodeRef 赋予初始控制和驻军；MapVisualDefinition 再以 nodeRef 为键描述坐标、地表、路线样式、地标锚点和镜头边界；Theme 描述颜色、雾、灯光、网格和材质族；AssetCatalog 解析真实文件。

引用方向必须保持：

~~~text
WarlordScenario → mapRef / nodeRef
MapVisualDefinition → mapRef / nodeRef
MapDefinition 绝不 → MapVisualDefinition / Theme / AssetCatalog
~~~

同一 MapDefinition 可以绑定 desert、tundra 或剧情专用视觉。换 Theme 不改变：

- 节点邻接；
- 容量和攻宽；
- 阵营关系；
- AI；
- 战斗结果；
- rulesDigest。

rulesDigest 只覆盖规则 MapDefinition、Scenario 规则和被引用的规则 profile；MapVisualDefinition、Theme、visualAnchor、模型和贴图只进入 presentationDigest。移动地标锚点不得改变规则 replay identity。

### 16.2 AssetCatalog 最小元数据

**LOCK**

每个 3D/贴图资产至少记录：

- assetId 与 schemaVersion；
- sourcePath 或运行时 URI；
- contentHash；
- assetKind；
- authoringUnit 与 runtimeScale；
- upAxis、forwardAxis、pivot；
- bounds 或安全占位尺寸；
- LOD 链；
- material/texture refs；
- provenance、license 或内部来源说明；
- fallbackAssetRef；
- 可选性能标签，如 triangleClass、textureClass。

MapVisual 和 Theme 只引用 assetId，不直接散落路径。缺失资源必须有程序化或低成本 fallback，不能让规则会话无法启动。

### 16.3 首版素材策略

**PROVISIONAL**

- Demo 1 继续优先使用程序化地形、低多边形地标和共享材质；
- Demo 2 先完成规则、LOD、instancing 和预算，再扩大 GLB 资产量；
- 独立模型进入正式资源链前，统一比例、pivot、轴向、LOD 和来源；
- 新鲜动作场景可以复用 AssetCatalog 下的不可变资源缓存，但不能复用可变场景实例。

## 17. AI 配置

### 17.1 三层 profile

**LOCK**

- ControllerProfile：战略目标权重，如守指挥所、扩张、夹击、保存指挥官、追击弱敌。
- UnitTacticalProfile：特定棋子在动作交战中的行为倾向和能力选择。
- EncounterDirectorProfile：某类地图/场景的出生、目标、节奏和特殊表现策略。

所有 profile 都是已登记、版本化实现的引用。XML 可以调有限权重、阈值和开关，但不得嵌入函数名、脚本片段或任意表达式。

### 17.2 合法命令枚举是公共规则能力

**LOCK**

核心提供 enumerateLegalCommands(factionId, state)，并保证：

- 只返回 validator 会接受的命令；
- 顺序稳定；
- 支持固定预算与提前截断；
- 玩家预览、AI 和无头模拟共享；
- 大地图下基于本阵营边界和局部邻接生成。

AI policy 只对合法候选评分，不重新实现容量、关系、AP、过境、指挥所和编组规则。

## 18. 两个 Demo 的产品定义

### 18.1 统一测试入口

**LOCK**

现有 `其他 → 测试 → 军阀演习测试` 改造成白名单 GameStage 测试选关目录；它不注册进默认生产目录：

- Demo 1：教程；
- Demo 2：四阵营大战役；
- 后续场景按 stable stageId 扩展。

每个条目调用正常 EnterGameStage，不直接构造 GameState。目录只接受固定 `catalogId=warlord-game-stage-test`，未知或缺失 catalogId 回落默认生产目录；短显示名不改交接给 AS2 的精确关卡名。开发 seed、fixture resolver、强制状态和 QA 注入只留在隐藏 dev harness 或专用测试存档。

测试完成转正式时，Slice 7 才改默认选关/NPC 副本任务对 stable stageId 的可见入口和授权，不复制 XML、不改规则、不换奖励版本。上线前仍需做一次窄范围 NPC 真实旅程，验证授权、进入、返回和奖励；它不替代前面的规则与 AS2 回归。

### 18.2 Demo 1：教程战术图

**LOCK**

目标：

- 保留现有九节点数量与拓扑，以逼仄、短路线和低同时信息量承担最初教程；
- 继续使用两阵营，但运行在已经泛化的 N 阵营核心上；
- 优先教授移动、节点容量、攻宽和基础交战；编制、Formation 和预备队按教学节奏逐项引入；
- 主角参与可以作为后段教学，但不要求一次灌输全部 Boss/外交规则；
- 利用狭窄节点让分组、窄阵地和重新汇总的作用快速可见；
- 使用真实 GameStage → StageManager → Warlord SubStage → 临时普通 StageInfo 路径。

同一份九节点 Demo 1 既是产品教程，也是迁移回归场景；只允许一套配置和一套通用运行时，不另建 legacy 产品路径。

### 18.3 Demo 2：四阵营大战役

**PROVISIONAL**

目标：

- 64～120 节点，首张代表性地图建议 72～96；
- 玩家、Itinerant、Gazer、Surveyor 各指挥约一个排，总体形成连级战争；
- 四个 Faction、四个 Controller、三个 VictoryGroup；
- 一个独立 Boss 对所有方 hostile，另两个 Boss 相互 allied 并共同敌对玩家和独立 Boss；

- 指挥所斩首、Boss 折损、重新生产、主角 Downed/撤离/重部署、亲临一线 AP 特权；
- 多阵营按固定 block phase 顺序逐方行动；
- 同盟仅允许受限过境，不共同驻军、不提供数值支援；
- 能构造 “玩家连续赢得局部动作战斗，却因战线/指挥所而输掉战略关卡” 的验收剧本；
- 约 100 节点的独立产品夹具验证规模合同，不要求首张剧情图机械等于 100。

## 19. 玩家语义可读性、帮助与零基础审核

### 19.1 默认玩家模型

**LOCK**

设计、开发和审核必须假定首次进入的玩家：

- 完全不懂英文，不能从 AP、AUTO、EXACT、LOD、R/B、G 等缩写推断含义；
- 没玩过战棋，不知道回合、行动点、攻宽、驻军容量、控制权和预备队是什么；
- 不知道开发团队认为理所当然的鼠标操作、颜色惯例或胜负条件；
- 只看到当前产品 UI 和可以随时打开的玩法帮助，没有开发者在旁口头解释；
- 可能先点错、先查看不可行动目标，或者在忘记教学后重新打开帮助。

在这个前提下，如果核心循环必须由测试员或开发者补一句才能继续，默认判定为产品表达缺陷，而不是玩家缺乏常识。

生产 UI 在任何可操作状态都应能回答：

1. 我是谁，哪些部队归我指挥？
2. 这一关怎样获胜，什么情况会失败？
3. 现在轮到谁，我现在可以做什么？
4. 为什么这个操作不能执行，我接下来可以怎么改？
5. 确认后会消耗什么、哪些部队会行动、是否会进入战斗？

### 19.2 内部术语与玩家语言分离

**LOCK**

内部模型可以继续使用稳定英文 ID 和工程术语，但生产界面必须通过 PlayerTextCatalog 投影中文。不得把内部枚举、reasonCode、profileId、nodeId 或调试异常直接显示给玩家。

首版玩家词汇建议固定如下：

| 内部概念 | 玩家界面 | 表达要求 |
| --- | --- | --- |
| Faction | 势力 | 同时显示中文势力名；不只显示颜色或单字母 |
| CommandElement | 部队 | 聚合后可称“编队”，但不能在同一页面随意混用棋子、单位、兵团 |
| TaskGroup | 临时编队 | 帮助中用一句话解释“把同一据点的部队临时合在一起行动” |
| FormationProfile | 阵型 | 显示实际效果，不只显示 profile 名 |
| ActionPoints / AP | 行动点 | 生产界面不得只写 AP |
| CommandLoad | 行动消耗 | 在命令预览中写“需要 X 行动点”，不要求玩家记住内部名词 |
| DeploymentSize | 部队规模 | 单位卡显示“规模 X”；节点显示“驻军 X / 上限 Y” |
| garrisonCapacity | 驻军上限 | 不单独显示裸 capacity |
| attackWidth | 本次最多投入 | 进攻预览显示“已投入 X / 最多 Y”，不只写“攻宽” |
| field commander bonus | 亲临一线 | 明写“下回合额外获得 X 行动点” |
| allied / neutral / hostile | 友军 / 中立 / 敌对 | 除颜色外必须有文字或图形加文字 |
| VictoryGroup | 共同胜负 | 帮助中解释哪些势力共同获胜或失败，不在主界面暴露内部名 |
| WarlordGold / G | 军费 | 显示“军费 X”，不能只显示 XG |
| Unknown receipt | 战斗结果尚未确认 | 明写“已暂停结算，不会判负”，不能显示技术术语 Unknown |
| AUTO / EXACT | 自动安排 / 指定据点 | 两种模式都用完整中文按钮 |

三名 Boss 的正式中文 displayName 固定为吴豫（Itinerant / cardId 111）、袁望（Surveyor / cardId 113）、阎凝儿（Gazer / cardId 112）。玩家无需识别英文才能区分人物。

一个概念只使用一个主称呼。若确需同义词，第一次出现必须写明关系；不能在“部队、棋子、单位、编队”之间无规则切换。颜色、图标、位置和动画只能加强含义，不能独自承担含义。

### 19.3 简短文案合同

**LOCK**

主操作面不堆百科说明。每条文案优先采用：

~~~text
动作或状态 + 直接结果
原因 + 下一步
~~~

推荐形式：

- 按钮：“进攻北部关隘”“结束本回合”“自动安排生产”；
- 预览：“消耗 2 行动点；3 支部队参战”；
- 容量：“已投入规模 5 / 最多 3；请减少参战部队”；
- 失败原因：“行动点不足，还差 2 点。可减少部队或结束回合”；
- 过境原因：“友军据点只能路过。请选择后方的我方或无主据点”；
- 编组原因：“只能重组位于同一据点的部队”；
- 重部署原因：“主角只能从我方指挥所重新出动”；
- 技术暂停：“战斗结果尚未确认，已暂停结算；不会因此判负”。

禁止只写：

- “非法命令”；
- “操作失败”；
- “条件不足”；
- “错误代码”；
- 没有单位的 3/5、+2、R2/B3；
- 玩家不知道如何修正的红色叉号。

行动按钮建议使用 2～8 个中文字符的动宾结构；即时原因默认不超过 1024×576 下两行。超过两行的解释转入帮助锚点，但当前界面仍要保留最关键原因和下一步。

合法命令确认前至少显示：

- 选中了哪些部队以及它们在哪里；
- 目标节点与目标势力；
- 消耗多少行动点；
- 实际会行动的数量和总规模；
- 是否触发动作战斗；
- 因容量或攻宽无法出动的部队。

系统不能静默裁掉部分选择。若只有 X/Y 支部队会行动，必须在确认前明显显示，并允许玩家返回修改。

不可执行的核心动作原则上保持可见，并附原因和帮助入口；不能通过隐藏按钮让玩家误以为功能不存在。只有与当前 Scenario 完全无关的机制才可以不展示。

禁用原因不能只放在鼠标悬停 title 中。原生 disabled 按钮通常无法获得键盘焦点；若玩家需要读取拒绝原因，应使用可聚焦的 aria-disabled 控件并拦截提交，或在旁边提供始终可访问的原因说明。

### 19.4 三层帮助结构

**LOCK**

帮助不是一次性弹窗，而是三层互补入口：

1. **就地提示**：紧贴当前步骤，只说下一件事。例如“先选择一支我方部队”。
2. **概念解释**：点击“行动点”“驻军上限”“本次最多投入”等词即可看到一到两句解释和一个当前数值例子。
3. **玩法帮助**：随时可打开的完整目录，关闭后回到原战略状态，不丢失选择、镜头、编组或命令预览。

玩法帮助首页按玩家任务组织，不按代码模块组织：

- 这关怎样获胜；
- 一回合怎样操作；
- 怎样移动和进攻；
- 地图上的颜色、图标和数字表示什么；
- 怎样编组、拆分和选择阵型；
- 指挥官、指挥所、倒地和重新出动；
- 为什么有些命令不能使用；
- 当前场景的势力关系和行动顺序。

页面顶部先用一屏回答“目标、回合、三步操作、失败条件”，进阶规则再分层展开。不要把几十段规则一次塞给首次玩家，也不要依赖 hover 才能阅读；鼠标、键盘和未来手柄入口应能到达同一解释。

Scenario 通过 helpProfileRef 选择本关帮助覆盖层，通用规则帮助由 rulesVersion 绑定。Demo 1 只展示当前已经引入的机制；Demo 2 再增加四方关系、胜利组、指挥所和大地图导航。

### 19.5 Demo 1 教学行为

**LOCK**

九节点的逼仄地图负责降低空间认知负担，UI 教学负责消除规则常识假设。Demo 1 的首次流程至少依次让玩家亲手完成：

1. 识别我方、敌方、当前目标和失败条件；
2. 看懂当前回合与剩余行动点；
3. 选择一支我方部队；
4. 区分可移动、可进攻和不可到达节点；
5. 看懂一次命令的消耗与实际出动数量；
6. 完成一次移动或进攻；
7. 主动结束回合；
8. 从战斗结果返回沙盘并理解节点发生了什么变化。

教程步骤可以跳过，也必须能从玩法帮助中重新打开。跳过只关闭引导，不改变规则和胜负条件。

TutorialProfile 只允许登记过的固定步骤类型、messageKey、helpAnchor 和已存在的游戏事件完成条件；不得发展成任意脚本或另一套目标 DSL。若教程暂时限制某个命令，界面必须明说“完成当前教学后开放”，不能让 validator 无说明拒绝。

### 19.6 原因码与帮助配置

**LOCK**

规则层返回稳定 reasonCode 和结构化参数，不返回准备直接展示的开发者英文句子。Presenter 通过 PlayerTextCatalog 生成：

~~~text
reasonCode
  → 中文短原因
  → 可执行的下一步
  → helpAnchor
  → 辅助技术可读文本
~~~

每个生产可达的 reasonCode 都必须有中文映射和帮助锚点。技术日志可以保留原始 code、ID 和英文诊断，但玩家通道不能泄漏这些内容。

PlayerTextCatalog、HelpProfile 和 TutorialProfile 需要自己的 schemaVersion 与 terminologyVersion。构建时校验它们与 rulesVersion 的兼容关系；规则新增原因码、状态或动作而没有玩家文案时必须 fail closed，不能回退显示内部 code。

### 19.7 已知迁移债务

**LOCK FOR MIGRATION**

当前军阀源码和维护文档仍可见 R/B、G、AP、AUTO/EXACT、攻宽/防宽以及部分内部 LOD/identity 术语。这些可以继续存在于源码变量、测试选择器、日志和工程 harness，但生产玩家界面需要迁移为完整中文：

- R/B → 中文势力名或“我方/敌方”；
- G → 军费；
- AP → 行动点；
- AUTO/EXACT → 自动安排/指定据点；
- 攻宽/防宽 → 本次最多投入/驻军上限或完整解释；
- LOD、identity、reasonCode → 只留工程通道。

迁移审核不能只搜索可见正文，还要覆盖 title、aria-label、toast、对话框、空状态、错误路径、帮助页和 WebGL fallback。

### 19.8 自动语义门

**LOCK**

自动审核至少包括：

- 玩家字符串清单：每个生产可达文本有 audience=player 和中文来源；
- 英文字母/缩写扫描：默认阻断，物理键名或专有商标必须列入小型 allowlist，并在同处提供中文含义；
- raw ID 扫描：nodeId、profileId、reasonCode、枚举值和异常堆栈不得进入玩家 DOM；
- reasonCode 覆盖：每个 validator 拒绝原因都有“原因 + 下一步 + helpAnchor”；
- 术语一致性：同一概念不出现未经登记的多个主称呼；
- 目标覆盖：当前 Scenario 的胜利、失败、行动顺序和特殊规则都有帮助入口；
- 1024×576、1366×768、1920×1080 的正文、按钮、toast 和帮助页无截断、遮挡或仅 hover 可见；
- 颜色独立：去色或色觉差异下仍可通过文字、形状和图标区分势力与合法性；
- 键盘可达：帮助、词义、禁用原因、确认和返回都能访问；
- fallback 一致：WebGL fallback 与 Three 路径使用同一玩家词汇和原因映射。

自动门只能证明字符串和界面契约完整，不能证明真实玩家已经理解。

### 19.9 零背景首次游玩审核

**LOCK**

语义可读性必须有独立于开发者自审的首次游玩观察。参与者按本节假设筛选；主持人只能处理启动、崩溃等技术问题，不能解释规则、指出按钮或翻译术语。参与者可以自由使用 UI 和玩法帮助。

核心任务：

- 进入后能指出我方、当前行动方、关卡目标和至少一个失败条件；
- 不经口头指导完成选择、移动或进攻、查看结果和结束回合；
- 遇到一次行动点或容量不足时，能依据界面原因自行修正；
- 能从帮助界面解释行动点、驻军上限和指挥所中的当前相关概念；
- 关闭帮助后回到原状态，继续完成操作；
- Demo 2 还需识别四方关系、共同胜负和受到威胁的指挥所。

审核记录应保留：

- 玩家原话，而不是开发者事后概括；
- 第一次停顿、误点、回退和打开帮助的位置；
- 哪个词、数字、颜色或图标导致错误推断；
- 是正文解决、帮助解决，还是最终需要主持人解释；
- 修订后对同一任务的 fresh 复测。

任何核心任务需要主持人解释，都视为尚未通过，不用满意度平均分掩盖。高级策略选择可以不会，但基础规则和下一步不能靠猜。

这是一项轻量、面向真实理解的专项门，不新增全局发布状态机。测试报告记录 semantic_readability=passed/failed 和具体阻断项即可。规则、术语、帮助结构或首次入口发生实质变化后需要 fresh 复测；纯 Theme 换色不自动触发完整规则复测，但仍需颜色独立检查。
