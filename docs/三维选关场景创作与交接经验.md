# 三维选关场景创作与交接经验

2026-09-21 整理。案例为黑铁会总部从 Three.js 布局原型、R7 美术交接、R8-I1-H1 回包到 E4 游戏选关界面的创作过程；最后核对代码基线：commit `f5577417571fbb8dd6fd389442e02fb97becea7c`。

本文保存可复用的方法、失败原因和适用边界。总部采用的具体空间决策以 [R7 工单](黑铁会总部R7布局与美术交接-2026-09-20.md) 为准；镜头、环境和标签迭代见 [E1—E4 集成记录](黑铁会总部游戏集成候选-2026-09-20.md)。当前参数以代码和资产配置为准，本文不另建配置源，也不将本案例的审美反馈推广成所有场景的硬规则。

## 1. 从资产依赖决定制作顺序

选关页顺序不必等于资产制作顺序。基地车库的堕落城需要把黑铁会总部作为地标，先确定总部的轮廓、尺度关系和建筑语言，再放回城市，有助于避免两个场景各自造出一个总部。

复用对象宜拆为建筑群本体、所属地形与交通接口、当前选关镜头需要的外围环境。城市远景可以简化总部本体，不能直接把为总部独立选关页填画幅的整个外围复制进去。可编辑对象、渲染批次与远景版本承担不同职责，不用合批后的运行模型取代编辑源。

早期用 Three.js 建立能转动、投影节点、比较镜头的布局原型，适合快速验证体量与关系；Blender 精修在布局和默认构图已有可验收底稿后接入。原型有视觉效果不代表材质、语义选择、生命周期和游戏入口已经集成。

## 2. 分开推演剧情顺序、实际交通与选关入口

| 层面 | 需要回答的问题 | 本案的教训 |
|---|---|---|
| 剧情顺序 | 玩家分几次行动，哪些行动之间回基地或去别处？ | 边缘、三堂、总堂不是一口气走到底的单次爬塔；不能把所有关卡强制串成唯一通路 |
| 空间交通 | 守卫、干部、补给、盟友和撤退分别怎么走？ | 后勤通道、退路的存在本身不是攻关漏洞；围墙与高差需要有对应的门、坡道和管理解释 |
| 选关语义 | 哪个 ID 指向哪个设施、范围或事件？ | 内外关卡需能区分；总部与遇袭事件可共用场所，不必制造第二套建筑或切换状态 |

读原关卡景色同样重要：外围、边缘明确是街区时，纯粹把每关变成一层楼会损失原有空间含义。总部最终采用要塞化企业园区与四层台地，表达逐步深入和抬升；三堂仍是分工部门，台地高度不自动证明组织上下级关系。

主线箭头要解释真实可走的关系。遇到明显绕行，先固定起终点，比较路径长度、入口朝向、门墙和高差，再判断绕行是否有防御、礼仪或地形理由。不要先画一条好看的折线，再补墙替它辩护；也不要以最短直线为由删除所有防御折转。已修正的具体路径与审阅裁决保留在 R7 工单中。

## 3. 先解释空间用途，再补建筑密度

空地不都需要填楼。先判断它是集散、操练、货运转弯、防火间隔、仪式前场还是单纯未设计的留白，再决定尺度与边界。宏伟感可以来自主次体量、层层抬高的台地、连续挡墙和门院进深；只加高主楼或密集堆房，会掩盖交通与组织关系。

本案把三堂分工落实到相应生产训练设施：翅虎堂药物与医务，火凤堂刑法审讯与看管，黑龙堂修造、锻造及物资训练。设施宜能从屋顶、院落、附属设备和运输接口辨认，不要求每种用途都做成一座宏大的独栋。干部住宅、客院与清修院也需要服务对象和通行关系，不能仅作为填空建筑。

仪式空间按参与规模和政治地位分层：中心日常公共坛承担聚集，最高台地的祖堂承担重大仪式与权威象征，行政交通走侧翼。这样既避免日常人流穿过总部，也区分了“公共设施受损”与“核心合法性象征失守”。这是一项空间设计解释，不据此改写剧情中的领土归属、祖先身份或反攻动机。

总部祖堂采用深檐、门槛、供案与内向神龛，替代容易读成升旗台的高台和旗杆。旧地下工程与建筑内的钻头井室则解释遇袭关卡复用总部；“审判日预埋设备被诺亚激活”等叙事仍按提案处理，不能因为做了模型便升级为实装设定。

## 4. 把攻击审阅当作找反例，而非投票验收

审阅输入宜同时给出剧情行动批次、路线起终点、地形高度、门墙开口、服务流线、默认视角与节点覆盖。分别寻找“玩家为何绕路”“守卫如何使用此门”“补给如何上台地”“标签究竟指哪栋楼”等具体反例，比笼统询问是否合理更有效。

本案 SWE2 的已完成审阅主要依据文本和坐标，不是实际游戏中的进攻模拟，也不等于看过所有图像。采纳意见前回到模型、源码与关卡材料核对：允许撤退的门不必然失效，相同坐标分量不证明路径相交，输入摘要未提到某设施也不证明模型中没有它。失败或未完成的调用不能算作独立通过票。

有价值的长期记录是“证据—问题—裁决—修改”，以及不采纳的理由；原始多模型对话作为背景资料按需查阅，不让模型共识替代主创判断。发起外部集群任务仍按当次授权执行，本文不建立自动调用服务的规则。

## 5. 默认镜头与界面应进入灰盒阶段

本案较晚才专门验收默认视角，导致美术回包后再次调整取景。后续布局原型应尽早叠加实际选关标题、节点、简报和返回按钮，在实际横向窗口内看效果，同时保留建筑近看视角。模型查看器里壮观，不等于玩家首次打开选关就能看清。

方形园区放进长方形画幅时，先比较俯角、方位和取景范围，再用有职能的外围填充剩余区域，例如低层街区、物流设施、道路和后部地形。不要拉伸园区，也不要默认缩小主体以容纳所有外景。本案最终采用原镜头方向放大，并让外围作为独立环境模块；具体镜头以生成后的 [场景数据](../launcher/web/modules/stage-select/stage-select-blackiron-data.js) 为准。

宗教和组织符号可以进入街区结构，而不必铺成地面徽章。E2 的完整圆纹与太极表达被用户认为过于刻意，E3 改为不闭合、中心与宽度不同的弧形街道，配合错落建筑、局部挡墙和排水走势，在方形核心外提供隐约的圆势。大门进路仍需直观。经验是让符号服务空间用途，不能把这一反馈理解成所有直白宗教标志都不可用。

比较镜头、环境、标签时尽量分开变量，保留少量可对照候选；默认镜头、世界锚点和二维回退图要成套核对。原美术包的镜头记录是历史输入，不能覆盖后续已采用的 E2—E4 决策。

## 6. BM-009：固定光影与自发光分工

美术回包的 BM-009 适用于固定夜景、风格化建筑沙盘：离线计算方向光、局部遮蔽与有限的窗光溢出，写入表面顶点色；主体使用 unlit 材质，窗与字牌独立处理自发光。屋面与石材的低对比纹理提供表面尺度。先在关闭 bloom 时检查基本层次，再调辉光，避免用后处理掩盖结构不清。

源脚本 `经验/脚本/build_style.py` 使用 BVH 射线、光照缓存与 `BakeColor` 顶点色，支持上述方法描述。接收端本轮核对的是源码与回包，未在本机重新执行 Blender 烘焙。它是面向固定观看条件的美术光照方案，不是完整物理全局光照；调整窗光亮度不会自动重算周围已烘焙的溢光，昼夜变化或移动光源需要另行设计。

回包中值得保留的排错经验：

- 发光窗不能成为遮挡自身溢光射线的障碍物。
- 共面屋坡采用一致采样，避免三角划分造成对角明暗缝。
- 高差先通过台地顶面、踏步、立面和挡墙的明暗关系读出来，不只依靠增加面数。
- 大坐标或异常距离检查出现 float32 疑点时，用更高精度复核，不直接放宽几何阈值。
- 保留编辑对象与合批来源映射；案例中的调色数值、灯窗数量和面数不是后续地图的通用标准。

生产材质与显示实现分别见 [资产配置目录](../launcher/web/assets/stage-diorama/blackiron-hq/) 和 [场景渲染器](../launcher/web/modules/stage-select/stage-select-blackiron-scene.js)。接入其他渲染环境时检查色彩空间、色调映射与后处理，避免再次照亮已经烘焙明暗的主体。

## 7. BM-010：语义选择独立于渲染合批

把“入口 → 设施 → 子区域 → 原始对象集合 → 锚点与聚焦镜头”作为选择关系维护。材质相同不代表语义相同，合批后的一个 mesh 也不必等于一栋建筑。回包将选择覆盖面和轮廓独立导出，只显示当前入口对应部分，避免用整个合批 mesh 的高亮指代一个小院。

选择集合可以跨越渲染批次，例如同一设施的招牌基座和墙体；强自发光窗与文字则宜避免被覆盖色洗掉。内外区域按实际语义检查分离；总堂与遇袭事件共用部分对象是有意例外，不应为了“集合必须全不相交”去造假几何。原始参考资料中的地点也不能直接新增为选关入口，当前 ID 仍由游戏源数据拥有。

几何覆盖与来源校验能证明选择面对应哪些原对象，不能单独证明它符合玩家对建筑范围的理解。鼠标与键盘聚焦都需要联动检查。独立展示页的解锁状态和点击动画不能成为游戏权威；锁定、难度、简报与进关请求沿用正式面板数据和协议。

关闭场景时一并管理未完成加载、动画帧、监听器、尺寸观察器、控制器、几何、纹理与后处理资源；已丢失的 WebGL context 不重复强制丢失。生产生命周期见 [diorama 控制器](../launcher/web/modules/stage-select/stage-select-diorama.js)。

## 8. E4：标签不重叠仍可能指错楼

本案测试反馈暴露了只约束标签方框的不足：引线穿过另一标签、两条线交叉，都会造成所属建筑不清。布局需要同时检查标签—标签、标签—节点、引线—标签与引线—引线的关系，并给相邻堂区稳定的优先放置侧。

地图标签可使用短称，但无障碍名称、悬停资料、简报和实际进关仍保留正式全称与原 ID。连接线采用亮色主线加深色描边，并在悬停和键盘聚焦时增强；线段从节点边缘连到标签边缘，且不拦截点击。这样识别不只依赖细线与背景的偶然对比。

具体排版实现集中在 [生成器辅助模块](../tools/lib/blackiron_presentation.py)，对应检查见 [总部选关测试](../tools/test-stage-select-blackiron.js)。固定视图下的碰撞检查和浏览器结果只覆盖所测条件，不能替代玩家实际窗口中的辨识验收。本案的标签尺寸与偏移是当前画面的参数，不是下一张地图照搬的模板。

## 9. 交接应保留决定的理由与可继续编辑的源

完整交接指任务相关闭包完整，不等于复制整个游戏仓库或把整段聊天当施工指令。可按以下职责组织已有材料，不需要每轮都重新建立全套文档：

| 材料 | 防止丢失的信息 |
|---|---|
| 当前工单、采用版本和待验收问题 | 什么已经决定、允许改什么、接下来由谁判断什么 |
| 关卡 ID、名称、任务顺序、场景参考与世界观出处 | 区分现役事实、设计解释、待定提案；完整保留与本任务相关的材料 |
| 编辑源、贴图、生成脚本、运行导出与对象映射 | 能继续施工，也能核对哪些结果来自哪个源；仅有盒体 JSON 不能替代完整模型 |
| 坐标、相对尺度、入口锚点、摄像机与固定预览 | 避免工具换轴、默认构图和交互位置漂移；本案的相对单位不套用人形资产的米制标尺 |
| 决策摘要、已否决方案及原因、必要的交流与审阅原文 | 后续人员理解为什么这样做，避免重走已经否决的路线 |
| 文件清单、哈希、重建说明与已知限制 | 分清编辑源和派生物，验证搬机器后能读取；记录材质、选择面、面数和包体各自口径 |
| 分层验证结果与人类反馈 | 分清发送端 Blender 检查、本地浏览器检查、游戏进关与实际审美反馈 |

传输包在新目录验证，预览依赖尽量随包或明确说明，避免依赖原盘符与临时服务器。美术机回包后，把可复用经验归纳进项目文档，把当前配置合入其权威文件；原包继续作为来源存档。脚本成为长期生产工具时再迁入受维护的工具入口，不把外部一次性脚本未经核对直接变成构建流程。
